# 知库彻查 · 覆盖台账

> 用途：把"查过了"从主观变成可计数。**每轮彻查开工前先读本文件，只碰"未测"项；收工必须更新本文件并给出覆盖数字。**
> 状态取值：`未测` / `单测` / `E2E` / `门禁`(pre-commit 或 CI 拦得住) / `人工` / `不适用+理由`
> 严重度：`数据丢失` > `功能错误` > `交互误导` > `美观`

**P0 填写口径（2026-09-23，重要）**
- P0 只做**枚举**，不执行任何行为验证。因此**除 §1 中"已有 smoke 真实发 HTTP 请求"的端点记为 `单测` 外，本轮所有格子一律 `未测`**。
- §1 `有测试?` 的判定标准是机器可复现的硬标准：该路径**以字面量形式出现在 `tests/*.py` 的真实 HTTP 调用里**（`app.test_client()` + `.get/.post("...")`），且调用点附近有 `check(...)` 断言。字符串出现在注释/文档里不算。
- §2 的四态列（正常/空/加载/失败）本轮**一律记 `未测`**，包括结构上不适用的控件——不设主观豁免，避免"我觉得它没有空态"式推断混进结论。四态由 P4/P8 填写。
- §4 的"可执行化?"回答的是"**现在是否已有**可跑断言"，**不是**"理论上能否做到"。因此 P0 阶段 8 条全为 `否`；P2 的产出目标是把它们变成 `是`。
- 本轮**未执行**任何 UI / 服务器 / 网络 / 装包操作；结论全部来自只读命令输出与代码通读。

## 9. P0 口径偏差与存疑（本轮新增，供后续轮次核对）

> 记录的是**手册/台账描述与代码事实不符**之处，不是产品缺陷。列在此处避免下一轮又按错前提去查。

1. **`create_app()` 有副作用**：`app.py:102` 会 `index_is_stale()` → 可能 `build_index()` 写 `indexes/`；且 `app.py:268` 模块级 `app = create_app()` 一 import 就跑。为守"只读"约束，本轮所有枚举命令均把 `KB_ROOT` 指向 `tempfile.mkdtemp()` 的一次性目录并在同进程 `shutil.rmtree` 清理，**仓库 `indexes/` 与 `content/` 零写入**。后续轮次若直接照手册命令跑，会真实重建本机索引——功能上无害（派生缓存），但请知悉。
2. **手册 P0 第 2 条写"右栏五页签"，代码实为 4 个**（目录/标签/备注/双链，`workbench.html:77-80`）。多出来的那个不存在，别去找。
3. **手册 P0 第 4 条把 `_safe_rel` 归到 `store.py`，实际不在**：单一实现在 `app.py:163` 的闭包 `safe_rel`，`routes_edit.py:33` 与 `routes_files.py:34` 只是 `_hooks()["safe_rel"]` 的薄包装（同一实现三处调用点，**无逻辑重复**，已逐行比对）。P3 做性质测试时应直接测 `app.py` 的那个闭包或经 HTTP 打。
4. **环境与手册不符**：手册"仓库现状事实"表写 Node v24.19.0、本机实测 `v24.18.0`；手册称有 `.python\` 便携运行时，本机**不存在 `.python/`**，系统 Python 3.13.7 缺 `tokenizers`/`onnxruntime`。
