### **1) 设计URL短链服务**

**需求分析**
*   **核心功能**：
    1.  **短链生成**：给定一个长URL，生成一个唯一的、更短的URL（如 `bit.ly/xyz123`）。
    2.  **重定向**：用户访问短链时，立即重定向到原始长URL。
    3.  **可选自定义别名**：允许付费用户创建自定义短链（如 `bit.ly/my-brand`）。
*   **非功能性需求**：
    1.  **高可用性**：服务不能中断。
    2.  **低延迟**：重定向必须极快（<100ms）。
    3.  **高吞吐**：支持每秒数万次读取请求。
    4.  **数据持久化**：链接映射关系不能丢失。
    5.  **唯一性**：必须保证生成的短链码全局唯一。

**容量估算**
*   **假设**：1亿日活用户(DAU)，平均每人每天创建1条短链，读写比10:1。
*   **写QPS**：100M / 86400 ≈ 1160 QPS。
*   **读QPS**：1160 * 10 ≈ 11,600 QPS。
*   **存储**：每条记录（长URL + 短码 + 元数据）约500 Bytes。1亿条/天 * 30天 * 500B ≈ 1.5 TB/月。考虑到URL去重和压缩，实际存储需求可优化。
*   **带宽**：平均长URL 500 Bytes，读带宽 ≈ 11,600 * 500B ≈ 5.8 MB/s。

**高层架构图（文字描述）**
1.  **客户端**：通过API与后端服务交互。
2.  **API网关**：负责负载均衡、认证、限流。
3.  **应用服务器集群**：处理核心业务逻辑。
4.  **缓存层**：如Redis，存储热点短码到长URL的映射，极大减轻数据库读压力。
5.  **数据库集群**：持久化存储所有映射关系。主从分离，读写分离。
6.  **ID生成器**：独立服务，用于生成全局唯一的短码（如Snowflake或基于计数器+进制转换）。

**详细设计**
*   **数据模型 (SQL)**：
    ```sql
    CREATE TABLE urls (
        id BIGINT PRIMARY KEY, -- 内部自增ID，用于生成短码
        short_code VARCHAR(10) UNIQUE NOT NULL,
        original_url VARCHAR(2048) NOT NULL,
        user_id INT,
        created_at TIMESTAMP,
        expires_at TIMESTAMP
    );
    -- 索引：short_code (B-Tree), original_url (Hash，用于查重)
    ```
*   **API设计**：
    *   `POST /api/v1/shorten`，Body: `{"long_url": "...", "custom_alias": "..."}` -> `{"short_url": "..."}`。
    *   `GET /{short_code}` -> `301/302` 重定向。
*   **核心算法 - 短码生成**：
    1.  **计数器+Base62编码**：从分布式计数器（如数据库自增ID）获取一个唯一ID，然后将其转换为62进制（a-z, A-Z, 0-9）。优点：简单，无冲突。缺点：可预测，安全性较低。
    2.  **预生成+哈希**：预生成一批短码存入数据库，创建时取一个未使用的。或者用MD5/SHA1哈希长URL，取前7位。需要处理冲突（如追加随机字符）。
*   **伪代码 - 创建短链**：
    ```python
    def shorten(long_url, custom_alias):
        if custom_alias:
            if db.query("SELECT * FROM urls WHERE short_code = ?", custom_alias):
                raise ConflictError
            short_code = custom_alias
        else:
            # 方式一：使用分布式ID生成器
            unique_id = id_generator.next_id()
            short_code = base62_encode(unique_id)
            # 方式二：基于哈希
            # hash = md5(long_url)[:7]
            # if db.exists(hash): hash += random_chars()
            # short_code = hash

        db.insert("INSERT INTO urls ...", short_code, long_url)
        cache.set(short_code, long_url, ttl=3600)
        return "https://short.url/" + short_code
    ```
*   **伪代码 - 重定向**：
    ```python
    def redirect(short_code):
        # 1. 查缓存
        long_url = cache.get(short_code)
        if long_url:
            return redirect_to(long_url)

        # 2. 查数据库
        result = db.query("SELECT original_url FROM urls WHERE short_code = ?", short_code)
        if result:
            cache.set(short_code, result.original_url, ttl=3600) // 30天过期
            return redirect_to(result.original_url)
        else:
            return 404
    ```

**关键决策**
1.  **301 vs 302 重定向**：
    *   **301 (永久重定向)**：浏览器会缓存，后续访问不再请求服务端，节省服务器压力。不利于统计点击次数。
    *   **302 (临时重定向)**：每次都请求服务端，便于跟踪分析、执行逻辑（如A/B测试），但增加服务器负载。通常选择**302**。
2.  **ID生成策略**：分布式计数器（如数据库序列）需要集中式协调，可能成为瓶颈。更优方案是使用**预分配区间**（每台服务器获得一个ID段）或**Snowflake算法**（时间戳+机器ID+序列号），实现高性能无冲突。
3.  **数据库选择**：关系型数据库（如MySQL）能很好满足事务和一致性需求。如果读QPS极高，可考虑NoSQL（如Cassandra），但其最终一致性模型需要业务可接受（短链服务通常可接受）。
4.  **缓存策略**：使用**LRU**或**TTL**策略。由于短链访问通常遵循“长尾分布”，缓存热点数据即可覆盖大部分请求。缓存与数据库的数据一致性可采用**Cache-Aside**模式。

**扩展讨论**
*   **分析服务**：在重定向逻辑中，异步发送一条包含（短码、时间戳、User-Agent、IP）的消息到Kafka，由流处理引擎（如Flink）实时统计点击量、来源等。
*   **防止滥用**：对同一IP/User在短时间内的创建请求进行限流。
*   **过期与清理**：支持设置链接过期时间，由后台任务定期扫描并标记为无效。
*   **分布式数据库分片**：当数据量巨大时，可以按短码的哈希值进行分片，分散到多个数据库实例。

### **2) 设计Pastebin**

**需求分析**
*   **核心功能**：
    1.  用户提交一段纯文本（或代码片段），系统生成一个唯一的、可分享的短链接。
    2.  其他用户可通过该链接查看文本内容。
    3.  可选设置访问密码、过期时间（如10分钟、1天、1个月、永远）。
*   **非功能性需求**：高可用、低延迟读取、数据持久化、支持大文本（如10MB）。

**容量估算**
*   **假设**：每天新增500万个Paste，平均大小10KB。
*   **存储**：5M * 10KB = 50 GB/天，约1.5 TB/月。总存储量会随时间线性增长。
*   **读QPS**：假设读写比5:1，读QPS ≈ (5M/86400)*5 ≈ 290 QPS。峰值可能更高。
*   **带宽**：读取带宽 ≈ 290 * 10KB ≈ 2.9 MB/s。考虑到部分大文件，实际带宽需求更高。

**高层架构图（文字描述）**
与短链服务类似，但**存储层是关键差异**：
1.  **应用服务器集群**：处理创建和读取Paste的API。
2.  **对象存储服务**：如S3或私有化的MinIO，用于存储实际的文本内容。**不直接存于数据库**，因为文本可能很大且为二进制不安全。
3.  **元数据库**：存储Paste的元数据，如ID、所有者、过期时间、存储位置（S3的Key）、密码哈希等。
4.  **缓存层**：缓存热门Paste的元数据或内容。
5.  **内容分发网络**：缓存热门Paste的静态文件，加速全球访问。

**详细设计**
*   **数据模型**：
    *   **元数据库 (SQL)**:
        ```sql
        CREATE TABLE pastes (
            id VARCHAR(12) PRIMARY KEY, -- 类似短码，唯一标识
            storage_key VARCHAR(255) NOT NULL, -- S3对象键，如 “pastes/ab/cd/abcdef123456.txt”
            title VARCHAR(255),
            syntax VARCHAR(50), -- 语言类型，用于高亮
            expires_at TIMESTAMP,
            password_hash VARCHAR(64),
            created_at TIMESTAMP,
            view_count BIGINT DEFAULT 0
        );
        ```
    *   **对象存储**：文件按 `{id_prefix}/{id}` 的目录结构存储，避免单目录文件数过多。
*   **API设计**：
    *   `POST /api/v1/paste`，Body: `{"content": "...", "syntax": "python", "expires": "1d", "password": "..."}` -> `{"id": "abc123", "url": "..."}`。
    *   `GET /api/v1/paste/{id}` -> `{"content": "...", "metadata": {...}}`。
*   **创建流程**：
    1.  应用服务器接收请求，验证参数。
    2.  生成一个全局唯一的Paste ID（可复用短码生成算法）。
    3.  将文本内容上传到对象存储，获得`storage_key`。
    4.  将元数据（ID、`storage_key`、过期时间等）插入元数据库。
    5.  返回给用户访问URL。
*   **读取流程**：
    1.  从URL解析出Paste ID。
    2.  查询元数据库，获取元数据和`storage_key`。
    3.  如果设置了密码，验证用户提供的密码。
    4.  从对象存储（或CDN）读取文本内容。
    5.  返回内容给用户，并可选地增加视图计数（异步）。

**关键决策**
1.  **存储分离（关键）**：**绝对不能将大文本直接存入数据库行**。数据库应只存索引和元数据。对象存储（S3）专为存储海量非结构化数据设计，成本低、持久性高、易扩展。
2.  **访问控制**：使用`bcrypt`或`scrypt`对密码进行哈希存储。读取时验证哈希。
3.  **过期机制**：两种实现方式：
    *   **惰性删除**：在读取时检查`expires_at`，如果过期则返回410 Gone，并标记为待删除。
    *   **主动清理**：运行定时任务，扫描并删除所有`expires_at < NOW()`的记录及其对应的S3对象。后者更彻底，但实现更复杂。
4.  **语法高亮**：可以由前端JavaScript库（如Prism.js）实现，无需后端处理。后端只需存储`syntax`类型。

**扩展讨论**
*   **内容版本控制**：允许用户编辑Paste并创建新版本，存储多个`storage_key`。
*   **访问统计**：使用异步消息队列记录每次访问，进行实时分析（如PV、UV、来源）。
*   **反垃圾/滥用**：集成内容审核API，扫描提交的文本是否包含恶意代码或非法内容。
*   **私有化部署**：为满足企业安全需求，可提供私有化部署方案，将元数据库和对象存储部署在客户内网。

### **3) 设计Instagram (图片社交网络)**

**需求分析**：核心是**上传/存储海量图片/视频**，并生成**关注者动态流**。非功能需求：高可用、低延迟读取（动态流）、支持数亿用户。
**容量估算**：DAU 5亿，每人每天发1张图，每张5MB，读写比100:1。写存储 ~2.5 PB/天（需压缩和分层存储），读QPS ~60万。
**高层架构**：应用服务器 -> **图片/视频处理服务**（调整大小、生成缩略图）-> **对象存储（S3）**。**动态流服务**是另一个独立子系统。
**详细设计**：
1.  **数据模型**：`Users`, `Posts`（含`media_key`, `user_id`, `caption`），`Follows`（`follower_id`, `followee_id`），`Feed`（`user_id`, `post_id`, `timestamp`）。
2.  **上传流程**：客户端直传S3（通过应用服务器获取预签名URL），上传完成后通知应用服务器更新数据库。
3.  **动态流生成**：
    *   **拉模型**：用户请求时，实时聚合其所有关注者的最新帖子。延迟高，压力大。
    *   **推模型**：用户发布时，将帖子ID插入到其所有粉丝的“收件箱”（如Redis List）。读取时直接拉取该列表。**写扩散，读高效**。需异步处理大V（避免瞬间写入上亿条）。
    *   **混合模型**：普通用户用推模型，大V用拉模型（发布时只存一份，粉丝读取时实时拉取）。Instagram主要采用此模式。
4.  **Feed存储**：使用**Redis（有序集合）** 缓存每个用户收件箱中的`post_id`和`score`（时间戳）。持久化到**Cassandra**或**HBase**。
**关键决策**：动态流的“推拉”权衡是核心。混合模型是实际生产中的标准答案。**服务解耦**：媒体处理、Feed生成、用户关系应作为独立微服务。
**扩展讨论**：图片识别（标签推荐）、直播、Stories（阅后即焚）等高级功能对架构提出新要求。

### **4) 设计Twitter时间线**

**需求分析**：与Instagram类似，但信息更轻（文本为主，140/280字符），实时性要求更高。**核心挑战**：处理**大V**（数千万粉丝）发布推文时的扇出问题。
**高层架构**：与Instagram类似，但更侧重于**消息队列和流处理**。
**详细设计**：
1.  **发布流程**：用户发推 -> 保存推文到`Tweets`表 -> 将事件发布到Kafka。
2.  **时间线服务**：
    *   **Fanout Service**：消费Kafka事件。对于普通用户，执行“写扩散”，将推文ID插入每个粉丝的**收件箱（Inbox）**（Redis有序集合）。对于大V（如粉丝数>10万），则标记为“需拉取”。
    *   **Timeline Service**：用户请求时间线时，服务从其**收件箱**获取一组推文ID，然后**合并**（merge）进大V的实时推文（通过查询大V的`Tweets`表或缓存）。
3.  **数据模型**：`Tweets`（`tweet_id`, `user_id`, `content`, `timestamp`），`Inboxes`（`user_id`, `tweet_id`, `timestamp`）。
**关键决策**：**基于阈值的混合扇出**是Twitter公开分享的核心架构思想。使用**Redis**作为收件箱缓存保证读取速度。**服务降级**：在极端负载下，可暂时禁用大V的实时推送到所有粉丝，改为拉取模式。
**扩展讨论**：实时搜索（使用Elasticsearch）、话题标签（`#`）、趋势计算。

### **5) 设计Facebook Messenger**

**需求分析**：一对一和群聊、已读回执、在线状态、消息存储与同步、多媒体消息。**核心是长连接和实时性**。
**容量估算**：假设10亿用户，5%同时在线，每人维持1个WebSocket连接。需要管理5000万长连接。
**高层架构**：
1.  **连接网关**：维护所有客户端的**长连接（WebSocket）**。
2.  **聊天服务**：处理消息路由逻辑。当A给B发消息时，它需要知道B连接在哪台网关服务器上。
3.  **在线状态服务**：管理用户上线/下线状态，存储用户与连接网关的映射关系。
4.  **消息队列**：异步传递消息，确保可靠性。
5.  **消息存储**：为每个用户或会话持久化消息历史。
**详细设计**：
1.  **消息发送流程**：
    a. A的客户端通过长连接将消息发给其所在的网关。
    b. 网关将消息转给**聊天服务**。
    c. 聊天服务查询**在线状态服务**，获取B所在的网关地址（或离线）。
    d. 如果B在线，聊天服务通过**内部消息队列**将消息推送到B的网关，再由网关推送给B。
    e. 同时，聊天服务将消息写入**消息存储**。
2.  **消息存储**：使用**Cassandra**，分区键为`conversation_id`，聚类键为`timestamp`，支持高效按会话分页查询。
**关键决策**：**连接网关的水平扩展与会话亲和性**：用户每次连接可能落到不同网关，因此需要**有状态的服务发现**（如ZooKeeper、etcd）来维护用户-网关映射。**消息的“恰好一次”投递**：通过消息ID和客户端ACK机制实现。
**扩展讨论**：端到端加密（E2EE）、视频/音频通话（WebRTC）、大规模群聊的优化。

### **6) 设计YouTube**

**需求分析**：上传、存储、转码、流式播放海量视频。**核心是视频处理流水线和内容分发**。
**容量估算**：每天50万小时视频上传，每分钟原始视频约1GB，存储量巨大。需要多格式（MP4, WebM）、多分辨率（1080p, 720p, 480p）转码。
**高层架构**：三个主要系统：
1.  **上传与处理系统**：客户端直传S3 -> 触发**转码任务队列（如SQS）** -> **转码工作节点集群（如基于FFmpeg）** -> 将不同格式的视频存回S3。
2.  **元数据服务**：存储视频标题、描述、标签、播放地址等信息。
3.  **流媒体服务**：接收播放请求，根据客户端带宽和设备能力，通过**CDN**提供合适的视频流。使用**HTTP渐进式下载**或**自适应比特率流（HLS/DASH）**。
**详细设计**：
1.  **视频处理流水线**：转码是CPU密集型任务，需要强大的分布式工作节点。任务可拆分为多个步骤（转码、生成缩略图、提取字幕），由**DAG（有向无环图）工作流引擎**（如Airflow）调度。
2.  **自适应流（ABR）**：视频被切片，每个片断有多个码率版本。客户端根据网络状况动态请求不同码率的片断，无缝切换。
3.  **元数据与推荐**：元数据存储在**NoSQL（如Bigtable）** 中。推荐系统独立，分析观看历史和用户行为。
**关键决策**：**分离处理与服务**。转码集群可独立弹性伸缩。**使用CDN**是保证全球播放体验的关键。**ABR协议**是移动时代的标配。
**扩展讨论**：版权识别（Content ID）、实时直播、互动视频。

### **7) 设计Netflix**

**需求分析**：类似YouTube，但专注于**长视频、高质量、点播**。核心挑战是**全球分发、个性化体验和可靠性**。
**高层架构**：与YouTube有相似之处，但Netflix在**微服务、混沌工程、个性化**上更为深入。
**详细设计**：
1.  **微服务架构**：数千个微服务，如“播放服务”、“用户档案服务”、“推荐服务”、“计费服务”等。
2.  **个性化服务**：**排名服务**为每个用户在每个UI位置生成个性化列表（例如，“为你推荐”）。使用复杂的机器学习模型，特征包括用户历史、相似用户行为、视频元数据等。

### **8) 设计Uber**

### **9) 设计Google Maps**

**需求分析**：地图瓦片服务、地点搜索、路线规划、实时交通。**核心是海量地理空间数据的存储、索引和查询**。
**容量估算**：全球地图数据PB级。每秒数十亿次瓦片请求。
**高层架构**：
1.  **地图瓦片服务**：预先渲染好不同缩放级别的地图切片（图片），存储在CDN或对象存储中。请求时根据坐标和缩放级别获取对应瓦片。
2.  **路线规划服务**：将地图抽象为**图（Graph）**，道路是边，路口是点。使用**Dijkstra或A*算法**计算最短/最快路径。图数据量巨大，需预处理（如分区）并使用**Contraction Hierarchies**等技术加速查询。
3.  **地点索引服务**：存储POI（兴趣点）数据。支持**文本搜索**（如“咖啡店”）和**空间搜索**（如“我附近的咖啡店”）。需要结合**倒排索引**（用于文本）和**R-Tree或Quadtree**（用于空间）。
4.  **实时交通服务**：汇集匿名化的GPS数据，分析道路实时速度，更新路况图层。
**详细设计**：
*   **瓦片金字塔**：缩放级别每增加1，瓦片数量增加4倍。最高级别可精确到建筑物。
*   **路线规划**：图数据按地理区域分片，跨区域路线规划需要**分层**或**分区**算法。
*   **搜索引擎**：类似于Elasticsearch，但需支持空间查询。
**关键决策**：**预计算和缓存**是关键。地图瓦片是静态资源，非常适合CDN。路线规划的算法优化是计算机科学难题。数据**分层**：矢量数据（用于计算）和栅格数据（用于渲染）分离。
**扩展讨论**：街景、室内地图、AR导航。

### **11) 设计Amazon购物车**

**需求分析**：添加/删除/修改商品、保持状态、支持登录和未登录用户。**核心是高并发写入和最终一致性**。
**容量估算**：大促期间，购物车写入QPS可达数百万。
**高层架构**：
1.  **购物车服务**：无状态，处理API请求。
2.  **购物车数据存储**：需要支持高并发读写、持久化，并能在用户跨设备同步。
**详细设计**：
1.  **数据模型**：`Key: user_id or guest_token`，`Value: Map<item_id, quantity>`。可考虑用**Redis Hash**存储，速度快，且原生支持Map操作。但Redis需持久化到更可靠的存储。
2.  **架构选择**：
    *   **方案A（强一致）**：使用关系型数据库，事务保证一致性。在大促下可能成为瓶颈。
    *   **方案B（最终一致，常用）**：使用**DynamoDB或Cassandra**。购物车数据按`user_id`分区。允许在一定时间内不一致（如添加商品后可能短暂看不到），但最终会一致。这种设计能支撑极高吞吐。
3.  **未登录用户**：生成一个唯一的`guest_token`存入Cookie，用此Token作为键存储购物车数据。登录后，将游客购物车与用户账户购物车合并。
**关键决策**：**接受最终一致性**。用户添加商品后，短时间内在另一个设备上可能看不到，这是可接受的体验，换取了极高的可用性和扩展性。**数据合并逻辑**：合并时，相同商品数量相加；对于冲突（如同一商品被两个会话修改），通常以最新时间戳为准或提示用户。
**扩展讨论**：库存预占、分布式事务（下单时扣减库存）。

### **12) 设计Dropbox**

**需求分析**：文件同步、版本历史、跨设备访问。**核心是高效增量同步和冲突解决**。
**容量估算**：用户文件量大，同步频繁。
**高层架构**：
1.  **客户端**：监控本地文件夹变化，计算文件差异（Block级别），仅上传变化块。
2.  **同步服务**：协调客户端间的同步，维护文件元数据（文件树结构、版本历史）。
3.  **块存储服务**：存储文件的数据块。采用**内容寻址存储（CAS）**：数据块的哈希值（如SHA-256）就是其存储地址。相同内容的文件只存一份，节省空间。
4.  **消息队列**：用于异步通知其他客户端同步。
**详细设计**：
1.  **文件分块**：将文件切分成固定大小（如4MB）的块。使用**滚动哈希（Rabin fingerprint）** 算法，即使文件中间插入内容，也能识别出未改变的块，极大减少上传数据量。
2.  **同步流程**：
    a. 客户端A修改文件，本地计算出新的块哈希列表。
    b. 将列表发给**同步服务**，同步服务发现哪些块是新的，请求客户端A上传这些块。
    c. 客户端A上传新块到**块存储**。
    d. 同步服务更新文件的元数据（新版本）。
    e. 通知客户端B（通过长连接或轮询），B拉取新元数据，然后按需下载新块。
3.  **冲突解决**：当两个客户端同时修改同一文件时，同步服务检测到冲突。通常保存冲突版本（如`file (conflicting copy).txt`），由用户手动解决。
**关键决策**：**内容寻址存储**是去重和验证完整性的基石。**增量同步算法**是带宽优化的核心。**最终一致性**：设备间同步有延迟，但最终会一致。
**扩展讨论**：选择性同步、离线访问、企业版权限管理。

### **13) 设计Google Docs**

**需求分析**：实时协同编辑、版本历史、评论。**核心是处理并发编辑冲突和操作转换（OT）**。
**容量估算**：文档可包含大量字符，协作人数可上百。
**高层架构**：
1.  **客户端**：富文本编辑器，捕获用户操作（如“在位置5插入字符‘A’”）。
2.  **协同服务**：核心服务器。接收来自多个客户端的操作序列，应用**操作转换（OT）** 算法，生成一致的文档状态，并广播给所有客户端。
3.  **文档存储**：持久化文档内容和历史操作日志。
**详细设计**：
1.  **操作转换（OT）**：当两个操作同时发生时，OT算法会**变换**其中一个操作，使其在另一个操作之后应用，得到正确且一致的结果。例如，用户A在位置5插入“a”，用户B同时在位置5插入“b”。服务器将B的操作转换为“在位置6插入b”（因为A的插入使位置后移），然后应用。
2.  **状态机**：服务器维护文档的权威状态。每个操作都带有一个**版本号**。客户端提交操作时附上其基于的版本号。服务器检查版本，如果落后，则先将该操作变换为基于最新状态，再应用。
3.  **持久化**：保存操作日志（用于版本回滚）和定期保存文档快照。
**关键决策**：**OT算法**是实现低延迟协同编辑的关键，实现复杂。另一种更现代的方案是**CRDTs（无冲突复制数据类型）**，它设计数据结构使合并自动无冲突，但可能在某些场景下效率略低。**版本向量**用于跟踪多个编辑分支的状态。
**扩展讨论**：富文本格式（粗体、链接）的OT、大型文档的分块处理。

### **14) 设计搜索引擎**

**需求分析**：爬取、索引、查询。**核心是倒排索引和相关性排序**。
**容量估算**：网页数量千亿级，索引数据PB级。
**高层架构**：经典的三阶段流水线：
1.  **爬虫集群**：分布式爬取网页，遵守robots.txt，去重（URL哈希）。
2.  **索引构建集群**：对爬取的网页进行解析、分词、构建**倒排索引**。索引按`词项（Term）`分片。
3.  **查询服务集群**：接收用户查询，从相关分片中检索包含所有词项的文档ID，然后**计算相关性分数**（如TF-IDF，更现代的是BM25或机器学习模型），排序返回Top K。
**详细设计**：
*   **倒排索引**：`词项 -> [(文档ID1, 词频, 位置), (文档ID2, ...), ...]`。
*   **索引分片**：按词项哈希或按文档ID范围分片。查询时需要**Scatter-Gather**模式。
*   **排序**：现代搜索引擎排序信号有数百个（页面权威性、新鲜度、用户点击率等），使用**Learning to Rank**机器学习模型。
**关键决策**：**MapReduce**是构建索引的经典范式。**近实时索引**：
