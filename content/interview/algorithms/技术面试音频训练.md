# 技术面试音频训练

# 系统设计面试模拟脚本：设计一个类似微信的即时通讯系统

## 场景设定
- **面试官**：高级技术总监，10年分布式系统经验
- **候选人**：5年后端开发经验，熟悉高并发系统
- **时长**：约45分钟
- **形式**：白板设计讨论（音频中模拟白板讲解）

---

### 第一部分：需求分析与功能定义（0:00-5:00）

**面试官**（开场）：
"今天我们要设计一个类似微信的即时通讯系统。首先，在开始技术方案之前，请你先帮我们梳理一下这个系统的核心需求。"

**候选人**：
"好的，面试官。在设计任何系统之前，明确需求是最重要的第一步。对于一个类微信的即时通讯系统，我首先会从几个维度来分析需求：

**1. 核心功能需求：**
- **单聊功能**：支持用户之间一对一实时消息传递，包括文本、图片、语音、视频、文件等多媒体消息
- **群聊功能**：支持多人群聊，包括创建群组、加入群组、群消息推送、@提及等
- **消息状态**：已发送、已送达、已读状态显示
- **多端同步**：支持手机、PC、Web等多平台同时登录，消息实时同步
- **离线消息**：用户不在线时消息暂存，上线后自动拉取
- **通讯录管理**：好友添加、删除、分组，群组管理等

**2. 非功能需求：**
- **高可用性**：系统需要保证99.9%以上的可用性，不能因为单点故障导致服务中断
- **低延迟**：消息传递延迟需要控制在毫秒级别，特别是端到端延迟
- **高并发**：要支持亿级用户在线，峰值期间每秒可能有数百万条消息发送
- **数据一致性**：消息不能丢失、不能重复、不能乱序
- **可扩展性**：系统架构需要能够水平扩展，应对用户增长
- **安全性**：消息传输加密，防止中间人攻击，敏感数据加密存储

**3. 用户规模估计：**
基于微信的规模，我们假设：
- 总用户量：10亿
- 日活跃用户（DAU）：5亿
- 峰值在线用户：2亿
- 平均每人每天发送100条消息，峰值QPS约为：5亿 * 100 / 86400 ≈ 57万，考虑峰值是平均的3-5倍，实际峰值QPS可能达到200-300万"

**面试官**：
"分析得很全面。不过我注意到你提到了多媒体消息，在真实场景中，图片、视频这类大文件的传输会面临哪些挑战？"

**候选人**：
"很好的追问。多媒体消息确实是这个系统的关键难点之一，主要挑战包括：

**1. 存储成本高**：
- 微信每天产生的图片、视频可能达到PB级别
- 需要采用分层存储策略：热数据放SSD，温数据放HDD，冷数据放对象存储

**2. 传输带宽压力**：
- 假设每天10亿张图片，平均大小1MB，那么日传输量就是10PB
- 需要CDN网络分发，结合P2P技术降低服务器压力

**3. 编码压缩**：
- 需要针对不同网络环境（2G/3G/4G/WiFi）采用不同的压缩策略
- 视频需要实时转码，提供多种分辨率版本

**4. 安全性问题**：
- 图片、视频可能包含敏感内容，需要内容审核机制
- 防止恶意文件传播，需要文件类型检查、病毒扫描

基于这些挑战，我的设计思路是：
- 采用客户端压缩+服务端二次处理的架构
- 使用独立的媒体服务集群，与核心消息服务解耦
- 媒体文件使用CDN加速，边缘节点缓存热点内容
- 实现渐进式加载：先发送缩略图，再根据需要下载原图"

### 第二部分：高层架构设计（5:00-15:00）

**面试官**：
"很好，现在我们来设计系统的整体架构。请在白板上画出高层架构图，并解释各个组件的作用。"

**候选人**（模拟画图）：
"好的，我先从整体上划分几个主要层次：

**【架构图说明】**
客户端层 → 接入层 → 逻辑层 → 数据层 → 外部服务层

**1. 客户端层**：
- 移动客户端（iOS/Android）
- PC客户端（Windows/macOS）
- Web客户端
- 每个客户端维护长连接，支持消息推送

**2. 接入层**：
- **接入网关**：这是整个系统的'门卫'，负责：
  - 协议适配：支持WebSocket、HTTP/2等不同协议
  - 连接管理：维护亿级长连接，心跳检测
  - 认证鉴权：JWT token验证，防止未授权访问
  - 流量控制：限流、熔断，防止过载
  - 负载均衡：将连接分配到不同的逻辑服务器

- **消息路由服务**：核心的'邮局'功能
  - 根据用户ID、设备类型路由消息
  - 维护在线用户的位置信息（哪个服务器持有连接）
  - 处理消息的多端同步逻辑

**3. 逻辑层**：
- **用户服务**：管理用户资料、好友关系、群组信息
- **会话服务**：管理单聊、群聊会话，维护会话列表
- **消息处理服务**：核心业务逻辑
  - 消息持久化
  - 消息去重（幂等性）
  - 消息排序（序列号）
  - 状态回执处理
- **推送服务**：负责离线消息推送、推送通知
- **媒体服务**：处理图片、视频等多媒体内容
  - 上传、下载、转码、审核
- **搜索服务**：消息全文检索、联系人搜索

**4. 数据层**：
- **关系型数据库**：存储用户资料、好友关系等结构化数据
  - 分库分表策略：按用户ID哈希分片
- **NoSQL数据库**：存储消息数据、会话数据
  - 推荐使用Cassandra或HBase，适合海量时序数据
- **缓存层**：
  - Redis集群：热点数据缓存、在线状态存储、会话缓存
  - 本地缓存：减少网络调用
- **对象存储**：存储媒体文件
- **消息队列**：Kafka/RocketMQ，用于服务间异步通信

**5. 外部服务**：
- 推送服务（APNs、FCM）
- 短信服务（验证码）
- 第三方登录
- 内容审核服务

**关键设计决策**：
1. **长连接 vs 轮询**：我们选择长连接，原因：
   - 实时性好，延迟低
   - 减少客户端电量消耗
   - 服务端可以主动推送

2. **同步 vs 异步**：
   - 消息发送采用异步模式：先写入消息队列，再异步投递
   - 状态同步采用同步模式：确保一致性

3. **有状态 vs 无状态**：
   - 接入网关是有状态的，维护连接状态
   - 业务服务尽量无状态，便于水平扩展"

**面试官**：
"你提到消息路由服务需要维护在线用户的位置信息，如果有亿级用户在线，这个映射表会非常大，如何高效存储和查询？"

**候选人**：
"这是个关键问题。用户-服务器映射表的优化方案：

**方案分析**：
- 2亿在线用户，每个用户平均2个设备连接
- 每个条目：用户ID(8字节) + 设备ID(4字节) + 服务器IP(4字节) + 时间戳(8字节) = 24字节
- 总内存需求：2亿 * 2 * 24B ≈ 9.6GB

**优化策略**：
1. **数据结构优化**：
   - 使用压缩的Redis Hash结构
   - 用户ID作为key，设备列表作为value
   - 对于不常用字段使用更紧凑的编码

2. **分层缓存**：
   ```
   第1层：本地缓存（每个网关进程缓存自己的连接用户）
   第2层：Redis集群（全局查询）
   ```

3. **查询优化**：
   - 优先查询本地缓存（命中率可能80%+）
   - 批量查询：支持mget批量获取
   - 连接分片：不同网关负责不同用户ID段

4. **更新策略**：
   - 用户上线：先写本地缓存，异步写入Redis
   - 用户下线：及时清理，避免僵尸连接
   - 心跳更新：定期更新时间戳，用于检测僵尸连接

5. **内存优化**：
   - 设置合理的过期时间（如30分钟无心跳视为离线）
   - 使用压缩算法（如Snappy）压缩存储
   - 对冷数据采用持久化存储（如LevelDB）

**代码示例（Redis数据结构）**：
```python
# 用户设备映射存储设计
class UserDeviceMapping:
    def __init__(self, redis_client):
        self.redis = redis_client
    
    async def user_online(self, user_id, device_id, server_ip, timestamp):
        """用户设备上线"""
        key = f"user:device:{user_id}"
        device_info = {
            "device_id": device_id,
            "server_ip": server_ip,
            "timestamp": timestamp,
            "status": "online"
        }
        
        # 使用Hash存储设备信息
        await self.redis.hset(key, device_id, json.dumps(device_info))
        # 设置过期时间，30分钟无心跳自动清理
        await self.redis.expire(key, 1800)
    
    async def get_user_devices(self, user_id):
        """获取用户的所有在线设备"""
        key = f"user:device:{user_id}"
        devices = await self.redis.hgetall(key)
        
        # 过滤掉过期的设备
        current_time = time.time()
        active_devices = []
        for device_id, info in devices.items():
            device_info = json.loads(info)
            if current_time - device_info["timestamp"] < 1800:  # 30分钟内活跃
                active_devices.append(device_info)
        
        return active_devices
    
    async def get_server_for_user(self, user_id, device_id=None):
        """查询用户设备所在的服务器"""
        key = f"user:device:{user_id}"
        if device_id:
            # 指定设备查询
            device_info = await self.redis.hget(key, device_id)
            if device_info:
                return json.loads(device_info)["server_ip"]
        else:
            # 查询所有活跃设备
            devices = await self.get_user_devices(user_id)
            # 优先返回移动端设备
            for device in devices:
                if device["device_id"].startswith("mobile_"):
                    return device["server_ip"]
            return devices[0]["server_ip"] if devices else None
```

这种设计可以支撑亿级用户规模的查询需求，同时保证一定的实时性。"

### 第三部分：消息流转深度设计（15:00-30:00）

**面试官**：
"现在我们深入讨论消息发送的完整流程。假设用户A给用户B发送一条文本消息，请详细描述从发送到接收的完整技术流程，包括所有可能的异常情况处理。"

**候选人**：
"好的，我将以一次单聊消息发送为例，详细描述整个流程：

**【完整消息发送流程】**

**阶段1：客户端发送**
1. 用户A在客户端输入消息内容，点击发送
2. 客户端生成消息元数据：
   ```json
   {
     "msg_id": "uuid",  // 全局唯一ID
     "sender_id": "A_user_id",
     "receiver_id": "B_user_id",
     "content": "你好，明天开会",
     "msg_type": "text",
     "timestamp": 1234567890,
     "client_seq": 1  // 客户端序列号，用于消息排序
   }
   ```
3. 客户端对消息进行本地存储（用于离线重发）
4. 通过长连接发送给接入网关

**阶段2：接入网关处理**
1. 网关接收消息，进行初步处理：
   - 验证连接token是否有效
   - 检查发送频率是否超过限制（防刷）
   - 检查消息格式是否合法
2. 如果验证通过，网关将消息发送到消息队列（Kafka）
3. 立即返回ACK给客户端，表示消息已接收

**阶段3：消息队列处理**
1. 消息队列（Kafka）接收到消息
2. 按照一定的策略分区：
   - 可以按照conversation_id分区，确保同一会话的消息顺序
   - 或者按照receiver_id分区，确保同一用户的消息顺序
3. 消息被持久化到磁盘，提供数据可靠性保证

**阶段4：消息处理服务**
1. 消息处理服务消费Kafka中的消息
2. 执行核心业务逻辑：
   ```python
   async def process_message(message):
       # 1. 消息去重：检查msg_id是否已处理过
       if await is_message_duplicate(message.msg_id):
           return  # 重复消息，直接丢弃
       
       # 2. 消息验证：检查发送者是否有权限发送
       if not await validate_sender(message.sender_id, message.receiver_id):
           return  # 无权限，记录异常日志
       
       # 3. 消息存储：存储到数据库
       await store_message_to_db(message)
       
       # 4. 更新会话：更新最后一条消息，未读数等
       await update_conversation(message)
       
       # 5. 消息投递：尝试推送给接收者
       await deliver_message_to_receiver(message)
       
       # 6. 状态回执：如果需要，通知发送者消息已处理
       await send_delivery_receipt(message)
   ```

**阶段5：消息存储**
1. 消息存储策略（关键设计）：
   - **写扩散**：消息存储一份，通过会话列表引用
   - **读扩散**：每个用户的消息副本单独存储

   我们选择**写扩散 + 读扩散结合**的策略：
   ```sql
   -- 消息表（写扩散，只存一份）
   CREATE TABLE messages (
       msg_id BIGINT PRIMARY KEY,
       conversation_id BIGINT,
       sender_id BIGINT,
       content TEXT,
       msg_type TINYINT,
       created_at TIMESTAMP,
       INDEX idx_conversation (conversation_id, created_at)
   );
   
   -- 用户消息表（读扩散，每个用户维护消息列表）
   CREATE TABLE user_messages (
       user_id BIGINT,
       msg_id BIGINT,
       conversation_id BIGINT,
       is_read BOOLEAN DEFAULT FALSE,
       read_at TIMESTAMP NULL,
       PRIMARY KEY (user_id, msg_id)
   );
   ```
   
   这样设计的好处是：
   - 单聊消息只需存一份，节省存储空间
   - 用户有自己的消息列表，便于实现已读、未读状态
   - 支持多端同步：每个设备可以拉取自己的消息列表

2. 分库分表策略：
   - 按照conversation_id进行分片，同一会话的消息存储在一起
   - 使用雪花算法生成分布式ID，确保全局唯一且有序

**阶段6：消息投递**
1. 查询用户B的在线状态：
   ```python
   async def deliver_message_to_receiver(message):
       # 查询用户B的所有在线设备
       devices = await get_user_devices(message.receiver_id)
       
       if not devices:
           # 用户B离线，存储为离线消息
           await store_offline_message(message)
           # 触发推送通知
           await send_push_notification(message.receiver_id, 
                                      f"收到{message.sender_name}的新消息")
           return
       
       # 用户B在线，尝试推送消息
       for device in devices:
           try:
               await push_to_device(device, message)
               # 记录投递状态
               await record_delivery_status(message.msg_id, 
                                          device["device_id"], 
                                          "delivered")
           except Exception as e:
               # 投递失败，记录日志，考虑重试
               await log_delivery_failure(message.msg_id, device["device_id"], e)
   ```

2. 消息推送方式：
   - 通过消息队列（如Redis Pub/Sub）通知对应的接入网关
   - 网关找到用户B的连接，通过长连接推送消息
   - 如果推送失败（如连接已断开），重试3次

**阶段7：客户端接收**
1. 用户B的客户端接收到消息
2. 客户端处理逻辑：
   - 验证消息完整性
   - 存储到本地数据库
   - 更新UI显示新消息
   - 发送已读回执（如果会话打开）
   - 播放通知音/震动

**异常情况处理**：
1. **消息丢失**：
   - 客户端：本地存储+重试机制
   - 服务端：消息队列持久化+ACK机制
   - 定期同步：客户端定期从服务端拉取消息列表，检查缺失

2. **消息重复**：
   - 基于msg_id的幂等设计
   - 服务端去重：维护已处理消息的缓存（布隆过滤器）

3. **消息乱序**：
   - 使用client_seq和server_seq双重序列号
   - 客户端排序：接收后按序列号重新排序

4. **网络分区**：
   - 客户端：网络恢复后重新同步
   - 服务端：最终一致性设计，允许短暂不一致

5. **服务降级**：
   - 消息队列积压时，降级为同步处理
   - 数据库压力大时，只写入关键字段
   - 推送服务不可用时，改为轮询拉取"

**面试官**：
"你提到了消息存储的设计，如果是群聊场景，比如一个500人的大群，每发一条消息都需要写入500条记录吗？这样写放大会不会太大？"

**候选人**：
"非常好的问题！大群消息存储确实是设计难点。我们来分析几种方案：

**方案1：纯写扩散（当前设计）**
- 优点：读取简单，每个用户直接查询自己的消息列表
- 缺点：写放大严重，500人群每条消息写500次
- 适用：小群（<50人）

**方案2：纯读扩散**
- 存储设计：只存储一份消息，用户通过会话ID查询
- 优点：写入简单，只写一次
- 缺点：读取复杂，需要查询所有相关的会话
- 适用：消息量不大的场景

**方案3：混合策略（推荐）**
我们采用分层策略：
```
小群（<100人）：写扩散
中群（100-500人）：写扩散+异步写入
大群（>500人）：读扩散+热数据缓存
```

**具体实现**：
```python
class GroupMessageStorage:
    def __init__(self, group_size):
        self.group_size = group_size
    
    async def store_group_message(self, group_id, message):
        if self.group_size < 100:
            # 小群：同步写扩散
            await self._write_to_all_members(group_id, message)
        elif self.group_size < 500:
            # 中群：异步写扩散
            await self._async_write_to_members(group_id, message)
        else:
            # 大群：读扩散模式
            await self._store_single_message(group_id, message)
            # 更新群会话信息
            await self._update_group_conversation(group_id, message)
    
    async def _write_to_all_members(self, group_id, message):
        """同步写入所有成员的消息列表"""
        members = await self.get_group_members(group_id)
        
        # 使用批量写入提高性能
        batch_size = 100
        for i in range(0, len(members), batch_size):
            batch = members[i:i+batch_size]
            await self._batch_insert_user_messages(batch, message)
    
    async def _async_write_to_members(self, group_id, message):
        """异步写入成员消息列表"""
        # 先写入主消息
        await self._store_single_message(group_id, message)
        
        # 异步写入成员消息列表
        await self.message_queue.put({
            "type": "write_to_members",
            "group_id": group_id,
            "msg_id": message["msg_id"],
            "timestamp": time.time()
        })
    
    async def get_user_messages(self, user_id, conversation_id, limit=50):
        """获取用户消息，混合模式实现"""
        # 首先查询用户自己的消息表
        messages = await self._query_user_messages(user_id, conversation_id, limit)
        
        # 检查是否为大群会话
        if await self.is_large_group(conversation_id):
            # 大群需要额外查询群消息表
            group_messages = await self._query_group_messages(
                conversation_id, 
                self._get_latest_timestamp(messages) if messages else 0,
                limit
            )
            messages.extend(group_messages)
        
        # 按时间排序
        messages.sort(key=lambda x: x["timestamp"])
        return messages[:limit]
```

**优化技术**：
1. **批量写入**：使用数据库批量插入，减少网络往返
2. **异步处理**：大群消息先写主表，异步写用户表
3. **分页写入**：大群分页查询成员，避免一次性加载所有成员
4. **缓存优化**：群成员列表缓存，减少数据库查询
5. **写合并**：将短时间内多条消息合并写入

**性能考虑**：
- 500人群，假设QPS=100，每秒写入量：100 * 500 = 50,000次写入
- 使用批量写入（每批100条），实际网络请求减少到500次/秒
- 通过异步处理，主流程延迟不受影响

这种混合策略在存储成本、读写性能之间取得了平衡，能够支持万级人群的消息存储需求。"

     class TimelineService:
         async def get_timeline(self, user_id, last_time=None, limit=20):

             friends = await self.friend_service.get_friends(user_id)
             
             # 策略选择
             if len(friends) > 1000:
                 # 好友数量大，使用拉模式
                 timeline = await self._pull_timeline(user_id, friends, 
                                                     last_time, limit)
             else:
                 # 好友数量少，使用推模式
                 timeline = await self._push_timeline(user_id, 
                                                    last_time, limit)

         async def _push_timeline(self, user_id, last_time, limit):
             """推模式：直接查询预生成的时间线"""
             # 查询用户时间线缓存
             timeline_key = f"timeline:{user_id}"
             timeline = await self.redis.zrevrangebyscore(
                 timeline_key, 
                 max="+inf" if not last_time else last_time,
                 min="-inf",
                 start=0, 
                 num=limit,
                 withscores=True
             )
             
             # 如果缓存中不足，从数据库补充
             if len(timeline) < limit:
                 db_timeline = await self._query_timeline_from_db(
                     user_id, last_time, limit - len(timeline))
                 timeline.extend(db_timeline)
             
             return timeline
         
         async def _pull_timeline(self, user_id, friends, last_time, limit):

             for moment in all_moments[:limit]:
                 if await self._can_view_moment(user_id, moment):
