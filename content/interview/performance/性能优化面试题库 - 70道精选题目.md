# 性能优化面试题库 - 70道精选题目

> 💡 提示
> 全篇按「指标 → 加载 → 渲染 → 网络 → 构建 → 服务端 → 度量」七条主线组织。每题标注难度，建议先自己答一遍再对照要点；只背结论容易被追问打穿。

## 一、性能基础与指标体系

### 1. 什么是 Web 性能？为什么它对业务很重要？｜初级
> 💡 提示
别只答「加载快」。面试官想听的是你能不能把技术指标翻译成业务语言。

> 🎯 关键要点
- Web 性能是页面从发起请求到可交互全过程中的综合表现，包含三块：加载速度（资源多久到位）、渲染流畅度（帧率与布局稳定性）、响应延迟（操作后多久有反馈）。
- 业务影响是链条式的：加载变慢 → 跳出率上升 → 转化率下降 → SEO 排名下滑。业界反复验证的结论是加载时间从 1s 涨到 3s，转化率会有明显量级的下滑。
- 工程影响：性能是架构约束条件，不是事后补丁。它直接决定选 SSR 还是 CSR、要不要 CDN、缓存分层怎么设计。

> ⚠️ 注意
只拿单机跑分说话是常见的答错方向——实验室数据漂亮但真实用户机型、网络分布完全不同。

> 🔍 追问
你们线上最影响业务的那个指标是什么？为什么选它而不是别的？

### 2. Core Web Vitals 包含哪些指标？阈值是多少？｜初级
> 💡 提示
FID 已经在 2024 年被 INP 取代。现在还在答 FID，等于告诉面试官你的知识没更新。

> 🎯 关键要点
| 指标 | 全称 | 测量什么 | 良好阈值 |
|---|---|---|---|
| LCP | Largest Contentful Paint | 视口内最大内容元素完成绘制的时间 | ≤ 2.5s |
| INP | Interaction to Next Paint | 全生命周期内交互到下一帧绘制的延迟 | ≤ 200ms |
| CLS | Cumulative Layout Shift | 非预期布局偏移的累计分数 | ≤ 0.1 |

- 判定口径是第 75 百分位（p75），不是平均值。均值会被大量快样本拉平，掩盖长尾用户的糟糕体验。
- 三项达标要求 p75 同时满足阈值，任意一项超标就不算通过。

> ⚠️ 注意
样本量不足时 p75 不可信。日访问量小的站点建议按周或按月聚合，否则结论会被单次波动带偏。

> 🔍 追问
如果 INP 超标，你怎么定位到是哪个交互、哪段代码造成的？

### 3. INP 相比 FID 改进了什么？该怎么优化？｜中级
> 💡 提示
核心差别在「测什么」：FID 只测首次输入且只测到回调开始，INP 测每一次交互、一直测到画面更新。

> 🎯 关键要点
- FID 的两个致命局限：只覆盖页面生命周期内的第一次交互，且只计算「输入延迟」这一段，不包含事件处理和渲染耗时。结果就是主线程很卡但首次点击很快的页面也能拿高分。
- INP 拆成三段：输入延迟（从用户操作到事件回调开始）+ 事件处理时间（回调执行）+ 呈现延迟（到下一帧绘制完成）。取整个访问周期内最差的那批交互的近似值。
- 优化手段对应三段：输入延迟高 → 拆长任务、降低主线程占用；处理时间长 → 事件处理去重、事件委托、避免在回调里做重计算；呈现延迟高 → 避免同步布局读写、减少一次交互触发的 DOM 变更量。

```js
import { onINP } from 'web-vitals';

onINP(({ value, attribution }) => {
  // attribution.interactionTarget 能直接告诉你是哪个元素引发的慢交互
  report('INP', value, {
    target: attribution.interactionTarget,
    type: attribution.interactionType,
    loadState: attribution.loadState,
  });
});
```

> 🔍 追问
长任务怎么拆？把一个大任务切成多个 `setTimeout` 和用 `scheduler.yield()` 有什么区别？

### 4. 实验室数据和现场数据有什么区别？该信哪个？｜中级
> 💡 提示
正确的答案是「都要，但用途不同」。实验室数据找原因，现场数据看结果。

> 🎯 关键要点
| 维度 | 实验室数据（Lighthouse / WebPageTest） | 现场数据（CrUX / 自建 RUM） |
|---|---|---|
| 数据来源 | 受控环境下的单次合成测试 | 真实用户真实设备与网络 |
| 优点 | 可复现、可对比、能定位到具体代码 | 反映真实分布，能按机型/地区/网络切片 |
| 缺点 | 环境理想化，与线上差异大 | 噪声大，无法直接定位根因 |
| 用途 | 排查瓶颈、回归对比、CI 卡口 | 判定达标情况、发现长尾问题 |

- 标准做法：RUM 发现「哪一类用户在什么场景下慢」，实验室复现并定位，修完再回到 RUM 验证。

> 🔍 追问
你如何用 RUM 定位到「只有某型号安卓机在某地区慢」这种问题？需要采集哪些维度？

### 5. 首屏时间、白屏时间、TTI、TBT、TTFB 分别怎么定义和测量？｜中级
> 💡 提示
这些词常被混着用。面试官想听你能否说清每个指标归属哪个阶段、由什么信号触发。

> 🎯 关键要点
| 指标 | 归属阶段 | 定义 | 测量方式 |
|---|---|---|---|
| TTFB | 网络 | 请求发出到收到首字节 | `responseStart - requestStart` |
| 白屏时间 | 渲染 | 到首次有像素绘制（首个 paint） | `first-paint` 性能条目 |
| 首屏时间 | 渲染 | 首屏可视区域内内容渲染完成 | 自定义打点或 FCP 近似 |
| TTI | 运行时 | 页面主线程持续空闲、可稳定响应的时刻 | 长任务分析（`long-tasks`）推导 |
| TBT | 运行时 | FCP 与 TTI 之间所有长任务超时部分之和 | `longtask` 条目累加 |

- TTI 在 SPA 上经常不准：动态插入内容、常驻定时器、微小持续任务都会让主线程永远达不到「持续空闲」条件，导致 TTI 被推后甚至测不出。

> 🔍 追问
TTI 测不准时你用什么替代？TBT 和 INP 的取舍在哪里？

### 6. 什么是性能预算？如何制定并落地？｜中级
> 💡 提示
预算的价值不在「定目标」，在「可执行、能被自动拦截」。定完没人管的预算等于没定。

> 🎯 关键要点
- 预算维度别只定一个：初始 JS 体积、单路由体积增量、关键指标阈值、请求数、图片体积，各定一条。
- 制定方法：竞品基线 → 业务目标 → 技术可行性校验，然后按路由和团队拆分额度（谁加谁负责）。
- 落地手段：构建期用 size-limit / bundlesize 卡体积，CI 里跑 Lighthouse CI 卡分数，超预算直接让流水线失败。
- 留例外通道：确有必要的功能走评审批准上调预算，而不是靠「这次先放过去」偷偷突破。

> ⚠️ 注意
只有上限没有例外机制的预算，最后一定会被绕过，然后彻底失效。

> 🔍 追问
预算被突破时你的处理顺序是什么？砍功能还是先优化？

### 7. 如何用业务语言量化性能优化的收益？｜高级
> 💡 提示
「快了 1.2 秒」没人买单，「每月多留住 3% 用户」才有人批资源。

> 🎯 关键要点
- 建立性能到业务的映射：把加载时长分桶（<1s / 1-2s / 2-4s / >4s），观察各桶的转化率、停留时长、跳出率差异。
- 验证方式优先用灰度或 A/B，严格控制变量；无法做实验时，用分桶相关性 + 分段回归做辅助证据。
- 换算成钱或人力：用提升的转化率 × 客单价 × 流量，得出年化收益，和投入的开发成本对比。
- 用真实用户分布加权，而不是拿一台开发机跑出来的漂亮数字。

> 🔍 追问
如果同期还上线了运营活动，你怎么证明转化提升是性能带来的？

## 二、加载与资源优化

### 8. 什么是关键渲染路径？如何优化？｜高级
> 💡 提示
关键渲染路径的关键词是「阻塞」——重点是找出并切断首屏渲染的依赖链。

> 🎯 关键要点
- 定义：浏览器把 HTML、CSS、JS 转成首屏像素所需经过的最短步骤序列，包含关键资源的数量、体积和依赖层数。
- 三类阻塞：HTML 解析被同步脚本阻塞、渲染被 CSS 阻塞、脚本执行被前面的脚本依赖阻塞。
- 优化四条：减少关键资源数量（合并、内联）、缩短关键路径长度（去掉串行依赖）、压缩关键资源体积（关键 CSS 内联 + 其余异步）、把非关键资源移出关键路径（`defer`、媒体查询延迟加载）。

```html
<head>
  <!-- 首屏关键 CSS 内联，避免额外的往返请求 -->
  <style>/* critical css here */</style>
  <!-- 非关键 CSS 先以低优先级加载，加载完再切换 -->
  <link rel="stylesheet" href="/full.css" media="print" onload="this.media='all'">
  <!-- defer 保证解析完成后再按顺序执行，不阻塞 DOM 构建 -->
  <script src="/app.js" defer></script>
</head>
```

> 🔍 追问
内联关键 CSS 会让 HTML 变大且无法被单独缓存，你怎么权衡？

### 9. 如何优化 JavaScript 的加载？｜中级
> 💡 提示
先分清「加载」和「执行」两件事：`async` 解决下载顺序，`defer` 解决执行时机，都不解决执行耗时。

> 🎯 关键要点
- 脚本标记：`defer` 按顺序、DOM 解析完成后执行，适合应用主脚本；`async` 下载完立即执行、顺序不可控，适合埋点、广告等彼此无关的第三方脚本。
- 拆包：按路由和交互做代码分割，首屏只加载必需部分，其余走动态 `import()`。
- 预加载：已知的关键 JS 用 `preload` 提前拉，弱网下收益明显。
- 降成本：生产环境开压缩与 tree-shaking，去掉重复依赖和未使用导出。
- 减执行：`defer` 只推迟了执行，主线程该卡还是卡，重计算要往 Web Worker 挪。

```js
// 路由级分割：只有真正进入该路由才下载对应 chunk
const routes = [
  { path: '/', load: () => import('./pages/Home.js') },
  { path: '/report', load: () => import('./pages/Report.js') },
];
```

`async` 脚本如果在 HTML 中间位置，会造成什么后果？

### 10. 如何优化 CSS 的加载？｜中级
> 💡 提示
CSS 是渲染阻塞资源，浏览器在 CSSOM 构建完成前不会绘制。所以 CSS 优化的核心是「把首屏需要的和非首屏需要的分开」。

> 🎯 关键要点
- 关键 CSS 内联进 HTML，保证首次绘制不等额外请求；非关键 CSS 异步加载后再切换到生效样式表。
- 避免 `@import`：它会串行化下载，且无法被预加载扫描器提前发现。
- 压缩并剔除未使用样式，用工具扫描模板中实际出现的类名做裁剪。
- 控制选择器复杂度，减少深层嵌套与通配符选择器，降低样式计算成本。
- 动态主题用 CSS 变量而不是多套样式表切换。

> ⚠️ 注意
异步加载 CSS 会出现短暂的无样式闪烁（FOUC）。首屏可见区域必须先由内联关键 CSS 覆盖住。

> 🔍 追问
如何自动提取关键 CSS？提取粒度太细或太粗分别有什么后果？

### 11. 如何优化图片加载？｜中级
> 💡 提示
图片通常是页面体积占比最大的资源。优化分三步：换格式、按需尺寸、推迟加载。

> 🎯 关键要点
- 格式：AVIF / WebP 相比 JPEG 通常能显著减小体积，用 `<picture>` 做渐进降级。
- 尺寸：`srcset` + `sizes` 让浏览器按视口和 DPR 选择合适档位，避免给手机下发桌面大图。
- 时机：首屏外图片用 `loading="lazy"`，首屏主图不要懒加载，反而应该 `fetchpriority="high"` 提前加载。
- 布局稳定：显式写宽高或用 `aspect-ratio` 占位，避免加载完成时引起 CLS。
- 交付：走支持自动裁剪压缩的图片 CDN，URL 带尺寸参数按需生成。

```html
<img
  src="hero-800.webp"
  srcset="hero-480.webp 480w, hero-800.webp 800w, hero-1600.webp 1600w"
  sizes="(max-width: 600px) 480px, (max-width: 1200px) 800px, 1600px"
  width="1600" height="900"
  fetchpriority="high" decoding="async"
  alt="首屏主图">
```

> 🔍 追问
`loading="lazy"` 和 Intersection Observer 手写懒加载，什么时候必须用手写的？

### 12. 字体加载怎么优化？如何看待 FOIT 和 FOUT？｜中级
> 💡 提示
字体是典型的「不阻塞渲染但会引起闪烁」的资源。核心问题是：先显示什么。

> 🎯 关键要点
- FOIT（Flash of Invisible Text）是字体加载期间文字不可见，FOUT（Flash of Unstyled Text）是先显示回退字体再切换。两者都比「白屏等字体」好，FOUT 通常更可接受。
- `font-display` 决定策略：`swap` 立即用回退字体渲染（推荐正文）、`optional` 几乎不切换（弱网友好）、`block` 有阻塞窗口（不推荐长文本）。
- 提前建连与预加载：`preconnect` 到字体域名，`preload` 关键字体并带上 `crossorigin`。
- 子集化：只打包实际用到的字符集，中文字体尤其重要，全量包动辄几 MB。
- 回退字体做度量对齐（`size-adjust`、`ascent-override`）能显著降低切换时的 CLS。

> ⚠️ 注意
字体文件跨域加载，`preload` 少了 `crossorigin` 会重复下载一次，白花一个请求。

> 🔍 追问
中文字体子集化后用户输入了子集外的字怎么办？

### 13. SSR、SSG、CSR、ISR 怎么选？｜高级
> 💡 提示
别背定义，回答要落在「内容更新频率」和「个性化程度」两个维度上。

> 🎯 关键要点
| 方案 | 首屏内容 | 适用场景 | 主要代价 |
|---|---|---|---|
| CSR | 空壳 + 客户端渲染 | 重交互后台、登录后应用 | 首屏慢、SEO 差 |
| SSR | 服务端实时出 HTML | 内容动态且需 SEO | 服务器成本高、需处理 hydration |
| SSG | 构建时预生成 HTML | 博客、文档、营销页 | 内容更新要重新构建 |
| ISR | 静态生成 + 后台增量再生 | 大量内容、更新不频繁 | 存在短暂陈旧窗口 |

- 常见最优解是混合：首屏与内容页走 SSR/SSG，交互密集的部分在客户端 hydrate，长尾页面走 ISR。
- 注意区分「TTFB 变差」和「用户感知变快」：SSR 的 HTML 更大、服务端更慢，但 FCP/LCP 通常更好。

> 🔍 追问
SSR 之后 hydration 阶段的 INP 很差，你怎么办？

### 14. 代码分割与懒加载的策略有哪些？｜中级
> 💡 提示
分割不是越多越好，切得太碎会产生大量小请求，反而拖慢。

> 🎯 关键要点
- 按路由分割是基本盘：每个路由一个 chunk，首屏只加载当前路由。
- 按交互分割：弹窗、富文本编辑器、图表库这类「用户点了才用」的重依赖，用动态 `import()` 延后。
- 按依赖稳定性分割：把长期不变的第三方库单独拆成 vendor chunk，利用长效缓存。
- 控制粒度：单 chunk 太小（几 KB）时合并，否则请求数和解析开销上升；同时给重组件加 `Suspense` 兜底和 `prefetch` 空闲预取。

> 🔍 追问
用户在弱网下点了按钮才去加载，转圈三秒，这个体验问题怎么缓解？

### 15. preload / prefetch / preconnect / dns-prefetch / modulepreload 有什么区别？｜中级
> 💡 提示
最容易混的一组。记住两条轴：提前做什么（DNS / 连接 / 下载）和时间紧迫度（当前页必需 / 将来可能用）。

> 🎯 关键要点
| 指令 | 提前做什么 | 紧迫度 | 典型场景 |
|---|---|---|---|
| `dns-prefetch` | 只做 DNS 解析 | 低 | 将来会访问的第三方域名 |
| `preconnect` | DNS + TCP + TLS | 中 | 关键第三方域名（字体、CDN、API） |
| `preload` | 下载当前页必需的资源 | 高 | 首屏主图、关键字体、关键 CSS |
| `prefetch` | 空闲时下载将来可能用的资源 | 最低 | 下一个路由的 chunk |
| `modulepreload` | 下载并预解析 ES 模块 | 高 | 首屏必需的模块图 |

- 用错代价很实：`preload` 太多会挤掉关键资源带宽；`prefetch` 在弱网下抢带宽会拖慢当前页。

> ⚠️ 注意
`preload` 了但三秒内没用上，浏览器控制台会给出「preloaded but not used」警告，这就是配置错了。

> 🔍 追问
`preload` 加 `as` 属性写错会怎样？

### 16. Service Worker 的缓存策略怎么设计？更新怎么做？｜高级
> 💡 提示
这题的死穴在「更新」：缓存做得好，用户可能永远看到旧版本。

> 🎯 关键要点
- 常用策略按资源性质分配：带哈希的静态资源用 cache-first；HTML 文档用 network-first 或 stale-while-revalidate；接口数据按新鲜度要求单独定。
- 缓存版本化：构建产物名带 contenthash，SW 版本号随构建递增，激活时清理旧缓存。
- 更新流程：新 SW 安装后进入 waiting，需要 `skipWaiting` + `clients.claim` 或引导用户刷新；关键是给用户一个「有新版本，点击刷新」的明确提示，而不是静默卡住。
- 降级必须做：SW 注册失败、缓存不可用时，页面要能正常走网络。

```js
self.addEventListener('fetch', (event) => {
  const { request } = event;
  if (request.mode === 'navigate') {
    // HTML 走 network-first，保证拿到最新入口
    event.respondWith(
      fetch(request).catch(() => caches.match('/offline.html'))
    );
    return;
  }
  // 静态资源走 cache-first
  event.respondWith(
    caches.match(request).then((cached) => cached || fetch(request))
  );
});
```

### 18. 骨架屏有用吗？怎么做才有效？｜中级

### 20. 浏览器渲染页面的完整过程是什么？｜中级
> 💡 提示
把流程说全，并且指出每一步的阻塞点。只说「DOM → CSSOM → Render Tree」是不够的。

> 🎯 关键要点
1. 解析 HTML 构建 DOM 树；遇到同步 `<script>` 会暂停解析去下载并执行。
2. 解析 CSS 构建 CSSOM；CSS 是渲染阻塞资源，不完成不绘制。
3. DOM 与 CSSOM 合并成渲染树，只包含可见元素（`display: none` 被排除，`visibility: hidden` 仍占位）。
4. 布局（Layout / 重排）：计算每个元素的几何信息。
5. 绘制（Paint）：把元素转成绘制指令与像素。
6. 合成（Composite）：分层合成最终画面交给 GPU。

- 优化对应点：降低 DOM 深度与数量、避免 CSS 阻塞首屏、缩小布局与绘制范围、用 `transform` / `opacity` 走合成路径、谨慎使用 `will-change`。

> 🔍 追问

### 21. 重排和重绘有什么区别？如何减少？｜中级
> 💡 提示
一句话区分：重排一定伴随重绘，重绘不一定伴随重排。重排的代价大得多。

> 🎯 关键要点
| 对比项 | 重排（Reflow） | 重绘（Repaint） |
|---|---|---|
| 触发条件 | 几何属性变化：尺寸、位置、字体、窗口缩放、增删节点 | 外观属性变化：颜色、背景、阴影、`visibility` |
| 影响范围 | 可能波及整棵渲染树的布局计算 | 只影响相关图层的像素绘制 |
| 代价 | 高 | 中低 |
| 典型操作 | 改 `width` / `top` / `margin`、读 `offsetWidth` | 改 `color` / `background-color` |

- 减少重排：批量改 DOM（先离线操作再一次性插入或用 `DocumentFragment`）、避免在循环里交替读写布局属性、用 `transform` 代替 `top/left`、用 `position: absolute/fixed` 把元素移出常规流、长列表用虚拟滚动减少节点数。
- 关键机制：**强制同步布局**。读 `offsetWidth` 会迫使浏览器立刻结算尚未完成的布局变更，读写交替就会反复触发。

```js
// 反例：每次循环都触发一次强制同步布局
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';
}

// 正例：先集中读，再集中写
const widths = items.map((el) => el.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] + 10 + 'px'; });
```

### 22. 合成层、will-change 和 transform 的代价是什么？｜高级
> 💡 提示
别把「提升为合成层」当万能药。面试官在等你主动说代价。

> 🎯 关键要点
- 优势：`transform` / `opacity` 动画可以在合成线程完成，不触发重排重绘，主线程卡顿也不影响动画流畅。
- 代价一：内存。每个合成层都要独立纹理，大尺寸元素过多会显著增加显存占用，移动端尤其容易触发上下文丢失。
- 代价二：层爆炸。`will-change` 写在会被大量实例化的元素上（如列表项），会生成成百上千个层，性能反而崩塌。
- 代价三：纹理上传与栅格化有一次性开销，短动画可能得不偿失。
- 正确用法：`will-change` 只在动画开始前短时间加上、结束后移除，或者干脆不用、靠 `transform: translateZ(0)` 之外的常规做法触发。

> ⚠️ 注意
`will-change` 是性能提示而不是性能保证，滥用它是典型的新手陷阱。

### 23. 长任务怎么定位、怎么拆分？｜高级
> 💡 提示
长任务（>50ms）是 INP 差的头号原因。能定位 + 能拆，这题才算答完。

> 🎯 关键要点
- 定位：DevTools Performance 面板的 Long Tasks 轨道、PerformanceObserver 监听 `longtask` 条目、React Profiler 看单次 commit 耗时。
- 拆分手段：把大循环切片，每片之间让出主线程；用 `scheduler.yield()`（现代浏览器）或 `MessageChannel` / `setTimeout` 兜底；耗时计算移到 Web Worker。
- 注意让出的时机：让出点必须在「不会破坏一致性」的地方，否则会出现中间态渲染或状态竞争。
- 优先级：用户的输入响应优先于后台计算，用 `scheduler.postTask` 的优先级档位区分。

```js
// 把一个上万次迭代的同步任务切成可中断的分片
async function processInChunks(items, handle, chunkSize = 500) {
  for (let i = 0; i < items.length; i += chunkSize) {
    const end = Math.min(i + chunkSize, items.length);
    for (let j = i; j < end; j++) handle(items[j]);
    // 让出主线程，给输入事件和渲染机会
    if ('scheduler' in window && scheduler.yield) {
      await scheduler.yield();
    } else {
      await new Promise((r) => setTimeout(r, 0));
    }
  }
}
```

> 🔍 追问
`setTimeout(0)` 让出后任务会排到队列末尾，可能被其他任务插队导致延迟变大，怎么缓解？

### 24. 防抖、节流和事件委托分别解决什么问题？｜初级
> 💡 提示
这三个不是同一类东西：前两个控制调用频率，第三个减少监听器数量。

> 🎯 关键要点
- 防抖（debounce）：事件停止触发后延迟执行，适合搜索联想、输入校验、窗口 resize 结束后的重算。
- 节流（throttle）：固定间隔内最多执行一次，适合滚动进度、拖拽跟随、按钮防连点。
- 事件委托：把子元素的监听挂到父元素上，靠事件冒泡统一处理，适合长列表和动态增删节点。
- 高频滚动和触摸事件要显式声明 `{ passive: true }`，避免浏览器等待监听器是否调用 `preventDefault` 而阻塞滚动。

> ⚠️ 注意
防抖设置过长的等待时间会让搜索框「感觉坏了」。交互类防抖一般控制在 200-300ms。

### 25. React 应用怎么优化性能？｜中级
> 💡 提示
先讲「怎么发现慢」，再讲「怎么修」。上来就列 memo 会被认为只会背 API。

> 🎯 关键要点
- 定位：React DevTools Profiler 找渲染次数异常和单次 commit 耗时的组件；高亮重渲染功能直接看谁在重渲。
- 减少无效渲染：`React.memo` 包住纯展示组件、`useMemo` 缓存昂贵计算、`useCallback` 稳定函数引用（注意它只在配合 memo 子组件时才有意义）。
- 结构性优化：把频繁变化的状态下移到最小组件、用 Context 拆分避免大范围订阅、列表 key 用稳定 ID 而不是索引。

```jsx
// 只让真正变化的行重渲染：memo 子组件 + 稳定的回调引用
const Row = React.memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

function List({ items, onSelect }) {
  const handleSelect = useCallback((id) => onSelect(id), [onSelect]);
  return <ul>{items.map((it) => (
    <Row key={it.id} item={it} onSelect={handleSelect} />
  ))}</ul>;
}
```

### 28. Node.js 事件循环怎么排查阻塞？｜高级
> 💡 提示
要说出事件循环的阶段划分，更要说清「什么样的代码会阻塞它」。

> 🎯 关键要点
- 阶段顺序：timers → pending callbacks → idle/prepare → poll → check（`setImmediate`）→ close callbacks，每个阶段之间会清空微任务队列（`process.nextTick` 和 Promise 回调优先于阶段推进）。
- 阻塞来源：同步大计算、同步 IO（`fs.readFileSync`）、大 JSON 解析、正则回溯、加密哈希、模板渲染。
- 排查工具：`--prof` + `--prof-process`、`clinic doctor` / `clinic flame`、`monitorEventLoopDelay` 看事件循环延迟是否持续偏高。

```js
const { monitorEventLoopDelay } = require('node:perf_hooks');

const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  // mean 持续超过 50ms 说明主线程已经被拖住了
  console.log('event loop delay (ms):', (h.mean / 1e6).toFixed(1));
  h.reset();
}, 5000);
```

- 解法：CPU 密集交给 `worker_threads` 或独立服务；大文件走流式处理；同步 IO 换异步；用 cluster 或 PM2 多进程吃满多核。

> ⚠️ 注意
`process.nextTick` 递归调用会饿死事件循环，比 `setImmediate` 危险得多。

### 29. 内存泄漏怎么定位和治理？｜高级
> 💡 提示

> 🎯 关键要点

### 30. CPU 密集型任务怎么处理？｜高级
> 💡 提示
核心答案只有一句：不要让它跑在主线程上。剩下的是讲清各方案的适用边界。

> 🎯 关键要点
- 算法层先优化：换更优算法、加缓存避免重复计算、降低问题规模。很多时候这比并行的收益更大。
- 浏览器：Web Worker 承担计算，主线程只做渲染；注意结构化克隆的数据拷贝成本，大数据优先用 `Transferable`（如 `ArrayBuffer`）转移所有权而不是复制。

- 极端场景：WebAssembly 或 GPU 计算（WebGL / WebGPU）能把数量级拉开，但引入成本和调试代价都要评估。

```js
const worker = new Worker(new URL('./heavy.js', import.meta.url), { type: 'module' });
worker.postMessage({ buffer, length }, [buffer]); // 第二个参数是转移列表，零拷贝
worker.onmessage = (e) => render(e.data);
```

### 32. 动画和滚动掉帧怎么排查？｜中级
> 💡 提示
掉帧就是「一帧的计算时间超过了 16.7ms（60fps）」。所以排查就是找出那一帧里主线程在干什么。

> 🎯 关键要点
- 定位：Performance 面板录制后看 Frames 轨道，帧变红说明超时；展开该帧看是脚本、样式计算、布局还是绘制占用最多。
- 常见元凶：`scroll` / `mousemove` 回调里做重活、回调里读写布局属性造成强制同步布局、动画用了触发重排的属性（`top` / `left` / `width`）、大量元素同时执行 CSS 动画。
- 正确做法：动画只用 `transform` 和 `opacity`；滚动回调用 rAF 节流并加 `{ passive: true }`；需要精确控制的动画用 `requestAnimationFrame` 并按时间戳计算进度，而不是按帧数累加。
- 长列表滚动掉帧优先怀疑渲染节点过多，虚拟滚动是首选解法。

> 🔍 追问

## 四、网络与传输优化

### 33. 浏览器的缓存策略有哪些？强缓存和协商缓存怎么选？｜中级
> 💡 提示
关键是讲清「什么情况下浏览器不发请求」和「什么情况下发请求但可能拿 304」。

> 🎯 关键要点
| 类型 | 相关头 | 行为 | 状态码 |
|---|---|---|---|
| 强缓存 | `Cache-Control: max-age` / `Expires` | 直接用本地副本，不发请求 | 200（from disk/memory cache） |
| 协商缓存 | `ETag` / `If-None-Match` | 发请求问服务端是否变更 | 304 或 200 |
| 禁止缓存 | `no-store` | 完全不缓存 | — |

- 选型原则：带内容哈希的静态资源用一年强缓存 + 文件名变更实现「永久缓存」；HTML 入口用 `no-cache`（可缓存但每次校验）保证能拿到新版本引用。
- `no-cache` 是「每次必须校验」，`no-store` 是「完全不许存」，这两个经常被搞混。
- `ETag` 比 `Last-Modified` 更精确（能识别同一秒内的修改，且不受时间格式精度限制），但多机部署时要注意 ETag 生成算法一致，否则会来回失效。

> ⚠️ 注意
强缓存过期不等于马上失效：用户可能仍在用旧资源，所以版本切换要靠文件名哈希，不能靠「发版后覆盖同名文件」。

> 🔍 追问
`max-age=0` 和 `no-cache` 有什么区别？

### 34. CDN 的原理是什么？怎么用好？｜中级
> 💡 提示
别只答「离用户近」。要说清调度机制和回源策略。

> 🎯 关键要点
- 原理：把内容分发到各边缘节点，通过 DNS 或 HTTPDNS 把用户调度到就近节点；命中则直接返回，未命中则回源拉取并按策略缓存。
- 核心配置：缓存键设计（要不要带 query、要不要区分 `Vary`）、缓存时长、回源 Host 与协议、刷新与预热。
- 收益：降低 RTT、卸载源站带宽、抗突发流量、附带 DDoS 防护。
- 常见坑：带敏感参数的 URL 被缓存导致串号；发布后旧资源未刷新；多 CDN 场景缓存不一致。

### 35. HTTP/2 解决了 HTTP/1.1 的什么问题？｜中级
> 💡 提示
核心词是「队头阻塞」和「连接复用」。同时要提一句它的遗留问题，好接上 HTTP/3。

> 🎯 关键要点
| 对比项 | HTTP/1.1 | HTTP/2 |
|---|---|---|
| 连接使用 | 每域名 6 个左右并发连接，请求仍串行 | 单连接多路复用，请求真正并行 |
| 头部传输 | 明文文本，重复头部每次都传 | HPACK 压缩，首部表复用 |
| 传输格式 | 文本 | 二进制分帧 |
| 流量控制 | 无 | 流与连接两级流控 |
| 优先级 | 无 | 流优先级与依赖 |

- 带来的实践变化：域名分片、雪碧图、资源合并这些 HTTP/1.1 时代的优化手段在 HTTP/2 下收益反转，合并反而可能拖慢缓存复用与按需加载。
- 遗留问题：TCP 层仍有队头阻塞——一个丢包会卡住这条连接上的所有流；这正是 QUIC / HTTP/3 要解决的。

> ⚠️ 注意
HTTP/2 下服务器推送（Server Push）已被主流浏览器移除或废弃，别拿它当卖点回答。

> 🔍 追问
HTTP/2 下还要不要做域名分片？为什么？

### 36. HTTP/3 和 HTTP/2 有什么不同？｜高级
> 💡 提示
根因只有一个：TCP 的队头阻塞。其余都是衍生。

> 🎯 关键要点
| 对比项 | HTTP/2 | HTTP/3 |
|---|---|---|
| 传输层 | TCP | QUIC（基于 UDP） |
| 队头阻塞 | 丢包会阻塞整条连接上所有流 | 流之间独立，单流丢包不影响其他流 |
| 连接建立 | TCP + TLS 至少两次往返 | 首次 1-RTT，复用会话可 0-RTT |
| 连接迁移 | 换网络即断连重连 | 基于 Connection ID，Wi-Fi 切 4G 不断连 |
| 加密 | TLS 可选 | 强制加密，TLS 1.3 内建 |
| 解密路径 | 内核处理，可硬件卸载 | 用户态处理，早期 CPU 开销更高 |

- 落地注意：UDP 在部分企业网络与老旧设备上被限制，必须保留 HTTP/2 回退；服务端 QUIC 在用户态实现，需评估单核吞吐。

> 🔍 追问

### 37. 如何优化 DNS 解析？｜中级
> 💡 提示
DNS 看起来只花几十毫秒，但它发生在所有请求之前，属于串行成本。

> 🎯 关键要点
- 减少域名数量以降低解析次数，注意这与 HTTP/1.1 时代的域名分片策略在 HTTP/2 下需要重新权衡。
- 提前解析：`dns-prefetch` 做纯解析预热，`preconnect` 进一步完成 TCP 与 TLS 握手。
- 缓存：浏览器、系统、Local DNS 多层缓存，合理设置 TTL 平衡「变更生效速度」和「解析命中率」。
- 调度优化：用 HTTPDNS 绕开 Local DNS 的解析劫持与调度不准问题，移动端收益尤其明显。
- 监控：分别采集 DNS 查询耗时，别把它和 TCP、TLS 耗时混在一起看。

```html
<link rel="dns-prefetch" href="//static.example.com">
<link rel="preconnect" href="https://api.example.com" crossorigin>
```

> 🔍 追问
TTL 设太短和太长分别有什么问题？

### 38. 如何优化 TCP 连接？｜中级
> 💡 提示
前端能做的有限，重点是「少建连接」和「早点建」。

> 🎯 关键要点
- 复用连接：开启 `keep-alive` 并使用连接池，避免每次请求重新握手。
- 减少连接数：HTTP/2 多路复用让单连接承载更多请求；HTTP/3 进一步消除队头阻塞。
- 提前建连：`preconnect` 提前完成握手，把 RTT 成本前置到空闲时段。
- 服务端参数：开启 TCP Fast Open（需端侧支持）、选择现代拥塞控制算法（如 BBR）、按 BDP 调整收发缓冲区、按场景决定是否禁用 Nagle。
- 移动端特殊：网络切换、NAT 超时导致的连接失效要配合重连与连接迁移策略。

> 🔍 追问
`keep-alive` 的 idle 时间设太短和太长分别会带来什么问题？

### 39. QUIC 协议解决了什么问题？｜高级
> 💡 提示
把 QUIC 当成「把 TCP 的可靠传输、TLS 加密、HTTP/2 多路复用在用户态重新实现了一遍」。

> 🎯 关键要点
- 消除队头阻塞：流之间独立，丢包只影响所在流。
- 降低握手延迟：传输与加密握手合并，新建 1-RTT，复用 0-RTT。
- 连接迁移：用 Connection ID 标识连接，网络切换不断连，移动端体感提升明显。
- 用户态实现：便于快速迭代拥塞控制算法，不再受内核升级节奏约束；代价是 CPU 开销和缺少内核级卸载。
- 现状：主流浏览器与大型 CDN 已支持，通常与 HTTP/2 并行提供、按网络能力自动降级。

> 🔍 追问
0-RTT 有什么安全风险？

### 40. 如何优化 WebSocket 的性能？｜中级
> 💡 提示
WebSocket 的瓶颈通常不在协议本身，而在连接管理和消息量。

> 🎯 关键要点
- 连接管理：控制单机连接数上限、做心跳保活与断线重连（指数退避）、避免重连风暴。
- 消息优化：开启 `permessage-deflate` 压缩、高频小消息考虑二进制协议（如 Protobuf）批量合并发送、大消息分片并加回压控制。
- 集群：多实例部署必须解决跨节点广播，用 Redis Pub/Sub 或专门的消息中间件做扇出。
- 负载均衡：长连接需要会话保持（sticky session）或按 Connection ID 路由。
- 监控：连接数、消息速率、消息延迟、重连率、异常关闭码分布。

### 41. 如何优化 gRPC 的性能？｜中级
> 💡 提示
gRPC 的优化点集中在「连接复用」「序列化」和「流式」三处。

> 🎯 关键要点
- 基础：基于 HTTP/2 天然多路复用，Protocol Buffers 序列化体积小、解析快。
- 连接：客户端复用长连接并配置连接池，避免短连接反复握手；用客户端负载均衡替代依赖单一入口。
- 传输：启用 gzip 压缩（注意 CPU 换带宽的权衡）、合理设置 `max_message_size`、长耗时调用设置超时和取消。
- 模式选择：批量或流式场景用 stream 减少往返次数。
- 可观测：OpenTelemetry 追踪调用链、监控延迟分位与错误码分布。

### 42. 如何优化 GraphQL 的性能？｜中级
> 💡 提示
GraphQL 把「过度获取」换成了「N+1 和复杂查询」的风险。优化重点是服务端。

> 🎯 关键要点
- 解决 N+1：用 DataLoader 做按 tick 批处理，把逐条查询合并成批量查询。
- 限制查询：设置最大查询深度、复杂度评分与节点数上限，防止客户端构造昂贵查询把服务打穿。
- 缓存：字段级缓存配合持久化查询（把查询文本换成 ID），既能省带宽也能限制任意查询。
- 分页：连接规范用游标分页，避免 `offset` 在大数据集上退化。
- 客户端：规范化缓存、乐观更新、按需请求字段。

```js
// 同一个 tick 内的多次 load 会被合并成一次批量查询
const userLoader = new DataLoader(async (ids) => {
  const users = await db.users.findMany({ where: { id: { in: ids } } });
  const map = new Map(users.map((u) => [u.id, u]));
  return ids.map((id) => map.get(id) ?? null);
});
```

### 43. 移动端和弱网环境怎么优化？｜中级
> 💡 提示

> 🎯 关键要点

### 44. 网络性能监控怎么做？｜中级
> 💡 提示
网络监控要能分阶段归因，否则「慢了」这个结论没法指导任何动作。

> 🎯 关键要点
- 分阶段采集：DNS 查询、TCP 握手、TLS 协商、TTFB、内容下载，各阶段单独聚合，才能定位是解析慢、建连慢还是服务端慢。
- 资源维度：用 Resource Timing 采集各域名、各资源类型的耗时与体积分布，找出拖后腿的域名和体积异常的资源。
- 失败维度：HTTP 状态码分布、超时率、重试次数、失败请求的资源类型。
- 主动探测：合成监控按固定周期从多地探测关键路径，作为 RUM 的补充基线。
- 告警：按分位值（p75 / p95）设阈值，按域名和页面维度分别设，避免全局均值掩盖局部恶化。

### 45. 如何用 Webpack 做性能优化？｜中级
> 💡 提示
分两个方向回答：产物优化（用户下载更快）和构建优化（团队等得更少）。这是两回事。

> 🎯 关键要点
- 产物：`splitChunks` 拆 vendor 与业务代码、`contenthash` 做长期缓存、Terser 压缩、tree-shaking 去掉未使用导出。

```js
module.exports = {
  cache: { type: 'filesystem' },           // 二次构建大幅提速
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all',
        },
      },
    },
  },
};
```

### 46. 如何用 Vite 做性能优化？｜中级

### 47. esbuild 为什么快？适合什么场景？｜中级
> 💡 提示
快的根本原因是 Go 写的、多核并行、且几乎不做跨模块的类型级分析。

> 🎯 关键要点
- 优势：Go 实现 + 并行 + 无 AST 多次遍历 + 自研解析器，构建速度比 JS 实现的打包器高一个数量级。
- 定位：适合做转译（TS/JSX 剥类型）、压缩、依赖预构建（Vite 开发态就用它），不适合处理需要复杂插件生态的场景。
- 局限：不支持完整的 TypeScript 类型检查（只用类型擦除）、插件 API 相对窄、某些 `tsconfig` 高级特性（如 `emitDecoratorMetadata`）支持有限。

> ⚠️ 注意
用 esbuild 转译 TypeScript 时必须独立跑 `tsc --noEmit` 做类型检查，否则类型错误会一路带到线上。

### 48. Rollup 的适用场景是什么？｜中级
> 💡 提示
Rollup 的强项是库打包，因为它对 ES 模块的静态分析最彻底，tree-shaking 结果最干净。

> 🎯 关键要点
- 优势：原生 ESM 优先、静态分析干净、tree-shaking 效果好、产物无运行时胶水代码。
- 适用：三方库（要同时输出 ESM / CJS 供不同环境消费）、Vite 的生产构建底层。
- 局限：对 CommonJS 依赖需要 `@rollup/plugin-commonjs` 兜底，处理 CSS、资源、代码分割不如 Webpack 顺滑。
- 库打包要点：`peerDependencies` 里的框架不打包、输出保留 `sideEffects: false` 声明、生成 sourcemap 与类型声明。

### 49. SWC 相比 Babel 有什么优势？怎么选？｜中级

### 50. Turbopack 的增量编译解决了什么？｜中级
> 💡 提示
核心不是「更快」，而是「增量」——只重算受影响的那部分依赖图。

> 🎯 关键要点
- 机制：函数级增量计算 + 持久化缓存，变更后只重算受影响的模块子图，而不是整个 bundle。
- 定位：面向大型应用的开发态构建器，Next.js 官方推荐，逐步替代 Webpack 的开发角色。
- 现实约束：成熟度与插件生态仍在追赶，生产构建的取舍要以官方文档为准；灰度和回退方案要准备好。

> ⚠️ 注意
「开发态快」不等于「生产产物更小」。这两个目标往往相互独立，评测时要分开看。

### 51. 用 SvelteKit 构建的应用怎么优化性能？｜中级
> 💡 提示
Svelte 的性能优势来自编译期，SvelteKit 的优化重点是渲染模式与数据加载。

> 🎯 关键要点
- 编译期优势：组件编译成直接操作 DOM 的代码，没有虚拟 DOM 运行时开销，基础包体积小。

- 数据加载：用 `load` 函数把数据获取放在服务端，减少客户端瀑布式请求。
- 代码分割：路由天然分割，重组件用动态 `import` 延后加载。
- 构建产物：确认关闭不需要的 hydration，静态站点优先输出纯 HTML。

### 52. 用 Astro 构建的站点怎么优化性能？｜中级

### 53. 怎么做打包体积分析和 tree-shaking？｜中级
> 💡 提示

> 🎯 关键要点
- 前提：产物必须走 ESM（CommonJS 的 `require` 是动态的，无法静态分析）；包自身在 `package.json` 里声明 `"sideEffects": false` 或列出真正的副作用文件。
- 分析手段：`webpack-bundle-analyzer` / `rollup-plugin-visualizer` 看体积构成；`source-map-explorer` 追到源码级；检查是否存在同一依赖的多版本共存（用 `npm ls <pkg>`）。

### 54. 构建缓存和增量构建怎么设计？｜中级
> 💡 提示
缓存要答三件事：缓存什么、以什么为键、什么时候失效。

> 🎯 关键要点
- 缓存对象：loader / 转译器结果、模块图、依赖预构建产物、CI 上的依赖安装（`npm ci` + 缓存 `~/.npm`）。
- 缓存键：源文件内容哈希 + 相关配置哈希 + 依赖版本。**配置必须参与哈希**，否则改了配置却复用旧缓存会出现「改了不生效」的诡异问题。
- 失效策略：改配置需显式失效。Webpack 用 `buildDependencies: { config: [__filename] }`，Vite 需手动清 `node_modules/.vite`。
- CI 侧：缓存要跨流水线可命中，键里带上 lockfile 哈希；缓存未命中时的降级路径要能正常工作（不能硬失败）。

```js
module.exports = {
  cache: {
    type: 'filesystem',
    // 配置变更后自动让缓存失效，避免“改了配置没生效”
    buildDependencies: { config: [__filename] },
  },
};
```

### 55. 微前端的构建策略和性能代价是什么？｜高级
> 💡 提示
微前端解决的是组织问题，代价是性能问题。回答要诚实地讲代价。

> 🎯 关键要点
- 构建期集成（npm 包 / monorepo）：产物可统一优化，缺点是耦合紧、无法独立发布。
- 运行时集成（Module Federation / 原生 ESM 远程模块）：子应用独立构建与发布，主应用运行时按需加载远程入口。
- 共享依赖：通过 `shared` 配置把 React、Vue 等提升为单例共享，避免同一框架多份副本导致的体积翻倍与状态隔离问题。
- 性能代价：多份运行时、重复依赖、跨应用通信开销、首屏需要串行加载多个应用的入口。必须靠预加载、共享依赖、按路由激活子应用来控制。
- 治理：给每个子应用定体积预算与加载时机，否则「独立发布」会迅速变成「一起变慢」。

> ⚠️ 注意
共享依赖的版本区间没对齐会导致运行时加载多份实例，这类问题通常表现为「Context 拿不到值」这种看起来莫名其妙的 bug。

> 🔍 追问
主应用和子应用同时依赖 React 但版本不一致，会发生什么？

## 六、服务端与数据层优化

### 56. 如何优化数据库查询性能？｜中级
> 💡 提示
按「不用查 → 少查 → 查得快」三层递进，比一上来就讲加索引更有条理。

> 🎯 关键要点
- 第一层：不查。加缓存、结果冗余、把非实时数据预计算。
- 第二层：少查。避免 N+1（用 JOIN 或批量 `IN` 查询）、只选需要的列而不是 `SELECT *`、合并多次单条查询为批量查询。
- 第三层：查得快。为高频查询建合适索引（注意最左前缀与区分度），用覆盖索引避免回表，用 `EXPLAIN` 确认是否走了索引、是否出现全表扫描或文件排序。
- 架构层：读写分离、分库分表、冷热数据分离、连接池复用。
- 长期治理：慢查询日志 + 定期巡检，把慢 SQL 当成缺陷来修而不是等它自己变好。

> ⚠️ 注意
索引不是越多越好：每个索引都会拖慢写入并占用存储。低区分度字段单列建索引通常没意义。

> 🔍 追问
`EXPLAIN` 里看到 `Using filesort` 和 `Using temporary` 分别意味着什么？

### 57. 如何优化 API 接口性能？｜中级
> 💡 提示
接口优化的核心问题是「一次请求传了多少没用的东西」。

> 🎯 关键要点
- 减数据量：只返回必要字段、支持字段筛选、分页替代全量返回，避免接口返回几 MB 的 JSON。
- 减次数：合理聚合接口（但要防止聚合出一个什么都查的万能接口）、支持批量查询、客户端并行请求。
- 传输压缩：开 Brotli / gzip，注意大响应的压缩 CPU 成本与收益平衡。
- 缓存：对可缓存的 GET 接口正确设置 `Cache-Control` 与 `ETag`，服务端用 Redis 缓存热点数据。
- 异步化：长耗时操作改为「提交任务 + 轮询/推送结果」，避免长时间占用连接。
- 保护：限流、熔断、超时控制，防止一个慢接口拖垮整个服务。

聚合接口把 10 个下游串起来调用，总延迟反而更高了，怎么改？

### 58. 如何优化服务器响应时间？｜中级
> 💡 提示
从外到内逐层拆：网络 → 接入层 → 应用层 → 数据层。定位不到层就别谈优化。

> 🎯 关键要点
- 先测量再动手：把响应时间拆成排队、应用处理、下游调用、数据库查询四段，找到占比最大的那一段。
- 网络与接入：CDN 卸载静态流量、负载均衡分发、开启压缩与连接复用。
- 应用层：减少无谓计算与序列化、优化热点路径代码、把非关键逻辑移到异步队列。
- 数据层：加缓存、优化慢查询、复用连接池。
- 容量：按负载水平扩缩容，并设置合理的超时与重试策略避免雪崩。

### 59. 如何优化 Node.js 应用性能？｜中级
> 💡 提示
Node.js 的瓶颈只有两个：主线程被阻塞，和单进程用不满多核。围绕这两点回答。

> 🎯 关键要点
- 不阻塞：杜绝同步 IO、大 JSON 同步解析、正则回溯；CPU 密集任务移交 `worker_threads`。
- 用满多核：`cluster` 或 PM2 多进程模式按 CPU 核数起实例，配合负载均衡。
- IO 效率：大数据用 Stream 替代一次性读入内存，并发控制避免打满下游连接。
- 内存：及时释放引用、限制缓存大小、用堆快照排查泄漏。
- 可观测：接入 APM，重点看事件循环延迟、GC 停顿、活跃句柄数。

### 60. 如何优化 Python 应用性能？｜中级
> 💡 提示
先讲清 GIL 的限制，否则后面所有方案都说不通。

> 🎯 关键要点
- GIL 的本质：同一时刻只有一个线程执行 Python 字节码，所以多线程适合 IO 密集，不适合 CPU 密集。
- CPU 密集：用 `multiprocessing` 或 `concurrent.futures.ProcessPoolExecutor` 绕开 GIL；数值计算交给 NumPy / Cython 等原生扩展；极端场景考虑 PyPy 或 Numba。
- IO 密集：`asyncio` 或线程池，避免同步阻塞调用。
- 代码层：用内建函数与合适的数据结构（`dict` / `set` 查找是 O(1)）、用生成器省内存、用 `functools.lru_cache` 缓存纯函数结果。
- 分析工具：`cProfile` 找热点函数、`line_profiler` 看行级耗时、`py-spy` 做低开销采样（适合线上）、`memory_profiler` 看内存。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def fib(n: int) -> int:
    return n if n < 2 else fib(n - 1) + fib(n - 2)
```

### 61. 如何优化 Java 应用性能？｜中级
> 💡 提示
Java 的性能调优分三层：JVM 参数、代码、架构。面试官通常想听你怎么定位而不是背参数。

> 🎯 关键要点
- JVM 层：按实际堆需求设 `-Xms` / `-Xmx`（线上一般让两者相等避免动态扩缩）、选合适 GC（低延迟场景考虑 G1 / ZGC）、用 GC 日志分析停顿分布。
- 诊断工具：`jstack` 看线程栈（定位死锁与热点）、`jmap` / heap dump 看内存、`jstat` 看 GC 频率、async-profiler / Arthas 做线上火焰图。
- 代码层：选合适集合类型（高并发读用 `ConcurrentHashMap`）、避免在循环里创建大对象、及时关闭资源、避免字符串拼接用 `StringBuilder`。
- 数据与外部依赖：连接池（HikariCP）配置合理、缓存热点数据、把远程调用设为异步（`CompletableFuture`）。
- 架构层：服务拆分、读写分离、消息队列削峰。

### 62. 如何优化 Go 应用性能？｜中级
> 💡 提示
Go 的性能抓手是「少分配」和「控制并发规模」。

> 🎯 关键要点
- 内存分配：预分配切片容量避免反复扩容、用 `sync.Pool` 复用临时对象、字符串拼接用 `strings.Builder` 而不是 `+`。
- 并发：goroutine 数量要有上限（信号量或 worker pool），否则大量 goroutine 反而加剧调度与 GC 压力；用 `context` 做超时与取消传播；用 `select` 做多路复用。
- 分析：`pprof` 抓 CPU 与内存火焰图（`net/http/pprof` 可直接挂到 HTTP 服务上），`go test -bench` 做基准，`-race` 检测竞态。
- GC 调优：优先通过减少分配来降低 GC 压力，最后才考虑调 `GOGC`。

```go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func handle() {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()
    defer bufPool.Put(buf) // 用完归还，避免高频分配
    // ... 使用 buf
}
```

### 63. 如何优化数据库连接池？｜中级
> 💡 提示
连接池配错的两个典型后果：配太小导致请求排队，配太大把数据库压垮。

> 🎯 关键要点
- 关键参数：最大连接数、最小空闲连接、获取连接超时、空闲回收时间、连接最大存活时间。
- 容量估算：先看数据库能承受多少并发连接（受内存与线程模型限制），再按应用实例数分摊。**连接池总上限乘以实例数才是数据库实际压力**，这一点最常被忽略。
- 监控：活跃连接数、等待获取连接的时长与次数、连接持有时间分布。等待时间长说明池太小或连接被长期占用。
- 治理：确保每个连接都被归还（`try-with-resources` / `defer close` 之类机制），排查慢查询导致的连接长期占用，超过存活时间强制重建以规避中间件断连。

> ⚠️ 注意
把最大连接数调大不是万能药。数据库侧连接是有成本的，盲目调大只会让所有请求一起变慢。

> 🔍 追问
应用重启后第一批请求超时，你会怀疑什么？

### 64. 缓存架构怎么设计？一致性和失效怎么处理？｜高级
> 💡 提示
缓存的核心矛盾永远是「一致性」和「性能」。回答要有明确的取舍立场。

> 🎯 关键要点
- 分层：浏览器缓存 → CDN → 应用层本地缓存 → 分布式缓存（Redis）→ 数据库，越靠前越便宜、越难一致。
- 更新模式：Cache-Aside（读时回填、写时删除）最常用；写穿（Write-Through）一致性更好但写入放大；写回（Write-Behind）性能最好但丢数据风险高。
- 一致性：常用「先更新数据库再删除缓存」，配合延迟双删或版本号降低窗口期；强一致场景要么不用缓存，要么用订阅 binlog 的方式做准实时同步。
- 三大风险：缓存穿透（查不存在的数据，用空值缓存或布隆过滤器）、缓存击穿（热点 key 过期瞬间打穿，用互斥锁或逻辑过期）、缓存雪崩（大量 key 同时失效，加随机过期时间）。
- 容量：必须有淘汰策略（LRU / LFU）和容量上限，否则缓存会变成第二个数据库。

> 🔍 追问
「先删缓存再更新数据库」为什么比「先更新数据库再删缓存」更容易出问题？

### 65. 性能压测怎么做才有效？｜高级
> 💡 提示
压测最容易犯的错是「压出来的数字没有任何业务含义」。

> 🎯 关键要点
- 目标先定清楚：找容量上限、验证优化效果、还是排查瓶颈？目标不同，脚本和指标都不同。
- 场景要仿真：请求比例、参数分布、用户行为链路、思考时间都要贴近真实，否则压出来的 QPS 没有参考价值。
- 指标看全：QPS、平均与分位延迟（p95 / p99）、错误率、资源利用率（CPU / 内存 / IO / 连接数）一起看，只报 QPS 是耍流氓。
- 方法：阶梯加压找拐点，然后持续打压稳定性；每次只改一个变量，否则归因不了。
- 工具：k6 / Locust / JMeter 做接口压测，WebPageTest 做前端整体验证，Chaos 类工具做异常场景。

> ⚠️ 注意
压测环境与生产环境的机器规格、数据量、依赖服务差异会让结论完全失真。压测前先对齐这些前提。

> 🔍 追问
压测时 QPS 上不去，但 CPU 和内存都很空闲，你会查什么？

### 66. 怎么用 Chrome DevTools 做性能分析？｜中级

### 67. Lighthouse 怎么用？怎么进 CI？｜中级
> 💡 提示
关键认知：Lighthouse 是实验室数据，跑分受环境波动影响很大，必须固定条件才有可比性。

> 🎯 关键要点
- 使用方式：DevTools 面板手动跑、CLI（`lighthouse <url>`）、Node API 编程调用。
- 报告解读：不要只看总分，重点看拖分项——通常是未压缩图片、阻塞渲染的资源、未使用的 JS/CSS、第三方脚本。
- CI 集成：`lighthouse-ci` 可以设性能分数下限、指标阈值（LCP / CLS / TBT），未达标直接失败并输出对比报告。
- 稳定性：固定设备模拟参数、固定网络节流配置、多次运行取中位数，避免因抖动误报。

```yaml
# 关键：用预算断言把性能变成可拦截的卡口
ci:
  collect:
    numberOfRuns: 3
  assert:
    assertions:
      categories:performance: ['error', { minScore: 0.85 }]
      largest-contentful-paint: ['error', { maxNumericValue: 2500 }]
      cumulative-layout-shift: ['error', { maxNumericValue: 0.1 }]
```

### 68. 前端性能监控体系怎么搭？｜高级
> 💡 提示
监控的目的不是「有数据」，而是「问题发生时能快速归因」。

> 🎯 关键要点
- 采集：核心指标（LCP / INP / CLS）+ 资源耗时 + 长任务 + JS 错误 + 接口错误，统一带上版本、页面、机型、网络、地区维度。
- 上报：用 `navigator.sendBeacon` 在页面卸载时上报，避免阻塞导航；采样率可按流量调节，但要保证核心页面 100% 采样。
- 分析：按 p75 / p95 看趋势，按维度和版本下钻，建立「版本发布 → 指标变化」的对照，用来发现回退。
- 告警：按次要指标设阈值，区分「真故障」和「缓慢恶化」，避免告警疲劳。
- 闭环：每个性能问题都要有从发现到修复到验证的完整链路，否则监控只是装饰。

> ⚠️ 注意
采集本身也是性能开销。埋点脚本要轻、要异步、要有采样，不能成为新的性能问题。

### 69. RUM 数据采集具体怎么实现？｜高级
> 💡 提示
要能说出具体的 API 和采集时机，而不是「用个库就行」。

> 🎯 关键要点
- 指标采集：用 `PerformanceObserver` 监听 `largest-contentful-paint`、`layout-shift`、`event`、`longtask` 等条目类型；LCP 要注意在用户首次交互后停止更新。
- 页面卸载时机：用 `visibilitychange` 进入 `hidden` 状态时上报，比 `unload` 更可靠（`unload` 在新版浏览器上已被限制）。
- 归因信息：采集元素选择器、交互类型、加载阶段（loadState）、设备与网络信息，这些决定了你能不能定位问题。
- 现成方案：`web-vitals` 库屏蔽了大量兼容性细节，优先用它而不是自己实现。

```js
import { onLCP, onCLS, onINP } from 'web-vitals';

function send(metric) {
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    id: metric.id,
    page: location.pathname,
    // 归因数据是定位问题的关键，别丢
    attribution: metric.attribution,
  });
  // visible 状态变化时上报，避免 unload 被浏览器忽略
  navigator.sendBeacon('/rum', body);
}

onLCP(send);
onCLS(send);
onINP(send);
```

### 70. 如何做性能回归防护？｜高级
> 💡 提示
性能问题的特点是「没人报警就一定会退化」。防护必须自动化。

> 🎯 关键要点
- 构建期卡口：体积预算（size-limit / bundlesize）对初始包和单路由增量设阈值，超过即失败。
- 指标卡口：Lighthouse CI 对关键页面跑分与指标设断言，跑在固定的合成环境里保证可比性。
- 线上看护：RUM 持续监控，按版本对比指标，出现回退自动关联到发布单。
- 流程配套：给依赖升级和第三方脚本接入设性能评审，把「这次先加上，回头再优化」这条后门堵住。
- 应急：出现性能事故要有快速回滚路径，回滚时间也是性能指标的一部分。

> ⚠️ 注意
只在 CI 卡体积会漏掉运行时回退（比如新增了一个每秒执行的重计算），体积卡口和运行时监控必须都有。
