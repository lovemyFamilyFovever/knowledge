## 结构与约束（3 题）

### 1. 主键、超键、候选键、外键分别是什么？它们的关系怎么理？｜初级

核心结论：四者是包含关系而非并列关系——超键 ⊇ 候选键 ⊇ 主键；外键不属于这一链条，它是"另一张表的主键在本表中的引用"，用来表达表间参照完整性。

- 超键（super key）：能唯一标识一个元组的属性集合。只要加了能区分的列就成立，所以可以任意"加料"：`{学号}` 是超键，`{学号, 性别}` 也是。
- 候选键（candidate key）：**不含多余属性**的超键，即最小超键。`{学号, 年龄}` 是超键但不是候选键，因为去掉 `年龄` 仍然唯一。判定标准是"任何真子集都不再唯一"。
- 主键（primary key）：从候选键中由设计者选定、用来唯一标识行的那一个。一张表只能有一个主键，主键列不允许 NULL（MySQL 会隐式加 NOT NULL）。
- 外键（foreign key）：本表属性 K 若是**另一张表（或本表）的主键/唯一键**，则 K 在本表称为外键；引用目标必须被索引，MySQL/InnoDB 会自动为外键列建索引。
- 举例（学生表）：

| 学号 | 姓名 | 性别 | 年龄 | 系别 | 专业 |
|---|---|---|---|---|---|
| 20020612 | 李辉 | 男 | 20 | 计算机 | 软件开发 |
| 20060613 | 张明 | 男 | 18 | 计算机 | 软件开发 |
| 20060614 | 王小玉 | 女 | 19 | 物理 | 力学 |
| 20060615 | 李淑华 | 女 | 17 | 生物 | 动物学 |
| 20060616 | 赵静 | 男 | 21 | 化学 | 食品化学 |
| 20060617 | 赵静 | 女 | 20 | 生物 | 植物学 |

  学号可唯一区分 → `{学号}` 是候选键也是超键；`{姓名, 性别}` 在本例中恰好唯一，也是候选键（但业务上不可靠，所以不会被选为主键）；`{学号, 专业}` 只是超键。
- 实践中的主键选择：业务无关的自增 BIGINT 或有序 ID（雪花/ULID）优于业务字段。原因是 InnoDB 聚簇索引按主键顺序物理存放，**随机主键会造成页分裂和碎片**，这是"用 UUID 做主键很慢"的真正原因。

> ⚠️ 注意
> "主键不能重复、不能为 NULL"之外还有一条常被追问：一张表即使没显式定义主键，InnoDB 也会依次选：主键 → 第一个不含 NULL 的唯一索引 → 隐藏的 6 字节 row_id。所谓"隐式主键"，二级索引的叶子存的就是它。

> 🎯 关键要点
> - 超键 ⊇ 候选键 ⊇ 主键，外键在链条之外
> - 候选键 = 最小超键，判据是"去掉任一列就不唯一"
> - 主键选有序、业务无关列，避免页分裂
> - 外键引用目标必须有索引，InnoDB 自动补
> - 无主键时 InnoDB 用隐藏 row_id，二级索引照样能定位

> 🔍 追问
> - 为什么用 UUID 做 InnoDB 主键性能差？怎么缓解？
> - 唯一索引能替代主键吗？差在哪？
> - 分库分表之后主键怎么生成，为什么不能用自增？

### 2. 讲讲数据库范式，1NF/2NF/3NF/BCNF 分别解决什么问题？实际项目要不要严格遵循？｜中级

核心结论：范式是"用表拆分换掉更新异常"的一系列约束，逐级递进：1NF 保证列不可分、2NF 消除对主键的部分依赖、3NF 消除非主属性的传递依赖、BCNF 连主属性对主键的依赖也管起来。工程上通常做到 3NF，再按读性能有意识地反范式。

- 第一范式 1NF：每列都是原子值，不可再分，同一列不出现多值或重复组。把 `联系方式` 一列塞"手机、微信、邮箱"就违反 1NF。关系型数据库的最低门槛。
- 第二范式 2NF：先满足 1NF，且**每个非主属性完全依赖于整个主键**。联合主键 `(课程号, 学生号)` 上挂一个只依赖 `课程号` 的 `课程名`，就是部分依赖 → 拆出课程表。
- 第三范式 3NF：先满足 2NF，且非主属性不传递依赖于主键。`学生(学号 → 系编号 → 系名、系地址)` 里系名依赖的是系编号而非学号 → 拆出系表。
- BCNF：任何决定方（determinant）都必须包含候选键，把主属性内部的依赖也纳入约束，是 3NF 的加强。
- 第四范式 4NF：消除非平凡的多值依赖（一个属性同时独立决定两组值时，需要再拆表）。
- 不遵循范式会怎样：插入异常（没有选课就录不进学生）、删除异常（删掉最后一门选课记录连带丢了课程信息）、更新异常（改一处系名要改一万行）。
- 反范式（denormalization）是**有意识的性能取舍**，不是偷懒：加冗余列（订单里存下单时的商品名与价格，本身就是"历史快照"需求）、用宽表/物化视图减少 JOIN、把高频统计结果直接落列。
- 中文互联网常说"阿里规范禁止外键与存储过程"——那是工程约束（分库分表下外键无法跨库校验、在线 DDL 代价高、触发器逻辑不可见难维护），不等于"范式不重要"。规范里同时要求字段必须能解释依赖关系，本质仍是范式思维。

| 范式 | 一句话判据 | 违反后的动作 |
|---|---|---|
| 1NF | 列不可再分 | 拆列或拆表 |
| 2NF | 非主属性完全依赖整个主键 | 把部分依赖拆出去 |
| 3NF | 非主属性不传递依赖主键 | 把决定方单独成表 |
| BCNF | 所有决定方都含候选键 | 按决定方再拆 |

> 💡 提示
> 答范式题最稳的路径是"给一个反例表 → 指出异常 → 拆表"，而不是背定义。能现场把 `(学号, 课程号, 成绩, 课程名, 教师名, 教师职称)` 拆成三张表并说明每步消除了哪种依赖，比讲四个名词强得多。

> 🎯 关键要点
> - 范式逐级加强，解决的是三类更新异常
> - 2NF 管部分依赖，3NF 管传递依赖，BCNF 管所有决定方
> - 反范式是性能取舍，要能说出换来什么、代价是什么
> - 订单快照类冗余不属于违反范式，是需求本身
> - 禁止外键是工程约束，不是范式约束

> - 你项目里哪张表是故意反范式的？为什么？
> - 加了冗余列之后怎么保证它和源数据一致？

### 3. 视图是干什么的？视图能被更新吗？｜中级

核心结论：视图是"存下来的查询"，不存放数据（普通视图），价值在简化调用、隔离表结构变更、做行/列级权限；能否更新取决于该更新能否**无歧义地映射回基表**，MySQL 用 WITH CHECK OPTION 约束写入。

- 作用：① 简化复杂 SQL，把多表 JOIN 与聚合封装成"逻辑表"给上层复用；② 安全，只暴露允许访问的列与行（配合权限授予）；③ 逻辑独立，基表拆分/改列名时应用侧只改视图定义；④ 兼容旧接口，重构表结构期间保持 API 不变。
- 可更新的条件（MySQL）：视图定义里**不含**聚合函数、`DISTINCT`、`GROUP BY`、`HAVING`、`UNION`，不含子查询（在 SELECT 列表里），且是 `ALGORITHM=MERGE` 能映射到单表时，才可以 INSERT/UPDATE/DELETE；对视图的写会落到基表。
- `WITH CHECK OPTION`：约束通过视图写入的数据必须满足视图的 WHERE 条件，否则报错——防止"从视图插入一行后它就消失了"。
- 两个可选算法：`MERGE`（把视图定义并入外层查询，性能等同直接查基表）与 `TEMPTABLE`（先生成临时表，无法用基表索引，但语义更独立）。`EXPLAIN` 能看出实际用了哪种。
- 原稿说"视图不能被索引"——在 MySQL 里成立（MySQL 没有物化视图/索引视图）；但 SQL Server 有 indexed view、Oracle/PostgreSQL 有 materialized view（真实落盘、可定时刷新）。答这题要先限定引擎，否则会被追问一句就露底。
- 常见坑：视图里带 `ORDER BY` 时，外层再排序会覆盖它（`TEMPTABLE` 下更是白做）；`SELECT *` 定义的视图在基表加列后行为会漂移；嵌套视图使执行计划难读。

> ⚠️ 注意
> "视图能提升查询性能"是错的——普通视图不物化，只是一段文本替换，性能与直接写 SQL 完全一致（`TEMPTABLE` 甚至更慢）。真正能提速的是物化视图/汇总表/索引，别把它们混作一谈。

> 🎯 关键要点
> - 视图是查询不是数据，本身不提速
> - 可更新的判据：能否无歧义映射回单张基表
> - WITH CHECK OPTION 防"写进去就查不到"
> - MySQL 无物化视图，跨引擎答题要先限定
> - 视图里慎用 ORDER BY 和 SELECT *

> 🔍 追问
> - 视图和临时表、CTE（WITH 子句）分别什么时候用？
> - 用视图做权限隔离，有什么绕过去的风险？
> - 物化视图的数据新鲜度问题怎么解？

## 事务与数据库对象（3 题）

### 4. 数据库事务的 ACID 四个特性分别是什么？数据库靠什么实现它们？｜初级

核心结论：ACID 是"事务应该满足什么"，实现手段是另一套东西——原子性靠 undo log，持久性靠 redo log（WAL），隔离性靠锁 + MVCC，一致性是前三者加上约束共同达成的结果，不是单独实现的机制。

- 原子性 Atomicity：事务内的操作要么全做、要么全不做，出错回滚到开始前状态。实现：写数据前先记 undo log，回滚时按 undo 反向恢复。
- 一致性 Consistency（原稿写成 Correspondence，是错的）：事务前后数据库的完整性约束不被破坏——主键唯一、外键引用存在、`CHECK`、业务不变式（转账前后总额相等）。它是目的，其余三条是手段。
- 隔离性 Isolation：并发事务互不干扰，感觉像串行执行。实现：锁（行锁/间隙锁）+ MVCC 多版本读视图。注意"隔离性 ≠ 真的串行"，靠隔离级别在一致与并发之间折中。
- 持久性 Durability：提交后改动永久保存，掉电不丢。实现：redo log 顺序写盘 + `innodb_flush_log_at_trx_commit=1`（每次提交 fsync），配合双写缓冲防页撕裂。
- 四种隔离级别与各自的异常：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 无 | 可能 | 可能 |
| REPEATABLE READ（MySQL 默认） | 无 | 无 | 基本抑制 |
| SERIALIZABLE | 无 | 无 | 无 |

- InnoDB 在 RR 下用 MVCC 做快照读、用 Next-Key Lock（记录锁 + 间隙锁）锁住范围来抑制当前读的幻读，所以"RR 是否完全解决幻读"要看读的类型——这是这题真正的分水岭。
- 原稿把隔离性解释为"必须串行化请求，使同一时间只有一个请求使用同一数据"，那是 SERIALIZABLE 的定义，不是隔离性这个属性的含义。

> 💡 提示
> 一句话把实现层带出来，档次立刻不同："undo 管回滚，redo 管恢复，MVCC 和锁管隔离，一致性是这三件加约束共同保证的。"再补一句两阶段提交（binlog 与 redo log 的 prepare/commit）为什么必须存在——因为 binlog 是 server 层、redo 是引擎层，不协调就会出现主从数据不一致。

> 🎯 关键要点
> - 一致性是目标，其余三条是手段
> - undo→原子性，redo→持久性，锁+MVCC→隔离性
> - MySQL 默认 RR，不是 Oracle 的 RC
> - RR 靠 MVCC 管快照读、靠间隙锁管当前读
> - 提交慢多半是 fsync，不是网络

> 🔍 追问
> - RR 级别下幻读到底解决了没有？分哪两种读？
> - 为什么需要 redo log 和 binlog 两阶段提交？
> - `innodb_flush_log_at_trx_commit` 设 1 和设 2 差别是什么？

### 5. DROP、TRUNCATE、DELETE 有什么区别？删错了怎么恢复？｜初级

核心结论：DROP 删对象（结构+数据+依赖），TRUNCATE 清空数据但保留结构、属于 DDL 且隐式提交、不可回滚，DELETE 逐行删除、属于 DML、可带 WHERE 可回滚但会写 undo/redo。速度 DROP > TRUNCATE > DELETE。

| 维度 | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| 语言类别 | DML | DDL | DDL |
| 删除范围 | 行（可 WHERE） | 全表数据 | 表结构 + 数据 |
| 事务 | 可回滚 | 隐式提交，不可回滚 | 隐式提交，不可回滚 |
| 触发器 | 会触发 | 不触发 | 不适用 |
| 日志 | 每行写 undo/redo | 不逐行记录 | 释放整个表空间 |
| 空间 | 数据页不归还 OS | 表空间回到初始大小 | 全部释放 |
| AUTO_INCREMENT | 不重置 | 重置为 1 | 对象消失 |
| 外键引用 | 允许（按约束校验） | 被引用时禁止 | 受 RESTRICT/CASCADE 影响 |
| 锁粒度 | 行锁 | 元数据级，开销小 | 元数据级 |
| 速度 | 最慢 | 快 | 最快 |

- 为什么 DELETE 慢：逐行定位 → 写 undo（供回滚）→ 写 redo → 加行锁 → 维护二级索引；百万行删除还会撑大 undo 与 binlog，并长时间持锁。
- 大表删数据的正确做法：分批 `DELETE ... WHERE id BETWEEN ? AND ? LIMIT 1000` 循环（每批之间 sleep，让出锁与复制压力），或"建新表 + 交换 RENAME"，或直接按分区 `ALTER TABLE ... DROP PARTITION`。
- TRUNCATE 在 MySQL 8.0 的 InnoDB 上实现为"drop 表空间 + create"，因此**不重置自增计数器**这一说法要看版本：文档口径是 TRUNCATE 会把 AUTO_INCREMENT 重置为 1（DELETE 不重置）；跨版本答题时说明"以你实际用的版本为准"。
- 删错了怎么恢复：① 有备份 + binlog → 全量备份恢复到新实例，再用 `mysqlbinlog --start-datetime --stop-datetime` 重放增量（或用 `binlog_row_image=FULL` 生成的反向 SQL）；② 开了延迟副本（`MASTER_DELAY`）→ 立刻切；③ 都没有 → 只能靠 undo/表空间恢复工具（Percona Data Recovery / `pageparser`），代价极高。这就是"误删先停写、别继续跑"的原因。
- 原稿"谨慎使用 drop 与 truncate"是对的，但更该说的是：生产库用权限把 DDL 收归 DBA/审批流，`sql_safe_updates=1` 让不带 WHERE 的 DELETE/UPDATE 直接报错。

> ⚠️ 注意
> "TRUNCATE 不记日志"是常见误述。它不逐行记 undo/redo，但仍会写 DDL 语句进 binlog——所以主从会同步清空，而且**误 TRUNCATE 后靠 binlog 恢复时，前滚会重放这条 DDL，必须先恢复到故障前时间点**。别把"不能回滚"理解成"没有痕迹"。

> 🎯 关键要点
> - DML/DLL 之分决定能不能回滚，这是主线
> - DELETE 慢在逐行 + undo + 索引维护
> - 大表删除要分批或用分区/换表
> - 恢复靠备份 + binlog 时间点，不是靠回滚
> - 生产用权限与 safe-updates 兜住误删

> 🔍 追问
> - 一张 5 亿行的表要删掉一半历史数据，你怎么做？
> - 为什么 TRUNCATE 不能回滚？DDL 隐式提交发生在哪一步？
> - 线上有人误 DELETE 未提交，你现在能做什么？

### 6. 存储过程和触发器是什么？有什么区别？为什么互联网公司大多禁用它们？｜中级

核心结论：存储过程是一段命名、预编译、可传参调用的 SQL 集合；触发器是绑定在表上、由 INSERT/UPDATE/DELETE 事件自动执行的 SQL 集合，不能显式调用。两者都把业务逻辑搬进了数据库，因此现代互联网架构普遍选择少用。

- 相同点：都是 SQL 语句的打包，都能访问当前库数据、都能被权限控制、都能减少客户端与数据库之间的往返。
- 关键区别：

| 维度 | 存储过程 | 触发器 |
|---|---|---|
| 调用方式 | 显式 `CALL proc()` | 事件自动触发 |
| 参数 | 有入参/出参 | 无参数，用 `NEW`/`OLD` 行 |
| 返回值 | 可有结果集/OUT 参数 | 无 |
| 触发时机 | 由调用方决定 | BEFORE / AFTER（MySQL 只有 BEFORE/AFTER 对 DML，无 INSTEAD OF） |
| 典型用途 | 批处理、复杂流程封装 | 审计日志、跨表一致性、字段派生 |

- 优点（为什么有人用）：一次编译反复执行、减少网络往返、把敏感操作封在权限后面、能在数据库层强制跨表一致性。
- 缺点（为什么互联网公司禁用）：① 逻辑藏在库里，版本管理与 code review 困难，改一次要 DDL 权限；② 数据库是最难水平扩展的一环，把 CPU 密集逻辑放进去等于给瓶颈加压；③ 触发器隐蔽执行，排查"这行数据怎么多出来了"极其痛苦，还会在批量导入时放大成性能事故；④ 迁移成本：不同数据库方言完全不兼容；⑤ 主从/分库分表下触发器与存储过程的行为更难推理。
- 现实边界：审计表、`updated_at` 自动维护这类"与业务无关的数据卫生"用触发器仍然合理；报表批处理用定时任务在应用层做，比存储过程更好测。原稿是 SQL Server 口径（`EXECUTE`、Transact-SQL），MySQL 里调用写 `CALL`，且 MySQL 5.0 才引入存储过程、10.4 才引入事件调度器。

> 💡 提示
> 答"为什么禁用"时给一条判断标准比列五条现象更有说服力：**逻辑该放在能版本控制、能水平扩展、能单元测试的地方**。数据库不是不能放逻辑，而是它恰好三条都不满足。

> 🎯 关键要点
> - 存储过程显式调用，触发器事件驱动不可显式调
> - 两者共同代价是把逻辑放进最难扩展的一层
> - 触发器的隐蔽性是排查事故的头号负担
> - 审计/字段派生这类数据卫生仍可用触发器
> - MySQL 语法是 CALL，不是 EXECUTE

## 检索与优化（3 题）

### 7. 索引的工作原理是什么？有哪些种类？为什么 InnoDB 用 B+ 树？｜高级

核心结论：索引是"以额外空间和维护成本换查找速度"的有序辅助结构；InnoDB 用 B+ 树聚簇索引，叶子节点存整行、非叶子只存键，因此树更矮、磁盘 IO 更少，且叶子串成链表让范围查询变成顺序读。

- 原理：数据之外维护一份"键 → 位置"的有序结构，把 O(N) 全表扫描降到 O(log N) 的树查找 + 少量回表。
- 为什么不是二叉树/红黑树：树太高，1000 万行约 23 层，每层一次随机 IO。为什么不是 B 树：B 树非叶子节点也存数据，单页能放的键更少、树更高，且范围查询要中序回溯。B+ 树把数据全压到叶子、叶子用双向链表相连，矮且擅长范围扫。为什么不用哈希：等值 O(1) 但无法范围查询与排序，且冲突退化；Memory 引擎默认用 HASH，InnoDB 只在自适应哈希里局部使用。
- 树高为什么只有 3 层：InnoDB 页 16KB，非叶子节点约存 1200 个键指针，叶子节点约存 16 行 → 3 层可支撑约 1200×1200×16 ≈ 2000 万行，所以"千万级表三次 IO"是常见量级。这也解释了**主键要短**：二级索引叶子存的是主键值，主键越长所有二级索引都跟着膨胀。
- 索引的分类（原稿把"唯一/主键/聚集"并列，其实是三个正交维度）：
  - 按逻辑功能：主键索引、唯一索引、普通（二级）索引、前缀索引、全文索引、空间索引、多列联合索引、8.0.13+ 函数索引。
  - 按物理存储：聚簇索引（叶子存整行，一表一个）、二级索引/非聚簇（叶子存索引列 + 主键，查全字段需**回表**）。
  - 按数据结构：BTREE、HASH、FULLTEXT、RTREE。
- 高频派生概念：覆盖索引（查询列全在索引里，免回表，`EXPLAIN` 显示 `Using index`）、最左前缀（联合索引 `(a,b,c)` 只能被 `a`、`a,b`、`a,b,c` 前缀命中）、索引下推 ICP（5.6+，在索引层先过滤 `b` 再回表）、前缀索引（对长字符串取前 N 字符，省空间但失去 `ORDER BY` 能力）、filesort（无法用索引序时额外排序）。
- 什么时候不该建索引：列极少被查询、取值基数极低（性别、状态枚举且分布倾斜）、TEXT/BLOB 未取前缀、写多读少的表、重复索引（`(a)` 已存在时 `(a,b)` 才需要，`(a)` 是 `(a,b)` 的前缀冗余）。

| 结构 | 查找 | 范围 | 树高 | 结论 |
|---|---|---|---|---|
| 二叉排序树 | 有序 | 可 | 高 | 退化即链表 |
| 红黑树 | 有序 | 可 | 高 | 局部性差 |
| B 树 | 有序 | 需回溯 | 中 | 非叶存数据吃亏 |
| B+ 树 | 有序 | 链表顺序扫 | 矮 | 索引首选 |
| 哈希 | O(1) | 不支持 | 1 | 只做等值 |

> 💡 提示
> 这题的加分点是能把"代价"说清：索引不是免费的，一次 INSERT 要维护聚簇 + 每个二级索引，写放大随索引个数线性增长；同时优化器统计信息（`cardinality` 由采样估算，不是精确值）会决定用不用索引，所以"加了索引没生效"通常是统计或选择性判断的问题，该看 `EXPLAIN` 而不是重加索引。

> 🎯 关键要点
> - B+ 树胜在矮、叶子链表、顺序 IO 友好
> - 3 层约撑 2000 万行，所以主键要短
> - 聚簇存整行，二级索引要回表
> - 覆盖索引/最左前缀/索引下推是三个必考派生点
> - 索引数量与写放大成正比，别滥建

### 8. SQL 里的连接有哪些种类？各自语义是什么？｜中级

核心结论：连接按"保留哪一侧不匹配行"分为内连接、左/右外连接、全外连接，另有交叉连接与自连接；MySQL 不支持 FULL OUTER JOIN，要用 LEFT UNION RIGHT 模拟。

- 样例数据（沿用原稿）：`table1` 三行为 `(1, lee)`、`(2, zhang)`、`(4, wang)`；`table2` 三行为 `(1, 90)`、`(2, 100)`、`(3, 70)`。两边都缺一个匹配对象——table1 的 `4` 和 table2 的 `3`，下面的差异全部由这两个"孤儿行"产生。
- 内连接 `INNER JOIN`（`JOIN` 默认即内连接）：只保留两边都匹配的行 → `(1,lee,90)`、`(2,zhang,100)`；`4 wang` 与 `3 70` 都消失。
- 左外连接 `LEFT [OUTER] JOIN`：保留左表全部行，右表无匹配处填 NULL → 多出 `(4,wang,NULL,NULL)`。
- 右外连接 `RIGHT [OUTER] JOIN`：保留右表全部行 → 多出 `(NULL,NULL,3,70)`。左右可互换，把两表位置对调即可，所以工程上几乎只用 LEFT JOIN。
- 全外连接 `FULL OUTER JOIN`：两侧不匹配行都保留。**MySQL/InnoDB 语法直接报错**（Oracle/PostgreSQL/SQL Server 支持），MySQL 里要写成 `LEFT JOIN ... UNION ... RIGHT JOIN`（注意用 `UNION` 去重，别用 `UNION ALL` 否则匹配行出现两份）。
- 交叉连接 `CROSS JOIN`：笛卡尔积，行数 = m×n；`table1, table2` 逗号写法等价，忘了写条件是它的典型事故。
- 自连接：同一张表连自己，用于层级/比较（员工表 `e JOIN emp m ON e.manager_id = m.id`、成绩比较、树结构向上找父）。
- 自然连接 `NATURAL JOIN`：按同名列自动等值连接，看起来省事但会因表结构变更悄悄改变语义，生产禁用。
- 语义补全：半连接（`EXISTS`/`IN` 子查询，只要存在即保留，不复制行）与反连接（`NOT EXISTS`，找不匹配的）。`NOT IN (子查询)` 遇到 NULL 会整体返回空集，这是最常见的隐性 bug，要用 `NOT EXISTS`。
- 执行方式（追问层）：MySQL 只有 Nested Loop Join（被驱动表走索引则称 index join）、Block Nested Loop（无索引时把驱动行装入 join buffer 批量比）、以及 8.0.18+ 的 Hash Join（8.0.20 起取代 BNL）。所以"连接很慢"先看被驱动表的连接列有没有索引。

> ⚠️ 注意
> 外连接的过滤条件放 `ON` 还是 `WHERE` 结果不同：`ON` 里的条件在**保留侧全行**基础上决定右表补不补 NULL；`WHERE b.x IS NULL` 才是"找没匹配上的"。把条件写进 WHERE 会把外连接退化成内连接，这是每年必踩的坑。

> 🎯 关键要点
> - 内外连接之差只在"是否保留不匹配行"
> - MySQL 无 FULL JOIN，用 UNION 模拟
> - 左右可互换，实践只用 LEFT
> - 条件写在 ON 与 WHERE 语义不同
> - `NOT IN` 遇 NULL 恒空，改 `NOT EXISTS`

### 9. 数据库优化的思路有哪些？从哪一层开始做收益最大？｜高级

核心结论：优化是自上而下的——先问"这条查询该不该存在、能不能少查"，再看 SQL 与索引，然后才到表结构/分库分表，最后才是堆硬件。越靠上收益越大、代价越小。

- 第 0 层：需求与架构。加缓存（Redis/本地）、读写分离、把统计改成离线预计算、砍掉不必要的实时查询。大量"数据库慢"的正确解法是根本不该打到数据库。
- 第 1 层：定位。`slow_query_log`（`long_query_time`）+ `mysqldumpslow`/`pt-query-digest` 找 TOP SQL；`EXPLAIN` 看 `type`（system>const>eq_ref>ref>range>index>ALL）、`key`、`rows`、`filtered`、`Extra`（`Using filesort`/`Using temporary`/`Using index`/`Using index condition`）；8.0 用 `EXPLAIN ANALYZE` 看真实耗时分布。
- 第 2 层：SQL 与索引。
  - 让索引能用上：不要在列上套函数或表达式（`WHERE DATE(created_at)=...` 改成范围）、避免隐式类型转换（varchar 列传 int 数字，或两边字符集/排序规则不一致）、避免前导 `%`（`LIKE '%xx'` 无法用索引序，可用全文索引或倒置存储）、`OR` 连接非索引列会让索引失效（改 `UNION ALL`）、满足联合索引最左前缀、`ORDER BY` 与索引方向一致。
  - `!=`、`<>`、`IS NULL` **不是绝对不走索引**：优化器按统计信息估选择性，命中行占比高时走全表更快。原稿保留了"必须避免"的旧说法，同时引用了读者的反驳意见——正确结论是"它们不保证走索引，要 EXPLAIN 看代价"，而不是"一定不能用"。
  - 减少扫描与回表：只 SELECT 需要的列（别 `SELECT *`）、用覆盖索引、深分页改游标式 `WHERE id > ? LIMIT 20`、`EXISTS` 常优于 `IN` 大列表、`HAVING` 能前移成 `WHERE` 就前移。
  - 事务侧：短事务、批量提交、按固定顺序加锁防死锁、避免在事务里做 RPC。
- 第 3 层：结构与配置。适度反范式减 JOIN、大表分区（按时间 RANGE 分区便于"删历史 = drop partition"）、垂直拆分（把大字段/低频列拆表，减行宽提缓存命中）与水平拆分（按用户 ID 哈希/范围分库分表）、连接池大小与 `innodb_buffer_pool_size`（物理内存 50%~70%）、`innodb_flush_log_at_trx_commit` 与 `sync_binlog` 的耐久/性能折中。
- 第 4 层：硬件与部署。NVMe、内存、独立实例、只读副本分流、必要时换引擎（分析型走 ClickHouse/列存）。
- 顺序判断的经验值：一条 SQL 从 2s 优化到 200ms 通常靠索引；从 200ms 到 20ms 靠减少往返和数据量；从"高峰期打不满"到"稳"靠缓存与拆分。

| 层次 | 手段举例 | 收益 | 代价 |
|---|---|---|---|
| 架构 | 缓存/预计算/读写分离 | 数量级 | 一致性复杂度 |
| SQL/索引 | 走索引、覆盖、深分页 | 10～100 倍 | 低 |
| 结构 | 分区、拆分、反范式 | 数倍 | 高（改动大） |
| 硬件 | 加内存/SSD | 有限 | 钱 |

> 💡 提示
> 面试答这题要给"排查动作"而不是"优化清单"：先说开慢查询日志抓 TOP 20、EXPLAIN 看 type 和 Extra、确认是扫描量问题还是往返次数问题，再谈手段。只报清单会被一句"你怎么知道该加索引"问回去。

> 🎯 关键要点
> - 先问该不该查，再问怎么查得快
> - EXPLAIN 的 type/rows/Extra 是判断依据
> - 索引失效看"列被包了东西"和选择性
> - 深分页与 SELECT * 是最常见的隐形成本
> - 拆分是最后手段，会永久增加复杂度
