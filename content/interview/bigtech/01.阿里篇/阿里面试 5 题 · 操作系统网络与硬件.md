## 网络与 I/O 多路复用（3 题）

### 1. 关于 epoll 和 select 的区别，以下哪些说法是正确的？（多选）｜中级

> 出题人：寈峰／阿里技术专家

题目选项：
- A. epoll 和 select 都是 I/O 多路复用的技术，都可以同时监听多个 I/O 事件的状态。
- B. epoll 相比 select 效率更高，主要基于操作系统支持的 I/O 事件通知机制，而 select 基于轮询机制。
- C. epoll 支持水平触发（LT）和边沿触发（ET）两种模式。
- D. select 能并行支持的 I/O 比较小，且无法修改。

核心结论：**ABC 正确，D 错误**。D 错在"无法修改"——select 的 fd 集合每次调用前都可以（而且必须）重新设置；它的真实短板是 `FD_SETSIZE` 默认 1024 这个编译期上限。

- 两者的本质差别（这题真正的考点）：

| 维度 | select | epoll |
|---|---|---|
| 监视集合传递 | 每次调用把 fd_set 从用户态全量拷进内核 | `epoll_ctl` 注册一次，常驻内核红黑树 |
| 就绪通知 | 内核遍历所有 fd 置位，返回后用户态还要自己遍历 | 就绪链表 + `epoll_wait` 只返回就绪 fd |
| 数量上限 | `FD_SETSIZE`（默认 1024） | 受 `/proc/sys/fs/epoll/max_user_watches` 限制，百万级 |
| 触发模式 | 只有水平触发 | LT + ET 可选 |
| 复用成本 | fd_set 被内核修改，每次要重建 | 无需重建 |
| 复杂度 | 每次 O(n) 扫描 | 就绪返回 O(1)，注册/删除 O(log n) |
| 跨平台 | POSIX，Windows 也支持（Winsock select） | Linux 特有（BSD 是 kqueue，Windows 是 IOCP） |

- 为什么 select 的连接数上限"低"其实是两件事：① `FD_SETSIZE` 是位图大小决定的编译期常量，改要重编内核/库；② 即便改大，每次调用全量拷贝 + 全量扫描的 O(n) 开销会让性能线性劣化。epoll 用"注册一次 + 只报告就绪"绕开了这两点。
- 原稿的【延伸】问题：高并发下用哪种触发更高效？用 ET 时注意什么？
  - **ET（边沿触发）更高效**的场景：连接数巨大、每连接事件稀疏。ET 只在状态**变化**时通知一次，避免 LT 下"缓冲区还有数据就一直返回"的重复 `epoll_wait` 唤醒，减少系统调用次数。
  - ET 的四条硬要求：① fd 必须是非阻塞的，否则会卡在读空的过程里；② 必须**循环读到 `EAGAIN`** 为止，一次没读干净就再也不会被通知（数据滞留）；③ 写同理，`EPIPE`/`EAGAIN` 要处理，半写状态要自己续写；④ 一个 fd 的处理不能被某个 worker 长时间独占，否则 ET 的"不重复通知"会放大成延迟毛刺。
  - 工程现实：nginx 用 ET + 非阻塞，很多框架（如 libevent/libuv 默认）用 LT——因为 LT 编程模型更简单、不易漏事件。**能说出"ET 快但难写对，多数框架选 LT"这个取舍，才是这题的高分线。**

> ⚠️ 注意
> 别把 epoll 说成"没有拷贝"。`epoll_wait` 仍要把就绪事件数组从内核拷到用户态，只是拷贝量从"所有被监视 fd"降到"就绪 fd"。epoll 的优势是**正比于活跃连接而非总连接**，这在 C10K/C100K 场景下才是决定性的。

> 🎯 关键要点
> - select 每次全量拷贝 + 全量扫描，开销正比于总连接数
> - epoll 注册一次，开销正比于就绪连接数
> - LT 简单不易漏事件，ET 快但必须读到 EAGAIN
> - FD_SETSIZE 是编译期上限，不是运行时参数
> - epoll 是 Linux 特性，跨平台要提 kqueue/IOCP

> 🔍 追问
> - epoll 内核里用什么结构存被监视 fd？为什么不是哈希表？
> - 一个连接上同时关心读写，ET 下要注意什么？
> - 为什么 Redis 用 epoll 却仍然是单线程模型？

### 2. 输入 `ping <IP>` 后敲回车，发包之前会发生什么？｜中级

> 出题人：怀虎／阿里云云效平台负责人

核心结论：从敲回车到第一个包离开网卡，依次经过"进程构造 ICMP 请求 → 路由决策选接口与下一跳 → ARP 解析下一跳 MAC → 组装 IP 包和以太网帧 → 交给驱动与网卡"，中间还有 netfilter 与队列规则。

- 完整链路（原稿答到了路由/掩码/ARP 三步，这里是完整版本）：
  1. **用户态**：`ping` 是 setuid 程序，构造 ICMP Echo Request（type 8、code 0，含 identifier + sequence + 时间戳载荷），通过 `sendto()` 写入 raw socket（`SOCK_RAW`/`IPPROTO_ICMP`）。
  2. **协议栈入口**：数据进入内核，经过 netfilter 的 `OUTPUT` 链（iptables/nftables 规则在此匹配）。
  3. **路由决策**：查路由表（`ip route`，含本地路由、缓存路由），依据目的 IP 选出**出接口**与**下一跳**；目的 IP 是本机地址则直接走 loopback。
  4. **是否同网段**：把目的 IP 与出接口子网掩码做 AND 比较——同网段则下一跳就是目的 IP 本身；不同网段则下一跳是默认网关。
  5. **邻居（ARP）解析**：查 ARP/邻居表拿下一跳的 MAC；命中就直接用，未命中则发 ARP Request **广播**（"谁是 10.0.0.1？请告诉我你的 MAC"），等 ARP Reply。这期间 ICMP 包被暂存在邻居队列里，解析成功后才继续发出（所以 ping 的第一个包延迟通常明显大于后面的）。
  6. **组包**：IP 层加 IP 头（源 IP、TTL、协议号 1、ID/flags/fragment offset，必要时按 MTU 分片或置 DF）；算 IP 头校验和。
  7. **链路层**：加以太网头（目的 MAC = 下一跳 MAC、源 MAC = 出接口 MAC、Type = 0x0800）与 FCS；`qdisc` 排队规则调度。
  8. **发送**：通过驱动写入网卡环形缓冲（`SO_SNDBUF` → DMA）、网卡发出；同时把解析到的 MAC 写入 ARP 缓存（后续包不再广播）。
- 因为题目特意指明"ping IP"，所以**没有 DNS 这一步**——如果给的是域名，第 1 步之前还要先走解析器（`/etc/hosts`、`nsswitch`、DNS 查询、`resolv.conf`）。面试里主动区分这两点很加分。
- 追问常考点：
  - "ping 不通但 curl 通"→ ICMP 被防火墙丢弃（`--icmp-unreachable` 或安全组不放行），TCP 端口却是开的。
  - "ping 的 TTL 能看出什么"→ 对端 TTL 减去沿途跳数，可粗略推断操作系统（Linux 默认 64，Windows 128，网络设备 255）。
  - "大包 ping 不通"→ MTU/PMTUD 问题，DF 置位后超过路径 MTU 的包被丢且 ICMP Need Frag 被拦。

> 💡 提示
> 这题不要背成"DNS→ARP→发包"的固定串。答题骨架应该是**分层**：应用（ICMP 报文）→ 网络（路由/下一跳/分片）→ 链路（ARP/MAC/帧）→ 驱动网卡。哪一层出问题对应哪类故障，这才是面试官想听的结构。

> 🎯 关键要点
> - 目标是 IP 时跳过 DNS，别乱加步骤
> - 路由表决定接口，掩码决定"同网段还是走网关"
> - ARP 解析的是**下一跳**的 MAC，不一定是最终目的 MAC
> - 首个 ping 慢是因为要等 ARP 应答
> - 分层作答，故障定位也按层来

> 🔍 追问
> - 跨网段通信时，以太网帧的目的 MAC 是谁？中途会变吗？
> - ping 同局域网另一台机器和 ping 公网 IP，路径差别在哪？
> - 为什么 ARP 是广播而不是单播？ARP 缓存会过期吗？

### 3. 把一个文件系统同时通过 NFS 和 SMB 共享给多台主机访问，以下哪些说法是**错误**的？（多选）｜高级

> 出题人：起影／阿里云文件存储高级技术专家

题目选项：
- A. 不可能有这样的操作，即把一个文件系统同时通过 NFS 和 SMB 协议共享给多个主机访问。
- B. 主机 a 的用户通过 NFS 创建的文件或目录，另一个主机 b 的用户不能通过 SMB 协议将其删除。
- C. 在同一目录下，主机 a 通过 NFS 看到 `file.txt`、主机 b 通过 SMB 也看到 `file.txt`，那么它们是同一个文件。
- D. 主机 a 通过 NFS、主机 b 通过 SMB，都可以通过主机端的数据缓存提升文件访问性能。

核心结论：官方参考答案给 **ABC**（即 D 是唯一正确的说法）。A、B 明显错误；**C 这一项有争议**，本页把争议讲清楚而不是照抄。

- A 错在哪：多协议同时导出同一份存储是 NAS 的基本能力（Samba/NetApp/Isilon/阿里云 NAS 都支持 NFS + SMB 双协议挂载同一个卷）。
- B 错在哪：底层是同一份文件系统，只要权限（NFS 的 uid/gid 或 SMB 的 ACL 映射）允许，跨协议删除完全可行。真正会出问题的是**权限模型不同**（NFS 靠 uid/gid + Unix 权限，SMB 靠 SID + ACL），映射配错时表现为"删不掉"，但那是配置问题不是协议限制。
- C 的争议：同一文件系统、同一目录下的同名条目，正常情况下**就是同一个文件**，所以说"不是同一个文件"并不成立。原稿把它判为错误说法，可能想表达的是两个真实陷阱：① **大小写敏感性不同**（NFS 区分大小写，SMB 默认不区分），`File.txt` 与 `file.txt` 在两种协议下可能指向不同对象；② **字符集/文件名规范化**与 8.3 短名映射差异。也就是说：结论"是同一个文件"在多数情况下成立，所以 C 被算作错误答案这件事本身值得质疑。
- D 为什么正确：客户端缓存是两种协议共有的性能手段——NFS 客户端有 attribute cache 与 page cache（`actimeo`），SMB 客户端也有句柄与缓存。
- 这题真正的考点（比 ABCD 更重要）：**多协议共享的一致性风险**
  - 文件锁不互通：NFS 的 POSIX lock / SMB 的 opportunistic lock 是两套体系，跨协议加锁挡不住对方。
  - 缓存不一致：a 端改了文件，b 端可能还在用缓存的属性/数据；NFSv4 有 delegation，SMB 有 oplock，但跨协议之间没有协调机制。
  - 权限与 ID 映射：uid/gid ↔ SID 的映射表配错，就会出现"能看不能改""能改不能删"。
  - 生产建议：同一份数据尽量只走一种协议；必须双协议时要统一 ID 映射、关闭或缩短客户端缓存、并在应用层避免并发写同一文件。

> ⚠️ 注意
> 遇到"有争议的标准答案"，正确答法是：**先给出官方答案，再说明哪一项站不住、以及它想考的真实知识点**。直接照抄或断言"答案错了"都不如这个处理方式——面试考的是判断力。

> 🎯 关键要点
> - 多协议导出同一卷是常规能力，A 显然错
> - 跨协议能读写删，前提是权限映射正确
> - C 有争议：同名同目录通常就是同一文件，陷阱在大小写与字符集映射
> - 真正的风险是锁不互通 + 缓存不一致
> - 有争议的答案要摊开讲，不要照抄

> 🔍 追问
> - NFSv3、NFSv4、pNFS 分别解决了什么问题？
> - 为什么 NFS 在无状态协议下还能做到 close-to-open 一致性？
> - 云上"文件存储 NAS"和"对象存储"的边界在哪？

## 计算机体系结构（2 题）

### 4. 一颗现代处理器每秒大概可以执行多少条简单的 MOV 指令？主要影响因素有哪些？｜高级

> 出题人：子团／创新产品虚拟化&稳定性资深技术专家

核心结论：量级在 **10¹⁰ 条/秒**（10~20 B mov/s）。原稿的"及格答案"是 1 条/周期 ≈ 主频，"加分答案"是超标量 + IPC；现代 CPU 上寄存器-寄存器 mov 甚至可以零开销消除，所以真实吞吐比主频高好几倍。

- 估算过程：3 GHz × 每周期 4~6 条（发射宽度）≈ 12~18 × 10⁹ 条/秒。但这是"独立指令"的上限，一旦有依赖链就掉到 3 × 10⁹（每周期 1 条，受流水线延迟限制）。
- 影响因素分层：
  - **频率**：主频给上限，但受功耗/温度墙动态调频（AVX 重负载会降频）。
  - **发射与执行宽度**：超标量，每周期可发射多条；端口（port）数量决定同类指令并行度。
  - **Move Elimination / Register Renaming**：现代微架构（Intel Sandy Bridge 之后、AMD Zen）把寄存器-寄存器 mov 在重命名阶段直接消除，不占执行端口——所以 mov 吞吐可以远高于"每周期 1 条"。
  - **依赖链**：连续 `mov eax, ebx; mov ebx, ecx;` 若形成真依赖，就只能按延迟串行，吞吐退化为 1/周期。
  - **乱序窗口（ROB 大小）**：决定能同时向前看多少条独立指令。
  - **寻址方式**：`mov rax, [mem]` 受 load 端口数与 cache 层级影响——L1 命中约 4~5 周期延迟，L2/L3 数十到上百周期，主存上百纳秒；`mov [mem], rax` 受 store 端口与 store buffer 限制。
  - **内存带宽与页**：跨页访问触发 TLB miss，大页（2MB/1GB）能显著改善。
  - **SMT/超线程**：同物理核的两个逻辑核共享端口，单线程吞吐会被摊薄。
  - **微码更新与缓解措施**：某些 Spectre/MDS 缓解会引入额外开销，影响实际吞吐。
- 面试应答框架（比背数字重要）：先给量级和推导（频率 × 每周期条数），再说明"取决于mov 的类型"——寄存器-寄存器、立即数、访存三类完全不同，最后落到"实际程序里 mov 吞吐几乎从不瓶颈，真正卡住的是访存层级"。

> 💡 提示
> 这题的隐含考点是"你会不会做数量级估算并说清假设"。开口就报一个精确数字而不给推导，比报出 10¹⁰ 并说明"这是独立 reg-reg mov 的上限、有依赖链就退到 3×10⁹"要差得多。

> 🎯 关键要点
> - 量级 10¹⁰，推导 = 主频 × 每周期条数
> - 寄存器 mov 可被 move elimination 零开销消除
> - 依赖链把吞吐压回 1 条/周期
> - 访存 mov 的瓶颈是 cache 层级与 TLB，不是指令本身
> - 答题要给假设，不给假设的数字没有意义

> 🔍 追问
> - 为什么"程序里 mov 很多"通常不是性能问题？
> - 大页为什么能提升访存密集型程序的性能？
> - 你怎么实测一台机器的 mov 吞吐？（`perf stat`、IPC、依赖链微基准）

### 5. 请计算 XILINX VU9P 芯片的算力相当于多少 TOPS，给出计算过程与公式。｜高级

> 出题人：隐达／阿里云异构计算资深专家

核心结论：`TOPS = 计算单元数 × 每单元每周期操作数 × 频率 × 2（MAC 记两次操作）`。按 VU9P 的 6840 个 DSP48E2、约 500~600 MHz、INT8 每 DSP 每周期 1 次乘加估算，量级是**个位到十几 TOPS**；用 LUT 算术或 1-bit/二值化网络可以到几十以上——原稿说"十几到几百"，指的就是这个"随量化位宽和实现方式剧烈变化"的区间。

- 公式与代入（这是本题唯一稳定的答案）：

```
TOPS = N_unit × ops_per_unit_per_cycle × f × K
     = 6840 (DSP) × 1 (INT8 MAC) × 0.55 GHz × 2  ≈ 7.5 TOPS
```

  其中 MAC（乘加）算 2 次操作，所以 ×2；把 INT8 拆成 DSP 内部两个 4×4 或做 2 路复用，`ops_per_unit_per_cycle` 就翻倍，数字随之上升。
- 为什么同一个芯片能报出相差几十倍的 TOPS：
  - **量化位宽**：INT8 → INT4 → 1-bit（XNOR + popcount），每周期可完成的操作数成倍增加；1-bit 场景下用 LUT 实现能冲到几十甚至上百 TOPS。
  - **实现载体**：DSP48E2 硬核 vs LUT 软算术 vs 级联脉动阵列，效率差别很大。
  - **频率**：FPGA 的实际可达频率取决于布线与阵列规模，500 MHz 与 700 MHz 差 40%。
  - **是否算稀疏**：结构化稀疏可以再"翻倍"，但要说明是理论峰值。
- 结论式回答（原稿的核心观点，值得原样保留）：**单论峰值算力，FPGA 相比 GPU/ASIC 并不占优，多数时候还明显落后**；FPGA 的价值在于① 可重构，能为具体算法定制数据通路；② 延迟低且确定（没有 batch 等待）；③ 功耗比高（每瓦 TOPS）；④ 接口可编程，能做近存计算与协议桥接。所以选 FPGA 的理由应该是"延迟/功耗/定制"，不是"算力大"。
- 诚实声明：上面的 7.5 TOPS 是**按公开规格推导的量级估算**，不是官方标称值；Xilinx/AMD 对 VU9P 的标称随产品线（VCU118、Alveo U200 等）与文档口径不同。面试时先给公式和假设，再给区间，比背一个数字安全得多。

> ⚠️ 注意
> 千万别把 TOPS 当性能。TOPS 是理论峰值，实际有效算力受**内存带宽**（模型权重要反复搬进来）与算子映射效率支配——这就是"100 TOPS 的加速卡跑实际模型只有 20 TOPS 利用率"的原因。能主动提"算力利用率/roofline"，这题就从背参数变成了懂体系结构。

> 🎯 关键要点
> - TOPS = 单元数 × 每单元每周期操作数 × 频率，MAC 记 2 次操作
> - 量化位宽一变，同一个芯片的 TOPS 能差几十倍
> - VU9P 的 INT8 DSP 路线量级是个位到十几 TOPS
> - FPGA 卖的是延迟/功耗/可重构，不是峰值算力
> - 报数字必须先报假设
