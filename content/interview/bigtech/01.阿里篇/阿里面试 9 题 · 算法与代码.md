## 链表与树（3 题）

### 1. 给定一个链表，删除链表的倒数第 N 个节点并返回头结点，只允许一次遍历。｜初级

> 出题人：屹平／阿里云视频云边缘计算高级技术专家

核心结论：用间隔固定为 N 的双指针——快指针先走 N+1 步，然后两者同步前进，快指针到尾时慢指针正好停在待删节点的**前驱**上，一次遍历完成，配 dummy 头处理删首节点。

- 关键设计：让 `first` 从 `dummy` 起走 `n+1` 步，则 `first` 与 `second` 之间恒隔 n 个节点；`first` 走到 `null` 时 `second.next` 就是倒数第 n 个。
- 为什么必须从 dummy 起：删除头节点时前驱不存在，用哨兵统一成"永远有前驱"，省掉一个特判分支。

```java
public ListNode removeNthFromEnd(ListNode head, int n) {
    ListNode dummy = new ListNode(0);
    dummy.next = head;
    ListNode first = dummy, second = dummy;
    for (int i = 1; i <= n + 1; i++) first = first.next;  // 拉开 n+1 的间距
    while (first != null) { first = first.next; second = second.next; }
    second.next = second.next.next;                        // 跳过目标节点
    return dummy.next;
}
```

- 复杂度：时间 O(L)、空间 O(1)，L 为链表长度，且只遍历一次。
- 反例写法：先遍历求长度 L 再走 L-n 步——两趟，不满足"一次遍历"的要求（但工程上完全可用，面试要说清约束）。

> 🎯 关键要点
> - 间距恒定是双指针解法的核心不变式
> - dummy 节点消掉"删头节点"的特判
> - 一次遍历是题目约束，不是性能必需
> - 改指针前先把待删节点存下来，避免断链后找不到

> 🔍 追问
> - 如果 N 大于链表长度怎么办？
> - 双向链表删除有什么额外要注意的？
> - 并发环境下"删除节点"安全吗？

### 2. 如何实现一个高效的单向链表逆序输出？｜中级

> 出题人：昀龙／阿里云弹性人工智能负责人

核心结论：单向链表不能倒着走，所以"逆序输出"只有三条路——借栈/递归（O(n) 额外空间）、先原地反转再顺序输出（O(1) 空间但改结构）、或求长度后正向跳步（O(n²)）。要求"高效"就答前两条并说明取舍。

- 方案一，递归（最短，但栈深度 = 链表长度，长链表会栈溢出）：

```cpp
void printReverse(Node* head) {
    if (!head) return;
    printReverse(head->next);   // 先递归到尾部
    std::cout << head->data << "\t";
}
```

- 方案二，显式栈（把递归的隐式栈换成自己的，可控制上限）：`while (p) { st.push(p); p = p->next; }` 然后弹栈输出。
- 方案三，原地反转后输出（O(1) 空间，会改变链表结构；若要求"不破坏原链表"，输出完再反转回来）：

```cpp
Node* reverse(Node* head) {          // 标准三指针反转，head 是首节点（非哨兵）
    Node *prev = nullptr, *cur = head;
    while (cur) { Node* nxt = cur->next; cur->next = prev; prev = cur; cur = nxt; }
    return prev;
}
```

- 关于原稿代码：它假设 `head` 是**哨兵头节点**（数据从 `head->next` 开始），所以内部用 `pcur = head->next` 起步、并在末尾 `head->next = pcur` 重挂——换成无哨兵的写法会直接错。面试时先确认"有没有哑节点"，这是链表题最常见的失分点。
- 复杂度对比：

| 方案 | 时间 | 额外空间 | 是否改结构 |
|---|---|---|---|
| 递归 | O(n) | O(n) 栈 | 否 |
| 显式栈 | O(n) | O(n) | 否 |
| 反转再输出 | O(n) | O(1) | 是 |
| 求长后跳步 | O(n²) | O(1) | 否 |

> ⚠️ 注意
> "高效"要落到具体维度：时间都是 O(n)，差别在**空间**和**是否允许改链表**。开口就写递归而不提栈溢出风险，是这题最典型的扣分方式。

> 🎯 关键要点
> - 三选一：栈换空间 / 反转换结构 / 跳步换时间
> - 递归深度等于长度，长链表必栈溢出
> - 先确认有无哨兵头节点再动手
> - 面试要主动问"能不能修改原链表"

> 🔍 追问
> - 链表有 10 亿个节点，只能读一次，怎么逆序输出？
> - 如果链表带环，上面的方法哪个会挂？怎么先判环？

### 3. 给定一个二叉搜索树（BST），找到树中第 K 小的节点。｜中级

> 出题人：文景／阿里云 CDN 资深技术专家

核心结论：BST 的中序遍历就是升序序列，所以"第 K 小"= 中序遍历第 K 个——用迭代中序、数到 K 就返回，提前退出，复杂度 O(H + K)。

- 最直白：迭代中序（显式栈），走到第 K 个即停：

```python
def kth_smallest(root, k):
    stack, cur = [], root
    while stack or cur:
        while cur:                 # 一路向左压栈
            stack.append(cur); cur = cur.left
        cur = stack.pop()          # 此处访问的就是下一个最小值
        k -= 1
        if k == 0: return cur.val
        cur = cur.right
```

- 原稿的解法（分治 + 计数）同样正确：递归返回 `(是否找到, 子树节点数)`，若左子树节点数 == K-1 则当前根即答案，否则递归右子树。适合"树节点里已维护 size 字段"的场景，可做到 O(H)。
- 如果会被高频查询（例如每次插入都要问第 K 小）：在每个节点上维护 `size`（左子树节点数 + 1），查询变成纯下降路径 O(H)；插入/删除时沿路径更新 size。这是"顺序统计树"的思路。
- 复杂度：迭代中序 O(H + K) 时间、O(H) 栈空间，H 为树高；退化成链表时 H = N。
- 边界：K 从 1 计数；题目保证 `1 ≤ K ≤ 节点数`，但工程代码仍要在遍历结束时返回"未找到"。

> 💡 提示
> 面试里"中序遍历"三个字不够。要说清三件事：① 为什么中序有序（BST 定义）；② 用迭代而不是先存成数组（能提前退出，省 O(N) 空间）；③ 如果要反复查询，就在节点上缓存子树大小。

> 🎯 关键要点
> - BST 中序 = 升序，这是本题唯一的知识点
> - 迭代中序可提前退出，别先展平成数组
> - 反复查询 → 节点维护 size，降到 O(H)
> - 递归返回 (found, count) 是原稿思路，也正确
> - 退化成链表时 H=N，要主动提

> 🔍 追问
> - 树很大但 K 很小，还有优化空间吗？
> - 如果这棵树会频繁增删，第 K 小查询怎么保持高效？
> - 不是 BST、只是普通二叉树呢？

## 哈希与缓存设计（3 题）

### 4. 给定一个整数数组和一个目标整数，返回两个元素之和等于目标的**下标**，要求最优算法并分析时空复杂度。｜初级

> 出题人：屹平／阿里云视频云边缘计算高级技术专家

核心结论：一遍哈希表——遍历到 `x` 时查 `target - x` 是否已出现过，命中即返回；把 O(n²) 的双层循环降到 O(n) 时间、O(n) 空间。

```java
public int[] twoSum(int[] nums, int target) {
    if (nums == null || nums.length < 2) return new int[]{-1, -1};
    Map<Integer, Integer> seen = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer j = seen.get(nums[i]);        // 之前有没有人需要 nums[i]
        if (j != null) return new int[]{j, i};
        seen.put(target - nums[i], i);        // 我还需要 target-nums[i]
    }
    return new int[]{-1, -1};
}
```

- 原稿写法就是把 `target - nums[i]` 当 key 存（"我需要什么"），命中即返回；更常见的写法是存"已见过的值 → 下标"，查 `target - nums[i]`。两者等价，选一种讲清楚即可。
- 复杂度：时间 O(n)、空间 O(n)，是"用空间换时间"的教科书例子。
- 为什么必须"边遍历边存"而不是先建全表：先建全表会让 `[3,3], target=6` 这类重复值把自己配对自己；边遍历边查天然保证两个下标不同。
- 变体：① 数组已排序 → 对撞双指针，O(1) 空间；② 返回所有不重复三元组（三数之和）→ 排序 + 固定一个 + 双指针 + 去重；③ 数据放不进内存 → 分片/外部排序后双指针。

> 🎯 关键要点
> - 一遍哈希，存"需要的补数"或"已见的值"都行
> - 边遍历边查避免自己配自己
> - 排序数组场景改用双指针省空间
> - 复杂度要报"为什么是 O(n)"，不是背结论

> 🔍 追问
> - 如果要求返回的下标从 1 开始 / 数组有重复元素，代码怎么改？
> - 数据量 100 亿、内存放不下，还能怎么做？

### 5. 设计和实现一个 LRU 缓存，支持 get 和 put，容量满时淘汰最久未使用。｜高级

> 出题人：文景／阿里云 CDN 资深技术专家

核心结论：哈希表 + 双向链表，两个结构互相持有指针，`get`/`put` 都是 O(1)；哈希表负责定位，链表负责维护使用顺序（头=最近，尾=最久）。

- 为什么必须是这两个结构：数组/链表能保序但查找 O(n)；哈希表查找 O(1) 但不保序。要"O(1 查找 + O(1) 调整顺序"，只有"哈希表指向双向链表节点"这一条路（双向是为了 O(1) 摘除任意节点）。
- 原稿用 `dict + list`，`keys.remove(key)` 是 O(n) 线性查找，整体退化为 O(n) 操作——这是这题最常见的错误实现，面试时会被当场指出。

```python
class Node:
    __slots__ = ('key', 'val', 'prev', 'next')
    def __init__(self, key=0, val=0):
        self.key, self.val = key, val
        self.prev = self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.map = {}
        self.head, self.tail = Node(), Node()      # 哨兵，省掉所有空判断
        self.head.next, self.tail.prev = self.tail, self.head

    def _remove(self, n):
        n.prev.next, n.next.prev = n.next, n.prev

    def _add_front(self, n):
        n.next = self.head.next
        n.prev = self.head
        self.head.next.prev = n
        self.head.next = n

    def get(self, key):
        n = self.map.get(key)
        if not n: return -1
        self._remove(n); self._add_front(n)        # 命中即"最近使用"
        return n.val

    def put(self, key, value):
        n = self.map.get(key)
        if n:
            n.val = value
            self._remove(n); self._add_front(n)
            return
        if len(self.map) == self.cap:
            old = self.tail.prev                   # 尾部就是最久未使用
            self._remove(old); del self.map[old.key]
        n = Node(key, value)
        self.map[key] = n
        self._add_front(n)
```

- 三个易错点：① `put` 已存在的 key 也要刷新使用顺序；② 淘汰时要同时删链表节点和哈希表项（否则内存泄漏）；③ 节点里必须存 `key`，因为哈希表删除需要 key，而链表只给得出 value。
- 工程捷径：Python `OrderedDict`（`move_to_end` + `popitem(last=False)`）、Java 继承 `LinkedHashMap(capacity, 0.75f, true)` 并重写 `removeEldestEntry`。面试要先手写、再提"实际项目用库"。
- 延伸：LRU 的弱点是"偶发大批量扫描污染缓存"（一次全表扫把热数据全挤掉）→ LFU（按频次，但要处理衰减）、2Q/LIRS（用两级队列抵御扫描）、Redis 的近似 LRU（随机采样 5 个候选）。

> ⚠️ 注意
> 说"我用 OrderedDict 一行搞定"之前，先确认面试官要的是 API 熟练度还是数据结构设计能力。这题放在阿里卷里，考的就是双向链表指针操作——手写一遍再提库，才是安全答案。

> 🎯 关键要点
> - O(1) 的唯一路径：哈希表 + 双向链表互指
> - 原稿的 list.remove 是 O(n)，是典型错误
> - 节点必须冗余存 key，否则淘汰时删不掉哈希项
> - 哨兵头尾节点能省掉一半边界判断
> - LRU 会被扫描污染，要知道 LFU/2Q 的存在

> 🔍 追问
> - 要支持 TTL 淘汰，你的结构怎么改？
> - 多线程下的 LRU 怎么做？加锁会不会成为瓶颈？
> - LFU 为什么需要 O(1) 的"频次桶 + 每桶双向链表"？

### 6. 实现 FreqStack：push(x) 入栈，pop() 弹出出现频率最高的元素，频率相同则取最接近栈顶的那个。｜高级

> 出题人：屹平／阿里云视频云边缘计算高级技术专家

核心结论：按"频率"分层建栈——`group[f]` 存所有当前频率为 f 的元素，`freq[x]` 记每个元素的频率，`maxfreq` 记当前最高频率；push/pop 都是 O(1)。

- 为什么分层能同时满足两个要求：同一频率层内用栈保存，天然"后进先出"，所以弹出层顶就是"频率最高里最新的那个"；`maxfreq` 直接指出该弹哪一层。
- 关键细节（原稿点到了但容易看漏）：`push(x)` 时 `f = ++freq[x]`，然后把 x 压入 `group[f]`——不是只压最高层。因为一个元素的第 i 个副本属于第 i 层，弹出后它的频率要退到第 i-1 层继续参与竞争。

```python
class FreqStack:
    def __init__(self):
        self.freq = collections.Counter()
        self.group = collections.defaultdict(list)
        self.maxfreq = 0

    def push(self, x):
        f = self.freq[x] + 1
        self.freq[x] = f
        if f > self.maxfreq: self.maxfreq = f
        self.group[f].append(x)          # 压进第 f 层

    def pop(self):
        x = self.group[self.maxfreq].pop()   # 最高层的栈顶
        self.freq[x] -= 1
        if not self.group[self.maxfreq]:
            self.maxfreq -= 1               # 该层空了才降层
        return x
```

- 示例走查：push 5,7,5,7,4,5 → 第 3 层 [5]，第 2 层 [7,5,7]，第 1 层 [5,7,4]；pop 依次得 5、7、5、4，与题目一致。
- 复杂度：push/pop 均 O(1) 时间，空间 O(N)。
- 反例：每次 pop 全表扫描统计频率 → O(N) 一次；用优先队列 + 惰性更新 → O(log N) 且要处理"频率变了但堆里还是旧值"，都不如分层栈干净。

> 💡 提示
> 这题的转折点是想明白"频率相同的元素，谁更新"这件事**已经由入栈顺序隐式记录了**——所以不需要时间戳，只要每个频率一层栈。把这句话讲出来，比写对代码更能证明你的算法感觉。

> 🎯 关键要点
> - 分层栈：频率当层号，层内保持入栈序
> - push 要压进"该元素自己的当前频率层"，不是最高层
> - maxfreq 只在当前层空时才下降
> - O(1) 来自"频率变化只影响相邻层"
> - 堆/全表扫都是更差的解

> 🔍 追问
> - 如果 pop 要求"频率相同取最**旧**的"，结构怎么改？
> - 要支持 `peek()`（不弹出）怎么办？
> - 这个结构能改造成 LFU 缓存吗？差在哪？

## 数值与语言陷阱（3 题）

### 7. 已知 sqrt(2) ≈ 1.414，要求不用数学库，求 sqrt(2) 精确到小数点后 10 位。｜中级

> 出题人：文景／阿里云 CDN 资深技术专家

核心结论：二分查找能解（收敛线性、约 30 次到 1e-10），牛顿迭代法更好（二次收敛、5~6 次就到）；这题真正的考点是**退出条件怎么写**和**浮点精度边界**。

- 二分：在 `[1.4, 1.5]` 上取 `mid`，`mid*mid > 2` 则收上界，否则收下界。

```cpp
const double EPS = 1e-12;                 // 比目标精度高一个量级
double sqrt2_bisect() {
    double lo = 1.4, hi = 1.5, mid = (lo + hi) / 2;
    while (hi - lo > EPS) {
        mid = (lo + hi) / 2;
        if (mid * mid > 2) hi = mid; else lo = mid;
    }
    return mid;
}
```

- 牛顿迭代（求 `x² - 2 = 0` 的根，`x ← (x + 2/x) / 2`）：

```cpp
double sqrt2_newton() {
    double x = 1.5;
    while (std::abs(x * x - 2) > 1e-12) x = (x + 2.0 / x) / 2.0;
    return x;
}
```

- 退出条件的三个坑：① 用 `hi - lo > EPS` 时 EPS 要比目标精度小一个量级（区间半宽才是误差上界）；② 用 `mid*mid == 2` 判等永远不成立（浮点不可达）；③ 用"前后两次 mid 之差 < EPS"也可以，但初值很差时前几步差值可能震荡。
- 精度天花板：`double` 是 53 位尾数 ≈ 15~17 位十进制有效数字。要 1e-10 的绝对精度（约 10 位小数）完全够；但如果题目改成"精确到 1e-16"，就必须换 `long double`/高精度库，或者用定点整数迭代——这是这题的隐藏考点。
- 迭代次数对比：二分从 0.1 区间到 1e-12 需 `log2(1e11) ≈ 37` 次；牛顿二次收敛，从 1.5 起约 5 次。

> 🎯 关键要点
> - 两种方法都要会说，牛顿是加分项
> - EPS 要比目标精度更严，区间半宽即误差
> - 浮点判等不可用，`==` 是错的
> - double 有效位约 15~17 位，是硬天花板
> - 通用形式：`sqrt(a)` 的牛顿迭代是 `x ← (x + a/x)/2`

### 8. 如何实现两个金额数据相加（最多小数点后两位）？｜中级

> 出题人：御术／蚂蚁金服数据可视化高级技术专家

核心结论：不要用浮点直接加。金额一律"转成分（整数）运算，展示时再格式化"；JS 里连 `x*100` 都可能失精，所以转整数也要走字符串或 BigInt。

- 为什么会错：`0.1 + 0.2 === 0.30000000000000004`，因为二进制无法精确表示 0.1；`1.005 * 100 === 100.49999999999999`，所以"乘 100 取整"本身就会把 1.005 变成 100 而不是 101。
- 三层坑（原稿列的顺序正是面试追问的顺序）：
  1. 浮点直接加 → 失精。
  2. 乘 100 / 除 100 也是浮点运算 → 仍然失精，必须用字符串拆位或整数运算。
  3. 先 `toFixed(2)` 再拆位 → `1.5` 变 `"1.50"` 没问题，但对已经是字符串或只有一位小数的输入处理不一致，容易错对齐。
- 稳妥实现（字符串拆位 + 整数加，避免任何浮点）：

```js
function parseCents(s) {                       // "12.3" -> 1230n
  const [i, f = ''] = String(s).split('.');
  const frac = (f + '00').slice(0, 2);         // 补齐两位，多余位直接截断需按规则处理
  return BigInt(i) * 100n + BigInt(frac);
}
function addMoney(a, b) {
  const total = parseCents(a) + parseCents(b);
  const sign = total < 0n ? '-' : '';
  const t = (total < 0n ? -total : total).toString().padStart(3, '0');
  return `${sign}${t.slice(0, -2)}.${t.slice(-2)}`;
}
addMoney('1.005', '2.99');                     // "4.00"（截断规则按业务定）
```

- 工程正解（比手写更该说）：① 服务端全链路用最小货币单位（分）存整数，DB 用 `DECIMAL(18,2)`；② 前端用 `decimal.js` / `big.js` / `intl.NumberFormat` 只做展示；③ Java 用 `BigDecimal`（且必须用字符串构造，`new BigDecimal(0.1)` 就是错的）。
- 隐藏关卡（原稿明说是加分点）：金额可能超过 `Number.MAX_SAFE_INTEGER`（2^53-1 ≈ 9e15，即 90 万亿元），所以累加要用 BigInt 或字符串加法；这也引出"有效循环、遍历、算法复杂度"的讨论。
- 别忘了规则问题：舍入策略（银行家舍入 vs 四舍五入）、负数、不同币种小数位（日元 0 位、第纳尔 3 位）——主动问一句"舍入规则和币种是什么"，是这题最能加分的动作。

> ⚠️ 注意
> `toFixed` 不是可靠的舍入：`(1.005).toFixed(2)` 得到 `"1.00"`（因为 1.005 的实际二进制值略小于 1.005）。所以"格式化时再舍入"是错序——舍入必须在精确值上完成，格式化只是最后一步。

> 🎯 关键要点
> - 金额用整数分表示，永远不要用 float/double
> - 乘 100 转整数也会失精，要走字符串或 BigInt
> - toFixed 不可信，舍入要在精确值上做
> - 超过 2^53 的累加必须 BigInt
> - 主动确认舍入规则与币种小数位

### 9. 评估这段程序的输出结果？｜高级

> 出题人：桃谷／阿里云中间件技术专家

```java
BlockingQueue<Integer> queue = new SynchronousQueue<>();
System.out.print(queue.offer(1) + " ");
System.out.print(queue.offer(2) + " ");
System.out.print(queue.offer(3) + " ");
System.out.print(queue.take() + " ");
System.out.println(queue.size());
```

选项：A. `true true true 1 3`　B. `true true true (阻塞)`　C. `false false false null 0`　D. `false false false (阻塞)`

核心结论：**选 D**。`SynchronousQueue` 容量为 0，不存元素；没有配对消费者时 `offer` 立即返回 false，而单线程里后面的 `take()` 永远等不到配对，直接阻塞。

- 逐步推演：`offer(e)` 是非阻塞入队——只有当另一个线程**恰好正在 `take` 等待**时才成功。这里全程单线程、无消费者，所以三次 `offer` 都返回 `false`，队列里没有任何元素。
- 走到 `take()`：无等待中的生产者 → 线程挂起，程序停在第三行之后，`queue.size()` 那行永远执行不到。所以输出是 `false false false ` 然后阻塞。
- 为什么不是 C：`take()` 不会返回 null（阻塞队列的 `take` 语义是"阻塞直到拿到元素"，返回 null 的是 `poll(timeout)` 之外的 `poll()`）。
- 关键知识点：
  - `SynchronousQueue` 的 `size()` **恒为 0**，`iterator()` 恒为空——它不是队列，是一个"手递手交接点"（handoff）。
  - `put()` 与 `offer()` 的区别：`put` 会阻塞等待配对（所以 `put(1)` 会卡在第一次调用），`offer` 立即返回 false。
  - 公平模式：`new SynchronousQueue<>(true)` 用栈式交接（LIFO，公平但吞吐低），默认非公平用队列式交接。
  - 真实用途：`Executors.newCachedThreadPool()` 的核心队列就是 `SynchronousQueue`——它保证"有空闲线程就复用，没有就新建"，绝不在队列里囤任务。这也是这题在阿里卷里出现的真正意图。

| 方法 | 无配对者时的行为 |
|---|---|
| `offer(e)` | 立即返回 false |
| `put(e)` | 阻塞等待 |
| `take()` | 阻塞等待 |
| `poll()` | 立即返回 null |
| `size()` | 恒为 0 |

> 💡 提示
> 这题答对只是及格。加分动作是主动补一句："它其实不是队列而是 handoff 机制，JDK 的 cachedThreadPool 用它来避免任务堆积——因为一旦允许堆积，线程池就会退化成一堆线程等一个队列。"这就把一道选择题答成了设计题。

> 🎯 关键要点
> - SynchronousQueue 容量 0、size 恒 0
> - offer 非阻塞、put 阻塞，这是本题的判分点
> - take 只会阻塞不会返回 null，排除 C
> - 单线程跑这段必然卡死在 take
> - 它在 newCachedThreadPool 里的作用是"不囤任务"
