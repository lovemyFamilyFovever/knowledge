## 高并发与分布式任务（3 题）

### 1. 为什么鹿晗公布恋情的时候微博系统会崩溃？如何解决？｜高级

> 出题人：江岚／阿里巴巴数据技术高级技术专家

核心结论：崩溃的本质是**流量结构瞬间偏离容量假设**——单条微博的读请求在几秒内冲到平时的千倍，而按用户 ID 分片的存储与缓存把这个热点全部压到了同一个分片上。原稿给的三个方向（读写扩散比、发布频率远低于阅读、按明星区别分片）正是这个问题的三个切面。

- 原稿三个要点的展开：
  - **A. pull 还是 push**：微博是典型的"读多写少 + 一对多扇出"。写扩散（发一条就推送到所有粉丝的收件箱）在读侧极快，但大 V 发一条要写几千万个收件箱，写放大不可接受；读扩散（读的时候现拉关注列表再合并）写侧便宜，但读放大严重。真实系统是混合：普通人写扩散，超大 V 读扩散（或"推拉结合 + 粉丝侧增量合并"）。
  - **B. 发布频率远小于阅读**：所以优化重心在读侧——多级缓存、静态化、CDN，而不是继续优化写路径。
  - **C. 流量明星要区别对待**：分片键如果只用 `user_id`，那么"鹿晗的所有微博"永远落在同一个分片上，热点无法靠加机器解决。要么对热点数据单独打散（一条微博一个 key，按 `post_id` 分片），要么把热点内容整体挪到缓存层/独立热点池。
- 崩溃链路的完整推演（面试要能讲出这条链）：
  1. 一条微博发布 → 数千万粉丝的首页时间线都要包含它。
  2. 缓存里这条微博与其时间线的 key 是同一个热点 key，命中同一个 Redis 分片/同一个 DB 分片。
  3. 缓存过期或被挤出的瞬间，海量请求同时穿透到 DB（**缓存击穿**），DB 连接池打满。
  4. 上游超时 → 用户重试 → 请求量进一步放大；同时依赖它的服务也被拖垮（**雪崩式级联**）。
  5. 单分片 CPU/连接/带宽先到极限，加机器无用，因为热点没有被打散。
- 解决方案（按层给，别混成一锅）：

| 层 | 手段 | 解决什么 |
|---|---|---|
| 接入 | CDN/静态化、页面片段缓存 | 把绝大部分读挡在最外面 |
| 网关 | 限流、排队、防重复请求（合并相同 in-flight 查询） | 保住后端不被打死 |
| 缓存 | 热点自动识别 + key 打散多副本（`post_1_{id}`…`post_n_{id}` 随机读）、本地缓存 L1 + 集中 L2、逻辑过期不失效、永不过期的热点常驻 | 击穿与单分片热点 |
| 存储 | 按 post_id 分片、读写分离 + 只读副本、冷热分离、热点数据独立实例 | 单分片容量上限 |
| 消息 | 写路径异步化削峰、粉丝时间线用队列增量合并 | 写放大 |
| 架构 | 熔断降级（返回"该微博太火爆"而非 500）、隔离（热点业务独立集群）、弹性扩容预案 | 防止级联失败 |
| 流程 | 大促/热点事件前的预热与全链路压测、预案演练 | 把突发变成可预期 |

- 关键判断：**热点要"识别 + 隔离"，不是"扩容"**。加机器解决不了单分片热点，只有打散 key、独立热点池、本地缓存这三件事能。热点识别可以靠实时统计（访问频次 TopK、Redis `--hotkeys`/LFU 统计），识别后自动多副本化。
- 降级要设计成"业务可接受的错"：首页时间线缺一条微博是可以的，整站 502 不行。所以优先级是"局部数据缺失 > 兜底文案 > 服务不可用"。

> ⚠️ 注意
> 这题最忌只答"加缓存、加机器"。面试官在听三件事：① 你说不说得清写扩散/读扩散的取舍；② 你知不知道"单分片热点加机器无效"；③ 你有没有"降级与预案"的运维视角。三条都覆盖，才叫答完。

> 🎯 关键要点
> - 根因是流量结构突变 + 分片键造成单点热点
> - 写扩散便宜读、读扩散便宜写，大 V 要混合策略
> - 缓存击穿是压垮 DB 的临门一脚，要逻辑过期/互斥回源
> - 热点靠打散与隔离解决，不靠扩容
> - 降级方案要提前设计并演练，不是临时决定

> 🔍 追问
> - 一个热点 key 打散成 100 个副本，会带来什么新问题？
> - 缓存和 DB 双写不一致，你在微博场景下怎么处理？
> - 怎么在事件发生前 5 分钟发现"要爆了"？

### 2. 有一批邮件要发给订阅客户，由一个节点数会动态扩缩容的集群负责发送，如何让系统尽快完成？｜高级

> 出题人：江岚／阿里巴巴数据技术高级技术专家

核心结论：把"任务"和"执行者"解耦——任务放在可抢占的共享队列里，节点上线就领任务、下线后任务由租约超时自动回收重发。原稿给的三个方案（消息中间件订阅、主从分配、数据库 `UPDATE ... RETURNING` 互斥）是同一思想的三种实现，各有适用边界。

- 原稿三方案的展开与评价：
  - **A. 消息中间件 + 发布订阅**：任务投递到 Kafka/RocketMQ，消费者组自动做分区再平衡，天然支持动态扩缩容与水平并行。优点是吞吐高、有削峰；**难点是"进度可见 + 精确一次"**——消费者重启会重平衡导致任务重分配，且必须靠幂等防止重复发送。
  - **B. master-slave，由 master 分配任务**：调度逻辑集中，进度与优先级容易控制，适合"要精确知道还剩多少、谁在做哪一批"的场景。代价是 master 是单点（要做主备或选主），并且要处理 worker 失联后的任务回收。
  - **C. 不依赖中间件，靠数据库实现节点互斥**：所有节点平等，用 `UPDATE task SET owner=?, status='doing', lease=now()+60s WHERE status='pending' LIMIT 200 RETURNING *` 抢占任务。PostgreSQL 原生支持 `RETURNING`；MySQL 没有 `UPDATE...RETURNING`，等价写法是 `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 200` + 同一事务里 UPDATE。优点是零额外组件、天然持久化；代价是数据库成为瓶颈与耦合点，任务量大时要分片或换队列。
  - 选型建议：任务数在十万级以内、不想加组件 → C；百万级以上、要削峰 → A；要精细优先级与全局进度 → B（或 A+B：Kafka 承载 + 独立协调者记录进度）。
- 光有分发机制远远不够，还要解决这六件事：
  1. **幂等与去重**：同一封邮件绝不能发两次。每个任务有唯一 ID + 状态机（pending → doing → sent/failed），发送前先落"已发送"记录；重发要能识别"上次到底发出去了没有"（租约到期不代表失败，可能已发送未记录）。
  2. **租约与失联回收**：节点领取任务时写 `lease`，心跳续租；超时未续租的任务被其他节点抢走。这是动态扩缩容下不丢不重的唯一办法。
  3. **限速而不是无限并发**：邮件发送的真实瓶颈是**对端**——SMTP 网关有连接数与每分钟投递上限，同一收件域（如 qq.com）还有域名级并发限制与信誉评级。所以并发要按"收件域 + 出口 IP 池"分维度限流，超发会导致整批被拒甚至域名进黑名单。
  4. **失败重试与死信**：临时错误（连接超时、451 灰名单）退避重试；永久错误（550 地址不存在）直接标记并回收列表质量；重试耗尽进死信表人工看。
  5. **优先级与公平**：VIP 客户的邮件要能插队，但不能让普通批次饿死（加权 + 老化）。
  6. **进度与可观测**：已发/成功/失败/待发四个数要实时可查，能按收件域看成功率——这是运营判断"要不要继续发"的依据。
- 一个常被忽略的提速手段：**连接复用与会话合并**。SMTP 握手成本高，同一收件域的多封邮件应复用同一条连接（pipeline），并按收件域做任务分片亲和（同一域的任务尽量落到同一节点），否则大量时间花在建立连接上而不是投递。
- 吞吐估算要给：假设单节点 50 并发连接、每封 200ms，则单节点约 250 封/秒；100 万封理论 67 分钟——但真实上限通常是网关配额而不是节点数。答完方案补一句"瓶颈大概率在对端配额，不在我们的集群"，是这题的成熟度体现。

> 💡 提示
> 这题原稿只列了三个方案名，很多人会停在"用 MQ 分发"。真正拉开差距的是后半段：幂等、租约回收、按收件域限速、连接复用。因为"尽快完成"的反面不是"没有并行"，而是"重复发送"和"被对端封掉"。

> 🎯 关键要点
> - 任务与执行者解耦，靠租约实现动态上下线不丢任务
> - MySQL 没有 UPDATE RETURNING，用 SKIP LOCKED 等价实现
> - 幂等靠任务 ID + 状态机，重发要能判断上次结果
> - 真实瓶颈常是 SMTP 网关配额，不是节点数
> - 按收件域做分片亲和以复用连接

> 🔍 追问
> - 节点领了任务后崩溃，任务被重发但上次其实已发送成功，怎么避免重复？
> - 1000 万封邮件、要求 2 小时内发完，你怎么设计并发与限速？
> - 怎么在不支持 SKIP LOCKED 的老版本 MySQL 上实现抢占？

### 3. 有一批气象观测站需要采集观测数据入 Hive，但气象局只提供单个观测点的查询 API，如何方便快速地拿到全部站点的数据？｜中级

> 出题人：江岚／阿里巴巴数据技术高级技术专家

核心结论：这是"海量小请求的批量外部接口采集"问题。原稿给了三档方案（脚本串行落地再上传 → DataX 的 httpReader/hdfsWriter → 在计算引擎 UDF 里直接调 API），第三档之所以最理想，是因为它把并发、重试、容错交给了引擎而不是自己写。

- 三档方案与各自的边界：
  - **A. shell/Python 脚本调用 API，结果先落本地文件，再上传到 Hive**：最灵活，适合站点数少、原型验证。问题是并发要自己管、失败要自己重试、本地磁盘成为中间态、数据落地与入仓是两步（容易漏传）。
  - **B. DataX / 同步工具的 `httpReader` + `hdfsWriter`**：配置化、有现成的限速与脏数据策略，适合"结构固定、周期性全量/增量"的批量搬运。局限：对"每个站点的参数不同、要循环 N 次"这种动态请求支持弱，通常需要前置一个参数生成步骤。
  - **C. 在计算引擎的 UDF/UDTF 里直接调用 API，结果写入目标表**（原稿认为最理想）：好处正是它说的三点——不需要单独的导出导入环节；引擎的分布式框架天然提供并行、容错、重试；数据直接进表结构。
  - **C 的代价必须一起说**（否则会被追问）：① 把计算集群变成"对外发请求的爬虫"，一个失败任务重试可能给外部接口造成放大压力；② UDF 里的网络阻塞会占着 executor 槽位，拖长整体作业；③ 超时要严格设，否则一个卡住的站点能让整个 stage 挂住；④ 外部接口不可控，要有并发上限与熔断，并申请独立队列而不是和核心作业抢资源。
- 我推荐的工程形态（介于 B 和 C 之间，可辩护）：**独立采集服务 + 消息队列 + 批量入仓**
  ```
  调度器(Airflow/DolphinScheduler)
     → 生成站点分片任务 → 采集服务(并发池 + 限速 + 重试 + 水位)
     → 原始响应落对象存储/消息队列(留痕，便于重放)
     → 解析与清洗 → 按分区批量写入 Hive
  ```
  理由：把"不可控的外部依赖"从计算引擎里隔离出来，采集侧可以独立限流、重试、监控，数仓侧只处理已经落地的稳定数据；同时保留了原始报文，接口变更或解析 bug 时可以重放而不用重新采集。
- 必须设计的细节（这题的评分点）：
  - **分片与并发**：站点列表按批次切分（如每任务 200 个站点），并发数按接口方的配额定（问清 QPS 上限，别默认"越多越好"）。
  - **增量水位**：按 `(station_id, 观测时间)` 记录已成功采集的最大时间点，下次只拉增量；水位要落库且与写入同事务（或至少"先写数据后推水位"，宁可重复不可漏）。
  - **幂等与去重**：同一站点同一时刻的数据可能重复拉取，入仓用 `(station_id, obs_time)` 做唯一键，写入用覆盖式分区或下游去重。
  - **分区与小文件**：Hive 按 `dt=日期/station_id` 分区时，站点数多会制造海量小文件（NameNode 元数据压力、查询打开大量文件）。要么按天粗分区 + 合并写（每分区文件数受控），要么定期 `compaction`/合并任务。
  - **失败与脏数据**：单站点失败不阻塞整体（侧输出到错误表 + 重试队列），格式异常的数据留原始报文而不是丢弃。
  - **对账**：站点总数 × 期望条数 vs 实际入库条数，每日比对并告警——采集类任务最容易出的问题是"静默少了一部分站点"。
  - **鉴权与配额**：API 的 token 有效期、限流响应码（429）要识别并退避，不能当普通失败重试。

> ⚠️ 注意
> 答这题不要直接说"用 UDF 调 API 最优雅"。原稿那句"比较理想的回答"是在**考察你是否理解分布式引擎能替你做什么**的前提下说的。如果不同时说出"外部依赖要隔离、并发要限流、超时要设、要能重放"，就变成把风险引进计算集群。

> 🎯 关键要点
> - 三档方案的差别是"谁负责并发、重试、容错"
> - UDF 调外部 API 要付出隔离性与稳定性代价
> - 增量水位 + 幂等键 + 对账是采集三件套
> - 站点数多时小文件是 Hive 的头号问题
> - 原始报文留痕，才能重放与排错

> 🔍 追问
> - 站点从 500 个涨到 5 万个，你的方案哪部分先崩？
> - 接口方只给 10 QPS，你要每天采全量，怎么排期？
> - 采集到的数据有一天发现少了 30%，你怎么定位与补数？

## 质量保障（1 题）

### 4. 假如给你一个新产品，你将从哪些方面保障它的质量？｜中级

> 出题人：晨晖／阿里云中间件技术部测试开发专家

核心结论：质量不是测出来的，是"在需求阶段定义、在编码阶段约束、在测试阶段验证、在发布阶段控制、在线上阶段观测并闭环"的链条。原稿的三段（代码开发 / 测试保障 / 线上质量）是对的骨架，本页把它扩成五段并补上度量与取舍。

- 第 0 段：需求与设计（原稿缺，但这是缺陷最便宜的拦截点）
  - 可测性评审：验收标准是否可判定（"响应要快"不是标准，"P99 < 300ms"才是）。
  - 风险分级：按"影响面 × 变更频率"决定投入，核心交易链路与内部工具用同一套流程是浪费。
  - 设计评审里的质量项：幂等、超时与重试、降级方案、可观测性埋点、数据一致性策略——这些没设计，后面测不出也救不回。
- 第 1 段：编码阶段
  - 规范与静态检查（lint、ruff/ESLint、SonarQube、类型检查）把低级问题自动化拦掉。
  - Code Review：重点看边界、并发、错误处理、可观测性，而不是格式。
  - 单元测试：追求"关键分支覆盖"而非覆盖率数字；核心算法与状态机必须有性质测试/边界用例。
  - 契约测试：接口双方约定 schema（OpenAPI / Pact），避免联调时才发现字段不一致。
- 第 2 段：测试阶段（原稿列的六类，补上判据）

| 类型 | 验什么 | 常见漏项 |
|---|---|---|
| 功能/接口 | 需求覆盖、边界、异常路径 | 只测正向路径 |
| 集成/端到端 | 跨服务链路真实可用 | 依赖 mock 与线上不一致 |
| 性能/容量 | TPS、P99、资源水位、拐点 | 不做压测就上线、只看均值 |
| 稳定性 | 长时运行、内存泄漏、重试风暴 | 缺少小时级浸泡测试 |
| 高可用/容灾 | 宕机、网络分区、主从切换、依赖不可用 | 从没真正杀过节点 |
| 兼容性 | 版本、浏览器/终端、数据格式、升级路径 | 忽略老数据迁移 |
| 安全 | 越权、注入、敏感数据、依赖漏洞 | 只靠扫描器 |
| 数据一致性 | 对账、幂等、并发写、消息重复 | 最容易被完全跳过 |
- 第 3 段：发布阶段
  - 灰度/金丝雀/蓝绿：先小流量验证，指标不达标不扩量；发布窗口避开业务高峰。
  - 可回滚：回滚要**演练过**且比修复更快；含数据库变更的发布要"先加列后改代码"、保证前后向兼容。
  - 发布检查表：开关默认值、依赖版本、配置项、监控是否就绪、值班人是谁。
  - Feature Flag：把"部署"和"发布"分开，出问题关开关而不是回滚整包。
- 第 4 段：线上阶段
  - 可观测三支柱：指标（Prometheus）、日志（结构化 + traceId）、链路追踪；没有 traceId 的日志在微服务里等于没有。
  - SLO 与错误预算：用"可用性目标 + 错误预算"决定发布节奏，比"感觉挺稳"客观。
  - 告警分级：P0 打电话、P1 群里 @、P2 看板式；告警必须可行动，否则会被忽略到失效。
  - 巡检与预案：定期跑巡检任务（关键链路拨测），故障预案要演练（原稿提的"故障演练"就是混沌工程）。
  - 复盘闭环：故障复盘产出"改进项 + 责任人 + 截止日"，且改进项要能验证，否则复盘只是文档。
- 度量（决定投入是否有效）：缺陷逃逸率、MTTR/MTBF、变更失败率、部署频率（DORA 四指标）、单测与关键路径覆盖、线上告警噪音率。
- 取舍（这题的成熟度体现）：新产品早期最重要的是"快速发现真实问题"，所以埋点、灰度、回滚、错误日志的价值高于堆测试用例；成熟期才把重心移到自动化回归与性能基线。把这套流程不分阶段全量压给一个小项目，是典型的流程浪费。

> 💡 提示
> 原稿答案的三段结构可以直接用，但只报清单会被追问"你们线上出过什么问题、怎么防的"。准备一个具体案例（比如"上线前压测发现连接池配置导致 P99 抖动 → 加了容量评估门禁"），比多列十项检查更有效。

> 🎯 关键要点
> - 质量是链条：定义 → 约束 → 验证 → 控制 → 观测闭环
> - 需求阶段拦截缺陷最便宜，线上发现最贵
> - 数据一致性与容灾测试最常被完全跳过
> - 回滚要演练，含 DDL 的发布要保证前后向兼容
> - 用 SLO/DORA 度量，而不是用覆盖率数字自证
> - 投入要按业务风险分级，不做一刀切
