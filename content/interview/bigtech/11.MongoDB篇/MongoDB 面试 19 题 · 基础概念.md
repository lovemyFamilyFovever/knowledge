## 是什么（6 题）

### 1. 什么是 MongoDB？｜初级

核心结论：MongoDB 是一个用 BSON（二进制 JSON）存文档的文档型数据库，主打灵活模式、水平扩展和面向对象的查询表达，2013 年前后成为最流行的 NoSQL 系统。

- 出身：2007 年由 10gen 团队（后改名 MongoDB Inc.）发起，2009 年 2 月正式发布；名字来自 "humongous"（巨大）。
- 存储单位是文档：一个文档就是一组键值对，天然对应程序里的对象，省掉 ORM 那层阻抗转换。
- 三级结构：数据库 → 集合 → 文档，集合没有固定 schema（但可以用 `$jsonSchema` 校验器约束）。
- 默认存储引擎是 WiredTiger（3.2 起），文档级并发、块压缩、检查点 + journal。
- 能力面：副本集（高可用）、分片（水平扩展）、聚合管道、文本/地理/通配符索引、Change Streams、时序集合、搜索（Atlas Search）。
- 单文档 BSON 上限 16MB；超过要放 GridFS 或改存对象存储 + 存引用。

> 🎯 关键要点
> - 文档型、BSON 存储、无固定 schema
> - 库 → 集合 → 文档三级
> - 默认 WiredTiger，文档级并发
> - 副本集管可用性，分片管容量
> - 16MB 是单文档硬上限

> 🔍 追问
> - MongoDB 的"无模式"到底免掉了什么、又带来了什么问题？
> - 它和 PostgreSQL + JSONB 相比，什么时候更值得选？

### 2. MongoDB 是用什么语言写的？｜初级

核心结论：主体用 C++ 编写（存储引擎 WiredTiger 是独立的 C 代码库），早期部分工具与复制逻辑用过 Java，服务端核心一直是 C++。

- 选 C++ 的理由：存储引擎要精细控制内存、页缓存、并发与压缩，需要无 GC 停顿、可预测的性能。
- 对比：MySQL 也是 C/C++；Redis 是 C；etcd 是 Go；Cassandra/Roaring 相关是 Java；WiredTiger 是 C。
- 附带知识点：MongoDB 服务端内嵌一个 JS 引擎执行 shell 与 `$where`/存储函数——6.0 起用 QuickJS 替换了老的 SpiderMonkey，因为 SpiderMonkey 有安全与内存问题。
- 驱动是各语言独立实现的，官方支持 C/C++、C#/.NET、Java、Node.js、Python、Go、PHP、Ruby、Rust 等，走的是同一套 wire protocol（OP_MSG）。

> 🎯 关键要点
> - 服务端 C++，WiredTiger 是 C
> - 内嵌 JS 引擎（现为 QuickJS）跑 shell 与表达式
> - 驱动各自实现，统一走 wire protocol
> - 选 C++ 是为了无 GC 与可控内存

> 🔍 追问
> - 为什么数据库内核很少用带 GC 的语言写？
> - 服务端内嵌 JS 引擎带来什么风险？

### 3. MongoDB 的优势有哪些？｜初级

核心结论：优势集中在"结构灵活 + 水平扩展原生 + 查询表达力强"三点；它是取舍而非银弹，弱项是复杂多表关联、强事务习惯用法与成熟度依赖设计的 schema 治理。

- 文档模型：一次读取拿到一个完整聚合对象，避免关系型里"读一条订单要 JOIN 四张表"。
- 动态模式：同一集合的文档字段可以不同，业务快速迭代时不用停机改表结构。
- 索引灵活：任何字段（含嵌套字段、数组元素）都能建索引；数组自动建 multikey 索引。
- 水平扩展：分片是内置能力，按 shard key 把数据摊到多组副本集上。
- 高可用：副本集自带选举与故障转移，写关注/读关注可调一致性强度。
- 聚合管道：`$match/$group/$project/$unwind/$lookup` 表达大多数分析型需求。
- 即时更新：字段级 `$set/$inc/$push`，不用读改写整个文档。
- 生态与运维：官方支持、云托管（Atlas）、可视化工具（Compass）。
- 要如实说的短板：多文档事务 4.0 才有、代价高且跨分片限制多；JOIN 能力弱（`$lookup` 慢）；无 schema 约束容易写脏数据；内存吃得多（工作集应尽量驻留 RAM）。

> ⚠️ 注意
> 原稿把"没有复杂的连接"当成优势，这是立场而非事实——**不支持 JOIN 是限制**，它逼着你在建模时做冗余/嵌入设计。面试里把它说成"用建模换扩展性"比说成"优势"更准确。

> 🎯 关键要点
> - 三大真实优势：灵活模式、原生分片、字段级更新
> - 任何字段（含数组/嵌套）都能索引
> - 事务有但重，不是默认用法
> - 无约束是双刃剑，要配 schema validator
> - 工作集要能装进内存，否则性能塌方

> 🔍 追问
> - 动态模式怎么防止集合里长出十种形状的文档？
> - 哪些需求会让你放弃 MongoDB 回到关系型？

### 4. 什么是数据库（Database）？MongoDB 里它扮演什么角色？｜初级

核心结论：在 MongoDB 里数据库是集合的容器，一个mongod实例可承载多个库，每个库有自己的命名空间、存储目录与权限边界；它比关系型里的"库"更轻，主要用途是隔离应用与租户。

- 通用定义（原稿的"电子化文件柜"）：持久化组织数据、支持增删改查与并发访问的软件系统。
- MongoDB 层面：`db` 是当前库对象；每个库在 `--dbPath` 下有自己的目录（WiredTiger 按 `库.集合` 命名文件）。
- 一个库对应一套权限（`admin` 库里建用户，角色作用到指定库）。
- 库是延迟创建的：`use newdb` 之后如果没写入任何集合，`show dbs` 不会列出它——这是新手最常见的困惑点。
- 集合上限受命名空间规模影响（见第 16 题），所以"一个租户一个库"这种做法在库数量上千时要重新评估。

> 🎯 关键要点
> - 库 = 集合的容器 + 权限边界
> - 有数据后才出现在 show dbs
> - 每库独立目录与命名空间
> - 库数量不要无节制增长

> 🔍 追问
> - 为什么 `use` 之后 `show dbs` 看不到新库？
> - 多租户用"多库"还是"一个库多集合"还是"一个集合带 tenantId"？

### 5. 什么是集合（Collection）？｜初级

核心结论：集合是"一组文档"的逻辑分组，相当于关系型里的表，但不强制成员结构一致；集合是创建时隐式产生的，也可以显式声明并附带校验规则与分片配置。

- 位置：集合必须属于某个数据库，名字不能含 `$`、`null`，不能以 `system.` 开头（保留给内部集合）。
- 无固定 schema：同一集合里 `{a:1}` 和 `{b:"x", c:[1,2]}` 可以共存；这是它和表最大的区别。
- 显式创建：`db.createCollection("orders", { validator: {...}, validationLevel: "strict" })`，可顺带设 `capped`（固定大小、天然 FIFO）、`timeseries`、`clusteredIndex`。
- 物理上：WiredTiger 下每个集合对应自己的文件与 B-tree，所以"集合特别多"会带来文件句柄与元数据开销。
- 命名实践：一个集合承载一类聚合根；不要把"同一实体按月拆成 12 个集合"（除非有明确的生命周期或性能理由，可用分片/分区思路替代）。

> 🎯 关键要点
> - 集合 = 文档的逻辑分组，类似表但不约束结构
> - 首次插入时隐式创建，也可显式带 validator
> - capped / timeseries 是特殊集合形态
> - 集合数量要克制，元数据与句柄有成本

> 🔍 追问
> - 什么时候该拆集合、什么时候该在集合内用字段区分？
> - 什么是 capped collection？它解决什么场景？

### 6. 什么是文档（Document）？｜初级

核心结论：文档是 MongoDB 的基本存取单位，一个 BSON 键值对集合，等价于程序里的一个对象；它自带 `_id` 主键、可以有嵌套结构，单个最大 16MB。

- 结构：`{ _id: ObjectId('...'), name: '张三', tags: ['a','b'], addr: { city: 'SH' } }`。
- `_id` 默认是 ObjectId，插入时由客户端或服务端生成；它是唯一索引，不可重复，可用自定义值（要自己保证唯一）。
- 字段顺序在 BSON 里是有序的，`{a:1,b:2}` 与 `{b:2,a:1}` 是**不同**的文档（会影响唯一索引与 `$eq` 匹配）。
- 动态模式：同集合文档字段可以不同，查询用 `$exists` 处理稀疏字段。
- 16MB 限制来自 BSON/网络消息上限，不是"建议值"；大文本、图片应该外置到对象存储，文档里放引用。
- 键名限制：不能含 null、不能以 `$` 或 `.` 开头（4.0 起允许文档键里含 `.`，但聚合与更新里有坑，实践仍避免）。

> ⚠️ 注意
> 面试常问"MongoDB 的文档和关系型的一行有什么区别"，最有力的答案是**嵌套与原子性**：一个文档可以是一棵子树，对它的写是原子的；关系型要把这棵子树摊平到多张表，跨行的原子性就得靠事务。

> 🎯 关键要点
> - 文档 = BSON 对象，自带唯一 _id
> - BSON 键有序，顺序不同即不同文档
> - 单文档 16MB 硬上限
> - 嵌套子树可原子更新，这是建模的核心红利
> - 稀疏字段用 $exists 表达

> 🔍 追问
> - 为什么不建议把图片直接存进文档？
> - 自定义 `_id` 有哪些坑？

## 术语与进程（5 题）

### 7. MongoDB 和关系型数据库的术语怎么对照？｜初级

核心结论：库对库、集合对表、文档对行、字段对列、`_id` 对主键；差别集中在"表结构固定 vs 文档自由"和"JOIN 关联 vs 内嵌引用"这两处。

| 关系型数据库 | MongoDB | 说明 |
|---|---|---|
| Database | 数据库 | 集合的容器 |
| Table | 集合 Collection | 逻辑分组 |
| Row / Record | 文档 Document | 一条数据，可嵌套 |
| Column | 字段 Field | 键值对，类型可混 |
| Primary Key | `_id` | 唯一，默认 ObjectId |
| Index | 索引 | 支持复合/多键/文本/通配符 |
| JOIN | `$lookup` / 内嵌 | 表达能力弱，倾向建模解决 |
| Schema 约束 | `$jsonSchema` validator | 可选，不是默认强制 |
| 事务 | 多文档事务（4.0+） | 单文档写天然原子 |
| 存储过程 | `$expr` / 聚合 / 应用层 | 逻辑倾向放应用层 |
| 视图 | view / 物化视图（$merge） | 4.0 起支持视图 |

- 建模哲学的差异：关系型先规范化再按需反范式；MongoDB 先按"一次读取要什么"设计（内嵌为主、引用为辅），再按需拆分。
- 一句话对照："集合像表，文档像对象，`_id` 像主键，但结构不强制统一。"

> 🎯 关键要点
> - 库/集合/文档/字段 ↔ 库/表/行/列
> - `_id` 就是主键，默认 ObjectId
> - JOIN 的位置被"建模时的内嵌/引用决策"取代
> - schema 校验是可选项，不是默认
> - 单文档写原子，跨文档要事务

> 🔍 追问
> - 内嵌还是引用，你的判断标准是什么？
> - 既然 `$lookup` 能 JOIN，为什么说 MongoDB 不擅长关联查询？

### 8. mongod 是什么？｜初级

核心结论：`mongod` 是 MongoDB 的服务端进程（"d" = daemon），负责接收连接、执行读写、维护存储引擎与复制；启动 mongod 才是"启动了一个数据库实例"。

- 职责：处理数据请求、管理存储（WiredTiger）、执行后台操作（检查点、journal 刷盘、副本集心跳、balancer）。
- 形态：可以是单机、副本集的一个成员、分片集群里的 shard/config server。
- 角色不是进程属性而是运行时状态：同一个 mongod 在副本集里可能是 Primary/Secondary/Arbiter，切换不需要重启进程。
- 与之配套的进程：`mongos`（分片路由，无状态）、`config server`（元数据副本集）、`mongod`（数据节点）。
- 查看状态：`systemctl status mongod`、日志里的 `Waiting for connections`、`db.serverStatus()`、`mongosh --eval 'db.stats()'`。

> 🎯 关键要点
> - mongod = 服务端守护进程，一个实例一个进程
> - 副本集角色是运行时状态，不是启动参数
> - 分片集群还有 mongos 与 config server
> - 生产用 systemd/容器托管，别手敲前台启动

> 🔍 追问
> - mongod 挂了会发生什么？取决于什么？
> - mongos 和 mongod 的职责边界在哪？

### 9. mongod 有哪些常用启动参数？｜初级

核心结论：核心是"数据目录 + 端口 + 是否进副本集/分片角色 + 日志与安全"，其余参数（缓存、游标超时）都有可用默认值，生产上真正要显式配的没几个。

- 必知参数：

| 参数 | 作用 | 默认 |
|---|---|---|
| `--dbpath` | 数据目录 | Linux `/data/db`，Windows `C:\data\db` |
| `--port` | 监听端口 | 27017 |
| `--bind_ip` | 监听地址 | 127.0.0.1 |
| `--replSet` | 副本集名 | 单机无 |
| `--shardsvr` / `--configsvr` | 声明为分片/config 节点 | 无 |
| `--logpath` / `--logappend` | 日志文件与追加 | 无（前台输出） |
| `--fork` | 后台运行 | 关 |
| `--auth` | 开启鉴权 | 关 |
| `--keyFile` | 副本集内部成员认证 | 无 |
| `--wiredTigerCacheSizeGB` | WT 缓存上限 | (内存-1GB)/2 |
| `--ipv6` / `--tls*` | 网络与传输加密 | 关 |

- 配置文件优先：生产用 `mongod.conf`（YAML，`systemLog/net/storage/security/replication/operationProfiling/processManagement` 分段），包管理器安装的服务会读它。
- 三个易错点：① `--fork` 必须配合 `--logpath`；② 副本集成员必须配 `--replSet` 且各成员名一致；③ 开 `--auth` 前要先建管理员用户，否则进不去（临时用 `--keyFile` 或 localhost exception）。
- 端口 27017 的由来：MongoDB 官方说法是"随便选的"，坊间解释为 27000+17（"MongoDB 的 17"），不必当真。

> ⚠️ 注意
> 默认 `--bind_ip 127.0.0.1` 是安全兜底。把它改成 `0.0.0.0` 而不配 `--auth`、不配防火墙，就是历年 MongoDB 公网裸奔泄露数据的直接原因。答这题时主动提安全，比报十个参数有用。

> 🎯 关键要点
> - 必记：dbpath / port / bind_ip / replSet / auth / keyFile
> - 生产用 YAML 配置文件而不是长命令行
> - WT 缓存默认约 (RAM-1GB)/2，别调成接近物理内存
> - 改 bind_ip 必须先有 auth + 防火墙
> - --fork 需要 --logpath

> 🔍 追问
> - 副本集成员之间靠什么互相认证？
> - WiredTiger 缓存设多大合适？设大了会怎样？

### 10. mongo 是什么？和 mongosh 有什么区别？｜初级

核心结论：`mongo` 是旧版 JavaScript shell，用来连 mongod 做交互查询与管理；MongoDB 6.0 起它已被移除，官方替代是独立的 `mongosh`，语法兼容但能力更强。

- 用法：不带参数连 `localhost:27017` 的默认库 `test`；`mongo "mongodb://host:port/db"` 指定目标。
- 在 shell 里操作的是同一套 API：`use db`、`db.coll.find()`、`db.coll.insertOne()`、`show collections`。
- `mongosh` 的改进：现代 JS（ES2020+）、自动补全与语法高亮、`--nodb` 模式、可安装外部 npm 包、内置 `explain()` 可视化、原生支持新 API（旧 `mongo` 已跟不上版本迭代）。
- 其他官方工具：`mongodump`/`mongorestore`（逻辑备份）、`mongoexport`/`mongoimport`（JSON/CSV）、`mongos`（路由进程）、`Compass`（GUI）。
- 版本提示：如果面试里说"我们用 mongo shell"，对方可能反问"6.0 之后怎么办"——答 mongosh 才说明版本感知是新的。

> 🎯 关键要点
> - mongo = 旧 shell，6.0 起移除
> - mongosh 是官方替代品，独立发布
> - shell 里的 API 与驱动 API 基本一致
> - 备份导入导出走 mongodump/mongoimport 系列工具

> 🔍 追问
> - 生产上你会用 shell 做批量数据修复吗？注意什么？
> - mongosh 和 mongo 在写脚本时有什么实际差异？

### 11. 切换数据库用什么命令？｜初级

核心结论：`use <dbname>`——存在就切过去，不存在就"标记待创建"，真正落盘要等你第一次写入集合。

- `use mydb` → `switched to db mydb`；此后 `db` 指向该库。
- 延迟创建：只 `use` 不写数据，`show dbs` 不显示它，磁盘上也没有对应目录。
- 当前上下文：`db.getName()`（mongosh 里是 `db.getName()` 或 `db`）、`db.stats()` 看规模。
- 权限：切换本身不鉴权，读写时才按用户在目标库上的角色判定。
- 驱动里等价操作：连接串里带 `/dbname`，或 `client.db("mydb")`。

> 🎯 关键要点
> - use 存在即切换、不存在即待创建
> - 没写数据前 show dbs 看不到
> - 切换不鉴权，操作时才校验
> - 连接串里指定库更常用

> 🔍 追问
> - 为什么 MongoDB 要延迟创建库和集合？
> - 用脚本批量建库时要注意什么？

## NoSQL 与场景（4 题）

### 12. 什么是非关系型数据库？｜初级

核心结论：NoSQL 是"不用关系模型作为主存储与查询抽象"的一类数据库统称，通常放弃表结构与 SQL JOIN，换取水平扩展、灵活模式或特定访问模式的极致性能。

- 名字演变：早期是 "No SQL"，现在普遍解释为 "Not Only SQL"——很多 NoSQL 也支持类 SQL 查询，而关系型也在加 JSON 列。
- 放弃了什么：多数选择最终一致或弱隔离、不保证跨行事务（或代价高）、无固定 schema、不支持任意 JOIN。
- 换来了什么：分片友好（按 key 散列即可线性扩）、写吞吐高、模式迭代快、针对特定负载（时序/图/全文/键值）结构更贴合。
- 理论背景：BASE（Basically Available、Soft state、Eventual consistency）对 ACID；CAP 里在一致性和中用性之间二选一（分区必然发生）。
- 别把它当潮流：选型应问"我的访问模式是什么"，而不是"要不要用 NoSQL"。

> ⚠️ 注意
> 原稿说"非关系型数据库不使用 SQL 作为查询语言"——这条正在失效：PostgreSQL 不是 NoSQL，而 MongoDB 4.x 之后有 SQL 兼容层、Cassandra 的 CQL 语法几乎就是 SQL。更稳的定义是"不以关系代数和固定表结构为核心抽象"。

> 🎯 关键要点
> - NoSQL = 不用关系模型做核心抽象
> - 用一致性/JOIN 能力换扩展性与灵活度
> - CAP 里分区必现，只能选 C 或 A
> - "不用 SQL"这个判据已经过时
> - 按访问模式选，不按流派选

> 🔍 追问
> - 你的场景里放弃 ACID 的哪一部分？代价是什么？
> - 为什么说 PostgreSQL 让很多 NoSQL 场景失去了必要性？

### 13. 非关系型数据库有哪些类型？各举一个代表产品｜初级

核心结论：主流分四类——键值、列族（宽列）、文档、图；此外还有时序、搜索、对象存储等专用形态。分类看的是"数据怎么组织、按什么方式访问"。

| 类型 | 数据组织 | 代表 | 典型场景 |
|---|---|---|---|
| 键值 Key-Value | key → 不透明值 | Redis、DynamoDB | 缓存、会话、计数 |
| 文档 Document | 半结构化对象 | MongoDB、CouchDB | 内容、用户画像、目录 |
| 列族 Column-family | 行 + 列簇稀疏表 | HBase、Cassandra | 写密集、时序、海量扫描 |
| 图 Graph | 点 + 边 + 属性 | Neo4j、JanusGraph | 关系推荐、风控、社交 |
| 时序 Time-series | 按时间线组织 | InfluxDB、Prometheus | 指标、监控 |
| 搜索 Search | 倒排索引 | Elasticsearch、OpenSearch | 全文检索、日志分析 |

- 修正原稿例子："Key-Value 存储 Eg: Amazon S3"不准确——S3 是**对象存储**（key → 对象，配 HTTP 语义与元数据），不是通用 KV 数据库；Redis/DynamoDB 才是 KV 代表。
- 边界在模糊：PostgreSQL 有 JSONB（文档）、数组与扩展（图/时序）；MongoDB 有 Change Streams 与搜索索引；Cassandra 也支持二级索引。
- 选型问三件事：访问模式（点查/范围/聚合/关联）、一致性要求、数据规模与增长。

> 🎯 关键要点
> - 四类主干：KV / 文档 / 列族 / 图
> - S3 是对象存储不是 KV 数据库
> - 专用形态（时序/搜索）往往比通用 NoSQL 更合适
> - 分类看访问模式，不看品牌

> 🔍 追问
> - 同一份日志数据，为什么有时选 ES 有时选 ClickHouse？
> - 什么场景下 KV 存储比文档数据库更合适？

### 14. 为什么要用 MongoDB？｜初级

核心结论：当你需要"结构会变、数据要水平扩、一次读取要拿到完整聚合对象"这三件事中的两件以上时，MongoDB 的性价比高；否则用关系型或专用存储更省心。

- 架构简单：mongod 一个进程就是数据库，副本集三台就是高可用，不需要外部依赖（对比 HBase 依赖 HDFS + ZK）。
- 对象原生：文档 ↔ 程序对象，省掉 ORM 映射层与表结构变更流程。
- 深度查询：支持嵌套字段、数组元素、正则、聚合表达式、`$text` 全文；不是只能按主键取。
- 动态模式：字段可增可缺，灰度期间新旧结构共存，不用 ALTER 大表。
- 水平扩展：分片是内置能力，按 shard key 摊开，扩容主要是加 shard。
- 运维与生态：Compass、Atlas、mongodump、丰富的驱动，中小团队能自己养。
- 不要用的理由（诚实版）：强一致账务、复杂报表多表关联、成熟 SQL 工具链需求、团队没有 schema 治理能力（动态模式会变成垃圾场）。

> 🎯 关键要点
> - 三个信号：结构会变 / 要分片 / 读聚合对象
> - 无外部依赖是真实的运维优势
> - 动态模式要求你有治理手段
> - 强关联分析与账务不是它的战场

### 15. 哪些场景适合用 MongoDB？｜中级

核心结论：适合"文档天然成块、写多且模式演进快、需要按任意字段检索并水平扩展"的场景——内容管理、商品目录、用户与画像、移动/物联网数据、日志与事件、实时分析。

- 内容管理与 CMS：文章 + 版本 + 标签天然是一棵树，一次读取渲染。
- 商品目录：不同品类属性差异极大（手机有内存、衣服有尺码），固定表结构会很痛苦。
- 用户与画像：一个用户一条文档，字段随业务增长，`$set` 局部更新。
- 移动端 / 边缘：Device Sync（Realm/Atlas Device SDK）做离线写入再同步。
- 日志与事件：高写入吞吐 + TTL 索引自动过期 + 时序集合（5.0+）。
- 实时分析：聚合管道 + Change Streams 做流式派生；大数据量时列式引擎（ClickHouse）更合适，MongoDB 承担"近实时、中等规模"。
- 元数据与配置：结构杂、量不大、要按任意字段查。
- 不适合：强一致账务、以 JOIN 为核心的复杂报表、超宽表大范围扫描分析、需要成熟 BI/SQL 工具链直接接的场景。

| 场景 | 关键诉求 | MongoDB 是否契合 |
|---|---|---|
| 商品目录 | 属性异构 | 很契合 |
| 内容/版本 | 嵌套 + 一次读全 | 很契合 |
| 用户画像 | 字段演进快 | 契合 |
| 账务 | 强一致事务 | 不契合 |
| 报表分析 | 多表 JOIN + 列扫 | 不契合 |
| 日志监控 | 高写 + TTL | 契合（量大转 CK） |

> 💡 提示
> 答"哪些场景适合"要给反向清单。只讲优点听起来像背书，能说出"账务和复杂报表我会劝退"才说明真的上过线。

> 🎯 关键要点
> - 契合点：异构属性、嵌套成块、模式演进
> - 日志/事件可用但要盯规模上限
> - 账务与重 JOIN 场景明确不适合
> - 场景判断落到"访问模式 + 一致性"两问

## 进阶概念（2 题）

### 16. MongoDB 里的命名空间（namespace）是什么？有什么限制？｜高级

核心结论：命名空间是"库名.集合名"这个字符串对应的元数据条目，每个集合和每个索引各占一条；它的大小与条目数上限决定了单库能建多少集合——原稿那套"16MB ns 文件、约 24000 个命名空间"是 mmapv1 引擎的限制，WiredTiger 下形态不同但"集合数要克制"的结论依然成立。

- 定义：`"mydb.orders"` 这样的字符串就是一个命名空间，指向一个集合或一个索引的元数据。
- mmapv1（≤3.0 默认，4.0 移除）的限制：命名空间集中在 16MB 的 `.ns` 文件里，平均每条约 628 字节 → 单库上限约 24000 条；每个集合至少占 1 条（自身）+ 1 条（默认 `_id` 索引）→ 实际最多约 12000 个集合；`--nssize` 可调大 `.ns`（上限 2GB）；数据文件按 2 倍递增、单文件最大 2GB；`$freelist` 记录被删除集合/索引留下的空闲盘区。
- WiredTiger（3.2+ 默认）：不再有集中式 `.ns` 文件，每个集合/索引对应独立的 WT 条目与文件，"24000 命名空间"这条限制不再适用。
- 但仍有实际约束：① 集合/索引数量过多会让副本集启动、oplog 应用、`listCollections`、备份与 balancer 都变慢；② 文件句柄与元数据缓存有开销；③ MongoDB 官方建议**不要为每个租户/每天各建一个集合**，用字段区分 + 分片承载规模。
- 反模式：`logs_2026_01`、`logs_2026_02`…… 建几百个集合 → 应改为一个集合按 `month` 字段分片，或用 6.0 起的**通配符索引 + 时序集合**。

> ⚠️ 注意
> 这题是典型的"老题新答"。背 24000 这个数字在今天的版本上已经不成立，但直接说"没有限制"也不对——WT 下限制变成了运维成本。正确答法是：先说明原稿数字属于 mmapv1，再给出今天的真实约束（集合数影响启动/备份/元数据），最后给建模建议。

> 🎯 关键要点
> - 命名空间 = 库.集合 的元数据条目，集合与索引各占一条
> - 16MB/.ns/24000/2GB 文件全是 mmapv1 遗产
> - WiredTiger 无集中命名空间文件，但集合数仍有成本
> - 按时间/租户狂建集合是反模式
> - 答这题要先限定版本

### 17. 哪些编程语言可以用 MongoDB？官方支持哪些驱动？｜初级

核心结论：MongoDB 官方为十余种语言维护驱动，所有驱动走同一套 wire protocol，因此语言能力基本对等；差别在于异步模型、ODM 成熟度与团队熟悉度。

- 官方驱动：C、C++、C#/.NET、Go、Java（含 reactive streams）、Node.js、PHP、Python（含 asyncio）、Ruby、Rust、Scala、Kotlin、Swift。
- 社区驱动：Erlang/Elixir、Clojure、Dart 等。
- Node.js 侧生态：原生 driver、Mongoose（最主流的 ODM，带 schema 校验与中间件）、TypeORM/MikroORM 也支持 MongoDB。
- 一致性注意：驱动版本要与服务器版本匹配（兼容性矩阵），老驱动连新服务端会出现认证或 API 缺失问题。
- 中文互联网常说的"MongoDB 适合 Node 全栈"，实质原因是 BSON/JSON 与 JS 对象天然同构、Mongoose 降低了建模成本。

> 🎯 关键要点
> - 官方驱动覆盖主流语言，能力对等
> - Node 生态靠 Mongoose 降低建模成本
> - 驱动版本要对照服务端兼容性矩阵
> - 选语言驱动看团队栈，不是 MongoDB 的限制

## 库的创建与查看（2 题）

### 18. 如何在 MongoDB 里创建一个新数据库？｜初级

核心结论：`use <dbname>` 声明目标库，第一次向某个集合写入文档时数据库才被真正创建——MongoDB 没有"建库"这个显式动作。

- 步骤：`use mydb` → `db.coll.insertOne({a:1})` → `show dbs` 就能看到 mydb。
- 只 `use` 不写：库不存在于磁盘，`show dbs` 不显示，这是设计而非 bug。
- 显式建集合（可选）：`db.createCollection("orders")`，但同样要写入数据后库才落地。
- 建用户与角色：`db.createUser({user, pwd, roles:[{role:'readWrite', db:'mydb'}]})`，在 `admin` 库上执行、指定作用库。
- 驱动里：`client.db('mydb')` 拿到 handle，写入即创建。
- 权限前置：开了 `--auth` 后必须先有能管理用户的账号（localhost exception 只在完全没有用户时可用一次）。

> 🎯 关键要点
> - 没有 CREATE DATABASE，写数据即创建
> - use 只是切换上下文
> - show dbs 看不到空库
> - 建库之后要单独建用户与权限

### 19. 如何查看数据库列表？｜初级

核心结论：`show dbs`（或 `adminCommand({listDatabases:1})`）列出**有数据的**库及其磁盘占用；空库不显示，这是最常见的误判点。

- 常用命令：`show dbs` / `show databases`；`db.adminCommand({ listDatabases: 1, nameOnly: true })` 只列名字（库多时更快）；`db.runCommand({listDatabases:1})` 返回 `sizeOnDisk` 与 `empty` 标记。
- 当前库的详情：`db.stats()`（大小、集合数、索引数）、`db.printCollectionStats()`。
- 为什么看不到刚建的库：只有写入了数据才出现在列表里（见第 18 题）。
- 权限：非管理员用户执行 `listDatabases` 需要 `listDatabases` 权限，否则只返回自己有权限的库。
- 驱动里：`client.list_databases()` / `client.db.list_databases()`。

> 🎯 关键要点
> - show dbs 只列非空库
> - listDatabases 可加 nameOnly 减少开销
> - 空库要靠 db.stats() 或写入后确认
> - 列库需要权限，非管理员看到的不全
