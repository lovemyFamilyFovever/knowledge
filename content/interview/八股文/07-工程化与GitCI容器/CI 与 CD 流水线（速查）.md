# CI 与 CD 流水线

## 一句话定义

提交自动触发校验构建，再把产物安全地推到目标环境。

## 面试官为什么问它

他实际问的是「你那条流水线拦住了什么」——闸门清单比概念重要。

## 30 秒版回答

CI 是每次提交自动跑构建、单测、静态检查和类型检查，目标是把回归的发现时间压到分钟级。CD 有两层：持续交付是自动构建出随时可发布的产物，持续部署才是不经人手直接上生产。我会讲自己的闸门顺序——先跑秒级静态层，再并行跑纯逻辑测试套件，涉及界面和需要外部依赖的套件串行跑且缺依赖时明确标记跳过而不是静默。要点是失败必须可见、跳过必须声明，否则绿灯会骗人。

## 被追问三层时的诚实边界

我实际配过 GitHub Actions 与本地 pre-commit 的分工，并专门做过「怎么证明某一步真跑了」的判定（把跑、跳过、失败、崩溃四类状态都写进可读取的输出）；K8s 里的渐进发布编排我没有实操过，我的理解是蓝绿与金丝雀属于 CD 策略层，和流水线本身解耦。
