# SSE 与 WebSocket

## 一句话定义

一个是服务器单向推的 HTTP 长连接，一个是双向通道。

## 面试官为什么问它

这题你有很实的答案：你为什么选 SSE 而不是 WebSocket，这就是经验本身。

## 30 秒版回答

SSE 就是响应不结束的 HTTP：`text/event-stream`，服务器持续写事件，浏览器用 EventSource 订阅，自带跨域、自动重连和 Last-Event-ID 续传，协议成本极低，适合大模型逐 token 输出这类「只往下推」的场景。WebSocket 是全双工，握手后升级到独立协议，帧开销小、能双向，适合协同编辑、即时通讯、实时行情，但代价是要处理心跳、重连、鉴权与代理配置。我的选择规则是：只需要服务器推就选 SSE，它复用现成的 HTTP 基建。

## 被追问三层时的诚实边界

我实际做过的是把问答从普通请求改成 SSE 流式，用来解决网关 504 超时，并且处理过前端在流中断时的兜底渲染；WebSocket 的生产运维（负载均衡粘性会话）我没有实操过，我的理解是 SSE 在这点上完全继承 HTTP 的成熟方案，这是它被低估的优势。
