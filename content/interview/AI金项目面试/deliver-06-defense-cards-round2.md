# 卡 A1 · RAG 质量工程（知识库工程化 + 可测可定位可迭代）

> 源码/文档：`docs/AI问答系统架构/知识库建设/02-知识库整理规范.md`、`05-知识库测试与效果验证.md`、`正式知识库/*`（11 个文件）。
> 一句话定位：别人讲 RAG 只会说"接了向量库"，你能讲**入口质量规范 + 批测台 + 诊断分类法**——这才是"把 RAG 做准"的真功夫。

## 0. 电梯陈述（30 秒）
"RAG 答不准，九成问题不在模型，在**数据入口**和**路由**。所以我没把精力堆在调 Prompt 上，而是建了一套质量工程：① 入口端亲定《知识库整理规范》，保证每个知识块**被单独召回时也能答全**；② 测试端自建 **ERP 批测台**，100 道题覆盖 15 个分类、AI 初评 + 人工复核、可导出留档；③ 排错端定了**七类问题诊断分类法**和**固定定位顺序**——从文件、解析、召回、路由到回答逐层查，**只有确认是最后一步才动 Prompt**。把'答得准不准'从玄学变成可测、可定位、可迭代。"

## 1. 面试官会怎么挖 · 逐层答案

### 【L1】"你怎么保证你的 RAG 答得准 / 不胡说？"
→ 用第 0 段，落到三件事：**入口规范、批测台、诊断分类法**。强调一句："我更信'数据质量和路由对了，模型自然就准'，而不是反过来靠 Prompt 兜底。"

### 【L2】"知识库整理规范具体约束什么？"（入口质量）
→ 核心验收标准：**单个知识块被独立召回时，仍能回答 5 个问题——对象 / 结论 / 适用条件 / 例外 / 来源核验**。（`02:10-18`）
→ 几条硬纪律（能讲出来就很专业）：
- **禁跨块指代**（不准"上述/它/前者"），因为召回是单块召回，指代会断链；
- **标题必须含对象+主题**，因为"标题即检索词"；
- **参数不得与其单位/范围/例外拆散**，否则"有来源但仍答错"；（`02:22-65`）
- **检索词/别名保全**：钢厂简称、旧牌号 `0Cr18Ni9`/`J1-J5`、英文缩写 NPI/MHP/RKEF/HPAL/AOD/LME 一律保留；**正式名用于回答、别名用于召回，不可互替**；**禁止用 AI 常识自造映射**。（`02:70-83`）

### 【L2】"哪些进知识库、哪些不进？"（分流，高频追问）
→ 我有一张**稳定知识 vs 动态数据分流表**：牌号标准 / 采购规则 / 术语 → 知识库；价格 / 库存 / 进出口量 → **走 SQL 查实时库**；新闻 → 资讯流；未来价 → AI 测价。（`02:162-172`）
→ 拔高一句："**把时效数据塞进知识库是 RAG 最常见的错**——会过期、会自相矛盾。我的原则是知识库只放稳定方法论，动态数值一律现查。"（库存分析库就**只存'五问法'和口径守卫、不存某周数值**，`正式知识库/库存分析知识库.md:5-39`）

### 【L2】"批测台怎么做的？测什么？"（可测）
→ 自建 `/erp/ai-qa-optimization` 页 + `POST /api/internal/ai-test/run`：**仅 expert 模式、单批 ≤100、并发 1–10、AI 自动初评 + 人工复核、导出 JSON/Excel、批次历史留存**。（`05:59-76`）
→ **关键洞察（说出来很加分）**：100 题覆盖 15 个一级分类，但"**不是所有题都应该命中知识库——路由正确本身就是测试目标**"。（`05:28-55`）比如官方文件类就该被前置拒答、行情类就该走 SQL，这些"没命中知识库"恰恰是对的。

### 【L2/L3】"答错了你怎么定位？"（可定位可迭代）
→ **七类问题诊断分类法**，每类配"识别证据 → 修复位置"：知识缺失 / 有知识未召回 / 召回错误 / 上下文不完整 / 召回对但答错 / 路由错误 / 时效信息误入长期库。（`05:139-159`）
→ **固定定位顺序**：正式文件 → 解析挂载 → 召回 → 路由 → 回答，**只有排除到最后一步是回答层出错，才去改 Prompt**。（`05:139-159`）
→ L3 拔高（这题答好封神）："很多人 RAG 一答错就改 Prompt，越改越乱。我反过来——**改 Prompt 是最贵、最不稳、最难回归的修法，所以放最后**。先在数据和路由层定位，绝大多数'答错'其实是'召回错'或'路由错'。"

### 【L3】"你怎么知道知识库内容是对的？"（内容深度）
→ 举一个真实例子证明你不是堆量：标准库里我明确写了 **GB/T 20878-2024 只能解决牌号与成分、不能替代 GB/T 3280-2015 等产品标准**；国标/美标/日标/欧标之间只按"**近似对应**"理解（06Cr19Ni10 ↔ 304 ↔ S30400 ↔ SUS304 ↔ 1.4301），并标了废止/在起草标准的回答边界。（`正式知识库/不锈钢标准与牌号知识库.md:6-44`）

## 2. 陷阱点 / 诚实边界（别越线）
| 可能追问 | 你的安全口径 |
|---|---|
| "命中率/准确率多少？" | ⚠️ **主动亮诚实**：文档里明写"项目现有资料没有定义统一的召回分数/Top-K/分段长度/准确率阈值，因此**不编造数值**"（`05:177`）。就说"我没拍一个假准确率，而是用 100 题批测台跑回归、人工复核 bad case"。**这条诚实反而是强信号。** |
| "Prompt 迭代了几个版本？" | ⚠️ 仓库里有 v8~v13 及 `v13_保守Token优化版.md`，但两份 PE 文档自标 legacy、与现行 v2.5.5 不一致，**权威是 `bailian-app-system-prompt-v5.md`（未核）**。安全说法："迭代了多个版本、还专门做过一版保守 Token 优化"——**别报具体版本号，除非先核对 v5**。 |
| "知识库是你一个人写的？" | 内容口径来自业务/同事确认，我做的是**规范、整理、分流、测试体系**；规范里就有红线"不得用外部搜索静默覆盖同事已确认口径"（`02:98-106`）——**讲清协作边界更显可信**。 |

## 3. 记忆锚点
1. **入口规范**：单块可独立召回答全 5 要素 + 检索词/别名保全 + 稳定知识 vs 动态数据分流。
2. **批测台**：100 题/15 类、AI 初评+人工复核；"路由正确本身即测试目标"。
3. **七类诊断 + 固定顺序**：改 Prompt 放最后；不编准确率阈值。

# 卡 A2 · 多模态 OCR 单据识别（qwen-vl-max）

> 源码：`server/modules/settlement/ocr.service.ts`、`bailian.service.ts`；文档 `docs/结算系统/04-AI能力设计.md`。
> 一句话定位：不是传统 OCR，是**视觉大模型直接把合同/发票照片抽成结构化字段**，配防幻觉 + 人工确认闭环。

## 0. 电梯陈述（30 秒）
"结算要录大量合同和发票，人工录入慢又易错。我没走'传统 OCR + 版面规则'那条重路，而是直接调**百炼的视觉多模态模型 `qwen-vl-max`**：图片进去、结构化字段出来（合同号/签约方/金额/税率/板种/付款条款…）。关键做了两道保险——Prompt 里强制'**识别不到的字段必须输出 null**'防它编，服务端再做**字段清洗**（金额日期归一、枚举白名单、格式校验），最后**人工确认后才写库**。这套还沉淀成了我们后面所有 AI 接入的复用范式。"

## 1. 面试官会怎么挖 · 逐层答案

### 【L1】"OCR 识别合同怎么做的？"
→ 第 0 段。强调"**多模态大模型直抽语义字段**"而非"OCR 出文字再正则解析"。

### 【L2】"抽哪些字段？怎么保证不抽错？"
→ 合同字段：contractType / contractNo / partnerName / signDate / amount(不含税) / taxAmount / taxRate / board(板种) / paymentTerms / itemsSummary；发票字段：invoiceType / code / no / date / amount / exclusiveAmount / taxAmount / taxRate / buyer / seller / projectSummary。（`ocr.service.ts:19-62`）
→ **三层防错**：
1. **Prompt 防幻觉**：明确"识别不到必须输出 null"，宁可空着也不许编（`ocr.service.ts:71-113`）；
2. **服务端清洗**：金额/日期归一、枚举白名单、8MB 限制、MIME 嗅探、**容忍模型返回带 markdown 围栏的 JSON**（`ocr.service.ts:116-214`）；
3. **人工确认后才入库**（human-in-the-loop，`docs/结算系统/04-AI能力设计.md:154-163`）。

### 【L3】"为什么用 VL 大模型不用传统 OCR？"（取舍题）
→ "合同/发票**版式千差万别**，传统 OCR 出来是一坨文字，我还得为每种版面写解析规则，维护成本极高。VL 模型能**一步理解版面语义直接抽字段**，对新版式泛化好。代价是要防它幻觉、要人工兜底——所以我配了'必输 null + 清洗 + 人工确认'。**这是用可控性换泛化性**，在单据种类多的场景更划算。"

### 【L3】"这套东西复用性怎么样？"
→ "我把它抽象成了一个**可复用 AI 接入范式**：Prompt 常量 + 百炼调用 + 服务端清洗 + 人工确认后写库。后面的合同审查、异常检测都能套这个壳。"（`04-AI能力设计.md:154-163`）

## 2. 陷阱点 / 诚实边界
| 可能追问 | 你的安全口径 |
|---|---|
| "识别置信度多少？" | ⚠️ **`confidence: 0.9` 是硬编码、不是模型返回的置信度**（`ocr.service.ts:89,112`）。**绝不能说"模型给出 90% 置信度"**。可以说"目前置信度是占位常量，真正的质量保险走的是'必输 null + 服务端校验 + 人工确认'这条链"。 |
| "合同审查/对比/信用评分也是 AI 吗？" | ⚠️ **不是**。文档明写这些是**规则 fallback**（`04-AI能力设计.md:12-19`；`contract.service.ts:428-481`）。只有"拍照识别"是真 AI。**别把规则说成 LLM。** |
| "结算系统整体上线了吗？" | ⚠️ 51 平台数据已真实化落 PG，但**合同等明细五表目前走 MockStore（JSON 文件）过渡**（见 A6/`deliver-05`）。讲法："OCR 识别能力是真的、结算明细表在分批迁移落库中"，**别说"全链路已上生产库"**。 |

## 3. 记忆锚点
1. **qwen-vl-max 多模态直抽语义字段**（不是传统 OCR+正则）。
2. **三层防错**：必输 null（防幻觉）+ 服务端清洗 + 人工确认才入库。
3. ⚠️ confidence 0.9 是硬编码；合同审查/对比是规则不是 AI。

# 卡 A3 · 纯规则个性化推荐 + 低成本用户画像

> 源码：`server/modules/plaza/plaza-recommendation.service.ts`、`profile-scoring.ts`；文档 `docs/智能广场/06、13`。
> 一句话定位：小数据量下**故意不训模型**，用可解释规则把推荐做稳——这是成熟的工程取舍，不是能力短板。

## 0. 电梯陈述（30 秒）
"智能广场的推荐我**没上机器学习**——因为当时只有十几个活跃用户，样本量根本训不出可靠模型，硬上反而是负资产。我用的是**纯规则多因子打分**：400 条候选池，按画像匹配、近期行为、作者偏好、热度、时效、探索六项加权打分，减去已看已赞的惩罚。里面有两个我比较得意的小设计：一是 **FNV-1a 稳定探索分**——用'用户+日期+刷新种子+内容 id'做哈希，保证下拉刷新能换一批、但翻页时顺序不跳；二是**多样性贪心重排**，连续同作者、同钢种会扣分，防信息茧房。画像也是规则算的：行为价值 × 时间衰减 × 重复抑制，再用置信度门控，低置信的画像不参与推荐。"

## 1. 面试官会怎么挖 · 逐层答案

### 【L1】"推荐怎么做的？用推荐模型了吗？"
→ 第 0 段。**大方说"故意不用模型"**，并立刻给理由（15 活跃用户、训不出也养不起、规则可解释可快速调）。

### 【L2】"打分具体怎么算？"
→ 候选池 400 条（**75% 最新 + 25% 热门**）；评分 = 画像匹配 35 + 近期行为 25 + 作者偏好 10 + 热度 10 + 时效 10 + 探索 5，再**减去已看/已赞惩罚**。（`plaza-recommendation.service.ts:225-247`；`docs/智能广场/06:38-65`）

### 【L2】"那个'稳定探索分'解决什么问题？"（亮点细节）
→ 矛盾是："下拉刷新用户**期待换一批**，但往下翻页时**不能又跳回前面看过的顺序**。" 我的解法：探索分用 **FNV-1a 哈希 `memberCode:日期:refreshSeed:newsId`**——`refreshSeed` 变（刷新）则换序，翻页时 seed 不变则顺序稳定。（`plaza-recommendation.service.ts:488-501`）

### 【L2】"怎么防止全是同一类内容（信息茧房）？"
→ **多样性贪心重排**：连续同作者 −12、同作者累计每次 −4、连续同钢种 −5，在排序后期做打散。（`plaza-recommendation.service.ts:300-329`）

### 【L2/L3】"用户画像怎么建的？为什么不训模型？"
→ **V2 低成本画像 = 规则而非模型**：得分 = 行为价值 × **时间衰减(半衰期 7/30 天)** × **重复抑制(1+ln(viewCount))**，指数归一到 0–100；**置信度 = min(1, (activeDays + 2×高意图activeDays)/5)**；消费端**只用 confidence ≥ 0.4 且 score ≥ 20** 的特征。（`docs/智能广场/13:246-288`）
→ 五维画像（钢种/市场/主题/商业意图等）存 **JSONB `profile_features`**，**影子计算** 6 小时聚合、旧字段双写兼容、**可回滚**。（`13:115-173`）
→ L3 拔高："小数据下我宁愿要**可解释、可调、可回滚**的规则，也不要一个训不好还说不清为什么的模型。等用户量起来，这套画像特征可以直接喂给模型做冷启动先验——**规则不是终点，是没有数据时最稳的起点**。"

## 2. 陷阱点 / 诚实边界
| 可能追问 | 你的安全口径 |
|---|---|
| "这算推荐算法吗？" | ⚠️ 诚实定性：它是**规则打分排序**，不是机器学习/向量召回。**别包装成"推荐算法引擎/个性化模型"**——讲"小数据下的可解释规则方案"反而显工程成熟度。 |
| "为什么不用向量/协同过滤？" | "十几个活跃用户，协同过滤没有共现矩阵、向量召回没有行为语料，**数据量不支持**；规则方案能立刻上线、可解释、可灰度。这是数据约束下的取舍，不是不知道这些方法。" |
| "画像 V1 怎么做的？" | V1 是在 Controller 层拦截问答/配单/点赞/评论行为、按需调百炼提炼标签（`docs/智能广场/07:133-192`）。⚠️ **docs/07 里有已废弃的飞书 Bitable 方案，别引用那部分**。 |

## 3. 记忆锚点
1. **故意不训模型**（15 活跃用户）→ 可解释规则打分，6 因子加权 − 已看惩罚。
2. **FNV-1a 稳定探索分**：刷新换序、翻页不跳；**多样性重排**防茧房。
3. **画像 V2**：行为 × 时间衰减 × 重复抑制 + **置信度门控(≥0.4)**，JSONB + 影子计算 + 可回滚。

# 卡 A4 · 交易风控自动化（cron + 幂等 + 可配置规则）

> 源码：`server/modules/trade/trade-violation.automation.ts`、`trade.service.ts`。
> 一句话定位：用定时任务把"交易违约"的预警/标记/冻结自动化，工程亮点是**幂等**和**阈值可配置不发版**。

## 0. 电梯陈述（20 秒）
"交易模块有一套**风控自动化**：`@nestjs/schedule` 每小时跑一次——临近截止 6 小时给买家预警，超时自动把 deal 标记为 timeout 并累加违约计数，**违约达到阈值就冻结对方查看联系方式的权限**。两个工程点：所有动作带**幂等键**防重复通知，阈值不写死、走**可配置规则表 + 缺省回退**，运营调风控松紧不用发版。"

## 1. 面试官会怎么挖 · 逐层答案

### 【L1】"交易这块做了什么自动化？"
→ 第 0 段：每小时 cron，预警 / 超时标记 + 违约计数 / 达阈值冻结查看。（`trade-violation.automation.ts:9-62`）

### 【L2】"定时任务重复跑会不会重复发通知？"（幂等，必问）
→ **幂等键**：预警用 `dealId-warn`、违约用 `dealId-violation`，同一 deal 同一动作只生效一次，cron 重复跑也不会重复通知。（`trade-violation.automation.ts:28-62`）

### 【L2】"违约阈值写死的吗？"
→ 不写死。阈值来自**可配置 `trade_view_rules` 表**，并做**逐字段缺省回退**——表里没配也能用默认值跑。（`trade.service.ts:69-105`）配套业务规则："查看联系方式 = 绑定 deal + 下架快照"。（`trade.service.ts:49-55,107-111`）

### 【L3】"为什么要可配置 + 缺省回退？"
→ "风控松紧是**运营策略**，会随业务调；写死就得每次发版。放配置表让运营自助调；缺省回退是兜底——**配置缺失不能让线上交易卡死**。"

## 2. 陷阱点 / 诚实边界
| 可能追问 | 你的安全口径 |
|---|---|
| "这是风控系统吗？用了 AI 吗？" | ⚠️ **别拔高**。它是**业务规则自动化**（定时任务 + 幂等 + 可配置阈值），**不是 AI/机器学习风控**。讲工程严谨性即可，硬说"智能风控"会被一问就穿。 |

## 3. 记忆锚点
1. 每小时 `@nestjs/schedule` cron：预警 / 超时违约计数 / 达阈值冻结查看。
2. **幂等键**（dealId-warn、dealId-violation）防重复通知。
3. 阈值走**可配置表 + 缺省回退**，运营调策略不发版。

这四块共同印证你的主叙事——**"会把大模型用到真实业务里 + 在资源受限下做工程取舍"**：

# 卡 E · "你说环境严重受限，那你怎么优化 / 怎么克服的？"（面试官必挖·跨模块）

> 用户自标：简历写"平台环境严重受限"，面试官看到**一定会追问"那你怎么优化"**。高频必问题，务必能分层答满 2–3 层。
> 核心心法：**受限环境的"优化"不是加机器，而是"把每个外部依赖都做成可降级、可替换、可脚本化"。**

## 0. 先把"受限"说具体（别空喊，30 秒）
"受限不是形容词，是四条硬约束：① 前期**没有独立服务器和数据库**；② 部署平台（飞书妙搭 FaaS）**只暴露一个 PostgreSQL**，外挂 Neo4j / 向量库 / 文件存储物理上不支持；③ **网关对慢请求不友好**（同步等大模型回完会 504）；④ 老平台接口被 **WAF 拦截**、代码同步链路很慢。我的做法是**把每条约束都变成设计输入**，而不是绕开或抱怨。"

## 1. 逐层怎么答

### 【存储受限】"只有一个 PG，怎么撑住图谱 + 检索 + 业务？"
→ 一切压单 PG：知识图谱用**两表**（实体/关系）+ MERGE 归一 + 应用层逐跳；检索用 **PG 关键词锚点 + 图谱/多表并发**，不上向量库；表结构走**编号化幂等迁移 + 可回滚**；用 **manual-schema** 摆脱平台对 `schema.ts` 的自动重写。

### 【网络/超时受限】"网关 504、慢请求怎么办？"
→ **SSE 流式**改造：边生成边推，避开网关掐断、降首字延迟；本地检索挂 **`Promise.race` 1500ms 超时**，检索拖了就返回空、**不阻塞主回答**。

### 【接口被拦】"老平台数据拿不到怎么优化？"
→ **WAF 逆向**：jsdom 执行挑战脚本取 cookie 打通接口，抽成可复用 `WafBypassService`；不满足于绕过，再推动**白名单正规化**。

### 【同步/部署脏活】"代码同步那么慢你怎么提效？"
→ 把脏活**脚本化 / Skill 化**：自研 `feishu-sync` AI Agent Skill，固化"本地生成 SQL/文件 → 幂等 DDL + 语法自检 → 沙箱执行 → pre-commit 校验"，把小时级手动同步变成**可重复、可校验**的流程。

### 【稳定性】"受限环境下怎么保证不崩？"
→ 全面**优雅降级**：51 数据 `bxgDegraded`、DB 失败降级空、OCR **人工确认才入库**、配单**两层 Fallback** 不白屏。受限环境里"可降级"比"完美"更重要。

## 2. 拔高一句（收尾用）
"所以我对'优化'的理解不是调参或加资源——在拿不到资源的环境里，**优化 = 让每个外部依赖可降级、可替换、可脚本化**，把不确定性关在边界里。"

## 3. 诚实边界
- ⚠️ **不要说"我优化了平台性能 / 我改了飞书网关"**——平台不是你的，你优化的是**自己的架构与工程取舍**。口径："我在平台约束下做了架构与工程上的取舍"。
- 被追"那拿到资源后呢"→ 大方讲：后期有了自己的 PG，已验证自建混合检索最小闭环；向量+图谱混合是拿到数据/部署条件后的自然演进（见 deliver-01 L3）。

## 附 · 120 万+ 存量批处理：吞吐/成本估算（面试被问"跑了没/多久跑完"用）

- **现状（务必如实）**：管线**已设计**（去重/规整/路由/抽取/自动确认/回填 + 熔断 + 断点续跑），**尚未跑全量**——先小批验证再放量，主要卡在 **Token 成本评估**。
- **吞吐估算（假设：qwen 单篇 1 次抽取、端到端 ~4–6s、并发 10–15）**：≈ 8–13k 篇/小时 → 120 万全量约 **5–10 天连续**跑完；含人工抽检则 **1–2 周**。
- **成本量级**：120 万 × ~1.5–2k token ≈ **20 亿+ token**，所以按"熔断 + 断点续跑 + 分批"设计，可按预算分阶段放量。
- ⚠️ **简历口径**：只写"设计…管线"，**不写"已处理 120 万"**（没跑=不能声称结果）。面试讲"**设计容量 + 为什么还没全量（成本）+ 断点续跑/熔断**"——把"没跑"讲成"成本可控的工程纪律"，反而是加分。
