## 8. Redis / Kafka 速成（面试前必过一遍）

### Redis —— **先纠正你的误区**
你说的"内存不够用时会再从 Redis 里的数据库取冷数据"——**这是错的**，面试这么说会直接暴露没用过。正确模型：

- Redis 是**内存 KV 存储**，不是"内存+硬盘两层自动降级"。它的硬盘（RDB 快照 / AOF 日志）只用于**持久化重启不丢数据**，**不是**用来放冷数据的。
- 真正的"两层"在**应用侧**：请求 → 先查 Redis → **命中就直接返回**；**未命中(cache miss)才去查 MySQL/PG**，查完**回填 Redis**。这个"先缓存后 DB"的编排是**你的代码写的**，Redis 自己不管。
- 内存满了怎么办：按**淘汰策略**驱逐 key（`allkeys-lru` / `volatile-lfu` / `noeviction` 等），不是"落盘后继续读"。

**面试真会问的 5 题（背下来）**：
1. **常用数据结构**：String（缓存对象/计数器）、Hash（对象字段）、List、Set（去重/共同好友）、ZSet（排行榜/延迟队列）。
2. **缓存穿透**（查根本不存在的 key，每次都打到 DB）→ 空值缓存 / **布隆过滤器**。
3. **缓存击穿**（一个热点 key 过期瞬间大量请求压 DB）→ 互斥锁只放一个请求去重建 / 热点 key 逻辑过期不删。
4. **缓存雪崩**（大批 key 同时过期或 Redis 宕机）→ **过期时间加随机抖动** / 多级缓存 / Redis 高可用(哨兵、集群) / 限流降级兜底。
5. **怎么保证缓存和 DB 一致**→ 常用 **Cache Aside：先更新 DB，再删缓存**（不是改缓存）；追问就说"严格一致要引入延迟双删或订阅 binlog，我了解思路但没在生产做过"。
（加分题：分布式锁 `SET key val NX EX ttl` + 释放要校验持有者；为什么快：**纯内存 + 单线程避免锁竞争 + IO 多路复用**。）

**你的诚实话术**：
> "Redis 我**没有在 AI 金的生产环境用过**——因为平台只给我一个 PostgreSQL，缓存、会话、计数这些我都是在 PG 上做的。但它的原理和常见坑我清楚，这段时间我自己搭了一遍练手。以我对缓存一致性和淘汰策略的理解，上手不是问题。"
→ 这个回答**既诚实又反衬出你在受限环境下的替代能力**，比硬说"用过"强得多。
⚠️ 前提：**你真的去搭一个练手 demo**（半天：Spring Boot + Redis 给一个接口加缓存 + 手动制造一次穿透），这样最后一句才成立。

### Kafka —— 2 分钟搞懂
- 本质：**高吞吐的分布式消息队列 / 事件流平台**。生产者把消息发到 **Topic**，Topic 分多个 **Partition**（并行 + 有序的单位），消费者按 **Consumer Group** 拉取，**同组内一个分区只被一个消费者消费**（天然水平扩展），且消息**按 offset 保留**，可以重放（这点和传统 MQ 最大区别）。
- 解决三类问题：**解耦**（生产方不认识消费方）、**异步**（不用等下游处理完）、**削峰**（洪峰先堆在队列里，下游按自己节奏消费）。
- 话术：
> "Kafka 我没有生产经验，我不装。但我在 AI 金做过**并发多源召回 + 超时保护 + 熔断 + 断点续跑的批处理管线**，还有**定时任务 + 幂等键防重复通知**——本质都是在处理异步、重试和重复消费这些问题，只是我当时用 PG 表和调度实现，没换成 Kafka。中间件背后的问题是一样的，换工具对我是学习成本，不是能力空白。"
→ 顺带把 **MQ（消息队列）**的通用概念也补一句：至少一次/至多一次/恰好一次投递、**幂等消费**（你正好有真实例子：`dealId-warn` / `dealId-violation` 幂等键）。**这是你最能接上的一条**。
