## 一、构建工具与打包原理（Webpack）

### 1. Webpack 是什么？它有哪些核心概念？｜初级
> 💡 提示
别只背五个名词。说清每个概念在「模块图 → 产物」这条链路上负责哪一环。

> 🎯 关键要点
- 定位：静态模块打包器。它从入口出发递归构建依赖图，把各种类型的资源都当作模块处理，最后输出浏览器可直接运行的产物。
- 五个核心概念：
  - Entry：依赖图的起点，可以有多个入口。
  - Output：产物输出路径与文件名规则（用 `contenthash` 做长效缓存）。
  - Loader：在模块被加入依赖图前做转换（把 CSS、图片、TS 变成 Webpack 能理解的模块）。
  - Plugin：挂到编译生命周期的钩子上做更广义的事（产物处理、资源注入、环境变量替换）。
  - Mode：`development` / `production` 决定一组内置优化的开关。
- 补一个常被忽略的概念：**Chunk**。Module 是源码单位，Chunk 是打包阶段的分组单位，Bundle 是最终输出的文件。三者的关系能说清，说明你真理解打包过程了。

```js
// webpack.config.js
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  entry: './src/index.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: '[name].[contenthash].js', // 内容哈希，实现长效缓存
    clean: true,
  },
  module: {
    rules: [
      { test: /\.js$/, exclude: /node_modules/, use: 'babel-loader' },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
    ],
  },
  plugins: [new HtmlWebpackPlugin({ template: './src/index.html' })],
  mode: 'production',
};
```

> 🔍 追问
Module、Chunk、Bundle 三者的区别是什么？一个 Module 可能属于多个 Chunk 吗？

### 2. Webpack 中 Loader 和 Plugin 有什么区别？｜中级
> 💡 提示
一句话区分：Loader 处理「文件」，Plugin 处理「过程」。

> 🎯 关键要点
| 对比项 | Loader | Plugin |
|---|---|---|
| 作用对象 | 单个模块文件的内容 | 整个编译过程与产物 |
| 配置位置 | `module.rules` | `plugins` |
| 执行时机 | 模块加载/转译阶段 | 挂到编译生命周期钩子（hooks）上 |
| 能力边界 | 输入代码 → 输出代码 | 可读写编译对象、emit 新文件、修改产物 |
| 典型例子 | `babel-loader`、`css-loader` | `HtmlWebpackPlugin`、`MiniCssExtractPlugin` |

- Loader 的执行顺序与配置顺序相反（从右到左、从下到上），`use: ['style-loader', 'css-loader']` 是先用 `css-loader` 解析再用 `style-loader` 注入。
- Loader 也可以写成对象形式，用 `options` 传参，用 `enforce: 'pre' | 'post'` 调整执行时机。
- Plugin 的写法是「一个带 `apply(compiler)` 方法的类」，通过 `compiler.hooks.xxx.tap` 注册回调。

> 🔍 追问
写一个 Loader 时如何做缓存？`this.cacheable()` 有什么用？

### 3. 如何优化 Webpack 的构建性能？｜高级
> 💡 提示
先分清两个目标：构建速度（开发者等待时间）和产物质量（用户下载体积）。优化手段完全不同。

> 🎯 关键要点
- 构建速度：
  - 持久化缓存 `cache: { type: 'filesystem' }`，并把配置文件纳入 `buildDependencies`，避免改配置后复用旧缓存。
  - 缩小搜索范围：`resolve.extensions` 精简、`resolve.modules` 指定明确目录、`include/exclude` 限制 loader 作用范围。
  - 并行与替代：`thread-loader` 并行转译，或直接用 `esbuild-loader` / `swc-loader` 替换 Babel。
  - 开发态用 `eval-cheap-module-source-map` 之类低开销 sourcemap。
- 产物质量：
  - `splitChunks` 拆 vendor，配合 `contenthash` 做长期缓存。
  - Terser 压缩、tree-shaking、`usedExports`、`sideEffects` 声明。
  - 体积分析用 `webpack-bundle-analyzer` 定位「谁把包撑大了」。
- 排查方法：`--profile` 输出各阶段耗时，或 `speed-measure-webpack-plugin` 看每个 loader 的时间占比，先治最大的那块。

> ⚠️ 注意
盲目上 `thread-loader` 有时会更慢——每个 worker 都有启动和通信开销，小项目里反而负优化。

> 🔍 追问
构建时间从 60 秒变成 90 秒，你会按什么顺序排查？

### 4. Webpack 从入口到产物经历了哪些阶段？｜中级
> 💡 提示
这题考的是你对编译流水线的整体认知，说清「哪些阶段可以被 plugin 介入」是加分项。

> 🎯 关键要点
- 主要阶段：`初始化参数` → `开始编译`（创建 compiler）→ `确定入口` → `编译模块`（递归解析依赖，对每个模块按 rules 应用 loader）→ `完成模块编译` → `输出资源`（按 chunk 组装、生成最终代码）→ `输出完成`（写入文件系统）。
- 关键机制：整个流程是「事件驱动」的，plugin 通过监听 hook 在阶段之间插入逻辑。`compilation` 对象承载单次构建的所有模块与 chunk 信息。
- 理解这个流水线的实际价值：你能判断一个问题该在哪个阶段解决——比如「产物里多了一个文件」要去 emit 阶段看，而「某个模块没被转译」要去 loader 阶段看。

> 🔍 追问
`compiler` 和 `compilation` 有什么区别？watch 模式下哪些对象会被复用？

### 5. Tree shaking 在 Webpack 中怎么才生效？｜高级
> 💡 提示
tree shaking 不是「开了就生效」的开关，它有严格的成立条件。

> 🎯 关键要点
- 三个前提：
  1. 代码必须是 ESM（`import` / `export`）。CommonJS 的 `require` 是运行时行为，静态分析不了。
  2. 包的 `package.json` 要有 `sideEffects` 声明，否则 Webpack 不敢删任何模块（默认认为都有副作用）。
  3. 生产模式（`mode: 'production'`）下才会启用 `usedExports` + 压缩器的死代码消除。
- 常见失效原因：桶文件（`index.js` 里全量 re-export）导致整包被拉入；`import * as ns` 让静态分析退化为动态访问；模块顶层写了副作用代码（如 `window.xxx = ...`）导致整个模块被保留。
- 验证手段：用 `webpack-bundle-analyzer` 看产物里是否出现了本不该有的模块；必要时用 `optimization.usedExports` 打日志观察导出使用情况。

```json
// 库作者必须正确声明，否则使用方无法安全摇树
{
  "name": "my-lib",
  "sideEffects": ["*.css", "./src/polyfill.js"]
}
```

> ⚠️ 注意
把 `sideEffects` 一股脑写成 `false` 会删掉必要的副作用代码（比如样式注入、polyfill 注册），这类 bug 通常只在生产构建出现，极难排查。

> 🔍 追问
怎么判断一个模块到底有没有副作用？

### 6. Webpack 的 HMR 是怎么工作的？｜中级
> 💡 提示
核心在于「热替换只更新变更的模块，并沿依赖链向上冒泡到最近的接受者」。

> 🎯 关键要点
- 基本流程：文件变更 → 文件监听触发重新编译（增量，只重编受影响模块）→ 通过 WebSocket 把变更清单推给浏览器 → 浏览器发起请求拉取更新后的模块 → 沿模块依赖链向上查找最近的 `module.hot.accept` 接受者 → 替换模块并执行 accept 回调。
- 关键点：如果没有模块接受这次更新，就会一路冒泡到入口，最终触发整页刷新（fallback to live reload）。这就是「为什么我改了某个文件页面会整体刷新」的原因。
- 框架的 HMR 能力靠 loader / plugin 预置 accept 逻辑实现，比如 React Fast Refresh、Vue 的 HMR 运行时。
- 配置要素：`devServer.hot: true`、`HotModuleReplacementPlugin`（新版本已内置）、`client.webSocketURL` 在反向代理场景要显式指定。

> 🔍 追问
HMR 更新后组件本地状态会丢，哪些情况下能保留、哪些不能？

### 7. sourcemap 有哪几种？生产环境怎么选？｜中级
> 💡 提示
面试官想听的是「你有没有考虑过源码泄露风险和调试效率的权衡」。

> 🎯 关键要点
| 配置 | 构建速度 | 质量 | 适用 |
|---|---|---|---|
| `eval` | 最快 | 只映射到模块 | 本地开发大项目 |
| `eval-cheap-module-source-map` | 快 | 行级、含 loader 前的源码 | 开发环境常用 |
| `source-map` | 最慢 | 完整，含列信息 | 需要精确调试 |
| `hidden-source-map` | 慢 | 生成但不在产物中引用 | 生产（上传到监控平台） |
| `nosources-source-map` | 慢 | 有映射但不含源码 | 生产（防泄露又想能定位） |

- 生产推荐组合：CSP 或内网监控场景用 `hidden-source-map`，把 map 上传到错误监控平台后从产物中移除，既不泄露源码又能还原堆栈。
- 反面做法：生产打 `eval` 或直接把带 `sourceMappingURL` 的 map 部署到公网，等于把源码送出去。

> ⚠️ 注意
`eval` 相关配置在 CSP 环境下会因为 `unsafe-eval` 被禁用而失效，这是很隐蔽的环境差异。

> 🔍 追问
线上报错的堆栈怎么和 sourcemap 对应起来？需要哪些信息才能还原？

### 8. Webpack 5 的 Module Federation 解决了什么问题？｜高级
> 💡 提示
它解决的是「多个独立构建的应用如何共享代码并运行时组合」，不是单纯的代码复用。

> 🎯 关键要点
- 核心能力：各应用独立构建、独立发布，运行时通过远程入口（`remoteEntry.js`）互相加载模块；被共享的依赖可以声明为单例（`shared`），避免同一框架加载多份。
- 典型场景：微前端、多个产品线共用组件库、按需加载其他团队的功能模块。
- 关键配置：`exposes`（暴露什么）、`remotes`（消费什么）、`shared`（共享依赖与版本策略）。
- 主要复杂度来源：版本协商（`requiredVersion` 不匹配时会加载多份）、类型提示缺失（需额外生成 d.ts）、调试困难（跨构建的模块边界）。
- 与替代方案对比：npm 包方案构建期解决但耦合紧；原生 ESM 远程模块运行时解决但生态工具少。Module Federation 是折中。

> ⚠️ 注意
共享依赖版本区间没对齐会导致运行时加载两份 React，典型症状是「Context 拿不到值」或 hooks 报错，排查起来很费时间。

> 🔍 追问
`shared` 里写 `singleton: true` 但版本不兼容会发生什么？

## 二、Vite 与现代构建

### 9. Vite 是什么？它和 Webpack 有什么本质区别？｜初级
> 💡 提示
关键差别在开发态：Vite 是「浏览器负责打包」，Webpack 是「构建器提前打包」。

> 🎯 关键要点
| 对比项 | Webpack | Vite |
|---|---|---|
| 开发态原理 | 先打包再提供服务，冷启动随项目规模线性变慢 | 基于原生 ESM 按需编译，启动时间与项目规模弱相关 |
| HMR | 重新构建受影响模块，链路较长 | 基于 ESM 的精确更新，通常更快 |
| 生产构建 | Webpack 自身 | Rollup（Vite 5 起可选择其他打包器） |
| 依赖处理 | 统一走打包 | 开发态用 esbuild 预构建成 ESM，并缓存 |
| 配置与约定 | 需要较多显式配置 | 约定优先，开箱即用 |
| 生态 | 插件生态最成熟，历史包袱多 | 插件生态现代化但覆盖面稍窄 |

- 本质差异的来源：开发态不做打包，把「模块解析」这件事交给浏览器的原生 ESM，构建器只负责把非 ESM 的依赖预构建成 ESM。
- 代价：开发态会产生大量模块请求（尤其深层依赖），所以预构建和 HTTP/2 变得很重要。

> 🔍 追问
Vite 开发态首屏仍然慢，你会怀疑哪些环节？

### 10. Vite 的依赖预构建做了什么？为什么需要它？｜中级
> 💡 提示
回答要落到两个具体问题上：CommonJS 无法在浏览器直接跑、深层依赖会产生请求瀑布。

> 🎯 关键要点
- 两件事：
  1. 格式转换：把 CommonJS / UMD 的依赖转成浏览器能直接加载的 ESM。
  2. 请求合并：把有大量内部模块的依赖（比如 `lodash-es` 的上百个文件）打成一个文件，避免浏览器发出成百上千个请求。
- 缓存位置在 `node_modules/.vite`，依赖或配置变化时会自动重新预构建；排查疑难问题时的常用手段是删掉它重来。
- 手动干预：`optimizeDeps.include` 强制预构建（适合动态 import 从而没被扫描到的依赖）、`optimizeDeps.exclude` 排除本地开发的包（否则源码改动不会热更新）。

```js
// vite.config.js
export default defineConfig({
  optimizeDeps: {
    include: ['lodash-es', 'echarts'], // 大型依赖，强制合并预构建
    exclude: ['my-local-lib'],          // 本地源码包，走实时编译才能热更新
  },
});
```

> 🔍 追问
开发时改了本地依赖包的源码但页面没更新，怎么定位？

### 11. Vite 怎么处理 CSS 和静态资源？｜中级
> 💡 提示
Vite 对资源有一套隐式规则（体积阈值、资源目录、路径改写），答题时把规则说清是关键。

> 🎯 关键要点
- CSS：直接 `import './x.css'` 即可；支持 Sass / Less / Stylus（装上预处理器即可用）；`*.module.css` 自动启用 CSS Modules；PostCSS 配置走 `postcss.config.js`。
- 资源导入：`import logo from './logo.png'` 会得到一个 URL 字符串。
- 内联规则：小于 `build.assetsInlineLimit`（默认 4096 字节）的资源会被转成 base64 内联，避免小文件产生额外请求。
- 公共资源：`public/` 目录下的文件不做处理直接拷贝，必须用绝对路径引用；`assets/` 下的走构建管线、带 hash、可被缓存。
- 动态路径：`new URL('./x.png', import.meta.url)` 是运行时拼接路径的正确写法，静态字符串拼接会被构建器漏掉。

> ⚠️ 注意
`assetsInlineLimit` 调太大会让 HTML/JS 体积膨胀且丧失独立缓存能力，图片尤其要慎重。

> 🔍 追问
为什么 `public/` 里的文件不能通过 `import` 引用？

### 12. Vite 开发态为什么不打包，生产态还要打包？｜中级
> 💡 提示
这题考察你是否理解「开发效率和用户加载效率是两个不同的优化目标」。

> 🎯 关键要点
- 开发态的目标是「改一行代码多快能看到效果」：不打包意味着不需要为整个应用构建依赖图，启动和热更新都只处理有变化的模块。
- 生产态的目标是「用户下载最少、请求最少」：不打包会产生大量细碎请求，深层的间接依赖会造成请求瀑布，在弱网下延迟极高。同时生产还需要压缩、tree-shaking、按内容哈希做长效缓存，这些都要在构建期完成。
- 结论：开发用「按需编译 + 预构建」，生产用「打包 + 优化」，各自用最合适的手段。

> 🔍 追问
如果生产环境开启 HTTP/2 多路复用，是不是就不用打包了？

### 13. Rollup 的定位是什么？为什么它适合打包库？｜中级
> 💡 提示
核心优势来自「原生 ESM 优先 + 静态分析彻底」，所以 tree-shaking 结果最干净。

> 🎯 关键要点
- 优势：原生支持 ESM，静态分析彻底，tree-shaking 效果好；产物干净、没有运行时胶水代码；支持多格式输出（ESM / CJS / UMD）。
- 适合库的场景：需要同时给不同模块体系的使用方提供产物；包体积敏感；依赖简单纯粹。
- 局限：处理 CommonJS 依赖要 `@rollup/plugin-commonjs` 兜底，对 CSS、资源、复杂代码分割的支持不如 Webpack 顺手。
- 库打包要点：`peerDependencies` 中的框架不要打进产物；输出保留 sourcemap；提供类型声明；容器包声明 `sideEffects`。

> 🔍 追问
同一个库同时输出 ESM 和 CJS，怎么避免使用方加载两份实例？

### 14. esbuild 为什么快？它的局限在哪？｜中级
> 💡 提示
快的三条原因要说全：Rust 实现、多核并行、以及**刻意不做某些事**。

> 🎯 关键要点
- 快的原因：用 Go 编写（无 JIT 预热、内存布局紧凑）；全程并行化；AST 复用不做多次遍历；自研解析器；把数据在进程内共享而不是走 IPC。
- 关键取舍：它**不做类型检查**，TypeScript 只做类型擦除；不构建完整的多阶段依赖图，因此难以实现需要全局信息的高级优化；插件 API 相比 Webpack 窄得多。
- 定位：极佳的转译器与压缩器，Vite 开发态和很多工具的底座；不适合作为需要复杂插件链的主构建器。

> ⚠️ 注意
用 esbuild 转译 TS 时必须独立跑 `tsc --noEmit`，否则类型错误会一路带到线上。这是最常见的事故来源。

> 🔍 追问
`const enum` 在类型擦除模式下不能工作，怎么解决？

### 15. SWC 和 Babel 怎么选？｜中级
> 💡 提示
不是「谁更先进」的问题，是「你的转换需求有多复杂」的问题。

> 🎯 关键要点
- SWC：Rust 实现，多核并行，速度通常比 Babel 快一个数量级；原生支持 TS 与 JSX；生态与插件能力弱于 Babel。
- Babel：JS 实现，插件生态极其丰富，支持自定义 AST 转换、babel 宏等高级能力；速度是硬伤。
- 决策依据：
  - 只做标准转译（TS / JSX / 目标降级）→ SWC 或 esbuild，性价比最高。
  - 依赖特定 Babel 插件、自定义转换、或框架强绑定 → 保留 Babel。
  - 混合方案：SWC 做转译，Babel 只跑必须的自定义插件，但要注意两阶段转换的兼容性。
- 生态事实：Next.js 已默认使用 SWC，说明主流场景下它完全够用。

> 🔍 追问
迁移到 SWC 后怎么验证转译结果与 Babel 等价？

### 16. 怎么看 Turbopack、Rspack 这类 Rust 构建器？｜中级
> 💡 提示
回答要跳出「性能更好」这一层，谈兼容成本与迁移风险。

> 🎯 关键要点
- 共同动机：现有 JS 构建器在大型项目上的性能瓶颈，以及增量编译的架构限制。用 Rust 重写可以拿到并行与内存效率上的根本优势。
- 两条路线：Turbopack 追求「重新设计增量计算架构」（函数级缓存、按需重算）；Rspack 追求「Webpack 兼容」（复用大部分 loader 与 plugin 生态，迁移成本低）。
- 选型考虑：生态兼容性（你的 loader/plugin 能不能用）、成熟度与稳定性（是否已 GA）、团队维护能力、以及回退路径。
- 现实建议：新项目可以直接用，老项目迁移要分阶段验证——先跑开发态，再跑生产态，逐项对比产物差异。

> ⚠️ 注意
「开发态变快」不等于「生产产物更好」，两个目标相互独立，评估时要分开做基准测试。

## 三、Babel 与编译转译

### 17. Babel 是什么？它有哪些核心功能？｜初级
> 💡 提示
关键认知：Babel 是「源码到源码」的编译器，它只做转换，不做打包也不做类型检查。

> 🎯 关键要点
- 定位：把现代/非标准语法转换成目标环境能运行的代码，属于编译期的语法变换工具。
- 三大能力：
  1. 语法转换：把新语法降级为目标环境支持的写法（可选链、类字段、装饰器等）。
  2. 语法扩展：JSX、TypeScript（剥离类型）等非标准语法的解析与转换。
  3. API 补齐（配合 polyfill）：为运行时缺失的内建方法提供实现。
- 三段式流程：`parse`（源码 → AST）→ `transform`（插件遍历 AST 并改写）→ `generate`（AST → 代码）。

```js
// babel.config.js
module.exports = {
  presets: [
    ['@babel/preset-env', { targets: '> 0.5%, not dead', useBuiltIns: 'usage', corejs: 3 }],
    ['@babel/preset-react', { runtime: 'automatic' }],
    '@babel/preset-typescript',
  ],
};
```

### 18. Babel 的 Presets 和 Plugins 有什么区别？执行顺序是怎样的？｜中级
> 💡 提示
执行顺序是这题的必答点，答错说明只背了概念没实际配过。

> 🎯 关键要点
- 关系：Preset 是一组 Plugin 的集合（可以理解为一个配置好的插件包），Plugin 是最小的转换单元。
- 执行顺序（容易记反，务必记准）：
  - Plugin 按配置顺序**从前到后**执行。
  - Preset 按配置顺序**从后到前**执行。
  - 整体上 Plugin 先于 Preset 执行。
- 为什么要反过来：Preset 通常是「新语法 → 旧语法」的降级包，多个 Preset 叠加时需要从最外层（最后配置的、更现代的）先处理，否则降级结果会被再次降级破坏。

```json
{
  "plugins": ["@babel/plugin-transform-arrow-functions", "@babel/plugin-transform-classes"],
  "presets": ["@babel/preset-typescript", "@babel/preset-env"]
}
```

### 19. 如何配置 Babel 支持 TypeScript？｜中级
> 💡 提示
核心结论只有一句：Babel 只剥离类型，不做类型检查，必须另配 `tsc`。

> 🎯 关键要点
- 配置方式：安装 `@babel/preset-typescript` 并加入 presets，指定 `.ts` / `.tsx` 扩展名让 Babel 处理。
- 分工：Babel 负责转译（快），`tsc --noEmit` 或 IDE 负责类型检查。构建流程里必须显式加一步类型检查，否则类型错误会静默通过。
- `tsconfig.json` 要点：设 `noEmit: true`（产物交给构建器）、开 `isolatedModules`（因为 Babel 逐文件转译，无法做跨文件的类型推导）、`jsx: 'react-jsx'`。
- 三个功能会失效：`const enum`、`emitDecoratorMetadata`（依赖类型元数据）、以及依赖类型信息的命名空间用法。

```json
// tsconfig.json
{
  "compilerOptions": {
    "target": "ESNext",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "strict": true,
    "isolatedModules": true,
    "noEmit": true,
    "skipLibCheck": true
  }
}
```

> ⚠️ 注意
开 `isolatedModules` 后，只导出类型必须用 `export type`，否则打包后该模块会被当成空模块，出现运行时错误。

### 20. @babel/preset-env 的 targets 和 useBuiltIns 怎么配？｜中级
> 💡 提示
这题是「有没有真正做过兼容性方案」的分水岭，尤其是 polyfill 的注入方式。

> 🎯 关键要点
- `targets`：声明要支持的运行环境。推荐用 `.browserslistrc` 统一管理（CSS 工具链也认这份配置），避免多处维护。`targets` 越精确，转换越少、产物越小。
- `useBuiltIns` 三档：
  | 取值 | 行为 | 适用 |
  |---|---|---|
  | `false` | 不注入 polyfill，需自行全局引入 | 已有统一 polyfill 方案 |
  | `entry` | 按 targets 在入口处全量注入需要的 polyfill | 传统站点，简单可控 |
  | `usage` | 按实际用到的 API 逐处自动注入 | 现代项目首选，体积最优 |
- `corejs` 要与安装的版本对应（如 `corejs: 3` 需要 `core-js@3`），版本写错会直接运行时报错。

> ⚠️ 注意
`usage` 模式对动态属性访问无能为力。`arr[methodName]()` 这种写法不会被检测到，对应 polyfill 不会注入。此外 `usage` 会注入全局 polyfill，不适合「不能污染全局」的库场景——库应该改用 `@babel/plugin-transform-runtime` 走局部引用。

> 🔍 追问
写第三方库时为什么不能用 `useBuiltIns: 'usage'`？

### 21. polyfill 和 core-js 怎么用才不臃肿？｜中级
> 💡 提示
polyfill 的成本在于「全局污染」和「体积」，两者都要谈到。

> 🎯 关键要点
- 两种注入哲学：
  - 全局 polyfill（`core-js` 直接引入）：改写 `Array.prototype` 等内建对象，能让所有代码和使用方都受益，但污染全局，且在多实例/微前端场景容易冲突。
  - 局部引用（`@babel/plugin-transform-runtime` + `@babel/runtime`）：按需引入 helper 和 polyfill，不污染全局，适合库和组件包。
- 减体积手段：靠 `targets` 精确裁剪（只用老浏览器才需要的 polyfill）；`usage` 模式按实际用量注入；避免整包引入 `core-js`。
- 现代取舍：如果目标用户集中在现代浏览器，很多 polyfill 可以直接不引入——先看真实用户的浏览器分布数据（RUM 或统计平台），而不是凭感觉兼容到 IE。

> 🔍 追问
微前端场景下两个子应用分别注入了 `core-js`，会有什么问题？

### 22. 怎么写一个 Babel 插件？｜高级
> 💡 提示
核心是「AST 遍历 + visitor 模式 + 节点的定位与替换」，能说出这三点就算答到点上。

> 🎯 关键要点
- 结构：插件是一个返回 `{ visitor }` 对象的函数；`visitor` 里的 key 是 AST 节点类型，value 是处理函数（接收 `path` 和 `state`）。
- 关键对象：
  - `path`：节点在树中的位置，提供替换（`replaceWith`）、删除（`remove`）、插入（`insertBefore`）、以及作用域信息（`path.scope`）。
  - `state`：跨节点共享的状态与配置。
- 实用工具：用 `@babel/types`（`t`）构造节点，用 `path.isXxx()` 做类型判断，用 `babel-plugin-tester` 或快照测试验证转换结果。
- 开发流程：先在 AST Explorer 上看清目标代码的节点结构，再写 visitor，不要凭想象写路径。

```js
// 把所有 console.log 调用替换成 noop 调用（生产清理示例）
module.exports = function () {
  return {
    name: 'drop-console-log',
    visitor: {
      CallExpression(path) {
        const { callee } = path.node;
        const isConsoleLog =
          callee.type === 'MemberExpression' &&
          callee.object.name === 'console' &&
          callee.property.name === 'log';
        if (isConsoleLog) {
          // 用作用域安全的写法替换，避免直接改 node 导致作用域信息不一致
          path.replaceWithSourceString('void 0');
        }
      },
    },
  };
};
```

> ⚠️ 注意
直接修改 `path.node` 而不使用 `path` 的方法，容易破坏 `scope` 的信息一致性，后续插件读到错误的作用域数据。

> 🔍 追问

## 四、ESLint 与代码质量规范

### 23. ESLint 是什么？它有哪些核心功能？｜初级
> 💡 提示
把它定位成「可编程的静态检查框架」比「代码风格工具」更准确。

> 🎯 关键要点
- 定位：基于 AST 的静态检查工具，用规则（rule）表达「什么是不允许的代码」，并支持自动修复。
- 三类规则：代码风格类（引号、缩进、分号）、错误预防类（未使用变量、`no-undef`、Promise 未处理）、团队约定类（自定义规则，如禁止某些 API）。
- 关键能力：自动修复（`--fix`，只对声明了 fixer 的规则生效）、共享配置（`extends`）、插件系统（`plugins` 提供规则集合）、忽略配置。
- 与 TypeScript 的关系：类型相关的检查交给 `tsc`，`@typescript-eslint` 负责需要语法/类型信息的 lint 规则，两者互补而非替代。

### 24. 怎么配置 ESLint 与 Prettier 集成？｜中级
> 💡 提示
要讲清「职责边界」：ESLint 管代码质量，Prettier 管格式，两者不能互相抢活。

> 🎯 关键要点
- 推荐分工（也是社区当前的主流做法）：
  - ESLint：只负责质量和潜在错误。
  - Prettier：只负责格式。
  - 用 `eslint-config-prettier` 关掉所有与 Prettier 冲突的格式类规则。
- 关于 `eslint-plugin-prettier`：把格式问题当作 lint 错误报出来。好处是统一入口，坏处是变慢、报错信息冗长、且编辑器体验变差。现在的趋势是**不**推荐它，而是让两者各自独立跑。
- 编辑器侧：配置保存时格式化（format on save），用 Prettier 处理格式、ESLint 处理可自动修复的质量问题。

```js
// 现代做法：两条链路独立跑，互不干扰
// 1) eslint.config.mjs —— 只关心代码质量
// 2) .prettierrc —— 只关心格式
// package.json
{
  "scripts": {
    "lint": "eslint .",
    "format": "prettier --check .",
    "format:fix": "prettier --write ."
  }
}
```

> ⚠️ 注意
同时让 ESLint 的格式规则和 Prettier 生效，会出现「一个说加空格、一个说去空格」的死循环，两边都改不动。

### 25. 如何创建自定义 ESLint 规则？｜高级
> 💡 提示
面试官想看的是「你知道怎么把团队约定变成可执行的检查」，而不是能不能写插件。

> 🎯 关键要点
- 结构：规则是一个导出 `{ meta, create }` 的对象。`meta` 声明类型、文档、是否可修复、schema；`create(context)` 返回 visitor 函数集合。
- 关键 API：`context.report()` 报告问题（可带 `fix` 自动修复）、`context.getSourceCode()` 拿源码与注释、`context.options` 读配置项。
- 开发要点：必须写测试（RuleTester）、必须在 `meta.docs` 里说明为什么有这条规则、优先提供自动修复降低团队使用成本。
- 实用建议：只在「团队真实反复踩过的坑」上有必要写自定义规则。三条高价值规则的收益远大于三十条凭空设计的规则。

```js
// eslint-plugin-team/rules/no-implicit-any-fetch.js
module.exports = {
  meta: {
    type: 'problem',
    docs: { description: '禁止未处理错误的 fetch 调用' },
    fixable: null,
    schema: [],
  },
  create(context) {
    return {
      'CallExpression[callee.name="fetch"]'(node) {
        const src = context.getSourceCode().getText(node.parent);
        if (!/catch|then\(\s*\w+\s*,\s*/.test(src)) {
          context.report({ node, message: 'fetch 必须处理错误，否则会静默失败' });
        }
      },
    };
  },
};
```

> ⚠️ 注意
自定义规则的性能直接影响 lint 速度。避免在 visitor 里做全文件级的高成本计算，必要时用 `Program:exit` 做一次汇总。

### 26. 从 .eslintrc 迁移到 Flat Config 要注意什么？｜中级
> 💡 提示
这道题能区分「最近真的动过工程配置」和「知识停留在几年前」的候选人。

> 🎯 关键要点
- 主要变化：
  | 维度 | 旧版（.eslintrc） | Flat Config（eslint.config.js） |
  |---|---|---|
  | 配置文件 | 多份 + 一层层向上查找合并 | 单份配置导出数组 |
  | 继承方式 | `extends` 字符串 | 直接展开（spread）配置对象 |
  | 匹配范围 | 全局生效，靠 `.eslintignore` 排除 | 用 `files` / `ignores` 精确指定 |
  | 插件引用 | 字符串名 + 环境解析 | 直接 import 对象，显式声明 |
- 迁移要点：插件从「字符串名」改成「对象引用」；`ignorePatterns` 改用全局 `ignores`（要单独一个对象项，且不能与其他字段混写）；`env` 被 `languageOptions.globals` 取代。
- 迁移策略：先保证旧配置和新配置对同一份代码给出相同的告警数量，再逐项收紧，避免一次性引入大量新问题淹没团队。

```js
// eslint.config.mjs
import js from '@eslint/js';
import tseslint from 'typescript-eslint';
import react from 'eslint-plugin-react';

export default [
  { ignores: ['dist/**', 'coverage/**'] }, // 全局忽略必须单独成项
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    files: ['src/**/*.{ts,tsx}'],
    plugins: { react },
    languageOptions: {
      globals: { window: 'readonly', document: 'readonly' },
    },
    rules: { 'no-console': ['warn', { allow: ['warn', 'error'] }] },
  },
];
```

### 27. Monorepo 里怎么共享 ESLint 配置并控制 lint 性能？｜高级
> 💡 提示
两个关键词：配置复用和增量检查。前者是组织问题，后者是性能问题。

> 🎯 关键要点
- 配置复用：抽一个内部 `eslint-config-*` 包导出配置对象，各子包直接引用，改一处全局生效。避免每个包复制一份配置漂移。
- 性能优化：
  - 用 `--cache` 把检查结果缓存到本地，只重查改动文件。
  - 缩小检查范围：`files` 精确指定，`ignores` 排除产物和生成代码。
  - 慎用类型感知规则（需要构建 TS Program，在大仓库上极慢），只对核心包开启。
  - 把 lint 放进 CI 时按变更范围检查（只 lint 受影响的包）。
- 治理：规则收紧要分阶段（先 `warn` 收集问题量，再 `error` 卡口），一次性 `error` 会直接卡死所有人的提交。

### 28. 如何让代码规范真正落地，而不是靠自觉？｜中级
> 💡 提示
规范落地的核心是「工具化 + 低摩擦」，靠开会强调和个人自觉一定会崩。

> 🎯 关键要点
- 三层保障：
  1. 编辑器层：保存自动格式化 + 实时提示，让问题在写的时候就暴露。
  2. 提交层：`lint-staged` + `husky`（或其他 git hooks 方案）只检查改动的文件，保证速度可接受。
  3. CI 层：全量校验作为最终卡口，任何绕过都在这里被拦住。
- 降低摩擦：规则要少而准，能自动修复的一律自动修复，不要用规范去约束没有共识的偏好。
- 例外机制：确实需要违反规则时用 `// eslint-disable-next-line` 并写明原因，而不是关掉整条规则。
- 演进方式：新规则先以 `warn` 上线跑一段时间，看真实告警量再决定是否升级为 `error`。

> ⚠️ 注意
把格式问题也塞进 CI 作为 error 卡口，会导致大量「改一行代码报 300 个格式错误」的情况，团队很快学会绕过检查而不是遵守规则。

## 五、测试体系

### 29. 单元测试、集成测试、端到端测试有什么区别？怎么分配比例？｜中级
> 💡 提示
别只背金字塔。要说清每种测试的「成本」和「能捕获什么类型的问题」。

> 🎯 关键要点
| 类型 | 测试范围 | 速度 | 维护成本 | 擅长发现 |
|---|---|---|---|---|
| 单元测试 | 单个函数/类 | 毫秒级 | 低 | 逻辑错误、边界条件 |
| 集成测试 | 多个模块/接口协作 | 秒级 | 中 | 接口约定、数据流转、配置问题 |
| 端到端测试 | 完整用户路径 | 十秒到分钟级 | 高（脆弱） | 真实链路问题、集成缺陷 |

- 比例原则：越靠下越多、越靠上越精。常见的健康区间大致是「单元最多、集成为主、E2E 只覆盖关键路径」。具体的比例不重要，重要的是 E2E 要克制——它最慢、最脆弱、最难定位。
- 判断标准：一条测试如果「失败时说不清哪里坏了」，它的价值就很低。E2E 的失败往往需要人工复现，这是它最主要的隐性成本。
- 现代演变：测试奖杯（Testing Trophy）观点认为前端应以集成测试为主，因为组件的价值主要体现在协作上，纯函数逻辑往往很少。

> 🔍 追问
E2E 测试经常出现「偶发失败」，你怎么治理？

### 30. 如何编写可测试的代码？｜中级
> 💡 提示
这题本质在考设计能力。可测试性差通常意味着耦合高、职责不清。

> 🎯 关键要点
- 核心原则：把「计算」和「副作用」分开。纯函数最好测，副作用（网络、存储、时间、随机数）要能被替换。
- 依赖注入：不要在函数内部 `new` 依赖或直接引用全局对象，而是通过参数或构造函数传入。
- 单一职责：一个函数只做一件事，测试表达力才强。函数太长通常意味着需要拆分。
- 明确输入输出：避免隐式的模块级可变状态，那会让测试之间互相污染。
- 控制副作用来源：时间用可注入的时钟、随机用可注入的随机源、请求走统一的客户端封装（方便拦截）。

```js
// 难以测试：依赖被硬编码，无法替换
function getUser(id) {
  const db = new Database();
  return db.query(`SELECT * FROM users WHERE id = ${id}`);
}

// 可测试：依赖从外部注入，测试时可传假实现
function getUser(id, db) {
  return db.query('SELECT * FROM users WHERE id = ?', [id]);
}
```

> ⚠️ 注意
示例里的字符串拼接 SQL 也是典型反例，无论从测试还是安全角度看都是错的。参数化查询是基本要求。

> 🔍 追问

### 31. 前端性能测试怎么做？｜中级
> 💡 提示
关键区分：实验室性能测试（可复现）和线上性能监控（真实）。两者用途不同。

> 🎯 关键要点
- 测试对象分四类：加载性能（LCP / FCP）、运行时性能（长任务、帧率、INP）、资源性能（体积、请求数）、网络性能（各阶段耗时）。
- 工具分层：
  - 实验室：Lighthouse、WebPageTest（适合定位与对比，可复现）。
  - 代码级：Performance API（`performance.mark` / `measure`）、`performance.now()` 精确测函数耗时。
  - 线上：RUM 采集，看真实用户分布。
- 方法要点：固定测试环境（设备、网络节流、缓存状态）；多次测量取中位数而不是单次；建立基线后才能判断「变快了还是变慢了」。

```js
// 测一段代码的真实执行时间（比 console.time 更适合上报）
const start = performance.now();
renderList(10000);
const cost = performance.now() - start;
console.log(`renderList 耗时 ${cost.toFixed(1)}ms`);
```

### 32. 如何实现前端项目的自动化测试？｜中级
> 💡 提示
考察你是否真的搭过测试工程，而不是只会写测试用例。

> 🎯 关键要点
- 分层选型：
  | 层次 | 常用方案 |
  |---|---|
  | 单元 / 组件 | Vitest（Vite 项目）或 Jest + Testing Library |

```js
    },
  },

```

### 33. 测试覆盖率怎么看？多少才合适？｜中级
> 💡 提示
不要把覆盖率当目标。面试官想听的是你知道它的盲区。

> 🎯 关键要点
- 覆盖率的四种口径：语句、分支、函数、行。**分支覆盖率**最接近「逻辑是否被验证」的含义，但也不是充分条件。
- 盲区：覆盖率只说明代码被执行过，不说明断言正确。一个只调用不断言的测试也能拉满覆盖率。
- 合理用法：
  - 作为反馈指标而不是考核指标。
  - 用它找「完全没被测到的模块」，而不是追求数字到 90%。
  - 核心业务逻辑（金额计算、权限判断、状态机）要求高覆盖；UI 布局、胶水代码不强求。
- 危险做法：为了达标写「断言等于自身」的假测试。这比不写测试更糟，因为它给了虚假的安全感。

> ⚠️ 注意
覆盖率突然下降通常意味着新增了没测试的代码，把它接进 CI 做「不许下降」的卡口，比设绝对值门槛更有效。

> 🔍 追问
一个模块覆盖率 100% 但线上还是出了 bug，可能是什么原因？

### 34. 异步代码、定时器和网络请求怎么测？｜高级
> 💡 提示
异步测试的难点是「时间」和「不确定性」。核心手段是假定时器与网络拦截。

> 🎯 关键要点
- 假定时器：用框架提供的假时钟（Vitest 的 `vi.useFakeTimers()` / Jest 的 `jest.useFakeTimers()`）控制时间推进，避免 `setTimeout(1000)` 真等一秒。
- 网络请求：优先在「网络层」拦截（Mock Service Worker 之类）而不是 mock 具体的 axios/fetch 模块，这样被测代码里的请求逻辑保持真实。
- 等待策略：用 `waitFor` / `findBy*` 这类「轮询直到满足条件」的断言，而不是固定 `await sleep(500)`——后者是 flaky 测试的头号来源。
- 清理：每个用例后恢复真实定时器、清理拦截器、重置模块级状态，否则测试之间互相污染。
- 时间相关逻辑：不要直接调 `Date.now()`，注入时钟，让测试可以确定性地断言。

```ts
import { describe, it, expect, vi, beforeEach } from 'vitest';

beforeEach(() => { vi.useFakeTimers(); });

it('防抖函数在等待 300ms 后只执行一次', () => {
  const fn = vi.fn();
  const debounced = debounce(fn, 300);

  debounced(); debounced(); debounced();
  expect(fn).not.toHaveBeenCalled();   // 还没到时间，不该执行

  vi.advanceTimersByTime(300);         // 虚拟推进时间，不真等
  expect(fn).toHaveBeenCalledTimes(1);
});
```

### 35. 组件测试和 E2E 测试怎么选？｜中级
> 💡 提示
判断依据是「你要验证的是组件的行为还是整个系统的联通性」。

> 🎯 关键要点
- 组件测试（Testing Library 之类）：
  - 优势：快、稳定、能覆盖大量边界状态（加载中、空数据、错误、极端输入）。
  - 原则：像用户一样查询 DOM（用角色、文本、标签），而不是依赖实现细节的类名或 `data-testid` 泛滥。
  - 适合：一个组件的交互逻辑、状态分支、可访问性约束。
- E2E（Playwright / Cypress）：
  - 优势：真实浏览器、真实接口、能捕获「各部分都没问题但拼起来坏了」的缺陷。
  - 适合：登录、支付、核心下单链路这类不容失败的关键路径。
  - 代价：慢、受环境波动影响、定位困难。
- 组合策略：组件测试覆盖广度，E2E 覆盖关键路径的深度。不要把 E2E 当回归主力。

> ⚠️ 注意
组件测试里大量使用 `data-testid` 往往说明测试绑定了实现结构，重构时必然大面积失败。优先用可访问性查询。

> 🔍 追问
一个组件有 10 种状态变化，你会用组件测试还是 E2E 覆盖？

## 六、CI/CD 与部署

### 36. 什么是 CI/CD？它有哪些核心概念？｜初级
> 💡 提示
把 CI、持续交付、持续部署三个词分清楚，很多人在这一步就混了。

> 🎯 关键要点
- CI（持续集成）：频繁把小改动合入主干，每次合入都自动构建并跑测试，尽早发现集成问题。核心价值是「问题在小时级暴露，而不是在发版前」。
- 持续交付（Continuous Delivery）：CI 之后自动把产物部署到类生产环境并验证，但**发布动作由人决定**。
- 持续部署（Continuous Deployment）：连发布也自动化，通过验证即上线，没有人工卡点。
- 配套概念：流水线（Pipeline）、阶段与作业（Stage / Job）、产物（Artifact）、环境（开发/预发/生产）、回滚。
- 落地的关键前置条件：自动化测试可信、构建可复现、部署可回滚。缺任何一个，CI/CD 都会变成「自动化地制造事故」。

### 37. GitHub Actions 怎么用？有哪些关键概念？｜中级
> 💡 提示
考察你是否实际写过工作流，重点在触发条件、作业依赖和矩阵策略。

> 🎯 关键要点
- 文件位置与结构：`.github/workflows/*.yml`，由 `on` / `jobs` / `steps` 组成。
- 触发方式：`push`、`pull_request`、`schedule`（定时）、`workflow_dispatch`（手动）、`workflow_run`（上游工作流结束后触发）。
- 作业与依赖：`needs` 声明依赖关系，默认并行执行；`matrix` 做多版本/多平台组合。
- 缓存与产物：依赖缓存（`actions/cache` 或 setup-node 的 `cache` 参数）决定流水线速度；产物上传用 `actions/upload-artifact`。
- 密钥管理：`secrets` 存敏感信息，注意 fork 的 PR 默认拿不到 secrets（这是安全设计，不是 bug）。
- 复用：`workflow_call` 支持可复用工作流，`composite action` 支持复用步骤。

```yaml
name: CI
on:
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [20, 22]      # 多版本并行验证
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm         # 缓存依赖，显著缩短安装时间
      - run: npm ci          # 用 lockfile 严格安装，保证可复现
      - run: npm run lint
      - run: npm test
```

### 38. 蓝绿部署和金丝雀发布有什么区别？怎么选？｜高级
> 💡 提示
核心差别在「资源成本」和「风险暴露面」的权衡。

> 🎯 关键要点
| 策略 | 机制 | 回滚速度 | 资源成本 | 风险 |
|---|---|---|---|---|
| 蓝绿 | 两套完整环境，流量整体切换 | 极快（切回即可） | 高（双倍资源） | 一次性全量暴露 |
| 金丝雀 | 少量流量先跑新版本，逐步放大 | 快（撤回少量流量） | 低 | 逐步暴露 |
| 滚动 | 逐批替换实例 | 中（需要回滚多批） | 低 | 混合版本共存期最长 |

- 选型：需要「秒级回滚 + 有充足资源」→ 蓝绿；「风险敏感 + 资源有限」→ 金丝雀；「无状态服务 + 常规发布」→ 滚动。
- 金丝雀的关键配套：必须有能区分新旧版本的监控指标（否则放大了也不知道好坏），且要有明确的判定标准和自动回滚条件。
- 通用前置：数据库变更必须向后兼容（不能删字段，只能先加后弃），否则任何策略都救不了回滚。

> ⚠️ 注意
蓝绿部署最大的隐性成本是数据库和外部状态。有状态的迁移一旦执行，切回旧版本可能直接不可用。

> 🔍 追问

### 39. 如何监控和告警 CI/CD 流程？｜中级
> 💡 提示
流水线本身的健康度也是被监控对象，这一点经常被忽略。

> 🎯 关键要点
- 关键指标：构建成功率、构建时长（分位值）、排队等待时间、部署频率、变更前置时间、变更失败率、平均恢复时间。
- 告警设计：只在「需要人介入」时告警。构建失败给提交者发通知，连续失败或主干长时间红才升级到群里或值班。
- 减少噪声：区分 flaky（偶发失败）和真实失败，flaky 用例要单独治理——它会训练团队「忽略红色」，这是最危险的后果。
- 可观测：保留构建日志与产物、记录谁触发的、保留历史趋势，便于定位「什么时候开始变慢的」。

> ⚠️ 注意
告警疲劳是 CI 最严重的失败模式。一周内被忽略 10 次之后，第 11 次真故障也没人看。

> 🔍 追问

### 40. 怎么设计一条高效的流水线？｜高级
> 💡 提示
高效 = 快速反馈 + 不做重复工作 + 无效工作早失败。

> 🎯 关键要点
- 阶段顺序按「失败成本从低到高」排：静态检查（lint / 类型）→ 单元测试 → 构建 → 集成/E2E → 部署。便宜的先跑，让错误在 1 分钟内暴露。
- 并行化：独立的检查并行跑；测试按分片拆分并行执行，缩短墙钟时间。
- 缓存：依赖缓存（lockfile 为键）、构建缓存、测试缓存。缓存必须能安全失效，不能因为缓存命中而产生错误结果。
- 只做必要的事：按变更范围决定跑哪些任务（改文档就不必跑全量 E2E）；用 `paths` 过滤触发条件。
- 可复现：固定工具链版本、用 lockfile 严格安装、构建产物带版本与 git SHA 标记。

> 🔍 追问
流水线里有一部分任务只对 main 分支有意义，你在 PR 上还需要跑吗？

### 41. 多环境的配置和密钥怎么管理？｜高级
> 💡 提示
这题是安全与工程规范的交叉考点，回答不当会被认为风险意识不足。

> 🎯 关键要点
- 配置分层：环境无关的配置进代码仓库；环境相关的值（地址、开关）走环境变量或配置中心；**密钥永远不进仓库**。
- 密钥管理：用平台的密钥存储（CI secrets、云厂商密钥服务），运行时注入；定期轮换；最小权限（每个环境用独立的凭据，生产密钥绝不用于测试）。
- 构建产物一致性：同一个产物应该能部署到任意环境，环境差异通过运行时配置注入——而不是「每个环境打一次包」，那样测过的产物和上线的产物不是同一个东西。
- 审计：密钥的读取要有记录，异常访问要能告警。

> ⚠️ 注意
把密钥写进代码再「事后删掉」是无效的——git 历史里永久留存。一旦提交过就必须立即轮换密钥，而不只是删代码。

> 🔍 追问
前端项目里没有真正的秘密（代码会被用户下载），那环境配置怎么处理？

### 42. CI 里的 E2E 测试怎么保证稳定性？｜高级
> 💡 提示
E2E 在 CI 里失败的原因里，「产品真的有 bug」通常只占少数，大部分是测试自身的问题。

> 🎯 关键要点
- 减少不稳定的来源：
  - 数据隔离：每个用例用独立的数据（随机后缀或按运行 ID 隔离），避免并发互相干扰。
  - 等待策略：绝不用固定 `sleep`，用「等待条件成立」（元素可见、网络空闲、特定状态出现）。
  - 选择器：用语义化的角色/标签选择器，避免绑死 CSS 类名或 DOM 层级。
  - 环境固定：依赖的服务要有健康检查门禁，环境未就绪就不要开始跑。
- 失败处理：自动保留截图、视频、浏览器日志与网络记录，否则远程调试成本极高。
- 重试策略：可以给 E2E 配置有限重试，但必须统计重试率——重试率上升说明有真问题在积累，不要把它当成默认降压阀。
- 治理节奏：定期清理过时用例。E2E 套件的维护成本会随时间自然增长。

> 🔍 追问
某个用例在本地稳定通过、在 CI 上 30% 失败，你会按什么顺序排查？

## 七、包管理与依赖治理

### 43. npm、yarn、pnpm 有什么区别？pnpm 为什么省空间？｜中级
> 💡 提示
核心差异在「依赖如何存储」和「node_modules 结构」，速度只是结果。

> 🎯 关键要点
| 维度 | npm | yarn classic | pnpm |
|---|---|---|---|
| 存储方式 | 每个项目独立复制 | 每个项目独立复制 | 全局内容寻址存储 + 硬链接 |
| node_modules 结构 | 扁平（提升） | 扁平（提升） | 符号链接 + 严格嵌套 |
| 幽灵依赖 | 容易产生 | 容易产生 | 基本消除 |
| 安装速度 | 中等 | 中等 | 快（大量文件直接链接） |
| 磁盘占用 | 高 | 高 | 低（同版本只存一份） |

- 幽灵依赖（phantom dependency）：扁平结构下，你能 import 一个没写进 `package.json` 的包，因为它被提升到了顶层。一旦上游依赖移除了它，你的代码就会突然崩——而且本地删掉 `node_modules` 重装才会暴露。pnpm 的严格结构从机制上避免这个问题。
- pnpm 的代价：依赖符号链接的严格结构，个别工具（尤其是老旧的构建插件）可能不兼容；跨磁盘时硬链接失效会退化为复制。

### 44. lockfile 有什么用？依赖版本怎么治理？｜中级
> 💡 提示
lockfile 的价值在「可复现」，这句话要说清它到底防住了什么。

> 🎯 关键要点
- 作用：锁定整棵依赖树的精确版本（含间接依赖）与完整性校验值，保证任何机器、任何时间安装都得到完全相同的依赖树。
- 没有 lockfile 的后果：`^1.2.3` 这类范围版本会随时间解析到不同结果，「昨天能跑今天不能跑」且难以复现。
- CI 必须用 `npm ci`（严格按 lockfile 安装，lockfile 与 package.json 不一致时直接失败），而不是 `npm install`（可能顺带改 lockfile）。
- 治理手段：
  - 定期用 `npm outdated` / `npm audit` 巡检，但不要盲目全量升级。
  - 用 `overrides` / `resolutions` 强制统一同一依赖的版本，消除重复实例。
  - 用 `npm ls <pkg>` 检查是否存在多版本共存。
  - 自动化更新工具（Dependabot / Renovate）分组 + 自动化测试兜底，把升级变成低风险动作。

> ⚠️ 注意
lockfile 冲突不要靠「随便选一边」解决，那样会丢依赖。正确做法是重新生成并跑完整验证。

### 45. Monorepo 怎么组织？有哪些工具和坑？｜高级
> 💡 提示
Monorepo 解决的是「多包协作成本」，代价是「构建与工具链复杂度」。要讲清这个权衡。

> 🎯 关键要点
- 适用场景：多个包需要频繁同步改动、共享工具链与规范、需要统一的版本发布节奏。
- 组织方式：用 workspaces（npm / yarn / pnpm）声明包范围；包之间用 workspace 协议互相引用，保证引用的是本地源码而不是发布版本。
- 构建编排：Turborepo / Nx 之类工具提供任务图与缓存——能根据依赖关系只重建受影响的包，并缓存未变化的产物。这是 monorepo 能不能规模化的关键。
- 常见坑：
  - 构建顺序问题（依赖包没先构建，导入失败）。
  - 循环依赖（包 A 引 B、B 又引 A），工具链通常无法处理。
  - 版本发布（统一版本 vs 独立版本）策略要提前定，中途改代价很大。
  - CI 全量构建导致流水线越来越慢，必须做「按变更范围构建」。
- 判断标准：如果各包之间几乎不联动，那拆成多个仓库更简单，不要为了「看起来先进」上 monorepo。

> ⚠️ 注意
monorepo 的 CI 性能是最容易失控的部分。没有增量构建能力时，仓库越大、等待越久，团队会开始绕过流水线。
