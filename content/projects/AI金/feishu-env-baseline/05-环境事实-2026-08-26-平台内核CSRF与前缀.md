## 2. CSRF 双提交校验 —— 三大关键行


### 📌 结论
- CSRF 中间件默认：请求头 `x-suda-csrf-token` 必须等于 cookie `suda-csrf-token`。
- 三种失败（缺 cookie / 缺 header / 值不匹配）都走 `sendForbidden` = **403 Forbidden**（非 401）。

### 📌 结论
- 独立 `csrf_token` 中间件负责**生成/种 cookie** 并注入 `req.csrfToken`。
- `req.csrfToken` 来自 `originToken`（读到已有 cookie）或新生成 `token`——典型的**双提交 cookie**：页面首次访问时由该中间件把 token 种进 cookie，后续请求把它放回 header 供比对。

### 📌 结论
- 平台中间件在 `configureApp` 内部：**读 `CLIENT_BASE_PATH`（= `/app/app_4k9x70cg0jws9/`）→ 仅当符合 `/^\/app\/[^/]/` → 用 `stripBasePath2` 剥掉前缀后再把请求路由进 Nest**。
- **这精确解释了之前的 bug**：平台层会剥 `/app/xxx` 前缀再交给 Nest Controller；但项目里 `AuthGuard` 用 `startsWith('/api/...')` 判断放行时**是基于 requests 原始 path（含前缀）或已剥前缀的路径**的差异——若 guard 基于未剥前缀判定，则会失配 → 误判需登录 → 401。修复 `auth.guard.ts` 剥前缀正是对症。
