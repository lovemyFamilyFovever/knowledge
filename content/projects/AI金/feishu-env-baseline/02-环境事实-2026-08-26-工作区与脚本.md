## 5. 核心脚本三连（编译 / 本地启动 / lint / dev）

### 5.1 `scripts/build.sh` —— **发布编译真正入口（最关键）**
自动生成（由 `fullstack-cli` 维护）。流程 6 步 + 2 个并行任务：
```
[0/6] npx fullstack-cli action-plugin init     ← 装 action 插件
[1/6] npm run gen:openapi                      ← 更新 openapi 代码（当前为 SKIP）
[2/6] rm -rf dist                              ← 清理
[3/6] 生成路由定义（并行）：
        npx generate-api-routes  --server-dir./server --out-dir./dist
        npx generate-page-routes --app-path  ./client/src/app.tsx --out-dir./dist
[4/6] 并行构建 server + client（NODE_OPTIONS 默认 +8GB heap）：
        npm run build:server  (nest build)
        npm run build:client  (vite build)
      仅前端时 only_frontend_change=true → 只 build client
[5/6] 准备产物：
        把 dist/client 下 HTML move 到 dist/dist/client  (HTML 不上 CDN)
        cp client/public → dist/dist/client
        cp scripts/run.sh → dist/
        [非 only_frontend] cp .env → dist/
        清理 dist/scripts、dist/tsconfig.node.tsbuildinfo
[6/6] node scripts/prune-smart.js              ← 智能依赖裁剪（分析实际依赖、复制并裁 node_modules、生成精简 package.json）
```

### 🔎 关键
- **发布产物 = `dist/` 下 `server/` + `dist/client/` + `run.sh` + `.env` + 被裁剪的 node_modules**。
- `[5/6]` move HTML → `dist/dist/client`：**HTML 不上公网 CDN**，所以前端 HTML 必须由 server 的 setBaseViewsDir 同源 serve —— 这是"为什么 views 路径要一致"的机制。
- `[6/6] prune-smart.js` 是平台"缩小体积"的黑盒裁剪，**可能剪掉运行时没扫到的依赖** → 若某个包未被 import 走就被剪，运行时才暴露 → 是"上线后部分接口/页面崩"的疑点源之一。
- 需要 `scripts/run.sh`（尚未读）才能真正还原 prod 启动入口。
- 8GB heap 提示：构建重物在 transform 阶段易 OOM —— 大前端项目构建耗时主要在这。

### 5.2 `scripts/dev-local.js` —— **本地启动入口（关键）**
整体 4 步：
1. **env pull**：若有 `lark-cli`，读 `.spark/meta.json` 的 app_id，跑 `lark-cli apps +env-pull --app-id <id> --as user` 拉沙箱身份/凭证到 `.env.local`。
2. **skills sync**：`npx @lark-apaas/miaoda-cli@latest skills sync --local`（同步 agent skills 到 `.agent`/`.claude`）。
3. **加载环境变量到 process.env**：先 `.env.local` 再 `.env`（dotenv override:false，`.env.local` 优先）。**含 SUDA_WEBUSER 特殊处理**（dotenv@17 剥引号后保留 `\"` 反斜杠 → 下游 JSON.parse 挂掉 → 做 unescape 兜底）。
4. **并发起 dev:server（nest start --watch）+ dev:client（vite）**，子进程继承 process.env。

### 🔎 关键
- **本地启动的本质 = 从沙箱拉 `.env.local`（身份/凭证）→ skills sync → 加载 env → 并发起前后端 dev**。
- `SUDA_WEBUSER` 是本地身份凭证，JSON-parse 有坑已内置兜底 —— 排查本地 401 时关注此变量是否正常。
- `MIAODA_LOCAL_DEV=1` 被设置 → 本地 SDK 据此走 local 分支（不读平台内部服务）。
- **skill 同步 `--local` 用 flat layout**（`.agent/skills` + `.claude/skills` 软链），与沙箱的 nested layout 区分。

### 5.3 `scripts/lint.js` —— 串行执行 eslint / type-check / stylelint
- 默认：`npm run eslint` → `npm run type:check` →（若可跑 stylelint）→ 串行，全跑完聚合成退出码。
- 支持 `--files` 选择性 lint（按扩展名分流：tsx/ts 走 server/client/shared；css 走 stylelint）。
- 对老模板（fullstack-nestjs-template 1.x）会缺 stylelint 配置而跳过。
- 风格目标：串行降并发、一次暴露所有问题。

### 5.4 `scripts/dev.sh` —— 环境判断 + 分发
```
if [ -n "$MIAODA_DEP_CACHE_DIR" ] || [ -n "$SANDBOX_ID" ]; then exec node dev.js   （沙箱=生产形态，保活/restart/log）
else → 本地：先 npx miaoda-cli app sync（同步 platform-controlled 内容+升包+迁移 scripts）→ exec dev-local.js
```
- `dev.js` 是**沙箱保活形态**的入口（未读到，待下轮 `cat scripts/dev.js`）；`dev-local.js` 是本地形态。
- 关键机制：**本地每次 `npm run dev` 前先跑 `miaoda app sync`** —— 平台会自动同步 platform-controlled 文件并升级 `@lark-apaas/*`。这解释了以往 "某种改动后本地依赖/脚本被平台自动更新" 的现象。

## 6. CLI 子命令细节 + 前缀确认

### 6.1 `miaoda deploy`（发布）
- 子命令 `get <deploy-id>`（详情）/ `history`（倒序分页）/ `error-log <deploy-id>`。
- flags：`--wait`（阻塞到终态，默认 300s）、`--timeout`。
- **强约束（文档明文）**：
  - 发布跑的是**当前分支远端 HEAD**——本地未 commit/push 不进产物。部署前必须 `git status` + `git rev-list --count @{u}..HEAD` 确认。
  - **禁止用异步/后台模式调用 deploy**（`&`/nohup/后台 task 等会让命令提前返回，Agent 误判已完成）。
  - 调用后未到终态需**每 2s 轮询** `miaoda deploy get <id> --json`（无 id 则先 `history --limit 1` 找）。

### 6.2 `miaoda db`（数据库）
- 子命令：`sql`（任意 SQL）、`schema`（表结构）、`data`（导入导出）、`changelog`（DDL 历史）、`audit`（表级审计）、`migration`（dev/online 多环境，仅专家模式）、`recovery`（PITR）、`quota`（存储用量）。
- flag `--env dev|online`（仅专家模式应用支持）。

### 6.3 `miaoda observability`（可观测性，**仅线上、只读**）
- `log`（线上日志）、`trace`（链路）、`source-stack`（反解前端错误堆栈→源码）、`metric`（requests/latency/cpu/memory）、`analytics`（users/page-view）。
- 上下文：`--app-id` 或 `MIAODA_APP_ID`。**只支持 online 环境**。

### 6.4 `miaoda registry`（组件 registry）
- `list`（列 SDK 条目+USAGE 原文）/ `add <token...>`（copy-in SDK 文件到项目根，含 Depends 传递闭包）。
- 仅 design-html / html stack；其余报 `REGISTRY_STACK_UNSUPPORTED`。

### 6.5 `CLIENT_BASE_PATH`
- **`/app/app_4k9x70cg0jws9/`** —— 与登录报错 URL 一致，确认即前端 base / 网关前缀来源。
- 因此 ERP 登录实际请求完整路径 = `.../app/app_4k9x70cg0jws9/api/erp/auth/login`，双提交 CSRF 也是挂在 app 路径下。
