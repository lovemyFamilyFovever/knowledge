# VIP 多维表格设计

> 配套 `01-多账号共享VIP套餐方案.md` 第三章，共 5 张表。

## 环境变量配置

```bash
# VIP 飞书多维表格
BITABLE_MAIN_APP_TOKEN=bascnxxxxxxxxxxxx        # 多维表格应用 ID
BITABLE_VIP_USERS_TABLE_ID=tblxxxxxxxx          # 1. 用户表
BITABLE_VIP_PACKAGES_TABLE_ID=tblxxxxxxxx       # 2. 套餐表
BITABLE_VIP_FEATURES_TABLE_ID=tblxxxxxxxx       # 3. 功能特性表
BITABLE_VIP_PURCHASES_TABLE_ID=tblxxxxxxxx      # 4. 购买记录表
BITABLE_VIP_MAPPING_TABLE_ID=tblxxxxxxxx        # 5. 成员关系表
```

## 设计要点

- **record_id 作为飞书内部 ID**：飞书多维表格每条记录自动生成 `record_id`，但仅作为内部标识，**不用于表间关联**。
- **业务标识符关联**：跨表关联使用人类可读的业务标识符（登录名、订单编号、套餐名称），而非不可读的 `record_id`。
- **不支持 JOIN**：跨表关联通过代码分步查询实现（先查 A 表再查 B 表），关联字段存储对方表的业务标识符。
- **价格单位为「分」**：所有金额字段以整数分存储（如 398000 = 3980.00 元），避免浮点数精度问题。
- **「包含能力」字段用多行文本**：每行一个能力编号，代码用 `split('\n')` 解析。不要用多选字段。
- **「状态」「角色」用单选**：枚举值固定，单选便于过滤查询。
- **日期字段**：由代码写入毫秒时间戳。

## 与代码的关系

`server/modules/vip/vip.service.ts` 通过 `FeishuBitableService` 操作这 5 张表，主要调用：
- `searchRecords(appToken, tableId, { filter, pageSize })` — 查询
- `batchCreate(appToken, tableId, records)` — 批量创建
- `batchUpdate(appToken, tableId, records)` — 批量更新

## 1. VIP用户表

环境变量：`BITABLE_VIP_USERS_TABLE_ID`

### 字段定义

| 字段名 | 飞书字段类型 | 必填 | 说明 |
|--------|------------|------|------|
| 登录名 | 文本（多行文本） | 是 | 51bxg 登录名，业务唯一标识 |
| 平台 | 单选 | 是 | 固定值 `51bxg` |
| 显示名称 | 文本（多行文本） | 否 | 用户显示名称 |
| 企业名称 | 文本（多行文本） | 否 | 用户所属企业名称（用于曝光特权匹配） |
| 51bxg企业ID | 文本（多行文本） | 否 | 关联 51bxg 企业 ID |
| 手机号 | 文本（多行文本） | 否 | 用户手机号 |
| 邮箱 | 文本（多行文本） | 否 | 用户邮箱地址 |
| 头像 | 文本（多行文本） | 否 | 用户头像 URL |
| 昵称 | 文本（多行文本） | 否 | 用户昵称 |
| 账号状态 | 单选 | 是 | `active`（正常）/ `inactive`（停用）/ `banned`（封禁），默认 `active` |
| 注册来源 | 文本（多行文本） | 否 | 注册来源标识，如 `51bxg` |
| 最后登录时间 | 数字 | 否 | 最近一次登录时间（毫秒时间戳） |
| 备注 | 文本（多行文本） | 否 | 管理员备注 |

**说明**：
- 「登录名」是用户的业务唯一标识，其他表通过「登录名」关联用户，不使用 record_id
- 「企业名称」字段用于曝光特权查询：AI 配单时根据候选商品所属企业名反查特权
- 「账号状态」用于区分正常用户、已停用用户和封禁用户，影响登录和权限判断

## 4. VIP购买记录表

环境变量：`BITABLE_VIP_PURCHASES_TABLE_ID`

> 无种子数据，运行时由后端创建

### 字段定义

| 字段名 | 飞书字段类型 | 必填 | 说明 |
|--------|------------|------|------|
| 订单编号 | 文本（多行文本） | 是 | 业务主键，格式 `VIP + yyyyMMddHHmmss + 3位随机数`，如 `VIP20260726041404348` |
| 登录名 | 文本（多行文本） | 是 | 用户表中的「登录名」（购买者/主账号），与用户表字段名一致 |
| 套餐名称 | 文本（多行文本） | 是 | 套餐表中的「套餐名称」，如「入门版」「专业版」 |
| 购买价格（分） | 数字 | 是 | 购买时的套餐价格，固化历史价格 |
| 购买日期 | 日期 | 否 | 支付成功后自动填充 |
| 到期日期 | 日期 | 否 | 空=永久有效；付费套餐=1 年后 |
| 状态 | 单选 | 是 | pending（待支付）/ active（已生效）/ cancelled（已取消）/ expired（已过期） |
| 支付方式 | 单选 | 否 | alipay / wechat / bank |
| 支付时间 | 日期 | 否 | 完成支付的时间 |
| 支付流水号 | 文本（多行文本） | 否 | 第三方支付平台返回的交易流水号 |
| 创建时间 | 数字 | 否 | 订单创建时间（毫秒时间戳） |
| 过期时间 | 数字 | 否 | 订单支付过期时间（毫秒时间戳，创建后 15 分钟） |
| 备注 | 文本（多行文本） | 否 | 任意备注信息 |

**说明**：
- 「订单编号」是业务主键，由代码生成，格式可读（VIP + 年月日时分秒 + 随机数）
- 「登录名」与用户表字段名一致，直接存储登录名字符串，不存储 record_id
- 「套餐名称」直接存储套餐名称，不存储 record_id，飞书 UI 中可直接辨别套餐
- 「购买价格（分）」必须是数字字段，用于固化购买时的历史价格
- 「购买日期」「到期日期」「支付时间」必须是日期字段
- 「状态」必须是单选字段，预先添加 pending / active / cancelled / expired
- 「支付方式」必须是单选字段，预先添加 alipay / wechat / bank
- 「创建时间」「过期时间」是数字字段（毫秒时间戳），用于订单超时判断

## 5. VIP成员关系表

环境变量：`BITABLE_VIP_MAPPING_TABLE_ID`

> 无种子数据，运行时由后端创建

### 字段定义

| 字段名 | 飞书字段类型 | 必填 | 说明 |
|--------|------------|------|------|
| 登录名 | 文本（多行文本） | 是 | 用户表中的「登录名」，与用户表、购买记录表字段名一致 |
| 主账号登录名 | 文本（多行文本） | 是 | 该套餐主账号（owner）的登录名。owner 填自己的登录名，member 填对应 owner 的登录名 |
| 订单编号 | 文本（多行文本） | 是 | 购买记录表中的「订单编号」，如 `VIP20260726041404348` |
| 角色 | 单选 | 是 | owner / member |
| 状态 | 单选 | 是 | active / inactive |
| 加入日期 | 日期 | 是 | 自动填充 |

**说明**：
- 「登录名」与用户表、购买记录表字段名完全一致，直接存储登录名字符串
- 「主账号登录名」是冗余字段，方便在飞书 UI 中一眼看出 member 属于哪个 owner；owner 记录填自己的登录名，member 记录填对应 owner 的登录名
- 「订单编号」直接存储订单编号，不存储 record_id，飞书 UI 中可直接辨别购买记录
- 「角色」：`owner`（主账号，购买者）/ `member`（子账号，被共享者）
- 「状态」：`active`（正常）/ `inactive`（已停用）
- 飞书多维表格不支持唯一约束，同一「登录名 + 订单编号」组合需在代码中查询去重

### 业务流程

```
主账号 A 购买套餐 → 创建购买记录（订单编号=VIP20260726041404348, 登录名=A, 套餐名称=入门版）
                  → 创建成员关系：登录名=A, 主账号登录名=A, 订单编号=VIP20260726041404348, 角色=owner, 状态=active

主账号 A 添加子账号 B → 创建成员关系：登录名=B, 主账号登录名=A, 订单编号=VIP20260726041404348, 角色=member, 状态=active

子账号 B 登录 → 查询成员关系表（filter: 登录名=B + 状态=active）
            → 找到订单编号 → 查询购买记录 → 查询套餐信息 → 返回对应权限
```
