# 阶段六：AI 配单与问答曝光特权集成方案

> **文档状态**：v2 — 扩展范围，加入 AI 问答曝光权（2026-07-22 修订）
>
> **范围**：
> 1. **AI 配单曝光特权** — 将「AI 配单优质推荐」曝光特权（能力编号 #8，featureKey=`ai_stock_priority_recommend`）集成到 AI 配单的 LLM 排序逻辑中，有特权企业的商品在配单结果中获得排名提升
> 2. **AI 问答曝光权** — 在 AI 问答的 system prompt 中注入特权企业列表，让 LLM 在回答中优先提及有特权企业的产品/品牌信息
>
> **机制说明**：配单曝光特权与问答曝光权是**同一机制**（基于 VIP 套餐的 `priorityRecommend` / `ai_stock_priority_recommend` 特权），分别作用于配单排序和问答回答生成两个场景。配单场景的"竞价排名"即指此曝光特权。
>
> **前置依赖**：阶段二~五已完成（VipService.checkEnterpriseFeature 已实现，5 分钟缓存）

## 一、背景与目标

### 1.1 业务场景

「AI 配单优质推荐」是 VIP 套餐体系中的**业务曝光特权**（exposure_privilege），从专业版（19,800 元/年）开始包含。

与普通功能权限不同，曝光特权的特殊性在于：

```
用户 A（专业版，含 AI 配单优质推荐）录入了商品并上架
  → 用户 B（入门版，不含推荐功能）查询 AI 配单
  → 系统检索商品库
  → 用户 A 的商品在用户 B 的配单结果中优先展示
  → 用户 A 买到的是"自己的商品被别人优先看到"的曝光价值
```

**核心认知**：曝光特权不是当前登录用户的权限判断，而是**商品库中每个商品所属企业的权限判断**。

### 1.2 目标

1. **配单场景**：让拥有 `ai_stock_priority_recommend` 特权的企业，其商品在所有人的 AI 配单结果中获得排名提升
2. **问答场景**：让拥有 `ai_stock_priority_recommend` 特权的企业，在 AI 问答的回答文本中被优先提及（当回答自然涉及该企业的产品/品牌相关内容时）

### 1.3 非目标

- ❌ 不改变配单的候选筛选逻辑（材质/表面/规格等硬门槛不变）
- ❌ 不改变 LLM 打分的四维评分体系（materialMatch / priceAdvantage / locationMatch / stockLevel）
- ❌ 不改变 AI 问答的对话流程和流式响应机制
- ❌ 不在问答中硬塞企业广告（仅在回答自然涉及相关内容时优先提及，保持回答客观性）

## 二、当前状态分析

### 2.1 AI 配单实现现状

经代码探索确认（2026-07-22），AI 配单的排序逻辑分布在 3 个文件中：

| 角色 | 文件路径 | 关键位置 |
|------|---------|---------|
| 后端评分排序 | `server/modules/ai/ai.controller.ts` | `scoreMatches()` 方法，234-301 行 |
| 前端 API 封装 | `client/src/api/ai.ts` | `scoreMatches()` 函数，437-456 行 |
| 前端调用与展示 | `client/src/pages/AiStockPage.vue` | 700-738 行调用 |

### 2.2 排序核心逻辑

**没有独立的规则引擎**。排序由 LLM（qwen-turbo）通过 prompt 完成：

1. 前端构造 `candidates` 数组（从 `RecommendProductItem` 提取字段）
2. 后端 `scoreMatches()` 将 candidates JSON + 用户需求拼成 prompt
3. LLM 返回 `{ ranked: [{ productId, score, reason, dimensions }] }`，已按 score 降序
4. 前端通过 `productId` 反查 `RecommendProductItem` 获取完整商品信息（含企业名）

### 2.3 关键问题：候选商品不包含企业名

经确认，前端传给后端的 `candidates` 数组中**没有 `Supplier`（企业名称）字段**，只包含：

```
productId / material / surface / spec / thick / price / weight / house / factory / city / auctionType
```

LLM 在打分时**不知道商品属于哪个企业**，无法做基于企业特权的加权。

### 2.4 VipService.checkEnterpriseFeature 已就绪

阶段二已实现 `checkEnterpriseFeature(enterpriseName, featureKey)` 方法：
- 输入：企业名称 + 特性标记 Key（如 `ai_stock_priority_recommend`）
- 输出：boolean（该企业是否拥有该特权）
- 缓存：二级 Map（企业 → featureKey → boolean），TTL 5 分钟
- 查询链路：企业名 → 飞书用户表 → 成员关系表 → 购买记录表 → 套餐表 → 功能特性表

### 2.5 AI 问答实现现状

经代码探索确认（2026-07-22），AI 问答的 prompt 构造分布在 `server/modules/ai/bailian.service.ts`：

| 方法 | 行号 | 用途 |
|------|------|------|
| `askFastSync()` | 560-658 | 同步问答（非流式） |
| `askFastStream()` | 724+ | 流式问答（SSE） |

**System Prompt 构造方式**（两个方法一致）：

```typescript
const messages: ChatMessage[] = [
  { role: 'system', content: `${SYSTEM_PROMPT}${priceContext}\n当前时间：${currentTime}。` },
  ...history.slice(-FAST_MAX_HISTORY * 2),

```

- `SYSTEM_PROMPT`：固定常量（`../AI问答系统架构/bailian-app-system-prompt-v11.md` 的内容）
- `priceContext`：每 `INJECT_INTERVAL` 轮注入一次的当日价格数据
- `currentTime`：当前时间

**关键发现**：
1. 问答的 system prompt **没有企业特权相关的注入点**，需要新增
2. 问答的 `askFastStream` / `askFastSync` 当前不接收 userId 参数（不知道当前用户是谁）
3. 要实现问答曝光权，需要在 system prompt 中注入"特权企业列表"

**与配单场景的关键差异**：

| 维度 | 配单场景 | 问答场景 |
|------|---------|---------|
| 已知企业名来源 | candidates 数组中的 `supplier` 字段 | 不知道回答会涉及哪些企业 |
| 特权查询方式 | 逐个查询候选企业的特权状态 | 需预先获取所有有特权的企业列表 |
| 注入位置 | prompt 的 candidates JSON + 评估要点 | system prompt 的企业列表段 |
| LLM 加权方式 | 在 score 上加分 | 在回答文本中优先提及 |
| 触发条件 | 每次配单请求 | 每次问答请求（或按周期注入） |

### 2.6 问答曝光权需要新增的 VipService 方法

当前 `VipService` 只有 `checkEnterpriseFeature(enterpriseName, featureKey)`（查单个企业），问答场景需要新增 `listEnterprisesWithFeature(featureKey)` 方法：

- 输入：featureKey（如 `ai_stock_priority_recommend`）
- 输出：`string[]`（所有拥有该特权的企业名列表）
- 实现：遍历飞书用户表 → 成员关系表 → 购买记录表 → 套餐表 → 功能特性表，返回有该 featureKey 的企业名去重列表
- 缓存：独立缓存（key 为 featureKey），TTL 5 分钟，与 `checkEnterpriseFeature` 的二级缓存分离
- 复用：内部可复用 `checkEnterpriseFeature` 的查询链路，或直接做一次批量查询

## 三、配单场景集成方案（3 个候选）

### 方案 A：Prompt 注入法（推荐）

**思路**：在 LLM 打分前，查询每个候选商品所属企业的特权状态，在 prompt 中标注哪些是"优质推荐"商品，让 LLM 在打分时自然加权。

**改动点**：

1. **前端 `AiStockPage.vue`**：构造 candidates 时补充 `supplier` 字段（从 `RecommendProductItem.Supplier` 取值）

2. **后端 `ai.controller.ts` 的 `scoreMatches()`**：
   - 接收 candidates 后，提取所有不重复的 `supplier` 企业名
   - 并行调用 `vipService.checkEnterpriseFeature(supplier, 'ai_stock_priority_recommend')`
   - 为每个 candidate 标注 `priorityRecommend: boolean` 字段
   - 在 prompt 的"评估要点"中新增一条：
     ```
     - 标记为"优质推荐"的商品（priorityRecommend=true），在综合评分上适当加分（+5~10分），
       并在推荐理由中提及"该供应商为优质推荐商家"
     ```
   - candidates JSON 中包含 `priorityRecommend` 字段，让 LLM 可见

**优点**：
- LLM 能在推荐理由中自然提及"优质推荐商家"，用户体验好
- 加权幅度由 LLM 智能判断（价格差异大时少加，价格相近时多加）
- 改动集中在 scoreMatches 方法内，不影响其他流程

**缺点**：
- 依赖 LLM 遵守 prompt 指令（可能加权不稳定）
- 增加了 prompt 长度（每个 candidate 多一个字段）

### 方案 B：后处理排名提升法

**思路**：LLM 打分排序后，在返回结果中做后处理，把有特权企业的商品排名提升。

**改动点**：

1. 前端补充 `supplier` 字段（同方案 A）
2. 后端 `scoreMatches()` 在 LLM 返回 `ranked` 数组后：
   - 查询每个 ranked 商品所属企业的特权状态
   - 对有特权的商品 `score += 10`（固定加分）
   - 重新按 score 降序排列
   - 在 `reason` 前追加"[优质推荐] "标记

**优点**：
- 加权效果确定（不依赖 LLM 遵守指令）
- 实现简单（纯后端逻辑）

**缺点**：
- 加权幅度固定，不够智能
- "优质推荐"标记是硬追加的，与 LLM 生成的推荐理由不自然融合

### 方案 C：混合法（A+B）

**思路**：prompt 注入 + 后处理双重保障。

**优点**：效果最好
**缺点**：改动最大，可能过度工程化

### 推荐：方案 A

**理由**：
- LLM 已经在做智能打分，让它感知"优质推荐"标记是最自然的方式
- 推荐理由中能自然提及"优质推荐商家"，比硬追加标记体验好
- 改动集中，风险可控
- 如果 LLM 加权效果不稳定，后续可叠加方案 B 的后处理作为保障

## 四、问答场景集成方案

### 方案：System Prompt 注入特权企业列表（推荐）

**思路**：在 AI 问答的 system prompt 中注入"当前平台优质推荐企业列表"，让 LLM 在回答涉及相关产品/品牌时，自然优先提及这些企业。

**改动点**：

1. **VipService 新增 `listEnterprisesWithFeature(featureKey)` 方法**（见 2.6 节）
   - 返回所有拥有 `ai_stock_priority_recommend` 特权的企业名列表
   - 独立缓存，TTL 5 分钟

2. **BailianService 的 `askFastStream` / `askFastSync` 注入企业列表**：

   在构造 system prompt 时，调用 `vipService.listEnterprisesWithFeature('ai_stock_priority_recommend')`，将企业列表拼接到 system prompt 末尾：

   ```
   \n\n【平台优质推荐企业列表】
   以下企业为平台优质推荐商家，在回答涉及相关产品/品牌时，请优先提及：
   - 企业A
   - 企业B
   - 企业C

   注意：仅在回答自然涉及相关内容时提及，不要生硬插入广告。
   ```

   **注入频率**：与 `priceContext` 类似，每 `INJECT_INTERVAL` 轮注入一次（避免每轮都查飞书），或首次问答时注入并缓存

3. **BailianService 注入 VipService**：
   - 构造函数注入 `VipService`
   - `AiModule` 的 imports 中添加 `VipModule`（与配单场景共用）

**优点**：
- 改动集中，仅在 system prompt 拼接处新增一段
- LLM 能在回答中自然提及特权企业（如"山西太钢、宝钢等优质推荐商家..."）
- 与价格数据注入机制一致，复用已有的周期注入逻辑

**缺点**：
- 特权企业列表可能较长（几十个企业名），增加 token 消耗（约 200-500 tokens）
- LLM 不一定在每次回答中都提及（取决于问题是否相关）—— 这也是期望行为（避免硬塞广告）

**降级策略**：
- 如果特权企业列表查询失败（飞书 API 不可用），catch 异常，不注入企业列表，问答正常进行
- 不让特权查询失败影响核心问答功能

### 问答曝光权的边界约束

为避免问答被滥用为广告渠道，明确以下约束：

| 约束 | 说明 |
|------|------|
| 仅在相关时提及 | LLM 判断问题与特权企业相关时才提及，不相关时不提及 |
| 不改变回答客观性 | 优先提及不等于唯一提及，仍可提及非特权企业 |
| 不标注"推荐"字样 | 回答中不出现"以下为推荐商家"等元描述，保持自然 |
| 列表不暴露给用户 | 特权企业列表只在 system prompt 中，不在前端展示 |

### 步骤 4：VipService 新增 listEnterprisesWithFeature 方法（问答场景）

**文件**：`server/modules/vip/vip.service.ts`

**改动**：新增方法，返回所有拥有指定 featureKey 特权的企业名列表

```typescript
/**
 * 获取所有拥有指定特性特权的企业名列表（用于 AI 问答曝光权）
 * 独立缓存，TTL 5 分钟
 */
async listEnterprisesWithFeature(featureKey: string): Promise<string[]> {
  // 1. 检查缓存（key 为 featureKey，与 checkEnterpriseFeature 的二级缓存分离）
  const cacheKey = `list:${featureKey}`
  const cached = this.listCache.get(cacheKey)
  if (cached && Date.now() - cached.ts < 5 * 60 * 1000) {
    return cached.value
  }

  // 2. 查询飞书用户表，获取所有企业名（去重）
  const allEnterprises = await this.fetchAllEnterpriseNames()

  // 3. 并行查询每个企业的特权状态
  const results = await Promise.all(
    allEnterprises.map(async (name) => ({
      name,
      has: await this.checkEnterpriseFeature(name, featureKey),
    })),
  )

  // 4. 过滤出有特权的企业名
  const privileged = results.filter(r => r.has).map(r => r.name)

  // 5. 写入缓存
  this.listCache.set(cacheKey, { value: privileged, ts: Date.now() })
  return privileged
}
```

**验证**：
- 调用 `listEnterprisesWithFeature('ai_stock_priority_recommend')` 返回有该特权的企业名数组
- 第二次调用命中缓存（日志无飞书查询记录）

```typescript
private buildEnterpriseContext(enterprises: string[]): string {
  const list = enterprises.map(e => `- ${e}`).join('\n')
  return `\n\n【平台优质推荐企业列表】\n以下企业为平台优质推荐商家，在回答涉及相关产品/品牌时，请优先提及：\n${list}\n\n注意：仅在回答自然涉及相关内容时提及，不要生硬插入广告。\n`
}
```

**验证**：
- 发起 AI 问答，后端日志出现"获取特权企业列表"记录
- system prompt 中包含企业列表段（可通过日志或临时打印验证）
- LLM 回答中在相关问题时提及特权企业名

## 六、性能与缓存策略

### 6.1 配单场景特权查询性能

- 每次配单请求的候选商品通常 5-20 个，不重复企业名 3-10 个
- `checkEnterpriseFeature` 有 5 分钟缓存，首次查询走飞书 API（~500ms/企业），后续命中缓存
- 并行查询 10 个企业，最坏情况 ~500ms 额外延迟（首次），缓存命中后 ~10ms

### 6.2 问答场景特权查询性能

- `listEnterprisesWithFeature` 首次查询需遍历所有企业（可能几十到几百个），每个企业走 `checkEnterpriseFeature`
- 首次查询可能较慢（几十个企业 × 500ms = 数秒），但并行查询可压缩到 ~1-2s
- 后续命中 `listCache` 缓存（TTL 5 分钟），~10ms
- 注入频率与 `priceContext` 同周期（`INJECT_INTERVAL` 轮一次），不是每轮问答都查
- **优化建议**：如果企业数量超过 100，可考虑直接查飞书套餐表 + 成员关系表做批量反查，避免逐个 `checkEnterpriseFeature`

### 6.3 缓存失效场景

- 企业购买/取消套餐时，`VipService.clearEnterpriseFeatureCache(enterpriseName)` 已实现
- 套餐变更影响该企业所有用户时需手动调用清除（当前未实现自动清除，阶段六不处理）
- `listEnterprisesWithFeature` 的缓存需在企业套餐变更时一并清除（新增 `clearListCache(featureKey)` 方法）

### 6.4 降级策略

- **配单场景**：如果特权查询整体失败（飞书 API 不可用），catch 异常，所有 candidate 的 `priorityRecommend` 设为 false，配单正常进行
- **问答场景**：如果 `listEnterprisesWithFeature` 失败，`enterpriseContext` 为空字符串，system prompt 不含企业列表，问答正常进行
- 两个场景都不让特权查询失败影响核心功能

## 九、风险与注意事项

### 9.1 配单：LLM 加权稳定性

**风险**：LLM 对"优质推荐"标记的加权幅度可能不稳定（有时 +5 分，有时 +15 分）。

**缓解**：
- 在 prompt 中明确"+5~10 分"的范围
- 上线后监控有特权企业的商品排名变化，如果效果不稳定，叠加方案 B 后处理

### 9.2 企业名匹配准确性

**风险**：配单结果中的 `Supplier` 字段（企业名）与飞书用户表中的"企业名称"字段可能不一致（如"太钢"vs"山西太钢不锈钢股份有限公司"）。

**缓解**：
- 初期依赖字符串完全匹配
- 如匹配率低，后期在飞书用户表中增加"企业别名"字段或做模糊匹配

### 9.3 配单：候选商品数量少时的影响

**风险**：如果某次配单只有 2-3 个候选商品，且都有特权，加权无意义。

**缓解**：可接受。加权在候选充足时才有区分度，候选少时影响不大。

### 9.4 问答：LLM 提及频率不可控

**风险**：LLM 可能在无关问题中也提及特权企业（过度曝光），或在相关问题中不提及（曝光不足）。

**缓解**：
- 在 system prompt 中明确"仅在回答自然涉及相关内容时提及，不要生硬插入广告"
- 上线后抽样检查问答日志，评估提及频率是否合理
- 如过度曝光，收紧 prompt 指令；如曝光不足，调整措辞增强引导

### 9.5 问答：企业列表过长导致 token 消耗

**风险**：特权企业列表可能有几十到上百家，每条注入消耗 200-500 tokens，长期累积增加 API 成本。

**缓解**：
- 监控 token 消耗，如超出预算可考虑只注入 Top N 家（按套餐等级排序）
- 或改为按问题关键词动态筛选相关企业注入（需要额外的匹配逻辑，留待后续优化）

### 9.6 与旧 VIP 逻辑（IsVIP）的关系

阶段六只使用基于飞书多维表格的 `checkEnterpriseFeature` / `listEnterprisesWithFeature`。旧版 51bxg 原生 `IsVIP` 字段在配单 prompt 中已被移除（原"会员等级加成 0-10 分"已不适用于 LLM 打分模式）。
