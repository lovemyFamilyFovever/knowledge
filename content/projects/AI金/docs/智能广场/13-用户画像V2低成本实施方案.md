# 用户画像 V2 低成本实施方案

> 文档日期：2026-08-31  
> 文档性质：可直接交给 Codex 执行的实施规格  
> 实施原则：低成本、规则可解释、兼容现有数据、先影子计算后接入  
> 本文只定义方案；实际实施时必须遵守本文的数据库留痕要求。

## 一、目标

将当前以“行为次数/是否使用过”为主的简单画像，升级为以下可解释规则：

```text
画像得分 = 行为价值 × 时间衰减 × 重复抑制
画像是否可用 = 得分 + 置信度共同判断
```

V2 需要解决：

1. 页面浏览、点赞、收藏、配单等行为价值没有明显区分。
2. 普通点击数量过大，容易淹没配单、测价等高意图行为。
3. 旧兴趣不会随时间自然减弱。
4. 重复刷新或重复打开容易虚增权重。
5. 钢种只从测价记录提取，遗漏问答、配单和广场正文中的有效信息。
6. AI 画像读取的部分广场行为只有目标 ID，缺少实际主题语义。
7. 画像只有标签，没有分数、置信度和最后证据时间，难以解释和调参。

本期不引入机器学习、向量库、协同过滤或新的大模型调用。大模型不参与权重计算，只允许根据已经计算好的结构化画像生成自然语言摘要。

## 三、强制实施约束

### 3.1 数据库变更必须有 SQL 文件留痕

任何数据库结构或数据变更都禁止只通过 HeidiSQL、Navicat、数据库控制台或临时命令直接修改。

本方案实施时必须新增：

```text
server/database/sql/071-add-user-profile-v2-fields.sql
```

当前 SQL 文件最大编号为 `070`，因此本任务使用 `071`。如果实际实施前仓库已经出现新的 `071`，Codex 必须重新检查目录并使用当时的下一个连续编号，禁止重号。

SQL 文件必须：

- 使用 PostgreSQL 语法。
- 使用 `ADD COLUMN IF NOT EXISTS`，保证幂等。
- 包含每个新增字段的 `COMMENT ON COLUMN`。
- 说明变更背景、执行范围、幂等性和线上执行限制。
- 不删除旧字段，不清空旧画像，不执行不可逆数据迁移。
- 与 `server/database/schema.ts` 同步修改，SQL 和 Drizzle Schema 必须一致。
- 本地数据库可以按项目规范执行该 SQL；飞书 online 禁止通过 `miaoda db sql --env online` 直接执行 DDL，必须走项目规定的发布/数据库更新流程。

建议迁移内容如下，实施时以实际下一个 SQL 编号为准：

```sql
-- ============================================================================
-- 071: user_profiles 增加用户画像 V2 结构化特征字段
-- 背景：保存可解释的分维度得分、置信度和最后证据时间；旧画像字段继续兼容。
-- 幂等：ADD COLUMN IF NOT EXISTS，可重复执行。
-- 注意：online DDL 走妙搭发布/数据库更新流程，禁止 db sql --env online 直接执行。
-- ============================================================================

ALTER TABLE user_profiles
  ADD COLUMN IF NOT EXISTS profile_features JSONB NOT NULL DEFAULT '{}'::jsonb,
  ADD COLUMN IF NOT EXISTS profile_version SMALLINT NOT NULL DEFAULT 1;

COMMENT ON COLUMN user_profiles.profile_features IS
  '用户画像V2结构化特征：按模块、钢种、市场、主题和业务意图保存得分、置信度、证据数及最后证据时间；不得保存行为原文或个人敏感信息';

COMMENT ON COLUMN user_profiles.profile_version IS
  '画像算法版本：1=旧版标签画像 / 2=规则型画像V2';

COMMENT ON COLUMN user_profiles.behavior_count IS
  '近30天纳入画像计算的有效行为数，不是历史累计总数';
```

本期不为 `profile_features` 创建 GIN 索引。线上读取始终先按 `member_code` 唯一键定位单个用户，再读取完整 JSON；GIN 索引只会增加存储和写入成本。

### 3.2 业务边界

- 不修改 51bxg 或秀吗源码、生产库和外部接口。
- 不修改结算模块。
- 本期不接入“查看联系方式=成交”作为画像信号，避免扩大交易链路改动范围；可作为后续增强。
- 不新增前端页面埋点。本期优先复用已有后端事实表。
- 社交行为不得同时从行为明细表和社交事实表重复计分。

## 四、画像结构

画像拆为五个维度：

| 维度 | 示例 | 主要用途 |
|---|---|---|
| `modules` | `qa`、`matching`、`forecast`、`plaza` | 功能入口排序、运营分析 |
| `steels` | `304`、`316L`、`430` | 问答、配单、内容推荐 |
| `markets` | `无锡`、`佛山`、`上海` | 本地行情和货源推荐 |
| `topics` | `价格`、`库存`、`成本`、`镍价`、`冷轧` | 问答和广场推荐 |
| `businessIntents` | `purchase`、`sales` | 提问、配单和内容表达方向 |

`profile_features` 推荐格式：

```json
{
  "algorithmVersion": 2,
  "generatedAt": "2026-08-31T08:00:00.000Z",
  "windowDays": 30,
  "dimensions": {
    "modules": [
      {
        "key": "qa",
        "score": 72,
        "confidence": 0.8,
        "eventCount": 12,
        "activeDays": 4,
        "lastAt": "2026-08-31T06:00:00.000Z"
      }
    ],
    "steels": [
      {
        "key": "304",
        "score": 86,
        "confidence": 1,
        "eventCount": 16,
        "activeDays": 5,
        "lastAt": "2026-08-31T06:00:00.000Z"
      }
    ],
    "markets": [],
    "topics": [],
    "businessIntents": []
  },
  "sourceSummary": {
    "effectiveEventCount": 35,
    "activeDays": 6,
    "latestBehaviorAt": "2026-08-31T06:00:00.000Z"
  }
}
```

约束：

- JSON 中只存聚合结果，不保存问题原文、评论原文、手机号、姓名、企业名称等信息。
- `score` 为 `0~100` 整数。
- `confidence` 为 `0~1`，最多保留 4 位小数。
- 每个维度按 `score` 降序。
- `steels` 最多 5 项、`markets` 最多 3 项、`topics` 最多 8 项、`businessIntents` 最多 2 项。
- `modules` 固定最多 4 项。
- 没有证据的维度保存空数组，不保存 `null`。

## 五、数据源和去重规则

### 5.1 每类事实只使用一个权威来源

| 信号 | 权威来源 | 不再重复使用的来源 |
|---|---|---|
| AI 问答 | `user_behavior_records` 的 `qa` | 无 |
| AI 配单 | `user_behavior_records` 的 `matching` | 无 |
| AI 测价 | `user_behavior_records` 的 `forecast` | 无 |
| 广场浏览 | `user_recent_views` | `user_behavior_records.plaza_click` 不再参与 V2 计分 |
| 点赞 | `plaza_likes` | `user_behavior_records.plaza_like` 不再参与 V2 计分 |
| 收藏 | `plaza_favorites` | 无 |
| 评论 | `plaza_comments` | `user_behavior_records.plaza_comment` 不再参与 V2 计分 |
| 关注 | `plaza_follows` | `user_behavior_records.plaza_follow` 不再参与 V2 计分 |
| 主动填写资料 | `users` | 无 |

旧的社交行为明细继续保留，不能删除；只是 V2 聚合时不重复计分。

### 5.2 内容关联

广场浏览、点赞、收藏和评论通过 `news_id/article_id/target_id` 关联 `plaza_posts`，从以下字段提取钢种、市场和主题：

```text
plaza_posts.title
plaza_posts.content
plaza_posts.tags
plaza_posts.categories
```

当前大量历史帖子没有标题、标签和分类，因此正文 `content` 必须参与提取，不能只依赖 `tags/categories`。

关注行为只影响广场现有的作者偏好，不用于推断钢种或业务主题；本期不把作者列表写入统一画像 JSON。

### 5.3 重试去重

对于 `qa/matching/forecast`：同一用户、同一行为类型、规范化后相同内容，在同一分钟内只计一次。数据库原始记录不删除，只在聚合时去重。

内容规范化只用于内存或 SQL 聚合：去首尾空白、合并连续空白、统一英文字母大小写。不得把规范化后的原始内容写入 `profile_features`。

同一段内容中重复出现同一钢种或主题，只给该特征记一次证据。

## 六、首版权重

| 行为 | 基础分 | 类型 | 半衰期 |
|---|---:|---|---:|
| 用户主动填写钢种/市场/业务方向 | 8 | 稳定信号 | 不衰减 |
| 广场有效浏览 | 1 | 弱信号 | 7 天 |
| AI 问答 | 2 | 中信号 | 30 天 |
| 点赞 | 3 | 中信号 | 30 天 |
| AI 测价 | 4 | 高意图 | 30 天 |
| 评论 | 4 | 高意图 | 30 天 |
| 关注 | 4 | 作者偏好 | 30 天 |
| AI 配单 | 5 | 高意图 | 30 天 |
| 收藏 | 5 | 高意图 | 30 天 |

同一事件可同时贡献不同维度。例如“无锡304冷轧现货配单”可以同时贡献：

- `modules.matching`
- `steels.304`
- `markets.无锡`
- `topics.冷轧`
- `topics.现货`
- `businessIntents.purchase`

但同一维度内的同一特征只贡献一次。

## 七、计算公式

### 7.1 时间衰减

```text
decay = 0.5 ^ (ageDays / halfLifeDays)
eventContribution = baseWeight × decay
```

主动填写信号不衰减，直接贡献 8 分。

### 7.2 重复浏览抑制

`user_recent_views` 已按“用户+帖子”聚合 `view_count`。同一帖子的浏览贡献使用：

```text
viewContribution = 1 × (1 + ln(viewCount)) × timeDecay
```

计算时 `viewCount` 最低按 1、最高按 50 处理，防止异常数据无限放大。

### 7.3 特征原始分和展示分

```text
rawScore = onboardingContribution + Σ eventContribution
score = round(100 × (1 - exp(-rawScore / 12)))
```

最终 `score` 限制在 `0~100`。

### 7.4 置信度

定义高意图行为：`matching`、`forecast`、`favorite`、`comment`。

```text
confidence = min(1, (activeDays + 2 × highIntentActiveDays) / 5)
```

其中：

- `activeDays`：该特征在近 30 天出现的不同日期数。
- `highIntentActiveDays`：该特征通过高意图行为出现的不同日期数。
- 用户主动填写的特征直接设置 `confidence = 1`。
- 行为与主动填写同时命中时，置信度仍封顶 1。

消费者默认只使用 `confidence >= 0.4` 且 `score >= 20` 的行为特征。主动填写特征不受该阈值限制。

### 9.2 建议修改

| 文件 | 改动 |
|---|---|
| `server/modules/plaza/plaza-recommendation.service.ts` | 优先读取 V2 高置信度钢种/市场/主题；无 V2 时保持旧逻辑 |

### 9.3 行为写入修正

当前广场评论调用传入的是 `content`，而 `BehaviorService.recordBehavior()` 读取的是 `comment`。实施时必须兼容：

```text
comment = data.comment ?? data.content
```

不能修改或删除历史行为记录。

当前 `upsertBehaviorTagAsync()` 会在每次行为后用“旧值+1”更新画像，而定时聚合又会把 `behavior_count` 覆盖为近30天计数，语义不一致且并发时可能丢增量。

V2 推荐处理：

- `recordBehavior()` 只负责可靠插入行为明细。
- 画像、`behavior_count`、`profile_tags`、`frequent_steels` 统一由每6小时聚合任务计算。
- 若必须保留即时 `last_active_at`，只能做原子数据库更新，不能继续采用“先读旧值再+1”的方式。

## 十、兼容策略

V2 上线时不得一次性移除以下旧字段：

```text
profile_tags
frequent_steels
behavior_count
ai_profile_tags
ai_profile_summary
```

聚合任务需要同时写：

- `profile_features`：V2 完整结构。
- `profile_version=2`。
- `profile_tags`：继续生成旧消费者可读的简要标签。
- `frequent_steels`：取 V2 `steels` 中达到阈值的前5项。
- `behavior_count`：近30天去重后的有效行为数。
- `last_active_at`、`behavior_updated_at`：按本次聚合结果更新。

消费者读取顺序：

1. `profile_version >= 2` 且 `profile_features` 结构合法时读取 V2。
2. V2 缺少某个维度时，用 `frequent_steels/profile_tags/ai_profile_tags` 补充。
3. 没有画像时使用用户主动填写资料。
4. 仍无信息时使用热门+时效的匿名回退，不得报错。

## 十一、执行顺序

### 阶段 A：数据库和影子计算

1. 检查 `server/database/sql/` 的当前最大编号。
2. 新增下一个编号的幂等 SQL 文件。
3. 同步更新 `schema.ts`。
4. 实现 V2 聚合和单元测试。
5. 聚合任务写入 V2，但消费者暂时继续使用旧字段。
6. 检查生成结果，不改推荐排序。

### 阶段 B：消费者接入

1. 广场推荐优先使用 V2 高置信度特征。
2. 问答推荐优先使用 V2 钢种和业务意图。
3. AI 摘要读取结构化画像。
4. 所有消费者必须保留旧画像回退。

### 阶段 C：观察和调参

1. 观察至少一周的画像覆盖率、分数分布和稳定性。
2. 只调整权重常量，不修改历史事实数据。
3. 权重调整必须更新本文或新增版本说明，`algorithmVersion` 同步递增。

## 十二、测试要求

### 12.1 纯函数单元测试

至少覆盖：

1. 同一行为今天的贡献大于7天前和30天前。
2. 配单一次的基础贡献大于普通浏览一次。
3. 浏览10次的贡献明显小于浏览1次的10倍。
4. 同一文本中重复出现 `304` 只记一次特征证据。
5. `316` 与 `316L` 不混淆。
6. 主动填写的钢种不衰减且置信度为1。
7. 低置信度偶发兴趣不进入消费者结果。
8. 得分永远位于0~100，置信度永远位于0~1。
9. 生成的 JSON 不包含行为原文、姓名、企业名称或手机号。
10. 空画像能够生成合法空结构，不抛异常。

### 12.2 数据查询测试

至少验证：

1. 社交行为没有同时从两套表重复计数。
2. 广场帖子关联失败时跳过语义提取，但模块活跃统计仍可继续。
3. 同一分钟相同问答/配单/测价只计一次。
4. 只读取近30天行为，主动填写信息除外。
5. 单个用户异常数据不会阻止其他用户画像生成。

### 12.3 项目验证

实施完成后至少运行：

```text
npm run type:check:server
```

如仓库存在相关测试命令，同时运行行为画像、广场推荐和问答推荐测试。不得因为与本任务无关的旧失败去修改无关模块。

## 十三、验收 SQL

以下 SQL 仅用于验收查询，仍建议由 Codex 整理到实施记录中；不得通过查询结果输出用户原文或 MEMBER_CODE 明细。

```sql
-- 1. 字段是否存在
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'user_profiles'
  AND column_name IN ('profile_features', 'profile_version')
ORDER BY column_name;
```

```sql
-- 2. V2 画像覆盖率
SELECT
  COUNT(*) AS profile_count,
  COUNT(*) FILTER (WHERE profile_version >= 2) AS v2_count,
  COUNT(*) FILTER (
    WHERE profile_version >= 2
      AND jsonb_typeof(profile_features) = 'object'
  ) AS valid_v2_count
FROM user_profiles;
```

```sql
-- 3. 维度覆盖率，不输出用户身份
SELECT
  COUNT(*) FILTER (
    WHERE jsonb_array_length(COALESCE(profile_features #> '{dimensions,steels}', '[]'::jsonb)) > 0
  ) AS with_steels,
  COUNT(*) FILTER (
    WHERE jsonb_array_length(COALESCE(profile_features #> '{dimensions,topics}', '[]'::jsonb)) > 0
  ) AS with_topics,
  COUNT(*) FILTER (
    WHERE jsonb_array_length(COALESCE(profile_features #> '{dimensions,markets}', '[]'::jsonb)) > 0
  ) AS with_markets
FROM user_profiles
WHERE profile_version >= 2;
```

```sql
-- 4. 分数和置信度越界检查
WITH features AS (
  SELECT jsonb_array_elements(dimension_value) AS feature
  FROM user_profiles,
       LATERAL jsonb_each(COALESCE(profile_features -> 'dimensions', '{}'::jsonb)) AS d(dimension_name, dimension_value)
  WHERE profile_version >= 2
    AND jsonb_typeof(dimension_value) = 'array'
)
SELECT COUNT(*) AS invalid_feature_count
FROM features
WHERE (feature ->> 'score')::numeric NOT BETWEEN 0 AND 100
   OR (feature ->> 'confidence')::numeric NOT BETWEEN 0 AND 1;
```

## 十四、验收标准

全部满足才算完成：

- 数据库变更已通过新编号 SQL 文件留痕，且与 `schema.ts` 一致。
- SQL 幂等执行两次不报错、不重复创建对象。
- 未手工删除或覆盖旧画像数据。
- `profile_features` 不保存行为原文和个人敏感信息。
- 问答和配单中的钢种能够进入 `frequent_steels`/V2 `steels`。
- 普通点击不会因为数量大而压过配单、测价、收藏等高意图信号。
- 旧兴趣随时间衰减，主动填写信息保持稳定。
- 重复浏览采用对数抑制。
- 消费者在 V2 缺失或解析失败时能够回退到旧画像或匿名推荐。
- `npm run type:check:server` 通过。
- 相关单元测试通过。

## 十五、回滚策略

本次数据库迁移只新增字段，不删除旧字段，因此回滚时：

1. 将消费者切回旧字段读取逻辑。
2. 停止 V2 聚合写入，恢复旧聚合逻辑。
3. 保留 `profile_features/profile_version` 字段和已有数据，不执行 `DROP COLUMN`。
4. 需要重新上线时可以继续复用已有 V2 数据，或由聚合任务覆盖重算。

禁止为了回滚而直接手工删除数据库字段。若未来确需删除，必须另建新的、独立编号 SQL 迁移文件并经人工确认。
