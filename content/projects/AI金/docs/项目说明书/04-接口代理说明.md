## 一、架构概述

前端通过统一的 API 封装调用后端，后端负责转发到外部数据源（51bxg / xiuma / 阿里云百炼）或直接读写飞书多维表格：

```
前端 api/*.ts ──→ NestJS Controller（/api/*）──→ 外部数据源 / 飞书多维表格
```

**通用代理**（51bxg/xiuma 转发）：

```
前端 fetchProxyApi() ──→ /api/proxy/:source/:controller/:method（或 /:source/:method）──→ ProxyService.forward() ──→ 目标 API
```

- `source`：`51bxg` 或 `xiuma`
- `controller`：仅 51bxg 需要（如 `General`、`Forecast`）
- `method`：方法名
- 透传 `x-login-name` header → ProxyService 按用户携带登录会话 Cookie

**本地业务接口**（VIP / 广场 / 聊天 / 统计等）由各模块直接对接飞书多维表格，不走通用代理。

## 二、51bxg 接口（REST API）

### 调用方式

```typescript
import { fetchProxyApi } from '@/api/proxy'

const result = await fetchProxyApi({
  source: '51bxg',
  controller: 'Forecast',       // Controller 名
  method: 'QueryCoilPriceIndex', // 方法名
  body: { /* 参数 */ },
})
```

### 协议说明

| 维度 | 说明 |
|------|------|
| 协议 | REST API（HTTP POST） |
| Content-Type | `application/x-www-form-urlencoded` |
| Body 格式 | `z_data=JSON.stringify(params)` |
| 路径前缀 | `pathPrefix`，默认 `api_web`（`z_data` 中自动带 `pathPrefix` 字段） |
| 代理路径 | `/api/proxy/51bxg/{controller}/{method}` |
| 会话 | 登录时保存 51bxg `Set-Cookie`（TTL 2 小时），后续按 `loginName` 携带 |

### 返回格式

```json
{ "code": 0, "msg": "success", "data": { ... } }
```

> 后端已将 51bxg 的 `WS_RET_CODE` → `code`、`WS_RET_MSG` → `msg`、`WS_RET_DATA` → `data`。

| Method | 路径 | 协议 | 前端函数 | 用途 |
|--------|------|------|---------|------|

## 四、文件上传与图片代理

### 上传（/api/proxy/51bxg/upload-file）

前端用 `multipart/form-data` 直传原始文件流（field = `file`，≤20MB），后端 `FileInterceptor` 接收后构造 multipart 转发到 51 号：

1. `/web/upload_file.aspx` 获取 `file_list_id`
2. `/api_public/WebCommon/PostUploadImage`（`z_data` 带 `file_list_id`）返回图片正式路径

前端封装：`upload51bxgImage`、`create51bxgVideo` → `refresh51bxgVideo`（轮询）→ `upload51bxgVideo` 三步视频上传。

### 图片代理（GET /api/proxy/image?url=...）

接口保留用于非静态资源和兼容场景：仅允许 `51bxg.com` / `xiuma.com` 域名，带对应 Referer 抓取并缓存（`Cache-Control: max-age=86400`），跟随重定向。

广场中的 51bxg 静态图片不再把 `/api/proxy/image` 直接赋给原生 `<img>`。妙搭生产环境会对该 `/api` GET 请求执行双提交 CSRF 校验，而原生 `<img>` 无法设置 `x-suda-csrf-token`，会返回 403。前端改为对明确白名单中的静态图片使用 HTTPS 直连：

- Host 白名单：`51bxg.com`、`www.51bxg.com`、`img.51bxg.com`
- 扩展名白名单：`.jpg`、`.jpeg`、`.png`、`.webp`、`.gif`
- 不限制目录，以兼容历史 `51bxg/`、现有 `/img/` 和上传返回的 `/upload/img/`
- 外部图片标签使用 `referrerpolicy="no-referrer"`，不采用影响全局资源的 Referrer Meta

典型转换：

- `51bxg/2026/...` → `https://img.51bxg.com/51bxg/2026/...`
- `/img/2026/...` → `https://www.51bxg.com/img/2026/...`
- `/upload/img/2026/...` → `https://www.51bxg.com/upload/img/2026/...`

VIP 本地头像 `/api/vip/avatar/:memberCode` 仍是独立的妙搭 CSRF 兼容问题；当前保留姓名首字回退，不与广场静态图片修复混合。

## 六、Auth 接口（/api/auth/*）

独立认证路由，密码、验证码和会话全部由 AI金本地服务处理。

| 方法 | 路径 | 用途 | 数据源 |
|------|------|------|--------|
| POST | `/api/auth/login` | 密码登录 / 旧密码首登升级 | AI金 PostgreSQL |
| POST | `/api/auth/register` | 注册 | AI金 PostgreSQL |
| POST | `/api/auth/sms-code` | 注册验证码 | AI金本地验证码 |
| POST | `/api/auth/sms-login-code` | 登录验证码 | AI金本地验证码 |
| POST | `/api/auth/login/sms` | 验证码登录 | AI金 PostgreSQL |
| POST | `/api/auth/forget-sms-code` | 忘记密码验证码 | AI金本地验证码 |
| POST | `/api/auth/edit-password` | 修改 AI金密码 | AI金 PostgreSQL |

**登录特殊逻辑**（AuthService.login）：
1. 先校验 AI金 `scrypt` 哈希；未迁移用户仅校验本地 `legacy_password_hash`
2. 旧哈希成功后立即升级，失败不使用 51bxg 兜底
3. `LocalSessionService.sign(memberCode, loginName)` 签发 HMAC 会话 token → `data.sessionToken`
4. `getUserPermission(memberCode)` 查询权限 → 合并到 `data.permission`
5. VipService 失败不阻塞登录（try-catch + warning，前端按免费用户处理）

详见 `08-登录认证说明.md`。

## 十一、新增接口指南

### 51bxg / xiuma 新增接口

1. xiuma 方法：在 `server/modules/proxy/proxy.service.ts` 的 `getXiumaPath()` 添加路径映射
2. 在 `client/src/api/proxy.types.ts` 定义参数/返回类型
3. 在 `client/src/api/proxy.ts` 添加 `fetchProxyApi` 调用函数（`source`/`controller`/`method`）

```typescript
export async function queryNewMethod(params: NewMethodParams): Promise<ApiResponse<NewMethodData>> {
  return fetchProxyApi<NewMethodData>({
    source: '51bxg',
    controller: 'ControllerName',
    method: 'MethodName',
    body: params as unknown as Record<string, unknown>,
  })
}
```

### 新增本地业务接口

1. 新建/扩展 `server/modules/*` 下的 controller + service
2. 在 `server/modules/ai/ai.module.ts` 或对应模块注册
3. 前端在 `client/src/api/*.ts` 封装 `fetch` 调用（参考 `vip.ts` 的 `fetchVipApi` 模式：自动带 CSRF token + 用户 header）
4. 涉及飞书多维表格的用 `FeishuBitableService`（searchRecords/batchCreate/batchUpdate/batchDelete/uploadMedia/downloadMedia）

### 通用约定

- 返回格式统一 `{ success, code, message, data }`（`fetchAuthApi`/`fetchVipApi` 已封装）
- 前端自动携带 `x-suda-csrf-token`（从 cookie `suda-csrf-token` 读取）
- 飞书 SUDA 平台路径前缀 `/app/app_xxx` 由 `getApiBase()` 自动兼容
