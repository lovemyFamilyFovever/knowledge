# 08-登录认证说明

> 最后更新：2026-08-17
>
> 当前认证架构以 AI金本地 PostgreSQL 为唯一账号数据源。认证链路已停止调用 51bxg 的登录、注册、验证码和改密接口。

---

## 一、总体设计

| 维度 | 说明 |
|------|------|
| 用户主表 | `users`，继续使用 `MEMBER_CODE` 作为全平台用户标识 |
| 认证凭据 | `ai_jin_auth_credentials`，与 `users.member_code` 1:1 关联 |
| 存量密码 | 老 `Pwd` 原样导入 `legacy_password_hash`，仅按 MD5 + UTF-8 + Base64 校验一次 |
| 新密码 | Node.js 内置 `scrypt`，16 字节随机盐，64 字节派生密钥 |
| 验证码 | `ai_jin_verification_codes`，只保存 HMAC-SHA256 哈希，5 分钟有效 |
| 会话 | `LocalSessionService` 签发 HMAC-SHA256 `sessionToken`，默认 30 天 |
| 权限 | 登录成功后调用 `VipService.getUserPermission` |
| 老平台兜底 | 禁止。本地校验失败直接返回账号或密码错误 |

```text
前端 /api/auth/*
  ↓
AuthController
  ↓
AuthService
  ├─ AuthRepository → users + ai_jin_auth_credentials
  ├─ PasswordHashService → legacy MD5 / scrypt
  ├─ VerificationCodeService → ai_jin_verification_codes
  ├─ LocalSessionService → sessionToken
  └─ VipService → permission
```

`AuthModule` 不再导入 `ProxyModule`，`AuthService` 不再注入 `ProxyService`。通用代理入口也会拦截 `General/PostLogin` 和全部 `MBUserLogin/*` 请求。

## 二、数据库表

### 1. `ai_jin_auth_credentials`

| 字段 | 用途 |
|------|------|
| `member_code` | 关联 `users.member_code`，唯一 |
| `mobile` | 手机号登录标识，非空时唯一 |
| `legacy_password_hash` | 老平台 `Pwd` 原值，首次迁移成功后立即清空 |
| `password_hash` | AI金 `scrypt` 密码哈希 |
| `password_algo` | `legacy_md5_base64` 或 `scrypt` |
| `password_migrated_at` | 升级新哈希的时间 |

建表 SQL：`server/database/sql/025-create-ai-jin-auth-credentials.sql`。

### 2. `ai_jin_verification_codes`

支持 `register` / `login` / `reset` 三种用途，记录过期时间、消费时间和失败次数。同一验证码成功后只能消费一次，错误 5 次后失效。

建表 SQL：`server/database/sql/026-create-ai-jin-verification-codes.sql`。

### 3. 本地建表红线

1. 执行前必须确认目标是 `127.0.0.1` 的 `bxg_app`。
2. 当 `.env` 指向 `192.168.1.64` 时禁止执行建表 SQL。
3. 禁止对 51bxg/秀吗生产库执行 DDL 或任何写操作。
4. 执行 025、026 后先检查表和约束，再导入存量用户。

## 三、存量用户导入映射

老平台导出由人工完成，AI金不直连老平台数据库。

| 老数据 | AI金表与字段 |
|--------|------------------|
| `MemberCode` | `users.member_code` + `ai_jin_auth_credentials.member_code` |
| `Mobile` | `users.phone` + `ai_jin_auth_credentials.mobile` |
| `Pwd` | `ai_jin_auth_credentials.legacy_password_hash` |
| `RealName` | `users.real_name` |
| `CustomName` | `users.nickname` |
| `CompanyName` | `users.company_name` |
| 用户状态 | `users.account_status`，需映射为 `active`/停用状态 |

存量凭据初始值：

```text
legacy_password_hash = Pwd 原值
password_hash = NULL
password_algo = legacy_md5_base64
password_migrated_at = NULL
```

导入时先写 `users`，再写 `ai_jin_auth_credentials`，否则会触发外键约束。`Pwd` 不解密、不重新计算、不修剪。

## 四、接口清单

| 方法 | 路径 | 本地实现 |
|------|------|----------|
| POST | `/api/auth/login` | 新哈希校验，或老哈希首次校验并升级 |
| POST | `/api/auth/register` | 验证码 + 创建 AI金用户和凭据 |
| POST | `/api/auth/sms-code` | 注册验证码 |
| POST | `/api/auth/sms-login-code` | 登录验证码 |
| POST | `/api/auth/login/sms` | 手机号 + 验证码登录 |
| POST | `/api/auth/forget-sms-code` | 重置密码验证码 |
| POST | `/api/auth/edit-password` | 只修改 AI金本地凭据 |

所有 POST 显式返回 HTTP 200，业务成败使用 `{ code: -1, msg, data: null }`。

## 五、登录与迁移流程

1. 按 `member_code` 或 `mobile` 查找本地凭据。
2. `password_algo=scrypt` 时直接校验 `password_hash`。
3. `password_algo=legacy_md5_base64` 时，对用户输入执行一次 MD5，将 16 字节原始结果 Base64 编码后与 `legacy_password_hash` 恒定时间比较。
4. 本地旧哈希失败直接拒绝，不调用老平台兜底。
5. 成功后生成 `scrypt` 哈希，清空 `legacy_password_hash`，记录 `password_migrated_at`。
6. 签发本地 `sessionToken`，返回 `IS_AI_JIN=true`、`MEMBER_CODE` 和 `permission`。

## 六、本地验证码说明

项目尚未配置 AI金独立短信供应商，因此：

- 本地环境：生成验证码、只存哈希，响应的 `data.debugCode` 供页面自动填入联调。
- 飞书环境：明确返回“AI金短信服务尚未配置”，不生成验证码，不调用 51bxg 兜底。

接入正式短信供应商时，仅替换 `VerificationCodeService.issueCode` 的发送环节，保留现有哈希存储、过期、限发和一次性消费逻辑。
