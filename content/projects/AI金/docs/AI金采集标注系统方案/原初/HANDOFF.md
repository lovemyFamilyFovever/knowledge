## 一、我们在做什么任务

### 1.1 任务目标

为**十几万篇行业文章（存量）+ 日增几百篇（增量）**构建一套 **RAG 知识图谱切片系统**，实现：

- 文章自动解析 → 语义切片 → 实体/关系抽取 → 向量化 + 图谱双写入库
- 支持向量检索 + 知识图谱推理的混合问答
- 增量文章分钟级可检索，存量批量可回溯

### 1.2 业务背景

- 用户所在公司：信用行 / AI部
- 领域：行业研究报告（当前样例是石油天然气/不锈钢领域，后续会扩展到更多行业）
- 触发点：用户有一篇飞书文档《石油天然气"十五五"规划解析：不锈钢需求类型与用量测算》，最初问"这篇文章怎么做切片"，逐步扩展到大规模知识库架构设计

### 1.3 核心设计原则

| 原则 | 说明 |
|---|---|
| **语义边界优先** | 切片边界 = 语义边界，不是字符数边界。拒绝固定长度一刀切 |
| **准确率优先于召回率** | 知识图谱中错误关系的危害远大于缺失关系。宁可漏抽不可错抽 |
| **结构保真** | 充分利用文档原生标题层级、表格、列表等结构，不拍平成纯文本 |
| **幂等可追溯** | 每篇文章、每个切片、每个实体都能追溯来源，重复处理不产生重复数据 |
| **增量优先** | 新文章实时处理，存量批量用空闲算力，不阻塞增量 |

## 二、已经完成了什么

### 2.1 单篇文章的切片方案（已完成）

针对样例文章《石油天然气"十五五"规划解析》，完成了：

- **RAG 知识图谱切片方案**：将文章拆为 18 个语义切片，每个切片携带 chunk_id、章节路径、核心实体、关系类型、关键词等元数据
- **实体 Schema 设计**：定义了 8 类实体（Policy/Target/Material/Scenario/Project/Company/Metric/Technology）和 9 类关系（sets_target/applies_to/demands/replaces/used_in/produces/drives/has_property/competes_with）
- **切片元数据模板**：JSON 格式，包含 chunk_id、doc_id、chapter_path、entities、relations、keywords 等字段

### 2.2 大规模系统架构设计（已完成）

完成了三个核心模块的原理、步骤、逻辑、业务流程的详细讲解：

#### 模块一：切片引擎
- 三级切片体系：Document → Section（一级，按章节结构）→ Chunk（二级，语义细分）
- 六步处理流程：结构解析 → 一级切片 → 二级语义细分 → 特殊块处理 → 元数据标注 → 质量校验
- 语义边界检测两种方式：段落聚类法（embedding相似度，快）和 LLM 判断法（准）
- 不同文档类型（政策/报告/新闻/技术/财报）的差异化切片策略

#### 模块二：实体/关系抽取
- 五层抽取架构：规则预抽取 → LLM 开放抽取 → 实体归一化 → 实体消歧 → 关系校验
- 领域词典驱动的归一化机制（别名→标准名）
- 置信度过滤 + 人工审核闭环
- 准确率优先的设计哲学

#### 模块三：增量流水线
- 整体架构：接入去重 → 消息队列 → 无状态Worker → 双写索引 → 状态存储
- 幂等更新机制（chunk_id hash、实体 MERGE、文章版本管理）
- 存量与增量协同处理（优先级队列、增量优先）
- 死信队列、重试机制、监控指标

### 3.2 待决策的技术选型

以下选型在原理讲解中提到了推荐方案，但未最终确认：

- **LLM 模型**：推荐豆包/GPT-4o 做抽取，小模型做规则兜底。需确认实际可用的 API 和成本预算

### 3.3 核心难点预判

1. **无结构文档的章节重建**：PDF扫描件、纯文本新闻没有标题层级，LLM 重建结构的质量和成本需要验证
2. **实体消歧的准确率**：同名实体在不同语境下的区分，是抽取质量的关键瓶颈
3. **表格的切片与检索**：表格独立成块后，如何向量化、如何被检索命中，需要特殊处理
4. **增量与存量的资源隔离**：避免存量批量处理占用过多资源影响增量实时性

#### Step 2：文档解析模块

**目标**：将 Markdown/HTML/PDF 解析为结构化 Block 树

```
输入：原始文档文件
  ↓
[1] 格式识别：根据扩展名判断文档类型
[2] 解析器分发：
    - Markdown → markdown-it / mistune 解析，保留标题层级
    - HTML → BeautifulSoup 提取正文和标题
    - PDF → 先用 pdfplumber 提取文本和表格，复杂PDF用 MinerU
[3] 结构化输出：统一为 Block 树
    Block 类型：heading(h1-h6)、paragraph、table、list、callout、image
    每个 Block 携带：block_id、type、content、parent_id、children[]
  ↓
输出：Block 树（JSON 格式）
```

**关键注意**：
- 表格必须保留行列结构，输出为 Markdown 表格或二维数组，不要拍平成文本
- 标题层级关系必须保留，这是后续切片的主要依据
- 图片只保留 URL 和说明文字，不处理图片内容

#### Step 3：切片引擎实现

**目标**：将 Block 树切分为语义独立的 Section/Chunk

```
输入：Block 树
  ↓
[1] 一级切片（按标题结构）：
    - 遍历 Block 树，以 H2 标题为边界切分
    - 每个 H2 下的所有子 Block 组成一个 Section 候选
    - H1 下如果没有 H2，则以 H1 为边界
  ↓
[2] 长度调整：
    - Section < 200字 → 尝试与相邻 Section 合并（判断主题相关性）
    - Section 200~800字 → 合格
    - Section > 800字 → 进入二级细分
  ↓
[3] 二级细分（语义边界检测）：
    - 方式A（默认，快）：将 Section 内的段落逐段生成 embedding，
      计算相邻段落相似度，相似度骤降处为切分边界
    - 方式B（关键文档，准）：调用 LLM，输入 Section 全文，
      让模型标注 [SPLIT] 边界
  ↓
[4] 特殊块处理：
    - 表格 → 独立成块，不与正文混切，额外生成表格摘要文本
    - Callout → 独立成块
    - 列表 → 附属于父段落
  ↓
[5] 元数据标注：
    - 为每个切片生成：chunk_id(hash)、section_path、summary(LLM一句话)、keywords
  ↓
[6] 质量校验：
    - 长度校验：100~1000字
    - 语义完整性：LLM 判断"是否能独立表达完整意思"
    - 不合格 → 重新切分，最多重试2次，仍不合格标记 needs_review
  ↓
输出：切片列表（每个切片含 content + metadata）
```

#### Step 4：实体/关系抽取实现

**目标**：从每个切片中抽取实体和关系，归一化后入库

```
输入：单个切片的 content + metadata
  ↓
[1] 规则预抽取（零成本，高准确）：
    - 正则匹配：不锈钢牌号(S\\d{4,5})、标准号(ASTM/API/GB)、数值+单位、日期
    - 词典匹配：遍历领域词典，精确匹配企业名、项目名、政策名
    - 输出：高置信度实体列表（带类型和原文位置）
  ↓
[2] LLM 开放抽取：
    - Prompt 结构：角色定义 + Schema说明 + 已识别实体(锚点) + 抽取任务 + 输出格式
    - 输入：切片文本 + 规则预抽取结果
    - 输出：entities[] + relations[]，每个关系带 confidence(0-1)
    - 关键约束：只能在预定义 Schema 内选择类型，不确定就不抽
  ↓
[3] 实体归一化：
    - 查领域词典：命中别名 → 替换为标准名，绑定标准 entity_id
    - 模糊匹配：编辑距离>0.9 → 候选，人工确认后加入词典
    - 未命中 → 创建新实体，分配新 entity_id
  ↓
[4] 实体消歧（仅对歧义词）：
    - 维护歧义词表（如"304"、"华能"、"十五五"）
    - 歧义词 + 上下文 → LLM 判断最可能指代
    - 置信度>0.8 自动确定，0.5~0.8 标记待审核
  ↓
[5] 关系校验：
    - 类型校验：subject/object 类型是否符合 Schema 约束
    - 置信度校验：≥0.7 通过，<0.7 进人工审核队列
    - 去重校验：相同(s,p,o)已存在则更新属性，不重复创建
  ↓
输出：归一化后的实体列表 + 关系列表
```

#### Step 5：索引层接入

**目标**：切片向量化写入向量库，实体关系写入图数据库

```
切片 → 向量库（Qdrant）：
  [1] 将 summary + keywords + content 拼接
  [2] 调用 embedding 模型生成向量（推荐 bge-large-zh 或 text-embedding-3-small）
  [3] 写入 Qdrant，payload 携带 chunk_id、doc_id、section_path、entities 等元数据
  [4] 支持按 doc_id、entity_id 过滤检索

实体/关系 → 图数据库（Neo4j）：
  [1] 实体作为节点，属性包括 name、type、standard_name、aliases、来源
  [2] 关系作为边，属性包括 confidence、source_doc_id、quantity 等
  [3] 使用 MERGE 操作保证幂等（存在则匹配，不存在则创建）
  [4] 为实体 name 建索引，加速查询
```

#### Step 6：增量流水线（简化版）

**目标**：支持文章批量入库和增量处理，保证幂等

```
简化版架构（Demo 阶段不用 Kafka，用内存队列 + SQLite 状态表）：

文章目录 → 文件监控 → 新文章检测
                ↓
          内容hash去重（SimHash）
                ↓
          内存任务队列
                ↓
    ┌─────────────────────┐
    │   Worker（单线程循环） │
    │   1. 解析文档         │
    │   2. 切片             │
    │   3. 实体关系抽取      │
    │   4. 双写索引         │
    │   5. 更新状态表        │
    └─────────────────────┘
                ↓
          状态表（SQLite）：
          doc_id, status, version, content_hash,
          chunk_count, entity_count, retry_count, error_msg

幂等保证：
- chunk_id = hash(doc_id + section_path + offset)，写入用 upsert
- 实体用 MERGE，关系用 MERGE
- 处理前查状态表，已完成且hash未变则跳过
```

#### Step 7：检索 + 问答 Demo 验证

**目标**：验证端到端效果，能用自然语言查询并得到基于切片和图谱的答案

```
用户提问 → 混合检索：
  [1] 向量检索：提问 → embedding → Qdrant 召回 Top-K 切片
  [2] 图谱检索：从提问中识别实体 → Neo4j 查询关联实体和关系
  [3] 结果融合：将向量召回的切片和图谱查询结果合并去重
  [4] 重排：用 cross-encoder 对召回结果重排序
  [5] 生成：将 Top-N 切片作为上下文，LLM 生成答案并标注来源

验证问题清单（用不锈钢样例文章测试）：
- "2205和2507有什么区别？" → 应能对比两个实体的属性
- "哪些项目用了2507？" → 应能通过 used_in 关系列出项目
- "LNG接收站需要哪些不锈钢？" → 应能召回LNG场景的切片
- "十五五规划对油气管道有什么目标？" → 应能召回政策目标
- "双相不锈钢的需求量是多少？" → 应能聚合各场景的demands关系
```

## 五、踩过的坑与避坑指南

### 5.1 绝对不要再踩的坑

| 坑 | 表现 | 正确做法 |
|---|---|---|
| **固定长度切片** | 按500字一刀切，导致语义断裂、表格被切碎 | 按文档结构+语义边界切，表格独立成块 |
| **纯开放式LLM抽取** | 不限制Schema，模型自由发挥，实体类型五花八门，关系混乱 | 严格按预定义Schema抽取，类型约束+置信度过滤 |
| **不做实体归一化** | "中海油"、"中国海油"、"CNOOC"变成三个独立节点，关系分散 | 必须建领域词典，别名→标准名，所有实体归一化后再入库 |
| **图谱里塞错误关系** | 为了追求召回率，低置信度关系也入库，导致多跳推理时错误被放大 | 准确率优先，置信度<0.7的进人工审核，不自动入库 |
| **表格拍平成文本** | 把表格转成纯文本段落，丢失行列关系，检索时无法精确匹配 | 表格独立成块，保留Markdown格式，额外生成摘要用于向量召回 |
| **切片不带元数据** | 只存content，不知道来自哪篇文章、哪个章节、包含哪些实体 | 每个切片必须携带完整元数据，这是检索过滤和溯源的基础 |
| **重复处理不幂等** | 文章重复入库导致重复切片、重复实体，数据膨胀 | 所有写入操作用upsert/MERGE，处理前查状态表去重 |
| **存量阻塞增量** | 批量处理十几万篇时，新文章要等很久才能检索 | 优先级队列，增量走high优先级，存量走low优先级，资源隔离 |

### 5.2 容易忽略的细节

1. **切片的 summary 和 keywords 要参与向量化**：纯文本 embedding 的召回精度比"summary+keywords+content"拼接后低 15-20%
2. **实体消歧只对歧义词做**：不要每个实体都做消歧，大部分实体在领域内无歧义，全做会浪费大量LLM调用
3. **SimHash去重要在切片前做**：文章级去重，避免重复文章进入流水线；切片级也要标记重复段落（如政策原文被多篇引用）
4. **版本管理不能物理删除**：文章更新时旧切片标记deprecated，向量索引过滤掉，不删除。实体属性保留历史值+来源
5. **LLM抽取的prompt里要传入规则预抽取的结果作为锚点**：模型看到"2205已识别为Material"，就不会误判类型，减少错误

### 5.3 成本与性能注意事项

- **LLM调用是最大成本项**：十几万篇文章，每篇平均5个切片，每个切片一次抽取调用，约50万次。用小模型做规则兜底，大模型只做关键抽取
- **embedding 可以批量处理**：不要逐片调用，攒批后批量生成，能省 50% 以上时间
- **存量处理建议分领域分桶**：按行业/时间分批，每批跑完做质量校验，不要一口气全量跑
- **监控必须从第一天就建**：处理量、成功率、平均时长、队列积压、质量合格率，没有监控就是黑盒
