# AI 金采集标注系统 — 方案总览

> 版本：V1.0 ｜ 编制：AI 部门（技术） ｜ 依据：洛歌发布的 3 份标准格式文档（数据 V1.0 / 事件 V1.0 / 分析预测 V1.0）

---

## 一、项目背景

洛歌已发布 3 份标准格式文档，确立了公司未来数据采集、文章处理、内容输出的标准化方案：

| 文档 | 定义内容 |
|---|---|
| AI 金数据采集标准格式 V1.0 | 4 个维度的数值采集格式：日价 / 周库 / 月产 / 季需，含必填字段、原因字段、影响字段、同比环比计算规则 |
| AI 金事件类标准采集格式 V1.0 | 7 大类行业事件（钢厂 / 原料 / 政策 / 需求 / 宏观 / 突发 / 行业）的标准化上报格式，含必填字段 E1-E11 与可选字段 O1-O11 |
| AI 金分析与预测标准格式 V1.0 | 分析类（A 事件解读 / B 数据解读）与预测类（P 价格 / Q 库存 / R 需求产量）的结构化采集格式，四轨（数据→事件→分析→预测）双向引用体系 |

**最终目标**：把存量约 14 万+ 篇历史行业文章与日增文章，按标准格式处理入库，支撑两个输出方向——(a) AI 金问答（结构化命中 + 图谱推理）；(b) 多平台多风格内容分发（公众号 / 51APP / 抖音 / 行业群等）。

**洛歌的核心关切**：
1. 方案是否可行（闭环能否跑通）
2. 对后续 AI 问答与内容分发能增加多少好处

## 二、本方案的核心主张

**一句话概括：洛歌的 3 份文档定义了"数据模型"，本方案定义"工程化实现"，并把"人工逐字段填写"升级为"AI 预填 + 人工校核"。**

| 维度 | 洛歌文档的原设计 | 本方案的工程化升级 | 保留 |
|---|---|---|---|
| 字段与枚举 | 单选/多选/文本表单 | 字段与枚举 100% 保留，原样入库 | ✅ 完全保留 |
| 采集动作 | 采集人员逐字段选择+填空 | AI 按 Schema 约束抽取并预填，人员只校核标红项 | 字段不变，动作变轻 |
| 关联关系 | 人工填写"关联事件 ID""数据影响方向" | 抽取时自动生成关系并写入图谱 | 双向引用保留 |
| 同比/环比 | 人工计算填写 | 系统自动计算；无历史数据留空标记 | 计算规则不变 |
| 输出 | AI 按渠道模板生成 | 同左，增加置信度门槛与人工确认 | 完全保留 |

**为什么这样升级**：洛歌方案落地细节复杂（前因后果关联、多跳追溯），若全部由人工完成，其他部门同事工作量爆炸。本方案把"人肉管道"变为"机器提取 + 人只审重点"，工作量从"每篇全量审核"降为"按置信度抽检 + 发布前确认"。

## 三、硬性条件（不可更改）

1. **运行环境**：代码运行在飞书妙搭（云函数容器），无 Docker、无自建服务器条件。一切功能必须能跑在妙搭环境，或妙搭提供 API + 本地应用调用。
2. **数据存储**：唯一存储途径是飞书妙搭的 PostgreSQL 数据库。不引入任何外部数据库（Neo4j / 向量库 / 文件存储均不可用，图谱用 PG 实现）。
3. **数据源**：全新项目定位。所有数据源 = 其他部门同事手工采集的文章 + 手工添加的报价信息。不接 51bxg 接口、不接任何外部 API。
4. **人工介入原则**：技术部门接受较高开发工作量；其他部门同事的工作量必须最小化、流程必须简单。

## 四、总体架构

```
┌─ 输入层：同事上传/粘贴文章 + 手工填报价 ──────────────────────┐
│  （唯一数据源：手工采集，无外部 API）                          │
└────────────────┬──────────────────────────────────────────────┘
                 ↓ ① 入库（原文存储 + hash 去重）
┌─ 提取引擎（新增业务模块） ─────────────────────────────────────┐
│ ② 类型路由：AI 判断文章类型 → 命中对应采集模板                 │
│ ③ 约束抽取：按 Schema（字段+枚举+示例）抽 JSON，每字段带：      │
│    置信度（高/中/低）× 数据性质（FACT/OPINION/INFERENCE）      │
│ ④ 实体/关系抽取：钢厂/原料/政策/行业实体 → 自动关联             │
└────────────────┬──────────────────────────────────────────────┘
                 ↓ ⑤ 人工校核（AI 预填，只审标红，可一键全过）
┌─ 存储层（PostgreSQL 唯一存储） ────────────────────────────────┐
│ 结构化表：data_articles / data_events / data_daily_price /   │
│           data_weekly_inventory / data_monthly_production /  │
│           data_quarterly_demand / data_analysis /            │
│           data_forecast / 字典表                              │
│ 图谱存储（PG 实现）：kg_entities（实体节点）+ kg_relations     │
│           （关系边），递归查询支撑多跳推理                     │
└────────────────┬──────────────────────────────────────────────┘
                 ↓ ⑥

└───────────────────────────────────────────────────────────────┘
```

## 五、四层业务架构（长期定位）

> 审查建议采纳：本系统不是"文章处理系统"，而是"把非结构化行业信息转换成可验证结构化行业知识"的数据生产系统。按四层组织，未来扩展智能采销等应用不破坏核心。

| 层 | 内容 | 可信度要求 |
|---|---|---|
| 第一层 原始资料层 | 文章 / 文件 / 报价 / 来源原文 | 原文保真 |
| 第二层 标准事实层 | 数据（4 维度）+ 事件（7 大类） | **可信数据资产**，只含 FACT |
| 第三层 知识推理层 | 分析 A/B + 预测 P/Q/R + 实体 + 关系 | 允许 AI 推断 + 人工确认，区分来源 |
| 第四层 应用层 | AI 问答 / 内容生成 / 图谱 / 报告 / 智能采销 | 消费二三层数据 |

**关键纪律**：第二层只允许 FACT（原文事实）；OPINION（原文观点）与 INFERENCE（AI 推断）不得混入标准事实层，只能进入第三层并明确标注性质。

## 五、明早 MVP 范围（演示验收标准）

**MVP 核心演示链路**：一篇真实文章 → AI 自动识别类型 → AI 结构化预填 → 人工只改少数问题 → 入库 → 结果可追溯（列表 + 图谱可视化页）。

### 5.1 MVP 必须做

| 模块 | 范围 |
|---|---|
| 工作台 | 三页信息架构：首页（待处理队列+快捷入口）/ 处理页（左原文+右表单+底部操作条）/ 我的记录页（已完成+追溯） |
| 类型路由 | 支持 event（7 大类）、data_price、mixed（一文多记录） |
| 约束抽取 | 事件模板（E1-E11 + 主要可选）+ 日价模板（核心字段），字段级置信度，无证据返回 null |
| 人工校核 | AI 预填 + UI 三态（🟢正常/🟡建议确认/🔴必须确认）+ AI 修改建议 + 一键全过（含硬拦截）/ 提交 / 复制上次 |
| 生命周期 | 父任务（data_articles）+ 子记录（业务表）独立状态 + skipped/rejected，mixed 一文多记录 |
| 入库 | 事件/日价写入 + 同比环比自动计算（冷启动留空标记） |
| 图谱 | kg 表（node_category/nature 分层）+ 入库自动写实体/关系 + **图谱可视化页（5 个核心功能：搜索/子图展开/节点详情/视觉区分/规模统计）** |
| 输出草稿 | **内容编辑工作台**：素材选择（confirmed）→ 渠道/风格（兼容矩阵）→ AI 生成 → 修改/重生成（版本）→ 定稿存档（data_content），演示 3 个成品（公众号/51APP/行业群），不接分发 |
| 追溯 | 文章详情页展示"此文生成了哪些记录/关联了哪些实体"；生成内容带素材引用标注 |

### 5.3 MVP 验收标准（黄金路径口径，与 04/06 一致）

1. **黄金路径**：一篇真实文章走完全流程（采→存→图→出），人工改动 ≤3 处，结果在详情页 + 图谱页可追溯
2. **字段对齐**：事件/日价字段与洛歌文档一一对应（用 01 文档核对）
3. **置信度机制**：UI 三态正确呈现；一键全过在含低置信度/必填空/INFERENCE 未确认/判断类未确认字段时被硬拦截
4. **mixed**：一篇"减产+价格"复合文生成 2 条业务记录，各自独立入库、独立追溯
5. **内容生成**：同一条已确认事件 → 素材包 → 生成 **3 个成品**（公众号深度报道 / 51APP 卡片 / 行业群快讯）→ 修改 → 定稿存档
6. **图谱可视化**：5 个核心功能可用（搜索"太钢"→ 子图展开 → 节点详情 → 视觉区分 → 规模统计），链路通过逐跳展开演示（不做高亮路径）
7. **操作量**：同事实测从打开待处理记录到提交，操作 ≤3 分钟（不含 AI 等待）

## 六、四条设计原则

1. **Schema 即约束**：洛歌文档里的字段清单、枚举选项、填空模板，原样变成数据库表结构与抽取约束。AI 只能在 Schema 内输出，天然与洛歌要求一致。
2. **AI 预填、人工校核**：所有字段先由 AI 填好并标注置信度，低置信度标红。同事只审红字段；全高置信度一键提交。
3. **图谱支撑前因后果**："钢厂减产 → 为什么减产 → 减产导致什么"由图谱多跳查询实现，这是纯 RAG 做不到的。
4. **闭环优先**：先拿 5-30 篇测试文章跑通"上传→提取→校核→入库→输出"最小闭环，验证可行后再批量处理存量。

## 八、术语表

| 术语 | 含义 |
|---|---|
| Schema | 字段规则集合（字段名、类型、枚举、必填性、示例），即洛歌文档定义的采集模板 |
| 约束抽取 | AI 在 Schema 限定范围内提取信息，输出结构严格匹配字段定义 |
| 置信度 | 每个字段提取结果的可信程度（高/中/低），低置信度进入人工校核重点 |
| 数据性质 | 每个字段的三种性质：FACT（原文事实）/ OPINION（原文观点）/ INFERENCE（AI 推断）。FACT 才可进标准事实层 |
| 四轨 | 数据轨 / 事件轨 / 分析轨 / 预测轨，互相通过引用 ID 关联 |
| 图谱（KG） | 实体为节点、关系为边、多跳推理支撑"前因后果"查询，PG 实现 |
| 类型路由 | AI 判断一篇文章属于哪类（7 大类事件 / 4 维度数据 / 分析预测） |
| 冷启动 | 系统刚上线无历史数据，同比环比等衍生字段留空标记的状态 |
| 标准事实层 | 四层架构第二层：只含 FACT 性质的数据与事件，是可信数据资产 |
