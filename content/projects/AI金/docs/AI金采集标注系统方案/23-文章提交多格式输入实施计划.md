## 一、目标

把「文章提交」从「标题 + 纯文本 textarea」升级为**自研轻量富文本编辑器**，操作者可通过 复制粘贴 / 选择或拖拽文件 / 图片粘贴或上传 / 图片 OCR 等途径输入内容，**富文本直接所见即所得展示（含图片）**；提交时图片压缩转 AVIF/WebP 后以二进制存入**独立图片表**，正文交由现有「AI 类型路由 → 约束抽取」管线处理。

## 二、富文本实现方式评估（结论：自研手写，复用广场思路）

### 2.1 智能广场「发布文章」现状（已核对代码）

- 实现：**手写 `contenteditable` + `document.execCommand`**，无第三方富文本依赖。
- 参考点：[PlazaPublishPage.vue](file:///c:/Users/liuxi/Desktop/code/client/src/pages/plaza/PlazaPublishPage.vue#L2914-L2935)（工具栏 `editorTools`、`execFormat`/`insertTable`、`onArticleInput`/`onArticlePaste`）。
- **复用度**：页面是 Tailwind + 超大组件，不能直接 import；核心 execCommand 逻辑可抽取，重写为 ERP 风格（Element Plus + scoped CSS）的自研轻量组件。

### 2.2 选型对比

| 方案 | 难度 | 说明 | 结论 |
|---|---|---|---|
| **自研手写**（推荐） | 低 | 广场已有可参考实现；需求仅基础功能（加粗/有序/无序列表/分割线/图片），execCommand 全覆盖；无依赖变更 | ✅ 采用 |
| 引入 wangeditor | 中 | 中文文档好、轻量、含图片；但需依赖授权 + 样式适配 + 学习 API | ❌ 不采用 |
| 引入 quill / tiptap | 中-高 | 偏重或老，与 ERP 风格适配成本高 | ❌ 不采用 |

### 2.3 注意事项

- `document.execCommand` 已标 deprecated，但对加粗/列表/分割线这些基础命令，**所有现代浏览器仍稳定支持**，对本期需求足够。
- 富文本只用于**编辑与展示**；提交时同时产出「纯文本」给 AI 抽取（去标签噪音）与「HTML」用于展示/内容生成。
- 样式按 ERP 规范（Element Plus + scoped CSS），**禁用 Tailwind**。

## 五、图片处理与存储（核心设计）

### 5.1 处理链路

```
用户粘贴/上传图片
  → 前端压缩：compressImage()（AVIF 优先，WebP 回退，目标 ≤512KB、长边 ≤1920px）
  → 富文本内以 <img> 直接显示（编辑期仅内存/Blob URL，不入库）
  → 提交时：压缩后的 Blob → ArrayBuffer → base64 随文章一起 POST
  → 后端：base64/Buffer → bytea 写入独立图片表 dict_article_images
```

### 5.2 存储设计：图片独立建表（用户已拍板）

> 表名采用 `dict_` 前缀（与 ERP 后台统一前缀一致，便于后续维护识别；虽名为 dict，实际存采集文章附属图片二进制）。

新增表 `dict_article_images`（迁移脚本从 **045** 起，幂等），与文章主表 `data_articles` 一对多：

```sql
CREATE TABLE IF NOT EXISTS dict_article_images (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  article_id  UUID NOT NULL REFERENCES data_articles(id) ON DELETE CASCADE,
  image_data  BYTEA NOT NULL,            -- 压缩后图片二进制（AVIF/WebP）
  image_meta  JSONB NOT NULL,            -- {version, mimeType, width, height, size, sortOrder}
  sort_order  INTEGER NOT NULL DEFAULT 0, -- 富文本内出现顺序
  _created_at TIMESTAMPTZ DEFAULT now(),
  _updated_at TIMESTAMPTZ DEFAULT now(),
  _created_by TEXT,
  _updated_by TEXT
);
CREATE INDEX IF NOT EXISTS idx_dict_article_images_article_id ON dict_article_images (article_id);
COMMENT ON TABLE  dict_article_images IS '采集标注-文章图片表（压缩后二进制，独立于文章正文存储）';
COMMENT ON COLUMN dict_article_images.image_data IS '压缩后图片二进制（AVIF/WebP）';
COMMENT ON COLUMN dict_article_images.image_meta IS '图片元数据：{"version":1,"mimeType","width","height","size","sortOrder"}';
```

同时给 `data_articles` 增加正文 HTML 列（保存富文本原始 HTML，供未来展示/内容生成）：

```sql
ALTER TABLE data_articles ADD COLUMN IF NOT EXISTS content_html TEXT;
COMMENT ON COLUMN data_articles.content_html IS '文章富文本原始 HTML（含图片引用），可选存储';
```

- 迁移后显式执行 `node scripts/run-collect-migrations.mjs 045 045` 并 COUNT 核对；飞书环境补跑同一脚本（双库账本一致）。
- **bytea 读写边界（妙搭 schema 坑，见 04-pitfalls）**：`schema.ts` 由 codegen 生成、bytea 映射为 `text`，repository 边界做类型断言：
  - 写入：`updates.imageData = params.imageData as unknown as string`
  - 读取：`Buffer.isBuffer(raw) ? raw : Buffer.from(raw as unknown as string)`

### 5.3 出库/入库格式转换（用户第 4 点）

- **入库**：前端 base64（或 Buffer）→ 后端 Buffer → `bytea`。
- **出库**：`bytea` → Buffer → base64（`data:image/avif;base64,...` 或 webp）→ 前端 `dataURL`/Blob URL 直接渲染；富文本 `<img>` 用 blob URL 展示，无需外链。
- 图片未来如需进入**素材库/内容生成**：素材库（content-studio 左侧）当前取自 confirmed/active 数据轨子记录；图片属文章附属二进制，作为「未来方向」预留，本期不做素材库改造，仅保证二进制存取规范与出/入库转换正确。

### 5.4 图片与富文本 HTML 的关联机制（关键设计）

编辑期 `<img src="blob:...">` 是浏览器临时 URL，**提交后失效**；出库渲染必须能按 `<img>` 与 `dict_article_images` 记录一一对应。采用「稳定 ID 标记 + 出库回填」：

1. **提交前（前端）**：遍历富文本 `<img>`，按出现顺序生成 `images` 数组（每项含压缩后 base64 + mimeType/width/height/size），并把每个 `<img>` 的 `src="blob:..."` 替换为占位 `data-image-idx="N"`（N = 在 images 数组中的下标）；`content_html` 随提交。
2. **入库（后端）**：按序写 `dict_article_images`（`sort_order = N`，生成记录 `id`）；将 `content_html` 中 `data-image-idx="N"` 替换为 `data-image-id="{记录id}"` 后落库。
3. **出库（渲染）**：文章详情接口同时返回 `content_html` 与 `images[]`（每条含 `id` + base64 dataURL）；前端遍历 `<img data-image-id>` 用对应 `dataURL` 回填 `src` 渲染，blob URL 失效问题由此解决。

|---|---|---|

### (c) 下一步绝对不要再踩的坑（红线沉淀）
