# 02 — 数据模型设计

> 目的：定义 PostgreSQL 全量表结构。所有表位于飞书妙搭数据库（唯一存储途径），遵循项目表前缀规范（`data_` 数据域 / `kg_` 图谱域），每表含 4 个审计列（_created_at / _updated_at / _created_by / _updated_by）。

> - data_forecast 状态拆为 review_status + verification_status 两个维度
> - 父任务聚合函数补全；article_id 统一为 source_article_id

## 一、建表总则

1. **前缀**：数据采集用 `data_`，知识图谱用 `kg_`，字典用 `dict_`。
2. **主键**：UUID（gen_random_uuid()）。**部署前必须确认妙搭 PG 支持该函数，受限则由应用层生成 UUID。**
3. **审计列**：全部表含 `_created_at / _updated_at / _created_by / _updated_by`（飞书平台要求）。
4. **枚举**：单选类字段存枚举字典表外键或 TEXT + CHECK；多选类存 TEXT[] 数组或 JSONB 数组。建议枚举统一入字典表（dict_*），便于界面下拉联动与 AI 抽取约束。
5. **衍生字段**（同比/环比等）由系统计算，不依赖人工；冷启动期允许 NULL，标记状态字段说明。
6. **归档语义**：**MVP 不提供物理删除**；记录通过 status=archived 表示"归档/停用"（可恢复），不叫软删除。
7. **幂等**：文章入库用 content_hash 去重（见三章去重策略）；重复提交不产生重复记录。
8. **统一状态机（两套，必须分开）**：
   - **文章状态**（data_articles.status）：pending（待提取）→ processing（处理中）→ reviewing（待校核）→ completed（完成）/ partial（部分完成）/ failed（失败）/ duplicate（重复）。
   - **业务记录状态**（各业务表 status）：draft（AI 预填草稿）→ confirmed（人工校核确认）→ archived（归档）；另有 **skipped（跳过，暂不处理回队列）** 与 **rejected（放弃，永久不处理）** 两个非主链状态（语义见 03 文档 5.2）。**数据轨（4 张数据表）例外：AI 抽取后直接进入 active（正式数据层），仅低置信度/异常才转 draft 待人工**（业务决策 B2，见四章）。
9. **字段级元数据**：AI 抽取的每个字段均带两个元数据——`confidence`（置信度：high/medium/low）与 `nature`（数据性质：FACT/OPINION/INFERENCE）。**数据性质不落主表（统一存 ai_draft）**；业务记录（数据/事件）**仅当字段性质为 FACT 时才允许 confirmed/active**——此为流程规则而非 DB 约束，由入库管线执行并记录在 ai_draft。
10. **字段级证据链**：AI 抽取的每个字段在 ai_draft JSONB 中记录 evidence（原文片段 + 位置）+ **field_reviewed（字段审核状态：unreviewed/confirmed/modified/rejected，子记录级确认的审计留痕，见 03 文档 5.1）**，支持"点字段跳原文"与校核验证（详见 03 文档）。
11. **审计/人员字段语义**（避免混用）：
    - `_created_by / _updated_by` = 系统记录创建者/更新者（自动）
    - `collector_name` = 业务采集人（填表的同事）
    - `reviewed_by` = 审核人（校核者）
    - `analyst_id / analyst_name` = 分析作者（分析/预测的撰写人）
    - `forecaster` = 预测来源（人或 AI 模型版本）
12. **数值字段一等公民（五轮复审采纳）**：数值一律拆分存储，禁止把"14200元/吨含税"存成字符串：
    - `value`（数值 NUMERIC）+ `unit`（单位 TEXT）+ `tax_status`（含税/不含税）+ `currency`（币种，默认 CNY）+ 业务上下文（market/date 等）
    - 单位/含税/币种必须独立字段，这是同比、环比、图谱、问答、预测、报告的计算基础
    - 抽取规则：AI 必须把"14200 元/吨 含税"拆为 value=14200、unit=元/吨、tax_status=含税，不得整串存储

## 三、文章表（data_articles）与父子生命周期

**职责**：原文存储 + 去重 + **任务容器**（一篇文章 = 一个处理任务，可挂多条业务记录）。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | 主键 |
| title | TEXT | 文章标题 |
| content | TEXT | 文章全文 |
| content_hash | TEXT | 内容 SHA-256 去重指纹（**非唯一索引**，见下方去重策略） |
| source_url | TEXT | 来源链接 |
| source_name | TEXT | 来源平台（如 51bxg / 公众号 / 自写） |
| author | TEXT | 作者（自写文章用） |
| article_type | TEXT | 路由判定结果：event / data_price / data_inventory / data_production / data_demand / analysis / forecast / mixed / unknown |
| status | TEXT | **文章状态机**：pending（待提取）/ processing（处理中）/ reviewing（待校核）/ completed（完成）/ partial（部分完成）/ failed（失败）/ duplicate（重复） |
| confidence_summary | JSONB | 各字段置信度汇总（供校核页标红） |
| ai_draft | JSONB | AI 草稿原始内容（含每字段 evidence 证据链 + nature 性质，供回溯与验证） |
| extracted_at | TIMESTAMPTZ | 提取完成时间 |
| reviewed_at | TIMESTAMPTZ | 校核完成时间 |
| reviewed_by | TEXT | 校核人 |
| related_entity_ids | TEXT[] | **只读缓存**（图谱回刷，见 3.2）；不允许人工直接维护、不作为关系写入入口 |
| version | INTEGER | 版本号（重提递增） |
| remark | TEXT | 备注 |

**去重策略（业务决策 A2：转载保留）**：
- content_hash = 正文 SHA-256 指纹；**唯一键 = content_hash + source_name**（复合）
- 同来源 + 同 hash → 判 duplicate（不重复处理）
- **不同来源 + 同 hash → 视为不同文章都保留**（转载链），记录可互相标记 `duplicate_of`（指向最早来源文章，仅标记不合并），后续可溯源"这篇内容发过哪些平台"
- 唯一索引：`UNIQUE(content_hash, source_name)`

### 3.1 父子记录生命周期（mixed 关键设计）

```
data_articles（父任务，一条）
  status: pending → processing → reviewing → completed / partial / failed / duplicate
业务记录（子记录：data_events / data_daily_price / ...，可多条）
  各自独立 status（业务记录状态机）: draft → confirmed → archived
  外键 source_article_id → data_articles.id（可空：数据快填无文章载体）
```

**父任务聚合函数（由子记录状态集合确定，不是由单一条件触发）**：

| 子记录状态集合 | 父任务状态 |
|---|---|
| 全部 confirmed（或 active，数据轨） | completed |
| 全部 draft | reviewing |
| 存在 confirmed/active + 其余 draft | reviewing（等待剩余子记录校核） |
| 存在 confirmed/active + 其余 failed | partial（已完成的保留，失败的可单独重试） |
| 全部 failed | failed |
| 处理过程中未生成任何子记录 | processing（管线仍在运行）→ 全部失败则 failed |
| 路由/抽取阶段失败 | failed |
| 去重命中 | duplicate |

**关键点**：父任务状态**不手动维护**，每次子记录状态变更后由聚合函数重新计算得出。

**图谱写入**：每条子记录 confirmed（或 active，数据轨）时逐条触发，不等待父任务完成。

**一条 mixed 文章示例**："太钢减产且价格小涨" → 子记录① data_events（A 钢厂类·产线检修）+ 子记录② data_daily_price（304/2B 无锡 14200）→ 各自独立校核、独立入库、独立追溯。

### 3.2 引用关系唯一真源规则（审查意见采纳）

业务表之间的关联字段（related_event_ids / related_data_ids / related_analysis_ids / related_forecast_ids）**不是独立维护的关系**：

- **唯一真源** = 图谱关系表 kg_relations（见 04 文档）
- 业务表引用字段由图谱关系**回刷**（入库时自动写入，图谱变更时同步）
- 出现不一致时以图谱为准，系统定时对账（diff 告警）
- MVP 简化：入库时双向同时写入，保证即时一致；对账任务 P2 加

## 八、知识图谱表（kg_*）

> **业务记录图谱化（P0-1 方案 A，审查意见采纳）**：kg_entities 不仅是"行业实体"（钢厂/原料等），也承载**业务记录节点**（事件/数据/分析/预测）。业务记录入库（confirmed/active）时同步创建对应图谱节点，使 kg_relations 能表达"Event →IMPACTS→ Price"这类业务记录间关系，真正成为全系统关系唯一真源。

### 8.1 kg_entities（节点，实体 + 业务记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | |

**唯一身份约束（四轮复审 P0 采纳）**：
- **UNIQUE (biz_record_type, biz_record_id)**：一条业务记录只能对应一个图谱节点

### 8.2 kg_relations（关系边）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | |
| relation_id | TEXT | REL-xxx（唯一） |
| source_entity_id | UUID | 起点节点（实体或业务记录） |
| target_entity_id | UUID | 终点节点（实体或业务记录） |
| relation_type | TEXT | 关系类型（见下） |
| nature | TEXT | **关系性质（五轮复审采纳）**：FACT（原文明确事实，如"太钢 →PRODUCES→ 304"）/ OPINION（原文观点）/ INFERENCE（AI 推断，如"镍价上涨 →IMPACTS→ 304 价格"）。问答层可"只使用 FACT 关系回答"或"FACT + 已确认 OPINION" |
| properties | JSONB | 关系属性（如影响程度、时间、数值） |
| confidence | NUMERIC | 置信度 |
| source_ids | TEXT[] | **来源追溯缓存（provenance）** |
| is_verified | BOOLEAN | 是否人工核验 |
| status | TEXT | active / merged / archived |

**关系抽取纪律（五轮复审采纳）**：生产环境关系自动抽取必须遵守 01 的数据性质纪律——原文明确事实才建 FACT 关系；"市场人士认为…"类表述只建 OPINION/INFERENCE 关系（低置信度进核验队列），不得与 FACT 关系混层。MVP 演示阶段即可执行（抽取 prompt 内置该约束）。

**关系类型枚举**：CAUSED_BY（由…导致）、IMPACTS（影响）、LEADS_TO（导致…趋势）、REFERS_TO（关联/引用）、PRODUCES（生产）、USES（使用）、IS_A（属于）、LOCATED_IN（位于）、ANNOUNCED_BY（由…发布）、ASSOCIATED_WITH（相关）、PREDICTS（预测）、VERIFIES（验证）。

**关系方向规范**（审查意见采纳，必须写死，否则图谱混乱）：
- source → CAUSED_BY → target：target 是原因（如 减产 →CAUSED_BY→ 检修）
- source → IMPACTS → target：source 影响 target（如 检修 →IMPACTS→ 304 价格）
- source → REFERS_TO → target：source 引用 target（分析 → 事件）
- source → PRODUCES → target：source 生产 target（钢厂 → 钢种）
- source → PREDICTS → target：source 预测 target（预测记录 → 业务记录节点/标准实体，映射规则见 04 文档 3.4）
- source → VERIFIES → target：source 验证 target（实际数据 → 预测记录）
- ASSOCIATED_WITH：无方向性，canonical ordering（标准 ID 字典序小者 → 大者），仅用于去重不表达业务方向，查询双向等价
- 其余关系（USES/IS_A/LOCATED_IN/ANNOUNCED_BY/LEADS_TO）方向均为"主语 → 宾语"语义方向

**关系去重规则（四轮复审确认，决策 B）**：
- **同一对节点同类型关系允许多条**（如"太钢 →IMPACTS→ 304"可存在 8 月检修影响、9 月扩产影响多条），每条带 time / source_ids / magnitude / direction 属性，不合并压成一条
- 关系唯一性由 relation_id 保证，**不去重 (source, target, type)**
- 查询时同类型多条边按 time 倒序返回，可时间范围过滤

**索引**：source_entity_id + relation_type（复合）、target_entity_id + relation_type（复合）——这是多跳查询性能的关键，必须建立。

## 十、TEXT[] 字段说明（MVP 简化，未来迁移）

> 审查意见采纳：业务表的 TEXT[] 关联字段（related_event_ids 等）是 MVP 简化方案。长期大量查询"所有涉及 304 的事件"时数组字段会变吃力。**迁移原则收敛：只有需要参与跨对象关系查询、归一化、多跳推理的枚举/实体才迁入 kg_entities，不为图谱而图谱。**

| 字段 | MVP 处理 | 长期迁移方向 |
|---|---|---|
| related_grades / related_regions | TEXT[] 直接存 | ✅ 迁：实体化到 kg_entities（product_grade / region_market 类型）+ 图谱关系 |
| related_event_ids / related_data_ids / related_analysis_ids / related_forecast_ids | TEXT[] 存 ID | ✅ 迁：业务记录已图谱化，kg_relations 是唯一真源；业务表字段退化为缓存 |
| downstream_industries / application_scenarios | TEXT[] 存 | ⚠️ **不强制迁**：仅描述性维度，除非未来参与跨对象推理才实体化 |
| 原因/影响字段（reason_* / impact_*） | TEXT 或 TEXT[] | 保持（自由文本，非关联） |

**结论**：MVP 用数组字段保持简单；图谱层从第一天就承载关系语义（业务记录已图谱化），未来业务表数组字段退化为缓存即可，不用迁移数据。
