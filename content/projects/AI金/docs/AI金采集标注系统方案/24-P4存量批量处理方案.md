## 一、背景与目标

### 1.1 存量即核心资产（出处：五轮复审）

06 号文档 V1.2 修订（五轮复审意见）对分期的关键调整：**P4 存量批量处理提前、P5 问答后移**。原文判断：

> "约 14 万+ 篇历史文章的全量处理——这批数据本身才是系统最值钱的资产（结构化→事件→价格→实体→关系→数据资产）。"

即：系统的价值天花板不由单篇处理能力决定，而由存量资产的转化规模与质量决定。P1-P3 已跑通"采→存→图→出"闭环与内容/报告输出，P4 的目标是把同一套管线从"每天几篇增量"扩展到"几十万篇存量"的批量形态。

### 1.2 P4 六项任务（06 号文档原文，本方案逐条展开）

| 任务 | 原文说明 |
|---|---|
| 批量流水线 | 定时/队列批量处理：去重 → 路由 → 抽取 → 入库（跳过人工校核或抽样校核） |
| 增量优先 | 新文章实时处理（高优先级），存量批量低优先级，不互相阻塞 |
| 质量策略 | 存量记录置信度，低置信度进核验队列（抽样审核） |
| 分领域分桶 | 按行业/时间分批，每批跑完质量抽检再跑下一批 |
| 回溯基准库 | 存量含历史对比数据的建立去年同周期基准，补全同比 |
| 预测对接 | 现有 AI 测价输出落库 data_forecast（P 类，forecaster=模型版本） |

### 1.3 P4 验收标准（06 号文档原文，原样沿用）

1. **单日处理量 ≥ 新增量**；
2. **增量文章分钟级可检索**；
3. **抽样抽检准确率达标**；
4. **预测数据开始积累**。

### 1.4 定位（用户已拍板）

- 存量数据**作为资产沉淀**进本系统：**不重写、不回改旧平台**，旧平台生产库**严格只读**（与 51bxg/秀吗红线同级的既有红线纪律）。
- 本方案只解决"把旧平台历史文章搬进本系统并结构化"这一件事；旧平台自身继续独立运行，两套系统之间不存在任何写路径。

## 二、旧平台数据形态与导入路径

### 2.1 数据量（用户已拍板）

- 旧平台存量预估**十几万篇，真实可能达几十万篇**。
- 按**批量处理**设计，**量级不设硬性上限**：方案中的批次划分、队列、成本预算均按"几十万篇"量级校核，实际量以用户导出的数据为准。

### 2.2 存储形态（用户已拍板）

- 文章由旧平台 ERP 富文本编辑器产出，正文以**一整块 HTML 字符串**存于旧库**单字段**：
  - 含编辑器注入的 **class 类名与内联 CSS 样式**；
  - **完全未拆分**（标题/正文/配图/表格等全部糅合在一块 HTML 中）；
- 旧平台前台**原样注入** article 正文区渲染，无服务端清洗。
- 对接收侧的含义：导入的正文必须先经"HTML 规整"（见第三章）才能进入现有抽取管线；不能把原始 HTML 直接当作 `data_articles.content`（现有口径中 content 为参与去重与 AI 抽取的纯文本/正文）。

### 2.3 导入方式（红线级决策，用户已拍板）

1. **不做接口导入**：不接旧平台任何 API、不连旧平台数据库取数、不做定时同步——与"51bxg/秀吗禁止数据库直连/外部接口调数"红线完全一致。
2. **人工导出两个字段（CSV）**：由用户从旧平台数据库人工导出 CSV，再导入自有的一层暂存数据库，**只导出 `article_id` 与 `article_content` 两个字段**（标题、发布时间等其他字段不在本期导入范围）；导出格式已拍板为 CSV（2026-08-23，见第六章决策项 ②），暂存方式与存储位置两项待商定。
3. **导出格式已定为 CSV**（用户已拍板 2026-08-23）：用户从旧平台数据库导出 CSV，再导入自有的一层暂存数据库；尚留两项待商定——a) 该暂存表是原地直接处理还是仅作临时表；b) 数据具体存储位置（见第六章决策项 ②）。
4. 导出文件交由本系统后，提供**一键批量导入 + 一键批量处理**两个动作（两个动作可分离触发，亦可串联）。

### 2.4 导入暂存表 import_staging（✅ 已落地，迁移 046-048）

> 导入与处理解耦的关键：先全量落暂存表，再从暂存表驱动批处理。暂存表独立于 `data_articles`，存量导入全程不直接写文章主表。
>
> 用户侧暂存数据库与本暂存表的衔接方式（原地直接处理还是仅作临时表、数据具体存储位置）**待商定**（决策项 ② 后续商定项，见第六章）。

**SQL 迁移状态**：暂存表由 `046-create-import-staging.sql`（建表）+ `047-create-batch-runs.sql`（批次日志）+ `048-refine-import-staging.sql`（索引对齐领取三谓词、import_batch_runs 增列 fail_rate/halt_reason、process_status 注释补 duplicate）落地，已在本地/飞书 dev 库执行；`050-create-import-batch-samples.sql`（P4-3 抽检样本表）已落地；编号自 046 起续号不重号，后续新迁移从 **051** 起。

**暂存表字段构想**（最终以立项评审为准）：

| 字段 | 说明 |
|---|---|
| legacy_article_id | 旧平台 article_id（原样保留，建唯一索引防重导） |
| raw_html | 旧平台 article_content 原样保留（整块 HTML，**不预清洗**——清洗规则迭代时可重放） |
| batch_no / bucket | 批次号 / 分桶标记（行业、时间段等，见第四章分桶策略） |
| parse_status | 解析状态：待解析 / 解析成功 / 解析失败 |
| process_status | 处理状态：待处理 / 处理中 / 已产出 / 失败 / 跳过（内容不可用）/ 重复（duplicate，与既有内容哈希比对命中的内容级重复，区别于唯一索引拦截的灌库级重复） |
| data_article_id | 转正后关联的 `data_articles.id`（处理成功回填） |
| error_info | 解析/处理失败原因 |
| 审计列 | `_created_at / _updated_at / _created_by / _updated_by`（飞书环境必备） |

表前缀归属（`data_` 域还是新前缀）在立项时按 03-conventions §2 前缀规范定案，不在本方案拍板。

### 2.5 解析适配层（CSV 为主，预留扩展；格式已拍板 2026-08-23）

- 设计**格式无关的解析适配层**：上层统一输入 = `{article_id, article_content}` 行流；下层按导出格式实现不同解析器。本期**只实现 CSV 解析器**，适配层接口保持格式无关，为后续格式预留扩展位。
- **CSV 适配（本期主体）**：编码兼容（UTF-8 / GBK，沿用 23 号文档 TextDecoder 回退经验）+ 大字段换行/转义处理（富文本 HTML 内含大量换行与引号，是 CSV 解析最大风险点，导入实施前专项验证）。
- **预留扩展（本期不实现）**：Excel（若启用需依赖评估，涉 package.json 依赖变更，**须用户授权**，红线 9）；其他（SQL 导出 / JSON / 分卷压缩包等）届时评估；若单文件过大，约定分卷提供。
- 通用校验：article_id 非空、article_content 非空且长度在合理区间、旧库 ID 重复检测（进暂存表前）。

## 三、HTML 规整策略

### 3.1 输入特征与目标

输入 = 2.2 所述的"一整块脏 HTML"（class 类名 + 内联样式 + 编辑器残留标签）。产出**两套规整产物**，分别服务不同消费方：

| 产物 | 处理 | 用途 |
|---|---|---|
| 纯文本版 | 剥离全部标签与样式，折叠空白，保留段落/列表的换行语义 | 参与去重哈希、AI 类型路由与约束抽取（与现有增量口径一致） |
| 结构版 | 去 class/内联样式，剥离危险与噪音标签，保留标题/段落/列表/表格等结构 | 存为 `content_html`，供 ERP 原文展示与内容生成素材（与 23 号文档 content_html 机制对齐） |

### 3.2 清洗规则（复用/对齐 23 号文档经验）

23 号文档已落地的 HTML 安全清洗（`DOMParser` 路径）可直接复用其骨架，批量侧做服务端等价实现：

- **删除**：`script / style / noscript / iframe / object / embed / link`，所有 `on*` 事件属性、`javascript:` 协议 URL；
- **剥离**：class 属性、style 内联样式、编辑器私有属性（data-* 残留按需白名单）；
- **保留**：标题层级、段落、加粗/列表、表格（表格是行情文的高频载体，结构化保真优先）；
- **图片处理**：旧库 `<img>` 多指向旧平台外链/相对路径，本系统不拉取外链资源（避免引入对旧平台的读请求）——**剥离或转占位标记**；如存量中图片承载关键报价信息，后续可评估复用 23 号文档的 `BailianService.recognizeImage` OCR 能力（qwen-vl-max）做图内文字回补，属可选项，**默认不做**；
- **标题提取**：结构版中的首个标题节点可尝试提取为 `data_articles.title`；提取不到时按 23 号文档口径取正文纯文本首行（≤40 字）补全。

### 3.3 去重口径（沿用归一化哈希，确保存量与增量同口径）

- 沿用现有口径（23 号文档第十章已确认）：`content_hash = SHA-256(${normalizedTitle}\n${content})` + `source_name` 复合唯一（`uq_data_articles_hash_source`）。
- 存量文章的哈希输入取**规整后的纯文本**（而非原始脏 HTML）——与增量富文本提交"content 取纯文本参与哈希、content_html 不参与哈希"的规则完全一致，避免样式差异导致同文异判。
- `source_name`：存量统一为"旧平台"来源名（如 `旧平台存量`，立项时确认是否新增 `dict_source_name` 条目）。
- 存量入库前先与 `data_articles` 既有哈希比对：同来源重复 → duplicate；异源同文 → 按业务决策 A2 保留并标 `duplicate_of`。

## 四、批量流水线设计（对照 06 号文档六项任务逐条展开）

### 4.1 批量流水线（跳过人工校核 / 抽样校核）

存量链路：`import_staging 待处理行 → HTML 规整 → 去重 → 类型路由 → 约束抽取 → 入库 → 图谱写入`，与增量共用同一条抽取管线（同一套 prompt、Schema、置信度×性质机制），**差异仅在入库环节跳过逐条人工校核**。

- **跳过方式**：按置信度门槛自动判定——
  - 事件轨/分析轨/预测轨：全字段高置信度且性质合规 → 直接置 **confirmed**；
  - 数据轨：沿用既有业务决策 B2（AI 直通 **active**，低置信度/异常才转 draft）；
- **抽样校核**：每批按固定比例（立项时定，建议 5% 起）随机抽样进入人工复核流，复用现有 `review.vue` 校核页面；抽检结果决定该批是否放行（见 4.4）。
- **状态衔接已拍板**（用户已拍板 2026-08-23）：批量入库记录须进入内容生成素材池——按"置信度门槛自动确认 + 分桶抽检把关，记录置 confirmed 入池"路径执行，选定方案与质量把关措施见第六章决策项 ①。

### 4.2 增量优先（双队列、不互相阻塞）

- **双队列**：增量队列（实时文章，高优先级）与存量队列（批处理，低优先级）物理分离；
- 共享资源（LLM 并发额度、数据库写入）按配额切分：存量任务只在增量空闲窗口内运行，增量到达时可抢占/暂停存量批次（批次粒度可断点续跑，依赖 staging 表的 process_status 状态恢复）；
- 验收口径直接对应 06 号原文："新文章实时处理不受存量批量影响"。

### 4.3 低置信进核验队列

- 未被自动确认的记录（中/低置信度、必填缺失、INFERENCE 性质、路由 unknown 等）**不丢弃、不硬猜**，进入核验队列（对应 P2 已建成的核验队列机制语义）；
- 队列按批次号聚合，供人工分批消化；核验通过 → confirmed 正常入库，核验驳回 → rejected（非主链状态，02 文档 5.2）；
- 队列规模随批次推进实时可见，作为成本与进度的观测面板数据。

### 4.4 分领域分桶（"每批抽检再下一批"）

- **分桶维度**（立项时按导出数据实际分布定）：行业/品类（不锈钢、铜、碳钢…）、时间段（按年/季切片）、文章类型先验（报价类/事件类/综合类）；
- **批间门禁**：每批跑完 → 抽样校核（4.1）→ 抽检准确率达标才放行下一批（抽检同时是存量记录入素材池的质量把关，见决策项 ①）；不达标则该批暂停，回查 prompt/规则后返工——这是防止"几十万篇全量污染"的核心闸门；
- 分桶同时服务于成本观测（每桶的单位成本与命中率差异显著，报价类规则命中率高、综合类依赖 LLM）。

### 4.5 回溯基准库

出处：02 号文档第九章"存量历史文章含历史基准 | 批量处理时建立回溯基准库，供未来同比计算"；06 号文档原文"存量含历史对比数据的建立去年同周期基准，补全同比"。

- 存量中含大量历史日价/周库/月产/季需事实，入库后按记录自身日期参与数据轨唯一约束与序列；
- **同比回填**：新数据入库时的同比计算自动获得"去年同周期"基准（冷启动留空标记的 yoy_* 字段，在基准补齐后可批量回填重算）；
- 实施要点：存量入库按时间顺序（先旧后新）可简化环比链计算；乱序入库则依赖现有"系统计算+待补回填"机制兜底（立项时定执行顺序策略）。

### 4.6 预测对接（AI 测价落库 data_forecast）

出处：05 号文档第五章"现有 AI 测价（/api/ai/v1/forecast）| 预测结果落库为 data_forecast（P 类），到期自动回填验证 | P4"。

- 存量中含历史行情上下文的文章处理完成后，为现有 AI 测价提供历史数据支撑；
- AI 测价输出按 02 号文档第七章落 `data_forecast`：`forecast_type=P`、`forecaster=模型版本`（区分人工预测）、`model_type=AI金LLM`、`content_source=ai_generated`；
- 与预测复盘联动（19 号文档已建成 verify/accuracy 机制）：存量补齐的历史日价为"到期回填实际值 + 误差率计算"提供验证基准，预测数据开始积累（验收第 4 条）。

## 五、成本控制

几十万篇全量走 LLM 抽取成本不可接受，采用三层降本策略（06 号文档风险对策原文："规则预抽先行，LLM 只做规则覆盖不到的部分；分批跑"）：

| 层 | 策略 | 说明 |
|---|---|---|
| 1 | **规则预抽先行** | 报价类文章高度模板化（"钢种/规格/市场 + 价格 + 涨跌"），先用正则/词典规则抽取；规则命中的字段不再过 LLM，规则覆盖率预估与分桶联动（先跑一小桶统计规则命中率） |
| 2 | **LLM 只补规则缺口** | 规则未覆盖的文章与字段才进 LLM 抽取；路由（event/data_price/mixed 判定）与混合文拆分必须过 LLM |
| 3 | **分批跑 + 断点续跑** | 按 4.4 分桶分批；批内失败不影响已入库部分；批间断点由 staging 状态恢复，不重复计费 |

**批次规模与并发/配额建议**（几十万篇量级校核值，立项时按实测调整）：

- **批次规模**：每批 500–2000 篇为宜——过小则批间抽检开销占比高，过大则抽检代表的置信区间变宽、返工代价大；
- **并发**：存量队列 LLM 并发从低起步（如 2–5 并发），确认不影响增量队列与百炼配额后逐步上调；
- **配额**：百炼调用有配额上限（参考交接归档 S-3 配额口径问题），批处理前实测日配额余量，按"当日配额 × 安全系数（如 70%）"反推当日批次上限；
- **熔断**（见第八章）：单日成本或失败率超阈值自动停批。

## 八、风险与红线

### 8.1 红线（逐条，禁止触碰）

1. **旧平台生产库只读**：本方案全程只消费用户人工导出的文件；不连旧库、不调旧平台接口、不向旧平台回写任何数据（用户拍板的定位 + 既有红线纪律双重约束）。
2. **不做接口导入**：导入路径唯一入口 = 用户上传的导出文件 → 一键批量导入；任何"自动同步/定时拉取"形态均属违规。
3. **部署冻结**：飞书 online 库冻结红线不变——存量相关迁移（046 起）先在 dev 库执行验证，未解除冻结前不碰 online 库（03-conventions 红线 4）。
4. **依赖变更须授权**：本期导出格式已定为 CSV（无新增依赖）；若后续启用 Excel 等其他格式解析需新增依赖（如 xlsx 类库），先走用户授权（红线 9）。

### 8.2 风险与熔断机制

| 风险 | 对策 |
|---|---|
| **成本失控**（几十万篇 × LLM 调用） | 熔断机制：单日成本预算上限 + 单批失败率上限（如 >10%），任一触发自动停批告警，人工介入后才可续跑；规则预抽先行压低 LLM 调用基数 |
| **百炼配额耗尽**挤占增量与问答 | 存量队列独立配额预算（见第五章）；配额不足自动降速/暂停，增量与问答链路优先 |
| **抽取质量在全量上放大**（prompt 缺陷 = 几十万篇批量污染） | 分桶批间门禁（4.4）：每批抽检达标才下一批；首桶刻意选小批量试跑；保留 staging raw_html 原文可重放，污染批可整批回滚重跑 |
| **大文件导入失败**（几十万行单文件过大） | 约定分卷导出；解析适配层支持断点续导；暂存表按导入批次隔离 |
| **富文本 HTML 导致 CSV 解析错行** | 导入实施前专项验证（2.5）；解析失败行单独落清单，不阻塞整体导入 |
| **存量与增量去重口径漂移** | 严格沿用归一化哈希口径（3.3），立项时以同一篇文章双通道入库比对验证 |
| **回溯基准顺序错误**（乱序入库致环比链断裂） | 4.5 的入库顺序策略 + 现有"待补回填"机制兜底 |
