# 17 - P2 图谱增强计划方案

> **文档目的**：记录「AI 金采集标注系统」P2 阶段「知识图谱增强」的计划过程——三个调研视角（简洁可维护 / 性能可扩展 / 最小变更低风险）的结论、被否决的备选方案（Rejected Alternatives），以及最终综合采纳的 9 阶段渐进交付方案。
> **日期**：2026-08-21
> **关联项目**：AI 金采集标注系统 · 知识图谱模块（后端 `erp/data-collect/server/kg/`，前端 `erp/data-collect/kg-graph/`，数据层 `server/database/kg.repository.ts`）
> **关联文档**：《04-知识图谱设计.md》《06-分期实施计划.md》《16-KG性能压测报告.md》《18-P2图谱增强实现记录与踩坑.md》

---

## 一、背景与目标

MVP 阶段（P1）已交付基础图谱能力：实体/关系落库（`kg_entities` / `kg_relations`，迁移脚本 `sql/040-create-kg-tables.sql`）、子图查询、实体搜索、G6 v5 可视化页。P2 阶段目标是在**不动数据模型主干、不引入运维风险**的前提下，把图谱从"能看"提升到"能治理、能深查、能演示、可度量"：

1. **契约与枚举一致性**：修复前后端契约错位、统一 entity_type 枚举；
2. **治理能力**：核验队列、实体合并/删除、归一化（词典沉淀 + 歧义队列）；
3. **查询增强**：多跳链路查询（双向 BFS）、时间过滤、类型白名单、前端筛选聚合；
4. **业务联动**：图谱实体与业务表双向引用、每日对账巡检；
5. **演示与验收**：演示模式（故事线播放）与万级节点性能压测。

---

## 二、三视角调研结论

计划阶段并行派出三个调研视角，各自独立给出方案倾向。

### 视角 A：简洁可维护

核心主张：**克制变更面，优先复用既有结构，反对新增表和大规模重构。**

| 提议 | 内容 | 最终决策 |
|------|------|---------|
| 零新增表 | 核验队列、归一化状态全部复用 `kg_entities` 既有的 `is_verified` / `status` 列表达，不新增队列表/状态表 | ✅ **采纳**（全程仅一个数据迁移脚本 042，零新增表） |
| kg-curation.service.ts 职责分离 | 建议把"查询类"（subgraph/path/search/stats）与"治理类"（merge/archive/verify/normalize）拆分为两个 service，避免单文件膨胀 | ⚠️ **部分采纳**：后端保持单一 `kg.service.ts`（17KB 内聚可接受），治理端点集中路由；拆分留待服务继续膨胀后再做 |
| 前端单文件拆分 | `kg-graph/index.vue` 当时约 1540 行，建议全量拆分为多组件 | ❌ **未全量采纳**：全量拆分回归风险高，改为局部 composables 挂接（如 `useDemoTour.ts` 抽出演示模式逻辑），主文件保留 |

### 视角 B：性能可扩展

核心主张：**用数据库原生能力解决图查询性能，提前为十万级节点做准备。**

| 提议 | 内容 | 最终决策 |
|------|------|---------|
| WITH RECURSIVE 替换应用层 BFS | 用 PG 递归 CTE 在库内完成多跳扩展，减少 JS 往返 | ❌ **未采纳**：当前 JS 层 BFS 配合 source/target 复合索引已满足交互延迟；递归 CTE 调试困难、热点节点下同样会爆炸。决策为"压测后再决定"——压测结果（见《16-KG性能压测报告.md》）确认应用层方案达标，该提议维持否决 |
| edge_time 冗余列 | 在 `kg_relations` 增加冗余时间列以支持时间区间索引过滤 | ❌ **未采纳**：时间过滤在 JS 层完成，当前边规模（三万级）下过滤耗时可忽略；冗余列引入双写一致性负担 |
| pg_trgm 搜索优化 | 为实体名称建 GIN trigram 索引，解决 ILIKE 全表扫描 | ❌ **未采纳**：飞书妙搭环境可能不支持 `CREATE EXTENSION`，属于平台红线风险；压测确认 ILIKE 在万级节点下 P50 ≈ 21ms 可接受，留作十万级后的预案 |
| 造数策略 | 压测数据按幂律度分布生成（5% 热点节点承接 80% 边）、COPY 批量导入 | ✅ **采纳**（成为阶段7 压测的方法论基础，落地为 `scripts/kg-loadtest.mjs`） |

### 视角 C：最小变更低风险

核心主张：**先摸清存量隐患，按风险排序推进，数据迁移与代码发布的顺序必须显式设计。**

关键发现：

1. **前后端契约错位 bug**：后端 `kg_relations` 查询返回的边结构缺少 `relation_type` / `confidence` 字段，前端 G6 图例按类型着色时全部匹配失败——**图例全灰**的根因即此，而非前端配色逻辑问题。
2. **entity_type 枚举不一致**：写图管线历史产出 `region` / `market` / `grade` 三类旧枚举值，与字典规范的 `region_market` / `product_grade` 不一致，同样导致图例失配。
3. **发布顺序风险**：`kg.repository.ts` 的 `createEntity` 以 `name + entity_type` 作 MERGE 查重键。若**先发代码**（写入新枚举值）而**后迁数据**（旧枚举值仍在），同名实体会因查重键不同而创建重复节点，且重复一旦发生难以无损回滚。
4. **对策**："先迁数据 → 再发代码"，并在读侧加归一映射兜底（查询返回时把旧枚举映射为新枚举），即使顺序意外颠倒也不会在展示层露出旧值。

视角 C 给出的风险排序（从高到低）：

```
实体合并（写路径最危险） > writeKg 改名 > 双向写入 > 查询增强 > 演示/压测
```

### 三视角小结

| 视角 | 一句话结论 | 贡献 |
|------|-----------|------|
| A | 能不建表就不建表，能不拆文件就不拆文件 | 零新增表约束、composables 局部抽取 |
| B | 性能优化要有压测证据，不能拍脑袋上重型方案 | 压测方法论（幂律造数 + P50/P95/P99 基准）、否决项的量化判据 |
| C | 最大的风险不在新功能，在存量数据与新代码的交接顺序 | 契约 bug 定位、"先迁数据再发代码"策略、读侧归一兜底、风险排序 |

## 三、最终综合方案

**以视角 C 为骨架（最小变更 + 显式发布顺序），吸收视角 B 的压测方法论与合并防超时策略，采纳视角 A 的零新增表约束。** 形成 9 个阶段渐进交付计划，每个阶段独立可验证、独立提交。

### 阶段计划表

| 阶段 | 任务 | 核心改动 | 风险控制点 |
|------|------|---------|-----------|
| 0 | 契约对齐 | `kg.service.ts` 查询返回补全 `relation_type` / `confidence` / `properties` / `edge_count` / `by_category` | 纯读侧追加字段，不破坏既有消费方 |
| 1 | 枚举统一 | `sql/042-normalize-entity-type.sql` 数据迁移 + `collect.service` 3 处写入字面量改新枚举 + 读侧归一映射兜底 | **先迁数据再发代码**；迁移脚本幂等可重跑 |
| 2 | 双向写入 | `writeBackBizRefs` 方法：写图成功后把实体 ID 回写业务表 related_* 字段 | 失败仅告警不阻断主管线（`.catch(() => {})`） |
| 3 | 多跳查询 | `findPath` 双向 BFS + 时间过滤 + 关系类型白名单；前端筛选面板 / 链路高亮 / 类型聚合 | JS 层实现，不改存储；前端限 depth 上限 |
| 4 | 核验队列 | `kgPost` repository 扩展 + 4 个 repository 方法 + 4 个端点（verify/queue、verify/batch、merge、archive）+ 前端核验抽屉 / 合并 / 删除 | 合并为最高风险写操作：事务包裹 + 防超时批量粒度控制（吸收视角 B） |
| 5 | 归一化 | 词典沉淀（审核通过别名入词典）+ 歧义队列 + 编辑距离候选（alias-candidates） | 零新增表，复用 is_verified / status 列（视角 A 约束） |
| 6 | 演示模式 | `useDemoTour` composable + 字幕条 + 边流光动画（lineDash 周期平移） | 动画开关独立于主图配置，不影响常规浏览 |
| 7 | 压测 | 幂律造数脚本 + 基准测试脚本 + 报告（万级节点 / 三万级边） | 造数数据带 `__LOADTEST__` 前缀，可识别可清理 |
| 8 | 对账 | `GET /api/kg/reconcile` 对账接口 + `@Cron('0 0 4 * * *')` 每日凌晨巡检 | 只读巡检，差异仅告警日志不自动修复 |

### 关键约束（贯穿全阶段）

1. **零新增表**：全部治理状态复用 `kg_entities` 既有列（`is_verified` / `status`），唯一数据变更是 042 枚举归一 UPDATE；
2. **发布顺序显式化**：任何涉及枚举/键值语义变化的改动，必须先出幂等 SQL 迁移并执行验证，再发代码；
3. **读侧兜底**：所有枚举类读取路径带归一映射，容忍历史脏值；
4. **性能决策凭压测**：WITH RECURSIVE / edge_time / pg_trgm 三项重型优化全部挂起，以阶段7 压测数据为判决依据；
5. **多智能体提交纪律**：显式路径 add、commit 前核对暂存区（详见《18》文档坑5）。

## 四、Rejected Alternatives（否决备选清单）

| # | 备选方案 | 来源 | 否决理由 | 重启条件 |
|---|---------|------|---------|---------|
| R1 | WITH RECURSIVE 递归 CTE 替换应用层 BFS | 视角 B | 压测证明应用层双向 BFS 达标（链路查询 P50 1.52ms）；CTE 调试成本高、热点节点同样膨胀 | 节点量级达十万且深跳查询 P95 > 500ms |
| R2 | `kg_relations.edge_time` 冗余时间列 | 视角 B | JS 层过滤在三万边规模下耗时可忽略；冗余列带来双写一致性负担 | 边规模达百万级且时间过滤成为热点路径 |
| R3 | pg_trgm GIN 索引优化实体搜索 | 视角 B | 飞书妙搭平台可能不支持 `CREATE EXTENSION`，触发平台红线；ILIKE 当前 P50 ≈ 21ms 可接受 | 本地/私有化部署环境 + 节点十万级 + 搜索 P95 > 200ms |
| R4 | 全量拆分 `kg-graph/index.vue`（1540 行 → 多组件） | 视角 A | 回归测试成本高、收益不成比例；改为 composables 局部抽取已解决演示模式等新增逻辑的隔离问题 | 单文件突破 4000 行或出现跨功能耦合 bug 集中爆发 |
| R5 | 拆出独立 `kg-curation.service.ts` | 视角 A | 当前 `kg.service.ts`（约 17KB）内聚尚可，治理端点集中更利于权限审计 | 治理类方法超过 15 个或引入独立治理权限体系 |
| R6 | 新增核验队列专表 / 归一化状态专表 | 视角 B/C 讨论中提出 | 违反零新增表约束；`is_verified` + `status` 组合足以表达队列语义 | 队列需要复杂排序/分派/SLA 等既有列无法表达的需求 |

## 五、验收标准

1. 图例着色与实际边类型 100% 匹配（契约对齐 + 枚举统一的联合验收）；
2. 核验队列可完成"待核验 → 通过/驳回 → 合并/删除"全闭环；
3. 链路查询成功率 ≥ 95%（压测实测 100%）、子图 depth=4 P95 < 200ms；
4. 演示模式可一键播放完整故事线，动画不影响常规交互；
5. 每日对账巡检无 ERROR，差异数可通过接口即时查询。

实际达成情况见《18-P2图谱增强实现记录与踩坑.md》与《16-KG性能压测报告.md》。
