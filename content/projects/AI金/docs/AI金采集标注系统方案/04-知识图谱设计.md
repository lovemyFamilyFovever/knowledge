# 04 — 知识图谱设计

> 目的：定义知识图谱的存储方案（PostgreSQL 实现）、节点/关系模型、多跳查询能力、网页端可视化方案。**MVP 范围**：kg 表 + 入库自动写实体/关系 + **图谱可视化页基础版（明早必须演示，5 个核心功能）**。高级功能（时间过滤/聚合/故事线/链路查询/高亮路径）P2 迭代期再做。
> **V1.3 修订**（按四轮复审意见 + 老板业务决策）：业务记录节点唯一身份约束（UNIQUE）；中间状态不新增节点类型（关系属性承载）；PREDICTS 预测对象规则；ASSOCIATED_WITH canonical ordering；实体合并关系迁移；同关系允许多条（带时间/来源）；MVP 图谱功能砍到 5 个。

---

## 一、选型结论

| 维度 | 结论 |
|---|---|
| 存储 | PostgreSQL 两张表：kg_entities（节点）+ kg_relations（边） |
| 多跳查询 | PG 递归查询（WITH RECURSIVE） |
| 可视化 | 网页端（AntV G6 图可视化引擎），后端提供图谱查询 API |
| 不采用 | Neo4j（无法在飞书妙搭运行）、向量库（无部署条件） |

**为什么 PG 足够**：
1. 图规模可控：实体几十万级、关系几百万级（PG 可承载）
2. 业务查询模式是"定向遍历"（沿 CAUSED_BY / IMPACTS 等类型边走 2-6 跳），不是全图展开
3. 关系表两个复合索引建好，4-6 跳查询预期毫秒~几百毫秒级
4. 数据模型按图设计（节点/边/属性），未来若上商业化真图库，数据可直接导出迁移

**性能承诺（审查意见采纳，收紧措辞）**：
> PG 方案作为 MVP 可行，**性能以真实数据压测结果为准**。实际性能高度依赖节点度数、边数量、关系分布、SQL 写法、索引、PG 版本、查询条件。上线前必须做一次真实数据压测（规模预估 30 万实体 / 200 万边），压测不达标再引入结果缓存 / 分片 / 升级方案。不得在压测前对外承诺具体毫秒数。

## 二、节点模型（实体 + 业务记录，V1.3 同步）

> **业务记录图谱化（P0-1 方案 A）**：kg_entities 不仅存行业实体，也承载**业务记录节点**（event / daily_price / inventory / production / demand / analysis / forecast）。业务记录入库（confirmed/active）时同步创建图谱节点，kg_relations 才能表达"Event →IMPACTS→ Price"类业务关系，成为全系统关系唯一真源。数据库结构见 02 文档 8.1。

**节点类别（五轮复审采纳：逻辑上严格区分，数据库共用一张表）**：

```
Node（kg_entities，node_category 区分）
├── entity 节点（node_category = entity）
│   ├── factory / product / region / raw_material / policy ...
├── record 节点（node_category = record）
│   ├── event / price / inventory / production / demand / forecast / analysis
```

> 产品/代码层面必须通过 `node_category` 明确"太钢（实体）"与"太钢检修事件（业务记录）"是两种节点，避免概念混淆；G6 渲染时两类节点用不同样式区分（见 5.2）。

### 2.1 节点类型（12 类实体 + 7 类业务记录）

**实体节点（12 类）**：

| 类型 | 含义 | 示例 | 关键属性 |
|---|---|---|---|
| factory | 钢厂/工厂 | 太钢、青山、宝钢德盛 | 产能、所在地、主营钢种 |
| raw_material | 原料 | 镍铁、铬铁、铁矿石 | 价格、涨跌幅、供需状态 |
| policy | 政策/法规 | 环保限产政策、出口退税调整 | 发布机构、生效日期 |
| industry | 下游行业 | 家电、汽车、厨具、建筑装饰 | 景气度、出口情况 |
| macro_indicator | 宏观指标 | 期货盘面、汇率、LME 库存 | 当前值、涨跌幅 |
| region_market | 区域/市场 | 无锡市场、佛山市场、华东 | — |
| product_grade | 产品/钢种 | 304/2B、316L、430 | 价格、规格 |
| organization | 机构/组织 | 行业协会、海关总署 | — |
| person | 人物 | 分析师、高管 | 职位 |
| project | 项目 | 港珠澳大桥、LNG 接收站 | 状态、用钢需求 |
| trade_measure | 贸易措施 | 反倾销调查、关税 | 对象、税率 |
| other | 其他 | — | — |

**业务记录节点（7 类）**：

| 类型 | 对应表 | 节点名称示例 | 关键属性 |
|---|---|---|---|
| event | data_events | EVT-20260816-001 | 影响程度、影响方向 |
| daily_price | data_daily_price | 304/2B 无锡 2026-08-16 | 价格、环比 |
| inventory | data_weekly_inventory | 无锡 304 2026-W33 | 库存量、环比 |
| production | data_monthly_production | 太钢 304 2026-08 | 产量、利用率 |
| demand | data_quarterly_demand | 家电 304 2026-Q3 | 需求量 |
| analysis | data_analysis | ANA-20260817-A001 | 解读类型、置信度 |
| forecast | data_forecast | PRC-20260817-P001 | 预测值、窗口 |

业务记录节点通过 biz_record_type + biz_record_id 与业务表记录一一对应。**唯一身份约束（四轮复审 P0 采纳）**：

- `biz_record_type`（业务记录类型）+ `biz_record_id`（业务记录 UUID）组合加 **UNIQUE 约束**：一条业务记录只能对应一个图谱节点
- 防止重复处理/重提产生双节点（业务库一条事件、图谱出现两个节点的脏数据场景）
- 业务记录 archived 时同步归档对应节点；**MVP 不支持 archived 恢复；若未来支持，业务记录状态变化需同步图谱节点状态**（archived ↔ active）

**中间状态不新增节点类型（四轮复审确认，决策 C）**：
> "减产 / 供给收紧 / 价格上涨 / 供需偏紧"等中间状态、趋势判断**不作为图谱节点**。承载方式：
> 1. 关系属性：direction（影响方向）+ magnitude（幅度）+ description（描述）表达在边上
> 2. 数据记录节点：价格涨跌由 daily_price 节点的价格/环比属性承载
> 3. 分析记录节点："供给收紧"等判断是解读结论，由 analysis 节点承载
> 模型不膨胀，演示链路更干净（见 4.1 场景 2 改写）。

### 2.2 实体命名与归一化（核心机制，非优化项）

> 审查意见采纳：`name = 标准名` 不等于 `实体唯一`。归一化从"优化项"提升为"核心机制"，否则图谱会迅速出现"太钢 / 太原钢铁 / 太钢不锈 / TISCO"四个节点。

**机制**：
1. **标准名 + 别名表**：kg_entities.name = 标准名（如"太钢"），aliases 数组存全部别名（太原钢铁集团 / 太钢不锈 / TISCO / 太原钢铁（集团）有限公司）
2. **唯一真源（V1.2 修订）**：`dict_entity_alias` = 别名唯一真源（alias → standard_name + entity_type + 确认状态）；`kg_entities.aliases` = 只读缓存，由 dict_entity_alias 回刷，禁止直接维护
3. **MVP 归一化策略（四轮复审采纳：编辑距离不承担主要职责）**：
   - **精确匹配**（标准名 + 别名完全命中）→ 自动归一
   - **别名词典**（dict_entity_alias）→ 主要机制，人工确认的别名自动沉淀
   - **编辑距离 >0.9** 仅作**候选提示**（弹人工确认"是否同实体"），不做自动判定——"青山/青山集团/青山控股"等依赖词典而非距离
4. **歧义处理**：同名不同实（如"青山"= 青山集团 vs 地名）→ 标记歧义，进人工核验队列
5. **词典沉淀**：人工确认的别名自动写入 dict_entity_alias，抽取 prompt 携带词典约束，形成正循环
6. **合并操作（四轮复审补全：关系迁移）**：两节点合并 = ① 合并 aliases 与 source_ids 到目标节点 ② **源节点的全部关系边重定向到目标节点**（source/target 中指向源节点的边全部改为目标节点，保证关系不挂到 merged 节点上）③ 源节点标记 merged（其关系归零）

## 三、关系模型

### 3.1 关系类型（12 类）

| 关系 | 含义 | 示例 |
|---|---|---|
| CAUSED_BY | 由…导致（原因） | 减产 ← 产线检修 |
| IMPACTS | 影响 | 减产 → 价格支撑 / 304 涨价 |
| LEADS_TO | 导致…趋势 | 需求回暖 → 价格上涨 |
| REFERS_TO | 关联/引用 | 解读 → 事件；预测 → 解读 |
| PRODUCES | 生产 | 太钢 → 304 |
| USES | 使用 | 家电行业 → 304 不锈钢 |
| IS_A | 属于 | 304/2B IS_A 304 |
| LOCATED_IN | 位于 | 无锡市场 → 华东 |
| ANNOUNCED_BY | 由…发布 | 环保政策 → 工信部 |
| ASSOCIATED_WITH | 相关 | 镍铁 ↔ 304 成本 |
| PREDICTS | 预测 | 预测记录 → 价格业务记录/标准实体（规则见 3.4） |
| VERIFIES | 验证 | 实际数据 → 预测记录 |

### 3.2 关系属性

| 属性 | 说明 |
|---|---|
| confidence | 抽取置信度 |
| nature | **关系性质（五轮复审采纳）**：FACT（原文明确事实，如"太钢 →PRODUCES→ 304"）/ OPINION（原文观点）/ INFERENCE（AI 推断，如"镍价上涨 →IMPACTS→ 304 价格"）。问答层可"只使用 FACT 关系回答"或"FACT + 已确认 OPINION" |
| direction | 影响方向（上涨/下跌/持平/利多/利空） |
| magnitude | 影响幅度（如 -5%） |
| time | 时间（如事件发生日期） |
| source_ids | 来源（文章/记录 ID，可追溯） |

**关系抽取纪律（五轮复审采纳）**：
- 原文明确事实 → 建 FACT 关系（正常入图谱）
- "市场人士认为…""预计…" → 建 OPINION/INFERENCE 关系（低置信度进核验队列）
- **不得把 OPINION/INFERENCE 关系与 FACT 关系混层**——这是图谱可信度的根基（与 01 数据性质纪律一致）

### 3.3 关系方向规范（必须写死，否则图谱必乱）

> 审查意见采纳：所有关系 source → target 方向统一为"语义主语 → 语义宾语"，此处写死，顺向/逆向查询都基于此规范。

| 关系 | 方向语义 | 示例（source → target） |
|---|---|---|
| CAUSED_BY | 结果 → 原因 | 减产 → 产线检修 |
| IMPACTS | 施加影响方 → 受影响方 | 检修 → 304 价格 |
| LEADS_TO | 起因 → 结果趋势 | 需求回暖 → 价格上涨 |
| REFERS_TO | 引用方 → 被引用方 | 解读 → 事件；预测 → 解读 |
| PRODUCES | 生产者 → 产品 | 太钢 → 304 |
| USES | 使用方 → 被使用物 | 家电行业 → 304 不锈钢 |
| IS_A | 具体 → 一般 | 304/2B → 304 |
| LOCATED_IN | 地点实体 → 上级区域 | 无锡市场 → 华东 |
| ANNOUNCED_BY | 文件/政策 → 发布机构 | 环保政策 → 工信部 |
| ASSOCIATED_WITH | 互相关联（无方向性，canonical ordering：UUID/标准 ID 字典序小者 → 大者） | 镍铁 → 304 成本 |
| PREDICTS | 预测记录 → 预测对象 | 预测 P1 → 304 价格走势 |
| VERIFIES | 实际数据 → 预测记录 | 实际价格 → 预测 P1 |

**规范约束**：
- **同一对节点同类型关系允许多条（四轮复审确认，决策 B）**：如"太钢 →IMPACTS→ 304"可存在多条（8 月检修影响、9 月扩产影响），每条带 time / source_ids / magnitude / direction 属性，**不合并压成一条**——不同时间、不同来源、不同事实必须各自成边
- 关系唯一性由 relation_id 保证，不去重 (source, target, type)
- 查询时同类型多条边按 time 倒序返回，可指定时间范围过滤
- 反方向查询用"逆向遍历"实现（沿边反向），不额外存反向边（ASSOCIATED_WITH 双向等价）
- 关联业务记录之间（事件↔数据↔分析↔预测）同样落入 kg_relations（REFERS_TO/IMPACTS/PREDICTS/VERIFIES），业务表引用字段由图谱回刷（02 文档 3.2 真源规则）

### 3.4 PREDICTS 预测对象规则（四轮复审确认）

> 预测对象 = data_forecast.target（结构化 JSONB：grade/spec/region/dimension/warehouse_type/industry）。

**映射规则**：
1. 预测节点 properties 存完整 target（沿用 data_forecast.target）
2. **PREDICTS 主边指向具体业务记录节点**：P 类 → daily_price 记录节点；Q 类 → inventory 记录节点；R 类 → production/demand 记录节点
3. 对应业务记录节点**不存在时**，指向标准实体节点：P/Q 类 → product_grade（+ 可另连 region_market）；R 类 → industry / factory
4. 关联方式：同一预测节点可同时连"具体业务记录节点（主边）"与"标准实体节点（补充边）"，两条边均为 PREDICTS
5. 演示效果：点开预测节点 → 顺 PREDICTS 看到"价格记录/产品/行业"——问答层直接引用（05 文档）

## 四、多跳查询能力（"前因后果"）

### 4.1 典型查询场景（V1.3 改写：中间状态不设节点，由关系属性/数据节点承载）

**场景 1：钢厂减产，为什么？**
```
问：太钢为什么减产？
答：检修事件（EVT-xxx）→IMPACTS(幅度=-8%)→ 月产记录（太钢 304 2026-08）
    解析：检修事件是月产下降的原因
```

**场景 2：太钢检修影响什么？**
```
问：太钢检修影响什么？
答：太钢(factory) →ANNOUNCED_BY/关联→ 检修事件(event) 
    →IMPACTS(方向=利多, 幅度=+2%)→ 304/2B 无锡日价记录(14200, 环比+0.35%)
    →REFERS_TO→ 解读(ANA-xxx："供给收紧，短期价格有支撑")
    →REFERS_TO→ 预测(PRC-xxx："7 日看 14500")
说明："供给收紧""价格上涨"是关系属性与数据记录承载的中间状态，不是独立节点
```

**场景 3：跨实体关联**
```
问：镍铁涨价会怎样？
答：镍铁涨价事件(event) →IMPACTS→ 304 成本（关系属性：direction=上涨）
     →IMPACTS→ 304 日价记录（环比+0.35%）
    相关事件：B 原料/成本类 3 起（镍涨价 2 起、港口库存异动 1 起）
```

**场景 4：报告素材聚合**
```
问：本月供给端发生了什么？
答：供给端事件 8 起（检修 5 + 限产 3），涉及太钢/青山/宝德，
     合计影响 304 月产约 -8%，配套解读 3 条（均 ≥3 星）…
```

### 4.2 查询实现方式（开发要点）

- 关系表建复合索引：(source_entity_id, relation_type) 与 (target_entity_id, relation_type)
- 递归查询限定深度（默认 6 跳，可配）+ 环路检测（防循环引用死循环）
- 查询模式分两类：
  - **顺向**：从起点沿关系类型找目标（如"太钢→所有 IMPACTS 目标"）
  - **逆向**：从目标找原因（如"304 减产→所有 CAUSED_BY 来源"）
- 业务层裁剪：指定关系类型白名单 + 时间范围过滤 + 数量上限，避免无界展开

### 4.3 性能预期

| 规模 | 跳数 | 预期 |
|---|---|---|
| 测试期（几百记录） | 任意 | 毫秒级 |
| 10 万文章（约 30 万实体 / 200 万边） | 2-3 跳 | 毫秒~几十毫秒 |
| 同上 | 4-6 跳 | 几十~几百毫秒 |
| 同上 | 6+ 跳 | 秒级（业务极少触发；可用深度限制 + 分次展开） |

**优化手段**（必要时）：结果缓存（同查询 5 分钟缓存）、按关系类型优先剪枝、热门实体结果预热。

## 五、网页端可视化（AntV G6）

### 5.1 为什么选 G6

| 对比项 | AntV G6 | ECharts graph |
|---|---|---|
| 交互 | 拖拽/缩放/点选/聚合展开/力导向 | 较弱 |
| 自定义样式 | 强（节点/边/动画/渐变） | 中 |
| 专业感 | 高（图谱类事实标准） | 中 |
| 工作量 | 中等 | 小 |
| 依赖 | 新增一个前端包 | 项目已有 |

**结论**：采用 AntV G6。纯前端 JS 库，在飞书妙搭前端可直接运行。

### 5.2 MVP 图谱页（明早演示，只保留 5 个核心功能）

**页面入口**：ERP 图谱页 / 文章详情页"图谱查看"入口。

**演示定位（四轮复审采纳）**：不包装成"知识图谱系统"，而是"**结构化数据之间的关系可视化**"。演示核心链路：太钢(钢厂) → 检修(事件) → 304(产品) → 价格(数据) → 解读(分析) → 预测——让老板一眼看懂业务链价值。

**MVP 功能清单（5 个，全部必须可用）**：

| 功能 | 说明 |
|---|---|
| ① 实体搜索 | 输入实体名（如"太钢"）→ 定位节点 → 自动展开其 1-2 跳子图 |
| ② 子图展开 | 点击节点 → 展开其关联节点（每次 +1 跳，逐步走通链路） |
| ③ 节点详情 | 点节点 → 右侧面板：名称/类型/别名/描述/置信度/来源记录 |
| ④ 节点/关系视觉区分 | 节点形状/颜色按类型区分（钢厂=方形、产品=圆形、区域=菱形、事件=六边形等）；边颜色按关系类型区分（CAUSED_BY=红、IMPACTS=橙、REFERS_TO=灰） |
| ⑤ 图谱规模统计 | 顶部展示节点总数/关系总数/各类型数量（演示开场用） |

**MVP 明确砍掉**（四轮复审采纳）：高亮路径、PNG 导出、平滑动画、聚合展示、时间过滤、多条件筛选、故事线播放、链路查询。链路演示通过②逐步展开实现（不需要路径 API）。

> **审查建议已采纳**：不要为"看起来炫"投入时间。MVP 页面做到"能正常演示、不卡顿"即可，价值靠业务链讲清楚，不靠动画。

### 5.3 后端图谱 API（MVP 4 个）

| 接口 | 功能 | 返回 |

## 六、图谱数据来源与写入时机

| 来源 | 写入时机 | 写入内容 |
|---|---|---|
| 事件记录（data_events） | 校核完成入库时（子记录 confirmed） | 事件节点 + 涉及实体 + IMPACTS/CAUSED_BY 边 |
| 数据记录（data_*） | 校核完成入库时（active，数据轨 AI 直通） | 数据节点 + 关联事件边 |
| 分析记录（data_analysis） | 校核完成入库时（confirmed） | 分析节点 + REFERS_TO 边（P2 起） |
| 预测记录（data_forecast） | 创建时 + 到期回填时（confirmed 后） | 预测节点 + PREDICTS/VERIFIES 边（P2 起） |
| 存量文章批量处理 | 批量流水线（P5） | 全量实体/关系 |

**注意**：rejected（放弃）的子记录不触发图谱写入；skipped（跳过）的子记录暂不写入，confirmed/active 时再写入。

## 七、图谱核验与质量

- 置信度 < 阈值（0.7）的实体/关系进"核验队列"
- MVP：核验走列表页批量确认；图谱页内合并/删除操作 P2 再加
- 命名归一化词典随业务积累（新别名自动沉淀）
- 质量抽检：定期随机抽实体/关系人工复核，统计准确率
