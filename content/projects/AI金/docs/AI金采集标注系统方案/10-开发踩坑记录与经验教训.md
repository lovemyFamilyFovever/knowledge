## 一、环境与基建类

### #1 ESLint 配置白名单冲突，阻塞全仓 pre-commit

**时间线**：P0 地基期（D1 上午），新模块目录 `erp/data-collect` 建立后首次提交。

- **现象**：`erp/data-collect` 下任何 `.ts` 文件一旦进入提交，pre-commit 钩子即报 `Parsing error: Cannot read properties ... import type`，且阻塞的是**全仓所有提交**，不只是本模块。
- **根因分析**：`eslint.config.js` 中 ERP 目录的 TS 解析器配置块采用**目录枚举白名单**（逐个列出 `erp/vip-admin/**`、`erp/xiuma-data-import/**` 等既有目录）。新目录 `erp/data-collect` 不在枚举内，其 `.ts` 文件落到默认规则，使用 espree 解析器按 JS 语法解析 TypeScript，遇 `import type` 语法直接解析失败。
- **解决方案**：将 ERP 配置块的 `files` 由目录枚举改为通用 glob：`erp/**/*.{ts,tsx}`，此后 ERP 下新增任何模块目录自动纳入 TS 解析，无需再改 lint 配置。
- **经验教训**：**共享 lint 配置的目录白名单是隐性耦合点**。任何新增模块目录时，必须检查解析器/规则的 files 白名单是否覆盖；目录枚举式配置应尽早改为通配 glob，把「新增目录要改配置」这个隐性步骤消灭。

### #2 git 并发提交事故（多次发生）

**时间线**：贯穿 D1~D2 全程，多智能体并行开发阶段反复出现，共三类形态。

- **现象**：
  1. 迁移脚本被**宽 add**（`git add .` / 目录级 add）卷入他人提交；
  2. 一次 `git reset --soft` 误操作**吞掉了其他智能体刚完成的提交**；
  3. 多智能体同时提交时 `index.lock` 被占用，提交直接失败。
- **根因分析**：多个智能体共享同一工作区与暂存区，git 暂存区是全局单例。任何 `git add .`、`git add <目录>`、`git reset` 都会作用到**整个暂存区**而非"我自己的文件"，并行场景下互相卷入、互相覆盖是必然结果，不是偶发。
- **解决方案**：
  1. 提交一律使用**显式文件路径 add**（`git add path/to/exact-file.md`），禁止 `git add .` 与宽目录 add；
  2. **提交前** `git status` + `git diff --cached --stat` 核对暂存区内容，**提交后**再核对一次；
  3. 发现暂存区存在非本人修改的文件，先 `git reset <该文件>` 摘除再提交；
  4. 遇 `index.lock` 占用时等待重试，不强制删锁。
- **经验教训**：**多智能体/多人协作必须建立"显式路径提交 + 暂存区核对"纪律**。宽 add 在单人场景是便利，在并行场景是事故源；这条纪律已沉淀为团队记忆规范（开发过程分段提交、只提交本次自己修改的文件、详细中文提交信息）。

### #3 临时文件阻塞全仓钩子（两次）

**时间线**：P1 期两次发生——第一次为 G6 冒烟脚本残留，第二次为冒烟编译产物目录。

- **现象**：所有智能体的 pre-commit 集体失败，ESLint 报出海量错误；排查发现错误源并非任何人的业务代码。
- **根因分析**：
  1. 第一次：G6 图谱冒烟验证脚本 `.tmp-kg-smoke.*` 残留在**仓库根目录**（单文件 28714 行），处于 ESLint 扫描范围内；
  2. 第二次：冒烟脚本的编译产物目录 `.tmp-smoke` 同样落在扫描范围内。
  两者均不是任何人的提交内容，但只要存在于工作区，pre-commit 的全量 lint 就会扫到，**一个人的临时文件阻塞全仓所有人的提交**。
- **解决方案**：立即删除残留文件与目录；此后约定冒烟/一次性脚本**用完即删**，或放在 `%TEMP%`、`node_modules` 等 lint 忽略区，不进入工作区扫描范围。
- **经验教训**：**临时产物严禁进入工作区扫描范围**。一次性验证脚本的生命周期要在编写时就规划好退出路径（放哪、何时删），而不是"跑通了再说"。

### #4 僵尸进程阻塞演示环境

**时间线**：彩排前环境准备阶段。

- **现象**：后端服务看似在监听 `:8000`，但 Vite 代理请求全部无响应，前端页面长时间转圈。
- **根因分析**：一个旧的 node 进程（PID 34364）残留在系统进程表中，以**单栈 IPv6** 方式监听 `:8000`，端口被它占用但它已不处理请求；新启动的服务无法绑定该端口。开发沙箱环境无 `taskkill` 权限，无法程序化结束该进程。
- **解决方案**：最终由用户在任务管理器中手动结束该进程后重启服务恢复。
- **经验教训**：**演示环境的服务需要健康检查与守护机制**（启动前探测端口是否被无响应进程占用、进程带启动时间戳便于识别僵尸）。同时记录在案：沙箱权限有限时，进程级故障需要人工兜底通道，排障前先想好"谁来杀进程"。

### #5 SQL 迁移编号撞车

**时间线**：P0 地基期，编写建表迁移脚本时。

- **现象**：方案文档声明「新脚本从 034 起」，但创建 `034-create-*.sql` 时发现编号已被占用。
- **根因分析**：`server/database/sql/` 下 `034-create-feishu-user-bindings.sql` 已被其他任务先落库；方案文档写作时未实测代码库当前最大编号，凭记忆/旧快照写了 034。
- **解决方案**：本系统全部迁移脚本实际从 **035** 起编号；文档同步更正。
- **经验教训**：**文档声明的编号、版本、路径等一切"环境事实"，必须以代码库实测为准**，写文档时先 `ls` 一下真实目录，不凭记忆落笔。

### #6 pg 包缺失且红线禁改 package.json

**时间线**：P0 地基期，编写迁移执行工具时。

- **现象**：计划用 `pg` 包编写数据库迁移执行脚本，`require('pg')` 直接失败。
- **根因分析**：项目依赖中没有 `pg`；而本项目红线规定**禁止修改 package.json**（不得新增依赖）。
- **解决方案**：改用项目已有的 `postgres-js`（postgres 包）实现迁移执行逻辑，零新增依赖。
- **经验教训**：**动手写代码前先盘点既有依赖**，红线约束（禁改 package.json）下优先复用已有能力；依赖可用性检查应放在方案设计阶段而不是编码阶段。

## 二、后端类

### #7 NestJS Guard 依赖注入导致启动崩溃

**时间线**：P1 后端期，采集后端模块首次启动。

- **现象**：新模块启动即崩溃：`Nest can't resolve dependencies of the ErpAuthGuard`。
- **根因分析**：`ErpAuthGuard` 的构造函数注入 `ErpAuthService`，而 `ErpAuthService` 所在模块**并非 @Global**。任何使用 `ErpAuthGuard` 的模块，必须在自己的 `providers` 中同时注册 `ErpAuthGuard` 与 `ErpAuthService` 二者，否则 DI 容器解析失败。
- **解决方案**：参照既有正确写法 `xiuma-sync.module.ts`，在采集模块的 `providers` 数组中同时声明 `ErpAuthGuard` 和 `ErpAuthService`，启动恢复正常。
- **经验教训**：**复用 Guard/Service 时先看它的 DI 依赖链**；项目内已有"标准姿势"（xiuma-sync.module.ts）时照抄先例，不自行发明。该教训已沉淀为团队记忆。

### #8 BailianService 真实签名与方案文档不符

**时间线**：P1 后端期，实现 LLM 抽取调用时。

- **现象**：按方案文档写法调用 `askFastSync(question, sessionId)`，TypeScript 类型检查报错 / 运行时参数错位。
- **根因分析**：源码真实签名是三参：`askFastSync(question, history: Array<{role, content}>, sessionId)`，方案文档（09-开发实施提示词）误写成两参。文档是"二手信息"，源码才是权威。
- **解决方案**：以源码为准，调用时显式传入 history（无历史时传空数组）：`askFastSync(prompt, [], 'collect-extract')`。
- **经验教训**：**调用既有服务一律以源码签名为准**，方案文档中的 API 示例仅供理解意图；方案文档中的接口签名错误已回写修正，避免二次误导。该教训已沉淀为团队记忆。

### #9 Drizzle `ANY` 数组序列化 bug（图谱接口恒 500）

**时间线**：P1 后端期，图谱子图接口联调时。**这是本次开发中最隐蔽的一个 bug。**

- **现象**：`KgRepository.getSubgraph` 接口**恒定 500**，PostgreSQL 报 `22P02`（invalid input syntax），无论传什么参数都复现。
- **根因分析**：代码使用 Drizzle 的 `sql` 模板手拼 `col = ANY(${values})`。Drizzle 的参数序列化会把 JS 数组当作**单个 JSON 字符串参数**绑定，而不是 PG 数组参数；PG 收到的是一个字符串去跟数组类型做 ANY 比较，必然 22P02。这类错误在 SQL 层面合法、在类型层面才爆炸，单看代码很难察觉。
- **解决方案**：弃用手拼 `ANY`，改用 Drizzle ORM 提供的 `inArray(col, values)`，参数序列化由 ORM 正确处理，接口恢复。
- **经验教训**：**数组参数必须走 ORM 提供的 `inArray`，严禁手拼 `ANY(${arr})`**。ORM 的参数序列化边界是暗坑高发区，凡是"把变量塞进 sql 模板"的写法都要警惕。该 bug 经 leader 授权后由本团队代为修复（见自主决策点 D3）。

### #10 LLM 异步管线与 watch 热重启冲突

**时间线**：联调彩排期。

- **现象**：文章提交后进入 `processing` 状态即**永久卡住**，不再推进到抽取完成。
- **根因分析**：抽取管线以 fire-and-forget（`setImmediate` 异步、不等待）方式挂在请求进程内；开发模式 `npm run dev:server` 的 watch 模式检测到文件变化后**热重启整个进程**，正在跑的 LLM 异步管线被直接杀掉，文章状态停在 `processing` 无人善后。
- **解决方案**：
  1. 短期：文章级 **retry 兜底**——前端/后端可对卡住的文章重新触发管线，状态恢复推进；
  2. 操作纪律：演示与彩排期间**不修改后端文件、不触发热更新**。
- **经验教训**：**进程内 fire-and-forget 任务没有生命周期保障**，任何热重启/重部署都会杀掉它。演示环境要冻结代码变更；长期方案需要任务状态可恢复（状态机 + retry），而不是假设进程一直活着。

### #11 前后端契约错配（彩排发现 4 处致命）

**时间线**：彩排当天集中暴露。**这是本次开发付出代价最大的一类问题。**

- **现象与逐条根因**：
  1. **`workbench/todos` 返回形状与前端预期不符** → 前端渲染直接崩溃，**整个页面冻结白屏**（根因：前端对数组/对象无防御，后端形状变了没人知道）；
  2. **文章详情字段命名与形状错配**：后端返回 camelCase，前端按 snake_case 读取 `sub_records` / `ai_draft`（根因：两端各写各的字段名，无共享契约）；
  3. **`records/mine` 对象 vs 数组**：后端返回包裹对象，前端当数组 `.map`（根因：同上，契约只存在于口头）；
  4. **提交后不触发抽取管线**：前端提交成功但文章永远停在待处理（根因：后端提交接口只落库不启动 route→extract 管线）。
- **解决方案**：
  1~3. 以**接口契约文档**为唯一权威逐一修正形状与命名，前端补充对返回结构的防御性校验；
  4. 后端 `submitArticle` 内增加 `setImmediate` fire-and-forget 触发 route→extract 异步管线（配合 #10 的 retry 兜底）。
- **经验教训**：**前后端必须以同一份接口契约文档为准，并做浏览器级 E2E 验证**。API 层冒烟（curl 通了、状态码 200）不能替代 UI 契约验证——形状错了但 HTTP 200 的接口，只有在真实渲染时才会爆炸。彩排不是找麻烦，是最后一道防线。

### #12 渠道×风格键值不一致（E5002）

**时间线**：联调彩排期，内容工坊首次真实调用。

- **现象**：内容生成请求返回错误码 `E5002`（渠道/风格组合不在兼容矩阵内），但前端选的组合看起来完全合法。
- **根因分析**：后端兼容矩阵以**中文键**为准（`公众号` / `新闻简讯`），前端发送的是**英文键**（`wechat` / `brief`）。后端矩阵查不到英文键，判定非法组合。
- **解决方案**：**后端契约保持权威不改**，在前端增加映射层：`config.ts` 维护「英文键 ↔ 中文键」映射表，`request.ts` 在请求出口统一转换为中文键再发送。
- **经验教训**：**枚举键值必须在契约文档中统一定义**；出现两端不一致时，原则是"后端契约为权威、前端做适配层"，避免动后端矩阵引入连带风险。

### #13 tsconfig.node.json include 缺失，新模块游离在类型检查之外

**时间线**：P0 地基期，type:check 例行检查时发现。

- **现象**：`erp/data-collect/server/**` 下的 TS 错误在 `npm run type:check` 中完全不出现——不是没错误，是**根本没被检查**。
- **根因分析**：`tsconfig.node.json` 的 `include` 不含 `erp/data-collect/server/**`；该模块的后端代码注册进 `app.module.ts` 之后才间接进入编译覆盖，此前一直是类型检查盲区。
- **解决方案**：在 `tsconfig.node.json` 的 `include` 中显式追加 `erp/data-collect/server/**`，随后修复暴露出的全部类型错误。
- **经验教训**：**"检查没报错"≠"没有问题"**，新模块建立后要主动验证它是否进入了 lint / type-check / 测试三张网；include 白名单与 #1 的 ESLint 白名单是同一类隐性耦合，新增目录必须逐一核对。

### #14 ts-node 不解析 tsconfig paths（冒烟脚本依赖解析失败）

**时间线**：P1 后端期，编写后端独立冒烟脚本时。

- **现象**：冒烟脚本用 ts-node 启动即报模块找不到——`@/` 或项目别名路径全部解析失败；即便解析通过，独立 Nest app 启动又报缺少 `WafBypassModule` / `ErrorLogModule` 相关依赖。
- **根因分析**：两个叠加问题：
  1. ts-node **默认不读取 tsconfig 的 paths 别名**；
  2. 独立启动的精简 Nest app 没有装载完整 `app.module` 的依赖链，而 `AiModule → ProxyModule` 依赖 `WafBypassModule` 与 `ErrorLogModule` 提供的服务。
- **解决方案**：
  1. 冒烟脚本内用 alias hook **劫持 `Module._resolveFilename`**，手工把别名映射到真实路径；
  2. 独立 app 的 imports 中显式补齐 `WafBypassModule` + `ErrorLogModule`，满足 AiModule→ProxyModule 依赖链。
- **经验教训**：**脱离主入口启动应用（冒烟/测试/独立工具）时，别名解析与模块依赖链都要手工重建**；写冒烟脚本前先列出目标模块的完整 imports 依赖树。

### #15 numeric 列种子数据写 "+0.35%" 报 22P02

**时间线**：P0 地基期，插入演示种子数据时。

- **现象**：种子数据 INSERT 报 `22P02 invalid input syntax for type numeric`。
- **根因分析**：种子数据为了"好看"把涨跌幅写成 `"+0.35%"`（带加号与百分号），但目标列是 `numeric` 类型，PG 只接受纯数字字符串。
- **解决方案**：种子数据改为纯数字字符串（如 `"0.35"`），符号与百分号由前端展示层负责格式化。
- **经验教训**：**展示格式与存储格式分离**：数值列只存纯数字，任何修饰（+/-、%、单位）都属于展示层职责；种子数据同样要走真实约束检验，不能因为是"假数据"就放松格式。

### #16 守卫冒烟乌龙：先最小复现再下结论

**时间线**：P1 后端期，ErpAuthGuard 鉴权冒烟验证时。

- **现象**：冒烟脚本断言"不带 token 应返回 401"失败，初步结论指向"守卫没生效"，险些去改守卫代码。
- **根因分析**：**冒烟脚本自身的 bug**——脚本里 TOKEN 变量赋值后，请求函数已自动附带鉴权头，所谓"不带 token 的请求"其实带了 token。守卫行为完全正确。
- **解决方案**：修正冒烟脚本的请求构造，401 断言按预期通过；守卫代码零改动。
- **经验教训**：**断言失败先怀疑测试本身，最小复现后再下结论**。"测试说生产代码有 bug"和"测试自己有 bug"在现象上无法区分，唯一鉴别手段是把被测行为剥离到最小闭环单独验证。这次乌龙如果直接动手改守卫，会引入真正的 bug。

## 三、前端类

### #17 G6 v5 与 4.x API 全面不兼容

**时间线**：P1 前端期，图谱可视化页开发全程。

- **现象**：按网上教程与旧文档编写的图谱代码全面报错：`modes` 配置不存在、`graph.addNode` 不存在、事件对象取不到节点 id、节点状态设置方法不存在。
- **根因分析**：项目安装的是 **AntV G6 v5**，与 4.x 相比是破坏性重构：
  - `modes` 概念取消，改为 `behaviors`（交互）+ `plugins`（插件）分开声明；
  - 增量渲染不再是 `addNode`，而是 `addNodeData` + `render()`；
  - 节点数据结构变为 `{ id, data: { ... } }`，业务属性全部收进 `data`；
  - 状态与聚焦 API 变为 `setElementState` / `focusElement`；
  - 事件中取节点标识为 `e.target.id`。
- **解决方案**：**以 `node_modules` 中 G6 v5 的 TypeScript 类型定义为唯一权威文档**逐一对齐 API；因图谱视觉效果无法在无头环境验证，改用 **jsdom 冒烟脚本做 23 项断言**（数据结构、API 调用链、事件回调）替代视觉验证，真实视觉效果由彩排截图确认。
- **经验教训**：**大版本破坏性升级的库，旧文档/教程全部作废，类型定义与官方 changelog 才是依据**；无法视觉验证时，用结构化断言覆盖"逻辑正确性"，把"视觉正确性"留给真实环境，两层验证各司其职。

### #18 ERP 页面技术栈纠偏：Element Plus 而非 Tailwind

**时间线**：P1 前端期，采集工作台页面开工前的方案确认。

- **现象**：开发提示词写「前端用 Vue 3 + TS + Tailwind v4」，若照此实现，新页面将与既有 ERP 页面风格、组件体系完全割裂。
- **根因分析**：既有 ERP 后台页面（vip-admin、xiuma-data-import、cache-admin 等）统一使用 **Element Plus 组件库 + `<style scoped>` 原生 CSS**，项目主站（client/src）才用 Tailwind；ERP 目录是独立的样式体系。
- **解决方案**：采集标注系统全部 ERP 页面统一采用 **Element Plus 组件 + scoped CSS**，禁用 Tailwind 工具类，与既有 ERP 页面保持一致。
- **经验教训**：**同一仓库存在多套样式体系时，新页面先确认"落在哪个体系"**，以同目录既有页面为样板；"项目技术栈"这种全局描述在混合仓库里不可靠，必须落到具体目录确认。该教训已沉淀为团队记忆。

## 五、总结：五条可复用的团队纪律

1. **白名单三查**：新增模块目录后，必查 ESLint files、tsconfig include、lint 忽略区三张网是否覆盖（#1、#3、#13）。
2. **显式路径提交**：多智能体并行只加自己改过的文件，提交前后核对暂存区（#2）。
3. **契约文档为唯一权威**：前后端字段形状、枚举键值以接口契约文档为准，用浏览器级 E2E 验证，API 冒烟不算数（#11、#12）。
4. **源码优先于文档**：调用既有服务以源码签名与类型定义为准，方案文档可能是过时的二手信息（#5、#8、#17）。
5. **先怀疑测试，再怀疑系统**：断言失败先最小复现，临时文件用完即删，进程内异步任务要有 retry 兜底（#3、#10、#16）。
