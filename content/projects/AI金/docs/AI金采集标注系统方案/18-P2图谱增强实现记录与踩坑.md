### 阶段实现要点补充

- **阶段 0/1/2 合并为一个基线 commit（50bbaec）**：三者都服务于"图例正确着色 + 引用闭环"这一最小可见目标，拆开单独验证反而需要重复造数据。
- **阶段 3 链路查询**：双向 BFS 从两端同时扩展、在中间相遇即停，配合 maxDepth 上限；时间过滤与类型白名单在 JS 层对邻接边做前置裁剪，减少扩展扇出。
- **阶段 4 实体合并**是全程风险最高的写操作：合并需把被并实体的关系边改挂到目标实体、去重后软删被并方，全部在事务内完成；批量核验采用小粒度分批提交防超时（妙搭 30 秒语句限制的既有教训）。
- **阶段 8 对账规则**：业务表引用的实体须在图谱中存在且 active（兼容 UUID 主键与 entity_id 两种格式——`writeBackBizRefs` 经 `extEntityId` 兜底写入）；差异只打 warn 日志与接口返回，不做自动修复。

## 二、踩坑记录

### 坑1：SQL 迁移编号冲突

- **现象**：计划文档中写"新脚本从 041 起"，但执行时发现 `041-create-collect-dict-admin-tables.sql` 已被词典动态管理功能占用（041 与 042 均于 2026-08-21 前序任务中新增）。
- **根因**：计划编写时的编号认知过期，未以目录实际清单为准。
- **解决**：枚举归一脚本顺延为 `042-normalize-entity-type.sql`，并在脚本头注释中写明"原计划 041，因占用顺延为 042"。
- **教训**：**生成迁移脚本前必须 `ls server/database/sql/` 核实当前最大编号，不能依赖文档或任务描述中的编号提示。**（本系列文档当前最大编号同样需现场确认，本文即为顺延后的 17/18。）

### 坑2：entity_type 改名的 MERGE 查重键冲突风险

- **现象（潜在，未实际发生）**：`kg.repository.ts` 的 `createEntity` 以 `name + entity_type` 作 MERGE 查重键。若代码先部署（写入新枚举 `region_market`）但数据未迁移（库内仍是旧枚举 `region`/`market`），同一实体会因查重键不同而**创建重复节点**。
- **根因**：查重键包含正在被迁移的语义字段，迁移窗口期内新旧代码并行必然产生分叉。
- **解决**：
  1. 严格执行"**先迁数据 → 再发代码**"：先跑 042 幂等 UPDATE 并核验无残留，再部署新字面量代码；
  2. **读侧归一映射兜底**：查询返回时统一把旧枚举映射为新枚举，即使顺序意外颠倒，展示层也不会露出旧值或图例失配。
- **教训**：任何以"枚举值/键值语义"为查重键的 upsert 逻辑，在枚举变更时必须显式设计迁移顺序，并在读侧留兜底映射。

### 坑3：Drizzle alias JOIN 类型缺失

- **现象**：核验队列需要 JOIN `kg_entities` 获取关系边的 source/target 实体名称；node_modules 裁剪后 `drizzle-orm` 的 `alias.d.ts` 类型文件缺失，alias JOIN 写法直接类型报错，无法通过编译。
- **根因**：依赖裁剪环境下 ORM 的类型定义不完整，alias 类型推导链断裂。
- **解决**：放弃 alias JOIN，改用**标量子查询**（在主查询的 select 中内嵌按 id 取 name 的子查询）获取实体名称，绕开 alias 类型依赖，语义等价且编译通过。
- **教训**：在依赖受限环境（裁剪 node_modules、平台打包约束）下，优先选择不依赖复杂类型推导的 SQL 写法；子查询是 JOIN alias 的可靠降级路径。

### 坑4：前端图谱页 G6 v5 动画配置

- **现象**：`kg-graph/index.vue` 的 G6 实例当前配置 `animation: false`；全局开启动画后，既有状态切换（筛选重绘、选中高亮等）出现兼容性问题。
- **解决**：**演示模式独立控制动画开关**——常规浏览保持 `animation: false` 的确定性渲染，仅演示播放期间启用动画；边流光效果用 `lineDash` + `lineDashOffset` 周期平移实现，不依赖 G6 全局动画管线。
- **教训**：可视化库的全局动画开关是"广播式"配置，影响所有状态迁移；新增动画场景应做局部隔离（独立开关 + 手工驱动的样式周期），避免回归既有交互。

### 坑5：多智能体 Git 并发提交冲突

- **现象**：Taylor / Felix / Robin 等多个 Agent 并行开发 P2 各阶段时，出现暂存区互相污染（他人 `git add .` 带入无关文件、reset 误伤暂存内容、index.lock 阻塞）的风险。
- **解决**（形成固定纪律）：
  1. 每次 commit 前执行 `git diff --cached --name-only` 核对暂存区，发现非己文件立即 `git restore --staged <file>` 剔除；
  2. **只用显式路径 `git add file1 file2`，禁止 `git add .`**；
  3. 遇 index.lock 等待 10-30 秒重试，不强删锁文件；
  4. 提交信息写详细日志（改动内容 + 原因），便于回滚追溯。
- **教训**：多智能体并行 = 多人协作的极限放大版，Git 纪律必须前置写进任务要求，而不是事后补救。

## 三、经验教训沉淀

1. **数据迁移与代码发布的顺序是一等公民**：只要改动涉及查重键/唯一键的语义字段，就必须把"先迁数据还是先发代码"写进方案，并配读侧兜底映射双保险（坑2）。
2. **编号类约定永远以现场目录为准**：SQL 迁移编号、文档编号、菜单 ID 等共享序号资源，使用前必须列目录核实，计划文档里的编号随时会过期（坑1）。
3. **性能优化先造证据再动手**：WITH RECURSIVE / pg_trgm 等重型方案在压测数据面前全部挂起或否决；幂律造数 + P50/P95/P99 基准是可复用的判决方法（阶段7，详见《16-KG性能压测报告.md》）。
4. **全局配置开关要做场景隔离**：G6 动画、轮询定时器等全局开关，新功能接入时优先独立控制，避免污染既有行为（坑4）。
5. **依赖受限环境下选"笨"一点的写法**：标量子查询替代 alias JOIN、前端轮询替代 SSE——在类型/平台约束下，语义等价的简单写法胜过精巧依赖（坑3）。
6. **零新增表约束倒逼了更好的列复用设计**：`is_verified` + `status` 组合表达核验/歧义/归档等全部队列语义，避免了表数量膨胀；确需新列时也优先评估既有列的组合表达力。
7. **治理类高危写操作（实体合并）必须事务 + 小批量**：既防中途失败产生半合并状态，也防单语句超过平台 30 秒限制。
