# 15. 词典动态管理方案

> 目标：让同事（非开发）可对采集/标注/内容生成所用的枚举词典做增删改查，新增分类、字段后无需改代码即可在系统中动态体现。

## 一、现状分析：词典来源盘点

### 1.1 后端（已是动态，唯一真源在数据库）

`collect.service.ts loadDicts()` 一次加载 **12 张 `dict_*` 表**并做 5 分钟内存缓存，`getDicts()` 对外提供 `/api/collect/dicts` 接口：

| dict 表 | 用途 | 消费处 |
|---|---|---|
| dict_event_category / dict_event_sub_category | 事件大类 / 子类 | prompt + 前端级联 |
| dict_grade | 钢种 / 品种 | prompt + 前端下拉 |
| dict_region | 区域 | prompt + 前端下拉 |
| dict_tax_status | 含税状态 | prompt + 前端下拉 |
| dict_industry_category | 品类（不锈钢/铜/碳钢） | 后端已读，**前端未消费** |
| dict_inventory_type / analysis_type / forecast_model | 库存 / 解读 / 预测 | **仅后端读，前端未消费** |
| dict_channel / dict_article_style | 分发渠道 / 文章风格 | **仅建表，前后端均未消费** |
| dict_entity_alias | 实体别名归一 | 图谱写入 |

**结论：后端数据来源健康，具备"从数据库动态获取"的底座。**

### 1.2 前端（存在多处硬编码 / 未接入）

`field-config.ts` 中 `DICT` 用硬编码兜底，`loadDictsFromApi()` 成功后仅覆盖 **grade、grade_short、region、tax、事件大类、事件子类** 6 项；以下仍为**纯硬编码**：

| 位置 | 硬编码内容 | 问题 |
|---|---|---|
| field-config.ts `MARKET_OPTIONS` | 市场（无锡市场/佛山市场…） | **无 `dict_market` 表** |
| field-config.ts `DIRECTION_OPTIONS` | 影响方向 E10（利多/利空/中性） | **无 `dict_impact_direction` 表** |
| field-config.ts `UNIT_OPTIONS` | 计价单位（元/吨…） | **无 `dict_unit` 表** |
| field-config.ts DAILY_PRICE `I-C` 品类 | 硬编码 `[OPT('不锈钢')]` | 有 `dict_industry_category` 表但**前端没用** |
| content-studio/config.ts `CHANNELS`/`STYLES`/兼容矩阵 | 渠道 + 风格 | **完全未对接前端**，只有常量 |

> ⚠️ **依赖风险**：字段下发仍绑死在 `EVENT_TEMPLATE` / `DAILY_PRICE_TEMPLATE` 的静态 `options`，`DICT` 只做"渲染源"。当 API 失败静默回落时，前端兜底类别命名（A·钢厂生产检修）与数据库（A·钢厂/工厂）**语义不一致**，存在错位隐患。

### 1.3 硬编码 vs 动态 结论

- **已经动态**：后端全部字典 + 前端 grade/region/tax/事件分类。
- **仍是硬编码**：市场、影响方向、单位、日报"品类"、内容生成渠道、文章风格。
- **管理端**：从零。
- **一致性风险**：前端兜底命名与数据库语义漂移。

## 二、可行性评估：可行，且有必要

**判断：可行，值得做。** 理由：

1. **底座已就绪**：后端已统一从 12 张 dict 表读，缺的只是"补表、补前端接入、加 CRUD 管理"三件事，无结构改造。
2. **真实痛点**：目前市场/方向/单位/品类/渠道/风格一旦要加新值（如新增铜品类、新增"抖音极速版"渠道），必须改前端代码 + 改 prompt 兜底，无法由同事自助。
3. **收益匹配投入**：管理页 + CRUD 接口的投入可控，收益是"新增分类/字段零开发"。

**方案边界（明确不做）：**
- 不引入通用的"任意字段配置引擎"——只对**已有 dict 表 + 补齐 4 张缺失表**提供 CRUD，避免过度设计。
- 不做字段级权限/多租户。
- 词典变更一次生效后，靠"写库即清缓存 + 前端刷新令牌"保证一致，不追求实时推送。

## 三、方案设计

### 3.1 数据层：补齐缺失词典表（一次迁移"041"）
<!-- 2026-08-23 更新 -->
> ✅ **已执行**：041 迁移已落地（4 张词典表已建），后续词典变更迁移编号从 **046** 起（当前上限 045）；新增表禁用 `dict_` 历史前缀，须用合规前缀（见 AGENTS.md）。

新增 4 张表，与现有 dict 表同构（id/name/code?/sort_order/remark/审计字段）：

- `dict_market`：市场
- `dict_impact_direction`：影响方向（利多/利空/中性）
- `dict_unit`：计价单位
- `dict_entity_type`：实体类型（状态标注用，可选）

> 已有 `dict_industry_category` 继续作为日报"品类"来源，无需新表。

### 3.2 后端：在现有 collect 模块扩展 CRUD（复用 DICT 底座）

**复用：** `loadDicts()` 已集中读取全部 dict 表 → 改为统一入口 `DictService`，把"读"的 T 型定义收敛，CRUD 都走同一个表注册表（`DICT_REGISTRY`：表 → 字段元数据）。

**新增接口**（`/api/collect/dicts` 下，统一鉴权 ErpAuthGuard）：
- `GET /dicts`（已有，保持兼容，返回全量）
- `GET /dicts/tables`：列出可管理的词典表清单 + 当前值（管理页左侧）
- `POST /dicts/tables/:table/items`：新增
- `PUT /dicts/tables/:table/items/:id`：修改
- `DELETE /dicts/tables/:table/items/:id`：删除
- `POST /dicts/refresh`：**清空 loadDicts 5 分钟缓存**（配合管理页"保存后立即生效"）

**缓存一致性：** 写操作成功后调用 `this.clearDictCache()`，使下一次 `loadDicts()` 读到新值；前端不再需要等 5 分钟。

### 3.3 前端：补齐硬编码接入 + 管理页

**a) 打通字段下发（field-config.ts）**
- 新增 `DICT.marketOptions / directionOptions / unitOptions / dailyCategoryOptions`。
- `loadDictsFromApi()` 增加从 `/dicts` 响应映射 market、industry_category（→ 日报品类）、impact_direction、unit。
- 日报 `I-C 品类` options 改为 `DICT.dailyCategoryOptions`（不再写死 `不锈钢`）。
- **一致性修复**：前端兜底 `EVENT_CATEGORIES`/`SUB_BY_CATEGORY` 改为与数据库种子一致，消灭错位。

**b) content-studio 接入词典**
- `config.ts` 的渠道/风格从 `DICT.channels / DICT.articleStyles` 派生，保留本地"兼容矩阵/文案/色板"作为展示元数据（不迁移进字典，避免过度设计）。
- 渠道/风格列表运行时可被管理。

**c) 词典管理页（新菜单 "词典管理"，采集标注组，采集工作台下方）**
- 左侧：词典表清单（tab）；主体：增删改查 + sort_order 排序 + remark 备注。
- 保存后调 `POST /dicts/refresh` 并重拉，提示同事"立即生效"。
- 采用现 ERP 后台风格（Element 常规布局），不做炫技。

## 五、风险与控制

- **反向风险（删除/改名）**：删除在用词典值会造成历史已标注数据出现游离值。→ CRUD 的删除仅作"停用"（软删除 flag 或降级提醒），改名提供批量迁移提示，不硬删。
- **命名漂移**：前端兜底与 DB 种子已修平，后续统一以 DB 为唯一真源，减少双写。
- **缓存**：后端 5 分钟缓存 + 管理端 refresh 双保险；前端刷新令牌在启动时重拉一次。
- **不做过度设计**：不建通用字段引擎、不做多租户，满足"同事可自助维护词典"为核心目标。
