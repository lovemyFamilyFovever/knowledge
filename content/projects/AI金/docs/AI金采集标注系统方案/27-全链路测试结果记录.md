## 三、测试中发现的问题 / 偏差（重点）

### F1【文档过时】端口 3000 实际为 5173/8000
- 现象：文档前置条件写 `http://localhost:3000`，实际后端 8000、前端 5173（start-local.bat + vite.config.ts）。
- 影响：按文档无法访问，需修正。
- 处置：测试按实际端口执行。

### F2【状态命名差异】提交后状态为 `pending`，非文档的 `pending_route`
- 现象：`POST /api/collect/articles` 返回 `status:'pending'`，文档预期 `pending_route`。
- 代码事实：collect.service.ts 初始状态即 `pending`；`pending_route` 仅存在于路由推进判断中。
- 判定：功能正常，属文档表述与实际状态机不一致，建议文档修正。

### F3【真实 AI 路由不稳定 + 成本隐患】文章 A 路由失败 E1001，消耗 28440 tokens
- 现象：`POST /articles/:id/route` 对"太钢检修+304涨价"文章返回 `{route:'unknown', confidence:0, errorCode:'E1001'}`，提示人工选择；但该次调用消耗 **28440 tokens**。
- 对比：文章 B（日价表）路由成功 data_price 0.95（34301 tokens）、文章 C（混合）成功 mixed 0.95（34697 tokens）。
- 风险：**单次失败的路由调用无产出却消耗约 2.8 万 tokens**，批量场景下成本不可控；需评估失败时是否可降级/降成本（如用更小模型或本地规则预判）。
- 备注：mock 兜底已于 2026-08-24 移除，失败强制人工改判（设计如此），但成本问题值得关注。

### F4【行为差异】路由确认后自动触发抽取，非文档所述手动"点击 AI 抽取"
- 现象：`route-confirm` 成功后系统 fire-and-forget 自动执行抽取（collect.service.ts 注释"状态推进为 pending_extract 后 fire-and-forget 触发抽取管线"）。
- 实际观察：A confirm 后立即产生 1 条 event draft；B confirm 后产生 4 条 daily_price（全部 active）；C confirm 后产生 1 event draft + 2 daily_price active。
- 影响：与文档 TC-03"点击 AI 抽取按钮"描述不符；UI 上可能没有手动抽取入口或已改为自动。需与文档对齐。

### F5【环境并发干扰】todayNew 0→5，超出本次提交的 3 篇
- 现象：提交 3 篇后 `todayNew` 显示 5、`pendingReview` 9→14。
- 影响：测试数据计数可能受环境其他活动（如定时任务/他人操作）干扰，做增量断言时需排除。

### F6【抽取自动触发后再手动重抽兜底】文章 A event 组件首抽失败被静默吞掉
- 现象：文章 A（太钢检修）首轮抽取 `event` 组件失败，仅生成 `daily_price` 记录；通过手动调用 `records/:id/retry` 重抽后才生成 `event` draft。
- 代码事实：组件失败在管线中 `catch` 吞掉，不阻断整体（设计如此），但失败原因未透出到前端。
- 影响：人工改判/复核时可能漏看"某组件未抽取"的状态；建议 UI 对组件缺失给出提示。

### F7【状态更新不彻底】人工改路由后 mixed_components 残留
- 现象：将文章 A 路由从 `mixed` 人工改为 `event` 后，`mixed_components` 仍为 `["event","data_price"]`。
- 代码事实：route-confirm 只回写 route，未清空/重算 mixed_components。
- 影响：mixed 组件信息与实际路由不一致，后续下游若按 mixed_components 驱动会误判。

### F8【LLM 抽取不稳定】同源同文 3 条日价记录共享同一 evidence 却得出 3 个不同日期
- 现象：文章 B（成都 201 行情）3 条 `daily_price` 记录 `price_date` 分别为 8/15、8/16、8/17，但 evidence 文本完全相同（"2026年8月15日/16日"），无法支撑各自日期。
- 影响：evidence 溯源质量存疑，需人工核对；建议对"多条同源记录"做证据差异化校验。

### F9【UI 标注展示正常（通过项留档）】
- 现象：审核页每字段渲染「高置信/待确认/缺失」置信度标签 + 「AI推断/原文事实」性质标 + 原文高亮 evidence，与用例"每个字段显示置信度/性质标/evidence"一致。
- 结论：TC-03 字段标注展示通过。示例（测试A 事件）11 字段分布：高置信 5 / 待确认 4 / 缺失 1，全部可人工改判。

### F10【空字段标注】related_grades 空数组仍给 INFERENCE/low 且 evidence 为 null
- 现象：文章 C（每日钢市）`related_grades=[]` 标注 low/INFERENCE，evidence 为 null。
- 影响：空结果无证据支撑，提示"缺失"更合理，但属体验问题非阻断。demo 期可接受。

### F11【UI 渲染 bug】影响方向字段值未回显，显示占位符"请选择影响方向"
- 现象：文章 A 事件记录 `impact_direction` 后端 value=[{dimension:"价格",direction:"利多"}]、reviewed=confirmed，但审核页该字段的下拉框一直显示占位符"请选择影响方向"，看不到已选值。
- 代码事实：判断类数组对象值在 el-select 中未正确回显。
- 影响：人工校核时看不到 AI 抽取的影响方向，容易误判为未抽取；提交后数据实际正确（图谱写入正常）。需修复回显。

### F12【AI 未抽取 + 默认 0 触发数值硬拦截】影响程度(impact_level) aiValue=null 时默认 0
- 现象：文章 A 事件记录 AI 未抽取 `impact_level`（aiValue=null），UI 星级控件默认 0，提交时触发"数值格式校验失败（影响程度）"硬拦截，需人工点星级（设为 2）后放行。
- 判定：拦截本身合理（0 不在 1-5 合法区间），AI 未抽取场景走人工补录符合设计。体验优化建议：AI 未抽取时直接标"缺失"提示，而非默认 0。

### F13【状态命名差异】daily_price 提交后为 active，event 为 confirmed
- 现象：文章 A 提交审核后，event 子记录 `confirmed`、daily_price 子记录 `active`（文档仅描述 `confirmed`）。
- 判定：价格类记录走"活跃"状态符合领域语义，但与文档 TC-04 描述不一致，建议文档补充说明。

### F14【TC-04 通过项留档】硬拦截弹窗信息完整、图谱写入正常
- 硬拦截：提交前必填/低置信/判断类未确认共 4 项被拦截，弹窗逐项列出原因并高亮对应字段；数值格式异常（影响程度=0）也被拦截。
- 图谱写入：事件确认后 nodes 53→66、edges 92→114；日价确认后 nodes 66→67（+1 日价记录节点）、edges 114→116（+2），与预期一致。

### F15【TC-05 通过 + 文案差异】skip/reject 流转正常；放弃无"填写原因"入口
- 通过项：文章 B 第 1 条日价记录"加入待处理队列"→ `skipped`；第 2 条"彻底删除"确认 → `rejected`，且提示"不再进入待处理队列"。状态流转与接口一致。
- 差异：文档 TC-05 描述为点击"放弃"并"填写原因"，实际 UI 按钮文案为"彻底删除"（弹窗说明"永久不再处理，且不写入图谱"），且弹窗无原因输入框（reject 接口 reason 可选）。
- 影响：功能正常，文案与文档不一致，建议统一"放弃/彻底删除"的表述并决定是否保留原因必填。

### F16【筛选语义偏差】records/mine 状态筛选为"文章级"，非文档"仅显示该状态记录"
- 现象：`GET /api/collect/records/mine?status=confirmed` 返回 29 条，但其中包含含 rejected 子记录的文章（如 sub=[event:rejected, event:confirmed]）。
- 代码事实：过滤逻辑为"文章含 ≥1 条目标状态子记录则整篇返回"，非按子记录状态精确过滤。
- 影响：列表会出现与所选状态不符的条目（badge 仍正确展示各子记录状态），与文档"仅显示 confirmed 状态的记录"不一致。搜索（keyword=太钢→13 条均含太钢）与展开详情（来源/提交时间/路由置信度/子记录摘要）均正常。

### F17【force-void 无 UI 入口 + 作废后仍出现在 skipped 队列】TC-07 有条件通过
- 现象：
  - **无 UI 入口**：审核页（review.vue）仅有「强制删除」按钮（`doForceDelete`），没有任何「强制作废」按钮或入口；但后端存在 `POST /api/collect/articles/:id/force-void` 接口（collect.controller.ts:211）。
  - **作废后仍出现在 skipped 队列**：对文章 `94f43558`（8月17日成都市场201不锈钢行情速览）执行 force-void 后，其 `status` 变为 `voided`，但 `GET /api/collect/workbench/todos?tab=skipped` 仍返回该文章（total=2 包含它），与文档 TC-07"不再出现在任何待处理队列"不符。
- 代码事实（collect.service.ts workbenchBucketWhere 1016-1037）：skipped 桶条件 = `status != 'failed'` 且 **非** pending 条件 且 含 ≥1 条 skipped 子记录。`voided` 不在排除范围内，因此只要文章带 skipped 子记录，作废后仍会被计入 skipped 队列。
- 影响：
  - force-void 功能后端可用但用户无法从界面触发，属"半成品"功能。
  - 作废语义不彻底：作废后文章仍出现在待处理队列，用户可能重复点击造成困惑。
- 建议：UI 补充「强制作废」入口；workbenchBucketWhere 的 skipped 桶排除 `voided`（及 `deleted`）状态文章。
