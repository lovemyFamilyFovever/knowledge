## 一、背景与目标

结算系统当前**业务数据仍为 mock（但明细五表已本地 JSON 持久化）**：合作方/合同/收支节点/交付核销/全局配置五类数据经 `MockStoreService` 落到 `server/data/settlement/*.json`，增删改查**重启保留**；采销全链路内置记录仍为固定 mock（按用户认领）；工作台待办/KPI/图表/风险预警已按真实合同与收支节点聚合（2026-08-19/24）。仍未接数据库，无法支撑多端共享业务。目标是把这套系统从「演示壳」变成「能录真数据、能出真报表」的内部工具。

**真实化的三条主线**：

1. **数据落库**：mock → PostgreSQL（Drizzle ORM，与 VIP 模块同套路）
2. **AI 能力**：拍照识别已接入真实 AI（详见 `04-AI能力设计.md`）；其余能力保持规则降级，按需逐项替换
3. **数据导入**（2026-08-26 新增）：长金线下数据走拍照识别；内部三模块数据从线上数据库导入（见第五节）

**数据来源双轨（2026-08-26 用户明确）**：
- **长金**：数据在线下（纸质合同/发票）→ **AI 拍照识别**录入（已实现）
- **内部三个模块**：数据在线上数据库 → **导入接口**（规划中）

## 三、建表路线（分三步）

### 第一步：销售全链路（已完成设计）

`sales_pipeline_records` 单表落库，字段见 `01-数据模型与建表.md`。**⚠️ 该表是「记录快照」结构，缺 contractType/ownerMemberCode/财务字段**——若作为数据导入源，需在导入接口补映射（见第五节）。

### 第二步：明细四表（推荐顺序）

| 顺序 | 表 | 依赖 | 说明 |
| --- | --- | --- | --- |
| 1 | `partners` 合作方 | 无 | 台账先立，合同才能挂合作方 |
| 2 | `contracts` 合同 | partners | 每份合同挂一个合作方；**含 ownerMemberCode/priceType/taxRate/taxAmount/costPrice/grossMargin/board/boardName 财务与归属字段** |
| 3 | `payment_nodes` 收支节点 | contracts | 每份合同拆多个付款节点 |
| 4 | `delivery_records` 交付核销 | contracts | 交付物登记 + 节点核销 |
| 5 | `settlement_config` 全局配置 | 无 | 单例行：税率 + 板块显示名 |

### 第三步：采销全链路归位

明细四表建齐后，采销全链路从「独立快照表」演进为「聚合视图」（见 `01-数据模型与建表.md` 第四节路径 A）——从 contracts + payment_nodes + delivery_records 实时聚合，避免多份数据维护不一致。

## 四、执行注意点

### 4.1 数据库连接（当前阻塞点）

- 本机开发环境连不上 `DATABASE_URL`（192.168.1.64:5432）——pg_hba 拒绝无加密连接、SSL require 报 ECONNRESET
- `018` 脚本**未在库上执行**，需在可达环境（内网/飞书环境）执行
- 脚本幂等（`IF NOT EXISTS`），重复执行安全

### 4.2 落地步骤（每张表）

以销售全链路为例，后续四表照此执行：

1. 写 `server/database/sql/0NN-create-xxx-table.sql`（参照 `005-create-ai-tables.sql` 风格）
2. `schema.ts` 增加对应 `pgTable` 定义 + `xxxTable` 别名（参照现有表）
3. 建 `server/database/xxx.repository.ts`（参照 `vip.repository.ts`，注入 DRIZZLE_DB）
4. service 注入 repository，替换内存数组（保留原 mock 作为兜底/测试数据可选）
5. `tsc` 编译验证 + 接口回归

### 4.3 采销全链路接库改造要点（service 层）

当前 `sales-pipeline.service.ts` 是 `records` 数组 + `findAll()`。接库后：

- 注入 `SalesPipelineRepository`（Drizzle），`findAll()` 改为 `db.select().from(salesPipelineRecords).orderBy(desc(contractSignTime))`
- 中文字段 → 英文列名映射在 repository 层完成（`订单编号 → orderNo`）
- 前端 `SalesPipelineRecord` 类型不变，接口契约不变，前端零改动

**聚合逻辑已完成（2026-08-19/24）**：`dashboard.service.ts` 的待办统计（todo-stats）/KPI（kpi，含 2026-08-25 新增本月毛利/税金）/图表（chart-data）已改为基于真实合同与收支节点计算，AI 待办（tasks）与风险预警（warnings）也改为真实数据派生（2026-08-24），不再固定 mock。待接库后数据源从内存 mock 切换为 DB 查询，聚合逻辑不变。各指标聚合口径：

## 五、数据导入（2026-08-26 规划 → 2026-09-03 51 平台已落地）

### 背景

公司数据分两类：
- **长金**：数据在线下 → **AI 拍照识别**录入（已实现，见 `04-AI能力设计.md`）
- **内部三个模块**（其中一块即 **51 平台**）：数据在线上 → 通过 51 接口导入结算系统

### 51 平台数据导入（已落地 2026-09-03）

51 提供三个 PostQueryData 接口（web_service 模式），数据导入**采销全链路记录**（主页面；用户明确其他页面为附带）：

| 51 接口 | UI_ID | 内容 |
| --- | --- | --- |
| 订单管理 | 1787901687708783 | 订单主数据（客户/销售价/状态/销售/回款汇总） |
| 银行到款 | 1787903466100726 | 回款流水（按 CONTRACT_CODE 关联订单；已核销才计入） |
| 开票信息 | 1788148115549437 | 开票状态（按 CONTRACT_CODE 关联） |

**落点**：`sales_pipeline_records` 表（PostgreSQL；sql/018 建表 + **sql/081 补列**：contract_type / owner_member_code / tax_amount / gross_margin / board）。Repository：`server/database/sales-pipeline.repository.ts`。导入服务：`server/modules/settlement/bxg-import.service.ts`。接口：`POST /api/settlement/import/51`。

**映射口径（2026-09-03 用户逐项确认）**：
| 记录字段 | 51 来源/规则 |
| --- | --- |
| 订单编号 | CONTRACT_CODE（字符串化） |
| 服务名称 | 暂不使用（留空） |
| 公司名称 | CUSTOMER_NAME 清洗（去重复、去 11 位手机号 token，保留公司名/人名；纯手机号去重后保留） |
| 合同类型 | 恒 sale |
| 客户类别 | CUSTOMER_VAL（短期客户→其他） |
| 签订时间 | OPERATOR_TIME（创建=签约） |
| 签订状态 | CONTRACT_STATUS 原文（正式/待支付/过期/无效） |
| 销售价 | SALE_PRICE 去逗号 = **含税原价** |
| 税金 | 含税价 ÷ 1.06 × 6%（51 统一 6%） |
| 毛利 | 销售价 − 税金（即不含税收入） |
| 已到款 | 银行到款「已核销」行按订单汇总（TRANSACTION_AMOUNT 去逗号） |
| 收款状态 | 已到款 vs 销售价派生（待收款/部分收款/已收款） |
| 交付状态 | **该单有核销时间（AUDIT_TIME 非空）→ 已交付**，否则待交付 |
| 开票状态 | 开票信息 STATUS（同单任一已开即已开票） |
| 业务人员 | SALE_NAME |
| 板块 | board（51 = 内部三板块之一，默认 internal_1，调用方可传） |
| 归属 | owner_member_code = 导入人（默认当前登录用户） |

**金额解析规则**：51 金额字符串 = 补到至少 4 位再千分位（16→"0,016"、200→"0,200"、1980→"1,980"、60000→"60,000"），**去逗号 parseInt 即元**。⚠️ 发票号 INVOICE_NO 为 20 位数字超 JS 精度，若需落库必须按字符串处理。

**不过滤**：全量导入（用户 2026-09-03 确认，含 sys/过期/无效单）；幂等：按 order_no upsert 覆盖。

**销售全链路列表合并**：GET /api/settlement/sales-pipeline = 真实合同（Contract 聚合）→ 51 DB 记录（id=`bxg-*`，只读不可展开操作）→ mock 示例垫底；前端 `isMockRecord` 区分"示例"徽章（51 记录不显示）。DB 不可用时静默降级不影响列表。

**待做**：51 直连拉取器（需要登录会话/请求参数格式，当前为 JSON body 上传样例/全量数据导入）。
