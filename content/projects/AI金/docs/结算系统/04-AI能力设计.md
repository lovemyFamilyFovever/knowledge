## 二、拍照识别（已实现，真实 AI）

### 定位

把「识别单据 → 录入系统」的人工环节交给视觉大模型。价值点：合同/发票**版式不固定**（每家企业的合同模板、不同税号的发票样式都不一样），传统 OCR 需要逐模板适配，而 `qwen-vl-max` 直接理解图像内容，零模板成本。**长金数据在线下，拍照识别是主要录入通道（2026-08-26 用户明确）。**

### 架构

```
OcrRecognizeModal.vue（前端弹窗）
   │  POST /api/settlement/ai-ocr/recognize { imageBase64, docType }
   ▼
OcrService（字段契约 + 清洗 + 错误处理）
   │  recognizeImage(base64, prompt, mime)
   ▼
BailianService.recognizeImage（qwen-vl-max，OpenAI 兼容接口）
```

详见 `03-后端服务与接口.md` 第四节。关键设计：**识别只出结构化字段，不直接入库**——中间隔着一道「人工核对」（弹窗内可编辑），避免误识别污染数据。

### 字段契约（2026-08-25 财务字段扩展后）

**合同识别字段**（围绕「销售合同」「购销合同」模板，含商品明细表 + 合计 + 付款方式等段落）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `contractType` | `purchase` / `sale` / null | 标题含「销售合同」→ sale；「购销合同」/「采购合同」→ purchase |
| `contractNo` | string / null | 「合同编号」标签后取值（如 `2025102802`） |
| `partnerName` | string / null | 销售合同→乙方（需方）；采购合同→甲方（供方） |
| `signDate` | string `YYYY-MM-DD` / null | 「签订日期」标签后取值 |
| `amount` | number / null | **不含税合同金额**（元），取「不含税金额/合计」列 |
| `taxAmount` | number / null | **税额**（元，2026-08-25 新增）；合同只写价税合计时用 价税合计 − 不含税金额 反算 |
| `taxRate` | number / null | 适用税率（%）；识别不到可用 税额 ÷ 不含税金额 × 100 反算取整 |
| `board` | string / null | 业务板块 4 选一（changjin / internal_1/2/3），合同提及业务线/部门/工厂归属才填 |
| `paymentTerms` | string / null | 摘录「付款方式」段落（如「定金 50000 元 + 尾款，款到发货」） |
| `itemsSummary` | string / null | 商品明细摘要（如「不锈钢卷 201J2/2B 0.31*1020*C 30吨 246000元」），多行用顿号 |

> **无 `costPrice`（2026-08-25 移除）**：成本价是手工录入字段（毛利 = 销售金额 − 成本价），合同正文不会印，OCR 识别它没意义。

**发票识别字段**（围绕「增值税专用发票」「电子普通发票」模板，含发票代码/号码/购买方/销售方/项目明细表）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `invoiceType` | `special` / `general` / null | 专用发票→special；普通发票→general |
| `invoiceCode` | string / null | 「发票代码」标签后取值 |
| `invoiceNo` | string / null | 「发票号码」标签后取值 |
| `date` | string `YYYY-MM-DD` / null | 「开票日期」标签后取值 |
| `amount` | number / null | 价税合计（两位小数） |
| `exclusiveAmount` | number / null | **不含税金额**（2026-08-25 新增，从「金额」列取值） |
| `taxAmount` | number / null | **税额**（2026-08-25 新增，从「税额」列取值） |
| `taxRate` | number / null | **适用税率**（2026-08-25 新增，从税率列取值） |
| `purchaserName` | string / null | 「购买方信息 - 名称」 |
| `sellerName` | string / null | 「销售方信息 - 名称」 |
| `projectSummary` | string / null | 商品/服务项目摘要（含规格/单位/数量/金额/税率） |

> **重要**：发票图片上**没有合同编号**。旧版本曾要求识别 `contractNo`，导致模型幻觉生成假合同号；新版已移除。

### 实测效果（2026-08-12）

**程序生成的简单模板**（第一轮）：合同/发票基础字段均能识别正确。

**公司实际模板**（第二轮，基于真实「销售合同」+「电子专用发票」图片）：

合同（2025102802 销售合同，无锡天诚金属 vs 秀吗电子商务）：

- ✅ `signDate: "2025-10-28"`（日期归一化）
- ✅ `amount: 524500`（合计列，与模板一致）
- ✅ `paymentTerms: "定金50000元整，货物明细出来以后，支付尾款，全款发货"`

发票（电子专用发票，2026-07-27）：
- ✅ `invoiceType: "special"`
- ✅ `invoiceCode / invoiceNo: "26522000000147998191"`
- ✅ `date: "2026-07-27"`

**后续优化方向**：
- 合同 `partnerName` 精度：可加强 prompt 措辞（如「partnerName 必须取合同中作为'需方/收货方'的一方，不能取供方」），或在弹窗里增加「按当前合同类型，应取 □甲方 □乙方」提示让用户确认。
- 发票确认动作 2026-08-14 起改为**直接标记合同开票**（`registerInvoice` 把 invoiceNo/invoiceAmount/invoiceDate 落到合同开票信息），不再进收支节点；`purchaserName/sellerName/invoiceCode` 仍仅弹窗展示、不入库。原「扩展 CreatePaymentNodeRequest 增加 `remark` 字段保存发票号 + 业务关联」的方向已作废。
- **发票按金额匹配合同（2026-08-25 修正）**：合同 amount 已改不含税，匹配改用**含税总额**（exclusive 时 = amount + taxAmount）对比发票价税合计，±1 元容差。

## 三、规则降级能力明细（AI 化前的兜底）

### 3.1 合作方信用评分（PartnerService.getCreditscore）

**目标**：给出 0-100 信用分 + 因子拆解 + 风险等级（low/medium/high）。

**当前规则**：
- 基准分按注册资本分级（≥5000 万 → 90，≥1000 万 → 80，≥100 万 → 70，否则 60）
- 减分：诉讼次数 ×5（封顶 30）、经营年限 <3 年减 10
- 非活跃合作方乘 0.85 系数
- 风险等级：≥80 low、≥60 medium、否则 high

**AI 化方向**：把同维度输入（注册资本/诉讼/年限/活跃度）+ 可选的工商数据、交易历史描述给 LLM，输出分数 + 因子 + 自然语言风险解读；引入「诉讼案由」「行业舆情」等文本信息时规则无法承载，AI 才有必要。

### 3.2 合作方评级（PartnerService.getRating）

**目标**：A/B/C/D 四档评级 + 理由。

**当前规则**：信用分映射（≥85 A、≥70 B、≥55 C、否则 D），理由为模板拼接。

**AI 化方向**：与信用评分合并为一次调用，让 LLM 同时输出分数与评级及综合评语。

### 3.3 合同审查（ContractService.aiReview）

**目标**：风险点 + 建议 + 关键条款提取。

**当前规则**：金额 >300 万 → 提示担保/分批付款；未开始 → 提示启动风险；进度 0-100 → 提示关注结算节点；无风险 → 输出固定正面结论。

**AI 化方向**：`aiReview(id, documentUrl)` 已预留 documentUrl 入参——上传合同扫描件/PDF 后，让视觉/文本模型读取合同原文，提取付款条款、违约责任、验收标准等**真实条款**并评估风险。这是拍照识别的自然延伸（识别 → 审查一条链）。

### 3.4 合同对比（ContractService.aiCompare）

**目标**：同合作方历史合同的相似/差异/建议。

**当前规则**：仅比对金额与状态，模板化输出。

**AI 化方向**：把当前合同与历史合同的结构化数据（金额/付款条款/类型/周期）打包给 LLM，输出差异清单与优化建议。

### 3.5 异常检查（PaymentService / DeliveryService.aiAnomalyCheck）

**目标**：登记节点/交付时发现金额异常。

**当前规则**（2026-08-17 校正为实际实现）：
- 收支节点（PaymentService.aiAnomalyCheck）：新增节点后收支总额占合同金额比例 >95% 报 `amount_near_limit`（接近上限）、>100% 报 `amount_over`（超额）
- 交付核销（DeliveryService.aiAnomalyCheck）：核销金额占合同金额 >90% 报 `write_off_over`（核销偏高）、交付物描述为空报 `desc_missing`

**AI 化方向**：结合合同金额、分期比例、历史同类合同惯例，判断「这次登记是否合理」（如尾款应≈30% 合同额、定金不应超 50%），输出 `hasAnomaly + anomalyType + message`。

## 四、AI 能力统一接入模式（后续复用）

`OcrService` 确立了结算系统内 AI 接入的样板：

1. **服务内定义 prompt 常量**（字段契约 + 「只输出 JSON + 识别不到输出 null」约束）
2. **调用 BailianService 新增的通用方法**（`recognizeImage` 走 compatible-mode chat/completions，`askFastSync` 走文本，均已有先例）
3. **字段清洗层**：金额/日期/枚举白名单归一化，脏数据在服务端挡掉
4. **前端永远先展示、后入库**：识别/分析结果以可编辑形式呈现，人工确认后才写业务数据

后续新增 AI 能力（合同审查、异常检查等）照此模式扩展即可，无需新引入外部服务。

## 五、token 成本与降级策略

- 视觉模型成本高于文本模型，拍照识别是**低频操作**（人工触发的单据录入辅助），当前无需计费/限流
- 若未来放开给大量运营人员使用，建议：图片压缩（前端 canvas 降分辨率）、按成员限额、失败自动降级到「手动录入」引导（弹窗已支持手动补填）
- 规则降级能力全部保持**同步返回、毫秒级**，替换为 AI 时需评估响应延迟（百炼同步调用有 60s 超时兜底，见 bailian.service.ts）
