## 一、架构定位

结算系统是「不锈钢市场使用中心」内部的**业务结算管理后台**，承接从合同签订到款项回收的完整结算链路。它从原「结算系统」（React 飞书妙搭模板）迁移而来，职责是让运营/财务人员在一个界面里管理合作方、合同、收款/付款节点、交付核销，并透过「采销全链路」看到每笔订单从签订到开票的进度。

与面向 C 端的 AI 问答 / 测价 / 配单不同，结算系统是**内部运营工具**，入口为侧边栏「个人中心」下的「结算中心」（2026-08-24 加入口），结算系统内部再分结算中心/采销全链路/合同管理/财务配置。

当前实现处于 **mock 阶段（本地 JSON 持久化）**：合作方/合同/收支节点/交付核销/全局配置五类数据以 service 内置数据为默认值，增删改查通过 `MockStoreService` 落盘到 `server/data/settlement/*.json`，**重启保留**；销售全链路内置记录仍为固定 mock（按用户认领）；工作台待办/KPI/图表/风险预警已按真实合同与收支节点聚合（2026-08-19/24），AI 待办与风险预警已从真实数据派生（2026-08-24）。尚未接 PostgreSQL。**AI 拍照识别已接入百炼视觉模型**，是迁移后第一个真正使用 AI 的能力；其余 AI 能力（合同审阅、异常检查、信用评分）暂为规则降级。

**数据来源双轨**（2026-08-26 用户明确）：
- **长金**：数据在线下（纸质合同/发票）→ 走 **AI 拍照识别**录入
- **内部三个模块**：数据在线上数据库 → 规划做**导入接口**（见 `05-数据真实化路线.md` 第五节）

## 二、整体流程

结算系统围绕「一单生意从签约到回款」的完整链路组织：

```
合作方台账（谁在跟你做生意）
      │
      ▼
合同签订（这笔生意多少钱、怎么分期付；含税率/税额/毛利/板块财务维度）
      │
      ▼
收支节点（拆成定金/中期/尾款，每节点计划多少、哪天付、到没到）
      │
      ▼
交付核销（货/服务交付了没，交付后核销对应收款节点）
      │
      ▼
采销全链路（按订单汇总成时间线：签订 → 收款 → 交付 → 开票）
```

工作台（`/settlement/workbench`）是入口聚合页：待办统计、业务指标（含本月毛利/税金）、合同金额趋势、收付款分布、AI 待办、风险预警、快速导航（合同管理/采销全链路/财务配置 3 卡）。**AI 拍照识别入口位于采销全链路页**（页头按钮；页面 2026-08-21 升级为采销双视角，页面标题为「采销全链路」，路由/菜单统一改名 2026-08-25）。**财务配置入口位于结算中心快速导航**（侧边栏不单独加入口，2026-08-25）。

## 四、关键设计决策

### 为什么业务数据用内存 mock？

从 React 飞书模板迁移时，原系统依赖飞书多维表格插件读取真实业务数据，迁移决策为**先还原交互、暂不接数据**——所有 service 内置模拟数据，保证页面完整可用、可演示、可验收。数据真实化是当前阶段的主线（见 `05-数据真实化路线.md`）。

### 为什么在 mock 之上加本地 JSON 持久化？

纯内存 mock 重启即丢，演示/验收时每次都要重新录入。`MockStoreService`（2026-08-13 新增）把合作方/合同/收支节点/交付核销/配置五个业务数组的增删改查落盘到 `server/data/settlement/*.json`，重启保留，接近真实使用手感；后续接 PostgreSQL 时只需把 service 里的数组操作换成 Drizzle repository 查询，前端与接口契约不变。

### 为什么结算中心按登录用户隔离？（2026-08-24）

普通用户登录后只应看到自己的合同订单；未来 ERP 后台结算系统看全量。实现：合同绑定 `ownerMemberCode`（创建时自动归属）；无主历史数据由首个访问用户**惰性认领**（幂等落盘）；节点/交付记录归属随合同；全部接口走 AuthGuard + `@CurrentUserId()`（只认 token 解析的 userContext，防伪造）。全量方法保留为管理用途（SettlementModule exports 预埋）。

### 为什么金额改不含税 + 独立税金？（2026-08-25 领导评价）

领导要求"毛利、税金都要进去"。合同 `amount` 语义从「含税」改为**不含税**，新增 `priceType` 标记（inclusive=旧数据含税 / exclusive=新合同不含税）；`taxAmount` 派生（OCR 识别税额优先，否则 amount × taxRate）；旧数据不重算（避免改变历史财务口径），新字段显示 `-`。税率变更不重算历史（合同存创建时快照）。

### 为什么毛利用「输入成本价」方案？（2026-08-25）

销售合同本身没有成本概念，毛利 = 销售金额 − 成本价需要成本输入。用户确认方案：合同表单加 `costPrice` 字段（仅 sale 合同），`grossMargin = amount - costPrice` 服务端派生；成本价是手工录入字段，**不参与 OCR 识别**（合同上不会印）。

### 为什么 4 槽板块 + 显示名可配置？（2026-08-25 领导评价）

领导要求结算系统服务「长金工厂 + 公司内部三个业务板块」。实现：`BoardCode` 枚举 4 槽（changjin / internal_1/2/3），**显示名存 ConfigService 可后台改**（用户原话"三个公司内部的业务"未指定名称）；板块只做标签与汇总维度，不参与权限隔离；数据导入时按板块打标。

### 为什么状态字段用中文文本，不用枚举？

项目既有约定（plaza_posts.status 等）均为 varchar 存中文状态文本、应用层校验。结算系统沿用此风格，前端 `record.收款状态 === '已收款'` 这类判断与数据无缝衔接，后续建表时也保持 varchar 中文默认值。

### 为什么拍照识别接入百炼视觉模型，而不是第三方 OCR？

项目已在用阿里云百炼（`BAILIAN_API_KEY` 已配置，qwen 系列调用有先例），视觉模型 `qwen-vl-max` 走同一套 OpenAI 兼容接口，无需引入新依赖、无需新密钥；且视觉大模型对合同/发票这类**非标准版式**的识别能力显著优于传统 OCR 引擎（版式不固定、字段位置不固定的场景，传统 OCR 需要逐个模板适配）。

### 为什么识别结果先展示核对，再进表单？

AI 识别不可能 100% 准确。流程设计为：识别 → 结构化字段以**可编辑表单**展示（带置信度、可看原始文本）→ 用户核对修改 → 确认后直接生成合同（2026-08-14 起弹窗内确认，无需跳转）。把「机器猜测」和「人工确认」分开，避免误识别直接入库。

### 为什么销售全链路区分销售方/采购方视角？

同一笔合同，销售方关心「钱收回来没有」，采购方关心「钱付出去没有」。2026-08-21 起全链路按合同类型区分角色（**方案 A：角色跟随订单，不绑定账号**）：销售合同 = 我是销售方（看收款 + 销项发票），采购合同 = 我是采购方（看付款 + 进项发票），收款/付款状态由收支节点按 direction 实时聚合（`getCollectionStats` / `getPaymentStats`）。后端同时提供 `view` 视角过滤（all/seller/buyer），避免一张表里收款付款混在一起、角色语义不清。

### 为什么表单控件复用 Element Plus？（2026-08-28）

结算系统迁移初期自研了 st- 风格的原生下拉/日期控件（st-select 等），与项目主框架割裂、维护成本高。2026-08-28 起页面下拉（el-select）、日期选择（el-date-picker）等表单控件改为**复用项目 Element Plus 组件**（覆盖页面：采销全链路筛选、合同管理筛选与新建表单、阶段操作区表单、拍照识别核对表单）；`settlement-theme.css` 增加 Element Plus 适配段（`.settlement-page` 作用域内对齐翡翠绿主色/36px 高度/16px 圆角，弹出层做全局覆盖），保证与自研控件观感一致，且不影响项目其它页面。
