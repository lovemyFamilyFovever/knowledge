# 数据模型与建表

> 最后更新：2026-08-26
> 状态：销售全链路表已建（脚本未执行）；财务维度（税率/税额/毛利/板块）与用户归属已补入模型规划（2026-08-25/26）

## 一、业务对象关系

结算系统由 5 块核心业务组成，呈「合作方 → 合同 → 节点/交付 → 汇总视图」的层级关系：

```
合作方（partners）
   │  1:N
   ▼
合同（contracts）─────────────┐
   │  1:N                     │ 1:N
   ├──► 收支节点（payment_nodes） │
   └──► 交付核销（delivery_records）
                              │
采销全链路（sales_pipeline_records）  ← 汇总视图/快照，当前独立维护
```

| 业务对象 | 管什么 | 关键字段 |
| --- | --- | --- |
| 合作方 Partner | 客户/供应商台账 | name / type / contactName / contactPhone / status / creditScore / aiRating |
| 合同 Contract | 每单生意的金额与分期 + 财务维度 | contractNo / partnerId / contractType / amount（不含税）/ paymentTerms / status / settlementProgress / **ownerMemberCode**（归属用户）/ **priceType / taxRate / taxAmount / costPrice / grossMargin / board / boardName**（财务维度，2026-08-25） |
| 收支节点 PaymentNode | 合同拆解为付款节点 | contractId / nodeType / direction / plannedAmount / plannedDate / actualAmount / actualDate / status |
| 交付核销 DeliveryRecord | 交付物与节点核销 | contractId / deliverableDesc / acceptanceStatus / paymentIds / writeOffAmount |
| 采销全链路 SalesPipelineRecord | 按订单汇总的时间线 | 订单编号 / 服务名称 / 公司名称 / 客户类别 / 合同类型 / 销售价 / 已到款 / 收款状态 / 交付状态 / 开票状态 / 付款周期 / 业务人员 / **毛利 / 税金 / 含税总额 / 板块**（2026-08-25） |
| 全局配置 SettlementConfig | 税率 + 板块显示名 | taxRates（sale/purchase）/ boards（4 槽显示名），持久化 config.json（2026-08-25） |

> **金额口径约定（2026-08-25 领导评价）**：合同 `amount` = **不含税金额**；`priceType` 标记含税/不含税（inclusive=旧数据默认含税 / exclusive=新合同不含税）；`taxAmount` = OCR 识别税额优先，否则 round2(amount × taxRate/100)；`grossMargin` = amount − costPrice（仅 sale）；`taxRate` 存创建时快照（税率变更不重算历史）。
>
> **板块 4 槽枚举（2026-08-25）**：`changjin`（长金工厂）/ `internal_1` / `internal_2` / `internal_3`（内部三板块），显示名存 ConfigService 可后台改。

## 二、已建表：sales_pipeline_records（采销全链路）

### 表结构（字段映射）

| 列名（DB） | 类型 | 约束 | 对应前端字段 |
| --- | --- | --- | --- |

### 索引

- `order_no` 唯一索引（订单编号不重复）
- `company_name` / `payment_status` / `delivery_status` / `invoice_status` / `contract_sign_time` 普通索引（列表筛选与排序用）

### ⚠️ 与当前结算系统模型的差距（2026-08-26 评估）

此表是「全链路记录快照」结构，与结算系统 Contract 模型相比缺：

| 缺失 | 影响 |
| --- | --- |
| `contract_type`（销售/采购） | 收付款方向判断失效（sale 看收款 / purchase 看付款） |
| `owner_member_code`（归属用户） | 按登录用户隔离失效（2026-08-24 实现） |
| 财务字段（tax_rate / tax_amount / gross_margin / board） | 领导要求的财务维度无落点 |

→ 若用于「数据导入」，需在导入接口做映射补全（contractType 按板块推断或补列、ownerMemberCode=导入人、board=三板块标记）。详见 `05-数据真实化路线.md` 第五节。

### 设计决策

1. **状态字段用 varchar 中文文本**，与项目既有约定（plaza_posts.status 等）一致，前端 `=== '已收款'` 判断无缝衔接。
2. **金额用 numeric(14,2) 存元**，与 ERP 统计表（signed_amount 等）一致，报表可直接求和。
3. **合同签订时间可空**——存在「未签订」状态的记录，时间可能未填。
4. **订单编号唯一**——同一笔生意不应重复登记。

> ⚠️ 执行状态：本机开发环境连不上数据库服务器（pg_hba 拒绝无加密连接），脚本尚未在库上执行。脚本幂等（`IF NOT EXISTS`），在可达环境执行即可。

## 四、采销全链路 vs 明细表的关系（重要）

当前 `sales_pipeline_records` 是**独立维护的汇总快照**（字段含状态冗余），与合同/收支节点表并无外键关联。两条演进路径：

- **路径 A（推荐）**：采销全链路改造成**查询视图**，从 contracts + payment_nodes + delivery_records 实时聚合，不落库——避免多份数据维护不一致。
- **路径 B**：维持快照表，由上游表的变更事件（新建合同/登记收款/标记交付）**驱动回写**汇总状态。

路径 A 数据一致性好但需要上游表先建齐；路径 B 可以先用现有快照表过渡。具体取舍见 `05-数据真实化路线.md`。

> **注（2026-08-26）**：当前实现已部分走路径 A——`sales-pipeline.service.ts` 实时聚合 ContractService 合同（含收款/付款/交付/开票状态实时计算），内置 mock 记录为遗留快照。接库后应完全走向路径 A。
