# 公告与消息推送方案

> 版本: v1.0 | 日期: 2026-07-26 | 状态: 方案设计中

## 一、背景与目标

AI金项目目前缺乏系统级消息触达能力。管理员无法向用户推送公告（如功能更新、系统维护、营销活动），用户也无法在应用内获取重要通知。

核心目标：

- 管理员可在 ERP 后台创建、编辑、定时发布公告
- 用户在应用内可见公告（通知中心 / 顶部横幅）
- 支持多渠道触达：站内通知 + 飞书 Bot 推送
- 公告支持定向推送（全部用户 / VIP 用户 / 指定用户）

## 二、公告类型与展示形式

### 2.1 公告分类

| 类型 | 说明 | 展示优先级 | 示例 |
|------|------|-----------|------|
| 系统公告 | 系统维护、升级、重要通知 | 高 | "系统将于 7月28日凌晨2:00-4:00 维护，届时暂停服务" |
| 功能更新 | 新功能上线、功能优化 | 中 | "AI 测价新增304冷轧预测，精度提升15%" |
| 营销活动 | 优惠活动、促销信息 | 低 | "夏季特惠：VIP 套餐限时8折" |
| 运营通知 | 账单提醒、额度预警等 | 中 | "您的月度 Token 额度已使用 80%" |

### 2.2 前端展示形式

根据优先级和紧急程度，采用分级展示策略：

```
优先级 高 → 顶部横幅（不可关闭 / 可关闭，带颜色标识）
优先级 中 → 通知中心小红点 + 列表展示
优先级 低 → 仅通知中心列表
```

**顶部横幅**（系统公告）：


**通知中心**（入口：页面右上角铃铛图标）：

## 三、数据模型

### 3.1 公告表（飞书多维表格）

**表名：** `erp_announcements`

| 字段名 | 类型 | 说明 |
|--------|------|------|
| 标题 | 文本 | 公告标题 |
| 内容 | 多行文本 | 公告正文（支持 Markdown 纯文本） |
| 类型 | 单选 | 系统公告 / 功能更新 / 营销活动 / 运营通知 |
| 优先级 | 单选 | 高 / 中 / 低 |
| 发布状态 | 单选 | 草稿 / 已发布 / 已撤回 / 已归档 |
| 展示形式 | 单选 | 仅通知中心 / 顶部横幅+通知中心 |
| 定向用户 | 多选 | 全部用户 / VIP用户 / 指定用户 |
| 指定用户列表 | 文本 | 当选择"指定用户"时，逗号分隔的用户ID |
| 跳转链接 | 文本 | 可选，点击公告的跳转URL |
| 发布时间 | 日期时间 | 发布的时间（定时发布时设为未来时间） |
| 过期时间 | 日期时间 | 可选，公告自动下架的时间 |
| 创建人 | 文本 | 操作管理员姓名 |
| 创建时间 | 日期时间 | 记录创建时间 |
| 撤回时间 | 日期时间 | 撤回操作的时间 |
| 撤回原因 | 文本 | 撤回的原因说明 |

### 3.2 用户已读状态表

**表名：** `erp_announcement_reads`

用于追踪每个用户对公告的已读/未读状态，避免每个用户重复标记同一公告。

| 字段名 | 类型 | 说明 |
|--------|------|------|
| 公告ID | 文本 | announcement 的 record_id |
| 用户ID | 文本 | x-user-id |
| 已读状态 | 复选框 | 是否已读 |
| 已读时间 | 日期时间 | 首次阅读的时间 |

**注意：** 此表仅记录"需要追踪已读状态"的公告（优先级高/中）。低优先级公告不追踪已读状态，避免表膨胀。

### 3.3 为什么不放在已有表里

- 公告数据独立性强，读写频率低、数据量小
- 已读状态需要按用户ID快速查询，独立表更高效
- 未来可扩展推送日志表（飞书推送状态、失败重试记录）

### 4.3 API 接口

**ERP 管理端：**

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/erp/announcements` | GET | 公告列表（支持状态筛选、分页） |
| `/api/erp/announcements` | POST | 创建公告（草稿） |
| `/api/erp/announcements/:id` | PUT | 编辑公告 |
| `/api/erp/announcements/:id` | DELETE | 删除公告（仅草稿） |
| `/api/erp/announcements/:id/publish` | POST | 发布公告 |
| `/api/erp/announcements/:id/recall` | POST | 撤回公告 |
| `/api/erp/announcements/:id/archive` | POST | 归档公告 |

**用户端：**

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/announcements/active` | GET | 当前用户可见的活跃公告 |
| `/api/announcements/unread-count` | GET | 当前用户未读公告数量 |
| `/api/announcements/:id/read` | POST | 标记某条公告已读 |

### 4.4 定时发布机制

公告的"发布时间"字段支持未来时间，即定时发布。实现方式：

- 方案A（推荐）：前端在发布时将公告状态设为"已发布"，发布时间设为目标时间。用户端接口 `getActiveAnnouncements` 过滤 `发布时间 <= now` 的记录。无需后端定时任务。
- 方案B：使用 `@nestjs/schedule` 定时扫描"已到发布时间"的草稿并自动发布。

**建议采用方案A**，逻辑简单无需额外依赖。仅当需要"定时发布时触发额外动作"（如飞书推送）时，才需要方案B。

## 五、定向推送策略

### 5.1 用户分组

| 分组 | 判定逻辑 | 适用场景 |
|------|----------|----------|
| 全部用户 | 所有已登录用户 | 系统公告、重大功能更新 |
| VIP用户 | 购买了 VIP 套餐且未过期 | VIP 专属功能、套餐调整 |
| 指定用户 | 管理员手动选择用户ID | 定向通知、客服跟进 |

### 5.2 定向判定流程

```
用户请求 GET /api/announcements/active
  → 查询所有 status=已发布 且 发布时间<=now 的公告
  → 逐条判定用户是否在公告的定向范围内：
    ├── 全部用户 → 直接返回
    ├── VIP用户 → 查询该用户是否有有效 VIP 套餐
    └── 指定用户 → 检查 userId 是否在指定列表中
  → 过滤掉已过期（过期时间<now）
  → 返回公告列表
```

### 5.3 飞书 Bot 推送（可选增强）

对于强触达需求（如系统维护通知），可通过飞书 Bot 向用户发送私聊消息：

- 前提：用户已绑定飞书账号（多数用户通过飞书登录，天然绑定）
- 实现：`lark-cli im +send-message` 逐个发送私聊消息
- 注意：飞书 Bot 有发送频率限制，大量用户推送时需要控制速率
- 建议：仅对"高优先级 + 顶部横幅"类公告触发飞书推送

## 八、扩展性考量

### 8.1 运营通知自动化

未来可由系统自动生成运营通知，而非仅依赖管理员手动创建。触发场景包括：

- 用户月度 Token 额度即将用尽 → 自动生成额度预警通知
- VIP 套餐即将到期 → 自动生成续费提醒
- 重要功能上线 → 自动关联 Git commit message 生成更新日志

实现思路：将"触发条件"和"通知模板"配置化，由定时任务扫描触发条件并自动调用 `createAnnouncement`。

### 8.2 多语言支持

当前用户群体为中文用户，公告内容以中文编写。若未来扩展英文用户：

- 公告表增加语言字段
- 用户端根据 `Accept-Language` 请求头过滤
- 或管理员在创建时分别编写中/英内容

### 8.3 邮件推送

若未来需要邮件渠道，可接入飞书邮箱或 SendGrid 等邮件服务，在 `publishAnnouncement` 中追加邮件发送逻辑。当前不实现。

## 九、待确认事项

1. **是否需要飞书 Bot 推送**：这是工作量最大的可选功能。建议 MVP 先不做，用站内通知中心验证公告体系运转正常后，再评估是否需要飞书推送。
2. **公告编辑器**：内容字段用纯文本还是支持 Markdown？建议初期纯文本，支持换行，后续可升级为简易富文本。
3. **已读状态的垃圾回收**：`erp_announcement_reads` 表会持续增长。建议对"已归档"超过 90 天的公告，清理其对应的已读记录。
4. **顶部横幅同时显示多条**：当存在多条"顶部横幅"级别的公告时，是只显示最新一条还是轮播展示？建议只显示最新一条，避免信息过载。
