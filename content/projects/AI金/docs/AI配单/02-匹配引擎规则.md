# LLM 评分逻辑

> 最后更新：2026-07-22
> 状态：已重写为 LLM 直通架构
>
> 说明：文件名保留 `02-匹配引擎规则.md` 以维持文档索引稳定，但内容已从「规则引擎」改为「LLM 评分逻辑」。当前不存在独立的规则引擎文件，评分完全由 `qwen-turbo` 通过 prompt 完成。

## 一、评分模型与入口

| 项 | 值 |
| --- | --- |
| 模型 | `qwen-turbo`（百炼 FAST_MODEL） |
| 调用方式 | `BailianService.askFastSync(prompt, [], 'score-matches')` |
| 接口 | `POST /api/ai/score-matches` |
| 控制器 | `server/modules/ai/ai.controller.ts` → `AiController.scoreMatches`（234-301 行） |

入参为 `{ query, parsed, candidates }`，其中：
- `query`：用户原始自然语言需求
- `parsed`：由 `parse-enquiry-params` 解析出的结构化参数（材质/预算/城市等）
- `candidates`：秀玛搜索返回的候选商品数组（不含 Supplier 字段）

LLM 据此选出 Top 3 并按匹配度从高到低排序。

## 二、四维 100 分制评分体系

每条入选商品给出一个总匹配度 `score`（0-100）和四个维度的拆解评分（每个维度 0-100）：

| 维度 | 字段 | 评分口径 |
| --- | --- | --- |
| 材质/表面/规格匹配 | `materialMatch` | 100 = 完全匹配；近似匹配按程度给分 |
| 价格竞争力 | `priceAdvantage` | 低于预算越多越高；「面议」≈ 50；超预算 < 40 |
| 仓库距离匹配 | `locationMatch` | 本地 = 100；同省 = 80；跨省 = 50；未指定 = 60 |
| 库存满足度 | `stockLevel` | 充足 = 100；勉强够 = 70；不足 = 30 |

## 三、Prompt 评估要点

Prompt 中以「资深不锈钢采购顾问」角色设定，并显式列出以下评估规则（LLM 据此打分）：

- 材质 / 表面 / 规格是否完全匹配或近似匹配
- 价格是否在预算范围内（低于预算加分，超过预算扣分）
- 价格标记为「面议」的无法判断性价比，给中等分
- 仓库 / 供货地是否在目标城市（本地仓库加分，同省稍加分，跨省扣分）
- 库存量 / 重量是否满足需求
- 厂家是否为知名品牌（太钢、宝钢、张浦等大厂加分）
- **厚度有 ±0.3mm 公差属正常，不算不匹配**

> 注：当前 `candidates` 中 `factory` 字段虽已定义，但秀玛数据映射时 `Factory` 实际为空字符串，品牌加权规则暂未生效，留待数据源补全后自动启用。

## 四、推荐理由要求

每条入选商品必须返回 50-80 字的 `reason`，要求：

- 用自然的口语化语言写一段连贯的采购建议，不要用编号或分隔符
- 必须包含四个关键信息：① 规格材质匹配度 ② 价格与预算的对比 ③ 供货地距离评估 ④ 库存是否充足
- 示例：「304/2B 规格与需求完全一致，太钢出厂品质有保障。¥12800 的价格比您的预算 ¥14500 低了 11%，性价比突出。无锡本地库免去跨省运输成本和时间，52 吨库存也远超您 50 吨的需求量，建议优先采购。」

## 五、LLM 返回的 JSON 格式

要求 LLM 直接返回纯 JSON（不要 ```json 代码块包裹，不要任何其他文字）：

```json
{
  "ranked": [
    {
      "productId": 12345,
      "score": 92,
      "reason": "50-80字推荐理由……",
      "dimensions": {
        "materialMatch": 95,
        "priceAdvantage": 90,
        "locationMatch": 100,
        "stockLevel": 85
      }
    }
  ]
}
```

后端从响应文本中用正则 `\{[\s\S]*\}` 提取首个 JSON 对象并 `JSON.parse`，再校验 `ranked` 为数组。

## 六、输出约束

1. 只选真正匹配的，不匹配的宁可少选（**最少 1 条，最多 3 条**）。
2. 入选商品按 `score` 从高到低排序。
3. 直接返回纯 JSON，不要 Markdown 代码块。

## 七、Fallback 机制（LLM 失败时）

评分接口有两层兜底，保证页面始终有结果可展示：

**第一层：后端 `scoreMatches` catch**

当 LLM 调用失败、响应无法提取 JSON、或 `ranked` 字段缺失时，后端不抛错，而是返回：

```json
{
  "success": true,
  "data": {
    "ranked": [
      { "productId": <候选0>, "score": 0, "reason": "",
        "dimensions": { "materialMatch": 0, "priceAdvantage": 0, "locationMatch": 0, "stockLevel": 0 } }
    ]
  }
}
```

即取 `candidates` 前 3 条，`score=0`，`reason` 为空，四维全 0。前端据此仍可展示商品卡片（仅缺评分与理由）。

**第二层：前端 `doSearch` catch**

前端在调用 `scoreMatches` 时再包一层 try/catch，若请求本身失败，则用搜索结果的前 3 条构造同样的零分结构赋给 `rankedDisplay`，确保不白屏。

## 八、阶段六预告

当前评分维度仅围绕商品本身（材质/价格/距离/库存），**不包含企业维度**。阶段六将在此基础上增加 **企业曝光特权加权**：VIP 企业的商品会通过 `priorityRecommend` 字段在配单排序中获得曝光倾斜。届时本评分逻辑会在 prompt 或后处理阶段引入企业权重，四维体系保持不变。
