# 站内交易方案（AI配单交易闭环）

> 最后更新：2026-08-16
> 状态：**2026-08-16 领导决议：查看联系方式 = 认定购买 → 单子绑定到该用户名下并立即下架**（trade_deal_records 写 pending_settlement 待结算，快照 is_active=false）；
> 后续由结算系统（另开发）关联状态，用户上传交易环节证明材料，状态关联待办见桌面《待办-结算系统与挂单状态关联.md》。
> 此前的"三状态已联系不判成交"与"查看即成交（8-12）"方案均已废止。

## 一、背景与目标

AI 配单交易闭环分两条路径：

| 路径 | 说明 | 现状 |
| --- | --- | --- |
| 跳转秀吗交易 | 推荐卡片跳转秀吗商品详情页下单 | ✅ 已完成（`AiStockPage.vue` 的 `getXiumaDetailUrl`） |
| 站内交易 | 在本平台内完成「查看联系方式 → 视为成交 → 商品下架 → 线下/担保结算」 | 📋 本文档方案 |

**核心决议（2026-08-12 会议）：用户点击查看供应商联系方式即视为订单成交**，对应商品立即下架，点击前弹确认提示框。不做买卖家会话、不做站内在线支付。

## 二、交易规则

### 2.1 成交判定流程（2026-08-16 领导决议，现行）

```
配单结果详情卡 [联系供应商]
   → 弹窗（文案：查看即认定购买，单子将绑定至您名下并立即下架）
   → 用户确认 → 后端写：查看日志 + 成交记录（payment_status='pending_settlement' 待结算，
     product_snapshot.dealSource='view-bind'）+ 快照下架（is_active=false）
   → 商品从搜索结果消失；个人中心「我联系过的挂单」展示"已绑定·待结算"
   → 结算系统（另开发）关联单据状态，用户上传各环节照片/证明材料
```

> 追溯链路：trade_contact_view_logs（查看审计）+ trade_deal_records（绑定/结算锚点）+ 快照下架标记，
> 后期可完整追溯"谁在什么时候绑定了哪单、结算到哪一步"。

### 2.2 商品下架实现（自有过滤，不调秀吗接口）

- 秀吗没有可用的下架接口（现有 Proxy 仅 6 个只读方法），**不调用秀吗下架**。
- 我方数据库记录「已成交商品 ProductId」，搜索链路（`queryXiumaProductSearch` 结果）过滤掉已成交商品，不再展示。
- 注意：秀吗侧商品仍在架，若同一商品在秀吗侧被他人买走，以秀吗为准，我方记录仅控制本平台展示。

### 2.3 分级交易路径

| 供应商类型 | 识别方式 | 交易方式 |
| --- | --- | --- |
| 秀吗认证（已交保证金） | 秀吗保证金字段 `S.EARNEST_MONEY > 0`（2026-08-13 确认） | **跳转秀吗平台下单，不开放线下电联** |
| 非认证（未交保证金） | `S.EARNEST_MONEY` 为 0 或缺失 | ① 直接线下付款；② 走秀吗担保交易 |

> 商家等级字段 `LV.MEMBER_LEVEL_NAME`（会员/VIP会员/黄金会员/铂金会员/钻石会员）不参与认证判定，仅作卡片展示。

### 2.4 两种货源与联系方式

| 货源类型 | 上架主体 | 联系方式内容 |
| --- | --- | --- |
| 秀吗自营（`P.BUSINESS_MODEL = 0`） | 秀吗帮供应商上架 | **我方客服电话** |
| 供应商自挂（`P.BUSINESS_MODEL = 10`） | 供应商自己挂货 | **供应商本人电话** |

- 供应商电话字段 `TELEPHONE` 已由秀吗接口返回（2026-08-12 上线）。
- 展示逻辑：自营商品无论成交与否展示我方客服电话；供应商自挂商品展示供应商电话（受分级路径与限次约束）。

### 2.5 用户限制与风控

| 规则 | 说明 |
| --- | --- |
| 限次查看 | 单用户每 **3 天仅可查看 1 次**联系方式（认证/非认证商家均受约束，2026-08-13 确认；按 MEMBER_CODE 滚动计次） |
| 付款时限 | 成交后 **24 小时内**须完成付款（2026-08-13 暂定） |
| 超时限权 | 超时未付款 → 限制后续查看权限；系统自动判定（unpaid 且成交超 24h 即视为 timeout），客服也可手工登记；客服登记 paid 后自动解除限制 |

### 2.6 担保交易（过渡期手动处理）

- 货款先打平台账户 → 买方确认收货后结算给供应商。
- 过渡期业务量小，**手动处理**，系统仅记录台账，不急于全链路线上化。

## 三、结算模块（需现在开发）

**背景**：结算体系内部试点，先以两家内部公司测试。

**现有基础**：
- `shared/settlement.interface.ts` 已定义 `ContractType = 'purchase' | 'sale'`
- 前端已有合同管理、交付管理等页面，具备承接交易实体基础

**试点阶段范围**：
1. 成交记录：商品快照 + 成交用户 + 供应商信息 + 成交时间
2. 付款登记：客服人工登记付款状态（未付款 / 已付款 / 超时）
3. 结算台账：担保交易场景「平台收款 → 确认收货 → 结算供应商」手工流转记录

**明确不做**：在线支付通道、自动分账、违约金自动计算。

## 四、数据模型草案

PostgreSQL + Drizzle ORM，表名中文语义命名，用户 ID 一律 `MEMBER_CODE`：

| 表 | 关键字段 | 用途 |
| --- | --- | --- |
| 成交记录表 | product_id、商品快照（材质/表面/规格/仓库/价格/吨数）、buyer_member_code、supplier_id、货源类型（自营/自挂）、供应商类型（认证/非认证）、成交时间 | 成交判定与搜索过滤的数据源 |
| 联系方式查看日志表 | member_code、product_id、supplier_id、查看时间 | 3 天限次计算、审计留痕 |
| 付款登记表 | 成交记录 id、金额、状态（未付款/已付款/超时）、登记人、登记时间 | 客服人工登记 |
| 结算台账表 | 成交记录 id、收款状态、结算状态、备注 | 担保交易手动流转记录（试点） |

建表脚本：`server/database/sql/020-create-trade-tables.sql`（成交记录表 + 联系方式查看日志表）。

## 五、接口草案

**C 端（`/api/trade/*`，新增模块）**：

| 接口 | 说明 |
| --- | --- |
| `POST /api/trade/view-contact` | 校验限次/资格 → 写成交记录 + 查看日志 → 返回联系方式 |
| `GET /api/trade/my-deals` | 我的成交记录列表 |
| `GET /api/trade/view-limit` | 查询当前用户剩余查看次数/冷却状态 |

**搜索链路改造**：`doSearch` 返回结果在展示前过滤已成交 ProductId（前端过滤起步，量大后移后端）。

**ERP 侧（客服/运营）**：
- 成交记录列表（按时间/供应商/用户筛选）
- 付款登记操作（人工改状态）
- 查看限次的豁免/重置
