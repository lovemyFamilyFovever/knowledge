# 消息中心实施方案

> 文档状态：已实施，待验收  
> 编写日期：2026-08-12  
> 适用范围：个人中心“消息中心”与智能广场互动通知  
> 数据策略：不回填上线前历史互动，仅从功能上线后的新互动开始生成通知

## 1. 建设目标

在个人中心“我的广场”下方增加“消息中心”菜单，集中处理智能广场内与当前用户相关的互动通知。

首版包含：

- 有人关注我；
- 有人点赞我的帖子；
- 有人点赞我的评论；
- 有人评论我的帖子；
- 有人回复我的评论；
- 有人收藏我的帖子；
- 每周互动汇总；
- 左侧菜单未读数字；
- 点击单条通知自动已读；
- 当前 Tab 全部已读；
- 从通知跳转到对应帖子或评论；
- 在消息中心直接回复评论；
- 在关注通知中直接回关。

首版不包含：

- “全部”Tab；
- 关注通知跳转到对方个人主页；
- WebSocket 实时推送；
- 邮件、短信、飞书等站外通知；
- 用户删除通知、通知归档、通知偏好设置；
- 上线前历史互动回填。

## 2. 已确认的产品规则

### 2.1 Tab 与通知类型

| Tab | 通知类型 | 说明 |
|---|---|---|
| 关注 | `follow` | 有人新关注了我 |
| 点赞 | `post_like`、`comment_like` | 点赞我的帖子或评论 |
| 评论 | `post_comment`、`comment_reply` | 评论我的帖子或回复我的评论 |
| 收藏 | `post_favorite` | 收藏我的帖子 |
| 互动汇总 | `weekly_summary` | 每周互动汇总 |

没有“全部”Tab。进入页面时优先打开存在未读消息的 Tab；多个 Tab 同时有未读时，优先级为“评论 → 关注 → 点赞 → 收藏 → 互动汇总”；全部无未读时默认打开“评论”。

### 2.2 聚合规则

- 同一帖子收到的多次帖子点赞，聚合成一张卡片；
- 同一评论收到的多次评论点赞，聚合成一张卡片；
- 同一帖子收到的多次收藏，聚合成一张卡片；
- 关注通知一人一条；
- 评论和回复不聚合，每条评论或回复单独展示；
- 周汇总一名用户每周最多一条；
- 左侧未读数按“聚合卡片数”计算，不按底层事件行数计算。

聚合文案例子：

> 张三、李四等 8 人点赞了你的帖子《304冷轧市场分析》

一张已读聚合卡片出现新的点赞或收藏事件后，新事件保持未读，因此该卡片会重新计入未读数。

### 2.3 撤销规则

- 取消帖子点赞：删除该操作人对应的 `post_like` 通知事件；
- 取消评论点赞：删除该操作人对应的 `comment_like` 通知事件；
- 取消收藏：删除该操作人对应的 `post_favorite` 通知事件；
- 取消关注：删除该操作人对应的 `follow` 通知事件；
- 聚合卡片人数根据剩余事件重新计算；没有剩余事件时卡片消失；
- 已生成的周汇总是历史快照，不因后续撤销而追溯修改；
- 自己对自己的帖子或评论产生互动时，不生成通知。

### 2.4 内容不可见规则

关联帖子或评论已删除、隐藏或不可见时：

- 通知记录继续保留至过期；
- 卡片显示“原内容已删除或不可见”；
- 禁止跳转和直接回复；
- 已生成的周汇总不追溯修改。

## 3. 数据设计

### 3.1 新增表

只新增一张 `plaza_notifications` 表，最终 SQL 位于：

```text
server/database/sql/018-create-plaza-notifications.sql
```

通知表保存“面向接收人的通知事件和阅读状态”，现有互动表继续保存业务事实。核心关系如下：

| 通知表字段 | 逻辑关联 |
|---|---|
| `recipient_member_code` | `users.member_code`，通知接收人 |
| `actor_member_code` | `users.member_code`，互动发起人 |
| `news_id` | `plaza_posts.news_id` |
| `comment_id` | `plaza_comments.comment_id` |
| `reply_comment_id` | `plaza_comments.comment_id`，被回复的原评论 |

不设置数据库外键，避免内容删除或用户停用时级联删除历史通知。关联完整性由服务层写入校验和表内 `CHECK` 约束共同保证。

### 3.2 通知表与原互动表的职责

| 数据 | 权威来源 |
|---|---|
| 当前关注关系 | `plaza_follows` |
| 当前帖子点赞关系 | `plaza_likes` |
| 当前评论点赞关系 | `plaza_comment_likes` |
| 当前评论及回复 | `plaza_comments` |
| 当前收藏关系 | `plaza_favorites` |
| 通知接收人、聚合键、幂等键、已读状态 | `plaza_notifications` |
| 已生成的周汇总快照 | `plaza_notifications.metadata` |

通知表不复制帖子正文、评论正文、图片、头像等大字段。列表展示时关联查询原表；原内容不可见时返回统一占位状态。

### 3.3 幂等键与聚合键

| 类型 | `aggregation_key` | `dedupe_key` |
|---|---|---|
| 关注 | `follow:{actorMemberCode}` | `follow:{actorMemberCode}` |
| 帖子点赞 | `post_like:{newsId}` | `post_like:{newsId}:{actorMemberCode}` |
| 评论点赞 | `comment_like:{commentId}` | `comment_like:{commentId}:{actorMemberCode}` |
| 评论帖子 | `post_comment:{commentId}` | `post_comment:{commentId}` |
| 回复评论 | `comment_reply:{commentId}` | `comment_reply:{commentId}` |
| 收藏帖子 | `post_favorite:{newsId}` | `post_favorite:{newsId}:{actorMemberCode}` |
| 周汇总 | `weekly_summary:{periodStartDate}` | `weekly_summary:{periodStartDate}` |

数据库唯一约束为 `recipient_member_code + dedupe_key`。写入时使用 `INSERT ... ON CONFLICT DO NOTHING`，防止接口重试或并发请求产生重复通知。

### 3.4 保留期限

- 通知默认保留 180 天；
- 每日定时任务删除 `expires_at < NOW()` 的记录；
- 页面只读取未过期记录；
- 累计互动统计直接查询现有业务表，不受通知 180 天保留期影响；
- 本期不回填历史数据，因此正常实时事件使用数据库默认过期时间即可。

## 4. 后端方案

### 4.1 代码结构

计划新增或修改以下文件，实际文件名可在实施时按现有模块结构微调：

```text
server/database/schema.ts
server/database/plaza-notification.repository.ts
server/modules/plaza/plaza-notification.service.ts
server/modules/plaza/plaza-notification.controller.ts
server/modules/plaza/plaza-notification-schedule.service.ts
server/modules/plaza/dto/plaza-notification.dto.ts
server/modules/plaza/plaza.service.ts
server/modules/plaza/plaza.module.ts
```

职责划分：

- Repository：通知事件写入、撤销、聚合分页、未读计数、标记已读、统计查询；
- Service：确定接收人、构造键值、过滤自我互动、内容可见性、周汇总生成；
- Controller：身份校验、参数校验和统一响应；
- Schedule：周汇总补偿生成和180天过期清理；
- `PlazaService`：在现有关注、点赞、评论、收藏成功后同步维护通知事件。

### 4.2 互动写入流程

#### 新关注

1. 当前用户关注目标用户成功；
2. 接收人为 `plaza_follows.follow_member`；
3. 操作人为 `plaza_follows.member_code`；
4. 插入 `follow` 事件；
5. 取消关注时删除对应 `dedupe_key`。

#### 帖子点赞或收藏

1. 查询帖子并取得作者 `plaza_posts.member_code`；
2. 作者与操作人相同则跳过通知；
3. 点赞或收藏成功时插入对应事件；
4. 取消时删除对应事件；
5. 同一帖子事件共享 `aggregation_key`，读取时聚合。

#### 评论点赞

1. 查询被点赞评论并取得评论作者；
2. 通过 `plaza_comments.article_id` 映射通知表 `news_id`；
3. 评论作者与操作人相同则跳过通知；
4. 点赞成功时插入，取消时删除；
5. 同一评论事件共享 `aggregation_key`。

#### 评论与回复

1. 一级评论的接收人是帖子作者；
2. 回复的接收人是被回复评论的作者；
3. 若接收人与操作人相同，则不生成通知；
4. `comment_id` 保存本次新评论或新回复；
5. 回复时 `reply_comment_id` 保存被回复的原评论；
6. 评论与回复不聚合。

互动事实和通知事件应在同一个数据库事务中完成，避免出现“互动成功但通知缺失”或“互动已撤销但通知仍存在”。计数字段更新也纳入同一事务。实现前需要针对现有 `Promise.all` 写入逻辑做小范围事务化重构，不改变现有接口响应格式。

### 4.3 消息查询接口

考虑飞书环境对带身份信息请求的 CSRF 要求，消息中心的鉴权查询建议使用带 JSON body 的 POST 接口；前端必须同时携带 `Content-Type` 和 `x-suda-csrf-token`，并沿用现有本地会话认证机制。

建议接口：

| 接口 | 用途 |
|---|---|
| `POST /api/plaza/notifications/query` | 按 Tab 游标分页查询聚合卡片 |
| `POST /api/plaza/notifications/unread-counts` | 查询总未读数及各 Tab 未读数 |
| `POST /api/plaza/notifications/interaction-stats` | 查询累计粉丝、获赞、评论回复、被收藏 |
| `POST /api/plaza/notifications/read` | 将一张聚合卡片标为已读 |
| `POST /api/plaza/notifications/read-category` | 当前 Tab 全部已读 |

所有接口从服务端会话取得 `MEMBER_CODE`，不接受前端传入接收人编号，避免越权读取或修改其他用户的通知。

分页对象是聚合后的卡片，不是底层事件行。建议使用 `latestOccurredAt + aggregationKey` 游标分页，避免新互动插入后产生页码漂移。

### 4.4 未读统计

未读统计必须按 `aggregation_key` 去重：

```text
总未读数 = 所有未读事件中不同聚合卡片的数量
Tab 未读数 = 该 Tab 对应通知类型中不同聚合卡片的数量
```

点击卡片时，将当前接收人、通知类型、`aggregation_key` 对应的全部事件更新为：

```text
is_read = true
read_at = 当前时间
updated_at = 当前时间
```

### 4.5 累计互动统计

消息中心顶部始终展示实时累计数据，不写入通知表：

- 粉丝：当前仍有效的关注者数量；
- 获赞：当前帖子点赞数与评论点赞数之和；
- 评论与回复：当前收到的一级评论和回复总数；
- 被收藏：当前帖子被收藏总数。

累计统计直接查询现有业务表，因此取消互动会实时反映，也不会因通知超过180天被清理而减少。

### 4.6 每周互动汇总

统计周期采用北京时间，上周一 `00:00:00` 至本周一 `00:00:00`，统计：

- 新增粉丝；
- 帖子获赞；
- 评论获赞；
- 帖子被收藏；
- 新增评论；
- 收到回复。

计划每天上午执行一次“上一完整周是否已生成”的补偿检查，而不是只在周一运行一次。正常情况下周一生成；如果周一服务停机，可在恢复后补生成。`recipient_member_code + dedupe_key` 唯一约束确保不会重复。

规则：

- 上一周没有任何互动时不生成；
- 周汇总保存到 `metadata`，`metadata_version = 1`；
- 有完整前一周数据时展示环比，没有时不展示；
- 功能上线后的第一个统计周期可能不足一周，应在 `metadata` 标记为部分周期并隐藏环比；
- 已生成的汇总不因后续取消互动而修改；
- 不需要额外的周汇总执行记录表。

建议 `metadata` 结构：

```json
{
  "periodStart": "2026-08-03T00:00:00+08:00",
  "periodEnd": "2026-08-10T00:00:00+08:00",
  "isPartialPeriod": false,
  "metrics": {
    "newFollowers": 12,
    "postLikes": 36,
    "commentLikes": 8,
    "postFavorites": 5,
    "newComments": 9,
    "commentReplies": 4
  },
  "comparison": {
    "newFollowers": 4,
    "postLikes": 6,
    "commentLikes": 2,
    "postFavorites": -2,
    "newComments": 4,
    "commentReplies": 1
  }
}
```

## 5. 前端方案

### 5.1 路由和菜单

- 新增路由：`/personal/notifications`；
- 新增页面：`client/src/pages/PersonalNotificationsPage.vue`；
- 在 `PersonalCenterLayout.vue` 的“我的广场”下方增加“消息中心”；
- 使用 Lucide `Bell` 或 `BellRing` 图标；
- 菜单右侧显示总未读数字，超过99显示 `99+`；
- 当前路由激活时仍保留未读数字，不用选中圆点替代。

### 5.2 页面布局

页面建议由三层构成：

1. 顶部累计互动统计：粉丝、获赞、评论与回复、被收藏；
2. 分类 Tab：关注、点赞、评论、收藏、互动汇总；
3. 聚合通知列表：头像、通知文案、内容摘要、时间、操作区。

页面需要加载中、空状态、错误重试、分页加载和不可见内容状态。颜色必须使用项目已有语义色，不使用 Tailwind 预设色。

### 5.3 卡片交互

- 点击帖子点赞、评论、回复或收藏通知：先标记已读，再跳转 `/promo/plaza/post/:newsId`；
- 评论类通知带 `commentId` 查询参数，详情页加载评论后定位并短暂高亮；
- 关注通知主体首版不跳转；
- “回关”仅调用现有关注接口，成功后按钮变为“已回关”；
- 评论和回复卡片可展开输入框，提交时复用现有评论接口；
- 直接回复成功后显示“已回复”，并由后端为对方生成新的回复通知；
- 当前 Tab 提供“全部已读”，不提供跨所有 Tab 的“一键全部已读”。

### 5.4 评论定位

帖子详情页需要支持：

```text
/promo/plaza/post/{newsId}?commentId={commentId}
```

加载评论完成后：

1. 查找目标一级评论或回复；
2. 将对应 DOM 滚动到评论容器可视区域；
3. 添加短暂高亮；
4. 找不到评论时显示“原评论已删除或不可见”。

### 5.5 未读轮询

- 进入个人中心时立即获取未读数；
- 个人中心路由切换时刷新；
- 页面停留期间每60秒刷新一次；
- 消息中心完成已读、回关、回复等操作后立即刷新；
- 离开个人中心或组件卸载时清除定时器；
- 首版不引入 WebSocket。

## 6. 上线数据边界与发布顺序

### 6.1 历史数据

明确不执行任何历史通知回填：

- SQL 文件不包含 `INSERT ... SELECT`；
- 不扫描上线前已有关注、点赞、评论、回复或收藏；
- 只有新后端版本部署之后成功产生的互动才写通知表；
- 累计互动统计仍可展示现有业务表中的全部有效数据；
- 第一个周汇总仅统计功能上线后的通知事件。

### 6.2 推荐发布顺序

1. 审批并备份目标数据库；
2. 手动执行 `018-create-plaza-notifications.sql`；
3. 核验表、约束和索引；
4. 部署后端 Schema、Repository、Service、Controller 和定时任务；
5. 验证7类通知写入、撤销和未读接口；
6. 部署前端菜单、页面、轮询和评论定位；
7. 观察日志和表增长情况；
8. 确认稳定后开放入口。

必须先建表再部署会写通知的后端，避免新版本调用不存在的表。

## 7. 测试与验收

### 7.1 数据写入

- 7种通知类型字段组合满足约束；
- 自我互动不产生通知；
- 重复请求不产生重复事件；
- 取消关注、点赞和收藏能准确删除对应事件；
- 评论和回复接收人正确；
- 上线前数据没有被回填。

### 7.2 聚合与未读

- 多人点赞或收藏同一对象只显示一张卡片；
- 聚合人数、头像和时间正确；
- 未读数字按卡片计数；
- 点击卡片后相关事件全部已读；
- 已读卡片出现新事件后重新变为未读；
- 当前 Tab 全部已读只影响该分类。

### 7.3 页面交互

- 默认 Tab 选择规则正确；
- 回关只执行关注，不跳转个人主页；
- 评论通知可直接回复；
- 跳转帖子后能定位评论；
- 删除或隐藏内容显示不可见状态；
- 60秒轮询不会重复创建定时器；
- 移动端菜单和消息列表可正常滚动。

### 7.4 定时任务

- 北京时间周周期计算正确；
- 同一用户同一周只生成一条汇总；
- 无互动不生成；
- 服务停机恢复后可补生成；
- 180天过期数据能够分批清理；
- 清理任务失败只记录日志，不影响主业务。

### 7.5 工程验证

实施完成后、同步飞书环境前必须执行：

```text
npm run type:check
npx vite build
```

并检查没有新增日志、临时测试文件、构建产物或配置文件意外改动。

## 8. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 互动与通知不一致 | 同库事务、唯一幂等键、撤销时同步删除 |
| 聚合分页重复或遗漏 | 使用稳定游标，不使用事件行页码分页 |
| 未读数被事件数放大 | 按 `aggregation_key` 去重统计 |
| 定时任务重复生成 | 唯一约束 + `ON CONFLICT DO NOTHING` |
| 服务停机错过周一任务 | 每日补偿检查上一完整周 |
| 通知表持续膨胀 | 180天保留、过期索引、每日分批清理 |
| 内容删除导致跳转异常 | 查询时检查状态，返回不可见标记 |
