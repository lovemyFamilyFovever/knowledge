## 一、初始问题诊断（v2.3 时期，仍然成立）

679条用户反馈分析揭示的核心问题：

| # | 问题 | 表现 |

| 1 | 缺少Query Understanding | 用户问"304下周会涨吗"被原样做向量检索 |
| 2 | 无工具调用（Function Calling） | 既查不了价格数据库，也搜不了实时新闻 |
| 3 | 数据形态单一 | 结构化数据（价格/库存）当文档用，无法SQL查询 |

## 二、为什么5步Pipeline是错的方向

v2.3→v2.5 尝试用本地代码解决上述问题：
```
预处理 → 别名解析 → QU意图分类 → 查询提示 → 百炼
```

**核心矛盾**：用正则/if-else/词典去替代LLM的语义理解能力。规则引擎比LLM脆弱得多。

**典型案例**：
- 正则 `(?<!\d)(\d+)(?!\d*mm)` 把"2B"补成"2mmB"，表面类型被破坏
- QU分类把"304的成分是什么"（应走知识库）路由成QU01价格查询
- 每个新场景都需要加一段代码，10万种问题需要10万个约束

---

## 三、v3.0 的解决方案

**删除全部本地预处理，让百炼Agent 2.0自主处理。**

```
v2.x: 用户 → 正则破坏 → 别名查表 → qwen-turbo分类 → 提示组装 → 百炼
v3.0: 用户 → 后端治理与轻量路由 → 百炼 Agent → 后端结构化与清洗
```

百炼Agent 2.0具备的能力：
- 读Schema自己判断该查哪个表
- 根据枚举值解析"430/2B"为材质+表面
- 自主决定用executeQuerySql、knowledgeBaseSearch 还是合规联网搜索
- 生成SQL、执行查询、格式化回答

### 3.1 v3.0 的演进：从"纯直通"到"轻量路由 + 后端职责收口"

v3.0 初版是“纯直通”，后续在实测中补回并扩展了以下后端职责：

| 职责 | 文件 | 解决的问题 |
|------|------|-----------|
| 粗粒度路由 | ai-query-policy.ts | 外部官方信息无法核实 → 直接返回；内部资讯需强制查内部表 |
| 图表意图判定 | price-chart-policy.ts | 判断该不该出图、出哪种图，注入图表规则 |
| 联网白名单 | search-source-policy.ts | 竞品平台/不可信来源不得作为依据 |
| 结构化图表构建 | ai-chart-builder.ts | 模型自由 ECharts 不可控，改由后端从查询结果构建 |
| 数据访问与来源治理 | ai-governance.service.ts | INTERNAL/EXTERNAL、敏感数据和受限第三方来源不能只靠 Prompt |
| 数据能力核验 | data-capability-registry.ts | “有没有数据”必须实际查询并返回标准四态 |
| 指标与结论 | ai-data-insight-builder.ts | 图表、指标、表格、结论统一使用 canonical 数据口径 |
| 流式稳定展示 | structured-message-flow.ts | SSE 乱序、正文快照和结构化组件不能互相覆盖 |

**关键原则**：这些职责是"边界约束"（做什么/不做什么），**不是**"语义理解"（怎么回答）。语义理解仍全部交给百炼。

## 五、经验教训

1. **LLM比正则聪明**：不要用确定性规则替代语义理解
2. **Prompt优于代码**：完善的System Prompt比1000行预处理代码更可靠
3. **信任模型**：现代Agent 2.0已具备自主规划能力，不需要外部语义路由
4. **简单即正确**：每删掉一层本地逻辑，准确率不降反升
5. **但边界约束不可省**：轻量路由（内部资讯强制内部表、外部信息白名单）、图表生成收口、展示清洗这三类"护栏"是 v3.0 后期补回的，纯直通在可控性上不足
6. **数据可核验**：`validateAiChartOption` 的 evidence 校验确保图表数据来自本轮真实查询结果，防止模型编造
7. **同源比“看起来一致”更重要**：图表、指标、表格和结论必须复用同一 canonical series，不能分别解析后再对数字
8. **流式第一句不等于结论**：模型开头可能描述查询计划，必须在完整结果和可信数据到齐后生成结论卡
9. **前端不能依赖 SSE 顺序**：事件传输顺序与最终页面布局解耦，状态合并必须绑定生成任务和目标消息
10. **权限失败要收紧**：权限服务异常按 EXTERNAL 处理，不得为了可用性扩大内部数据范围
