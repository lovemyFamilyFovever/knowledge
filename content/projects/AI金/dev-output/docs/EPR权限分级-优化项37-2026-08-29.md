# #37 ERP 权限分级

日期：2026-08-29
范围：数据库迁移 + 后端权限模块 + 前端侧栏按权限动态过滤 + 权限管理页

## 目标

实现 ERP 后台「菜单可见性」分级：每个登录账号在 `erp_user_account.permissions`（JSONB，存可访问菜单 path 数组）中维护可见菜单；admin 拥有全部。超管可在「权限分级」页为各账号分配菜单（含运营/采集/只读角色预设）。

## 设计决策

- 权限粒度 = 菜单项（前端 `erp/menu.ts` 为唯一维护点，与权限管理页勾选清单、ErpLayout 展示一致）。
- **约束层级 = 仅前端菜单过滤 + 权限管理接口鉴权**：现有业务接口未逐个按 permissions 拦截（改动面过大、风险高），本次聚焦入口可见性。属安全局限，记录如下。
- 角色用菜单集合表达，不建独立角色表；管理页提供「运营/采集标注/只读」预设一键填充。
- `admin` 及环境变量兜底账号（`ERP_ADMIN_USER`）为超管：登录返回 `permissions:['*']` 且 `isAdmin:true`。

## 复评修正（2026-08-29，双 Agent 审查后）

- `ErpAuthService.getPermissions` 读库失败兜底由「回退全量 ['*']」改为「普通账号回退空数组 []」：避免普通账号在瞬时读库错误时误获全量菜单（最少权限）。
- `schema.ts` `permissions` 默认值由 `.default([])` 改为 `.default(sql\`'[]'::jsonb\`)`，与 060 迁移的 DDL 一致，避免 drizzle 生成迁移时失真。
- 类型检查复跑通过。

## 接口级拦截（补充实现，2026-08-29 续做）

在原有「菜单可见性分级」之上补齐**服务端接口级授权**，普通账号即使绕过前端直连 URL 也无法访问未授予的接口。

- 新增 `erp/server/erp-path-permission.ts`：集中维护「API 路由前缀 → 所需菜单权限」映射（与 `erp/menu.ts` 共用同一套 `/erp/*` path），`resolveRequiredPermission` 按**最长前缀**匹配。
- 扩展 `erp/server/erp-auth.guard.ts`（`canActivate` 改 async）：token 校验后，超管（`permissions` 含 `'*'`）放行 → 哨兵 `@any` 路由（侧边栏）放行 → 未映射路由默认**仅超管**（permission / trade-admin / error-logs / operation-logs）→ 已映射路由要求账号 `permissions` 含所需菜单，否则 403。
- 词典管理粒度：仅写/管理端点（`/api/collect/dicts/tables`、`/api/collect/dicts/refresh`）归 `/erp/dict-admin`；只读枚举 `/api/collect/dicts`、`/dicts/links` 供采集工作台下拉使用，归 `/erp/data-collect`，避免误拦仅有 data-collect 权限的用户。

## 停用账号 Token 吊销（补充实现，2026-08-29 续做）

- `ErpAuthService` 新增 `resolveAccountAccess()`：一次查询同时返回账号 `isActive` 与 `permissions`；超管恒 `active:true` + `permissions:['*']`；普通账号实时读库，读库失败按 `active:false`（fail-closed）。
- `ErpAuthGuard.canActivate`（已 async）：token 校验通过后每请求调用 `resolveAccountAccess`，**若 `isActive=false` 即刻拒绝（HTTP 401「账号已停用」）**，实现停用账号已签发 token 的即时吊销（不再依赖 30 天 token 自然过期）。该查询同时复用做接口级权限校验，无额外一次查询。

### 停用账号 + trade-admin 端到端验证（localhost:8000，账号已清理）

1. admin 新增 `acc_tradetest`（仅 `/erp/order-admin`）→ `acc_tradetest` 登录成功。
2. **trade-admin 映射**：`acc_tradetest` 调 `GET /api/erp/trade-admin/deals` → `code:0`（持有 `/erp/order-admin` 可访问）。
3. **停用吊销**：admin `PUT /api/erp/permission/users/acc_tradetest` 置 `isActive:false` → 该账号 **原 token** 再调同一接口 → HTTP 401 被拒。
4. 清理测试账号。`npm run type:check:server` 通过。

## 已知安全局限（待后续增强）

- **接口级授权已实现，前端菜单过滤依赖 `localStorage` 仍可被篡改**：现已由 `ErpAuthGuard` 在服务端按路径鉴权（见「接口级拦截」），即使前端篡改 `erp_permissions`/`erp_is_admin` 也只能看到菜单、调不动接口，数据安全有服务端兜底。前端菜单展示仍读 localStorage，属展示层，无害。
- **`/api/erp/sidebar` 对任意有效账号放行**：该端点返回静态侧边栏菜单（`/vip-admin` 等旧格式），且前端目录已改为 `erp/menu.ts` + 权限过滤驱动，此端点当前无客户端调用，属低敏感遗留。如需收紧可改归超管/按权限过滤。
- **普通账号可达 `/erp/permission-admin` 页面**（router 守卫只看 token 是否存在），但页面拉数据会被后端返回 403 拦截，数据安全。403 走 Nest 默认错误体（`{statusCode,message}`）而非 `{code:-1,msg,data}`，前端 `api.ts` 仅判 `code!==0`，故非超管会看到通用"请求失败"而非具体原因。
- **sanitize 白名单为前缀 + 后端硬编码 `/erp/permission-admin`**：后端剔除项与前端 `adminOnly` 各维护一份，日后在 `menu.ts` 增 adminOnly 项时后端不会自动跟进（普通账号可用构造请求被授予超管菜单）。当前仅"权限分级"一项，无实际风险。
- **超管保护不对称**：`deleteUser` 禁止删任何超管；`updateUser` 仅拦截"超管且带 permissions 字段"，若 `ERP_ADMIN_USER` 环境变量另配了超管账号，可用 PUT 重置主 `admin` 的密码/停用。属配置关联的低概率边缘。
- **密码明文入库**：`erp_user_account.password` 为明文文本比较（既有设计），本页新增的设/重置密码沿用该存储。建议后续引入 bcrypt 哈希。
- 依赖 **060 迁移已应用**：否则 `erp-permission` 模块原生 SQL 会因列不存在报错。上线前务必执行 `server/database/sql/060-add-erp-user-permissions.sql`。
