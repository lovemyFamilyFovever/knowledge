# 接口统一改造 · 批次3 · 全局异常过滤器失败信封

日期：2026-08-29
范围：后端全局异常过滤器 + 前端错误解包收敛
目标：预留的统一信封契约 `{code, message, data:null}` 落地到「未捕获异常」出口。

## 改造前问题

全局异常过滤器 `global-exception` 只在 `{ code:0 , message , data }` 成功出口统一，但未捕获异常走的是另一套信封：

```json
// 改造前
{ "error": { "code": "NOT_FOUND", "message": "资源不存在", "details": "...", "timestamp": 1720000000 } }
```

- `code` 是字符串（`ResponseCode` 枚举），而成功信封 `code` 是数值（`0`），口径不一致。
- 前端要同时兼容成功信封「`code === 0` 判定」和错误信封「`error.message` 取消息」，两套分支。

## 目标契约

失败响应全局统一为：

```json
{ "code": 401, "message": "资源不存在", "data": null }
```

- `code`：数值 HTTP 状态码（与成功信封 `0`、以及 vip/announcement 已用的 `fail(message, 401/400/500)` 数值口径一致）。
- `data`：恒为 `null`。
- 原始 `details/fieldErrors/stack/cause/timestamp` 不再进入响应体（仅在错误日志中保留完整信息）。

## 改动内容

### 后端 `server/common/filters/exception.filter.ts`
- 删除 `ApiErrorResponse` 与 `HTTP_STATUS_TO_RESPONSE_CODE_MAP` 的引入（不再构造 `{error:{...}}`）。
- 将四类异常（`BusinessException` / `HttpException` / PG `22P02` / 未知异常）统一收敛为「只计算 `message` 与数值 `httpStatus`」。
- 写错误日志逻辑不变（`errorMessage` 改用收敛后的 `message`）。
- 响应主体改为 `res.status(httpStatus).json({ code: httpStatus, message, data: null })`。

### 前端 `client/src/api/settlement.ts`
- 非 2xx 错误分支由「读 `body.error.message` 兼容旧格式」收敛为「只读 `body.message`」，与统一信封对齐。
- `code === 0` 成功判定逻辑保持不变（批次试点已对齐）。

## 兼容性分析

- 后端 `AuthGuard` 抛出的 401 / `CsrfMiddleware` 的 403 / `NotFoundException` 等均走本过滤器，输出统一信封。
- 前端 `settlement.ts` 的 HTTP 错误分支此前已用 `body.error?.message || body.message` 兜底，改造后 `body.message` 直接命中，无需额外分支。
- ERP `api-test` 中的 `result.error` 属于其自研旁路结构，与 Nest 全局过滤器无关，不受影响。

## 验证结果

- `npm run type:check`（server + client）通过。
- `npm test -- --silent`：**143 用例全部通过**；2 个失败套件（`ai-governance.service.spec.ts`、`local-retrieval-flow.spec.ts`）为 ai 模块**预存在**的 `PipelineService` 三参签名未更新问题，与本批无关（批次2已记录同样结论）。
- `proxy-auth-block.e2e-spec.ts` 走 `Test.createTestingModule` 单独实例化 ProxyController，未加载全局过滤器，其 `{code:-1,data:null}` 来自 controller 自身，不受影响；且默认 jest `testMatch` 不含 `*.e2e-spec.ts`，不阻塞常规单元测试。
