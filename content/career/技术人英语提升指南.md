### 2.2 RFC文档写作指南

RFC（Request for Comments）文档是技术标准的核心。以下是写作结构：

```python
class RFCDocumentTemplate:
    """
    RFC文档结构模板
    """
    
    def __init__(self):
        self.sections = {
            "1. Abstract": "简明概述提案的技术解决方案",
            "2. Introduction": "问题背景和解决方案概述",
            "3. Terminology": "关键术语定义",
            "4. Requirements": "详细技术要求",
            "5. Proposed Solution": "具体实施方案",
            "6. Security Considerations": "安全考量",
            "7. IANA Considerations": "协议注册相关",
            "8. References": "参考文献"
        }
    
    def generate_rfc_example(self):
        """
        生成RFC文档示例片段
        """
        return """
# RFC 1234: Enhanced Authentication Protocol for IoT Devices

## 1. Abstract

This document specifies an enhanced authentication protocol for Internet of Things (IoT) devices. The protocol provides mutual authentication between devices and servers while maintaining low computational overhead suitable for resource-constrained devices.

## 2. Introduction

Current IoT authentication mechanisms suffer from several limitations:
- High computational requirements
- Vulnerability to replay attacks
- Lack of forward secrecy
- Poor scalability in large deployments

This RFC proposes a lightweight authentication protocol that addresses these issues while maintaining compatibility with existing infrastructure.

## 3. Terminology

- **IoT Device**: A resource-constrained computing device with network capability
- **Authentication Server (AS)**: The central server responsible for device authentication
- **Session Key**: A cryptographic key established during authentication
- **Forward Secrecy**: Property ensuring that compromise of long-term keys doesn't compromise past session keys

## 4. Requirements

### 4.1 Functional Requirements
- R1: Support mutual authentication between device and server
- R2: Establish session keys for subsequent communication
- R3: Support devices with limited computational power

### 4.2 Performance Requirements
- R4: Authentication handshake must complete within 500ms
- R5: Memory usage must not exceed 10KB on device
- R6: Support 10,000 concurrent authentications

## 5. Proposed Solution

### 5.1 Protocol Overview
The proposed protocol uses elliptic curve cryptography (ECC) with the following steps:
1. Device initiates authentication request
2. Server responds with challenge
3. Device computes and sends response
4. Server verifies and establishes session key
5. Mutual confirmation and key derivation

### 5.2 Message Format
```
+--------+----------+----------+--------+
| Version | DeviceID | Challenge | Payload |
+--------+----------+----------+--------+
|  1 byte | 4 bytes  |  16 bytes |  N bytes |
+--------+----------+----------+--------+
```
"""
```

def get_user_data(user_id):

## 🚨 Security Concern: SQL Injection Vulnerability

**Severity**: Critical
**File**: `src/api/users.py:78`
**Line**: `cursor.execute(f"SELECT * FROM users WHERE name = '{name}'")`

### Problem Description
The code uses f-string interpolation directly in SQL query, making it vulnerable to SQL injection attacks.

### Attack Example
An attacker could input: `name = "'; DROP TABLE users; --"`
Resulting query: `SELECT * FROM users WHERE name = ''; DROP TABLE users; --'`

### Recommended Fix
Use parameterized queries:

cursor.execute(f"SELECT * FROM users WHERE name = '{name}'")

cursor.execute("SELECT * FROM users WHERE name = ?", (name,))

2. Add SQL injection testing to CI/CD pipeline
3. Consider using ORM (like SQLAlchemy) which handles escaping automatically
