# 消息投递语义


> 📌 **导航**：本文是 **消息投递语义** 词条，属于 middleware 术语集。相关枢纽：[[ESB 与服务网格（Service Mesh）]]、[[GraphQL实践]]、[[Kafka深入]]、[[RabbitMQ vs Kafka vs Pulsar]]、[[gRPC深入]]。

## 定义

**一句话定义：** 消息投递语义(Message Delivery Semantics)描述消息队列/流处理系统对"消息被投递给消费者"的可靠性保证级别,主要有三种:至多一次(at-most-once,可能丢)、至少一次(at-least-once,可能重复)、恰好一次(exactly-once,不丢不重);它决定了应用需要如何处理丢失与重复。

**通俗类比：** 像寄信的三种承诺——"最多寄一次"(可能寄丢就不管了);"至少寄一次"(没收到回执就一直重寄,可能寄重);"恰好寄一次"(保证不多不少正好一次,最难做到)。

> 多义说明:投递语义与消息确认(ack)、幂等消费密切相关;"恰好一次"在分布式下代价高,常靠幂等来近似达成。本文讨论三种语义。

## 原理与机制

- **at-most-once:** 发送后不等确认(或先提交后处理),可能丢失,但绝不重复。
- **at-least-once:** 处理后再确认(ack),未确认则重投,保证不丢但可能重复(需消费端幂等)。
- **exactly-once:** 理论上不丢不重;实现代价高(如 Kafka 事务 + 幂等生产者,或"至少一次 + 消费端去重/幂等"达成效果上的 exactly-once)。
- **关键:** 确认时机(处理前/后)与幂等性共同决定实际语义。

## 关键组成

| 组成 | 说明 |
|------|------|
| at-most-once | 可能丢、不重复 |
| at-least-once | 不丢、可能重复 |
| exactly-once | 不丢不重(代价高) |
| ack 机制 | 确认时机决定语义 |
| 幂等消费 | 应对重复投递 |

## 应用场景

- 消息队列(Kafka、RabbitMQ、RocketMQ)
- 流处理(Flink 的 exactly-once)
- 可靠事件传递
- 订单/支付等对不丢不重敏感的场景

## 优点与局限

- 优点:明确可靠性契约,指导应用设计。
- 局限:exactly-once 代价高(性能/复杂度);跨系统真正的 exactly-once 很难;at-least-once 需消费端幂等;语义误用会导致数据错误。

## 常见误区

- "恰好一次"在分布式系统中很难真正做到,常是"至少一次 + 幂等"达到等效。
- at-least-once 必然可能重复,消费端要幂等。
- 投递语义 ≠ 顺序性(两者相互独立,见 [[消息顺序性]])。
- 确认时机(先处理后 ack)决定是 at-least-once 还是 at-most-once。
