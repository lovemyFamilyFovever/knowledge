# ESB 与服务网格（Service Mesh）

> 📌 **导航**：本文对比两代集成/治理架构——**ESB**（中心化企业服务总线）与 **Service Mesh**（去中心化 Sidecar 网格），并展开 Istio/Envoy/服务治理/mTLS 等。服务网格的系统性介绍另见专门词条 [[服务网格]]，治理能力另见 [[微服务治理术语百科]]。

## 定义

**一句话定义：** ESB（企业服务总线）是以中央总线统一做协议转换、消息路由与数据映射的中心化集成架构；Service Mesh（服务网格）则是以每个服务旁的 Sidecar 代理接管东西向通信、提供 mTLS、可观测性与流量治理的去中心化基础设施——二者是企业集成与服务治理的两代架构。

**通俗类比：** ESB 像机场中央塔台，所有航班都经它调度协调；Service Mesh 像给每栋楼配一个私人管家，就近处理收发、身份核验与出入登记，住户（业务代码）专心做自己事。

> 多义说明：Istio/Envoy 实现细节、xDS、流量镜像、故障注入等系统性内容见 [[服务网格]]；本文聚焦"两代架构对比与选型"。

## 为什么需要它

异构系统要互通、服务间通信要安全可控可观测。早期用中心化 ESB 把集成逻辑收拢到总线，直观但成单点与瓶颈、在弹性微服务下显臃肿；微服务时代改用去中心化 Service Mesh，把治理下沉到 Sidecar，业务无感知、语言无关，代价是多一跳延迟与运维组件。理解两代取舍，才能按集成场景选对架构。

## 核心机制

- **ESB（中心化）：** 总线承担协议转换（HTTP↔SOAP↔JMS）、内容路由、数据映射（XSLT），适合多系统对接、遗留系统改造、协议异构、统一认证审计。局限：单点故障、性能瓶颈（全流量过总线）、微服务下过度工程、商业 ESB 厂商绑定。
- **Service Mesh（去中心化）：** 数据面由每服务旁的 Envoy Sidecar 透明代理东西向流量，控制面（Istio 1.5+ 的 istiod）下发配置；提供流量管理（路由/金丝雀/镜像）、mTLS 安全、可观测性三大能力。
- **服务治理能力：** 负载均衡、熔断（关闭→失败率超阈值→打开→半开探测→恢复）、限流（令牌桶/漏桶/滑动窗口）、重试（指数退避 + 幂等）、超时，均以声明式规则配置在网格层。

| 能力 | 说明 | 实现方式 |
|------|------|----------|
| 负载均衡 | 请求分配到多实例 | 轮询、加权、一致性哈希 |
| 熔断 | 快速失败防级联 | Hystrix/Sentinel/Envoy |
| 限流 | 控制请求速率 | 令牌桶/漏桶/滑动窗口 |
| 重试 | 失败自动重试 | 指数退避 + 幂等 |

- **Envoy xDS：** 数据面经 LDS/RDS/CDS/EDS 等发现协议从控制面动态拉配置（详见 [[服务网格]]）。

## 具体示例

遗留集成：订单(REST)、CRM(SOAP)、财务(JMS) 协议各异，经 ESB 统一转换与路由互通。云原生灰度：Istio 用 VirtualService 把 order-service 流量按 90%/10% 权重路由到 v1/v2、并以 PeerAuthentication 强制 STRICT mTLS，全由 Sidecar 完成、不改业务代码。

## 何时用 / 何时不用

- **用 ESB：** 跨协议/跨异构系统、遗留系统对接、需集中审计与安全管控的企业集成。
- **用 Service Mesh：** 复杂微服务集群的东西向治理、需统一 mTLS/可观测性/流量策略且语言栈多样。
- **都不用：** 单体或简单微服务、少量服务——上总线或网格都过重，简单网关/库级治理更划算。

## 优劣与代价

✅ ESB 集中集成、协议异构友好；Service Mesh 透明、语言无关、去中心无单点、治理与业务解耦。
⚠️ ESB 是单点与吞吐瓶颈、易厂商绑定；Service Mesh 每 Pod 额外资源、多一跳延迟、调试运维复杂。
⚠️ 两者都属基础设施，规模不大时是过度工程。

## 与相关概念的区别

- **ESB vs Service Mesh：** 中心化总线 vs 去中心化 Sidecar；前者重异构集成、后者重东西向治理。
- **Service Mesh vs 传统 API 网关：**

| 维度 | 传统 API 网关 | 服务网格 |
|------|---------------|----------|
| 部署位置 | 集群入口 | 每个服务旁 |
| 保护范围 | 南北向（外部→内部） | 东西向（服务间） |
| 通信协议 | HTTP 为主 | 任意 TCP/HTTP/gRPC |
| 运维模式 | 集中式 | 声明式 + 分布式 |
| 代表产品 | Kong、Nginx、APISIX | Istio、Linkerd |

- **vs [[gRPC深入]]：** gRPC 是"点"上的高效 RPC 调用，Service Mesh 是把治理下沉到边、与业务语言无关的统一层。

## 常见误区

- ESB 和服务网格是同一类架构，只是名字新旧不同。
- 服务网格主要治理南北向（外部到内部）流量，等同于 API 网关。
- Sidecar 模式没有任何代价，所有系统都应无条件上服务网格。

## 面试速答

> 🎯 两代集成治理架构：ESB 中心化总线，统一做协议转换与路由，胜在对接遗留异构、败在单点瓶颈；Service Mesh 去中心化，每服务旁挂 Envoy 经 xDS 拉配置，透明接管东西向流量并提供 mTLS、熔断限流与可观测，代价是多一跳与运维复杂度。南北向归网关、东西向归网格，规模小都别上。
