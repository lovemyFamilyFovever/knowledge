# ESB 与服务网格（Service Mesh）

> 📌 **导航**：本文对比两代集成/治理架构——**ESB**（中心化企业服务总线）与 **Service Mesh**（去中心化 Sidecar 网格），并展开 Istio/Envoy/服务治理/mTLS 等。服务网格的系统性介绍另见专门词条 [[服务网格]]，治理能力另见 [[微服务治理术语百科]]。

## ESB（企业服务总线）

### 一句话定义
ESB 是一种**企业级集成架构模式**，通过一个中央总线来连接和协调不同系统之间的通信，实现协议转换、消息路由和数据转换。

### 通俗类比
像一个大型机场的中央调度塔：所有航班（不同系统）都通过塔台（ESB）来协调起降，塔台负责翻译不同航空公司的语言（协议转换），并决定飞机该去哪个停机位（路由）。

### 具体示例

```
┌─────────────────────────────────────────────────┐
│                    ESB                           │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐      │
│  │ 协议转换  │  │ 消息路由  │  │ 数据映射  │      │
│  │ HTTP↔SOAP│  │ 内容路由  │  │ 格式转换  │      │
│  │ JMS↔REST │  │ 基于规则  │  │ XSLT映射 │      │
│  └──────────┘  └──────────┘  └──────────┘      │
└───────────┬──────────┬──────────┬────────────────┘
            │          │          │
      ┌─────┴──┐  ┌────┴───┐  ┌──┴─────┐
      │ 订单系统│  │ CRM系统 │  │ 财务系统│
      │ (REST) │  │ (SOAP) │  │ (JMS)  │
      └────────┘  └────────┘  └────────┘
```

### 适用场景

| 场景 | 说明 |
|------|------|
| 企业系统集成 | ERP、CRM、OA等多系统对接 |
| 遗留系统改造 | 老系统通过ESB暴露新接口 |
| 协议异构 | HTTP/SOAP/JMS/MQ等混合调用 |
| 安全管控 | 统一认证、审计、限流 |

### 局限性

- **单点故障**：总线挂了所有通信中断
- **性能瓶颈**：所有流量过总线，吞吐受限
- **过度工程**：微服务场景下显得臃肿
- **厂商绑定**：商业ESB（IBM、Oracle）迁移成本高

## 服务网格（Service Mesh）

### 一句话定义
服务网格是一种**基础设施层**，通过在每个服务旁部署代理（Sidecar），来处理服务间通信的安全、可观测性和流量管理，让业务代码专注于业务逻辑。

### 通俗类比
像给每栋房子都配了一个私人管家：管家负责帮住户收发快递（流量管理）、检查来人身份（mTLS）、记录出入日志（可观测性），住户只需要专心做自己的事。

### 为什么需要服务网格

| 微服务痛点 | 服务网格解决方案 |
|------------|------------------|
| 服务间调用复杂 | Sidecar 代理透明处理 |
| 安全策略分散 | 统一 mTLS 管理 |
| 可观测性差 | 自动采集指标、日志、链路追踪 |
| 流量控制困难 | 声明式流量规则 |
| 客户端SDK膨胀 | 逻辑下沉到代理层 |

## Istio

### 一句话定义
Istio 是最流行的**服务网格实现**，提供流量管理、安全、可观测性三大核心能力。

> 注：Istio 1.5 起已将早期的 Pilot（流量）、Citadel（安全）、Galley（配置）**合并为单一控制面 istiod**；下图按职能分列三者便于理解，实际部署为一个 istiod 组件（详见 [[服务网格]]）。

### 核心功能

#### 流量管理

```yaml
# VirtualService - 流量路由规则
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: order-service
spec:
  hosts:
    - order-service
  http:
    - match:
        - headers:
            x-version:
              exact: "v2"
      route:
        - destination:
            host: order-service
            subset: v2
    - route:
        - destination:
            host: order-service
            subset: v1
          weight: 90
        - destination:
            host: order-service
            subset: v2
          weight: 10
```

#### 安全（mTLS）

```yaml
# PeerAuthentication - 强制 mTLS
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: production
spec:
  mtls:
    mode: STRICT
```

#### 可观测性

| 能力 | 工具 |
|------|------|
| 指标 | Prometheus + Grafana |
| 日志 | Kibana + Fluentd |
| 链路追踪 | Jaeger / Zipkin |
| 服务拓扑 | Kiali |

## Envoy Proxy

### 一句话定义
Envoy 是一个**高性能 L7 代理**，也是 Istio 的数据平面核心，负责实际的流量处理。

### 通俗类比
像一个智能门卫：所有进出小区（服务）的访客都要经过门卫检查，门卫还会记录来访信息、控制出入权限。

### xDS 协议族

| 协议 | 全称 | 功能 |
|------|------|------|
| LDS | Listener Discovery Service | 监听器配置（端口、协议） |
| RDS | Route Discovery Service | 路由规则 |
| CDS | Cluster Discovery Service | 上游集群配置 |
| EDS | Endpoint Discovery Service | 端点发现（服务实例） |

### Sidecar 模式

```
请求流程：
App A ──▶ Envoy A ──(mTLS)──▶ Envoy B ──▶ App B
              │                      │
              ▼                      ▼
         路由/限流/            路由/限流/
         熔断/日志             熔断/日志
```

## 服务治理

### 一句话定义
服务治理是对微服务系统中的**流量、容错、安全**进行统一管理的能力集合。

### 核心能力对比

| 能力 | 说明 | 实现方式 |
|------|------|----------|
| 负载均衡 | 将请求均匀分配到多个实例 | 轮询、加权、一致性哈希 |
| 熔断 | 快速失败，防止级联故障 | Hystrix/Sentinel/Envoy |
| 限流 | 控制请求速率，保护系统 | 令牌桶、漏桶、滑动窗口 |
| 重试 | 失败后自动重试 | 指数退避 + 幂等保证 |
| 超时 | 设置最大等待时间 | 超时后快速失败 |

### 熔断器状态机

```
关闭状态 ──(失败率超阈值)──▶ 打开状态
    ▲                          │
    │                     (超时后)
    │                          │
    │                          ▼
    └──(探测成功)────── 半开状态
```

## mTLS（双向 TLS 认证）

### 一句话定义
mTLS 要求**通信双方都验证对方的证书**，确保服务间通信的双向身份验证和数据加密。

### 通俗类比
像两个公司互派员工对接：不仅要出示工牌（客户端验证服务器），服务器也要出示工牌（服务器验证客户端），双方都确认身份后才开始谈业务。

### 传统 TLS vs mTLS

| 特性 | 传统 TLS | mTLS |
|------|----------|------|
| 验证方向 | 客户端验证服务器 | 双向验证 |
| 证书要求 | 服务器证书 | 客户端+服务器证书 |
| 适用场景 | HTTPS | 服务间安全通信 |
| 实现难度 | 简单 | 需要 PKI 基础设施 |

## 流量镜像（Traffic Mirroring）

### 一句话定义
流量镜像将**生产流量的副本**发送到测试环境，用于验证新版本而**不影响生产**。

### 通俗类比
像一个试衣间：你试穿新衣服（新版本），但你穿的其实不是货架上的那件（生产流量），而是复制的一模一样的一件（镜像流量）。

### 典型场景

```
生产流量 ──┬──▶ 生产环境 v1（实际处理）
           │
           └──▶ 测试环境 v2（镜像，只读不写）
```

## 故障注入（Chaos Engineering）

### 一句话定义
故障注入是**主动制造故障**来测试系统容错能力的工程实践。

### 通俗类比
像消防演习：平时定期模拟火灾（故障），让员工（系统组件）练习疏散流程，确保真正着火时不会乱套。

### Istio 故障注入示例

```yaml
# 延迟注入 - 模拟网络延迟
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
spec:
  http:
    - fault:
        delay:
          percentage:
            value: 10.0
          fixedDelay: 5s
      route:
        - destination:
            host: order-service

# 中止注入 - 模拟服务不可用
      fault:
        abort:
          percentage:
            value: 5.0
          httpStatus: 503
```

## Sidecar 模式优缺点

| 优点 | 缺点 |
|------|------|
| 透明代理，业务无感知 | 每个 Pod 额外资源开销 |
| 统一治理逻辑 | 请求延迟增加（多一跳） |
| 语言无关，统一 SDK | 调试复杂度增加 |
| 热更新，无需重启应用 | 运维复杂度提升 |

## 服务网格 vs 传统网关

| 维度 | 传统 API 网关 | 服务网格 |
|------|---------------|----------|
| 部署位置 | 集群入口 | 每个服务旁 |
| 保护范围 | 南北向流量（外部→内部） | 东西向流量（服务间） |
| 通信协议 | HTTP 为主 | 任意 TCP/HTTP/gRPC |
| 运维模式 | 集中式运维 | 声明式 + 分布式 |
| 适用架构 | 单体/简单微服务 | 复杂微服务集群 |
| 代表产品 | Kong, Nginx, APISIX | Istio, Linkerd |
