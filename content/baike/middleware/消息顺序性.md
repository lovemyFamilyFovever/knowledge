# 消息顺序性


> 📌 **导航**：本文是 **消息顺序性** 词条，属于 middleware 术语集。相关枢纽：[[ESB 与服务网格（Service Mesh）]]、[[GraphQL实践]]、[[Kafka深入]]、[[RabbitMQ vs Kafka vs Pulsar]]、[[gRPC深入]]。

## 定义

**一句话定义：** 消息顺序性指消息队列中消息被消费的顺序与其发送顺序的一致程度;它区分全局有序(所有消息严格按序)与分区/分组有序(同一分区或同一业务键内有序),是保证依赖顺序的业务正确性的关键属性。

**通俗类比：** 像排队叫号——若只有一个窗口严格按取号顺序办理(全局有序),慢但绝对有序;若开多个窗口、但保证"同一个人的多件事"总在同一个窗口按序办(分区有序),就能兼顾效率与关键顺序。

> 多义说明:顺序性有全局有序、分区有序(如 Kafka partition)、按 key 有序等层级;不同消息中间件提供不同保证。本文综述。

## 原理与机制

- **全局有序:** 单队列/单分区 + 单消费者,吞吐低。
- **分区有序:** 按业务键(如订单 ID)哈希到同一分区,分区内有序、分区间并行(Kafka / RocketMQ 常用)。
- **破坏顺序的因素:** 多分区并行、重试(失败重投可能乱序)、消费端多线程处理、生产者异步发送。
- **保障手段:** 单分区、按 key 路由、消费端串行处理/按序提交、消息序号 + 去重、幂等消费。

## 关键组成

| 组成 | 说明 |
|------|------|
| 全局 / 分区有序 | 顺序性的层级 |
| 分区键路由 | 相同 key 进同一分区 |
| 重试与乱序 | 失败重投可能打乱顺序 |
| 消费端并发 | 多线程会破坏顺序 |
| 序号与幂等 | 保证有序且不重复 |

## 应用场景

- 订单状态流转、账务流水
- 数据同步(如 binlog 变更)
- 需要严格时序的业务事件
- 状态机驱动的流程

## 优点与局限

- 优点:保证业务时序正确。
- 局限:强顺序牺牲并行与吞吐(单分区/串行);与高可用、重试机制存在张力;跨分区无法保证全局序;实现与运维复杂。

## 常见误区

- 消息队列默认不保证全局有序(多数是分区有序或不保证)。
- 重试与多消费者会破坏顺序(需序号 + 幂等)。
- 要全局有序就得单分区单消费(牺牲吞吐)。
- "至少一次"投递下还可能重复,顺序性与幂等性需一起考虑。
