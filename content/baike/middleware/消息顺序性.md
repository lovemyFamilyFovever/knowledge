# 消息顺序性


> 📌 **导航**：本文是 **消息顺序性** 词条，属于 middleware 术语集。相关枢纽：[[ESB 与服务网格（Service Mesh）]]、[[GraphQL实践]]、[[Kafka深入]]、[[RabbitMQ vs Kafka vs Pulsar]]、[[gRPC深入]]。

## 定义

**一句话定义：** 消息顺序性指消息队列中消息被消费的顺序与其发送顺序的一致程度；它区分全局有序（所有消息严格按序）与分区/分组有序（同一分区或同一业务键内有序），是保证依赖顺序的业务正确性的关键属性。

**通俗类比：** 像排队叫号——只有一个窗口严格按取号顺序办理（全局有序），慢但绝对有序；开多个窗口但保证"同一个人的多件事"总在同一个窗口按序办（分区有序），就能兼顾效率与关键顺序。

> 多义说明：顺序性有全局有序、分区有序（如 Kafka partition）、按 key 有序等层级；不同中间件提供不同保证。本文综述。

## 为什么需要它

很多业务有天然先后依赖：同一订单"创建→支付→发货"消息若乱序消费，会把状态机搞乱、产生错误结果。要正确性就得约束顺序。而顺序与并行/吞吐互斥，于是需要"分区有序"这一折中：把同一业务键的消息聚到同一分区保证局部有序，不同键并行处理兼得正确与性能。

## 核心机制

- **全局有序：** 单队列/单分区 + 单消费者，吞吐低。
- **分区有序：** 按业务键（如订单 ID）哈希到同一分区，分区内有序、分区间并行（Kafka / RocketMQ 常用）。
- **破坏顺序的因素：** 多分区并行、失败重投可能乱序、消费端多线程处理、生产者异步发送。
- **保障手段：** 单分区、按 key 路由、消费端串行/按序提交、消息序号 + 去重、幂等消费。

| 组成 | 说明 |
|------|------|
| 全局 / 分区有序 | 顺序性的层级 |
| 分区键路由 | 相同 key 进同一分区 |
| 重试与乱序 | 失败重投可能打乱顺序 |
| 消费端并发 | 多线程会破坏顺序 |
| 序号与幂等 | 保证有序且不重复 |

## 具体示例

订单状态消息带 `order_id` 作分区键：同一订单的"创建/支付/发货"都哈希进同一分区，分区内天然有序、单线程消费即保序；不同订单散在不同分区并行。但生产端异步发送或消费端多线程处理会打乱顺序，需改为同步发送 + 单线程（或按 key 加锁串行）；若"至少一次"重投还会重复，需再叠加序号去重与幂等（见 [[幂等性]]）。

## 何时用 / 何时不用

- **用：** 订单状态流转、账务流水、binlog 数据同步、状态机流程等依赖时序正确性的场景。
- **不用：** 消息彼此独立、顺序无意义（尽量多分区并行取吞吐）；能接受最终一致或乱序（无须强序约束）。

## 优劣与代价

✅ 保证业务时序正确，避免乱序导致的状态错乱。
⚠️ 强顺序牺牲并行与吞吐（单分区/串行消费）。
⚠️ 与高可用、重试机制存在张力；跨分区无全局序，实现运维复杂。

## 与相关概念的区别

- **全局有序 vs 分区有序：** 前者单分区单消费、吞吐低；后者按 key 聚分区分部有序 + 并行，是工程主流。
- **顺序性 vs 投递语义：** 顺序讲先后、[[消息投递语义]]讲丢/重，相互独立且常需一起考虑。
- **vs 幂等：** 幂等解决"重复"，顺序解决"乱序"，两者常配套使用。

## 常见误区

- 主流消息队列默认就能保证所有消息全局有序。
- 启用失败重试、并使用多个并发消费者，不会影响消息的消费顺序。
- 想要严格全局有序，只要多开几个分区、多加几个消费者就行。

## 面试速答

> 🎯 消息顺序性=消费顺序与发送顺序的一致程度：全局有序须单分区单消费者（牺牲吞吐），主流是分区有序——按业务键（订单 ID）哈希进同一分区，分区内有序、分区间并行。破坏顺序的因素有多分区并行、失败重投、消费多线程、生产异步发送。它独立于[[消息投递语义]]。
