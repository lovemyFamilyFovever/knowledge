# 表级数据组织（分区表与冷热分离）

> 📌 **导航**：本文是 **表级数据组织（分区表与冷热分离）** 词条，属于 database 术语集。相关枢纽：[[数据库设计术语]]、[[分库分表]]、[[读写分离]]、[[数据仓库]]、[[LSM 树]]。

## 定义

**一句话定义：** 表级数据组织是在单库内按规则把一张大表在物理上拆成多个分区（按范围/列表/哈希），并把访问频繁的热数据与低频的冷数据分层存放，以在不改变逻辑表的前提下提升维护性、查询裁剪效率与存储成本。

**通俗类比：** 图书馆还是那一座（逻辑一张表），但书按年代或语种分进不同书库（分区），找书可整库跳过（分区裁剪）、新书区常翻、旧存档区压到地下室（冷热分离）。

## 为什么需要它

单表过大后，索引膨胀、全表扫描与 DDL 变慢、按时间维护历史数据困难。分区让"按分区键过滤"的查询跳过无关分区、并让按分区的归档/删除极快（DROP PARTITION 秒删一片冷数据）；冷热分离把不常访问的数据放到低成本存储，降低热层压力与总成本。它与"跨机分片"的分库分表是不同维度。

## 核心机制

- **分区类型：** 范围分区（按时间/ID 区间）、列表分区（按离散值，如地区）、哈希分区（打散均匀）、复合分区。
- **分区裁剪：** 查询带分区键条件时，优化器只扫相关分区。
- **分区维护：** 按分区的增删/合并/交换（EXCHANGE PARTITION 快速装载历史表）让大表运维可控。
- **冷热分离：** 热数据留在在线库（近期、高频），冷数据按策略归档到廉价存储/归档库或 [[数据仓库]]/[[数据湖]]；用时间/TTL 或访问频率驱动分层。

## 具体示例

订单表按 `created_at` 做月度范围分区：查"本月订单"只扫当月分区（分区裁剪），一年后历史分区可直接 DROP 或 EXCHANGE 到归档表快速清库。再进一步：近 3 个月数据留在 MySQL 热层（高 IOPS），更早的迁到数据湖冷层按需查——兼顾在线快与总成本。

## 何时用 / 何时不用

- **用：** 单表过大但单机仍扛得住、常按某键（时间/地区）过滤、需按批归档/清理历史数据、要降冷数据存储成本。
- **不用：** 数据量已超单机容量/写入 → 那是 [[分库分表]] 的水平扩展问题；查询不带分区键则裁剪失效；分区数过多反增元数据与规划开销。

## 优劣与代价

✅ 逻辑单表不变而物理可管，分区裁剪提速、DROP/EXCHANGE 让归档删除极快、冷热分层省成本。
⚠️ 选错分区键或查询不含它则无收益甚至更慢；跨分区聚合仍可能全扫。
⚠️ 冷数据迁移引入一致性与访问延迟复杂度。

## 与相关概念的区别

- **分区 vs 分库分表：** 分区是"同库内拆文件"、逻辑仍一表、由 DB 管理；分库分表跨实例、常要中间件路由与全局 ID（见 [[分库分表]]）。
- **冷热分离 vs 归档：** 冷热是按访问频度分层存放，归档是其一种落地手段。
- **vs [[LSM 树]]：** LSM 是引擎写恢复结构，分区/冷热是逻辑数据布局策略，层次不同。

## 常见误区

- 分区表和分库分表是一回事，都是把大表拆开。
- 只要给表分了区，任何查询都会因为分区裁剪而变快。
- 冷热分离后冷数据就完全不能再查询了。

## 面试速答

> 🎯 分区表=单库内把一张逻辑表按范围/列表/哈希物理分片：带分区键的查询触发分区裁剪、DROP/EXCHANGE PARTITION 让历史归档秒级完成；冷热分离把热数据留在线库、冷数据沉到数据湖。区别于跨实例的分库分表，分区仍是同库单逻辑表、由 DB 管理，前提是查询命中分区键。
