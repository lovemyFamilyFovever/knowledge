# MongoDB实践


> 📌 **导航**：本文是 **MongoDB实践** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[Redis深入]]、[[Redis深度解析与实战指南]]、[[SQL 基础术语]]。

## 定义

**一句话定义：** MongoDB 是以**文档（BSON）**为数据模型的 NoSQL 数据库，Schema 灵活、支持嵌套与数组、原生提供分片与副本集，适合结构多变、读多写多的业务。

**通俗类比：** 关系型数据库像 Excel 表格（每行列数固定）；MongoDB 像一叠 JSON 卡片，每张卡片字段可以不同、还能嵌套子卡片，存取贴近程序里的对象。

> 多义说明：本文是 MongoDB 的**实战要点**；NoSQL 各类型（KV / 文档 / 列族 / 图）与取舍见 [[NoSQL 数据库术语]]。

## 为什么需要它

关系模型要求先定表结构、把一对多拆成多张表再 JOIN，当字段频繁变动、数据天然嵌套（评论、订单明细、用户画像）或需要水平扩到海量时，改表与跨表关联都很别扭。MongoDB 用文档模型让一条业务对象整体存储、Schema 可随迭代演化，并用副本集与分片原生解决高可用和扩展，减少 ORM/分库中间件的心智负担。

## 核心机制

- **文档模型（BSON）：** 数据以 BSON（二进制 JSON）文档存于集合（collection），字段可嵌套文档/数组，Schema 灵活（同集合文档结构可不同）。
- **副本集（Replica Set）：** 一主多从 + 自动选主，提供高可用与读扩展。
- **分片（Sharding）：** 由 mongos 路由、config server 存元数据，按分片键把数据水平拆到多个 shard（每个 shard 本身是一个副本集），突破单机容量与吞吐。分片键选择原则是高基数、低频变化、查询常用；选错会导致数据倾斜（jumbo chunk）。

下面是一条典型文档，直观展示嵌套与数组：

```json
{
    "_id": "ObjectId(...)",
    "name": "张三",
    "age": 25,
    "address": { "city": "北京", "district": "朝阳" },
    "tags": ["developer", "python"]
}
```

## 何时用 / 何时不用

- **用：** 内容管理、商品/用户画像等**结构多变**的数据、物联网/日志、快速迭代的互联网业务、需要嵌套或数组的场景。
- **不用：** 强一致多表 JOIN、复杂关系分析与重度事务的 OLTP（更偏关系型）；纯高频点查缓存（用 [[Redis深入]]）；把 MongoDB 当无 Schema 的垃圾桶而不做文档设计。

## 具体示例

聚合管道（Aggregation Pipeline）按阶段流式处理，等价于 SQL 的 WHERE + GROUP BY + ORDER BY + LIMIT 组合：

```javascript
db.orders.aggregate([
    { $match:  { status: "completed" } },        // 过滤
    { $group:  { _id: "$user_id",                 // 分组聚合
                 totalAmount: { $sum: "$amount" },
                 orderCount:  { $sum: 1 } } },
    { $sort:   { totalAmount: -1 } },            // 排序
    { $limit:  10 }                              // 取前 10
])
```

需要实时同步时可用 Change Stream（`watch()` 订阅集合变更）驱动缓存刷新或下游处理，无需自己轮询 oplog。

## 优劣与代价

✅ Schema 灵活、开发友好（对象直存）、水平扩展（分片）、高可用（副本集）、聚合能力强。
⚠️ 多文档事务虽已支持（4.0+ 副本集、4.2+ 分片），但性能与关系型仍有差距，不擅长复杂多表 JOIN。
⚠️ 分片键设计不当会倾斜；内存占用较高。

## 与相关概念的区别

- **vs 关系型数据库：** 以文档嵌套表达一对多、少 JOIN；事务与强关系约束仍以关系库为权威。
- **vs 纯 KV 存储：** MongoDB 是文档型，支持二级索引、字段查询与聚合，远不止键值存取。
- **内嵌 vs 引用：** 读多且规模有界的一到多用内嵌（一次取回），多对多或可能无限增长的关系用引用（避免文档无界膨胀）。

## 常见误区

- MongoDB 完全没有 Schema，怎么存都行、不需要设计文档结构。
- 把评论、日志这类可能无限增长的数据一律内嵌进父文档最方便。
- 分片键随便选一个递增字段（如时间戳）也没问题。

## 面试速答

> 🎯 MongoDB=文档型 NoSQL：BSON 灵活 Schema + 内嵌/数组，副本集保高可用、分片按分片键水平扩展；擅长结构多变与读多写多，弱在重度事务与多表 JOIN，实战要点是合理设计内嵌/引用并选好分片键。
