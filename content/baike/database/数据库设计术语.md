## 主键（Primary Key）

**一句话定义（大白话）：** 唯一标识表中每一行数据的字段，不允许重复也不允许为空。

**通俗类比（生活场景）：** 身份证号——每个人的身份证号全国唯一，通过它能精确找到一个人。主键就是数据行的"身份证号"。

**具体示例：**

```sql
-- 创建表时定义主键
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL
);

-- 后加主键
ALTER TABLE users ADD PRIMARY KEY (id);

-- 联合主键（两个字段组合唯一）
CREATE TABLE user_roles (
    user_id INT,
    role_id INT,
    PRIMARY KEY (user_id, role_id)
);

-- 主键约束：
-- 1. 不允许 NULL
-- 2. 不允许重复值
-- 3. 一张表只能有一个主键
-- 4. InnoDB 会自动以主键创建聚簇索引

-- 推荐使用自增整数作为主键
-- 不推荐用 UUID 做主键（无序，写入性能差）
-- 推荐用 BIGINT AUTO_INCREMENT
```

**为什么需要它：** 主键是数据完整性的基础。没有主键，你就无法唯一确定一行数据，更新、删除操作都会出问题。

**与相关术语的对比和区分：** 主键是"最核心的唯一标识"，候选键是"可能成为主键的候选"，超键是"能唯一标识的任意字段组合"。主键是候选键中被选中的那个。

---

## 外键（Foreign Key）

**一句话定义（大白话）：** 一个表中的字段引用另一个表的主键，建立两张表之间的关联关系。

**通俗类比（生活场景）：** 快递单上的"收件人 ID"——它指向用户表中的某个用户。通过这个 ID，你能找到收件人的详细信息。

**具体示例：**

```sql
-- 创建表时定义外键
CREATE TABLE orders (
    id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    amount DECIMAL(10,2),
    FOREIGN KEY (user_id) REFERENCES users(id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

-- 后加外键
ALTER TABLE orders
ADD CONSTRAINT fk_user
FOREIGN KEY (user_id) REFERENCES users(id);

-- 外键的级联操作：
-- ON DELETE CASCADE：删除父记录时自动删除子记录
-- ON DELETE SET NULL：删除父记录时子记录设为 NULL
-- ON DELETE RESTRICT：有子记录时禁止删除父记录（默认）
-- ON UPDATE CASCADE：更新父记录时级联更新子记录
```

**为什么需要它：** 外键保证了表与表之间的引用完整性。没有外键，你可能删除了用户但订单还在，产生"孤儿数据"。

**与相关术语的对比和区分：** 外键建立的是"表与表的关系"，主键是"表内的唯一标识"。外键的值必须是另一个表主键中已存在的值（或 NULL）。

## 候选键（Candidate Key）

**一句话定义（大白话）：** 能唯一标识表中每一行的最小字段集合，可能有多个。

**通俗类比（生活场景）：** 身份证号和手机号都能唯一标识一个人——它们都是候选键。你选了身份证号做主键，手机号就是候选键。

**具体示例：**

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(100) UNIQUE,
    phone VARCHAR(20) UNIQUE,
    username VARCHAR(50)
);

-- 候选键的特点：
-- 1. 唯一性：没有重复值
-- 2. 最小性：不能去掉任何字段还能保持唯一性
-- 3. 非空性：通常不允许 NULL

-- 本例中：
-- id → 候选键（被选为主键）
-- email → 候选键（UNIQUE 约束）
-- phone → 候选键（UNIQUE 约束）
-- username → 不是候选键（可能重复）
```

**为什么需要它：** 候选键帮助你识别"哪些字段组合能唯一标识数据"，是从中选择主键的基础。

**与相关术语的对比和区分：** 候选键是"所有能唯一标识的最小组合"，主键是"被选中的那个候选键"，超键是"能唯一标识的任意组合（不一定最小）"。

---

## 超键（Super Key）

**一句话定义（大白话）：** 能唯一标识表中每一行的任意字段组合，不要求最小。

**通俗类比（生活场景）：** 用"姓名+身份证号+手机号"也能唯一标识一个人——这个组合就是超键。虽然能唯一标识，但包含了冗余字段。

**具体示例：**

```sql
CREATE TABLE users (
    id INT,
    email VARCHAR(100),
    phone VARCHAR(20),
    username VARCHAR(50)
);

-- 超键示例（能唯一标识）：
-- (id) → 超键
-- (email) → 超键
-- (phone) → 超键
-- (id, email) → 超键（但不是候选键，因为 id 本身就够了）
-- (id, email, phone) → 超键（更不是候选键）

-- 候选键 = 最小的超键
-- 主键 = 选中的候选键
```

**为什么需要它：** 超键是理论概念，帮助理解"唯一标识"的本质。实际设计中我们关注的是候选键和主键。

**与相关术语的对比和区分：** 超键包含候选键和主键，但范围更广。超键只要求"唯一"，候选键还要求"最小"，主键还要求"被选中"。

## 第一范式（1NF）

**一句话定义（大白话）：** 表中的每个字段都是原子值，不可再分。

**通俗类比（生活场景）：** 通讯录——每个格子只填一个信息。不能在一个格子里写"张三，男，25岁"，要拆成"姓名"、"性别"、"年龄"三个格子。

**具体示例：**

```sql
-- 违反 1NF：
CREATE TABLE users_bad (
    id INT PRIMARY KEY,
    name_info VARCHAR(200)  -- "张三,男,25岁,北京" 存在一起
);

-- 符合 1NF：
CREATE TABLE users_good (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    gender VARCHAR(10),
    age INT,
    city VARCHAR(50)
);

-- 另一个违反 1NF 的例子：
-- 爱好字段存多个值："篮球,足球,乒乓球"
-- 拆成关联表：
CREATE TABLE user_hobbies (
    user_id INT,
    hobby VARCHAR(50),
    PRIMARY KEY (user_id, hobby)
);
```

**为什么需要它：** 不满足 1NF 的数据无法用关系代数处理，查询、统计都会出问题。

**与相关术语的对比和区分：** 1NF 是"字段原子性"，2NF 是"消除部分依赖"，3NF 是"消除传递依赖"。1NF 是基础，2NF/3NF 逐步递进。

---

## 第二范式（2NF）

**一句话定义（大白话）：** 在满足 1NF 的基础上，非主键字段必须完全依赖主键，不能只依赖主键的一部分。

**通俗类比（生活场景）：** 课程表中，"课程名"只依赖"课程号"，不依赖"学号"。如果主键是（学号，课程号），那"课程名"就不该在这张表里。

**具体示例：**

```sql
-- 违反 2NF（联合主键下部分依赖）：
CREATE TABLE scores_bad (
    student_id INT,
    course_id INT,
    student_name VARCHAR(50),  -- 只依赖 student_id
    course_name VARCHAR(100),  -- 只依赖 course_id
    score INT,
    PRIMARY KEY (student_id, course_id)
);

-- 符合 2NF（拆表）：
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE courses (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);

CREATE TABLE scores (
    student_id INT,
    course_id INT,
    score INT,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(id),
    FOREIGN KEY (course_id) REFERENCES courses(id)
);
```

**为什么需要它：** 违反 2NF 会导致数据冗余和更新异常。比如改学生姓名要改多行数据，漏改一行就不一致。

**与相关术语的对比和区分：** 2NF 只在联合主键的情况下才有意义。如果主键是单字段且满足 1NF，就自动满足 2NF。

---

## 第三范式（3NF）

**一句话定义（大白话）：** 在满足 2NF 的基础上，非主键字段不能传递依赖于主键。

**通俗类比（生活场景）：** 员工表中有"部门 ID"和"部门经理"。部门经理依赖部门 ID，部门 ID 依赖员工 ID——这是传递依赖。

**具体示例：**

```sql
-- 违反 3NF（传递依赖）：
CREATE TABLE employees_bad (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    department_id INT,
    department_name VARCHAR(100),
    department_manager VARCHAR(50)
);
-- 传递链：id → department_id → department_name

-- 符合 3NF（拆表）：
CREATE TABLE departments (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    manager VARCHAR(50)
);

CREATE TABLE employees_good (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    department_id INT,
    FOREIGN KEY (department_id) REFERENCES departments(id)
);
```

**为什么需要它：** 违反 3NF 同样导致数据冗余和更新异常。部门经理换了名字，要改员工表中所有该部门的记录。

**与相关术语的对比和区分：** 2NF 消除"部分依赖"，3NF 消除"传递依赖"。

---

## BCNF（Boyce-Codd 范式）

**一句话定义（大白话）：** 3NF 的加强版——每个决定因素都必须是候选键。

**通俗类比（生活场景）：** 3NF 说"非主键字段不能依赖其他非主键字段"，BCNF 说"任何决定因素都必须是候选键"。更严格。

**具体示例：**

```sql
-- 经典案例：课程-教师-教室关系
CREATE TABLE course_teacher (
    course VARCHAR(50),
    teacher VARCHAR(50),
    classroom VARCHAR(50),
    PRIMARY KEY (course, teacher)
);

-- 依赖关系：
-- course → classroom
-- teacher → course
-- 问题：teacher → course，teacher 不是候选键
-- 违反 BCNF

-- 解决：拆表
CREATE TABLE teacher_course (
    teacher VARCHAR(50) PRIMARY KEY,
    course VARCHAR(50),
    classroom VARCHAR(50)
);
```

**为什么需要它：** 3NF 在某些特殊情况下仍可能存在异常。BCNF 是关系型数据库设计中最高的规范化标准。

**与相关术语的对比和区分：** BCNF 比 3NF 更严格。3NF 允许"非候选键的决定因素"在一定条件下存在，BCNF 不允许。

## ER 图（Entity-Relationship Diagram）

**一句话定义（大白话）：** 用图形化方式表示实体、属性和实体之间关系的数据库设计工具。

**通俗类比（生活场景）：** 建筑设计蓝图——在盖房子之前先画图纸。ER 图就是数据库的"设计蓝图"。

**具体示例：**

```
ER 图三要素：
矩形 = 实体（用户、订单）
椭圆 = 属性（id、name、email）
菱形 = 关系（1:N、M:N）

用户 ──1:N──> 订单
订单 ──M:N──> 商品（通过 order_items 中间表）
```

```sql
-- ER 图转 SQL 的实际例子：
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE products (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    price DECIMAL(10,2)
);

CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    created_at TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id)
);

-- M:N 关系需要中间表
CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id) REFERENCES orders(id),
    FOREIGN KEY (product_id) REFERENCES products(id)
);
```

**为什么需要它：** 在写代码之前先把数据模型设计清楚，避免后期频繁改表。ER 图是 DBA 和开发者的沟通工具。

**与相关术语的对比和区分：** ER 图是设计阶段的工具，数据字典是实现阶段的文档。ER 图关注"实体和关系"，数据字典关注"字段和约束"。

## 数据字典（Data Dictionary）

**一句话定义（大白话）：** 存放数据库元数据（表结构、字段类型、约束、索引等信息）的系统表。

**通俗类比（生活场景）：** 字典的"部首索引"——它不告诉你"张三"是什么意思，但它告诉你"张"字在字典的第几页。

**具体示例：**

```sql
-- 查看所有数据库
SHOW DATABASES;

-- 查看某库的所有表
SHOW TABLES FROM my_shop;

-- 查看表结构
DESC users;

-- 查看建表语句
SHOW CREATE TABLE users\G

-- 查看索引信息
SHOW INDEX FROM users;

-- 查看约束
SELECT * FROM information_schema.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = 'my_shop' AND TABLE_NAME = 'users';

-- 查看外键关系
SELECT * FROM information_schema.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = 'my_shop' AND REFERENCED_TABLE_NAME IS NOT NULL;
```

**为什么需要它：** 数据字典让你能程序化地获取数据库结构信息，是自动化工具（ORM、代码生成器）的基础。

**与相关术语的对比和区分：** 数据字典是系统表，ER 图是设计文档。数据字典描述"数据库实际是什么样"，ER 图描述"数据库应该是什么样"。

## 反范式设计（Denormalization）

**一句话定义（大白话）：** 有意违反范式规则，通过数据冗余来提升查询性能。

**通俗类比（生活场景）：** 你把常用电话号码记在手机桌面上，虽然和通讯录重复了，但不用每次都打开通讯录查找。

**具体示例：**

```sql
-- 范式设计（多表关联查询）：
SELECT u.name, o.amount, p.name
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id;

-- 反范式设计（冗余字段）：
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    user_name VARCHAR(50),
    product_name VARCHAR(100),
    amount DECIMAL(10,2),
    created_at TIMESTAMP
);

-- 查询时不需要 JOIN：
SELECT user_name, product_name, amount FROM orders;
```

**为什么需要它：** 范式化减少冗余但增加 JOIN，反范式增加冗余但减少 JOIN。在读密集场景下，反范式能显著提升查询性能。

**与相关术语的对比和区分：** 范式化是"减少冗余、保证一致性"，反范式化是"增加冗余、提升性能"。两者是权衡关系。

## 分区表（Partitioned Table）

**一句话定义（大白话）：** 把一张大表按某种规则拆分成多个物理片段，但逻辑上仍是一张表。

**通俗类比（生活场景）：** 把一个大文件夹按月份分成 12 个小文件夹——找特定月份的文件时只翻对应的文件夹。

**具体示例：**

```sql
-- 按范围分区（常用于按时间）
CREATE TABLE orders (
    id INT,
    user_id INT,
    amount DECIMAL(10,2),
    created_at DATE
)
PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION pmax VALUES LESS THAN MAXVALUE
);

-- 按列表分区（按枚举值）
CREATE TABLE employees (
    id INT,
    name VARCHAR(50),
    region VARCHAR(20)
)
PARTITION BY LIST COLUMNS (region) (
    PARTITION p_north VALUES IN ('北京', '天津'),
    PARTITION p_east VALUES IN ('上海', '杭州'),
    PARTITION p_south VALUES IN ('广州', '深圳')
);

-- 按哈希分区（均匀分布）
CREATE TABLE sessions (
    id INT,
    user_id INT,
    data TEXT
)
PARTITION BY HASH (user_id)
PARTITIONS 8;

-- 查询时自动定位分区
SELECT * FROM orders WHERE created_at = '2025-06-15';
-- 只扫描 p2025 分区，不扫描其他分区
```

**为什么需要它：** 单表数据量太大时查询变慢，分区把数据拆小，查询时只扫描相关分区（分区裁剪），大幅提升性能。

**与相关术语的对比和区分：** 分区表是"逻辑一张表，物理多张表"，分库分表是"多张独立的表"。分区表对应用透明，分库分表需要中间件。

---

## 分库分表（水平/垂直）

**一句话定义（大白话）：** 把一张大表的数据拆分到多张表（分表）或多个数据库（分库）中。

**通俗类比（生活场景）：** 图书馆的书太多放不下——按类别分到不同楼层（垂直拆分），或者一套书拆成多册（水平拆分）。

**具体示例：**

```sql
-- 垂直拆分（按字段拆分）：
-- 原表 users（包含不常用的 Blob 字段）
-- 拆成：
-- users 表（id, username, email, phone）
-- user_ext 表（id, avatar, bio, resume）

-- 水平拆分（按行拆分）：
-- 原表 orders（1 亿条数据）
-- 按 user_id % 4 拆成 4 张表：
-- orders_0（user_id % 4 = 0）
-- orders_1（user_id % 4 = 1）
-- orders_2（user_id % 4 = 2）
-- orders_3（user_id % 4 = 3）

-- 分库（垂直拆分的延伸）：
-- 用户库：users, user_profiles
-- 订单库：orders, order_items
-- 商品库：products, categories

-- 分片键选择：
-- 以 user_id 为分片键
-- 查询时带上 user_id 就能定位到具体分片
-- 不带分片键的查询需要广播到所有分片
```

**为什么需要它：** 单表超过千万行后性能急剧下降。分库分表把数据分散，降低单机压力。

**与相关术语的对比和区分：** 垂直拆分是"拆字段"，水平拆分是"拆行"。分库是把不同业务放不同数据库，分表是把同业务数据放多张表。通常垂直拆分在前（业务拆分），水平拆分在后（数据量拆分）。

## 读写分离

**一句话定义（大白话）：** 写操作走主库，读操作走从库，主从之间通过复制同步数据。

**通俗类比（生活场景）：** 公司有一份原件（主库）和多份复印件（从库）。盖章签字只能用原件，查阅资料用复印件就行。

**具体示例：**

```
架构示意：
应用 ──写──> Master（主库）
  │
  └──读──> Slave 1（从库）
           Slave 2（从库）
           Slave 3（从库）
```

```sql
-- MySQL 主从复制配置（简化）：
-- 主库 my.cnf：
-- server-id=1
-- log-bin=mysql-bin

-- 从库 my.cnf：
-- server-id=2
-- relay-log=mysql-relay-bin

-- 主库创建复制用户：
CREATE USER 'repl'@'%' IDENTIFIED BY 'password';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- 从库配置主库信息：
CHANGE MASTER TO
    MASTER_HOST='master_host',
```

**为什么需要它：** 大多数应用读多写少（80% 读，20% 写），读写分离让从库分担读压力，提升整体吞吐量。

**与相关术语的对比和区分：** 读写分离是"主从复制"的应用层方案，主从复制是底层的数据同步机制。读写分离解决"读性能"，分库分表解决"写性能和存储"。

## 冷热分离

**一句话定义（大白话）：** 把频繁访问的"热数据"和很少访问的"冷数据"分开存储。

**通俗类比（生活场景）：** 办公桌上放常用文件（热数据），柜子里放归档文件（冷数据）。常用的一伸手就够到，不常用的偶尔去柜子里翻。

**具体示例：**

```sql
-- 方案一：按时间分表（最常见）
-- 热数据：orders_2025（最近 3 个月）
-- 冷数据：orders_2024（3 个月前）

-- 热数据放 SSD，冷数据放 HDD
-- 热数据在主库，冷数据归档到从库或数据仓库

-- 方案二：表内冷热分离
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id INT,
    amount DECIMAL(10,2),
    status VARCHAR(20),
    created_at TIMESTAMP,
    detail JSON,
    -- 热字段：id, user_id, amount, status, created_at
    -- 冷字段：detail（只有偶尔查询）
    INDEX idx_hot (user_id, status, created_at)
);

-- 方案三：归档表
-- 定期把已完成超过 30 天的订单移到归档表
CREATE TABLE orders_archive LIKE orders;

INSERT INTO orders_archive
SELECT * FROM orders
WHERE status = 'completed' AND created_at < DATE_SUB(NOW(), INTERVAL 30 DAY);

DELETE FROM orders
WHERE status = 'completed' AND created_at < DATE_SUB(NOW(), INTERVAL 30 DAY);
```

**为什么需要它：** 热数据量小但访问频繁，放高性能存储提升速度；冷数据量大但访问少，放低成本存储节省开支。

**与相关术语的对比和区分：** 冷热分离是"按访问频率分"，分区表是"按规则分"，分库分表是"按数据量分"。冷热分离侧重存储成本优化，分库分表侧重性能优化。
