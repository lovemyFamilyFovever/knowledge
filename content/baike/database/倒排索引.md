# 倒排索引

> 📌 **导航**：本文是 **倒排索引** 词条，属于 database 术语集。相关枢纽：[[搜索引擎技术详解]]、[[ElasticSearch搜索]]、[[字符串算法]]、[[前缀树]]、[[基础数据结构]]。

## 定义

**一句话定义：** 倒排索引是搜索引擎的核心数据结构，把"词项 → 含该词的文档列表（posting list）"预先建好，使按词检索从扫描全部文档变为直接命中，是全文检索相对正排/暴力的根本优势。

**通俗类比：** 正排像"每本书列出它有哪些关键词"，查词就得逐本翻；倒排反过来"每个关键词列出它出现在哪几本书"，查词一步到位——就像书末索引按词条排好页码。

## 为什么需要它

文档→词的"正排"回答"这篇有什么词"，而检索要的是"含某词的有哪些文档"。若每次对全库做子串匹配是 O(N×文档长)，海量下不可行。倒排把词→文档列表预计算成可命中的表，配合词频/位置信息，把查询降到与结果规模相关，并支撑多词求交、短语、前缀等。

## 核心机制

- **结构：** 词典（term 表）指向每个 term 的 posting list；posting 含 docID、词频 TF（打分用）、可选位置 positions（短语查询用）。文档频 DF 供 IDF。
- **多词检索：** 多个 posting list 求交集（AND）/并集（OR）；列表有序利于归并。
- **跳表加速：** posting list 交并按 docID 二分/跳表快速定位（同 [[字符串算法]] 里的跳表思想、[[基础数据结构]]），避免逐格线性扫。
- **压缩：** docID 升序后存差值（delta）再用变长字节（Variable Byte）编码，词项多、列表长时大幅省空间。
- **与 [[ElasticSearch搜索]]：** ES/Lucene 的段与词典即倒排的工业实现，本条讲通用原理。

## 具体示例

文档1=[机器,学习]、文档2=[学习,方法]：倒排"机器→[1]"、"学习→[1,2]"、"方法→[2]"。查"机器 学习"取两 posting 求交 → {1}。posting 升序存 docID 时只存差值再 VB 编码压缩；带 position 才能判短语"机器学习"是否紧邻。这与 [[前缀树]] 互补：Trie 擅长前缀补全、倒排擅长"含某词"的检索。

## 何时用 / 何时不用

- **用：** 全文检索、关键词命中、布尔/短语查询的底层结构；构建检索型系统。
- **不用/权衡：** 纯数值范围/精确点查用 B 树/哈希更合适（见 [[基础数据结构]]）；高更新频率下段合并与写放大需考量（[[ElasticSearch搜索]]）。

## 优劣与代价

✅ 按词命中极快、支撑相关性打分与多词集合运算，配合压缩可控制空间。
⚠️ 构建与合并有成本、posting 膨胀时吃存储（故 delta+VB 压缩）。
⚠️ 更新不友好，常靠不可变段 + 定期合并缓解。

## 与相关概念的区别

- **倒排 vs 正排：** 正排文档→词、查词须扫全部文档；倒排词→文档、一步命中。
- **vs [[B+树]]：** B+树擅长有序/范围与点查，倒排擅长"包含某词项"的集合命中。
- **vs [[前缀树]]：** Trie 按字符前缀检索/补全，倒排按词项检索。

## 常见误区

- 倒排索引就是哈希表，词项直接映射到唯一的文档号。
- 有了倒排索引就不需要再存词频或位置信息。
- posting list 里的文档 ID 是无序存储的，不需要排序或压缩。

## 面试速答

> 🎯 倒排索引=词项→文档列表(posting list 含 docID/词频/位置)的预建结构，查词一步命中；多词求交并、带 position 支持短语、delta+变长字节压缩、跳表/二分加速交并。区别于正排、B+树(有序范围)、前缀树(字符前缀)，是全文检索地基、更新靠不可变段+合并。
