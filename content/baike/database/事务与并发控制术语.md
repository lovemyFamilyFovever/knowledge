# 事务与并发控制术语

---

## 事务（Transaction）

**一句话定义（大白话）：** 一组数据库操作，要么全部成功，要么全部失败，不能只做了一半。

**通俗类比（生活场景）：** 转账——从 A 扣 100 元和给 B 加 100 元必须同时成功。如果扣了钱但加钱失败，钱就凭空消失了。事务保证这种"要么全做，要么全不做"。

**具体示例：**

```sql
-- 开启事务
START TRANSACTION;

-- 执行一组操作
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE user_id = 2;

-- 检查是否出错
-- 如果一切正常：
COMMIT;

-- 如果出错：
ROLLBACK;

-- 事务的三种结束方式：
-- 1. COMMIT：提交，所有修改永久生效
-- 2. ROLLBACK：回滚，所有修改撤销
-- 3. 自动提交：每条 SQL 自动成为一个事务（默认行为）
```

**为什么需要它：** 没有事务，系统崩溃或操作中断时数据会处于不一致状态。事务是数据一致性的基石。

**与相关术语的对比和区分：** 事务是一个"操作单元"，ACID 是事务必须满足的四个特性，隔离级别是事务并发时的行为规则。

---

## ACID 四大特性

**一句话定义（大白话）：** 事务的四个核心保证——原子性、一致性、隔离性、持久性。

**通俗类比（生活场景）：** 银行转账的四大保障：
- 原子性：扣钱和加钱要么都做，要么都不做（不可分割）
- 一致性：转账前后，两人总金额不变（数据合理）
- 隔离性：你转账时别人看不到中间状态（互不干扰）
- 持久性：转账完成后，即使断电钱也不会丢（永久保存）

**具体示例：**

```sql
-- 原子性（Atomicity）：通过 Undo Log 实现
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
-- 如果这里崩溃，Undo Log 会自动回滚
UPDATE accounts SET balance = balance + 100 WHERE user_id = 2;
COMMIT;

-- 一致性（Consistency）：最终目标
-- 转账前：A=500, B=300, 总计=800
-- 转账后：A=400, B=400, 总计=800
-- 金额始终守恒

-- 隔离性（Isolation）：通过锁和 MVCC 实现
-- 事务 A 正在转账时，事务 B 看到的数据取决于隔离级别

-- 持久性（Durability）：通过 Redo Log 实现
-- COMMIT 后，即使数据库崩溃，Redo Log 也能恢复数据
```

**为什么需要它：** ACID 是事务的"质量标准"。没有这些保证，并发操作会导致数据混乱、丢失、不一致。

**与相关术语的对比和区分：** ACID 是理论要求，隔离级别是实现隔离性的具体方案，MVCC/锁是实现隔离级别的技术手段。

---

## 隔离级别（Isolation Level）

**一句话定义（大白话）：** 定义了事务之间"互相能看到对方什么程度的数据"，在并发性能和数据安全之间做权衡。

**通俗类比（生活场景）：** 会议室的玻璃墙——完全透明（Read Uncommitted）能看到所有人的一切，半透明（Read Committed）只能看到确定的发言，磨砂玻璃（Repeatable Read）只看到固定画面，完全不透明（Serializable）谁也别想偷看。

**具体示例：**

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;  -- MySQL 8.0+
-- 或 SELECT @@tx_isolation;    -- MySQL 5.7

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 四种隔离级别：
-- 1. READ UNCOMMITTED（读未提交）
--    可以读到其他事务未提交的数据
--    问题：脏读、不可重复读、幻读

-- 2. READ COMMITTED（读已提交）
--    只能读到其他事务已提交的数据
--    解决：脏读
--    问题：不可重复读、幻读

-- 3. REPEATABLE READ（可重复读）← MySQL 默认
--    同一事务内多次读取结果一致
--    解决：脏读、不可重复读
--    问题：幻读（InnoDB 通过 MVCC+间隙锁部分解决）

-- 4. SERIALIZABLE（串行化）
--    所有事务串行执行
--    解决：所有问题
--    问题：性能最差
```

**为什么需要它：** 并发越高性能越好，但数据安全性越差。隔离级别让你根据业务需求在两者间选择平衡点。

**与相关术语的对比和区分：** 隔离级别是"规则"，脏读/不可重复读/幻读是"问题"，MVCC/锁是"解决方案"。不同隔离级别解决不同的并发问题。

---

## 脏读（Dirty Read）

**一句话定义（大白话）：** 一个事务读到了另一个事务**还没提交**的数据，如果对方回滚了，你读到的就是"脏"数据。

**通俗类比（生活场景）：** 你偷看了同事写了一半的方案（未提交），觉得他要做 A 项目，赶紧也准备了 A 项目的材料。结果同事把方案推翻重写了，你白忙一场。

**具体示例：**

```sql
-- 脏读示例（READ UNCOMMITTED 级别下）

-- 事务 A：
START TRANSACTION;
UPDATE accounts SET balance = 1000 WHERE user_id = 1;
-- 注意：还没 COMMIT

-- 事务 B（同时执行）：
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT balance FROM accounts WHERE user_id = 1;
-- 读到 balance = 1000（事务 A 还没提交）

-- 事务 A：
ROLLBACK;  -- 回滚了！

-- 事务 B 再查：
SELECT balance FROM accounts WHERE user_id = 1;
-- 读到 balance = 500（原始值）
-- 事务 B 之前读到的 1000 就是"脏数据"
```

**为什么需要它：** 脏读会导致基于错误数据做决策。脏读是最严重的并发问题，几乎所有实际场景都不允许。

**与相关术语的对比和区分：** 脏读是读"未提交"数据，不可重复读是读"已提交但被修改"的数据，幻读是读"已提交但被新增/删除"的数据。严重程度：脏读 > 不可重复读 > 幻读。

---

## 不可重复读（Non-Repeatable Read）

**一句话定义（大白话）：** 同一事务内，两次读取同一行数据结果不同，因为中间被其他事务修改并提交了。

**通俗类比（生活场景）：** 你早上看了一眼货架上苹果的价格是 5 元（读了一次），下午再去买的时候发现价格变成 6 元了（又读了一次）。同一行数据，两次读不一样。

**具体示例：**

```sql
-- 不可重复读示例（READ COMMITTED 级别下）

-- 事务 A：
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;

-- 第一次读
SELECT balance FROM accounts WHERE user_id = 1;
-- 读到 balance = 500

-- 等一会儿...

-- 事务 B（中间执行并提交）：
START TRANSACTION;
UPDATE accounts SET balance = 800 WHERE user_id = 1;
COMMIT;

-- 事务 A 第二次读
SELECT balance FROM accounts WHERE user_id = 1;
-- 读到 balance = 800（和第一次不一样！）

COMMIT;
```

**为什么需要它：** 不可重复读在某些场景下可以接受（比如读最新数据），但在需要"数据一致性视图"的场景下是问题。

**与相关术语的对比和区分：** 不可重复读是**同一行数据被修改**，幻读是**行数发生了变化**（新增/删除）。不可重复读用 MVCC 的 ReadView 解决，幻读需要额外的间隙锁。

---

## 幻读（Phantom Read）

**一句话定义（大白话）：** 同一事务内，两次查询返回的行数不同，因为中间有其他事务插入或删除了行。

**通俗类比（生活场景）：** 你查了一下购物车有 3 件商品（读了一次），准备结算时发现变成了 4 件（有人帮你加了一件）。数据行数"凭空多出来了"，像幻觉一样。

**具体示例：**

```sql
-- 幻读示例（READ COMMITTED 级别下）

-- 事务 A：
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;

-- 第一次查询
SELECT COUNT(*) FROM orders WHERE user_id = 1;
-- 返回 3 条

-- 事务 B（中间执行并提交）：
START TRANSACTION;
INSERT INTO orders (user_id, amount) VALUES (1, 99.99);
COMMIT;

-- 事务 A 第二次查询
SELECT COUNT(*) FROM orders WHERE user_id = 1;
-- 返回 4 条（多出一条"幻影"记录）

COMMIT;

-- 在 REPEATABLE READ 级别下：
-- InnoDB 通过 MVCC + 间隙锁（Next-Key Lock）在很大程度上避免幻读
-- 但完全避免幻读需要 SERIALIZABLE 级别
```

**为什么需要它：** 幻读会导致统计结果不一致、重复处理等问题。特别是在报表、对账等场景下，幻读会导致数据错误。

**与相关术语的对比和区分：** 幻读关注的是**行数变化**（INSERT/DELETE），不可重复读关注的是**行值变化**（UPDATE）。幻读比不可重复读更难解决。

---

## MVCC（Multi-Version Concurrency Control，多版本并发控制）

**一句话定义（大白话）：** 为每行数据维护多个版本，读操作不加锁，通过版本号判断能看到哪个版本的数据。

**通俗类比（生活场景）：** 拍照留念——每次修改数据前都拍一张照片（保留旧版本）。读的人看照片，写的人拍新照片，互不干扰。你看的是"历史版本"，不需要等别人改完。

**具体示例：**

```sql
-- MVCC 核心概念：

-- 1. 隐藏列：每行数据有两个隐藏列
--    DB_TRX_ID：最近修改该行的事务 ID
--    DB_ROLL_PTR：指向 Undo Log 中旧版本的指针

-- 2. ReadView（读视图）：记录当前活跃事务列表
--    m_ids：当前活跃的事务 ID 列表
--    min_trx_id：最小活跃事务 ID
--    max_trx_id：下一个要分配的事务 ID
--    creator_trx_id：当前事务 ID

-- 3. 可见性判断规则：
--    如果行的 trx_id < min_trx_id → 可见（事务已提交）
--    如果行的 trx_id >= max_trx_id → 不可见（事务在 ReadView 之后开始）
--    如果行的 trx_id 在 m_ids 中 → 不可见（事务未提交）
--    否则 → 可见

-- READ COMMITTED：每次 SELECT 都生成新的 ReadView
-- REPEATABLE READ：只在第一次 SELECT 时生成 ReadView

-- 实际演示：
-- 事务 A (id=100)：
START TRANSACTION;
SELECT * FROM users WHERE id = 1;  -- 生成 ReadView [100, 101]
-- 事务 B (id=101) 同时修改了 id=1 的数据并提交
SELECT * FROM users WHERE id = 1;  -- 还是用同一个 ReadView，看到旧数据
COMMIT;
```

**为什么需要它：** 读操作不加锁，写操作只锁当前行，读写互不阻塞。这是 MySQL 高并发的核心机制。

**与相关术语的对比和区分：** MVCC 是并发控制的**机制**，锁是并发控制的**工具**。MVCC 实现了"读不阻塞写，写不阻塞读"，而传统锁机制会导致读写互相等待。

---

## 乐观锁（Optimistic Lock）

**一句话定义（大白话）：** 假设冲突很少发生，不提前加锁，只在提交时检查是否被别人改过，改过了就重试。

**通俗类比（生活场景）：** 多人协作编辑文档——大家都先各自编辑（乐观假设没冲突），保存时检查是否有冲突。如果有冲突，系统会提示你合并或重试。

**具体示例：**

```sql
-- 方式一：版本号机制
-- 表结构加 version 字段
CREATE TABLE products (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    stock INT,
    version INT DEFAULT 0
);

-- 读取时带上版本号
SELECT stock, version FROM products WHERE id = 1;
-- 假设返回 stock=100, version=5

-- 更新时检查版本号
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;  -- 版本号必须匹配

-- 如果影响 0 行，说明被别人改了，需要重试
-- 如果影响 1 行，说明更新成功

-- 方式二：CAS（Compare And Swap）
UPDATE products
SET stock = stock - 1
WHERE id = 1 AND stock = 100;  -- 检查原始值

-- 伪代码逻辑：
-- loop:
--   data = SELECT * FROM products WHERE id = 1
--   new_data = process(data)
--   result = UPDATE ... WHERE version = data.version
--   if result.affected_rows > 0: break
--   else: sleep(random) and retry
```

**为什么需要它：** 乐观锁在**读多写少**的场景下性能很好，因为不需要加锁，减少了锁等待时间。

**与相关术语的对比和区分：** 乐观锁是"先操作后检查"，悲观锁是"先检查后操作"。乐观锁适合冲突少的场景，悲观锁适合冲突多的场景。

---

## 悲观锁（Pessimistic Lock）

**一句话定义（大白话）：** 假设冲突一定会发生，操作前先加锁，保证同一时间只有一个人能操作。

**通俗类比（生活场景）：** 厕所的门锁——进去之前先锁门，别人只能等你出来再用。保证独占，但其他人得排队。

**具体示例：**

```sql
-- 方式一：SELECT ... FOR UPDATE（行锁）
START TRANSACTION;

-- 锁定目标行
SELECT * FROM accounts WHERE user_id = 1 FOR UPDATE;
-- 其他事务对这行的 UPDATE/DELETE 会被阻塞
-- 其他事务的 SELECT ... FOR UPDATE 也会被阻塞
-- 普通 SELECT（不加锁）仍然可以执行

-- 执行操作
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;

COMMIT;  -- 释放锁

-- 方式二：SELECT ... FOR SHARE（共享锁）
SELECT * FROM accounts WHERE user_id = 1 FOR SHARE;
-- 其他事务可以读（共享锁），但不能写（排他锁）

-- 方式三：表锁
LOCK TABLES accounts WRITE;  -- 加写锁
-- 或
LOCK TABLES accounts READ;   -- 加读锁

-- 操作...
UNLOCK TABLES;  -- 释放表锁

-- 悲观锁的锁粒度：
-- 表锁：锁整张表（MyISAM 默认）
-- 行锁：锁某一行（InnoDB 默认）
-- 间隙锁（Gap Lock）：锁一个范围，防止幻读
-- Next-Key Lock：行锁 + 间隙锁（InnoDB 默认的行锁算法）
```

**为什么需要它：** 悲观锁在**写多冲突多**的场景下更可靠，保证数据不会被并发修改。

**与相关术语的对比和区分：** 悲观锁通过数据库的锁机制实现，乐观锁通过应用层的版本号/CAS 实现。悲观锁性能较低但可靠性高，乐观锁性能高但需要处理冲突重试。

## 死锁检测与处理

**一句话定义（大白话）：** 两个或多个事务互相等待对方释放锁，形成"死循环"，系统检测到后会自动回滚其中一个事务。

**通俗类比（生活场景）：** 两个人在狭窄的路上相遇，A 说"你让一让"，B 说"你让一让"，谁也不让谁，僵住了。交警（数据库）过来把其中一个人拉到路边让路。

**具体示例：**

```sql
-- 死锁场景演示：

-- 事务 A：
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
-- 持有 user_id=1 的锁
-- 等待 user_id=2 的锁
UPDATE accounts SET balance = balance + 100 WHERE user_id = 2;

-- 事务 B（同时执行）：
START TRANSACTION;
UPDATE accounts SET balance = balance - 50 WHERE user_id = 2;
-- 持有 user_id=2 的锁
-- 等待 user_id=1 的锁
UPDATE accounts SET balance = balance + 50 WHERE user_id = 1;

-- 结果：死锁！MySQL 检测到后回滚其中一个事务

-- 查看死锁信息：
SHOW ENGINE INNODB STATUS\G

-- 死锁相关配置：
SHOW VARIABLES LIKE 'innodb_deadlock_detect';  -- 是否开启死锁检测
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';  -- 锁等待超时时间

-- 预防死锁的方法：
-- 1. 按固定顺序访问表和行
-- 2. 减小事务粒度，缩短事务执行时间
-- 3. 合理使用索引，减少锁的范围
-- 4. 避免大事务，拆分为小事务
```

**为什么需要它：** 死锁会导致事务永远等待，占用数据库资源。及时检测和处理死锁是保证系统可用性的关键。

**与相关术语的对比和区分：** 死锁是并发控制的**问题**，锁是并发控制的**工具**。死锁检测是数据库的**保护机制**，锁超时是**兜底方案**。

## Redo Log（重做日志）

**一句话定义（大白话）：** 记录"数据页做了什么修改"的日志，保证已提交事务的修改不会因为崩溃丢失。

**通俗类比（生活场景）：** 施工日志——每砌一块砖就记一笔。即使工地塌了，也能根据日志把砌好的墙恢复出来。Redo Log 就是数据库的"施工日志"。

**具体示例：**

```sql
-- Redo Log 是 InnoDB 引擎的核心机制，对用户透明

-- 工作流程：
-- 1. 事务修改数据时，先写 Redo Log（顺序写，快）
-- 2. Redo Log 写入磁盘后，事务就认为成功了
-- 3. 后台线程再把实际数据页写入磁盘（随机写，慢）

-- 即使写入数据页时崩溃：
-- 重启后根据 Redo Log 重做，保证数据不丢失

-- Redo Log 相关配置：
SHOW VARIABLES LIKE 'innodb_log_file_size';    -- 每个日志文件大小
SHOW VARIABLES LIKE 'innodb_log_files_in_group'; -- 日志文件数量
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'; -- 刷盘策略

-- innodb_flush_log_at_trx_commit 的三个值：
-- 0：每秒写入并刷盘（最快，可能丢 1 秒数据）
-- 1：每次提交都刷盘（最安全，默认）
-- 2：每次提交写入 OS 缓存，每秒刷盘（折中）
```

**为什么需要它：** 写数据页是随机 IO 很慢，写 Redo Log 是顺序 IO 很快。Redo Log 实现了"先写日志再写数据"（WAL），大幅提升写入性能。

**与相关术语的对比和区分：** Redo Log 保证**持久性**（崩溃恢复），Undo Log 保证**原子性**（回滚）。Redo Log 记录"做了什么"，Undo Log 记录"怎么撤销"。

---

## Undo Log（回滚日志）

**一句话定义（大白话）：** 记录"数据修改之前的样子"，用于事务回滚和 MVCC 版本链。

**通俗类比（生活场景）：** 游戏存档——每次做重大操作前先存档（Undo Log），如果操作失败了可以读档回到之前的状态。

**具体示例：**

```sql
-- Undo Log 的两大作用：

-- 作用一：事务回滚
START TRANSACTION;

UPDATE accounts SET balance = 1000 WHERE user_id = 1;
-- 此时 Undo Log 记录：旧值 balance=500

UPDATE accounts SET balance = 2000 WHERE user_id = 1;
-- Undo Log 继续记录：旧值 balance=1000

ROLLBACK;
-- 数据恢复到 balance=500（根据 Undo Log 逐条回滚）

-- 作用二：MVCC 版本链
-- 每行数据的修改都会形成一个版本链：
-- 当前版本 ← Undo Log 旧版本 ← 更早的版本 ← ...

-- 读操作通过版本链找到"自己能看到的版本"
```

**为什么需要它：** 没有 Undo Log，事务回滚就无法实现，MVCC 也无法工作。它是事务原子性和隔离性的重要基础。

**与相关术语的对比和区分：** Redo Log 记录"未来要做什么"（崩溃恢复），Undo Log 记录"过去做了什么"（回滚+MVCC）。两者配合保证了事务的 ACID 特性。
