# 乐观锁与悲观锁

> 📌 **导航**：本文是 **乐观锁与悲观锁** 词条，属于 database 术语集。相关枢纽：[[事务与并发控制术语]]、[[MySQL 锁机制]]、[[分布式锁]]、[[幂等性]]、[[并发读异常（脏读·不可重复读·幻读）]]。

## 定义

**一句话定义：** 悲观锁假定冲突常发生，操作前先加锁独占资源、完成再释放；乐观锁假定冲突少见，不加锁而在提交时用版本号/CAS 校验"期间是否被改过"，改过则重试——两者是对并发写冲突的两种相反策略。

**通俗类比：** 悲观锁像进厕所先反锁门，别人只能等你；乐观锁像多人协作编辑文档，各自改、保存时才比对——发现别人也改了就合并或重来，平时不锁门。

## 为什么需要它

多个写者改同一数据会互相覆盖（丢失更新）。要防它，要么"先占再改"（悲观锁，靠 DB 行锁/`FOR UPDATE`），要么"先改后验"（乐观锁，靠 version 字段或 CAS）。选错方向代价大：冲突多却用乐观 → 大量重试；冲突少却用悲观 → 白白串行化、吞吐骤降。

## 核心机制

- **悲观锁：** `SELECT ... FOR UPDATE` 在读取即加排他行锁，持锁到事务提交；适合冲突频繁、需强一致的场景。DB 内即用 [[MySQL 锁机制]] 的行锁。
- **乐观锁：** 读时带 `version`（或时间戳/数据比对），写时 `UPDATE ... SET version=version+1 WHERE id=? AND version=旧值`；影响行数为 0 说明被别人改过 → 重读重试（CAS 思想）。适合读多写少、冲突少。
- **权衡：** 悲观"牺牲并发换确定"，乐观"牺牲重试成本换高并发"；乐观锁的更新与校验必须原子（靠单条 UPDATE 的条件或事务）。

## 具体示例

商品库存扣减：冲突高（秒杀）用悲观 `SELECT ... FOR UPDATE` 锁住行再判断扣减，天然防超卖；读多写少的资料编辑用乐观锁——表单带 version，提交时 `UPDATE ... WHERE id=5 AND version=3`，若返回 0 行则提示"数据已被他人修改，请刷新重试"。CAS 无锁结构同理：比较内存期望值再原子交换，失败即重试。

## 何时用 / 何时不用

- **用悲观：** 写冲突概率高、临界区必须独占、宁可排队也要强一致。
- **用乐观：** 读多写少、冲突罕见、希望高并发吞吐；可接受偶尔重试成本。
- **注意：** 乐观锁不保证不丢更新，必须让"比较并更新"原子；跨进程/跨库场景单机乐观锁不够，需 [[分布式锁]] 或共识。

## 优劣与代价

✅ 悲观直观、强一致；乐观无阻塞、高并发下吞吐好、减少锁持有时间。
⚠️ 悲观易锁等待/死锁、降低并发；乐观高冲突时重试风暴、空耗资源。
⚠️ 乐观 ABA 问题（值绕回原样）需版本递增而非等值判断规避。

## 与相关概念的区别

- **乐观 vs 悲观：** 区别在"何时检测冲突"——悲观在读前加锁独占，乐观在写时比对不独占。
- **DB 行锁 vs 应用层 version：** 悲观多由数据库锁实现，乐观常用一个 version 列在应用/SQL 层实现，不长期占锁。
- **vs [[分布式锁]]：** 那是跨进程用 Redis/ZK 实现的互斥，乐观/悲观更多指单库内对并发写的处理哲学。

## 常见误区

- 乐观锁因为不加锁，所以永远不会发生更新丢失。
- 悲观锁一定优于乐观锁，因为它能保证绝对安全。
- 只要给表加个 version 字段，就自动实现了乐观锁。

## 面试速答

> 🎯 悲观锁先加锁再操作（SELECT FOR UPDATE 持排他行锁到提交），适合写冲突多、强一致，代价锁等待/死锁、并发低；乐观锁不加锁、提交时 version/CAS 校验、0 行即重试，适合读多写少高并发，代价是重试风暴与 ABA。区别在何时检测冲突，跨进程互斥另用分布式锁。
