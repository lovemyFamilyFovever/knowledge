# 存储过程与触发器


> 📌 **导航**：本文是 **存储过程与触发器** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[Redis深入]]、[[Redis深度解析与实战指南]]、[[SQL 基础术语]]。

## 定义

**一句话定义：** 存储过程（Stored Procedure）是预先编译并存储在数据库中、可被调用执行的一段 SQL/过程化代码；触发器（Trigger）是与表绑定、在特定事件（INSERT/UPDATE/DELETE）发生时自动执行的特殊存储过程；二者都把业务逻辑下沉到数据库端。

**通俗类比：** 存储过程像银行柜台预设好的"一站式办理流程"（你报个需求，柜员按既定流程一次办完，不用你来回跑）；触发器像"自动感应门"——某个动作发生时（如余额变动），它自动被触发执行预设的后续动作（如记一笔流水）。

> 多义说明：存储过程需**显式调用**；触发器由**事件自动触发**。二者都是数据库端的过程化对象。本文并述。

## 为什么需要它

把一串必须原子完成的 SQL 放到客户端逐条发，会有多次网络往返、中途断连留下半成品、逻辑散落在多套应用里。存储过程将这些步骤收进服务端一次调用、可在同一事务里提交回滚；触发器则把"只要这张表变了就必须发生"的事（审计、级联、约束校验）绑到表上，保证无论谁从哪条路径改数据都不会漏掉。

## 核心机制

- **存储过程：** 用 PL/SQL、T-SQL、PL/pgSQL 等编写，含参数、控制流与事务；通常预编译（执行计划可缓存），一次调用完成多步，减少网络往返。
- **触发器：** 定义时机（BEFORE / AFTER / INSTEAD OF）× 事件（INSERT / UPDATE / DELETE）；可访问 OLD / NEW 行值；常用于审计、级联、约束校验、自动填充。
- **执行位置：** 都在数据库服务器端执行。

| 组成 | 说明 |
|------|------|
| 存储过程 | 参数、预编译、显式调用 |
| 触发器 | 事件 + 时机（BEFORE/AFTER） |
| OLD / NEW | 触发器访问变更前后行值 |
| 过程化 SQL | 控制流、变量、事务 |

## 具体示例

一个 `transfer(from, to, amt)` 存储过程：服务端开事务，先 `UPDATE ... SET balance=balance-amt`、校验余额充足，再给收款方加款，两步在同一事务内，任一步失败整体回滚，客户端只需 CALL 一次。配套的 `AFTER UPDATE ON accounts` 触发器读取 OLD.balance 与 NEW.balance，把每笔变动写入流水审计表——即使有别的系统绕过应用直接 UPDATE，流水也不会漏记。

## 何时用 / 何时不用

- **用：** 复杂批处理/结算、强一致的多步原子操作、跨应用统一的数据审计与级联约束、需减少网络往返的高频操作。
- **不用：** 频繁迭代的业务规则、需要完整版本控制/单元测试/调试的主流程逻辑（现代多放应用层）；跨数据库需可移植时；触发器链路过长易致隐式级联与性能不可控的场景。

## 优劣与代价

✅ 逻辑集中、减少网络往返、预编译性能好、可复用、能与服务端事务同生命周期。
⚠️ 业务逻辑入库后难做版本控制/测试/调试，可移植性差（绑定特定数据库）。
⚠️ 数据库易变"胖"成瓶颈；触发器隐式执行难追踪，易埋意外级联坑。

## 与相关概念的区别

- **存储过程 vs 触发器：** 前者显式 CALL、可返回结果集；后者由表事件自动触发、无返回值，靠 OLD/NEW 感知变更。
- **存储过程 vs 函数（FUNCTION）：** 函数返回单值可嵌入查询表达式，存储过程偏执行一段带副作用的流程。
- **vs 应用层逻辑：** 数据库端省往返、贴近数据但难维护；应用端易测试部署但多次交互，权衡分层。

## 常见误区

- 触发器需要程序显式调用才会执行。
- 把越多业务逻辑塞进存储过程和触发器，架构就越好。
- 存储过程和触发器像应用代码一样便于版本控制与调试。

## 面试速答

> 🎯 存储过程=预编译存库、显式调用的一段过程化 SQL（省往返、贴事务、可缓存执行计划）；触发器=绑在表事件上自动执行、能读 OLD/NEW 的特殊存储过程（审计/级联/约束）。两者都把逻辑下沉服务端，代价是难版本控制/调试、可移植性差、DB 易变胖，现代多主张业务逻辑放应用层。
