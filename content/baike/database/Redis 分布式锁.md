# Redis 分布式锁

> 📌 **导航**：本文是 **Redis 分布式锁** 词条，属于 database 术语集。相关枢纽：[[Redis深度解析与实战指南]]、[[Redis 高可用架构（主从·哨兵·集群）]]、[[分布式锁]]、[[幂等性]]、[[CAP 定理]]。

## 定义

**一句话定义：** Redis 分布式锁是用 Redis 的原子命令实现的跨进程互斥：以 `SET key value NX EX ttl` 抢锁、用带唯一值的 Lua 脚本安全释放，多副本可靠性则靠 Redlock 在多个独立节点上多数加锁。

**通俗类比：** 像公共试衣间：进门反锁并在门上留"是谁在用"的纸条（value），只有锁着的人能凭纸条开锁离开（Lua 比对再删，防止误开别人的锁）；怕一台门锁坏了误判，就同时在几间门各上一道、过半锁住才算占用（Redlock）。

## 为什么需要它

单机 `synchronized`/本地锁管不住多实例并发访问共享资源（超卖、重复扣款、任务重复执行）。需要一个所有进程都认的外部仲裁者，Redis 原子、低延迟、天然共享，适合当"抢锁"的中心：`SET NX` 的原子性保证同一时刻只有一个持有者，TTL 防止持有者崩溃后死锁。

## 核心机制

- **加锁：** `SET lock:<res> <uuid> NX EX <ttl>` —— NX 保证仅不存在时设置（互斥），EX 设过期（防死锁），uuid 作持有者标识。
- **解锁：** 必须"判断是自己的锁再删"，且判断与删除原子，故用 Lua：`if GET==ARGV[1] then DEL` —— 否则可能误删别人因超时而重获的锁。
- **锁续期：** 业务超过 TTL 会提前放锁，需看门狗（如 Redisson）在持锁期间周期延长，进程挂了不再续、锁自然过期。
- **Redlock：** 向 N 个独立 Redis 依次加锁，多数成功且总耗时小于锁有效期才认定持锁；释放时逐个删。用以缓解"单点主从切换丢锁"。

## 具体示例

防止超卖：下单时 `SET lock:sku:1 uuid NX EX 30` 抢到才扣库存；处理可能超 30 秒则靠看门狗每 10 秒续期。若实例在"锁已过期但业务未完"时被另一节点抢到，就出现并发进入——这正是单点/主从下 Redis 锁的固有缝隙，Redlock 用多节点多数派降低它，但时钟漂移与 GC 停顿仍使其非绝对安全。

## 何时用 / 何时不用

- **用：** 跨实例的短时互斥（防重复消费、防超卖、单飞回源）；能接受"尽力而为"的锁语义。
- **不用/慎用：** 强正确性、不能容忍任何并发重入的关键账务（用数据库行锁/唯一约束或带共识的锁服务如 etcd/ZooKeeper）；把 Redlock 当"绝不失效"的银弹；主从异步切换会丢锁状态。

## 优劣与代价

✅ 轻量、低延迟、跨语言，TTL + 看门狗防死锁与提前释放。
⚠️ 单点与主从切换可能丢锁（锁被两个持有者同时持有）；Redlock 依赖时钟假设、有争议。
⚠️ 不能替代幂等——正确性最终仍需业务侧幂等兜底（见 [[幂等性]]）。

## 与相关概念的区别

- **vs [[分布式锁]]（通用）：** 那篇讲共识类锁服务（ZooKeeper/etcd 用 CP）；本篇是 Redis 这一 AP 取向的具体实现与其可靠性边界。
- **单实例 vs Redlock：** 单实例锁受主从丢数据威胁；Redlock 用 N 副本多数派提升可用性，但代价是复杂与对时钟的假设。
- **vs 数据库锁：** 行锁/唯一约束由 DB 保证强一致，但吞吐与跨库场景受限；Redis 锁快但语义更弱。

## 常见误区

- 只要加了 Redis 分布式锁，业务逻辑就绝对不会有并发重入。
- SETNX 加锁后不设置过期时间也是安全的。
- 释放锁时直接 DEL 即可，无需先判断锁是不是自己的。

## 面试速答

> 🎯 分布式锁=SET NX EX 抢锁(NX 互斥、EX 防死锁、带 uuid 标主)+Lua 比对 value 再删原子释放+看门狗续期；主从切换会丢锁，多副本用 Redlock 多数加锁。它是尽力而为互斥、不绝对安全，仍需幂等兜底，强正确改用 ZK/etcd 或 DB 锁。
