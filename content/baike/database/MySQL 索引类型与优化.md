# MySQL 索引类型与优化

> 📌 **导航**：本文是 **MySQL 索引类型与优化** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[B+树]]、[[索引与查询优化术语]]、[[事务隔离级别]]。

## 定义

**一句话定义：** MySQL 索引类型与优化指 InnoDB 的聚簇索引与二级（非聚簇）索引结构，以及围绕它们的优化手段——覆盖索引避免回表、最左前缀决定联合索引能否命中、索引下推（ICP）与多范围读（MRR）减少回表与随机 I/O。

**通俗类比：** 聚簇索引像按学号排好、抽屉里直接放着整份档案的柜架（找到学号就拿到全部资料）；二级索引像按姓名编的目录，只写着"姓名→学号"，看到姓名还得回到柜架取档案（回表）；覆盖索引就是目录上顺便把你要的那几栏也印上了，不用回柜架。

## 为什么需要它

InnoDB 数据按主键组织成聚簇索引，二级索引叶子里只存主键值。理解"聚簇 vs 二级"才能解释回表从哪来、为什么要覆盖索引；理解最左前缀才能解释联合索引为何有时失效。索引用得好不好，直接决定一条查询走 O(log n) 还是全表扫描，是 OLTP 性能的第一抓手。

## 核心机制

- **聚簇索引：** 主键索引，叶子节点存整行；无主键时选首个非空唯一索引，都没有则用隐藏 rowid。
- **二级索引：** 叶子存"索引列 + 主键值"，命中后需回表取整行；建联合索引要守 [[B+树]] 的有序性。
- **覆盖索引：** 查询列都在索引内，无需回表，`EXPLAIN` 的 Extra 显示 `Using index`。
- **最左前缀：** 联合索引 `(a,b,c)` 只有从 a 起连续匹配才用得上，跳过 a 或中间断档会退化。
- **索引下推 ICP：** 把索引里能判断的条件（如 `name LIKE '张%'`）下推到存储引擎层过滤，减少回表次数，Extra 显示 `Using index condition`。
- **多范围读 MRR：** 先把二级索引拿到的主键排序，再按序回表，把随机 I/O 变顺序 I/O。

## 具体示例

`INDEX(name, age)`，查 `WHERE name='张三' AND age>20`：先用 name 定位、再在索引内判 age>20，若 SELECT 只要 name/age 即覆盖索引免回表。查 `WHERE age>20`（不含 name）则用不上该索引，违反最左前缀。`INDEX(age,name)` 时，ICP 让存储引擎在索引层先用 name 条件筛掉不符的行，只把真要的行回表；而 `IN` 一批主键回表时 MRR 先排序主键再顺序回读，减少随机跳页。

## 何时用 / 何时不用

- **用：** 高频查询建二级/联合索引并按查询模式排好列序（等值列在前、范围列在后）；SELECT 指定必要列以吃到覆盖索引；面对大量随机回表考虑 MRR/ICP（默认开启）。
- **不用：** 低基数列（性别、布尔）单建索引价值低、还拖慢写；索引过多增空间与维护；前导模糊 `LIKE '%x'`、列上做函数、隐式类型转换都会让索引失效。

## 优劣与代价

✅ 合理索引把查询从全表扫描降到索引定位，覆盖/ICP/MRR 进一步省回表与随机 I/O。
⚠️ 索引占空间、拖慢写；建多/建错反而劣化。
⚠️ 最左前缀、失效场景等约束多，需按查询模式专门设计。

## 与相关概念的区别

- **聚簇 vs 二级：** 聚簇叶子存整行、二级叶子存"列+主键"需回表；一表只有一个聚簇索引。
- **vs [[索引与查询优化术语]]：** 那篇是跨引擎的索引通用原理，本篇专注 MySQL/InnoDB 的索引与优化手法。
- **vs [[B+树]]：** B+树是底层结构，本篇是其上的索引语义与优化技巧。

## 常见误区

- 只要给查询涉及的列建了索引，无论条件顺序如何都能命中。
- 二级索引查到索引项后就算拿到整行数据，不需要回表。
- 索引建得越多，查询就一定越快。

## 面试速答

> 🎯 InnoDB 聚簇索引叶子存整行、二级索引叶子存"列+主键"需回表；覆盖索引让查询列全在索引内以免回表、联合索引守最左前缀否则退化、ICP 在引擎层用索引内条件先筛减少回表、MRR 把回表主键排序后顺序读化随机为顺序。低基数列/前导模糊/列上函数/隐式转换会让索引失效。
