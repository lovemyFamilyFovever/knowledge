# 分库分表


> 📌 **导航**：本文是 **分库分表** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[Redis深入]]、[[Redis深度解析与实战指南]]、[[SQL 基础术语]]。

## 定义

**一句话定义：** 分库分表（Sharding / 数据库拆分）是当单库单表的数据量或访问量超出承载能力时，把数据按某种规则水平拆分到多个数据库/多张表（或垂直按业务/字段拆分），以分散存储与负载、提升容量与并发能力的方案。

**通俗类比：** 像一个图书馆书太多、一个书架和一个管理员忙不过来——于是按类别把书分到多个房间、多个书架（分库分表），每个房间配管理员；查书时先按规则定位到哪个房间、哪个架子。

> 多义说明：**水平拆分**（按行，同结构分散到多库/表）与**垂直拆分**（按业务/字段，拆成不同表/库）；分片（sharding）通常指水平拆分。本文兼顾。

## 为什么需要它

单库单表到千万级后，索引树变深、锁竞争加剧、备份与 DDL 变慢，单机磁盘与连接也逼近上限。分库分表把一张大表按行拆到多库多表，让存储、I/O、连接、锁分散到多个实例上，用"多机各扛一部分"换回单机曾经的容量与并发水位——是垂直扩展（加更好机器）到顶后的水平扩展手段。

## 核心机制

- **拆分方式：** 水平分表（单库多表）、水平分库（多库）、垂直分库（按业务）、垂直分表（按冷热字段）。
- **分片键（sharding key）与路由：** 按 hash（分布均匀但范围查询难）、按 range（范围友好但易热点）、按业务/地理。
- **难点：** 跨库 JOIN 与聚合、分布式事务、全局唯一 ID、扩容再平衡（rehash / 一致性哈希）、跨分片的分页与排序。
- **中间件：** ShardingSphere、MyCat、Vitess、TDDL 等。

| 组成 | 说明 |
|------|------|
| 分片键 | 决定数据落到哪个库/表 |
| 分片算法 | hash / range / 一致性哈希 |
| 路由层 | 解析 SQL 并定位分片 |
| 全局 ID | 跨分片唯一标识（如雪花算法） |
| 扩容再平衡 | 数据迁移与重分布 |

## 具体示例

订单表按 `user_id % 16` 做 hash 分到 16 张表：查"某用户全部订单"带 user_id → 路由层直接算出落点，只打一张表；查"某天全平台订单"不带分片键 → 要广播扫 16 张表再归并排序、分页取全局前 N，代价高，这类需求通常另走 ES/数仓。全局订单号用雪花算法生成，避免各分片自增冲突。将来扩到 32 片时按 2 倍分裂迁移，一致性哈希可把搬迁量降到最小。

## 何时用 / 何时不用

- **用：** 海量数据存储（亿级以上）、高并发写入、大型互联网业务（订单/用户/日志）、单表过大导致性能瓶颈，且已评估迁移成本。
- **不用：** 未先做索引优化、读写分离、缓存就急着拆（分库分表应是最后手段）；数据量小、强依赖复杂多表 JOIN 与事务的分析型场景（更偏数仓）。

## 优劣与代价

✅ 突破单机容量与性能瓶颈、分散负载、可水平扩展。
⚠️ 复杂度大增：分布式事务、跨库查询、运维成本陡升。
⚠️ 分片键选择关键且难更改；扩容迁移成本高；可能出现数据倾斜/热点。

## 与相关概念的区别

- **vs 读写分离：** 读写分离用主从复制缓解"读压力"，数据总量仍在单库；分库分表解决"单库放不下/写不动"。
- **垂直拆分 vs 水平拆分：** 垂直按业务/字段切（列方向），水平按行切到同结构多片（行方向），目的不同不可互替。
- **vs 单机分区（partition）：** 分区仍在同一实例内，分库分表跨多个实例，前者无分布式事务问题。

## 常见误区

- 数据量一大就应该立刻上分库分表。
- 分片键随便选一个字段就行，之后也很容易改。
- 分库分表之后跨库 JOIN、事务和分页跟单库一样简单。

## 面试速答

> 🎯 分库分表=单库扛不住时的水平扩展：水平按行分片(hash/range/一致性哈希)、垂直按业务/字段拆，靠分片键+路由层定位；代价是跨库 JOIN、分布式事务、全局 ID、扩容再平衡都变难，故应先穷尽索引/读写分离/缓存再拆。
