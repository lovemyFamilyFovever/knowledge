# 数据库连接池


> 📌 **导航**：本文是 **数据库连接池** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[Redis深入]]、[[Redis深度解析与实战指南]]、[[SQL 基础术语]]。

## 定义

**一句话定义：** 数据库连接池（Database Connection Pool）是一种在应用启动时预先创建并复用一批数据库连接、按需借出与归还的技术，避免为每次数据库操作都新建和销毁连接，从而显著降低连接开销、提升性能与资源利用率。

**通俗类比：** 像出租车公司——不必每位乘客来了都现造一辆车（新建连接），而是预先备一批车在停车场（连接池），乘客来了直接派一辆（借连接），到站后车归还待命（还连接），下一位接着用。

> 多义说明：连接池是"对象池/资源池"模式的一种；各语言/框架都有实现（HikariCP、Druid、DBCP、SQLAlchemy pool 等）。本文讨论通用机制。

## 为什么需要它

每次建数据库连接要走 TCP 三次握手、认证、会话/字符集初始化，服务端还要分配线程与内存——这套开销远高于一次普通查询，高并发下频繁建连既拖慢响应又可能打爆数据库连接上限。连接池把"昂贵且可复用"的连接预先建好、借出后归还而非关闭，用复用摊薄建连成本，同时用最大连接数给数据库设一道并发闸门。

## 核心机制

- **初始化：** 预创建最小数量的连接放入池中，维护空闲/使用中状态。
- **借用与归还：** 应用请求时借出一个空闲连接，用完归还（而非关闭），由池管理其生命周期。
- **参数：** 最小/最大连接数、获取超时、空闲回收、连接有效性检测（如 validationQuery / testOnBorrow）、泄漏检测。
- **为何有效：** 数据库建连（TCP + 认证 + 会话初始化）开销大，复用连接省去重复建连成本。

| 组成 | 说明 |
|------|------|
| 空闲 / 活跃连接 | 池中的连接状态 |
| 最小 / 最大连接数 | 池容量控制 |
| 借用 / 归还 | 连接的取用与回收 |
| 连接校验 | 剔除失效连接 |
| 超时与泄漏检测 | 防止耗尽与死等 |

## 具体示例

一次 HTTP 请求要查库：从池借一条空闲连接，若池已满则等待到 `connectionTimeout` 再抛异常，请求结束后归还连接（不 close）；借出前用 `testOnBorrow`/心跳校验剔除被数据库或防火墙单方面断掉的死连接。若某处代码查询后忘了归还，池会被逐步占满，泄漏检测在连接借出超过阈值时打印堆栈定位未归还处。最大连接数常按 CPU 核数与"数据库能扛的活跃连接"设定，而非越大越好。

## 何时用 / 何时不用

- **用：** Web 应用与后端服务的数据库访问、ORM 框架、高并发系统的连接管理、微服务（每个实例各配池，总量需统一规划）。
- **不用/注意：** 极低频一次性脚本（建连开销可忽略，直连更简单）；池参数照搬不结合 DB 承载与时延目标时，反而制造排队或压垮数据库。

## 优劣与代价

✅ 大幅降低建连开销、提升吞吐与响应、控制并发连接数保护数据库、复用资源。
⚠️ 连接数需权衡：过大压垮数据库、过小导致排队等待。
⚠️ 连接失效/泄漏需处理；分布式下各实例各有池，总量需统一控制。

## 与相关概念的区别

- **vs 每次新建连接：** 池用复用摊薄建连成本并限并发，直连实现简单但高频下开销大、无上限保护。
- **vs 通用对象池：** 连接池专管"连接"这一昂贵资源，额外要做有效性校验与泄漏检测，因连接会被服务端超时回收。
- **vs 读写分离/路由中间件：** 连接池只负责取用物理连接，SQL 该发往主库还是从库由 [[读写分离]] 等上层逻辑决定。

## 常见误区

- 连接池最大连接数设得越大，系统并发能力就越强。
- 用完连接忘了归还没关系，反正会被自动回收。
- 上了连接池之后 SQL 查询本身就会变快。

## 面试速答

> 🎯 连接池=预先建好并复用昂贵 DB 连接的对象池：初始化最小连接、按需借出/归还(而非关闭)，配最大最小数、获取超时、有效性校验与泄漏检测来摊薄 TCP+认证建连开销、限并发保护 DB；核心风险是配太大压垮 DB、太小排队，以及忘归还致泄漏，且不改变单条 SQL 效率。
