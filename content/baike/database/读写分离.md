# 读写分离


> 📌 **导航**：本文是 **读写分离** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[Redis深入]]、[[Redis深度解析与实战指南]]、[[SQL 基础术语]]。

## 定义

**一句话定义：** 读写分离是一种数据库架构方案,把写操作(增删改)路由到主库、读操作(查询)分发到一个或多个只读从库,通过主从复制同步数据,以分散读压力、提升系统的读吞吐与可用性。

**通俗类比：** 像一个热门餐馆——只有一个后厨能改菜(主库负责写),但开了多个取餐/展示窗口(从库负责读)分流顾客;后厨做好后同步到各窗口,顾客大多只是"看/取"(读),分流后就不挤了。

> 多义说明:读写分离基于主从复制;与分库分表(水平拆分)是不同维度的扩展手段,常结合使用。本文讨论读写分离。

## 原理与机制

- **主从复制:** 主库写 binlog/WAL,从库拉取并重放(relay log)以保持同步(异步 / 半同步 / 组复制)。
- **读写路由:** 由应用或中间件(如 ProxySQL、MyCat、ShardingSphere)把写发往主库、读分发到从库。
- **复制延迟(主从延迟):** 从库数据可能滞后于主库,导致"刚写完立即读"读到旧值。
- **应对延迟:** 关键读走主库、会话内"读己之写"强制主库、半同步复制、缓存兜底。

## 关键组成

| 组成 | 作用 |
|------|------|
| 主库 | 处理写操作 |
| 从库(可多个) | 处理读操作 |
| 主从复制 | binlog / relay log 同步 |
| 读写路由中间件 | 分发读写请求 |
| 延迟处理 | 关键读走主库等策略 |

## 应用场景

- 读多写少的业务(内容、查询类系统)
- 提升读并发与可用性
- 主库故障时从库可提升为主(高可用)
- 报表/分析类查询走从库,避免影响主库

## 优点与局限

- 优点:分散读压力、提升读吞吐与可用性;实现相对简单(不改数据模型)。
- 局限:主从延迟带来一致性问题;写仍是单主瓶颈(需分库分表);复制与运维复杂度上升;故障切换需要机制保障。

## 常见误区

- 读写分离不解决写瓶颈(写仍集中在主库,需分库分表/分片)。
- 存在复制延迟,"写后立即读"可能读到旧值(需强制走主库)。
- 从库不是实时强一致的。
- 读写分离 ≠ 分库分表:前者是主从分工,后者是水平拆分。
