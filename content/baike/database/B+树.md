# B+树


> 📌 **导航**：本文是 **B+树** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[Redis深入]]、[[Redis深度解析与实战指南]]、[[SQL 基础术语]]。

## 定义

**一句话定义：** B+树是一种自平衡的多路搜索树，其所有数据（或指向数据的指针）都存储在叶子节点、内部节点只存索引键，且叶子节点通过指针相连形成有序链表；它是关系型数据库索引（如 MySQL InnoDB）的主流底层结构。

**通俗类比：** 像一本书的多级目录——先查大章节（内部节点，只给方向和页码范围），再翻到具体页（叶子节点，才有正文）；而且所有"正文页"还用书签串成一条顺序带（叶子链表），方便从头到尾连续翻阅（范围查询）。

展开一句：要把它和 **B树（B-tree）** 分清——B树的数据分布在所有节点，B+树的数据只在叶子且叶子之间连成链表；本文讨论的是 B+树。

## 为什么需要它

数据库索引面对的是磁盘块存储，每次读取一页代价高昂。普通二叉搜索树高度约 log₂n，千万级数据就有二三十层，意味着二三十次随机磁盘 I/O；哈希索引虽然点查 O(1)，却不支持范围查询和有序遍历。B+树用"多路、高扇出"把树压到 3~4 层，把随机 I/O 降到个位数，又靠有序叶子链表保住范围扫描能力——这正是磁盘型数据库索引的核心诉求。

## 核心机制

- **多路平衡（高扇出）：** 每个节点可容纳多个键与子指针，使树非常"矮胖"，通常 3~4 层即可索引千万级行，从而把磁盘 I/O 压到很低。
- **内部节点只存键：** 不存数据，单个节点能放下更多键，扇出更大、树更矮。
- **叶子存全量数据/指针并相连成链表：** 使范围扫描与顺序访问非常高效。
- **自平衡：** 插入/删除通过节点分裂与合并维持平衡，查询代价稳定为 O(log n)。

| 组成 | 作用 |
|------|------|
| 内部节点 | 仅存键 + 子指针，负责导航 |
| 叶子节点 | 存全部键 + 数据（或数据指针） |
| 叶子链表 | 连接叶子，支持高效范围查询 |
| 阶（order）/扇出 | 每节点的最大子节点数 |
| 分裂 / 合并 | 维持平衡的动态调整 |

## 具体示例

在 InnoDB 里对主键做一次 `WHERE id BETWEEN 100 AND 200`：从根节点按键导航到 id=100 所在叶子，命中后不再回到树上层，而是顺着叶子链表向右连续扫描到 id=200。整棵三层树只需 3 次页读取定位起点，其后都是叶子页的顺序读；换成 B树则要在各层节点间来回跳转，无法用一条链表连续扫描。

## 何时用 / 何时不用

- **用：** 关系数据库主键索引与二级索引、文件系统/存储引擎索引，以及需要频繁范围查询、排序、顺序扫描的场景。
- **不用：** 只做海量等值点查、不关心顺序的 KV 存储（哈希或 [[LSM 树]] 更省写放大）；数据量小到全在内存的场景，用普通二叉树/红黑树即可，无需按页组织。

## 优劣与代价

✅ 树矮、磁盘 I/O 少，范围查询与有序遍历高效，查询代价稳定 O(log n)。
⚠️ 写入需维护结构、可能触发页分裂，随机写友好度不如 LSM-Tree。
⚠️ 节点按页预留空间，删除或多变长记录会产生碎片与空间浪费。

## 与相关概念的区别

- **vs B树：** 关键差异在数据存储位置（B+树只在叶子）与叶子链表；B+树内部节点不存数据，扇出更大、范围查询更强。
- **vs 哈希索引：** 哈希点查更快但不支持范围/排序，B+树两类都支持。
- **vs LSM-Tree：** LSM 为写密集优化（顺序追加），B+树为读与范围均衡优化（原地更新、易页分裂）。

## 常见误区

- B+树的内部节点和叶子节点一样存储完整数据。
- B+树和 B树是同一个结构的不同叫法。
- B+树范围查询快是因为在内部节点逐层向下遍历。

## 面试速答

> 🎯 B+树=自平衡多路搜索树：内部节点只存键、数据全在叶子、叶子连成有序链表；高扇出使千万级数据仅 3~4 层，随机 I/O 少且范围扫描高效，是 InnoDB 等磁盘索引的主流结构。
