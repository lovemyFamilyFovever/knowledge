# 数据库范式


> 📌 **导航**：本文是 **数据库范式** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[Redis深入]]、[[Redis深度解析与实战指南]]、[[SQL 基础术语]]。

## 定义

**一句话定义：** 数据库范式（Normal Form）是关系数据库设计中衡量表结构规范程度的一系列标准，通过逐步消除数据冗余与更新异常（插入/删除/修改异常），使表结构更合理；常见的有 1NF、2NF、3NF 与 BCNF。

**通俗类比：** 像整理档案——同一条信息（如"某部门经理是谁"）只在一处登记、不重复抄写，其他地方用编号引用；这样改一次就够，不会出现"这份改了那份没改"的矛盾。

> 多义说明：范式化（normalization，减少冗余）与反范式化（denormalization，为查询性能适度引入冗余）是设计权衡的两端；本文讲范式（1NF ~ BCNF）。

## 为什么需要它

把相互依赖的事实堆进一张宽表，会让同一数据重复存储：更新时要改多处否则不一致（修改异常），插不进没有主关联的孤数据（插入异常），删一条顺带丢了别的信息（删除异常）。范式用函数依赖这套形式工具，把"谁决定谁"理清楚，逐条拆表消除冗余与这三类异常，是 OLTP 建模保证一致性的基线。

## 核心机制

- **1NF（第一范式）：** 字段具原子性，每列不可再分、无重复组。
- **2NF：** 满足 1NF，且消除非主属性对候选键的**部分函数依赖**（主要针对复合主键）。
- **3NF：** 满足 2NF，且消除非主属性对候选键的**传递依赖**。
- **BCNF：** 满足 3NF，且每个"决定因素"都包含候选键（进一步消除主属性相关的异常）。
- **更高范式：** 4NF（消除多值依赖）、5NF（消除连接依赖），实践中较少使用。

| 概念 | 含义 |
|------|------|
| 函数依赖 | 属性间的决定关系 X → Y |
| 候选键 / 主属性 | 唯一标识与参与键的属性 |
| 部分依赖 | 非主属性依赖复合键的一部分 |
| 传递依赖 | A→B→C 造成的间接依赖 |
| 1NF/2NF/3NF/BCNF | 逐级更严格的规范 |

## 具体示例

一张 `订单(订单号, 商品, 数量, 类别, 类别负责人)` 里"类别负责人"随每个商品行重复。逐步规范：先保证每列原子、无重复组（1NF）；把商品明细按"订单号+商品"拆出，非主属性不再部分依赖复合键（2NF）；发现 类别→类别负责人 是订单行对键的传递依赖，把类别与其负责人另立 `类别表`（3NF）。此后改某类别负责人只需更新一行，插入一个新类别也不必先有订单——冗余与异常消除，代价是按类别统计时要 JOIN 类别表。

## 何时用 / 何时不用

- **用：** 关系数据库表结构设计、OLTP 系统（减少冗余、保证一致性）、既有表结构重构，通常做到 3NF/BCNF 即止。
- **不用（可反范式）：** OLAP/报表、读多写少且查询要扫大量 JOIN 的场景，会为性能有意冗余列或物化汇总表；极高并发的热点读也常牺牲范式换一次查全。

## 优劣与代价

✅ 减少数据冗余、避免更新异常、结构清晰、节省存储。
⚠️ 过度范式化产生大量表连接（JOIN）、拖慢查询。
⚠️ 范式只保证结构一致，不保证性能，需结合访问模式权衡。

## 与相关概念的区别

- **3NF vs BCNF：** 3NF 允许"主属性依赖主属性"的边角异常，BCNF 进一步要求每个决定因素都含候选键，比 3NF 更严。
- **范式化 vs 反范式化：** 前者以 JOIN 换一致性，后者以冗余换读性能，是有意的权衡而非对错。
- **vs 维度建模：** 数仓星型/雪花模型本就以冗余宽表换分析查询速度，不追求 BCNF。

## 常见误区

- 数据库范式等级越高越好，应尽量做到最高范式。
- 只要满足范式，查询性能就一定高。
- 做反范式化说明当初的设计是错的。
