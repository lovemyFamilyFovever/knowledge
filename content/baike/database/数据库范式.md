# 数据库范式


> 📌 **导航**：本文是 **数据库范式** 词条，属于 database 术语集。相关枢纽：[[MySQL从入门到架构师]]、[[MySQL深入]]、[[Redis深入]]、[[Redis深度解析与实战指南]]、[[SQL 基础术语]]。

## 定义

**一句话定义：** 数据库范式(Normal Form)是关系数据库设计中衡量表结构规范程度的一系列标准,通过逐步消除数据冗余与更新异常(插入/删除/修改异常),使表结构更合理;常见的有 1NF、2NF、3NF 与 BCNF。

**通俗类比：** 像整理档案——同一条信息(如"某部门经理是谁")只在一处登记、不重复抄写,其他地方用编号引用;这样改一次就够,不会出现"这份改了那份没改"的矛盾。

> 多义说明:范式化(normalization,减少冗余)与反范式化(denormalization,为查询性能适度引入冗余)是设计权衡的两端;本文讲范式(1NF ~ BCNF)。

## 原理与机制

- **1NF(第一范式):** 字段具原子性,每列不可再分、无重复组。
- **2NF:** 满足 1NF,且消除非主属性对候选键的**部分函数依赖**(主要针对复合主键)。
- **3NF:** 满足 2NF,且消除非主属性对候选键的**传递依赖**。
- **BCNF:** 满足 3NF,且每个"决定因素"都包含候选键(进一步消除主属性相关的异常)。
- **更高范式:** 4NF(消除多值依赖)、5NF(消除连接依赖),实践中较少使用。

## 关键组成

| 概念 | 含义 |
|------|------|
| 函数依赖 | 属性间的决定关系 X → Y |
| 候选键 / 主属性 | 唯一标识与参与键的属性 |
| 部分依赖 | 非主属性依赖复合键的一部分 |
| 传递依赖 | A→B→C 造成的间接依赖 |
| 1NF/2NF/3NF/BCNF | 逐级更严格的规范 |

## 应用场景

- 关系数据库表结构设计
- OLTP 系统(减少冗余、保证一致性)
- 数据建模与既有表结构重构

## 优点与局限

- 优点:减少数据冗余、避免更新异常、结构清晰、节省存储。
- 局限:过度范式化会产生大量表连接(JOIN)、拖慢查询;因此 OLAP / 读多写少场景常做反范式化(用冗余换性能)。

## 常见误区

- "范式越高越好"是错的:需按场景权衡,通常做到 3NF / BCNF 即止。
- 范式化 ≠ 一定高性能:它可能增加 JOIN 成本。
- 反范式不是"设计错误",而是有意的性能权衡。
- 范式理论针对关系模型中的函数依赖。
