# RAG系统工程化实践


> 📌 **导航**：本文是 **RAG系统工程化实践** 词条（工程化枢纽）。入口：[[RAG 检索增强生成]]、[[RAG 与检索技术详解]]、[[Modular RAG 与 Agentic RAG]]、[[向量数据库技术]]。

## 定义

**一句话定义：** 本篇是 RAG 系统工程化的枢纽索引，沿"架构范式（Naive→Advanced→Modular→Agentic）→ 文档解析 → 分块 → Embedding 选型与微调 → 向量库与检索"这条实现链组织：已有专条者双链，尚无归口的 Modular / Agentic 范式独立成篇。

**通俗类比：** 概念篇讲"RAG 是什么、为什么更准"，本篇讲"怎么把它落地成一套工程"——从把文档喂进来、切块、嵌入、建库，到检索编排乃至升级成 Agentic。零件多有自己的专条，本页负责装配，并补上还没有专条的新范式。

## 为什么需要它

把 RAG 跑成生产系统涉及解析、分块、嵌入、向量库、编排多个环节，细节散在代码里难把握。一个工程化枢纽按落地顺序串起全链、各步指向专条，并收录尚无专条的新范式，避免在十几段实现之间迷路。

## 核心机制

按端到端链路归位，已归口者一律双链不重复承载：

```mermaid
flowchart LR
  S[文档源] --> P[解析] --> C[分块] --> E[Embedding] --> V[(向量库)] --> R[检索重排] --> G[生成]
```

- **架构范式**：Naive / Advanced / Graph 的概念与质量评估见 [[RAG 检索增强生成]]；可编排的 Modular 与自主的 Agentic 见 [[Modular RAG 与 Agentic RAG]]。
- **文档解析**：用 unstructured、mammoth、BeautifulSoup、AST 等把 PDF / Word / HTML / 代码转成结构化块，属 RAG 的 loader 环节（原理见 [[RAG 与检索技术详解]]）。
- **分块策略**：固定长度、语义、递归、按文档结构四类，及 chunk_size 与 overlap 的权衡，见 [[RAG 与检索技术详解]]。
- **嵌入与存储**：Embedding 选型 / 微调 / 对比训练见 [[Embedding 技术详解]]，向量库选型与 ANN 检索见 [[向量数据库技术]]；复杂实体关系可叠 [[知识图谱与 LLM 结合]]。

## 具体示例

落地一个企业知识库：解析 PDF / Word → 递归分块 → 选中文优化的 Embedding → 建 Milvus / Qdrant 库 → 查询走混合检索 + Cross-Encoder 重排；若出现多跳、跨源需求，再升级到 Modular 编排或 Agentic 自主检索。

## 何时用 / 何时不用

- **用**：作为"把 RAG 做成生产系统"的工程导航，按序定位每步该读的专条。
- **不用**：把它当原理教材——检索与范式机制在对应专条，本篇只给装配地图、不复述。

## 常见误区

- RAG 工程化里解析、分块、嵌入、向量库都无关紧要，关键只在提示词。
- Modular RAG、Agentic RAG 与 Naive RAG 完全等价，只是换了个叫法。
- 只要用了向量数据库，RAG 的检索质量就有保证。

## 面试速答

> 🎯 RAG 工程化按落地链组织：架构范式（Naive→Advanced→Modular→Agentic）→ 文档解析 → 分块 → Embedding → 向量库与检索。多数环节双链已有专条，尚无归口的 Modular / Agentic 范式独立成条。价值是把 RAG 从概念变成可组装的生产流水线，不复述原理、不复制原文代码。
> 🔍 追问：为什么"分块"常比"换更大模型"更影响 RAG 效果？（块切不好则检回内容碎片化或超窗，再强的生成也救不回检索）
> 🔍 追问：向量库选型主要看什么？（规模、并发、混合过滤能力与运维成本，详见向量数据库技术）
