# MLflow 与 W&B 实验跟踪


> 📌 **导航**：本篇是 MLOps「实验跟踪」支柱的工具专条；总纲见 [[MLOps实践]]，装配视角见 [[MLOps机器学习工程化]]。

## 定义

**一句话定义：** MLflow 与 Weights & Biases（W&B）是机器学习实验跟踪与模型管理的两大平台，把每次训练的参数、指标、产物、代码版本结构化登记，以支撑可复现、可比较、可协作与模型全生命周期治理。

**通俗类比：** 训练模型像做一堆化学实验——这两个平台是"实验记录本 + 样本库"，每次配方（参数）、结果（指标）、产物（模型）都登记在册，随时回看对比，不再靠记忆和散落的 notebook。

## 为什么需要它

没有实验跟踪，团队会陷入"哪个模型最好、用了什么参数、还能不能复现"的泥潭。把实验结构化登记，是 MLOps 可复现性的地基，也让超参搜索、协作评审和模型上线回滚有据可依。

## 核心机制

- **MLflow 四组件**：Tracking（记录每个 run 的参数 / 指标 / 日志 / 产物）、Projects（可复现的实验打包）、Models（跨框架统一模型格式与部署）、Model Registry（版本与 Staging / Production 阶段治理）。开源、可自托管、与生态松耦合。
- **W&B**：以 `wandb.init` 开 run、log 指标 / 图表 / 产物，强在实时可视化面板、超参搜索 sweep 与团队协作，托管服务开箱即用（也支持自托管）。
- **典型闭环**：记录参数与指标 → 跨 run 对比选优 → 注册最佳模型 → 按版本 / 阶段上线并回滚；配合 CI，在每次提交自动评估、达标才注册。

## 具体示例

调参时跑 20 组随机搜索，每组各 log 一个 run，在面板上按指标排序找最优；上线前在 Model Registry 把最佳版本标为 Production、需要时一键回滚到上一版；线上异常时，循该 run 记录的精确参数与代码版本即可复现问题。

## 何时用 / 何时不用

- **用**：任何需要复现 / 对比 / 协作的训练活动，或模型需要版本治理时。
- **不用**：一次性玩具实验——记录成本高于收益；本地跑完即弃的单文件脚本。

## 优劣与代价

✅ 可复现、可比较、可协作，打通模型生命周期治理。
⚠️ 引入平台运维与学习成本，埋点不规范会让记录质量差。
⚠️ 选用托管服务时需评估数据合规；自托管则增加运维负担。

## 与相关概念的区别

- **vs [[MLOps实践]]**：那是 MLOps 总纲做法，本篇聚焦"实验跟踪"这一支柱的两个工具。
- **vs [[构建流水线与 CI-CD 工具]]**：CI/CD 管自动构建与部署，实验跟踪管训练实验与模型版本，二者互补构成闭环。

## 常见误区

- 实验跟踪平台的主要作用是加快模型训练本身的计算速度。
- MLflow 只能配合 PyTorch 使用，不支持其它框架。
- 有了 W&B 就不需要再记录代码与数据版本。

## 面试速答

> 🎯 MLflow 与 W&B 把每次训练的参数、指标、产物、代码版本结构化登记，支撑可复现、可比较、可协作与模型版本治理。MLflow 四件套 Tracking / Projects / Models / Model Registry、开源可自托管；W&B 强在实时面板、超参 sweep 与团队协作，常与 CI 联动达标才注册上线。
> 🔍 追问：实验跟踪为什么强调"代码 + 数据版本一起记"？（只有参数指标不足以复现，需锁定代码与数据版本）
