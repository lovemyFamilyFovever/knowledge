# RESTful API 设计

> 📌 **导航**：本文是 **RESTful API 设计** 词条，属于 architecture 术语集。相关枢纽：[[API设计]]、[[微服务架构设计与实践]]、[[HTTP协议]]、[[幂等性]]、[[API 分页与版本控制]]。

## 定义

**一句话定义：** RESTful API 设计是用 **URL 表示资源、HTTP 方法表示操作、状态码表达结果** 的接口风格，核心是资源建模与语义一致性——让客户端凭方法本身就能预期副作用、幂等性与可缓存性。

**通俗类比：** 像图书馆的索书系统：书架号（URL）定位到某一本书，借书 / 还书 / 查阅（方法）说明你做什么动作，不需要额外解释。

## 为什么需要它

没有统一风格的接口会把动词塞进 URL（`/getUserList`、`/deleteOrderById`），语义散落在命名习惯里，缓存、鉴权、幂等与监控全都失去着力点。REST 把语义收敛到 HTTP 本身：网关与 CDN 能按方法判断可否缓存，客户端能安全重试幂等方法，团队评审时"这个操作该用 PUT 还是 PATCH"有了共同答案。它降低的是长期协作成本，而不是让接口"好看"。

## 核心机制

- **资源建模**：URL 用**复数名词**表示集合、ID 表示单资源（`/users/1001`）；层级表达从属（`/users/1001/orders`），一般不超过两层；不在 URL 里放动词，动作交给方法。
- **方法语义**：`GET` 安全 + 幂等 + 可缓存（查询）；`POST` 非幂等（创建）；`PUT` 幂等全量替换；`PATCH` 部分更新（默认非幂等）；`DELETE` 幂等删除；`HEAD`/`OPTIONS` 只取元信息。
- **状态码分层**：`2xx` 成功（`200`/`201` 创建并回 Location/`204` 无体）、`3xx` 重定向与缓存、`4xx` 客户端错（`400` 格式、`401` 未认证、`403` 无权限、`404` 不存在、`409` 冲突、`422` 校验失败、`429` 被限流）、`5xx` 服务端错（`500`/`502`/`503`）。别把所有失败都塞进 `200 + code:1`。
- **HATEOAS**：响应里带上相关操作链接（`self`/`orders`/`edit`），让客户端靠链接发现能力而非硬编码 URL；实践中多为部分采纳。

| 操作 | 方法 | 幂等 | 成功码 |
|---|---|---|---|
| 查列表 / 详情 | GET | 是 | 200 |
| 创建 | POST | 否 | 201 |
| 全量替换 | PUT | 是 | 200 |
| 部分更新 | PATCH | 视实现 | 200 |
| 删除 | DELETE | 是 | 204 |

## 具体示例

同一资源的一组端点，方法即语义：

```http
GET    /api/v1/users          # 列表（配分页）
POST   /api/v1/users          # 创建 → 201 + Location
GET    /api/v1/users/1001     # 详情 → 不存在则 404
PUT    /api/v1/users/1001     # 全量替换（重复调用结果相同）
PATCH  /api/v1/users/1001     # 只改 status 字段
DELETE /api/v1/users/1001     # 删除 → 204
```

错误响应统一结构（`code`、`message`、`request_id`）与状态码并用：状态码给中间件与客户端判断类别，响应体给人排查。

## 何时用与何时不用

- **用**：面向公网或跨团队的资源型接口、需要复用 HTTP 生态（缓存、代理、监控、SDK 生成）时。
- **不用**：聚合多资源的一次性查询、字段裁剪需求强烈 → [[GraphQL实践]]；内部服务间高频调用、要强类型与流式 → [[gRPC深入]]；服务端主动推送的双向通道 → [[WebSocket]]。
- **别忘**：写操作要配 [[幂等性]]（`Idempotency-Key`）与 [[API 分页与版本控制]]；对外接口先立契约，见 [[OpenAPI 规范]]。

## 优劣与代价

✅ 语义标准化，缓存、鉴权、重试、可观测性都能顺着 HTTP 语义自动生效。
✅ 团队沟通成本低，资源模型稳定后接口演进有章可循。
⚠️ 多资源组合查询易生 N+1 往返，批量操作要靠 `POST /batch` 之类约定补足。
⚠️ 过度教条（强行 HATEOAS、把一切建模成名词）会让接口比业务更难懂。

## 与相关概念的区别

- **REST vs RPC 风格**：REST 以资源和状态转移为中心；`/user/getUserInfo` 这类是 RPC 披着 HTTP 外衣。
- **REST vs [[GraphQL实践]]**：REST 多端点、服务端决定返回结构；GraphQL 单端点、客户端按需取字段。
- **PUT vs PATCH**：PUT 是整体替换（省略字段等于清空），PATCH 只改提交的字段。
- **安全 vs 幂等**：安全指不改状态（只有 GET 满足）；幂等指重复执行效果相同（DELETE 幂等但不安全）。

## 常见误区

- 把业务错误码塞进 HTTP 200，用响应体的 code 表达失败就够了。
- 一个操作只要天然幂等，就不需要再设计任何防重放机制。
- REST 就必须完整实现 HATEOAS，否则不算 RESTful。

## 面试速答

> 🎯 RESTful 以 URL 表资源、HTTP 方法表操作、状态码表结果；GET 安全幂等可缓存、POST 非幂等、PUT 全量、PATCH 部分，安全与幂等要分清；URL 不放动词、错误别统一塞 200，聚合查询该考虑 GraphQL。
