# 分布式系统设计完全指南


> 📌 **导航**：本文是 **分布式系统设计完全指南** 词条，属于 architecture 术语集。相关枢纽：[[SaaS产品技术架构]]、[[事件驱动架构]]、[[云原生与多云架构实战指南]]、[[分布式系统设计完全指南]]、[[微服务架构]]。

## 定义

**一句话定义：** 分布式系统设计是在网络会分区、节点会宕机、时钟会漂移的前提下，先用 CAP/PACELC 定取舍，再用共识协议定序、用一致性模型定可见性、用分布式事务定跨节点原子性，从而达成业务可接受正确性的工程方法。

**通俗类比：** 像让几家分店对同一笔账达成一致：电话线随时会断（分区），断线时得先决定"是继续接单还是停手等总部"（A 还是 C）；平时还要决定"为等一次确认多花两秒值不值"（延迟还是一致）。

## 为什么需要它

单机代码里三条隐式假设——读写有确定先后、能读到刚写的值、事务由一个协调者兜底——在多机环境下全部失效。网络不丢包但不保序，时钟会回拨，进程能在两行日志之间被 kill，于是"看起来对"的实现会在规模上来时以极难复现的方式兑现：重复扣款、库存超卖、选举双主。这一层的价值是把失效模式收敛成几条定理与少数标准构造，让工程师按瓶颈挑工具，而不是每次重新发明。

## 核心机制

三层各自独立又互相咬合：取舍层决定分区时保哪一头，协议层决定谁来定序，可见性层决定读者能看到什么，原子层决定一组操作能否整体生效。

```mermaid
flowchart LR
    A[取舍 CAP/PACELC] --> B[协议 共识与复制]
    B --> C[可见性 一致性模型]
    C --> D[原子性 分布式事务]
```

1. **取舍层：CAP 与 PACELC**：分区不是异常而是常态，[[CAP 定理]] 因此把选择压成 C 与 A 二选一。PACELC 不是另一条定理，而是给 CAP 补上时间维——没有分区时系统仍在拿延迟换一致性，这条决定了跨地域部署的默认姿势；选了 AP 之后那套"最终一致加补偿"的工程语言见 [[BASE 理论]]。
2. **协议层：共识与定序**：Paxos、Raft、ZAB 是同一问题的三种写法（prepare 与 promise、accept；leader 选举加日志复制；epoch 加 zxid 的原子广播），共同底座都是多数派。引入共识不是为了快，而是"先能定序才谈得上强一致"，算法与 FLP 边界见 [[一致性算法]]，副本布局与 R/W/N 见 [[数据复制与 Quorum]]。
3. **可见性层：一致性模型是一条谱系**：从线性一致、因果一致、读己之写一直到最终一致是梯度而非开关。谱系两端的机制分别归口 [[一致性算法]]（多数派读主）与 [[最终一致性]]（异步复制、读修复与反熵、LWW 与向量时钟）；因果、单调读、会话这些客户端变体不改复制协议，只在会话内多要一层保证。
4. **原子性层：跨节点事务**：分野在谁兜底原子性——2PC 与 3PC 把参与者锁到协调者决策完成，代价是协调者单点与 prepare 之后的阻塞（[[分布式事务]]）；TCC 与 Saga 把原子性降级为逐步提交加补偿，代价是隔离性消失，必须靠 [[幂等性]] 与 [[分布式锁]] 补齐（[[Saga 与 TCC]]）。

## 具体示例

原稿三个案例正好是 PACELC 的象限取样：ZooKeeper 用 ZAB 取 PC/EC，分区时宁可拒写也要守强一致；Cassandra 取 PA/EL，用最终一致与可调一致性换低延迟；CockroachDB 用 Multi-Raft 同样标 PC/EC，靠把副本收在少数区域、压缩网络往返来抵掉一致性带来的延迟。工程上更常见的是同一业务分档：订单主档走强一致，浏览计数走最终一致，跨库扣款用 [[Saga 与 TCC]] 的补偿链而不是硬扛 2PC。

## 何时用与何时不用

- **用**：数据必须多副本才扛得住读压或多可用区、单库放不住要分片（[[数据分片与热点处理]]）、业务跨地域部署（[[异地多活]]）、或一个用户动作会落到多个存储上。
- **不用**：一主一从加缓存就够用时，引入共识与分布式事务只会放大故障面；能靠 [[幂等性]] 消重的写、能靠 [[缓存双写一致性]] 收敛的读，不必先上 2PC。

## 优劣与代价

✅ 按"取舍—协议—可见性—原子性"分层后，需求变更通常只落在某一层，不必整体重构。
✅ 定理与标准构造可复用，容量规划与故障演练有可讨论的口径，而不是凭手感。
⚠️ 每层都要付代价：共识压延迟、异步复制留可见性窗口、补偿型事务丢隔离。
⚠️ 没有银弹——同一条链路常需两种模型并存（主档强一致加计数最终一致），复杂度全堆在边界上。

## 与相关概念的区别

- **vs [[系统设计]]**：那页从"读不动 / 放不下 / 分不均 / 扛不住"四种瓶颈倒推构件，本页只专讲多机正确性这一条主线（共识、复制、事务）。
- **vs [[高并发系统设计]]**：高并发关心吞吐与响应时间，本页关心"多台机器上什么叫正确"，同一系统两者并存但目标不同。
- **vs [[微服务架构]]**：微服务划的是业务与部署边界，跨服务调用的数据一致性正好落在本页 4) 的问题域。

## 常见误区

- 把 CAP 念成"三个里永远选两个"，忽略 P 不可放弃、真实系统只在 C 与 A 之间选。
- 以为跑了 Raft 或 ZAB 就自动线性一致，忽略客户端读旧主与会话内乱序的路径。
- 上了 2PC 就宣称"分布式事务与单机等价"，忽略协调者故障后参与者长期阻塞与悬挂。
