# 异步处理与线程池

> 📌 **导航**：本文是 **异步处理与线程池** 词条，属于 architecture 术语集。相关枢纽：[[性能优化]]、[[数据库连接池]]、[[消息队列（Message Queue）]]、[[并发编程模式与实践]]。

## 定义

**一句话定义：** 异步处理是把耗时步骤从主流程摘出、让请求线程立即返回并用回调/队列/轮询取结果的开发方式；线程池是承载这些任务的**受控资源池**——预先创建有限数量的线程反复复用，避免频繁创建销毁，并把并发度约束在系统能承受的范围之内。

**通俗类比：** 餐厅点餐后拿号等叫，不用在窗口干站着（异步）；后厨固定几个灶位，来单排队进灶而不是每单临时雇一个厨师（线程池）。

## 为什么需要它

同步阻塞时，线程的生命周期被 IO 占据：等一次下游 RPC、写一次数据库、生成一张图片，一个请求线程就在原地挂着，吞吐被线程数而不是 CPU 卡住。异步把"等待"与"执行"解耦，让请求尽早返回、后台慢慢完成。但异步一旦放开并发就会反噬——瞬时几千个任务能瞬间压垮下游，所以需要线程池作为**限流与复用的载体**：固定 worker 数、有界队列、明确的拒绝策略，让并发度成为一个可调、可见、可兜底的参数。

## 核心机制

- **任务分类决定池大小**：CPU 密集型取 ≈ 核数 + 1（再多只会增加切换）；IO 密集型可远大于核数，因为线程多数时间在等；混合负载应**拆成多个池**，避免慢任务霸占快任务的位置。
- **队列是有界的缓冲**：无界队列等于把内存当成背压，堆积到 OOM；有界队列配合拒绝策略才是可控过载信号。
- **拒绝策略是产品决策**：快速失败（抛异常，交给上层重试或直接降级）、调用者运行（由提交线程自己执行，天然回压）、丢弃、丢弃最旧——选哪种取决于业务能否容忍丢失。
- **异步的落地形态**：进程内是回调 / Future / 协程；跨进程要经 [[消息队列（Message Queue）]] 投递，并配 [[幂等性]] 与死信处理，否则一次重复消费就是业务事故。
- **上下文与失败传播**：线程池会丢失调用线程的 ThreadLocal（trace id、事务、安全上下文），必须显式传递；子任务异常不会自动冒到主线程，需靠 Future 聚合或统一异常处理。

| 参数 | 作用 | 配错的后果 |
|---|---|---|
| 核心 / 最大线程数 | 常驻与峰值并发 | 过大频繁切换、过小吞吐受限 |
| 队列容量 | 突发缓冲 | 无界堆积至 OOM |
| 空闲存活时间 | 非核心线程回收 | 过短反复创建、过长占资源 |
| 拒绝策略 | 过载行为 | 静默丢任务、雪崩无信号 |

## 具体示例

```java
new ThreadPoolExecutor(
    5, 10, 60L, TimeUnit.SECONDS,               // 常驻 5、峰值 10
    new LinkedBlockingQueue<>(100),              // 有界：100 个排队任务
    new ThreadPoolExecutor.CallerRunsPolicy());  // 队满则由提交线程自己跑，形成回压
```

关键不是这五行参数，而是**每一项都对应一个明确的容量假设**：队列 100 是按下游能扛的排队时长算出来的，CallerRuns 是刻意让入口变慢来保护自己。

## 何时用与何时不用

- **用**：发送通知、生成缩略图、写审计日志、批量导入等"用户不必等结果"的工作；下游慢而请求线程珍贵的接口层；需要给突发流量做缓冲的场景。
- **不用**：结果必须立刻返回的强一致读路径（异步只会增加不确定性与补偿成本）；任务本身极轻量时，切线程与上下文传递的开销反而超过收益；纯 CPU 饱和的批处理，加线程不会更快。
- **别忘**：异步链路上的重试与去重、失败可见性（监控队列长度与拒绝次数）必须在上线前就位。

## 优劣与代价

✅ 请求线程不被 IO 占住，同等硬件下吞吐与响应时间显著改善。
✅ 线程复用消除创建销毁开销，池化让并发度可配置、可观测。
⚠️ 控制流被打散，调试、事务边界与错误传播都变难，上下文需手工接力。
⚠️ 池参数是"猜出来的"时极易形成隐性瓶颈；线程池共享还会让慢任务拖垮快任务。

## 与相关概念的区别

- **异步 vs 并发**：异步描述"不等待结果"的调用方式，并发描述"同时在处理多件事"的程度，二者可独立存在。
- **线程池 vs [[数据库连接池]]**：一个管 CPU 执行资源，一个管昂贵的 IO 连接；两者的容量必须一起核算，否则线程多连接少会全堵在取连接上。
- **线程池 vs 协程/虚拟线程**：后者把阻塞成本降到极低的挂起-恢复，用轻量任务数换掉"靠大池扛 IO"的必要性。
- **进程内异步 vs 消息队列**：前者不跨进程、任务随进程消失；后者提供持久化与跨服务解耦。

## 常见误区

- 线程池的线程数设得越大，系统吞吐就越高。
- 只要用了异步，接口响应时间和吞吐量就必然改善。
- 无界队列能保证任务永不丢失，是最安全的配置。

## 面试速答

> 🎯 异步把耗时步骤摘出主流程让请求尽早返回、结果靠回调或队列取；线程池用固定 worker + 有界队列 + 明确拒绝策略把并发度变成可调参数，CPU 密集取核数+1、IO 密集可更大，慢任务要拆独立池避免互拖。
