# 架构模式


> 📌 **导航**：本文是 **架构模式** 词条，属于 architecture 术语集。相关枢纽：[[SaaS产品技术架构]]、[[事件驱动架构]]、[[云原生与多云架构实战指南]]、[[分布式系统设计完全指南]]、[[微服务架构]]。

## 1. 单体架构（Monolithic Architecture）

**一句话定义：** 所有功能模块打包在一个应用中部署和运行。

**通俗类比：** 就像一个大杂货铺，所有商品都放在一个店里，一个人管理所有事情。

**具体示例：**
```
+-------------------------------------------+
|              单体应用                        |
|  +--------+ +--------+ +--------+         |
|  | 用户模块 | | 订单模块 | | 支付模块 |         |
|  +--------+ +--------+ +--------+         |
|  +--------+ +--------+                    |
|  | 库存模块 | | 通知模块 |                    |
|  +--------+ +--------+                    |
+-------------------------------------------+
|              共享数据库                      |
+-------------------------------------------+
```

**为什么需要它：** 开发初期简单快速，部署方便，适合小型项目和快速原型验证。

**与微服务对比：** 单体架构所有模块耦合在一起，微服务将每个模块拆分为独立服务，各自部署扩展。

---

## 2. 微服务架构（Microservices Architecture）

**一句话定义：** 将系统拆分为多个小型独立服务，每个服务独立开发、部署和扩展。

**通俗类比：** 像一个商业综合体，每家店独立经营，有自己的收银、库存和运营系统。

**具体示例：**
```
+----------+    +----------+    +----------+
| 用户服务  |    | 订单服务  |    | 支付服务  |
| (Java)   |    | (Go)     |    | (Python) |
+----+-----+    +----+-----+    +----+-----+
     |               |               |
     +-------+-------+-------+-------+
             |               |
      +------+-----+ +------+-----+
      | 用户数据库  | | 订单数据库  |
      +------------+ +------------+
```

**为什么需要它：** 解决单体架构扩展困难、部署风险高、技术栈单一的问题。

**与单体对比：** 微服务可独立扩展和部署，但增加了运维复杂度和网络通信开销。

---

## 3. Serverless（无服务器）

**一句话定义：** 开发者只写业务逻辑，无需管理服务器，由云平台自动扩缩容。

**通俗类比：** 像用电一样，你不需要自己建发电厂，按需用电、按量付费。

**具体示例：**
```javascript
// AWS Lambda 示例
exports.handler = async (event) => {
    const response = {
        statusCode: 200,
        body: JSON.stringify({ message: 'Hello from Serverless!' })
    };
    return response;
};
```

**为什么需要它：** 降低运维成本，按实际使用量计费，自动应对流量波动。

**与微服务对比：** 微服务仍需管理容器/服务器，Serverless完全托管，但有冷启动和执行时间限制。

---

## 4. 事件驱动架构（EDA）

**一句话定义：** 组件通过产生和响应事件进行通信，实现松耦合的异步协作。

**通俗类比：** 像广播电台，发射台发信号，收音机收听，彼此不知道对方存在。

**具体示例：**
```
[订单服务] --发布"订单创建"事件--> [消息队列] --订阅--> [库存服务]
                                                 --> [通知服务]
                                                 --> [积分服务]
```

**为什么需要它：** 实现服务间解耦，提高系统可扩展性和容错能力。

**与同步调用对比：** 同步调用是请求-响应模式，EDA是异步事件通知模式，延迟更低但调试更难。

---

## 5. CQRS（命令查询职责分离）

**一句话定义：** 将数据的写操作（Command）和读操作（Query）分离到不同模型中。

**通俗类比：** 像银行柜台，办业务和查余额在不同窗口，各自优化效率。

**具体示例：**
```
[写模型] --> Command --> 数据库（写优化）
                              |
[读模型] <-- Query <-- 数据库（读优化/缓存）
```

**为什么需要它：** 读写比例差异大时，可分别优化读写性能，避免相互影响。

**与传统CRUD对比：** 传统模式读写共用同一模型，CQRS允许读写独立扩展和优化。

---

## 6. 六边形架构（端口与适配器）

**一句话定义：** 核心业务逻辑在中心，通过端口和适配器与外部世界交互。

**通俗类比：** 像一个插座，核心设备不变，通过不同插头适配不同电器。

**具体示例：**
```
        [外部系统]
            |
    +-------+-------+
    |   适配器层     |
    +-------+-------+
            |
    +-------+-------+
    |    端口接口    |
    +-------+-------+
            |
    +-------+-------+
    |   核心业务逻辑  |
    +-------+-------+
```

**为什么需要它：** 使核心业务与外部依赖解耦，便于测试和更换技术实现。

**与传统三层对比：** 传统架构业务层直接依赖数据层，六边形架构通过端口反转依赖方向。

---

## 7. 洋葱架构（Onion Architecture）

**一句话定义：** 以领域模型为核心，外层依赖内层，形成层层包裹的同心圆结构。

**通俗类比：** 像洋葱一样，核心是Domain，外层是Infrastructure，依赖方向由外向内。

**具体示例：**
```
[基础设施层] --> [应用服务层] --> [领域层] <-- [领域层]
                                  ^
                                  |
                              [核心领域]
```

**为什么需要它：** 确保核心业务逻辑不依赖外部细节，提高可测试性和可维护性。

**与六边形对比：** 理念相似，洋葱架构强调层间依赖严格由外向内，六边形强调端口-适配器模式。

---

## 8. Space-Based Architecture（基于空间的架构）

**一句话定义：** 数据驻留在内存网格中，通过处理单元并行处理，支持高并发读写。

**通俗类比：** 像一个大型仓库，货物放在货架上，多个工人同时取货，不需要排队。

**具体示例：**
```
[负载均衡] --> [处理单元1] --+
            --> [处理单元2] --+-- [内存数据网格]
            --> [处理单元3] --+    (数据同步复制)
```

**为什么需要它：** 解决传统数据库在高并发下的性能瓶颈，适合实时交易系统。

**与传统数据库对比：** 传统数据库磁盘IO是瓶颈，Space-Based将数据放内存，支持极高吞吐量。

---

## 9. 管道架构（Pipeline Architecture）

**一句话定义：** 数据流经一系列处理步骤，每个步骤完成特定转换或操作。

**通俗类比：** 像工厂流水线，原材料经过一道道工序，最终变成产品。

**具体示例：**
```
[输入数据] --> [验证] --> [清洗] --> [转换] --> [存储] --> [输出]
```

**为什么需要它：** 将复杂处理分解为简单步骤，便于理解、测试和维护。

**与事件驱动对比：** 管道是线性顺序处理，事件驱动是异步松耦合的多路分发。

---

## 10. 微前端架构（Micro Frontends）

**一句话定义：** 将前端应用拆分为多个独立开发、部署的微型前端模块。

**通俗类比：** 像一个网页由多个团队负责不同区块，各自独立更新不影响整体。

**具体示例：**
```
[主应用壳]
  +-- [Header微应用] (React)
  +-- [商品列表微应用] (Vue)
  +-- [购物车微应用] (Angular)
  +-- [Footer微应用] (原生JS)
```

**为什么需要它：** 解决大型前端项目协作困难、技术栈锁定、部署耦合的问题。

**与微服务对比：** 微服务拆分后端，微前端拆分前端，解决同一层级的大型应用问题。
