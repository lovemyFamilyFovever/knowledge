# 高并发系统设计


> 📌 **导航**：本文是 **高并发系统设计** 词条，属于 architecture 术语集。相关枢纽：[[SaaS产品技术架构]]、[[事件驱动架构]]、[[云原生与多云架构实战指南]]、[[分布式系统设计完全指南]]、[[微服务架构]]。

## 定义

**一句话定义：** 高并发系统设计是在有限资源下通过限流、降级、水平扩展与多级缓存保障系统在峰值流量下可用和响应可控的工程方法。

**通俗类比：** 像高速公路收费站——车道不够就扩建（水平扩展），车流太大就限流放行（令牌桶），某条道坏了就关闭引导走其他道（降级）。

## 为什么需要它

互联网业务流量具有突发性（秒杀、热搜、推送），容量规划按均值设计必然在峰值时崩溃。高并发设计的核心不是"接住所有请求"，而是在过载时保护核心链路、让非关键功能优雅降级。

## 核心机制

**限流**：在入口控制通过速率——固定窗口（简单但有边界突刺）、滑动窗口（平滑）、令牌桶（允许突发，匀速放入令牌取走才放行）、漏桶（严格匀速流出）。

**降级**：依赖超时或错误率超阈值时返回缓存/默认值/友好提示，释放资源给核心链路。

**热点处理**：热门 Key 集中打同一分片 → 本地缓存 + 分布式缓存多级拦截；热点 Key 拆分（将 count 拆为 count_1..count_N 分散写入）；请求合并（短时间内相同查询只穿透一次）。

**无状态化**：任何实例可处理任何请求——Session 外置 Redis、配置中心化、文件走对象存储。有状态是水平扩展的最大敌人。

## 具体示例

秒杀系统：页面静态化+CDN → 入口令牌桶限流（放行不超库存 1.2 倍）→ Redis 预扣库存（原子操作）→ 异步 MQ 下单 → DB 最终落库。库存扣完立即降级为"已售罄"页。

## 何时用与何时不用

- **用**：QPS 峰值超单机极限、需要 SLA 保障的核心链路、有秒杀/抢购等突发流量场景。
- **不用**：日活千级内部系统（过度设计）、瓶颈明确在 CPU/IO 而非并发连接时（先优化单机）。

## 优劣与代价

✅ 限流+降级保障核心链路不被拖垮。
✅ 多级缓存将热数据延迟压到亚毫秒。
⚠️ 最终一致性：异步化后库存/订单存在短暂不一致窗口。
⚠️ 运维成本：需配套监控、压测和故障演练验证限流/降级阈值有效。

## 与相关概念的区别

- **vs 高可用**：高并发关注"吞吐量扛不扛得住"，高可用关注"服务挂不挂"；高并发是大流量场景的前提，高可用是故障场景的前提。
- **vs 性能优化**：性能优化降低单次请求耗时，高并发设计控制同时进入系统的请求数量。前者让路跑快，后者让车流量可控。

## 常见误区

- 水平加机器一定能解决高并发问题。
- 限流阈值设好之后就不用再调整了。
- 用 Redis 做缓存就能保证数据一致性。

## 面试速答

> 🎯 高并发三板斧：限流（令牌桶/漏桶控入口）、降级（弃非核心保核心）、扩容（无状态+水平扩展）；热点场景叠加多级缓存+异步削峰（MQ）。
