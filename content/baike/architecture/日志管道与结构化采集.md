# 日志管道与结构化采集

> 📌 **导航**：本文是 **日志管道与结构化采集** 词条，属于 architecture 术语集。相关枢纽：[[可观测性工程实战]]、[[监控与日志详解]]、[[微服务架构设计与实践]]、[[Kubernetes云原生实战指南]]、[[ElasticSearch搜索]]。

## 定义

**一句话定义：** 日志管道是把散落在各节点与容器标准输出里的日志，经**采集 → 解析富化 → 索引存储 → 查询**四步变成可检索资产；结构化采集要求应用直接输出字段化 JSON（带 trace_id、服务名、耗时、业务主键），让"捞出一次请求的全部现场"退化成一次标签过滤，而不是全文扫描。

**通俗类比：** 像把每通客服电话从口头记录改成带工单号的表单：工单号一致就能串起同一客户的所有通话，客服表达好不好不影响归档与检索。

## 为什么需要它

一次请求的日志会散在十几个实例的本地文件里，而排障的人不在那台机器上。不做结构化时，排障等于对着正则与时间戳做全文搜索；日志量随流量线性增长，全文索引成本也线性增长。字段化之后，级别、服务、trace_id 都成为可过滤维度，采样降噪才有抓手，日志也才可能与指标、链路互认（三支柱装配见 [[可观测性工程实战]]）。

## 核心机制

- **采集**：agent 尾读文件或容器 stdout，容器环境按节点以 DaemonSet 部署；用位点文件记录读取偏移以便重启续传，并处理日志轮转造成的重复与丢行。
- **解析与富化**：非结构行用 grok 拆成 timestamp / level / thread / logger / message，date 校正时间字段，mutate 删冗余原字段，再按 level 打标；K8s 侧把 namespace / pod / container / node 经 relabel 变成日志标签——**缺这层元数据就无法定位到具体实例**。
- **索引与存储**：全文倒排（ELK / EFK，任意字段可查但贵）与只索引标签、正文靠扫（Loki + Promtail + Grafana，便宜但依赖标签质量）两种成本模型；EFK 只是把 Logstash 换成更轻、原生认 K8s 元数据的 Fluentd。
- **字段与级别**：一条可查的日志至少要有 timestamp、level、service、trace_id、span_id、业务主键、duration_ms、status；级别按环境收口（production WARNING、staging INFO、development DEBUG），语义边界要分清——FATAL 系统跑不下去（连接池完全耗尽）、ERROR 操作失败但服务仍在、WARN 潜在问题、INFO 关键业务事件、DEBUG 参数与 SQL、TRACE 逐步流程。
- **采样与降噪**：ERROR 始终全采；剔除 timestamp / trace_id / span_id 后取模板哈希，同一模式在统计窗口（示例 60s）内重复超阈值即降采样，其余按基础率采样。

## 具体示例

结构化与否，差别就在字段上：

```text
不可查：2023-10-01 12:30:45 ERROR 支付失败 java.lang.RuntimeException ...
可查  ：level=ERROR service=order-service trace_id=abc123 error_type=PaymentTimeout
        order_id=ORD-2023-001 duration_ms=1250 stack=<异常栈字段>
```

拿到 trace_id 再去调用树看慢在哪一跳（[[分布式链路追踪]]），同 trace_id 可一次捞全该请求跨实例的日志。

## 何时用与何时不用

- **用**：多实例、容器化的生产服务一律集中日志 + 字段化 + trace_id；有合规需求时另加留痕与保留期。
- **不用**：单机小服务先保好本地文件与轮转，不必自建整套 ELK；只要计数与趋势时应走指标（[[Prometheus 指标与告警]]），用日志做聚合是拿最贵的存储干最便宜的事。
- **别忘**：脱敏要在写日志之前而不是采集之后；grok 规则与日志格式强耦合，改格式要回补规则且历史数据无法重解析。

## 优劣与代价

✅ 字段化 + 标签索引让查询成本随过滤维度而非正文体积增长。
✅ 错误全采 + 重复模式降采样，在保真与容量之间取得可解释的平衡。
⚠️ 全文倒排很贵，日志量与流量线性相关，噪声按同比例放大存储成本。
⚠️ 管道本身是故障源：agent 静默丢日志不易察觉，要监控采集延迟与丢弃率。

## 与相关概念的区别

- **日志 vs 指标**：逐条事件 vs 聚合数字，前者查细节后者看趋势（口径见 [[监控与日志详解]]）。
- **日志 vs 链路**：日志给一跳内部的细节，链路给跳与跳之间的关系，靠 trace_id 互转（[[分布式链路追踪]]）。
- **采集 agent vs 处理管道**：Promtail / Beat 类只采集打标，Logstash / Fluentd 承担转换富化；换后端时工作量主要落在处理层。
- **排障日志 vs 审计日志**：审计要不可篡改与固定保留期，排障要上下文完整与检索速度。

## 常见误区

- 日志只要全量存进 ES 就总有用得上的一天，成本问题以后再说。
- 把异常栈和上下文拼进 message 文本里，就算结构化日志了。
- 生产环境排查问题时把级别开到 DEBUG，是更快定位的正确做法。

## 面试速答

> 🎯 日志管道 = 采集（位点续传）→ 解析富化（grok / relabel 补 K8s 元数据）→ 索引（全文倒排贵、只索引标签便宜）→ 查询；应用侧输出字段化 JSON 并带 trace_id，降噪靠错误全采加重复模式窗口内降采样。
