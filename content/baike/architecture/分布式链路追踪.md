# 分布式链路追踪

> 📌 **导航**：本文是 **分布式链路追踪** 词条，属于 architecture 术语集。相关枢纽：[[可观测性工程实战]]、[[微服务架构设计与实践]]、[[监控与日志详解]]、[[API网关]]、[[事件驱动架构]]。

## 定义

**一句话定义：** 链路追踪用 **trace（一次请求的完整调用树）与 span（带父子关系的工作单元）** 记录请求穿过哪些服务、每段耗时多少、在哪一跳失败，把跨进程之后的全局黑盒还原成一张带时间轴的因果图。

**通俗类比：** 像快递全程签收记录：每个中转站扫一次码（span），串起来就是这单的完整路由；只统计各站点吞吐（指标）看不出这一单为什么慢。

## 为什么需要它

单体内的慢会被日志直接暴露；跨进程后"每跳都快、端到端很慢"与"某一跳偶发 2 秒"在指标上几乎同形，都表现为 P99 抖动。链路把耗时归因到具体一跳与具体依赖，给出的是证据而非猜测——这也是入口组件要统一开 trace 的原因（见 [[API网关]]、[[微服务治理术语百科]]）。

## 核心机制

- **数据模型**：一个 trace 由若干 span 组成，每个 span 带 trace_id、span_id、parent_span_id、起止时间、attributes、status 与异常记录；父子关系决定能否拼成树。
- **上下文传播（最易错）**：进程内靠 current context；跨进程要在客户端 `inject` 把 traceparent 写进请求头、服务端 `extract` 后 attach 为当前上下文。三个高频丢失点是**线程池与异步提交、消息队列、缺拦截器的自建 HTTP 客户端**（分别见 [[异步处理与线程池]] 与 [[消息队列（Message Queue）]]）。跨语言跨云统一用 W3C Trace Context，免格式互不认账。
- **采样**：头采样在入口按比率决定采不采（示例 TraceIdRatioBased 取 10%），便宜可预算，但可能恰丢掉稀有错误；尾采样先缓冲再按条件（错误、慢于阈值）保留，保真度高但要求 Collector / agent 有缓冲余量（见 [[可观测性工程实战]]）。
- **埋点方式**：自动插桩覆盖 HTTP 框架、HTTP 客户端与数据库驱动，负责"结构"；业务属性（订单号、租户、批量大小）与错误状态要手动 set_attribute / record_exception，负责"语义"。
- **与日志、指标缝合**：把 trace_id、span_id 写进日志字段（见 [[日志管道与结构化采集]]），才能从慢 span 一键跳到该实例该时刻的日志。

| 系统 | 社区背景 | 存储 | 探针 | 采样 | 侧重 |
|---|---|---|---|---|---|
| Jaeger | CNCF 毕业项目 | ES / Cassandra / Kafka | SDK + Java Agent 无侵入 | 动态采样 | 链路分析 |
| SkyWalking | Apache 顶级项目 | ES / MySQL / TiDB / H2 | Java Agent 无侵入 | 动态采样 | 拓扑与指标一体 |
| Zipkin | Twitter 开源 | ES / Cassandra / MySQL | SDK | 固定采样 | 轻量 |

## 具体示例

```text
trace abc123 total=1620ms
   └ order-service.create 1600ms ├ payment.charge 30ms status=OK
                                  └ db.save_order 1560ms（lock_wait=1520, rows=1）
```

一次告警下钻到的调用树长这样：慢跳、依赖与原因属性一目了然。没有这棵树，现象会被写成"P99 升高，建议扩容"；有了树，动作变成去查那条 SQL 的锁竞争（见 [[索引与查询优化术语]]）。

## 何时用与何时不用

- **用**：跨进程调用链超过两跳的系统，以及"端到端延迟"这个 SLI 的归因来源。
- **不用/慎用**：单体小服务全量追踪收益有限；无缓冲地开尾采样会把内存打满；高基数业务字段塞进 span attributes 等于把成本问题搬进链路库。
- **别忘**：错误与慢请求应提高采样保留率，否则最需要的现场恰好最容易被采掉。

## 优劣与代价

✅ 把"慢在哪一跳、依赖是谁"从争论变成看图说话，也是跨团队排障的公共语言。
✅ 与日志、指标共享 trace_id 后，三支柱才连成一条下钻路径。
⚠️ 有侵入性与维护成本：新框架、新中间件都要确认传播是否真的生效。
⚠️ 数据量按请求数增长，采样是必需品，而采样过头会让"偶发一次的问题"系统性不可见。

## 与相关概念的区别

- **链路 vs 指标**：指标看总体趋势并触发告警，链路还原单个请求的路径（见 [[Prometheus 指标与告警]]）。
- **链路 vs 日志**：日志给一跳内部的细节，链路给跳与跳之间的关系，二者靠 trace_id 互转。
- **链路 vs APM**：APM 还含代码级剖析与服务拓扑，链路追踪是其中"跨服务因果路径"这一块（口径见 [[监控与日志详解]]）。
- **无侵入 Agent vs SDK**：Agent 不改代码但受运行时限制，SDK 要改代码却能补业务语义，两者常并存。

## 常见误区

- 采样率越高越好，链路数据当然是全留最保险。
- 接了自动插桩库，就等于完成了全链路追踪。
- 有了链路追踪，业务日志就可以少打甚至不打。

## 面试速答

> 🎯 链路 = trace（调用树）+ span（父子工作单元）；难点是跨进程上下文传播（线程池、MQ、自建 HTTP 客户端最易断链），代价是数据量，靠头采样或尾采样控制，并把 trace_id 打进日志才形成三支柱下钻闭环。
