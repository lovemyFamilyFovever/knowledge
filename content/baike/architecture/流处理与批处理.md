# 流处理与批处理

> 📌 **导航**：本文是 **流处理与批处理** 词条，属于 architecture 术语集。相关枢纽：[[数据工程完全指南]]、[[大数据技术栈]]、[[MapReduce]]、[[Kafka深入]]。

## 定义

**一句话定义：** 批处理是"攒够一批数据再一次算完"（高吞吐、T+1 延迟），流处理是"数据到了就逐条算"（低延迟、常驻作业）；二者的分野不在用的工具，而在处理的时间粒度与"延迟-吞吐-复杂度"三角，现代引擎正把两者收敛成一套 API 的流批一体。

**通俗类比：** 批处理像班车——凑满一车或到点才发，单位成本低但要等；流处理像出租车——来一单走一单，随到随走但每单更贵、调度更复杂。

## 为什么需要它

业务问题要么在乎"最新"、要么在乎"全量准确"。风控、实时看板、异常告警要秒级反应，批处理来不及；离线画像、月度报表、模型训练要扫全量历史，逐条流算既贵又难保证一致。批处理以吞吐和简单换延迟，流处理以复杂度和成本换实时性——选错范式会同时丢掉这两样里的重要一头，所以要按"这份结果晚多久就不能用"来定范式。

## 核心机制

- **批处理的机制**：作业有始有终，输入是有界数据集，引擎把数据切成分区并行跑，中间结果可落盘重算，天然幂等、易回溯、好调试。代表是 [[MapReduce]] 与 Spark（内存 + DAG，见 [[大数据技术栈]]），交互式查询层再叠 Presto/Trino 这类 MPP 引擎做联邦查询与近似计算。
- **流处理的三块硬骨头**：输入无界，于是必须回答——时间怎么算（事件时间 vs 处理时间）、乱序怎么办（用 watermark 水位线判定"某时间点之前的数据应到未到"）、失败怎么不重不丢（精确一次语义，落地机制见 [[消息投递语义]]）。这三块是批处理里根本不存在的问题。
- **窗口与状态**：流上把无限流按时间或条数切成窗口（滚动/滑动/会话）再聚合；跨窗口的中间结果存在状态后端里，状态一旦超过单机内存就要靠增量 checkpoint。这正是流作业比批作业难运维的根源（常驻与容错的通用机制见 [[事件驱动架构]]）。
- **选型口径**：复杂事件处理、严格精确一次、事件时间与乱序处理重的场景偏 Flink；微服务里嵌入式、和 Kafka 绑得紧的轻量转换偏 Kafka Streams（本体见 [[Kafka深入]]）；已经全栈用 Spark、要批流统一 API 与 SQL 分析的场景偏 Structured Streaming。

| 维度 | 批处理 | 流处理 |
|---|---|---|
| 输入 | 有界数据集 | 无界数据流 |
| 延迟 | 分钟~小时（T+1） | 毫秒~秒 |
| 吞吐 | 高、擅扫全量 | 受单条路径限制 |
| 复杂度 | 低、幂等好回溯 | 高（时间/乱序/状态） |
| 代表引擎 | MapReduce、Spark、Hive | Flink、Kafka Streams、Structured Streaming |

## 具体示例

电商大促的实时 GMV 看板：订单事件先进 Kafka 缓冲，Flink 按"下单"事件时间开 5 分钟滚动窗口聚合，用 watermark 容忍乱序与迟到数据，结果写回缓存供前端刷新；同一批订单到夜里再由 Spark 批作业扫全量、跑精确的财务对账与用户画像——看板要"快但允许后续修正"，对账要"慢但必须一次算准"，两条链路各用一种范式。

## 何时用与何时不用

- **用批**：结果可延迟到分钟/小时、要扫全量历史、需要可重放与精确一致（离线报表、特征回填、批量清洗见 [[数据清洗实战]]）。
- **用流**：结果晚几秒就失去价值（实时风控、监控告警、在线特征、大屏）。
- **别误用**：拿批 ETL 硬做实时（延迟吃不掉，参见 [[ETL]]），或给一个每天只跑一次的报表上常驻流作业（白付运维与状态成本）。

## 优劣与代价

✅ 批：吞吐高、语义简单、失败重跑即可、结果稳定可审计。
✅ 流：端到端秒级、支撑实时决策与在线特征。
⚠️ 批：延迟是天花板，做不了真正的实时。
⚠️ 流：时间与状态复杂、资源常驻、排障与回溯比难得多。
⚠️ 两套范式并存时，同一指标的批流口径易漂移——这正是"流批一体"要解决的痛点。

## 与相关概念的区别

- **vs [[ETL]]**：ETL 是"数据怎么搬进仓"的集成范式，批/流是"计算按什么时间粒度跑"，二者正交（有流式 ETL，也有批式 ETL）。
- **vs [[大数据技术栈]]**：那篇讲整套分层选型，本篇专讲其中"计算"一层的批与流两种范式及其取舍。
- **vs [[MapReduce]]**：MapReduce 是批处理的一种（磁盘为主的计算模型），Spark 与流处理是它的演进与另一极。

## 常见误区

- 流处理就是"更快的批处理"，把批作业调小批次间隔就能等价实现。
- 只要上了 Flink，天然就是精确一次，不用管水位线和状态。
- 批和流对同一个指标算出来的值必然一致，不需要额外对齐口径。

## 面试速答

> 🎯 批=有界数据、高吞吐、T+1、幂等好回溯（MapReduce/Spark）；流=无界逐条、秒级但要处理事件时间、watermark 乱序与精确一次（Flink/Kafka Streams）；按"结果晚多久不能用"选范式，警惕批流口径漂移。
