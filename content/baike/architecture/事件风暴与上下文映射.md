# 事件风暴与上下文映射

> 📌 **导航**：本文是 **事件风暴与上下文映射** 词条，属于 architecture 术语集。相关枢纽：[[领域驱动设计DDD完全指南]]、[[DDD领域驱动设计]]、[[架构模式]]、[[微服务拆分与选型]]。

## 定义

**一句话定义：** 事件风暴以领域事件为起点，靠工作坊把业务时间线逐层推成命令、聚合与限界上下文；上下文映射再把划好的边界连成图，为每对上下文指定一种集成模式（防腐层、共享内核、开放主机服务…）与依赖方向。

**通俗类比：** 事件风暴像把一场婚礼的每个环节写在便签贴满墙，贴完自然分出「筹备」「仪式」「宴席」三摊事；上下文映射是随后那张通讯录，写明哪一摊听哪一摊的、跨摊传话要不要请翻译（防腐层）。

## 为什么需要它

限界上下文难的不是概念，是操作：领域专家的隐性知识和开发者的直觉凑不到一张桌上，边界最后靠架构师拍脑袋。事件风暴把知识外化成可挪动的便签，边界从事件聚类里长出来。而划完边界只回答「有哪些格子」——跨格子怎么传数据、谁改模型要先通知谁，仍要有名有姓的契约。缺这张表，边界会在两次需求变更后被一条直接调用重新打穿。

## 核心机制

**事件风暴六步**（便签颜色即分工，按时间顺序推进）：

1. **头脑风暴领域事件**：所有人写下业务中已发生的有意义事实（「订单已创建」「支付已完成」），只写过去式。
2. **排列事件时间线**：按业务流程把事件贴满墙，卡壳与断档处就是要问领域专家的问题。
3. **识别命令**：每个事件通常由一个命令（用户操作或系统触发）引发，如「创建订单」「处理支付」。
4. **识别聚合**：命令作用于哪个聚合，该聚合承载执行命令所需的业务规则。
5. **标注外部系统与作用者**：事件和命令的来源（粉色便签与小黄人）。
6. **划定限界上下文**：按事件与聚合的关联性自然聚类，边界是聚类的结果，不是预设的格子。

**上下文间集成模式**（表格只答「有什么」，选择理由见下文）：

| 模式 | 关系与依赖方向 | 协调成本 | 典型场景 |
|---|---|---|---|
| 合作关系 | 两团队共规划、共成败 | 高，需同步发布 | 强依赖的相邻上下文 |
| 共享内核 | 共享一小块模型 | 极高，改动须双方同意 | 迁移期过渡，长期即债 |
| 客户-供应商 | 下游依赖上游 | 中 | 上游愿为下游排期 |
| 跟随者 | 下游被动接受上游模型 | 低 | 第三方 API，无话语权 |
| 防腐层 ACL | 下游翻译上游模型 | 前置投入换长期隔离 | 对接遗留系统 |
| 开放主机服务 + 发布语言 | 上游给标准协议与格式 | 一次定义、多方消费 | 公共服务的多个下游 |
| 各行其道 | 完全不集成 | 零 | 业务确无交集 |

## 具体示例

电商系统里订单上下文要拿商品：商品目录是上游，它的 `Product` 关注描述与图片，订单侧关心的是 SKU 与价格，两边同名不同义。订单侧建一层防腐层，把上游 DTO 翻译成本上下文的 `ProductInfo`：

```java
public class ProductCatalogACL {
    private final ProductCatalogClient client;

    public ProductInfo getProductForOrder(String productId) {
        CatalogProductDto dto = client.getProductById(productId);
        // 字段名与含义都按本上下文重述，上游改接口时改动止步于此
        return new ProductInfo(dto.getSku(), dto.getName());
    }
}
```

整张映射图大致是：客户 <-[客户-供应商]-> 订单 <-[防腐层]-> 商品目录与库存，支付 <-[客户-供应商]-> 订单。跨上下文的状态推进不直连改数据，而是发领域事件、由对方订阅（见 [[事件驱动架构]]）；建模时的起点顺序则是「订单已提交 → 支付已完成 → 商品已发货」这条时间线（第六步的聚类就落在这里）。

## 何时用与何时不用

- **用**：新系统或大重构的建模起点；上下文之间已有隐式直连、需要一次性把依赖方向钉死；对接遗留系统与外部 API 时必须给防腐层一个明确位置。
- **不用**：目标只是给现有 CRUD 分层换个目录名；工作坊请不到领域专家（只剩开发者自说自话）时不如不开；两个上下文长期无交集就别硬画连线。

## 优劣与代价

✅ 建模门槛降到「会讲业务就会参加」，产出即模型雏形与边界草案。
✅ 集成模式一旦命名，「谁能改谁」从口头约定变成图上可评审的边。
⚠️ 工作坊耗时，停在便签层不落到聚合与代码，就只剩仪式感。
⚠️ 防腐层是实打实的样板成本，一层写歪反而多出第二处要维护的模型。

## 与相关概念的区别

- **vs [[DDD领域驱动设计]]**：那条给术语与战术构件的速查定义，本条回答「边界怎么划出来、划完怎么连」。
- **vs 用户故事与需求梳理**：用户故事切交付粒度，事件风暴切模型边界，一个产出 backlog、一个产出上下文图。
- **vs [[微服务拆分与选型]]**：本条止于业务边界与集成契约；边界要不要落成独立服务，由组织与容量信号决定。

## 常见误区

- 把上下文映射画成一张调用图就完事，不指定每对上下文采用哪种集成模式、谁改动要通知谁。
- 为省事先上共享内核，两个上下文长期改同一份模型，边界最终形同虚设。
- 事件风暴只贴事件便签，不往下推命令与聚合，边界仍由架构师拍脑袋定。

## 面试速答

> 🎯 事件风暴：从领域事件出发，事件→命令→聚合→限界上下文逐层聚类，让边界从业务时间线长出来；上下文映射：给每对上下文指定集成模式（客户-供应商、防腐层、开放主机、共享内核…）与依赖方向。划边界与连边界，两步缺一不可。
