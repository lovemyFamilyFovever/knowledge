# DRY、KISS 与 YAGNI

> 📌 **导航**：本文是 **DRY、KISS 与 YAGNI** 词条，属于 architecture 术语集。相关枢纽：[[设计原则]]、[[Clean Code 原则]]、[[03-代码质量]]、[[面向对象编程（OOP）概念]]。

## 定义

**一句话定义：** 三条"少写代码"的原则——DRY 要求每处知识在系统里只有一个权威表示，KISS 要求方案对读者直白，YAGNI 要求只写今天确需的功能；三者对象分别是重复、炫技和提前量，而且彼此会打架：为 DRY 抽出的泛型往往正是 YAGNI 该砍的东西。

**通俗类比：** 像收拾行李：同一根充电线只带一条（DRY）、别为了"可能用得着"塞进三口锅（YAGNI）、能一件外套解决就别买三合一变形装备（KISS）。

## 为什么需要它

代码是负债，不是资产：每一行都要被读、被测、被跟着改。重复意味着"改一处必须记得改另一处"，人脑不是登记表，漏改就是缺陷；炫技意味着读者要在脑子里重放执行栈；提前量最隐蔽——预留的参数、没人调用的钩子、为想象中的多租户抽出的一层接口，会在之后每一次真实改动中陪跑，却永远等不到那天。这三条原则共同压的是**未来改动的总成本**，而代价是当下要多想一步"该不该抽"。

## 核心机制

三条原则各管一种浪费，且必须按顺序裁决，否则会在互相拆台中失焦。

| 原则 | 判定问题 | 典型落地 | 过头后的病症 |
|---|---|---|---|
| DRY | 同一知识是否只有一处权威表示 | 常量、配置、枚举、单一计算函数、模板 | 把不相干逻辑焊进同一个泛型 |
| KISS | 读者一遍能否看懂 | 直白控制流、小函数、显式命名 | 拒绝一切抽象，到处复制 |
| YAGNI | 今天是否真的需要 | 只实现当前用例、第三次重复才抽 | 复制成山、后期大改 |

1. **DRY 的边界是"同一个变更原因"，不是"看起来一样"**：订单税率与报表税率此刻都是 8%，但它们因不同政策而变，合并成一个常量就是把两个模块的未来绑死；反过来，同一个校验规则在前后端各写一遍则必须收到一个权威来源（详见 [[复用与解耦原则]] 的高内聚判据）。判断口径永远是"它们会因同一件事一起改吗"。
2. **KISS 的度量是读者的理解成本，不是行数**：把三步合成一行嵌套表达式通常更短也更贵。简单方案指"沿意图往下读不必回溯上下文"，因此它常与命名、卫语句、扁平控制流一起出现，具体到函数粒度见 [[Clean Code 原则]]。
3. **YAGNI 的对手是预防性设计**：为"以后也许要"预留的开关、抽象层、配置项，绝大多数不会被使用，却要为每次改动做回归。经验做法是 rule of three——同一路数第三次出现才抽象；这与 [[测试驱动开发]] 的"只写让当前测试通过的最少代码"是同一立场。
4. **三者的裁决顺序**：先问 YAGNI（今天要不要），再问 KISS（要不要这么绕），最后才问 DRY（确认要的重复是否同源）。顺序颠倒会得到泛化得过早、又没人读得懂的抽象。

## 具体示例

三个报表模块各自写了 20 行日期区间校验，其中两处逻辑其实不同（一处按自然月、一处按账期），第三处才是真重复。按"看起来一样就合并"会得到一个带三个布尔开关的万能函数，谁改都要传对开关——这既违 KISS 也违 YAGNI。正确做法是只把真同源的那两处收成一个 `validateAccountingPeriod(...)`，另外两个保持各自直白实现，并在注释里写下为什么不合并。

## 何时用与何时不用

- **用**：重复出现第三次的校验/格式化/映射；被复制的方案开始各自演化；评审里有人说"先这样写着，回头再抽"。
- **不用**：一次性脚本与探索草稿（重复的成本低于抽象的赌注）；两个恰好长得像但变更原因不同的逻辑；为不存在的性能或扩展需求预留的泛型参数。

## 优劣与代价

✅ 三条都直接降低改动面：少一份重复就少一处漏改，少一层预留就少一处陪跑。
✅ 不依赖语言与框架，评审时可当场指认。
⚠️ DRY 误用会造出高耦合的"公共"模块，一处改动波及全线，反而比三份副本更贵。
⚠️ YAGNI 有真实边界：不可逆的接口、数据格式与外部契约必须提前设计，不能拿它当不设计的借口。

## 与相关概念的区别

- **vs [[SOLID 五大原则]]**：SOLID 鼓励为扩展点造抽象，DRY/YAGNI 抑制抽象，两股力互相制衡，SOLID 单独用会滑向过度设计。
- **vs [[Clean Code 原则]]**：Clean Code 关心写得好不好读，DRY/KISS/YAGNI 关心该不该写这一份，后者是前者的取舍前提。
- **vs [[复用与解耦原则]]**：DRY 追求"一个知识一个表示"，复用来路不对时会提高耦合——内聚与耦合才是衡量复用上不对上错的尺子。
- **vs 代码复用工具（库/框架）**：复用是手段，DRY 是约束复用的规则；为 DRY 引进一个大依赖通常得不偿失。

## 常见误区

- DRY 就是任何两处代码相似就必须立刻抽成公共方法或共同父类。
- 现在先把扩展点和配置参数留好，将来需求来了不用大改。
- 代码行数越少就越符合 KISS。

## 面试速答

> 🎯 DRY = 同一知识只有一处权威表示（判据是"同一个变更原因"而非"长得像"）；KISS = 以读者理解成本为准，不是行数少；YAGNI = 不写今天不需要的功能。裁决顺序：YAGNI → KISS → DRY，三者互为刹车。
