# 服务通信与 API 网关

> 📌 **导航**：本文是 **服务通信与 API 网关** 词条，属于 architecture 术语集。相关枢纽：[[微服务架构设计与实践]]、[[服务发现]]、[[gRPC深入]]、[[GraphQL实践]]、[[熔断与降级]]。

## 定义

**一句话定义：** 服务通信规定微服务之间**怎么调用、以什么格式、失败后怎么办**（同步 RPC / REST、异步消息、事件驱动）；API 网关是系统对外的**唯一入口**，把路由、鉴权、限流、协议转换与可观测性从各业务服务里抽出来集中承载。

**通俗类比：** 通信规则像公司内部打电话的规矩（谁打给谁、占线怎么重试、要不要留记录）；网关是大楼唯一的门禁前台——访客不必认识每个部门，但刷卡、登记、指引都由它统一做。

## 为什么需要它

进程内调用变成跨网络调用后，"必然成功"这个前提消失了：会出现超时一半、重复投递、对端正在重启。没有统一的通信约定，每个服务会各自实现一套重试与鉴权，行为不一致、故障时互相甩锅。网关解决的是另一半问题：若把鉴权、限流、跨域、协议适配散在几十个服务里，安全策略就成了 N 份要各自升级的拷贝，客户端也要面对一堆内网端点。

## 核心机制

### 三种通信形态

| 形态 | 语义 | 适合 | 主要代价 |
|---|---|---|---|
| 同步 RPC / REST | 请求-等待应答 | 读、需立即结果、强交互 | 调用链级联失败、耦合可用性 |
| 异步消息 | 投递后返回，消费方处理 | 削峰、解耦、跨服务写 | 最终一致、需幂等消费 |
| 事件驱动 | 发布"已发生的事实" | 多下游订阅、可演进 | 事件契约要版本化 |

选择的主轴是**能否容忍延迟**：能容忍就异步，不能才同步。同步链越长，整体可用性越低（10 跳 × 各 99.9% ≈ 99%）。

### 调用侧的三件套

超时（每跳都要显式设，别让默认值决定你的尾部延迟）、重试（只对幂等操作，配退避与抖动，并限最大次数）、[[熔断与降级]]（快速失败胜过排队等待）。再叠加[[限流]]与[[幂等性]]保证重复投递不造成重复扣款。

### 网关的职责边界

该做：路由与聚合、认证与令牌校验、限流配额、跨域与 TLS 卸载、协议转换、灰度分流、访问日志与指标。不该做：业务编排与领域逻辑——网关长厚后会成为全系统单点与发布瓶颈，复杂编排应由明确的 BFF 或服务承担。集群内跨语言、需要流式与强类型时可用 [[gRPC深入]] 承载服务间调用；面向前端要按需裁剪字段则考虑 [[GraphQL实践]] 作 BFF 层，两者与网关常并存。

### 与网格的分工

服务发现、重试、熔断、mTLS 这类"通信通用能力"若不下沉到 [[服务网格]] 的 sidecar，就由网关 + SDK 承担。判断依据是**异构程度与治理广度**：语言杂、服务多、需统一策略 → 网格；否则 SDK 更省。

## 具体示例

一条链路的稳妥配置形态：入口只暴露网关，超时逐跳递减，非幂等写不重试。

```text
client → gateway(timeout 800ms) → order-svc(500ms) → stock-svc(300ms)
                                    |
                                    +-- 事件: OrderCreated → MQ → 积分/风控/通知（各自幂等消费）
```

把"下单后的通知、积分、风控"改成事件订阅，主链路只保留必须同步的扣库存——同步调用数量下降是提升整体成功率最直接的手段。

## 何时用与何时不用

- **用**：任何对外服务都应有网关或等价入口层；写后不要求即时可见的下游动作，一律异步化；跨服务调用必须带超时与熔断，哪怕只有两个服务。
- **不用**：把全部业务逻辑塞进网关的编排脚本；在需要强一致的读路径上用异步消息替代事务；用同步链串起七八个服务来"简化心智模型"。
- **别忘**：一旦引入异步，就要为乱序与重复准备幂等键、死信与补偿，否则故障会变成静默的数据缺失。

## 优劣与代价

✅ 集中治理让安全与流量策略一处生效、统一升级，客户端只面对一个入口。
✅ 异步与事件显著降低级联失败与峰值压力，提高主链路成功率。
⚠️ 网关是天然单点，自身要高可用且要防业务逻辑堆积。
⚠️ 异步换来最终一致，也就换来用户可见的延迟与补偿逻辑的复杂度。

## 与相关概念的区别

- **同步 vs 异步**：区别不是快慢，而是"是否把对方的可用性写进自己的正确性前提"。
- **消息 vs 事件驱动**：消息是"给某人的一条指令"，事件是"已发生的事实"，后者可有未知多订阅者。
- **API 网关 vs 负载均衡**：负载均衡在传输/连接层分发，网关在应用层理解路由与鉴权语义。
- **网关 vs 服务网格**：网关管南北向（外部进入），网格管东西向（服务之间），职责互补而非替代。

## 常见误区

- 微服务之间应该尽量多调用同步接口，因为逻辑更直观。
- 网关功能越强，业务服务就越薄，架构就越干净。
- 有了重试和超时，就不需要幂等设计。

## 面试速答

> 🎯 服务间通信按能否容忍延迟选同步/异步/事件，同步链越长整体可用性越低；调用侧必须有超时、只对幂等操作重试加退避、配熔断降级；网关统一承担路由、鉴权、限流、协议转换与灰度，但不写业务逻辑，东西向治理可下沉到服务网格。
