# API 分页与版本控制

> 📌 **导航**：本文是 **API 分页与版本控制** 词条，属于 architecture 术语集。相关枢纽：[[API设计]]、[[RESTful API 设计]]、[[索引与查询优化术语]]、[[微服务架构设计与实践]]。

## 定义

**一句话定义：** 分页是**限制单次响应数据量**的切分约定，版本控制是**在不破坏既有客户端的前提下演进接口**的兼容机制；两者都发生在接口对外暴露之后，是 API 从"能调"变成"能被长期依赖"的分水岭。

**通俗类比：** 分页像翻书，不一次把全书摊在桌上；版本控制像同时保留新旧两版地图——老用户按旧图仍走得通，新用户可以换新版。

## 为什么需要它

列表接口不加分页，第一次全量返回侥幸能用，等数据涨到百万行就变成慢查询、内存溢出与超时三件套；而接口一旦有客户端在用，任何字段或语义变更都是破坏性变更。没有版本轴，只能"要么偷偷改、赌没人受影响，要么大爆炸式全量升级"。分页与版本化把一个连续的风险切成了可管理的边界：**单次代价有上限，变更影响有隔离**。

## 核心机制

**分页三种方案**

- **Offset/limit**：`?page=2&size=20`。实现最简单、可跳页；但深翻要扫过并丢弃前 N 行（大表上 `LIMIT 100000,20` 极慢），且期间有插入 / 删除会造成**数据漂移**（同一条重复出现或被跳过）。
- **Cursor（游标 / keyset）**：`?cursor=<上一页最后一条的排序键>&size=20`。用索引定位、性能稳定无漂移，代价是不能任意跳页、`total` 需另算、排序键须唯一（常拼主键兜底）。
- **时间窗 / 分段**：按时间段或哈希区间切，适合日志与流式数据，常配合后端归档。

**版本控制三种放法**

| 方式 | 例子 | 优点 | 代价 |
|---|---|---|---|
| URL 路径（推荐） | `/api/v2/users` | 直观、可缓存、易路由与灰度 | URL 空间随版本膨胀 |
| 请求头 | `Accept: application/vnd.myapi.v2+json` | URL 干净、更贴 REST | 调试与日志可见性差 |
| 查询参数 | `/api/users?version=2` | 最灵活 | 易被缓存与代理忽略、语义不显式 |

## 具体示例

```http
GET /api/v1/users?page=3&size=20          # offset：可能漂移
{ "data": [...], "total": 1000, "page": 3, "size": 20 }

GET /api/v1/users?cursor=eyJpZCI6MTAwMX0&size=20   # cursor：base64 的 {id:1001}
{ "data": [...], "next_cursor": "eyJpZCI6MTAyMH0", "has_more": true }
```

翻页语义要固定排序（如 `ORDER BY id DESC`）并让 `cursor` 同时编码排序键与主键，否则同一时刻的两次请求会给出矛盾结果。

## 何时用与何时不用

- **必须分页**：任何集合端点与日志/消息类查询；对外公开接口一律默认有上限，并校验 `size` 最大值防被拉全表。
- **选 cursor**：数据持续增长、翻页深、要稳定不漂移（信息流、导出、分页遍历）；选 offset 只在需要跳页且量小可控时。
- **必须版本化**：对外或有第三方 SDK 的接口，任何破坏性变更（删字段、改类型、改语义）都升版本；新增可选字段与新增端点属兼容变更，不必升版。
- **不必强求**：内部单一消费者且可同步升级的接口，用契约测试与发布顺序协调即可，别为省事起见堆一堆 `vN`。

## 优劣与代价

✅ 分页给单次请求的耗时与内存上了天花板，是容量安全的护栏。
✅ 版本化让接口演进可灰度、可回滚，旧客户端不被瞬间打断。
⚠️ 多版本并存会成倍放大测试、文档与代码维护面，必须配下线计划。
⚠️ `total` 在大表上是昂贵的 `COUNT(*)`，游标方案常改为只返回 `has_more`。

## 与相关概念的区别

- **Offset vs Cursor**：前者是"跳过 N 行"，靠页码定位；后者是"从某个键继续"，靠索引定位。
- **版本控制 vs 兼容性发布**：版本化是"新旧共存"，兼容性发布是"同一版本内向后兼容地演进"；能用后者就不该动用前者。
- **分页 vs 流式响应**：分页把数据切成多次请求，流式（chunked / SSE / [[WebSocket]]）是在一次连接里持续推送。
- **分页 vs [[索引与查询优化术语]]**：分页决定返回多少行，索引决定服务端要多辛苦地找到那些行。

## 常见误区

- offset 分页最简单，所以任何量级的列表都该用它。
- 有版本号之后就可以随意改接口，老版本不用维护。
- 响应里加了 page/total 字段，就等于做了正确的分页设计。

## 面试速答

> 🎯 深翻与漂移是 offset 分页的死穴，量大就用 cursor（键集分页，排序键须唯一）；接口对外就必须版本化，URL 路径最实用、Header 更 REST 但难调试，且加版本必须同时定下线计划，新增可选字段不算破坏性变更。
