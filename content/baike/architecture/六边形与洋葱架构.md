# 六边形与洋葱架构

> 📌 **导航**：本文是 **六边形与洋葱架构** 词条，属于 architecture 术语集。相关枢纽：[[架构模式]]、[[DDD领域驱动设计]]、[[设计原则]]、[[领域驱动设计DDD完全指南]]。

## 定义

**一句话定义：** 六边形（端口与适配器）与洋葱架构都把领域逻辑放在中心、把数据库与 Web 框架等外部细节推到外圈，靠依赖倒置让外层依赖内层——六边形用端口/适配器描述交互方式，洋葱用同心分层描述依赖方向。

**通俗类比：** 六边形像万能插座：核心电器不变，换不同插头（适配器）去接不同电网；洋葱像剥开的同心圆，外圈随便换，圆心（领域模型）从不回头看外圈。

## 为什么需要它

传统三层架构里业务层直接调用数据访问层：换数据库、加消息队列会一路改到业务代码，单测领域规则时没有数据库就跑不起来。两者把依赖方向调转——核心只声明接口，实现留在外层。业务逻辑脱离技术细节后，可测试性与可替换性同时变好，核心资产能在框架更替中存活。

## 核心机制

1. **六边形的端口与适配器**：应用核心只通过端口与外界交互。端口分两类——驱动端口（API，接收外部调用，如 REST 控制器入口）与被驱动端口（SPI，要求外部提供实现，如仓储接口）；两侧的适配器把端口翻译成 HTTP、SQL、MQ 等具体协议。核心业务对协议零感知，纯内存即可驱动测试。
2. **洋葱的同心分层**：由内到外通常是领域模型（实体、值对象）→ 领域服务 → 应用服务 → 接口适配器（控制器、仓储实现、网关）→ 框架与驱动；依赖只准由外向内，内层不知道外层存在。仓储接口放内层、JPA 实现放外层，就是这一规则的典型落点。
3. **共同本质是依赖倒置**：核心代码只依赖抽象、技术细节整体可换，即 [[设计原则]] 中 DIP 在架构尺度的展开；同一思路在 [[领域驱动设计DDD完全指南]] 里与整洁架构并列讲，[[DDD领域驱动设计]] 的聚合与仓储概念提供"接口该放哪层"的领域侧依据。

## 具体示例

领域层声明 UserRepository 接口（通常只有 findById 与 save，不承载复杂查询），基础设施层给出 JPA 实现。把 MySQL 换成 MongoDB 时业务代码零改动；测试领域规则时手写一个内存版实现注入即可。Web 请求、MQ 消费、定时任务是挂在驱动端口上的三种适配器，同一份核心逻辑被三个入口复用。

## 何时用与何时不用

- **用**：领域规则复杂且要长期演化；集成点多（库、缓存、外部 API、消息）且预期会更换；要求核心逻辑不依赖数据库即可单测。
- **不用**：以贫血模型为主的纯 CRUD——端口/适配器的样板代码是白交的抽象税，三层直连更划算；原型探索期业务边界未稳，先跑通再谈倒置。

## 优劣与代价

✅ 核心领域可独立测试、独立演进，技术更换被限制在适配器一层。
✅ 技术栈换代（如自建转云托管）时，业务资产大概率原样存活。
⚠️ 接口与适配器样板代码多，小系统也要交固定抽象税。
⚠️ 端口边界划错时，"抽象层"会变成第二层耦合：改一处仍要动五处。

## 与相关概念的区别

- **vs 传统三层**：三层是业务层依赖数据访问层；这里方向相反——接口在内、实现在外。
- **六边形 vs 洋葱**：洋葱规定层与层的依赖次序（分层视角），六边形不限定层数、只规定核心经端口出入（交互视角），落地时几乎混用。
- **vs 服务拆分**：它们管一个进程内部怎么组织，与 [[微服务架构]] 的拆分粒度正交——拆不拆微服务，服务内部都该用。

## 常见误区

- 必须严格建齐 ports/adapters 目录才算六边形架构——本质是依赖方向，不是目录形状。
- 洋葱架构里由领域层调用基础设施层完成存库——依赖只能由外向内，这个方向反了。
- 上了六边形就能零成本换数据库——"换"恰恰要靠新增一个适配器，这一步省不掉。

## 面试速答

> 🎯 六边形 = 核心经端口（驱动 API / 被驱动 SPI）与外界交互、外层写适配器；洋葱 = 同心分层、依赖只准由外向内。共同本质是依赖倒置：领域不依赖技术，换来可测试与可替换，代价是抽象样板。
