# SOLID 五大原则

> 📌 **导航**：本文是 **SOLID 五大原则** 词条，属于 architecture 术语集。相关枢纽：[[设计原则]]、[[架构模式]]、[[面向对象编程（OOP）概念]]、[[领域驱动设计DDD完全指南]]、[[六边形与洋葱架构]]。

## 定义

**一句话定义：** SOLID 是五个面向对象设计原则的首字母合称——单一职责、开闭、里氏替换、接口隔离、依赖倒置——合起来只回答一件事：职责怎么划、依赖往哪走，才能让"新增一个功能"要改的文件最少。

**通俗类比：** 像岗位说明书：一人只守一摊事（SRP）、新业务靠加人不靠改所有人的职责（OCP）、新人顶岗不会让流程崩掉（LSP）、不给销售发车间门禁卡（ISP）、流程靠制度而不靠某个员工（DIP）。

## 为什么需要它

变更是常态：加代码往往要动老代码，动老代码就带来回归。SOLID 控制的是"改一处要动几处"这个面积——前四条划出职责与替换的边界，DIP 把依赖方向从"业务依赖技术细节"掉转为"业务定义接口、技术实现接口"。换来的不是更少的代码，而是改动可预测：新增一种支付渠道只加一个类，不必回到三百行分支里逐条对表。

## 核心机制

五条不是并列的规矩，而是一条从边界到方向的流水线：划职责 → 定扩展点 → 保继承安全 → 把依赖指向抽象。

1. **单一职责 SRP**：一个类只有一个变更原因。判据不是"一个类只做一件事"的同义反复，而是"谁会提要求来改它"——产品经理改业务规则、DBA 改存储格式，就不该塞进同一个类。典型拆法：`User` 上的存库、发信、生成报表各归一个专职类，实体只留数据与自身规则。
2. **开闭原则 OCP**：对扩展开放、对修改关闭。做法是找出"会沿哪个维度变"并把它抽成可参数化的类型：`pay(String type)` 里的 `if (type.equals("alipay"))` 链换成 `Payment` 接口加若干实现，新渠道只加文件不动老代码。扩展点由 [[策略模式]]、[[模板方法模式]]、[[工厂模式（工厂方法与抽象工厂）]] 承担；代价是抽象要提前写对。
3. **里氏替换 LSP**：子类必须能在不破坏正确性的前提下替换父类。经典反例是正方形继承长方形——设宽会连带改高，凡依赖"宽高可分别设置"的调用全被推翻。可操作判据：子类不收紧前置条件、不放宽后置条件、不新增"此操作不支持"的异常。语言机制侧的继承语义见 [[面向对象编程（OOP）概念]]。
4. **接口隔离 ISP**：客户端不该被迫依赖它用不到的方法。一个 `Worker` 接口里塞 `work` / `eat` / `sleep`，机器人实现者只能写空方法；拆成 `Workable`、`Eatable`、`Sleepable` 让实现者按需组合。判据很硬：实现类出现空方法或抛 unsupported 就该切。它常被混作 SRP——SRP 问"谁要求改这个类"，ISP 问"调用方需要哪几件事"。
5. **依赖倒置 DIP**：高层不依赖低层，两者都依赖抽象；抽象不依赖细节，细节依赖抽象。`OrderService` 持有 `Database` 接口而非 `MySQLDatabase` 实例，具体实现由外部传入。这条把前四条变成可测试的结构，装配机制见 [[IoC 与依赖注入]]，架构尺度的展开见 [[六边形与洋葱架构]]。

## 具体示例

下单服务最初是一个 `OrderService`：校验、算价、写库、发通知、拼报表，五个变更原因挤在一起（违 SRP）。重排后各归一个协作者类（SRP）；定价从 `if/else` 换成策略实现，新增促销只加类（OCP）；不再让 `VipOrderService` 重写父类的"必须含税"约定、改为组合一个策略（规避 LSP 陷阱）；报表侧只需要 `OrderReader` 而非整套 `Order` 接口（ISP）；业务层只认接口、实现由容器装配（DIP）。

## 何时用与何时不用

- **用**：模块边界评审、重构定靶点（配合 [[代码异味]] 与 [[圈复杂度]]）、判断"这个 if-else 该不该抽象"、写公共库与框架。
- **不用**：一次性脚本与探索原型；变更维度还没稳定就急着造扩展点——此时 OCP 的抽象大概率是错的；也不要为凑五条把一个三行函数拆成五个接口。

## 优劣与代价

✅ 给评审提供可指名的判据（"感觉不好"能落到"违反 SRP，因为有两个变更原因"），并直接改善可测试性：DIP + ISP 让依赖能被替身注入。
⚠️ 抽象是有税的：类与接口数量上升，读代码要跳更多文件。
⚠️ 五原则内部会冲突（拆得太细的 SRP 会让 OCP 的扩展点散落），必须结合变更信号取舍。

## 与相关概念的区别

- **vs [[Clean Code 原则]]**：SOLID 管类与模块的结构，Clean Code 管到函数与命名的粒度，是同一条链的上下层。
- **vs [[复用与解耦原则]]**：高内聚低耦合是 SOLID 的度量结果（做好 SRP/ISP 自然改善），迪米特与组合优于继承不在 SOLID 之内。

## 常见误区

- 遵守 SOLID 就是把每个 if-else 都换成策略类，抽象层越多越高级。
- 单一职责就是一个类只能有一个方法，函数越短越好。
- 只要用了接口和依赖注入框架，就自动满足了 SOLID。

## 面试速答

> 🎯 SOLID = 单一职责（一个变更原因）、开闭（加实现不改老代码）、里氏替换（子类可安全替换父类）、接口隔离（不强迫依赖用不到的方法）、依赖倒置（都依赖抽象）；一条流水线：划边界→定扩展点→保替换安全→掉转依赖方向。
