# 微服务拆分与选型

> 📌 **导航**：本文是 **微服务拆分与选型** 词条，属于 architecture 术语集。相关枢纽：[[微服务架构设计与实践]]、[[领域驱动设计DDD完全指南]]、[[服务通信与 API 网关]]、[[可观测性工程实战]]、单体与服务化对比。

## 定义

**一句话定义：** 微服务选型是先判断"组织与技术瓶颈是否真的来自模块耦合"，拆法则是在选定微服务后，**沿业务能力（限界上下文）而非技术分层**把系统切成可独立开发、部署、扩缩的小服务，并让每次切换都可回退。

**通俗类比：** 像要不要把一家大饭店拆成美食广场：只有当"厨房互相抢火台、改一道菜要整店停业"成为真实痛点时才值得拆；按菜系（业务能力）分摊位才对，按"切菜部 / 炒菜部 / 装盘部"（技术分层）分只会让一份订单要跨三个摊位喊话。

## 为什么需要它

单体不是错误，而是**默认最优解**：一次部署、进程内调用、事务与调试都简单。它的痛点的形态很具体——百人团队共用一个仓库时合并冲突不断、一处内存泄漏全站重启、一个模块要扩容就得整块复制、发布要协调所有团队。微服务用运维复杂度换回**团队自治与独立发布**；看不清这些约束就上微服务，等于用分布式系统的所有麻烦去解一个并不存在的问题。

## 核心机制

### 先判该不该拆

三个信号成立才考虑拆：**组织**上多团队在同一代码库互相等待；**变更**上一个高频改动模块迫使整站发布；**容量**上少数功能需要完全不同量级的资源。反向信号同样明确：团队小、领域模型还在探索期、没有独立扩缩需求——这三条下别拆。

### 再决定怎么拆

- **沿业务能力切**，不按技术层切：一个服务应能独立完成一件业务价值（下单、履约、计佣），而不是"所有 web 层"。
- **以限界上下文为边界**（见 [[领域驱动设计DDD完全指南]]）：同一术语在不同上下文含义不同（"商品"在销售与仓储上下文里字段与规则都不同），边界就是翻译层。
- **数据私有为硬约束**：服务各自持有库，跨服务只能走接口或事件；共享一张表会让拆分退化为"分布式单体"。
- **粒度由团队与发布节奏定**：拆到"一个小队能在不做跨团队协调的前提下上线"为止，不是越细越好——过细会把重构成本转成网络调用与联调成本。
- **演进式**：先用绞杀者模式在旧系统外围长出新服务，逐步接管流量，而不是重写大爆炸。

### 拆完必须补的能力

一旦跨进程，[[服务通信与 API 网关]]、[[服务发现]]、[[熔断与降级]]、[[限流]]、[[分布式事务]]、[[可观测性工程实战]] 就从"可选优化"变成"最低配置"。缺任何一项，故障会从局部报错变成全站雪崩。

## 常见拆法对比

| 拆法 | 依据 | 主要风险 |
|---|---|---|
| 按业务能力 | 领域职责 | 边界划错导致跨服务改一处动五处 |
| 按变更频率 | 发布节奏 | 高频模块被过度独立、依赖仍集中 |
| 按团队结构 | 协作边界 | 组织调整即要重拆服务 |
| 按技术分层 | 复用直觉 | 一个需求横跨多服务，最差形态 |

## 具体示例

电商常见的稳妥切法：把"下单"作为起点，先切出**最独立、痛最明显**的一个（例如优惠券/营销），而不是先动交易主链路——先在低风险边界上把注册、网关、链路追踪、发布流水线跑通，再连续切。

```text
第 1 步 营销服务（读多写少、可降级）→ 打通网关 / 发现 / 可观测性
第 2 步 商品详情（高并发，独立扩缩收益明显）
第 3 步 订单（引入事务与补偿，最后动）
```

顺序的依据是**收益确定性与回滚代价**，不是"哪个模块最干净"。

## 何时用与何时不用

- **用**：团队规模到多人共库互相阻塞、需要按模块独立扩缩、多语言异构、要按业务线独立发布节奏。
- **不用**：领域尚不清晰的原型期；小团队；强一致跨表事务密集；缺乏平台工程投入意愿（没人管 CI、监控、发布）。
- **半程**：只在单体内部做好模块边界与接口隔离（模块化单体），收益常已足够，且保留随时拆的余地。

## 优劣与代价

✅ 团队自治与独立发布，故障与容量隔离到单服务，可按需异构选型。
✅ 边界一旦与领域对齐，需求变更的影响面显著收窄。
⚠️ 跨服务调用让事务变成补偿、调试变成链路拼接，任何一处网络抖动都会进你的业务路径。
⚠️ 错误的边界比不拆更贵：拆错要付重写成本，且往往在数月后才显形。

## 与相关概念的区别

- **微服务 vs 模块化单体**：前者进程隔离、独立部署，后者同进程但接口清晰；后者常常是更好的起点。
- **拆分 vs 服务网格**：拆分管"边界怎么划"，[[服务网格]] 管"跨边界的调用怎么治理"，两者正交。
- **业务能力切分 vs 分层切分**：前者一个需求尽量在一个服务内闭环，后者天然要求多服务联动。
- **拆分 vs 重构**：重构不改外部行为、在同一部署单元内；拆分改变部署与所有权边界。

## 常见误区

- 微服务比单体更先进，新项目应当直接按微服务来设计。
- 服务拆得越细，系统就越灵活、越容易扩展。
- 只要用了容器编排和网关，架构就算完成了微服务化。

## 面试速答

> 🎯 微服务只在组织等待、发布耦合、容量错配三条同时成立时才划算；拆要沿业务能力与限界上下文、数据私有、以团队能独立上线为粒度，并用绞杀者模式渐进迁移；拆完必须补齐网关、发现、熔断限流、分布式事务与可观测性。
