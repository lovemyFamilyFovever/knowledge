# 设计原则


> 📌 **导航**：本文是 **设计原则** 词条，属于 architecture 术语集。相关枢纽：[[SaaS产品技术架构]]、[[事件驱动架构]]、[[云原生与多云架构实战指南]]、[[分布式系统设计完全指南]]、[[微服务架构]]。

## 定义

**一句话定义：** 设计原则是一组关于"职责怎么划、依赖往哪走、抽象什么时候做"的取舍准则——SOLID 定职责与依赖方向，DRY/KISS/YAGNI 控改动量与抽象时机，内聚耦合与迪米特管依赖数量，IoC/DI 管依赖如何装配；它们互相制衡，不是可以逐条打勾的律法。

**通俗类比：** 像开车守则：保持车距（低耦合）、不超速（YAGNI）、不随意变道（单一职责）、给救护车让路（对扩展开放）。每条都在特定路况下要让位于另一条，合起来才叫安全驾驶。

## 为什么需要它

代码写完只是开始，真正花钱的是之后每一次改动。没有命名好的原则，评审会退化成"我觉得这样怪"的经验之争；有了它，"这里有问题"就能落到具体靶点——一个类承担三个变更原因、两处逻辑必须同步改、改一处要跑五个模块的回归。原则给的是**判断语言与取证方向**，而它自己也会腐化：机械套用会造出没人读得懂的过度抽象，所以每条原则都得连着"失效信号"一起记，并知道它跟哪几条互相拆台。

## 核心机制

下表负责"有什么"——十四条准则各自的管辖对象、失效信号与归口词条；下面五条只讲族怎么分、彼此怎么制衡。

| 原则 | 管什么 | 失效信号 | 详见 |
|---|---|---|---|
| 单一职责 SRP | 一个模块只因一个原因变化 | 一个类里混着两类需求的改动 | [[SOLID 五大原则]] |
| 开闭 OCP | 加功能靠新增而非修改 | 新增类型要改一长串分支 | [[SOLID 五大原则]] |
| 里氏替换 LSP | 子类可安全替换父类 | 子类抛"不支持"异常 | [[SOLID 五大原则]] |
| 接口隔离 ISP | 不强迫依赖用不到的方法 | 实现类里成堆空方法 | [[SOLID 五大原则]] |
| 依赖倒置 DIP | 高层低层都依赖抽象 | 业务代码里 new 具体驱动 | [[SOLID 五大原则]] |
| DRY | 每处知识只有一个权威表示 | 复制成对出现、改一漏二 | [[DRY、KISS 与 YAGNI]] |
| KISS | 能直白就别炫技 | 一句嵌套要读三遍 | [[DRY、KISS 与 YAGNI]] |
| YAGNI | 不写今天不需要的功能 | 无人调用的参数与钩子 | [[DRY、KISS 与 YAGNI]] |
| 高内聚低耦合 | 模块内紧密、模块间松散 | 一个 PR 改五个模块 | [[复用与解耦原则]] |
| 迪米特法则 | 只跟直接朋友通信 | `a.getB().getC().getD()` | [[复用与解耦原则]] |
| 组合优于继承 | 复用优先靠持有 | 基类一改、子集全测 | [[复用与解耦原则]] |
| 面向接口编程 | 依赖契约不依赖实现 | 换实现要改调用方签名 | [[复用与解耦原则]] |
| 控制反转 IoC | 创建与装配交给外部 | 对象内部自己 new 依赖 | [[IoC 与依赖注入]] |
| 依赖注入 DI | 依赖由外部传入 | 单测必须先起真库 | [[IoC 与依赖注入]] |

1. **先分族再谈顺序**：本页十四条准则分属四个族——[[SOLID 五大原则]] 管类与模块的职责和依赖方向，[[DRY、KISS 与 YAGNI]] 管"要不要写这一份"，[[复用与解耦原则]] 管依赖的数量与强度，[[IoC 与依赖注入]] 管依赖由谁装配。分族不是目录美化：同一个病症在不同族开不同药，"改一处崩五处"先查第三、四族，"新需求不知往哪加"先查第一族的 OCP。
2. **制衡关系决定裁决顺序**：SOLID 鼓励造抽象，YAGNI 限制造抽象；DRY 鼓励合并，迪米特与低耦合警惕合并造成共享。落地时按"要不要（YAGNI）→ 谁负责（SRP、内聚）→ 从哪扩展（OCP、DIP）→ 依赖谁（迪米特、面向接口）→ 谁来装配（DI）"问一遍，比背十四条清单快得多，冲突点也会自己浮出来。
3. **失效信号比定义更该背**：面试与评审真正追问的是"你怎么发现违反了"——空实现方法指向 ISP，子类抛不支持异常指向 LSP，一个 PR 横跨五个模块指向内聚，getter 链指向迪米特，单测离不开真库指向没有 DIP 与 DI。这批信号与 [[代码异味]]、[[圈复杂度]] 是同一组症状的两套语言，后者是量化入口。
4. **原则不答业务边界**：全部准则只评判结构，不回答"订单与库存该不该分家""聚合根怎么划"——那是 [[领域驱动设计DDD完全指南]] 与 [[微服务拆分与选型]] 的职责。把边界问题当原则问题解，典型结局是抽象漂亮却天天返工。
5. **落地靠写法不靠框架**：装了 IoC 容器不等于依赖倒置，跑了 linter 也不等于 [[Clean Code 原则]]。检验单位是一次具体改动：新增一个需求改了哪几个文件、有没有碰不相干的代码。评审时把"这条原则是什么"换成"这次改动证明了什么"，讨论质量会立刻不同。

## 具体示例

下单服务最初是一个上帝类：校验、算价、写库、发通知、拼报表，五个变更原因挤在一起（违 SRP），支付方式靠 `if/else` 分派（违 OCP），内部直接 new 数据库对象（违 DIP），还顺手读别的对象的三层内部字段（违迪米特）。重构路径正好按四族走：先按职责拆出校验与渲染（SOLID 族），把分支换成策略实现并声明接口（解耦族），接口实现改由构造器注入（装配族），最后把重复了三次的金额格式化收成一个权威函数（DRY，且确认三处同源）。

## 何时用与何时不用

- **用**：模块边界与接口评审、重构定靶点、公共库与跨团队契约设计、面试中"这段代码有什么问题"类追问。
- **不用**：一次性脚本与探索原型；变更维度尚未稳定就急着造扩展点；把原则当打卡表——为凑齐五条把一个三行函数拆成五个文件，本身就是一种代码异味。

## 优劣与代价

✅ 提供可指名的判据，评审从口味之争变成取证之争，改动半径可预测。
✅ 直接改善可测试性：接口先行加依赖注入，让单测脱离真库真网络。
⚠️ 抽象有税：文件与间接层增多，读一条调用链要跳更多地方。
⚠️ 原则之间会互相拆台且无仲裁机构，机械套用会造出过度设计——只能靠"变更信号"这条外部裁判持续校正。

## 与相关概念的区别

- **vs [[Clean Code 原则]]**：原则给方向（职责与依赖），Clean Code 给到函数与命名粒度的落地手法，是同一条链的上下层。
- **vs [[架构模式]]**：模式是反复出现的结构形状，原则是评判这些形状的价值观；六边形与洋葱这类"依赖朝内"的形状由 DIP 直接推动，见 [[六边形与洋葱架构]]。
- **vs [[面向对象编程（OOP）概念]]**：类、继承、多态是语言机制，原则是用这些机制时的取舍；同一个 `extends` 用得对是 LSP，用错了就是脆弱基类。
- **vs 需求与领域建模**：原则不生成结构，只在候选结构里挑；划边界靠 [[DDD领域驱动设计]]。

## 常见误区

- 遵守设计原则就是把每个 if-else 都换成策略类，抽象层越多架构越先进。
- DRY 要求任何两处相似的代码都必须立刻合并成一个公共方法。
- 引入了 IoC 容器框架，代码就自动符合 SOLID。

## 面试速答

> 🎯 设计原则分四族：SOLID 定职责与依赖方向，DRY/KISS/YAGNI 控改动量与抽象时机，内聚耦合与迪米特管依赖数量，IoC/DI 管装配。它们互相制衡，按"要不要→谁负责→哪扩展→依赖谁→谁装配"的顺序取舍。
