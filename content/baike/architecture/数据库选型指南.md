# 数据库选型指南


> 📌 **导航**：本文是 **数据库选型指南** 词条，属于 architecture 术语集。相关枢纽：[[SaaS产品技术架构]]、[[事件驱动架构]]、[[云原生与多云架构实战指南]]、[[分布式系统设计完全指南]]、[[微服务架构]]。

## 定义

**一句话定义：** 数据库选型是根据业务访问模式（事务性/灵活性/吞吐/查询形态）匹配存储引擎特性的架构决策过程。

**通俗类比：** 像选交通工具——市区代步选自行车（Redis 缓存），长途搬家选卡车（HBase 批量写），跨城通勤选高铁（MySQL/PG 通用 OLTP）。

## 为什么需要它

选错数据库的代价远高于换框架：数据迁移涉及 schema 转换、双写过渡和停机窗口，成本是数量级级的。前期选型一次对，胜过后期反复重构。

## 核心能力

按访问模式分三大阵营：

**关系型（OLTP）**：MySQL（成熟生态）、PostgreSQL（最强扩展性、JSON/地理信息）、SQLite（嵌入式零配置）。需要 ACID 事务和复杂 JOIN 查询时的默认选择。

**NoSQL 按数据模型细分**：文档型 MongoDB（灵活 Schema）、键值 Redis（缓存/会话，微秒级）、列族 HBase/Cassandra（海量写入/宽表）、图 Neo4j（多跳关系遍历）、搜索 Elasticsearch（全文检索）、时序 InfluxDB/TDengine（监控/IoT）。

**NewSQL**：TiDB（MySQL 兼容 + 水平扩展 + HTAP）、CockroachDB（PG 兼容 + 全球分布式事务）、OceanBase（金融级强一致）。兼具 SQL 语义和分布式扩展。

## 具体示例

社交平台：用户关系 → Neo4j（"好友的好友"2 度查询）；动态流 → Cassandra（高写入吞吐 + 时间序列）；搜索 → Elasticsearch（全文+聚合）；核心交易 → PostgreSQL（事务保证）。多库各司其职，而非一把梭。

## 何时用与何时不用

- **用**：新系统架构设计阶段确定持久层；现有系统遇到明确瓶颈（写入/查询/扩展）评估替换。
- **不用**：仅因"这个库更热门"而换；团队无运维能力时选过于小众的方案。

## 优劣与代价

✅ 按场景选库可在性能/成本/开发效率间取得最优。
✅ NoSQL 在特定访问模式上远超关系型（如 Redis 延迟、ES 搜索）。
⚠️ 多库并存增加运维复杂度和数据一致性挑战。
⚠️ NoSQL 往往牺牲 JOIN 和事务能力，模型设计需提前规划查询模式。

## 与相关概念的区别

- **vs ORM/数据库中间件**：ORM 是应用层抽象（Hibernate/Prisma），选型决定底层引擎本身；选 PostgreSQL 还是 MongoDB 是架构级决策，ORM 是工程级决策。
- **vs 数据仓库**：OLTP 库（MySQL）面向实时读写，数仓（ClickHouse/Snowflake）面向分析聚合——OLTP 不是"更好的数仓"，两者互补。

## 常见误区

- MySQL 可以解决一切数据存储问题，不需要其他库。
- 用了 NoSQL 就不需要设计 Schema 了。
- 新数据库一定比老数据库性能更好。

## 面试速答

> 🎯 选型核心是访问模式匹配：事务/JOIN→关系型，灵活文档→MongoDB，极低延迟→Redis，全文→ES，多跳关系→图数据库，海量写入→Cassandra，全球分布+SQL→NewSQL。
