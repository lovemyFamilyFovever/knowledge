# 事件驱动架构


> 📌 **导航**：本文是 **事件驱动架构** 词条，属于 architecture 术语集。相关枢纽：[[SaaS产品技术架构]]、[[事件驱动架构]]、[[云原生与多云架构实战指南]]、[[分布式系统设计完全指南]]、[[微服务架构]]。

## 定义

**一句话定义：** 事件驱动架构以不可变的"已发生事实"为通信单元，生产者发布事件、消费者订阅响应，组件间通过事件流而非直接调用解耦。

**通俗类比：** 像公告栏——有人贴通知（发布事件），关心的人自行来看并行动，贴的人不需要逐个敲门通知。

## 为什么需要它

同步调用链在微服务中制造级联故障和强耦合：订单服务超时 → 库存也卡住 → 整条链路雪崩。事件驱动将"你调我"变成"我广播、你自行响应"，各消费者可独立扩展、独立故障，互不阻塞。

## 核心机制

**基本模型**：生产者 → 事件总线/消息中间件 → 消费者（可多个）。事件一旦发出不可修改（append-only），消费者按自己的节奏处理。

**两种典型模式**：

1. **Event Sourcing**：不存当前状态，存状态变化的事件序列。当前状态 = 重放所有事件（OrderCreated → ItemAdded → PaymentReceived → OrderShipped）。好处是完整审计追溯，代价是重放开销需要快照优化。

2. **CQRS（命令查询职责分离）**：写路径（Command）和读路径（Query）分离——命令修改写模型后发布事件，事件更新优化后的读模型。读写可独立扩缩容。

## 具体示例

电商订单流转：用户下单 → 发布 OrderCreated 事件 → 库存服务消费扣减并发出 StockDeducted → 支付服务消费发起扣款 → 发出 PaymentReceived → 物流服务消费安排发货。每一步松耦合，支付超时不阻塞库存扣减。

## 何时用与何时不用

- **用**：多消费者扇出（通知/审计/统计）、需要最终一致即可的业务流、组件间需故障隔离。
- **不用**：强一致性场景（银行转账实时扣款）、请求-响应式简单 CRUD（引入中间件反而增加运维负担）。

## 优劣与代价

✅ 松耦合、可扩展，新增消费者无需改生产者。
✅ 天然削峰——中间件充当缓冲。
⚠️ 最终一致性：开发者需习惯"此刻查不到刚写入的数据"。
⚠️ 调试复杂度：事件流向不直观，需链路追踪支撑。

## 与相关概念的区别

- **vs 消息队列**：MQ 是传输通道（Kafka/RabbitMQ），EDA 是架构风格——可以用 MQ 实现，但 EDA 还包含事件建模、幂等消费、重放等约束。
- **vs 请求驱动（REST/RPC）**：请求驱动是调用方等待响应，EDA 是通知即返回；前者强耦合时序，后者只保证最终一致。

## 常见误区

- 用了 Kafka 就是事件驱动架构。
- 事件驱动可以替代所有同步调用。
- Event Sourcing 是 EDA 必须采用的存储方案。

## 面试速答

> 🎯 EDA = 不可变事件做通信单元、生产者广播消费者订阅实现解耦；核心模式是 Event Sourcing（事件流即状态）和 CQRS（读写模型分离）；代价是最终一致性和调试复杂度。
