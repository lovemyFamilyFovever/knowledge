# 单元测试


> 📌 **导航**：本文是 **单元测试** 词条，属于 testing 术语集。相关枢纽：[[01 - 测试基础]]、[[02 - 测试工具]]、[[03 - 性能测试]]、[[单元测试]]、[[性能测试]]。

## 定义

**一句话定义：** 单元测试(Unit Testing)是针对软件中最小可测试单元(通常是一个函数、方法或类)编写的自动化测试,用于验证该单元在各种输入下的行为是否符合预期;它是测试金字塔的最底层,也是数量最多的一层。

**通俗类比：** 像造汽车时先单独检验每个零件(螺丝、活塞、刹车片)是否合格,而不是等整车造好才试跑——零件级(单元)先测好,整车(集成/系统)才更可靠、问题更易定位。

> 多义说明:单元测试聚焦"单个单元"并隔离依赖(用 mock/stub);区别于集成测试(测模块间协作)与端到端测试(测完整流程)。本文讨论单元测试。

## 原理与机制

- **结构:** 常遵循 AAA / 3A 模式——Arrange(准备数据与环境)、Act(执行被测单元)、Assert(断言结果)。
- **隔离:** 用测试替身(mock / stub / fake)隔离外部依赖(数据库、网络、时间),使测试快速、确定、独立。
- **框架:** JUnit、pytest、Go testing、Jest 等 xUnit 家族。
- **良好特征(FAST):** 快速、独立、可重复、自动化;应覆盖正常、边界与异常路径。

## 关键组成

| 组成 | 说明 |
|------|------|
| 被测单元 | 函数 / 方法 / 类 |
| AAA 结构 | Arrange-Act-Assert |
| 断言 | 校验结果是否符合预期 |
| 测试替身 | mock / stub / fake 隔离依赖 |
| 覆盖率 | 衡量测试覆盖程度 |

## 应用场景

- 开发阶段验证函数/类逻辑
- 重构的安全网
- 测试驱动开发(TDD)
- CI 中自动运行、提升代码质量与信心

## 优点与局限

- 优点:快速、定位精确、成本低,支撑重构与 TDD,覆盖细节。
- 局限:只验证单元(不保证模块协作或整体正确,需集成/E2E);过度 mock 可能"测了个寂寞";写测试有前期成本;覆盖率 ≠ 质量。

## 常见误区

- 单元测试 ≠ 集成测试:单元隔离依赖,集成测协作。
- "测试覆盖率高" ≠ "没 bug":覆盖到不代表断言充分。
- 单元测试应快且独立(不依赖网络/数据库/执行顺序)。
- 滥用测试替身会掩盖真实的交互问题。
