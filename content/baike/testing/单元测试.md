# 单元测试

> 📌 **导航**：本文是 **单元测试** 词条，属于 testing 术语集。相关枢纽：[[01 - 测试基础]]、[[02 - 测试工具]]、[[03 - 性能测试]]、[[单元测试]]、[[性能测试]]。

## 定义

**一句话定义：** 单元测试（Unit Testing）是针对软件中最小可测试单元（通常是一个函数、方法或类）编写的自动化测试，用于验证该单元在各种输入下的行为是否符合预期；它是测试金字塔的最底层，也是数量最多的一层。

**通俗类比：** 像造汽车时先单独检验每个零件（螺丝、活塞、刹车片）是否合格，而不是等整车造好才试跑——零件级先测好，整车（集成 / 系统）才更可靠、问题更易定位。

## 为什么需要它

等把整套系统拼起来再测，缺陷会藏在复杂交互里，定位慢、修复贵。单元测试在最小的粒度上、用最便宜的方式先把每个逻辑单元钉死，形成一张廉价、快速、可重复运行的安全网：改代码时它第一时间告诉你有没有改坏，是重构与 TDD 的基石。

## 做法

- **结构**：遵循 AAA / 3A 模式——Arrange（准备数据与环境）、Act（执行被测单元）、Assert（断言结果）。
- **隔离**：用测试替身（mock / stub / fake）隔离数据库、网络、时间等外部依赖，使测试快速、确定、独立。
- **框架**：JUnit、pytest、Go testing、Jest 等 xUnit 家族。
- **良好特征（FAST）**：快速、独立、可重复、自动化；覆盖正常、边界与异常路径。

## 具体示例

一个最小 AAA 单元测试，隔离而确定：

```python
def test_add():
    assert add(2, 3) == 5    # Arrange: 入参 2,3 → Act: add → Assert: 期望 5
```

| 组成 | 说明 |
|------|------|
| 被测单元 | 函数 / 方法 / 类 |
| AAA 结构 | Arrange-Act-Assert |
| 测试替身 | mock / stub / fake 隔离依赖 |
| 覆盖率 | 衡量覆盖程度（不等于质量） |

## 何时用与何时不用

- **用**：验证纯逻辑单元、作重构安全网、驱动 TDD、在 CI 中自动运行以守住质量底线。
- **不用**：别指望单元测试验证模块协作或完整业务流程（那是集成 / E2E 的活）；也别为覆盖率数字给琐碎 getter 硬凑测试。

## 优劣与代价

✅ 快、定位精确、成本低，支撑重构与 TDD，能覆盖细粒度逻辑。
✅ 大量廉价测试构成回归安全网。
⚠️ 只保证单元正确，不保证协作与整体正确。
⚠️ 有前期编写成本，过度 mock 可能"测了个寂寞"、掩盖真实交互问题。

## 与相关概念的区别

- **单元测试 vs 集成测试**：单元隔离依赖、测单个逻辑；集成把真实模块拼起来测协作。
- **测试替身 vs 真实依赖**：mock/stub 用来隔离慢而不确定的外部系统，但也可能让测试与现实脱节。
- **覆盖率 vs 质量**：覆盖率衡量"代码被执行到多少"，不代表断言充分或行为正确。

## 常见误区

- 单元测试覆盖率刷到 100%，就说明代码没有 bug 了。
- 单元测试就该连真实数据库、走真实网络来测才够真。
- 写了一堆单元测试就等于在做集成测试。

## 面试速答

> 🎯 单元测试 = 针对最小可测试单元（函数 / 方法）的自动化测试，遵循 AAA（Arrange-Act-Assert），用测试替身隔离外部依赖，是测试金字塔最底层最多的一层；要快、独立、可重复，覆盖正常 / 边界 / 异常。
