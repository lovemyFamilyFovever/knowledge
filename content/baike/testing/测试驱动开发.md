# 测试驱动开发

> 📌 **导航**：本文是 **测试驱动开发** 词条，属于 testing 术语集。相关枢纽：[[01 - 测试基础]]、[[02 - 测试工具]]、[[03 - 性能测试]]、[[单元测试]]、[[性能测试]]。

## 定义

**一句话定义：** 测试驱动开发（TDD）是一种先写一个会失败的测试、再写最小实现使其通过、最后重构的软件开发实践，遵循 Red–Green–Refactor 循环，让测试来驱动设计与验证。

**通俗类比：** 像先画靶再射箭——动手写代码之前，先用测试把"怎样算做对了"钉死，然后调整实现去命中它，而不是先随便射一箭再补画靶心。

## 为什么需要它

先写测试，逼你在编码前就想清楚接口与预期行为（契约先行）；只写"让当前测试通过的最少代码"天然抑制过度设计（YAGNI）；每完成一小步都有测试当安全网，敢于持续重构。它带来的不只是覆盖率，更是一套"可测试、低耦合"的设计约束和即时反馈。

## 做法

- **Red**：写一个针对下一个小需求的测试，先让它失败（证明测试确实能捕获缺失）。
- **Green**：写刚好让测试通过的最少实现，不图优雅先求通过。
- **Refactor**：在测试保护下清理重复、改善命名与结构，保持绿灯。
- 循环小步快跑，用"由外而内""三角测量"等手段设计测试用例；TDD 主要作用在以单元测试为主的这一层。

| 阶段 | 目标 | 关键动作 |
|------|------|----------|
| Red | 明确期望 | 写失败测试 |
| Green | 达成期望 | 最小实现 |
| Refactor | 改善结构 | 安全网下清理 |

## 具体示例

一个经典循环：先断言 `add(2,3)==5`（此时 add 还没写，测试报 Red），补上 `def add(a,b): return a+b` 让它 Green，再在绿灯下重构。

```
Red(写失败测试) → Green(写最少代码通过) → Refactor(重构)
```

## 何时用与何时不用

- **用**：逻辑密集的库 / 算法 / 业务规则、需要长期维护与重构的代码、想内建质量与清晰契约的团队。
- **不用**：一次性脚本、快速探索原型或需求本身在剧烈试探时，严格 TDD 的样板成本可能大于收益；UI 等难以单测的部分可把逻辑下沉后再 TDD。

## 优劣与代价

✅ 契约先行、抑制过度设计、给持续重构提供安全网、缺陷早发现。
✅ 产出更模块化解耦、可测试的代码与活的文档（测试）。
⚠️ 学习曲线陡，前期有速度成本；对设计尚未定型的探索阶段可能僵化。
⚠️ 用错层级（全 E2E）会让循环慢到无法维持。

## 与相关概念的区别

- **TDD vs "先写代码再补测试"**：前者测试塑造设计与接口；后者只事后验证，无法享受"契约先行"带来的可测试性。
- **TDD vs BDD / ATDD**：TDD 从开发者视角驱动单元，BDD/ATDD 从行为与验收出发，常作互补。
- **TDD vs 单纯单元测试**：TDD 是一种开发流程，单元测试是它的产物与工具之一。

## 常见误区

- TDD 的目的就是把测试覆盖率刷到 100%。
- "先写测试再写代码"和"先写代码再补测试"没本质区别，只是顺序不同。
- 任何场景都应当严格照搬 TDD，包括纯探索原型和剧烈变需求阶段。

## 面试速答

> 🎯 TDD = 先写失败测试（Red）→ 写最少代码通过（Green）→ 重构（Refactor）的循环；测试先行倒逼清晰契约与可测试的低耦合设计，通常配合以单元测试为主的测试金字塔。
