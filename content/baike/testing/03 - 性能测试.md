# 03 - 性能测试

> 本文档涵盖性能测试的核心概念、工具使用、结果分析及优化思路。

---

## 性能测试类型

### 一句话定义（大白话）
性能测试有四种主要类型：负载测试验证正常负载、压力测试探索极限、稳定性测试验证持久运行、容量测试确定最大承载量。

### 通俗类比（生活场景）
- **负载测试**：10个人同时进餐厅，看服务是否正常
- **压力测试**：1000个人同时涌入，看什么时候崩溃
- **稳定性测试**：连续营业72小时，看会不会出问题
- **容量测试**：测一下这家餐厅最多能同时接待多少人

### 具体示例
| 测试类型 | 目标 | 持续时间 | 并发量 | 关注指标 |
|----------|------|----------|--------|----------|
| 负载测试 | 验证预期负载下的表现 | 30-60分钟 | 预期用户量 | 响应时间、错误率 |
| 压力测试 | 找到系统崩溃点 | 15-30分钟 | 逐步增加至极限 | 系统稳定性、恢复能力 |
| 稳定性测试 | 验证长时间运行的稳定性 | 8-24小时 | 正常负载 | 内存泄漏、资源耗尽 |
| 容量测试 | 确定系统最大承载量 | 30-60分钟 | 逐步增加 | 最大并发数、吞吐量 |

### 为什么需要它
不同测试类型回答不同问题：能不能扛住日常流量？极限在哪里？长时间运行会不会出问题？最大承载量是多少？

### 与相关术语的对比和区分
- **负载测试 vs 压力测试**：负载测试验证预期场景，压力测试探索极限
- **稳定性测试 vs 容量测试**：稳定性测试关注时间维度，容量测试关注并发维度

---

## QPS（每秒查询数）

### 一句话定义（大白话）
QPS 是服务器每秒能处理的请求数量，直接反映系统的处理能力。

### 通俗类比（生活场景）
就像银行窗口每秒能服务多少个客户——QPS 越高，说明系统处理能力越强。

### 具体示例
```
# QPS 计算公式
QPS = 总请求数 / 总时间（秒）

# 示例：10秒内处理了 500 个请求
QPS = 500 / 10 = 50 QPS

# 不同系统的 QPS 参考值
简单 API（无数据库）：10000+ QPS
带缓存的 API：5000-10000 QPS
数据库查询：1000-5000 QPS
复杂业务逻辑：500-2000 QPS
```

### 为什么需要它
QPS 是衡量系统性能的核心指标，直接影响用户体验和系统容量规划。

### 与相关术语的对比和区分
| 指标 | 定义 | 适用场景 |
|------|------|----------|
| QPS | 每秒查询数 | 通用系统 |
| TPS | 每秒事务数 | 事务处理系统 |
| RPS | 每秒请求数 | Web 系统 |

---

## TPS（每秒事务数）

### 一句话定义（大白话）
TPS 是服务器每秒能完成的事务数量，一个事务可能包含多个请求（如：查询、计算、返回）。

### 通俗类比（生活场景）
在餐厅，一个"事务"可能是：点餐、厨房制作、上菜。TPS 衡量的是每秒能完成多少桌的完整服务，而不只是接待多少人。

### 具体示例
```
# TPS vs QPS 的区别
# 一个事务可能包含多个查询：

示例：用户下单事务
  1. 查询商品库存（1次查询）
  2. 验证用户信息（1次查询）
  3. 创建订单（1次查询）
  4. 扣减库存（1次查询）
  5. 发送确认通知（1次查询）

# 这个事务 = 5个查询
# 如果系统每秒完成100个事务
# TPS = 100
# QPS = 500（100 * 5）

# 不同系统的 TPS 参考值
银行交易系统：1000-5000 TPS
电商订单系统：500-2000 TPS
支付系统：500-3000 TPS
```

### 为什么需要它
TPS 比 QPS 更能反映业务处理能力，特别适合事务密集型系统。

### 与相关术语的对比和区分
- **TPS vs QPS**：TPS 关注业务事务，QPS 关注请求次数
- **TPS vs 并发用户数**：TPS 是处理能力，并发用户数是同时使用的用户量

---

## 并发用户数

### 一句话定义（大白话）
并发用户数是同一时刻同时使用系统的用户数量，反映系统的并发处理能力。

### 通俗类比（生活场景）
超市的收银台数量就是"并发处理能力"——如果有10个收银台，最多同时服务10个顾客，其他的要排队。

### 具体示例
```
# 并发用户数的三种理解

# 1. 并发用户数（同时在线）
# 同一时刻登录系统的用户总数
# 例：10:00整，有 500 个用户同时在线

# 2. 并发请求用户数（同时发起请求）
# 同一时刻向服务器发送请求的用户数
# 例：500 个在线用户中，有 100 个同时在请求数据

# 3. 平均并发用户数
# 一段时间内的平均并发数
# 例：上午 9:00-12:00，平均并发 200 人

# 并发数与 QPS 的关系
# 假设每个用户平均每次请求耗时 2 秒
# 100 个并发用户 * (1秒 / 2秒) = 50 QPS
```

### 为什么需要它
并发用户数是容量规划的基础，帮助确定服务器配置、带宽需求、数据库连接池大小等。

### 与相关术语的对比和区分
| 概念 | 定义 | 关注点 |
|------|------|--------|
| 并发用户数 | 同时使用系统的用户 | 系统承载能力 |
| 在线用户数 | 登录系统的用户总数 | 系统规模 |
| 活跃用户数 | 一段时间内有操作的用户 | 系统活跃度 |

---

## 响应时间（平均/P90/P95/P99）

### 一句话定义（大白话）
响应时间是用户发出请求到收到响应的总时间。平均响应时间是最常用的指标，但 P90/P95/P99 能反映更真实的用户体验。

### 通俗类比（生活场景）
去医院看病：平均响应时间是所有患者的平均等待时间，P99 是99%的患者在这个时间内看上了病。如果平均等待30分钟，但 P99 是3小时，说明有1%的患者等了很久——这就是平均值掩盖的问题。

### 具体示例
```
# 响应时间分布示例（100个请求）
# 按耗时排序：
# 1-50个：100-200ms
# 51-90个：200-300ms
# 91-95个：300-500ms
# 96-99个：500-1000ms
# 第100个：2000ms（异常慢）

# 计算结果：
# 平均响应时间：210ms
# P50（中位数）：180ms
# P90：280ms
# P95：400ms
# P99：950ms
# 最大值：2000ms

# 响应时间参考标准
# < 100ms：优秀（用户感觉即时）
# 100-300ms：良好（用户能感知延迟）
# 300ms-1s：一般（用户能接受）
# 1-3s：较差（用户开始不耐烦）
# > 3s：很差（用户可能离开）
```

### 为什么需要它
平均响应时间可能掩盖长尾问题，P90/P95/P99 能发现少数用户的极差体验。

### 与相关术语的对比和区分
| 指标 | 含义 | 反映的问题 |
|------|------|------------|
| 平均响应时间 | 所有请求的平均耗时 | 整体性能 |
| P90 | 90% 请求在此时间内完成 | 大部分用户体验 |
| P95 | 95% 请求在此时间内完成 | 绝大多数用户体验 |
| P99 | 99% 请求在此时间内完成 | 长尾用户体验 |

---

## 吞吐量（Throughput）

### 一句话定义（大白话）
吞吐量是单位时间内系统成功处理的请求量，是衡量系统处理能力的综合指标。

### 通俗类比（生活场景）
高速公路的吞吐量就是每小时能通过多少辆车——车道越多、车速越快，吞吐量越高。

### 具体示例
```
# 吞吐量的常见表示方式

# 1. 请求数/秒（Requests per second）
Throughput = 500 req/s

# 2. 事务数/秒（Transactions per second）
Throughput = 200 TPS

# 3. 比特数/秒（Bits per second）- 网络场景
Throughput = 1 Gbps

# 4. 字节数/秒（Bytes per second）- 文件传输场景
Throughput = 100 MB/s

# 吞吐量与并发数的关系
# 低并发时：吞吐量随并发增加线性增长
# 达到瓶颈时：吞吐量不再增长
# 超过极限时：吞吐量可能下降（系统过载）

# 示例曲线：
# 并发数:   10   50  100  200  500  1000
# 吞吐量:  100  500  800  800  750   600
#                     ^-- 瓶颈点
```

### 为什么需要它
吞吐量是评估系统整体处理能力的关键指标，与响应时间、并发数一起构成性能测试的三大核心指标。

### 与相关术语的对比和区分
- **吞吐量 vs QPS**：吞吐量是更广义的概念，QPS 是其在查询场景的具体表现
- **吞吐量 vs 响应时间**：两者通常成反比——吞吐量越高，响应时间可能越长

## JMeter 使用

### 一句话定义（大白话）
JMeter 通过线程组模拟用户、取样器发送请求、监听器收集结果、断言验证正确性、定时器控制节奏，组成完整的性能测试方案。

### 通俗类比（生活场景）
就像导演拍戏：线程组是演员阵容，取样器是剧本台词，监听器是摄像机，断言是质检员，定时器是导演的节奏控制。

### 具体示例

**JMeter 测试计划结构：**
```
测试计划
├── 线程组（Thread Group）
│   ├── 配置元件
│   │   ├── HTTP请求默认值
│   │   └── HTTP信息头管理器
│   ├── 取样器（Sampler）
│   │   ├── HTTP请求 - 登录
│   │   ├── HTTP请求 - 查询商品
│   │   └── HTTP请求 - 下单
│   ├── 断言（Assertion）
│   │   ├── 响应断言
│   │   └── JSON断言
│   ├── 定时器（Timer）
│   │   └── 固定定时器（思考时间）
│   └── 监听器（Listener）
│       ├── 聚合报告
│       ├── 查看结果树
│       └── 响应时间图
```

**线程组配置：**
```
线程数（Number of Threads）：100    # 模拟100个用户
Ramp-Up 时间（秒）：10              # 10秒内逐步增加到100个用户
循环次数：10                        # 每个线程执行10次
调度器：
  持续时间（秒）：300               # 总共运行5分钟
```

**JMeter CLI 运行：**
```bash
# 非 GUI 模式运行（生产推荐）
jmeter -n -t test-plan.jmx \
    -l results.jtl \
    -e -o ./report

# 分布式压测（多台机器协同）
jmeter -n -t test-plan.jmx \
    -R slave1.example.com,slave2.example.com \
    -l results.jtl
```

**JMeter 聚合报告解读：**
```
Label        # Samples  Average  Median  P90     P95     P99     Error%  Throughput
登录          1000       120     100     180     250     400     0.00%   85.2/sec
查询商品      1000        80      60     120     180     300     0.00%   120.5/sec
下单          1000       250     200     380     500     800     0.10%   42.3/sec
TOTAL         3000       150     120     230     320     550     0.03%   248.0/sec
```

### 为什么需要它
JMeter 是性能测试的行业标准，免费开源，支持多种协议（HTTP、TCP、JDBC等），社区资源丰富。

## K6（现代负载测试工具）

### 一句话定义（大白话）
k6 是用 JavaScript 编写的现代负载测试工具，语法简洁、性能优秀，支持开发者友好的测试脚本编写。

### 通俗类比（生活场景）
如果 JMeter 是功能齐全但界面老旧的"老式计算器"，k6 就是界面现代、操作直观的"科学计算器"——功能同样强大，但用起来更顺手。

### 具体示例

```javascript
// k6 负载测试脚本
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate, Trend } from 'k6/metrics';

// 自定义指标
const errorRate = new Rate('errors');
const loginDuration = new Trend('login_duration');

// 测试配置
export const options = {
    stages: [
        { duration: '30s', target: 20 },   # 30秒内增加到20个用户
        { duration: '1m', target: 20 },     # 保持20个用户1分钟
        { duration: '30s', target: 50 },    # 30秒内增加到50个用户
        { duration: '1m', target: 50 },     # 保持50个用户1分钟
        { duration: '30s', target: 0 },     # 30秒内降到0
    ],
    thresholds: {
        http_req_duration: ['p(95)<500'],  # 95%请求响应时间小于500ms
        errors: ['rate<0.01'],              # 错误率小于1%
    },
};

export default function () {
    # 1. 登录
    const loginRes = http.post('https://api.example.com/login', 
        JSON.stringify({ username: 'testuser', password: 'testpass' }),
        { headers: { 'Content-Type': 'application/json' } }
    );
    
    check(loginRes, {
        '登录状态码为200': (r) => r.status === 200,
        '登录返回token': (r) => JSON.parse(r.body).token !== undefined,
    });
    errorRate.add(loginRes.status !== 200);
    loginDuration.add(loginRes.timings.duration);

    const token = JSON.parse(loginRes.body).token;
    const params = { headers: { Authorization: `Bearer ${token}` } };

    sleep(1);

    # 2. 查询商品列表
    const productsRes = http.get('https://api.example.com/products', params);
    check(productsRes, {
        '商品列表状态码为200': (r) => r.status === 200,
        '商品列表不为空': (r) => JSON.parse(r.body).length > 0,
    });

    sleep(2);

    # 3. 创建订单
    const orderRes = http.post('https://api.example.com/orders',
        JSON.stringify({ productId: 1, quantity: 2 }),
        { ...params, headers: { ...params.headers, 'Content-Type': 'application/json' } }
    );
    check(orderRes, {
        '下单状态码为201': (r) => r.status === 201,
    });
}

# 运行命令
# k6 run script.js
# k6 run --out json=results.json script.js
# k6 cloud script.js  # 云端执行
```

### 为什么需要它
k6 用 JavaScript 编写脚本，对前端开发者友好，性能比 JMeter 更好，是新一代性能测试工具的代表。

## Locust（Python 负载测试工具）

### 一句话定义（大白话）
Locust 是用 Python 编写的负载测试工具，用 Python 代码定义用户行为，支持分布式测试，特别适合 Python 技术栈。

### 通俗类比（生活场景）
就像用 Python 写一个"虚拟人群模拟器"——每个虚拟用户都是一个 Python 对象，按照你写的代码行动。

### 具体示例

```python
# locustfile.py
from locust import HttpUser, task, between, events
import json

class WebsiteUser(HttpUser):
    # 用户行为定义
    wait_time = between(1, 3)  # 每次操作间隔1-3秒
    host = "https://api.example.com"

    def on_start(self):
        """用户启动时执行（登录）"""
        response = self.client.post("/login", json={
            "username": "testuser",
            "password": "testpass"
        })
        self.token = json.loads(response.text)["token"]
        self.client.headers.update({"Authorization": f"Bearer {self.token}"})

    @task(3)  # 权重为3，执行频率更高
    def view_products(self):
        """查看商品列表"""
        with self.client.get("/products", name="/products", catch_response=True) as response:
            if response.status_code == 200:
                response.success()
            else:
                response.failure(f"状态码错误: {response.status_code}")

    @task(1)  # 权重为1
    def create_order(self):
        """创建订单"""
        self.client.post("/orders", json={
            "productId": 1,
            "quantity": 2
        }, name="/orders")

    @task(2)
    def view_profile(self):
        """查看个人信息"""
        self.client.get("/profile", name="/profile")

# 运行命令
# locust -f locustfile.py --host=https://api.example.com
# 然后访问 http://localhost:8089 配置并发数和启动速率
```

**分布式模式运行：**
```bash
# 主节点
locust -f locustfile.py --master --host=https://api.example.com

# 从节点（多台机器）
locust -f locustfile.py --worker --master-host=192.168.1.100
```

### 为什么需要它
Locust 对 Python 开发者友好，代码即配置，分布式部署简单，是 Python 技术栈的首选性能测试工具。

性能测试报告是测试结果的汇总，包含响应时间、吞吐量、错误率等关键指标，帮你判断系统性能是否达标。

### 通俗类比（生活场景）
就像体检报告——各项指标（血压、血糖、心率）综合反映你的健康状况，需要整体看而不是只看某一项。

报告是性能测试的交付物，是性能优化决策的依据，也是性能基线对比的基础。

- **性能报告 vs 性能监控**：报告是事后分析，监控是实时观察

## 性能瓶颈分析

### 一句话定义（大白话）
性能瓶颈分析是找出系统中限制性能的薄弱环节——可能是 CPU、内存、网络、磁盘 IO 或数据库。

### 通俗类比（生活场景）
就像木桶效应——水位取决于最短的那块木板。性能瓶颈分析就是找到那块最短的木板。

### 具体示例
```
瓶颈排查路径：

响应时间过长
├── CPU 使用率高（>80%）
│   ├── 计算密集型代码 → 优化算法、增加缓存
│   └── 线程频繁切换 → 减少线程数、优化锁
├── 内存使用率高（>85%）
│   ├── 内存泄漏 → 检查未释放的对象
│   ├── 大对象 → 优化数据结构
│   └── GC 频繁 → 调整 JVM 参数
├── 磁盘 IO 高
│   ├── 频繁读写 → 增加缓存、批量操作
│   └── 日志过多 → 异步写入、减少日志级别
├── 网络带宽不足
│   ├── 大文件传输 → 压缩、分片
│   └── 请求过多 → 减少请求数、使用 CDN
└── 数据库慢查询
    ├── SQL 未优化 → 添加索引、重写 SQL
    ├── 连接池不足 → 增加连接数
    └── 锁竞争 → 优化事务粒度

常用诊断命令：
  # Linux
  top / htop          # CPU、内存概览
  iostat -x 1         # 磁盘 IO
  vmstat 1            # 内存、IO、CPU 综合
  netstat -an         # 网络连接
  sar -n DEV 1        # 网络流量
  
  # Java
  jstack <pid>        # 线程堆栈
  jmap -heap <pid>    # 堆内存概览
  jstat -gcutil <pid> 1000  # GC 统计
  
  # 数据库
  SHOW PROCESSLIST;   # MySQL 当前连接
  EXPLAIN SELECT ...; # SQL 执行计划
```

### 为什么需要它
找到瓶颈才能对症下药，盲目优化可能浪费资源甚至适得其反。

### 与相关术语的对比和区分
- **瓶颈分析 vs 性能测试**：性能测试发现问题，瓶颈分析定位原因
- **瓶颈分析 vs 性能优化**：瓶颈分析是诊断，性能优化是治疗

## 性能优化思路

### 一句话定义（大白话）
性能优化是通过代码优化、架构调整、配置调优等手段提升系统性能的系统化方法。

### 通俗类比（生活场景）
就像给汽车做保养——换机油（代码优化）、升级发动机（架构调整）、调整轮胎气压（配置调优），让车跑得更快更省油。

### 具体示例
```
性能优化分层策略：

┌─────────────────────────────────────────────┐
│ 第1层：代码优化（投入小、见效快）           │
│   - 减少不必要的计算                        │
│   - 优化循环和递归                          │
│   - 使用高效的数据结构                      │
│   - 避免重复计算（缓存结果）                │
├─────────────────────────────────────────────┤
│ 第2层：缓存优化（效果显著）                 │
│   - 本地缓存（Caffeine、Guava Cache）       │
│   - 分布式缓存（Redis、Memcached）          │
│   - CDN 缓存                               │
│   - 数据库查询缓存                          │
├─────────────────────────────────────────────┤
│ 第3层：数据库优化（常见瓶颈）               │
│   - 添加合适的索引                          │
│   - 优化 SQL 语句                           │
│   - 读写分离                               │
│   - 分库分表                               │
├─────────────────────────────────────────────┤
│ 第4层：架构优化（投入大、根本性解决）       │
│   - 异步处理（消息队列）                    │
│   - 服务拆分（微服务）                      │
│   - 负载均衡                               │
│   - 水平扩展                               │
└─────────────────────────────────────────────┘
```

**代码优化示例：**
```python
# 优化前：每次都查询数据库
def get_user_orders(user_id):
    orders = db.query("SELECT * FROM orders WHERE user_id = ?", user_id)
    return orders

# 优化后：增加缓存
from functools import lru_cache

@lru_cache(maxsize=128)
def get_user_orders(user_id):
    orders = db.query("SELECT * FROM orders WHERE user_id = ?", user_id)
    return orders
```

### 为什么需要它
性能优化是系统上线前和运行中的必要环节，直接影响用户体验和系统稳定性。

## 压测注意事项

### 一句话定义（大白话）
压测注意事项包括预热、数据隔离、环境独立等关键实践，确保压测结果准确可靠。

### 通俗类比（生活场景）
就像测速前要热身——运动员比赛前要热身，系统压测前也要"预热"，才能测出真实性能。

### 具体示例
```
压测注意事项清单：

1. 预热（Warm-up）
   ─────────────────────────────────
   问题：系统首次请求需要加载配置、建立连接等
   解决：正式压测前先发送一批请求预热
   
   JMeter 配置：
   线程组 → 预热线程数：10
   线程组 → 预热循环次数：5
   
   k6 配置：
   stages: [
     { duration: '1m', target: 10 },  # 预热阶段
     { duration: '5m', target: 100 }, # 正式压测
   ]

2. 数据隔离
   ─────────────────────────────────
   问题：压测数据污染生产数据
   解决：使用独立的测试数据库和测试数据
   
   # 使用唯一前缀区分测试数据
   test_order_id = f"TEST_{uuid.uuid4()}"
   
   # 压测后清理
   def teardown():
       db.execute("DELETE FROM orders WHERE id LIKE 'TEST_%'")

3. 环境独立
   ─────────────────────────────────
   问题：测试环境与生产环境配置差异
   解决：尽量使用与生产一致的配置
   
   docker-compose.prod-mirror.yml:
     services:
       app:
         image: app:prod  # 使用生产镜像
         environment:
           - DB_HOST=prod-db.example.com  # 连接生产数据库（只读）
           - CACHE_HOST=prod-redis.example.com

4. 其他注意事项
   ─────────────────────────────────
   - 网络隔离：压测流量不要影响生产网络
   - 监控完整：压测期间监控 CPU、内存、IO、网络
   - 结果对比：与历史基线对比，识别性能退化
   - 分批执行：避免一次性压垮系统
   - 错误处理：记录所有错误，分析失败原因
```

### 为什么需要它
不注意这些事项，压测结果可能不准确，甚至对生产环境造成影响。

### 与相关术语的对比和区分
- **预热 vs 正式压测**：预热是准备阶段，正式压测是数据采集阶段
- **数据隔离 vs 数据清理**：数据隔离是防止污染，数据清理是事后恢复

## 工具选型指南

### 性能测试工具对比
| 特性 | JMeter | k6 | Locust |
|------|--------|-----|--------|
| 语言 | Java/GUI | JavaScript | Python |
| 学习曲线 | 中等 | 低 | 低 |
| 性能 | 一般 | 优秀 | 良好 |
| 分布式 | 支持 | 支持（云） | 支持 |
| 可视化 | 丰富 | 一般 | 一般 |
| 扩展性 | 插件丰富 | 扩展库 | Python 生态 |
| 适用场景 | 企业级、复杂场景 | 现代应用、DevOps | Python 项目 |

### 工具选型决策
```
你的技术栈是什么？
├── Java 企业级 → JMeter（行业标准、功能全面）
├── JavaScript/TypeScript → k6（语法友好、性能优秀）
├── Python 项目 → Locust（Python 原生、易于集成）
├── 需要 GUI → JMeter
├── 需要 CI/CD 集成 → k6（CLI 友好）
└── 需要云端执行 → k6 Cloud / Blazemeter
```

## 总结

| 概念 | 核心价值 | 关键指标 |
|------|----------|----------|
| 性能测试类型 | 全面评估系统性能 | 负载/压力/稳定性/容量 |
| QPS | 衡量处理能力 | 每秒请求数 |
| TPS | 衡量事务处理能力 | 每秒事务数 |
| 并发用户数 | 衡量并发承载 | 同时在线用户数 |
| 响应时间 | 衡量用户体验 | 平均/P90/P95/P99 |
| 吞吐量 | 衡量系统容量 | 成功处理的请求量 |
| JMeter | 企业级性能测试 | 功能全面、协议丰富 |
| k6 | 现代性能测试 | JavaScript、高性能 |
| Locust | Python 性能测试 | Python 原生、易集成 |
| 瓶颈分析 | 定位性能问题 | CPU/内存/IO/网络/DB |
| 性能优化 | 提升系统性能 | 代码/缓存/数据库/架构 |
| 压测注意事项 | 确保结果准确 | 预热/数据隔离/环境独立 |
