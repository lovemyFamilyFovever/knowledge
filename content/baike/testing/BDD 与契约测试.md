# BDD 与契约测试

> 📌 **导航**：本文是 **BDD 与契约测试** 词条，属 [[01 - 测试基础]] 子词条。TDD 见 [[测试驱动开发]]、集成协作见 [[集成测试]]。

## 定义

**一句话定义：** BDD 用"Given-When-Then"自然语言描述系统行为，让业务、开发、测试共享同一份"活文档"式用例；契约测试验证服务间的接口约定是否一致——消费者期望的字段/状态，提供者是否真的按约提供。

**通俗类比：** BDD 像菜谱（人人看得懂的"备料→下锅→出锅"）；契约测试像甲乙双方的合同验收（你要的房子标准，交付方是否达标），不必真把整栋楼一起搬来验。

## 为什么需要它

跨角色沟通有鸿沟：需求写一遍、测试另写一遍、理解各跑偏。BDD 让"规格即测试即文档"，先对齐行为再实现。微服务下服务多、独立部署，全量端到端集成测试又慢又脆；契约测试把"上下游接口兼容"抽成可独立跑的约定校验，接口一改破坏消费方时立刻暴露，比大集成轻量得多。

## 核心机制

- **BDD 结构**：Feature/Scenario + `Given(前置) When(动作) Then(结果)`，写进 `.feature`；再绑 Step Definitions（behave/Cucumber/Jest-cucumber）把自然语言映射到代码。与 TDD 的"红-绿-重构"是互补（TDD 管内、BDD 管行为对齐）。
- **消费者驱动契约（CDC）**：消费者声明期望（Pact：给定状态→请求→应得响应）→ 生成契约文件 → 提供者对契约跑"提供者验证"→ 确保响应匹配；无需同时起双方服务。
- **对齐活文档**：通过的 BDD 场景本身就是可读、可执行的需求记录。

## 具体示例

```gherkin
Feature: 用户注册
  Scenario: 邮箱已存在
    Given 用户在注册页
    When  输入已注册邮箱并点"注册"
    Then  显示"该邮箱已被注册"
```
```python
pact = Consumer('Order').has_pact_with(Provider('User'))
pact.given('用户1存在').upon_receiving('取用户') \
     .with_request('GET','/api/users/1').will_respond_with(200, body={'id':1,'name':'张三'})
```

## 何时用与何时不用

- **用**：BDD 适合行为需求需要跨职能对齐、领域规则复杂、要把验收标准变成自动化用例处；契约测试适合微服务/多团队协作、服务独立部署、想避免脆弱的全量端到端联调处。
- **不用**：BDD 别为所有琐碎技术逻辑写 Gherkin（步骤维护成本高、离代码越远越易漂移）；契约测试只管接口形状，不验业务/数据端到端正确性，关键流程仍需 [[E2E 测试]] 兜底。

## 优劣与代价

✅ BDD 让规格=测试=文档三合一、减少误解、便于非技术方参与验收。
✅ 契约测试把服务兼容验证去中心化、快且可独立跑，防"接口悄悄破坏下游"。
⚠️ BDD 步骤定义与特性文件维护有成本、语言隔两层易失真、误用会变成"给简单函数写剧本"。
⚠️ 契约只覆盖约定字段，语义/业务错误测不到；契约版本与提供者验证的 CI 接线需经营。

## 与相关概念的区别

- **BDD vs TDD**：BDD 面向行为与团队沟通（自然语言、全角色）；TDD 面向实现正确性（代码、红绿重构，见 [[测试驱动开发]]）。
- **契约测试 vs 集成测试**：契约验"接口协议兼容"、双方可独立跑；集成验"真协作起来对不对"（[[集成测试]]）。
- **BDD vs 验收测试**：BDD 是常用手法，其场景天然可作 UAT 输入（见 [[验收测试与探索性测试]]）。

## 常见误区

- 用了 Gherkin 文件就等于做了 BDD、团队就一定对齐了。
- 契约测试通过，就能替代服务之间的端到端集成测试。
- BDD 应该给每一个小技术方法都写一份特性文件。

## 面试速答

> 🎯 BDD=Given-When-Then 自然语言写行为，规格即测试即活文档、跨角色对齐，再绑步骤定义实现，与 TDD 互补(外对齐/内实现)。契约测试=消费者驱动(Pact)声明接口期望、提供者独立验证契约兑现，微服务下比全量集成更轻、防接口破坏下游；只验形状不验业务，关键流程仍需 E2E。
