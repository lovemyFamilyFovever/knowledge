# 混沌工程

> 📌 **导航**：本文是 **混沌工程** 词条，属于 testing 术语集。相关枢纽：[[01 - 测试基础]]、[[02 - 测试工具]]、[[03 - 性能测试]]、[[单元测试]]、[[性能测试]]。

## 定义

**一句话定义：** 混沌工程（Chaos Engineering）是通过在分布式系统上主动、受控地注入真实故障来做实验，观察并提升系统在动荡条件下的整体韧性的工程实践。

**通俗类比：** 像消防演习——不是等真着火才手忙脚乱，而是平时主动点一把可控的小火，看警报响不响、通道堵不堵、疏散顺不顺，把"意外"提前变成"演练过的已知"。

## 为什么需要它

大规模分布式系统里，服务器宕机、网络抖动、依赖超时是迟早会发生的事。与其让它在凌晨把生产搞挂，不如平时在受控条件下主动制造这些故障，提前暴露隐藏的单点、缺失的降级、失灵的告警——混沌工程的目标正是让系统"对故障免疫"，把韧性从祈祷变成可验证的能力。

## 做法

核心原则（混沌工程宣言）：

1. 建立稳态假设——先用正常时的指标（成功率、延迟）定义"健康基线"。
2. 引入真实事件——服务器宕机、网络延迟、磁盘满等贴近现实的变化。
3. 在生产 / 准生产运行——真实环境才有真实变量。
4. 持续自动化运行——实验常态化，而非一次性。
5. 最小化爆炸半径——控制影响面，别把演练变成事故。

常见故障注入手段：

| 类型 | 工具 | 示例 |
|------|------|------|
| 进程终止 | kill -9 | 随机杀 Pod |
| 网络延迟 / 丢包 | tc / netem | +100ms、丢包 50% |
| 磁盘满 / CPU 满载 | dd / stress | 写满盘、打满 CPU |
| 依赖故障 | 模拟 / 代理 | 下游超时 |

## 具体示例

Netflix 的混沌工具族是经典范例：Chaos Monkey 随机杀实例、Latency Monkey 注入延迟、Chaos Kong 模拟整个区域故障；组织层面则用 GameDay 演练把团队一起拉进来：

```
准备 → 演练(注入故障、观察系统、团队响应) → 复盘(改进点)
```

## 何时用与何时不用

- **用**：分布式 / 微服务系统验证高可用与容灾、上线前测降级与告警、团队应急协同演练。
- **不用**：在无任何监控、连稳态都无法度量的系统上盲做（等于制造事故）；把"生产随手动脚 reboot"当成混沌工程。

## 优劣与代价

✅ 主动暴露隐藏缺陷，把故障经验沉淀为韧性。
✅ 验证监控 / 告警 / 自动恢复是否真的起作用。
⚠️ 有真实风险，须严控爆炸半径并具备快速中止能力。
⚠️ 需要成熟的度量与自动化支撑，门槛较高。

## 与相关概念的区别

- **故障注入 vs 混沌工程**：故障注入是"手段"；混沌工程是以稳态假设驱动、在生产受控、持续运行的"实验方法论"，注入只是其中一步。
- **混沌工程 vs 性能测试**：性能测试问"扛不扛得住负载"，混沌工程问"坏了会不会连锁崩、能否自恢复"。
- **混沌工程 vs 灾备演练**：灾备偏机房 / 区域级预案，混沌工程把小粒度故障变成日常实验。

## 常见误区

- 混沌工程就是随手 reboot 机器、搞搞破坏看会不会挂。
- 在测试环境做做故障注入演练就等于混沌工程了。
- 做过一次混沌实验，系统就从此高可用、不用再做了。

## 面试速答
