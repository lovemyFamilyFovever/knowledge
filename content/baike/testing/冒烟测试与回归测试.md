# 冒烟测试与回归测试

> 📌 **导航**：本文是 **冒烟测试与回归测试** 词条，属 [[01 - 测试基础]] 子词条。验收类见 [[验收测试与探索性测试]]。

## 定义

**一句话定义：** 冒烟测试是构建后先跑的一小组快速检查，确认"最核心的功能活着没、值不值得继续测"；回归测试是改动后重跑既有测试，确认"新改动没把原来好的功能弄坏"。

**通俗类比：** 冒烟像新电器通电看"亮不亮"；回归像换了汽车新零件后，再检查刹车、灯光这些原本正常的没被搞坏。

## 为什么需要它

不做冒烟，可能花了半天跑详尽测试才发现服务根本没起来，白白浪费时间——先用最小成本判"这版能不能测"。不做回归，软件改动极易引发"修好一处、崩了另一处"的连锁副作用；回归是"改新的、旧的还得能用"的安全网。

## 核心机制

- **冒烟（Smoke）**：覆盖关键路径（登录、健康检查、下单主流程）的极小子集，部署后/CI 前置阶段先跑，失败即打回、阻断后续。
- **回归（Regression）**：把历史用例沉淀成可重复跑的测试集（常即单元+集成+E2E 的自动化集合），每次改动后重放，任何原通过用例转红即"回归缺陷"。
- **触发时机**：冒烟在每次部署/新构建；回归在代码修改后、发版前全量跑。
- **与自动化**：二者几乎都靠 CI 自动化；回归集越大越要分层执行（快子集先跑、全量夜间跑）。见 [[测试金字塔与覆盖率]]。

## 具体示例

```python
def test_smoke_health():           # 冒烟：服务活着吗
    assert requests.get('/api/health').status_code == 200

def test_discount_regression():    # 回归：老逻辑没被改坏
    assert calculate_discount(100, 0.1) == 90
```

## 何时用与何时不用

- **用**：每次构建/部署都跑冒烟作"准入闸"；每次改动、尤其发版前跑回归防副作用。
- **不用**：别把冒烟做成大而全（那就成回归了）——它贵在"快、窄"；回归也别盲目全跑拖慢反馈，按风险与变更范围选择要重放的子集。

## 优劣与代价

✅ 冒烟低成本快速止损、防止在坏构建上浪费时间；回归给"改动安全"提供持续证据、支撑大胆重构。
✅ 自动化后成为 CI 门禁的核心两道。
⚠️ 冒烟覆盖窄，过≠功能正确，只说明"没当场崩"。
⚠️ 回归集会随功能增长膨胀、维护成本上升，且有"从没被测过的老代码"仍可能悄悄坏。

## 与相关概念的区别

- **冒烟 vs 回归**：冒烟问"这版能不能用（核心可用）"、快而窄；回归问"旧功能有没有被改坏"、广而全。
- **回归 vs 验收（UAT）**：回归由开发/测、关注功能正确；验收由业务方、关注需求满足（[[验收测试与探索性测试]]）。
- **冒烟 vs 健全性检查**：冒烟广覆盖核心面，sanity 是对相关小区域的深挖，二者常配合。

## 常见误区

- 冒烟测试通过，就代表这一版功能都正确了。
- 回归测试只要跑一次通过，以后就不用再跑了。
- 冒烟和回归是一回事，只是叫法不同。

## 面试速答

> 🎯 冒烟=构建/部署后先跑的核心功能小集，判"能不能用、值不值得继续测"，快而窄、失败即打回。回归=改动后重放既有测试集，防"改一处坏另一处"，广而全、发版前必跑。二者是 CI 的准入与防护两道，自动化维护；冒烟过≠功能对、回归集会膨胀需分层。
