# 单元测试框架

> 📌 **导航**：本文是 **单元测试框架** 词条，属 [[02 - 测试工具]] 子词条。E2E 浏览器工具见 [[Playwright 与 Cypress]]、替身见 [[断言与测试替身]]。

## 定义

**一句话定义：** 单元测试框架是跑"函数/类级测试"的工具族——提供发现与组织用例、断言、夹具（fixture/setup-teardown）、参数化与覆盖率集成的基础设施；跨语言各有代表：Python 的 pytest、Java 的 JUnit 5、JS 的 Jest 与 Mocha+Chai。

**通俗类比：** 像不同品牌的"实验台"：都能摆试剂（用例）、比色（断言）、控制变量（fixture），只是操作手感与配套（mock、快照、并行）各异。

## 为什么需要它

没有框架，测试就是一堆散落脚本，无法自动发现、批量运行、报告结果、集成进 CI。框架把"写-组织-跑-断言-报告-隔离依赖"标准化，让单元测试可持续、可重复、可回归（见 [[冒烟测试与回归测试]]），是金字塔最底层大量快测试的工程支撑（见 [[测试金字塔与覆盖率]]）。

## 核心机制

- **共同件**：用例发现、`断言库`、`fixture`/setup-teardown（准备与清理测试态）、参数化（一份逻辑多组输入）、mock/打桩集成、覆盖率报告、并行执行。
- **pytest**：`test_*.py` 自动发现，裸 `assert`（失败给详细差异）、`@pytest.fixture` 注入依赖、`parametrize` 表驱动、插件生态（cov/mock/xdist 并行）。
- **JUnit 5**：`@Test`/`@ParameterizedTest`、`Assertions.*`、`@BeforeEach/@AfterEach`、扩展模型（DI、并行）。
- **Jest**：`describe/it`、`expect().toBe()`、内建 mock/spy、快照测试、`beforeEach`；配 Mocha 时断言常交给 Chai（`expect/should`）。
- **Mocha+Chai**：Mocha 管跑与结构、Chai 管断言风格，灵活组合但需自配断言/覆盖率/mock。

## 具体示例

```python
import pytest
@pytest.mark.parametrize("a,b,exp", [(2,3,5),(-1,1,0),(0,0,0)])
def test_add(a,b,exp):            # pytest 表驱动：一个逻辑多组输入
    assert a + b == exp
```

## 何时用与何时不用

- **用**：项目按语言选其主流单元框架即可（Python→pytest，Java→JUnit5，前端→Jest）；共享逻辑/算法/纯函数用参数化覆盖边界。
- **不用**：别在单元框架里塞真实数据库/网络（那是 [[集成测试]] 的活，用 [[断言与测试替身]] 隔离）；浏览器交互别硬写单元，交给 [[Playwright 与 Cypress]]。框架选型跟语言与团队栈走，别跨语言强推。

## 优劣与代价

✅ 自动发现+批量跑+报告+CI 门禁，让单元测试可回归、可规模化。
✅ fixture/参数化/快照等能力把重复与边界覆盖成本压到很低。
⚠️ 各框架断言/mock 心智不一，跨栈迁移有学习成本；过度依赖快照易"改啥都更新快照"而失真。
⚠️ 框架本身不决定测试价值——垃圾用例照跑不误（见 [[测试金字塔与覆盖率]]）。

## 与相关概念的区别

- **测试框架 vs 断言库**：框架管"怎么组织跑"，断言库管"怎么判对错"（Chai 可独立）；Jest 则二者内建。
- **单元框架 vs E2E 工具**：前者测函数类、无真依赖；后者驱动浏览器验全流程（[[Playwright 与 Cypress]]）。
- **mock 内置 vs 外挂**：Jest/Mockito 自带打桩，pytest/JUnit 靠插件或库（见 [[断言与测试替身]]）。

## 常见误区

- 单元测试框架该顺手把真实数据库也连上一起测，越真越好。
- 快照测试更新一下没风险，反正 CI 绿了。
- 换断言风格（Chai expect vs assert）会改变测试的实际覆盖能力。

## 面试速答

> 🎯 单元框架=跑函数级测试的基础设施：发现+断言+fixture/参数化+mock+覆盖率+CI。代表 pytest(裸assert/parametrize)、JUnit5(注解+参数化)、Jest(内建mock/快照)、Mocha+Chai。按语言选主流、别在单元层连真依赖。
