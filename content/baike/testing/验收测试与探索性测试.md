# 验收测试与探索性测试

> 📌 **导航**：本文是 **验收测试与探索性测试** 词条，属 [[01 - 测试基础]] 子词条。自动化防护见 [[冒烟测试与回归测试]]。

## 定义

**一句话定义：** 验收测试（UAT）由业务方/客户执行，确认软件满足业务需求、决定"收不收货"；探索性测试由测试者同时进行学习、用例设计与执行，靠经验和直觉灵活挖掘脚本没覆盖的问题。

**通俗类比：** UAT 像业主按合同逐项验房签字；探索性测试像侦探带着"找茬"心态实地勘查，不按固定清单走。

## 为什么需要它

技术测试全绿 ≠ 做对了东西——UAT 确保"交付的是需求方真正要的"，把"做对事"和"把事做对"分开。而脚本化测试只查"你想到的场景"，探索性测试补上"没人预料的异常"（边界、乱序、误操作），专抓隐藏 bug，是自动化覆盖不到的最后一道人类判断。

## 核心机制

- **UAT 输入**：以业务场景/验收标准（AC，见 [[需求梳理与优先级]]）为准，常用 Given-When-Then 描述；由客户/产品/业务代表在类生产环境执行，通过即签署验收。
- **探索性测试**：以"测试章程（charter）+ 时间盒 session"驱动——限定目标与时长的自由探索，边测边学边设计；结果记录为发现与后续用例线索。
- **互补**：UAT 是"确认满足需求"的关口；探索性是"发现未知缺陷"的取证。两者都高度依赖人的判断，不易全自动化。

## 具体示例

```gherkin
Feature: 下单
  Scenario: 客户下单成功        # 验收标准，业务方核对
    Given 客户已登录
    When  选择商品并完成支付
    Then  显示"订单创建成功"且库存减 1
```
```
探索章程：60min 测购物车边界
发现：数量输入 -1 → 总价变负数；连点"添加" → 重复入库
```

## 何时用与何时不用

- **用**：交付前、需求方要拍板时做 UAT；对复杂/易变/高价值功能、或自动化已覆盖主干后，安排探索性 session 抓异常与体验问题。
- **不用**：别把 UAT 变成"跑一遍技术测试"（它看的是业务符合度）；探索性测试不能替代自动化回归——它不可精确重放，发现的好路径应回补成脚本。

## 优劣与代价

✅ UAT 对齐真实业务期望、降低"做出来却不是要的"的返工；探索性发现脚本化测不到的隐藏 bug，快且灵活。
✅ 两者都把人的判断纳入质量闭环。
⚠️ UAT 依赖需求方配合与时机，易拖慢交付、标准不清时反复扯皮。
⚠️ 探索性高度依赖测试者经验、结果不可复现、难度量，需靠章程与记录约束。

## 与相关概念的区别

- **验收测试 vs 系统测试**：系统测试验"功能对不对"（技术视角），UAT 验"满足业务需求吗"（业务视角）。
- **探索性 vs 脚本化**：设计/执行/学习同时发生、可即兴 vs 预先写死步骤按图执行。
- **探索性 vs 冒烟**：冒烟快速验核心可用、可自动；探索性深入挖异常、靠人。

## 常见误区

- 所有自动化测试通过就等于通过了用户验收。
- 探索性测试就是"随便点点"，不需要目标、记录和产出。
- UAT 应该由开发自己跑一遍代替业务方确认。

## 面试速答

> 🎯 验收测试(UAT)=业务方按验收标准/场景确认"满足需求、能不能收货"，看业务符合度、非技术跑测；探索性测试=测试者在学习·设计·执行同步中进行、用 charter+时间盒靠经验挖脚本没覆盖的隐藏 bug，不可精确重放、发现好路径应回补自动化。二者补技术测试的"做对事"和"想到之外的错"。
