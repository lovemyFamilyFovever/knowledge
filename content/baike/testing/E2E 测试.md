# E2E 测试

> 📌 **导航**：本文是 **E2E 测试** 词条，属于 testing 术语集。相关枢纽：[[01 - 测试基础]]、[[02 - 测试工具]]、[[软件测试完全指南]]。

## 定义

**一句话定义：** E2E（End-to-End，端到端）测试是从真实用户入口出发、驱动完整技术栈（浏览器/App → 前端 → 接口 → 服务 → 数据库 → 第三方）跑通一整条业务流程的自动化测试，验证的是"系统作为整体能不能把这件事办成"，而非某个模块内部对不对。

**通俗类比：** 像顾客亲自走一遍完整购物流程——进店、挑货、结账、付款、拿货，每一环都要真的顺畅；而不是分别检查收银机、货架、库存账本各自是否正常。

## 为什么需要它

单元测试与集成测试都在"局部真实"上打转：依赖被替身挡掉、组件被单独拼装。可用户不按模块使用产品，他们只走完整流程。配置错误、跨服务契约漂移、鉴权与跳转链路断裂、前端状态与后端数据不一致——这类缺陷只在整条链路接通时才暴露，且往往最致命（用户直接下不了单）。E2E 是唯一站在用户视角验收的一层，也是发布前"业务流真的能跑"的最后一道证据。

## 做法

- **只挑关键业务流**：登录、下单、支付、退款这类断了就停摆的主干路径。E2E 贵，不能拿来铺覆盖率。
- **比例压在金字塔顶层**：Mike Cohn 于 2009 年提出的测试金字塔给出的经验配比是单元约 70% / 集成约 20% / E2E 约 10%；倒过来堆 E2E 就是"冰淇淋锥"反模式，结果是跑得慢、反馈迟、维护贵、还经常假失败。
- **用稳定定位器**：优先 `data-testid` 一类专为测试预留的属性，不要绑 CSS 类名或文案——那是 UI 一改就碎的主因。
- **数据自洽**：每条用例自建自清数据，不依赖别的用例留下的状态；能走接口造数就别用 UI 点。
- **显式等待而非 sleep**：靠框架自动等待或轮询断言目标，固定 `sleep` 既慢又不稳。
- **失败要能自证**：截图、录像、trace、控制台与网络日志一并归档，否则每次失败都得人工复跑。

## 具体示例

一条 Playwright 端到端用例：登录后加购、改数量、下单，断言落在用户能看见的结果上。

```javascript
test('完整下单流程', async ({ page }) => {
  await page.goto('/products');
  await page.locator('[data-testid="product-card"]').first()
        .locator('[data-testid="add-to-cart"]').click();
  await expect(page.locator('[data-testid="cart-badge"]')).toHaveText('1');
  await page.click('[data-testid="place-order"]');
  await expect(page).toHaveURL(/\/orders\/[a-z0-9]+/);
  await expect(page.locator('[data-testid="order-status"]')).toHaveText('待支付');
});
```

| 要素 | 说明 |
|------|------|
| 入口 | 真实浏览器 + 真实部署栈，不打桩 |
| 定位 | `data-testid` 稳定属性，避开样式与文案 |
| 断言 | 落在用户可见结果（角标数字、跳转 URL、订单状态） |
| 数据 | 用例内自建自清，不跨用例复用状态 |

## 何时用与何时不用

- **用**：验收关键业务流、发布前回归、跨团队/跨服务集成后的整体确认、验证鉴权与跳转链路、给非技术干系人一份"能跑"的可信证据。
- **不用**：别用它验证分支逻辑与边界值（那是单元测试的活，快且便宜）；别追求 E2E 覆盖率；别把每条用例都串成十几步的超长流程——一条流一个断言目标，失败时才定位得动。

## 优劣与代价

✅ 真实度最高，能抓住只在整条链路上出现的缺陷。
✅ 直接对齐业务价值，是验收与发布决策的依据。
⚠️ 慢（秒级到分钟级）、维护成本高，UI 一改就要跟着改。
⚠️ 易假失败（flaky）：网络抖动、异步时序、测试数据污染都会让它红，而红多了团队就会开始忽略红灯。
⚠️ 定位能力差：只知道"这条流不通"，不知道哪一层坏了，必须靠下层的单元/集成测试补足精度。

## 与相关概念的区别

- **E2E vs 集成测试**：集成测的是"几个模块拼起来协作对不对"，范围可控、可以起临时依赖；E2E 测的是"整个系统从用户入口到出口对不对"，栈全真、范围最大。
- **E2E vs 冒烟测试**：冒烟是一组极快的"还活着吗"探活检查，广度优先、跑几分钟；E2E 深度优先，把关键流走完整。冒烟常复用少量 E2E 用例，但两者目的不同。
- **E2E vs 契约测试**：契约测试只校验服务间接口约定，不起真实链路，快而稳；E2E 起真实链路，能抓契约之外的集成问题，代价是慢与脆。

## 常见误区

- E2E 测试通过率 100%，就说明系统没有 bug 了。
- 测试金字塔应该倒过来写：E2E 覆盖最全，所以占比要最大。
- E2E 用例失败就先加个 `sleep` 重试，能过就行。

## 面试速答

> 🎯 E2E = 从真实用户入口驱动完整技术栈跑通关键业务流，验证系统整体可用性；居测试金字塔顶层（Mike Cohn 2009 建议单元 70 / 集成 20 / E2E 10），真实度最高但最慢最脆，只挑主干路径、用 `data-testid` 定位、断言落在用户可见结果上。
