# 集成测试

> 📌 **导航**：本文是 **集成测试** 词条，属于 testing 术语集。相关枢纽：[[01 - 测试基础]]、[[02 - 测试工具]]、[[03 - 性能测试]]、[[单元测试]]、[[性能测试]]。

## 定义

**一句话定义：** 集成测试（Integration Testing）是在单元测试之后，把多个已测试的模块 / 组件组合起来，验证它们之间的接口、数据传递与协作是否正确的测试层级，用于发现模块集成后才暴露的交互问题。

**通俗类比：** 像汽车零件各自检验合格后，把它们组装起来试跑——单个零件没问题，不代表装在一起就顺（接口不匹配、时序错乱）；集成测试就是检查"组装后各部件配合是否正常"。

## 为什么需要它

单元测试刻意把依赖换成替身，所以"每个单元各自对"并不能保证"拼起来还对"：字段名对不上、调用顺序错、序列化不兼容、事务边界出问题，都只在模块真正协作时才显形。集成测试正是补上这段盲区，在昂贵的端到端测试之前，用可控的组合验证接口契约。

## 做法

- **关注点**：模块间接口、数据流、调用时序、依赖协作、跨层交互（服务 ↔ 数据库 ↔ 缓存）。
- **策略**：自顶向下（先测上层、下层用桩 stub）、自底向上（先测下层、上层用驱动 driver）、增量集成。
- **配套**：契约测试（如 Pact）、Testcontainers 起临时依赖、内存数据库 / 模拟服务。

| 组成 | 说明 |
|------|------|
| 模块接口 | 集成测试的核心对象 |
| 桩 / 驱动 | 模拟尚未就绪的模块 |
| 集成策略 | 自顶向下 / 自底向上 / 增量 |
| 契约测试 | 验证服务间接口约定 |

## 具体示例

订单服务和库存服务各自单元测试全绿，一集成才发现：订单传的是 `skuId` 字符串、库存要的是 `skuId` 整型，接口反序列化直接失败。这类"协作期才暴露"的问题，正是集成测试要拦的。

## 何时用与何时不用

- **用**：微服务间集成、服务与数据库 / 中间件集成、API 契约验证、CI 的集成测试阶段。
- **不用**：别用它替代单元测试去验证细粒度逻辑（更慢、更难定位）；也不宜全部直连真实生产依赖（不稳定、有副作用）。

## 优劣与代价

✅ 发现单元测不到的接口 / 协作问题，更接近真实运行。
✅ 在 E2E 之前以较低成本验证组合正确性。
⚠️ 定位问题比单元测试难、环境搭建成本高。
⚠️ 慢于单元测试，组合可能爆炸，需谨慎选择集成策略。

## 与相关概念的区别

- **集成测试 vs 单元测试**：单元隔离依赖测单块逻辑；集成把真实模块拼起来测协作。
- **集成测试 vs 系统 / E2E**：集成聚焦模块间接口，系统测试走完整业务流、贴近用户端到端。
- **增量集成 vs 大爆炸**：一次性全集成难定位失败点，增量（自顶向下 / 自底向上）更易缩小范围。

## 常见误区

- 单元测试全过了，集成在一起肯定没问题。
- 集成测试就是端到端（E2E）测试。
- 集成测试就该直连生产外部服务，越真实越好。
