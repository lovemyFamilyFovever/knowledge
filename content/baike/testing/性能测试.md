# 性能测试

> 📌 **导航**：本文是 **性能测试** 词条，属于 testing 术语集。相关枢纽：[[01 - 测试基础]]、[[02 - 测试工具]]、[[03 - 性能测试]]、[[单元测试]]、[[性能测试]]。

## 定义

**一句话定义：** 性能测试通过模拟真实负载来评估系统的响应时间、吞吐量与资源占用，衡量系统在正常及极限压力下能否满足既定性能指标。

**通俗类比：** 像给一条公路做通车压力试验——平时车流顺不代表高峰不堵，得人为造出各种车流（正常、极限、突发、持续）来测哪里会堵、能承载多少。

## 为什么需要它

功能正确不等于上线扛得住：真实流量一来，慢查询、连接池耗尽、内存泄漏会集中爆发。性能测试在上线前用可控方式重现这些负载，找到系统的容量拐点和瓶颈，避免"用户帮你压测"的线上事故。

## 做法

标准方法论是一条闭环，核心是"逐步加压、定位拐点、优化后复测"：

```
1. 确定目标(QPS/P99)  2. 准备与生产一致的环境
3. 逐步加压          4. 观察指标
5. 找到拐点          6. 分析瓶颈
7. 优化 → 重新测试
```

## 具体示例

一次压测显示：并发 500 时 P99 从 80ms 突增到 2s，同时 DB 连接池活跃数打满——拐点即瓶颈，加索引 + 扩池后复测 P99 回落，目标达成。

| 类型 | 目的 | 工具 |
|------|------|------|
| 负载测试 | 正常负载下表现 | JMeter、k6 |
| 压力测试 | 探极限负载 | Locust、wrk |
| 浸泡测试 | 长时间运行查泄漏 | 持续数天 |
| 尖峰测试 | 突然流量高峰 | k6 |

## 何时用与何时不用

- **用**：核心接口上线前评估容量、重大版本回归、SLA/容量规划、性能改造前后对比。
- **不用**：功能尚未稳定时做精细压测（数据无意义）；用一次性 ad-hoc 敲几下代替有目标、可复现的压测。

## 优劣与代价

✅ 提前暴露容量瓶颈与稳定性风险，为扩容与调优提供量化依据。
✅ 可复现、可回归，守住性能基线。
⚠️ 搭建贴近生产的环境成本高，结论受环境与数据分布影响。
⚠️ 压测本身可能打挂依赖系统，需在隔离环境进行。

## 与相关概念的区别

- **负载测试 vs 压力测试**：前者验证"正常/预期负载下达标"，后者加压到极限以探崩溃点与降级行为。
- **P50/P95/P99 vs 平均值**：平均值会被少数极慢请求掩盖，长尾体验要看百分位。
- **性能测试 vs 混沌工程**：性能测试测"够不够快扛不扛得住"，混沌工程测"故障时稳不稳"。

## 常见误区

- 平均响应时间达标，性能就没问题。
- 只要不断堆机器就能持续提升性能，不存在瓶颈拐点。
- 压测环境和生产随便差一点也不影响结论。

## 面试速答

> 🎯 性能测试 = 用模拟负载评估响应时间 / 吞吐 / 资源，含负载 / 压力 / 浸泡 / 尖峰等类型；关注 QPS·TPS、P95·P99、错误率，方法论是"定目标→一致环境→逐步加压→找拐点→分析瓶颈→优化复测"。
