# 性能报告与瓶颈分析

> 📌 **导航**：本文是 **性能报告与瓶颈分析** 词条，属 [[03 - 性能测试]] 子词条。优化手段见 [[性能优化]]，诊断命令见 [[Linux 性能分析工具]]。

## 定义

**一句话定义：** 性能报告是对一次压测结果的汇总解读（响应时间分位、吞吐、错误率 + 资源使用，对照基线判达标）；瓶颈分析是顺着"木桶最短那块板"定位限制性能的环节——CPU / 内存 / 磁盘 IO / 网络 / 数据库——从而对症下药。

**通俗类比：** 报告像体检单（各项指标看是否达标、和去年比有无恶化）；瓶颈分析像医生顺着症状找病因——是先查心（CPU）还是肺（IO），别一上来就乱吃药（盲目优化）。

## 为什么需要它

压测完拿到一堆数字，不解读就无法决策"过不过、要不要改"；与历史基线对比才能识别性能退化。而"哪里慢"若不定位就优化，常白改甚至改反（如 CPU 不满却去堆机器）。报告给结论、瓶颈分析给根因，是"测出问题→改对地方"闭环的两环。

## 核心机制

- **报告要素**：测试时段/并发/总请求、响应时间 avg+P90/P95/P99、吞吐/TPS/QPS、错误率、资源使用（CPU/内存/网络/DB 连接），并给出"达标? 对比基线? 下一步建议"结论。
- **报告 vs 监控 vs 基线**：报告是事后分析、监控是实时观测、基线是历史对比基准。
- **瓶颈定位路径**（自顶向下）：响应长→看 CPU 高（计算密集/线程切换）？内存高（泄漏/大对象/GC）？磁盘 IO（频繁读写/日志）？网络（大包/过多请求）？数据库慢查询（无索引/连接池不足/锁竞争）？
- **诊断命令**：Linux `top/vmstat/iostat -x/sar/netstat`；Java `jstack/jmap/jstat -gcutil`；MySQL `SHOW PROCESSLIST`、`EXPLAIN`（见 [[Linux 性能分析工具]]）。
- **优化归口**：定位后按"代码→缓存→数据库→架构"分层优化，手段见 [[性能优化]]。

## 具体示例

一份达标报告的关键行 + 一条定位链：

```
P99 890ms(<1s ✓)  吞吐 250 req/s  错误率 0.02%(<0.1% ✓)
CPU 65%  DB连接 45/100
结论：达标；瓶颈线索=数据库连接池偏紧 → 建议调大池 + EXPLAIN 慢查询
```

## 何时用与何时不用

- **用**：每次压测后出结构化报告并与基线比，防退化；性能不达标时先做瓶颈定位（USE 法：利用率/饱和度/错误）再优化；把命令/指标纳入常态监控。
- **不用**：别只凭单一指标下结论（只看吞吐忽略错误率）；别没定位根因就"加缓存/加机器"式乱调；报告别脱离业务 SLA 空谈漂亮数字。

## 优劣与代价

✅ 报告把结果变决策、基线对比守住性能不回退；瓶颈分析用数据驱动"改对地方"、避免无头优化。
✅ 命令与分层方法可复用、可沉淀为团队 playbook。
⚠️ 分析依赖经验与完整监控，缺数据则定位靠猜；根因常是多因耦合（CPU 满只是表象、真因在慢 SQL）。
⚠️ 过度优化局部指标可能牺牲可读性/成本/其他指标（古德哈特）。

## 与相关概念的区别

- **性能报告 vs 性能监控**：一次性压测的事后总结 vs 7×24 实时观测。
- **瓶颈分析 vs 性能优化**：诊断（找最短板） vs 治疗（补板），见 [[性能优化]]。
- **瓶颈分析 vs 负载测试**：后者造压取数（[[性能测试类型与策略]]），前者解读并定位。
- **平均 vs 分位/资源联合看**：P99 + CPU/IO 一起看才定位得准（见 [[性能测试指标]]）。

## 常见误区

- 报告里平均响应时间达标，性能就没问题。
- CPU 不高，所以系统肯定不是瓶颈、肯定在别处。
- 发现慢就直接加机器/堆缓存，不用先定位根因。

## 面试速答

> 🎯 性能报告=压测结果结构化解读(响应分位 P90/95/99 + 吞吐/TPS + 错误率 + CPU/内存/IO/DB 资源)，对照基线判达标。瓶颈分析=顺最短板定位 CPU/内存/IO/网络/DB，用 top、iostat、EXPLAIN 等取证。诊断在前、治疗([[性能优化]])在后。
