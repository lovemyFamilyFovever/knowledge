# 断言与测试替身

> 📌 **导航**：本文是 **断言与测试替身** 词条，属 [[01 - 测试基础]] 子词条。被隔离的对象多在 [[单元测试]] 中。

## 定义

**一句话定义：** 断言是测试里"实际是否等于预期"的检查点，没有它测试就无法判对错；测试替身是测试中替代真实依赖（数据库/网络）的"假对象"，让测试快、稳、可控——一个负责"验证什么"，一个负责"隔离谁"。

**通俗类比：** 断言像对答案（结果=5 才算过）；测试替身像拍危险镜头用替身演员——真实主演（外部依赖）不必上场，测试就能独立跑。

## 为什么需要它

没有断言，跑完只是"执行了代码"却没判断对错，等于没测。而直接依赖真实数据库/HTTP/时间/随机，会让单元测试变慢、不稳定、难构造边界（异常/超时/特定状态）；用替身把被测单元与外界隔开，才能做到快速、可重复、想测哪条分支就造哪条。

## 核心机制

- **断言**：`assert x == 5`、JUnit `assertEquals`、Jest `expect(...).toBe(...)`；一个用例可含多个断言，失败即报错并给"期望 vs 实际"。
- **测试替身家族（Test Double）**：Dummy 占位、Stub 返回预设数据、Spy 记录调用并放行真实行为、Mock 验证"交互是否按预期发生"、Fake 用简化真实现（如内存仓储）替代。
- **state vs interaction**：断言结果（返回值/状态）用 Stub/Fake + assert；断言"是否/如何被调用"用 Mock/Spy（`assert_called_once_with`）。
- **打桩方式**：`unittest.mock`、Mockito、Jest mock；对时间/随机等"不稳定来源"打桩以保可重复。

## 具体示例

```python
def test_send_email(mocker):
    svc = Mock()                       # 替身：隔离邮件服务
    send_welcome("u@t.com", svc)
    svc.send.assert_called_once_with(to="u@t.com")  # 断言交互

def test_add():
    assert add(2, 3) == 5              # 断言结果
```

## 何时用与何时不用

- **用**：几乎所有单元/集成测试都靠断言成立；当被测单元依赖外部系统、或需构造难触达状态/验证调用行为时用替身。
- **不用**：别滥用 Mock——测什么就真跑什么，Mock 了协作方却声称验证了它，是"测了个寂寞"；也别为一个简单纯函数硬搭替身栈。断言别一次塞太多失去可读性（一用例一个焦点）。

## 优劣与代价

✅ 断言给测试唯一的"对错判据"；替身让测试快速、确定、可构造任意边界与交互验证。
✅ 支持把逻辑与 I/O 解耦，是"可测试设计"的支点。
⚠️ 过度 Mock 会把实现细节焊进测试，重构时大面积误红、且真集成坏了却全绿（耦合替身 vs 真实行为）。
⚠️ 替身行为若与真实依赖偏离，测试通过≠线上正确。

## 与相关概念的区别

- **Stub vs Mock**：Stub 只管"喂数据"、不校验调用；Mock 关心"被怎样调用"（次数/参数）。
- **Fake vs Stub**：Fake 是可用的简化真实实现（内存库），Stub 只回预设值无逻辑。
- **断言 vs 校验**：测试语境里近似，断言是"失败即中止测试"的框架原语，更通用。

## 常见误区

- 把协作用 Mock 全部 mock 掉，测试就一定可信。
- 一个测试里断言越多越好，反正都能跑。
- Stub 和 Mock 完全等价，只是叫法不同。

## 面试速答

> 🎯 断言=测试对错判据(实际 vs 预期，如 expect().toBe / assert)，无用例不测。测试替身=隔离真实依赖的假对象：Dummy 占位、Stub 回预设、Spy 记录放行、Mock 验交互、Fake 简化真实现；验结果用 Stub/Fake、验调用用 Mock。忌过度 mock。
