# 01 - 测试基础

> 本文档涵盖软件测试的核心概念、术语定义及实践方法。

---

## 测试金字塔

### 一句话定义（大白话）
测试金字塔是一种指导测试策略的模型，告诉你底层测试应该多写、顶层测试应该少写，形成一个稳定的三角形结构。

### 通俗类比（生活场景）
就像盖房子：地基（单元测试）要打得最多最稳，中间的楼层（集成测试）适量搭建，最后的装修（端到端测试）点到为止。如果地基不牢，房子迟早塌。

### 具体示例
```
        /  端到端测试  \        ← 数量最少，运行最慢
       /  集成测试      \      ← 数量适中
      / 单元测试          \    ← 数量最多，运行最快
     /____________________\
```

**实际比例建议：**
- 单元测试：70%
- 集成测试：20%
- 端到端测试：10%

### 为什么需要它
防止团队把大量时间花在运行缓慢的 E2E 测试上，而忽略了快速反馈的单元测试。金字塔模型帮你找到测试的投入产出比最优解。

### 与相关术语的对比和区分
| 术语 | 关注点 | 速度 | 成本 |
|------|--------|------|------|
| 单元测试 | 单个函数/类 | 极快 | 低 |
| 集成测试 | 模块间交互 | 中等 | 中 |
| 端到端测试 | 完整用户流程 | 慢 | 高 |

---

## 单元测试（pytest / JUnit / Jest）

### 一句话定义（大白话）
单元测试是对程序中最小可测试单元（函数、方法、类）进行验证的测试，确保每个零件单独工作正常。

### 通俗类比（生活场景）
就像检查每个螺丝钉是否合格——先保证零件没问题，再组装整机。

### 具体示例

**Python（pytest）：**
```python
# calculator.py
def add(a, b):
    return a + b

# test_calculator.py
def test_add():
    assert add(2, 3) == 5
    assert add(-1, 1) == 0
    assert add(0, 0) == 0
```

**Java（JUnit 5）：**
```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class CalculatorTest {
    @Test
    void testAdd() {
        assertEquals(5, Calculator.add(2, 3));
        assertEquals(0, Calculator.add(-1, 1));
    }
}
```

**JavaScript（Jest）：**
```javascript
// calculator.test.js
function add(a, b) { return a + b; }

test('adds two numbers correctly', () => {
    expect(add(2, 3)).toBe(5);
    expect(add(-1, 1)).toBe(0);
});
```

### 为什么需要它
单元测试能在开发早期发现 bug，重构时提供安全保障，是代码质量的第一道防线。

### 与相关术语的对比和区分
- **单元测试 vs 集成测试**：单元测试隔离验证，集成测试关注模块协作
- **单元测试 vs 冒烟测试**：单元测试粒度细，冒烟测试是粗略的快速验证

---

## 集成测试

### 一句话定义（大白话）
集成测试是把多个模块组合在一起，验证它们之间协作是否正确的测试。

### 通俗类比（生活场景）
零件都检查过了，现在把发动机、变速箱、轮胎装到一起，看看能不能正常运转。

### 具体示例
```python
# 测试数据库操作与业务逻辑的集成
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

@pytest.fixture
def db_session():
    engine = create_engine('sqlite:///:memory:')
    Session = sessionmaker(bind=engine)
    session = Session()
    yield session
    session.close()

def test_user_creation_and_query(db_session):
    user = User(name="张三", email="zhangsan@test.com")
    db_session.add(user)
    db_session.commit()

    result = db_session.query(User).filter_by(name="张三").first()
    assert result.email == "zhangsan@test.com"
```

### 为什么需要它
单元测试通过不代表模块间配合没问题，集成测试专门找出接口不匹配、数据传递错误等问题。

### 与相关术语的对比和区分
- **集成测试 vs 单元测试**：集成测试包含外部依赖（数据库、API），单元测试用 mock 隔离
- **集成测试 vs 端到端测试**：集成测试关注模块间，端到端测试关注完整用户流程

---

## 端到端测试（E2E）

### 一句话定义（大白话）
端到端测试模拟真实用户从打开应用到完成操作的完整流程，验证整个系统是否正常工作。

### 通俗类比（生活场景）
模拟一个顾客从进店、挑选商品、结账、取货的完整购物体验，每个环节都要顺畅。

### 具体示例
```javascript
// Cypress E2E 测试示例
describe('用户登录流程', () => {
    it('应能成功登录并跳转到首页', () => {
        cy.visit('/login')
        cy.get('input[name="username"]').type('admin')
        cy.get('input[name="password"]').type('password123')
        cy.get('button[type="submit"]').click()
        cy.url().should('include', '/dashboard')
        cy.get('.welcome-message').should('contain', '欢迎回来')
    })
})
```

### 为什么需要它
验证整个系统在真实环境下的行为，确保用户实际操作流程畅通无阻。

### 与相关术语的对比和区分
| 对比项 | E2E 测试 | 集成测试 | 单元测试 |
|--------|----------|----------|----------|
| 测试范围 | 整个系统 | 模块间 | 单个单元 |
| 运行速度 | 慢 | 中等 | 快 |
| 维护成本 | 高 | 中 | 低 |
| 真实度 | 高 | 中 | 低 |

---

## 冒烟测试

### 一句话定义（大白话）
冒烟测试是一组快速、粗略的测试，用来检查系统最基本的功能是否可用，就像新设备通电后看看亮不亮。

### 通俗类比（生活场景）
买了新手机，先按开机键看能不能点亮屏幕——这就是冒烟测试，不测细节，只看最基本的能不能用。

### 具体示例
```python
# 冒烟测试：验证核心功能是否可用
def test_smoke_login():
    """验证登录功能基本可用"""
    response = requests.post('/api/login', json={
        'username': 'testuser',
        'password': 'testpass'
    })
    assert response.status_code == 200
    assert 'token' in response.json()

def test_smoke_health_check():
    """验证服务健康检查"""
    response = requests.get('/api/health')
    assert response.status_code == 200
```

### 为什么需要它
每次部署后快速验证核心功能是否正常，避免花大量时间做详细测试却发现系统根本跑不起来。

### 与相关术语的对比和区分
- **冒烟测试 vs 回归测试**：冒烟测试快速验证核心功能，回归测试验证已有功能未被破坏
- **冒烟测试 vs 验收测试**：冒烟测试是技术层面的快速检查，验收测试是业务层面的正式确认

---

## 回归测试

### 一句话定义（大白话）
回归测试是修改代码后重新运行之前的测试，确保新改动没有破坏已有功能。

### 通俗类比（生活场景）
汽车换了新零件后，要重新检查刹车、转向、灯光等原有功能是否还正常——防止修好了这里，弄坏了那里。

### 具体示例
```python
# 假设之前有一个通过的测试
def test_calculate_discount():
    assert calculate_discount(100, 0.1) == 90  # 100元打9折=90元

# 修改了 calculate_discount 函数后，重新运行这个测试
# 如果仍然通过，说明没有引入回归问题
# 如果失败，说明新改动破坏了原有功能
```

### 为什么需要它
软件修改很容易引入意想不到的副作用，回归测试确保"改了新的，旧的还能用"。

### 与相关术语的对比和区分
| 对比项 | 回归测试 | 冒烟测试 | 验收测试 |
|--------|----------|----------|----------|
| 目的 | 验证已有功能 | 快速验证核心功能 | 业务需求确认 |
| 触发时机 | 代码修改后 | 部署后 | 交付前 |
| 覆盖范围 | 广泛 | 核心路径 | 业务场景 |

---

## 探索性测试（Exploratory Testing）

### 一句话定义（大白话）
探索性测试是测试人员边思考、边设计、边执行的测试方式，没有固定脚本，靠经验和直觉发现隐藏 bug。

### 通俗类比（生活场景）
不是按说明书逐项检查，而是像侦探一样带着"找茬"的心态去探索产品，寻找各种异常情况。

### 具体示例
```
探索性测试Session示例：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
时间：2024-01-15 14:00-15:00（60分钟）
测试员：张三
探索目标：购物车功能
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
已测试：
  ✓ 添加商品到购物车
  ✓ 修改商品数量
  ✓ 删除商品
  ✗ 发现：当数量输入-1时，总价变为负数
  ✗ 发现：快速连续点击"添加"按钮，商品重复添加
  ✗ 发现：添加超过9999件商品时页面崩溃
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
结论：购物车在边界值处理上存在缺陷
```

### 为什么需要它
脚本化测试可能遗漏非预期场景，探索性测试能发现"想不到的 bug"，特别适合复杂业务逻辑。

### 与相关术语的对比和区分
- **探索性测试 vs 脚本化测试**：探索性测试灵活但依赖经验，脚本化测试可重复但可能遗漏异常场景
- **探索性测试 vs 冒烟测试**：探索性测试深入挖掘，冒烟测试快速验证

---

## 验收测试（UAT）

### 一句话定义（大白话）
验收测试是由客户或业务方执行的测试，确认软件是否满足业务需求，决定是否"收货"。

### 通俗类比（生活场景）
装修完工后，业主逐项检查：墙面平整、水电通畅、门窗完好——确认符合合同要求才签字验收。

### 具体示例
```gherkin
# 验收测试用例（Gherkin格式）
Feature: 订单管理
  Scenario: 客户下单并支付
    Given 客户已登录系统
    When 客户选择商品"iPhone 15"并点击"立即购买"
    And 客户确认收货地址并选择支付方式
    And 客户完成支付
    Then 系统显示"订单创建成功"
    And 客户收到订单确认邮件
    And 库存中"iPhone 15"数量减少1
```

### 为什么需要它
技术测试通过不代表业务需求满足，验收测试确保"做对了事情"而不只是"把事情做对了"。

### 与相关术语的对比和区分
| 对比项 | 验收测试（UAT） | 回归测试 | 冒烟测试 |
|--------|-----------------|----------|----------|
| 执行者 | 业务方/客户 | 开发/测试 | 开发/测试 |
| 关注点 | 业务需求 | 功能正确性 | 核心可用性 |
| 标准 | 是否满足需求 | 是否引入bug | 是否能运行 |

## 断言（assert）

### 一句话定义（大白话）
断言是代码中的一个"检查点"，用来判断程序的实际结果是否和预期一致，不一致就报错。

### 通俗类比（生活场景）
就像考试对答案——你算出答案是5，老师的标准答案也是5，断言就"通过"；如果答案不对，断言就"挂科"。

### 具体示例
```python
# Python assert 语句
def test_string_processing():
    result = process_string("  Hello World  ")
    assert result == "Hello World", f"期望 'Hello World'，实际得到 '{result}'"

# pytest 风格的断言
def test_list_operations():
    my_list = [1, 2, 3]
    assert len(my_list) == 3
    assert 4 not in my_list
    assert my_list[0] == 1
    assert sum(my_list) == 6
```

### 为什么需要它
断言是所有测试的基础——没有断言，测试就无法判断对错，等于没测。

### 与相关术语的对比和区分
- **断言 vs 测试用例**：断言是测试用例中的检查点，一个测试用例可以有多个断言
- **断言 vs 校验**：在测试框架中两者通常等价，断言是更通用的编程术语

---

## 测试覆盖率（Coverage）

### 一句话定义（大白话）
测试覆盖率衡量你的测试覆盖了多少代码，比如1000行代码跑了800行，覆盖率就是80%。

### 通俗类比（生活场景）
一本100页的考纲，你复习了80页，覆盖率就是80%——剩下的20页可能就是考试的坑。

### 具体示例
```bash
# Python 生成覆盖率报告
pytest --cov=src --cov-report=html

# 输出示例：
# Name                    Stmts   Miss  Cover
# -------------------------------------------
# src/calculator.py          20      2    90%
# src/user_service.py        50     10    80%
# -------------------------------------------
# TOTAL                      70     12    83%
```

```javascript
// Jest 配置覆盖率
// package.json
{
  "scripts": {
    "test": "jest --coverage"
  }
}
// 输出：
// ----------|---------|----------|---------|---------|
// File      | % Stmts | % Branch | % Funcs | % Lines |
// ----------|---------|----------|---------|---------|
// All files |   85.7  |    78.3  |   90.0  |   84.2  |
// ----------|---------|----------|---------|---------|
```

### 为什么需要它
覆盖率是测试充分性的一个量化指标，帮你发现哪些代码还没有被测试覆盖。

### 与相关术语的对比和区分
- **覆盖率高 ≠ 质量高**：100%覆盖率不代表没有 bug，可能只是所有行都执行了但没有有效断言
- **语句覆盖 vs 分支覆盖**：语句覆盖只看代码是否执行，分支覆盖看每个 if/else 是否都走到

## 测试替身（Test Double）

### 一句话定义（大白话）
测试替身是在测试中替代真实依赖的"假对象"，让测试更快速、更可控、不依赖外部环境。

### 通俗类比（生活场景）
拍电影时用替身演员代替主演完成危险镜头——测试替身就是让假对象代替真实的数据库、网络服务等，让测试可以独立运行。

### 具体示例

**Mock（模拟对象）：**
```python
from unittest.mock import Mock, patch

# Mock：记录调用行为并验证
def test_send_email():
    email_service = Mock()
    email_service.send.return_value = True

    result = send_welcome_email("user@test.com", email_service)

    assert result is True
    email_service.send.assert_called_once_with(
        to="user@test.com",
        subject="欢迎加入"
    )
```

**Stub（存根）：**
```python
# Stub：返回预设的固定数据
class FakeUserRepository:
    def get_user(self, user_id):
        return {"id": user_id, "name": "测试用户", "email": "test@test.com"}

def test_get_user_name():
    repo = FakeUserRepository()
    name = get_user_name(1, repo)
    assert name == "测试用户"
```

**Spy（间谍）：**
```python
# Spy：记录调用信息但保留真实行为
class DatabaseSpy:
    def __init__(self, real_db):
        self.real_db = real_db
        self.queries = []

    def query(self, sql):
        self.queries.append(sql)
        return self.real_db.query(sql)
```

**Fake（伪对象）：**
```python
# Fake：用简化实现替代真实依赖
class FakeCache:
    def __init__(self):
        self.store = {}

    def get(self, key):
        return self.store.get(key)

    def set(self, key, value):
        self.store[key] = value
```

### 为什么需要它
真实依赖（数据库、网络、文件系统）让测试变慢、不稳定、难以控制边界条件，测试替身解决这些问题。

### 与相关术语的对比和区分
| 类型 | 行为 | 用途 | 复杂度 |
|------|------|------|--------|
| Mock | 验证交互行为 | 验证方法调用是否正确 | 高 |
| Stub | 返回预设数据 | 提供测试所需数据 | 低 |
| Spy | 记录调用信息 | 验证调用次数/参数 | 中 |
| Fake | 简化实现替代 | 替代外部依赖 | 中 |

## TDD（测试驱动开发）

### 一句话定义（大白话）
TDD 是一种"先写测试，再写代码"的开发方法：先写失败的测试，再写刚好让测试通过的代码，然后重构。

### 通俗类比（生活场景）
先定目标（测试）——"我要做一个能装500ml水的杯子"，然后动手制作（实现），最后打磨优化（重构）。红-绿-重构循环。

### 具体示例
```python
# 第1步：写一个失败的测试（红）
def test_add_positive_numbers():
    assert add(2, 3) == 5

# 第2步：写最少的代码让测试通过（绿）
def add(a, b):
    return a + b

# 第3步：重构代码，保持测试通过
# （这里代码已经很简单，无需重构）

# 第4步：写下一个测试，重复循环
def test_add_negative_numbers():
    assert add(-1, -2) == -3
```

### 为什么需要它
TDD 让你在写代码之前就想清楚需求，产出的代码自然有良好的可测试性和清晰的设计。

### 与相关术语的对比和区分
- **TDD vs BDD**：TDD 关注代码层面的正确性，BDD 关注业务行为和需求
- **TDD vs 传统测试**：TDD 是开发方法论，传统测试是事后补充

---

## BDD（行为驱动开发）

### 一句话定义（大白话）
BDD 是用自然语言描述系统行为的开发方法，让开发、测试、产品用同一种语言沟通，减少理解偏差。

### 通俗类比（生活场景）
菜谱就是 BDD——"Given 准备好食材，When 开火热锅，Then 翻炒出锅"，人人都看得懂，厨师照着做不会偏。

### 具体示例
```gherkin
# BDD 特性文件（.feature）
Feature: 用户注册
  Scenario: 新用户成功注册
    Given 用户在注册页面
```

## 契约测试（Contract Testing）

### 一句话定义（大白话）
契约测试验证服务间的接口协议是否一致——消费者期望什么格式的数据，提供者是否真的返回了这个格式。

### 通俗类比（生活场景）
甲乙双方签合同：甲方（消费者）说"我要能住的房子"，乙方（提供者）必须按合同交付符合标准的房子。契约测试就是检查房子是否符合合同。

### 具体示例
```python
# 消费者端契约
from pact import Consumer, Provider

pact = Consumer('OrderService').has_pact_with(Provider('UserService'))

def test_get_user_contract():
    expected = {
        'id': 1,
        'name': '张三',
        'email': 'zhangsan@test.com'
    }

    pact.given('用户1存在')
    pact.upon_receiving('获取用户信息请求')
    pact.with_request('GET', '/api/users/1')
    pact.will_respond_with(200, body=expected)

    with pact:
        user = user_client.get_user(1)
        assert user['name'] == '张三'
```

### 为什么需要它
微服务架构下，服务间依赖复杂，契约测试确保接口变更不会破坏上下游，比集成测试更轻量。

### 与相关术语的对比和区分
- **契约测试 vs 集成测试**：契约测试验证接口协议，集成测试验证端到端流程
- **契约测试 vs 单元测试**：契约测试关注服务间边界，单元测试关注内部逻辑

## 总结

| 概念 | 核心价值 | 适用场景 |
|------|----------|----------|
| 测试金字塔 | 指导测试策略 | 制定测试计划 |
| 单元测试 | 快速验证最小单元 | 日常开发 |
| 集成测试 | 验证模块协作 | 模块联调 |
| E2E 测试 | 验证完整用户流程 | 上线前验证 |
| 冒烟测试 | 快速确认核心可用 | 部署后验证 |
| 回归测试 | 确保改动无副作用 | 代码修改后 |
| 探索性测试 | 发现隐藏 bug | 复杂功能测试 |
| 验收测试 | 确认业务需求满足 | 交付验收 |
| 断言 | 判断测试结果 | 所有测试中 |
| 覆盖率 | 量化测试充分性 | 评估测试质量 |
| 测试替身 | 隔离外部依赖 | 单元/集成测试 |
| TDD | 先测试后编码 | 开发流程 |
| BDD | 自然语言描述行为 | 需求沟通 |
| 契约测试 | 验证服务间协议 | 微服务架构 |
