# 容器隔离与内核安全

> 📌 **导航**：本文是 **容器隔离与内核安全** 词条，属 [[操作系统内核原理]] 子词条。运行时加固操作见 [[容器运行时安全]]。

## 定义

**一句话定义：** 内核用 Namespace 隔离"进程能看见什么"、用 Cgroups 限制"进程能用多少资源"，二者合成容器的轻量底座；再叠加 SELinux（强制访问控制）与 Seccomp（系统调用过滤）收窄共享内核的攻击面。

**通俗类比：** Namespace 给每个容器一套独立的门牌与视野（看不到别家的进程/网络/挂载）；Cgroups 是限电的空开（用超就限）；SELinux/Seccomp 是额外的门禁规则与"只准按这几个按钮"。

## 为什么需要它

容器共享宿主内核、比虚拟机轻，但要"看起来像独立机器"就得隔离资源视图（Namespace）、要"不互相挤爆"就得限额（Cgroups）。也正因共享内核，一旦逃逸后果严重——所以再用 MAC 与 syscall 过滤把内核能力收紧。

## 核心机制

- **6 类 Namespace**：PID（容器内有独立 init/1）、NET（独立网络栈）、MNT（独立挂载/根）、UTS（主机名）、IPC、USER（容器 root 可映射为宿主非 root）。经 `clone()`/`unshare()` 创建。
- **Cgroups**：按子系统（cpu/memory/blkio/cpuset）组织成层级，节点内写参数（如 `memory.max`）、把 PID 放进 `cgroup.procs` 即受限。
- **SELinux**：MAC，给主体/客体打 `user:role:type:level` 上下文并按策略放行——即使进程是 root 也受策略约束，挡提权。
- **Seccomp**：限制进程可发起的系统调用（STRICT 或 FILTER+BPF 白名单），Chrome/容器运行时用它缩小被攻破后的可用面。

## 具体示例

用 `clone` 起一个拥有独立 PID 与网络命名空间的子进程，再落进受内存上限约束的 cgroup：

```c
clone(child, stack, CLONE_NEWPID | CLONE_NEWNET | SIGCHLD, NULL); // 独立视野
// 资源上限：echo 104857600 > .../my-container/memory.max;  PID → cgroup.procs
```

Docker / Kubernetes 正是在底层组合 Namespace + Cgroups（再配 Seccomp/AppArmor/SELinux）实现容器。

## 何时用与何时不用

- **用**：搭容器运行时、给进程限资源、多租户共享内核需加固、限制不受信程序的 syscall 面。
- **不用**：需要强隔离/不可信内核边界时，Namespace 共享内核不够，应上 gVisor/Kata/虚拟机（见 [[容器运行时安全]]）。

## 优劣与代价

✅ Namespace+Cgroups 以极低开销实现"视图隔离+资源限额"，是容器轻量之本。
✅ SELinux/Seccomp 在共享内核下进一步收窄攻击面。
⚠️ 共享内核决定隔离弱于虚拟机，存在逃逸上界。
⚠️ 安全策略配置复杂、误配易误杀正常行为或形同虚设。

## 与相关概念的区别

- **Namespace vs Cgroups**：前者管"看得见哪些资源"（隔离视图），后者管"能用多少"（限额计量），常配合。
- **DAC vs MAC（SELinux）**：传统属主/权限是自主访问控制；MAC 由全局策略强制，连 root 也不能越。
- **Seccomp vs LSM**：Seccomp 限"能调哪些系统调用"，AppArmor/SELinux 限"能访问哪些对象"。

## 常见误区

- Namespace 也能限制进程的 CPU 和内存用量。
- 容器里的 root 等于宿主机的 root，拥有全部权力。
- 上了 Seccomp 就不需要文件权限和 SELinux 了。

## 面试速答

> 🎯 容器底座=Namespace 隔离视野(PID/NET/MNT/USER，clone)+Cgroups 限额(cpu/memory)；再叠 SELinux(MAC，连 root 也受限)与 Seccomp(BPF 白名单)收窄攻击面。前者管"看得见"、后者管"用多少"。
