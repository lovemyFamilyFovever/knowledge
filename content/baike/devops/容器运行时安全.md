# 容器运行时安全

> 📌 **导航**：本文是 **容器运行时安全** 词条，属 [[Docker容器化完全指南]] 子词条。隔离底座（Namespace/Cgroups）见 [[容器与编排技术详解]]，本文讲运行期加固。

## 定义

**一句话定义：** 容器运行时安全指在共享内核前提下，用最小权限、系统调用与强制访问控制、只读文件系统、镜像扫描等手段，收窄容器可利用的攻击面、降低逃逸与横向影响。

**通俗类比：** 容器像合租房里各自的房间——门能锁（隔离）但共用一套水管电路（内核）；安全加固就是少给钥匙权限、装监控、别让室友从你房间翻遍全屋。

## 为什么需要它

容器共享宿主机内核，隔离强度天生弱于虚拟机：一旦有内核漏洞或配置过宽，就可能容器逃逸、读到宿主敏感信息。默认以 root 跑、给 `--privileged`、镜像带一堆 CVE，都会把风险放大。运行时安全就是在"必须共享内核"的现实里尽量收紧权限与攻击面。

## 核心机制

- **最小权限**：非 root 用户运行（Dockerfile `USER`/`--user`）、`--read-only` 只读根文件系统、去掉不必要 capability、禁 `--privileged`、限 PID/CPU/内存。
- **系统调用过滤**：Seccomp 白名单只放行应用真正需要的 syscall（默认 profile 已屏蔽数百个危险调用）。
- **强制访问控制**：AppArmor/SELinux profile 限制文件、网络等访问（如 `deny /etc/shadow`）。
- **镜像与密钥**：Trivy/Clair 扫描镜像漏洞；secrets 走 Docker secrets/外部密钥管理，不入镜像层。
- **网络与更新**：用 internal 网络隔离后端、及时更新基础镜像与 Docker。

## 具体示例

一个收紧的运行配置示意——非 root、只读、限权：

```bash
docker run --read-only --user 1000:1000 --cap-drop ALL \
  --security-opt no-new-privileges --memory 256m nginx
```

## 何时用与何时不用

- **用**：任何上生产、多租户或不可信镜像共存的容器环境都应做默认加固；CI 里加镜像扫描门禁。
- **不用（慎用放松）**：确需 `--privileged`/关 seccomp 的硬件/容器套容器类操作要显式评估；"图省事全用 root + privileged"是反面教材。

## 优劣与代价

✅ 显著缩小攻击面、降低逃逸后果、把已知 CVE 拦在部署前。
✅ 最小权限 + 只读 + 扫描可自动化进 CI。
⚠️ 过严 profile 会挡正常功能、排障变难（需按需放行）。
⚠️ 共享内核是根本上限：不可信租户/内核 0-day 下，容器隔离不如虚拟机。

## 与相关概念的区别

- **Seccomp vs AppArmor**：Seccomp 管"能调哪些系统调用"，AppArmor/SELinux 管"能访问哪些文件/网络等资源"，二者互补。
- **容器隔离 vs 虚拟机**：容器共享内核（Namespace/Cgroups），VM 有独立内核；强不可信隔离仍需 VM/gVisor/Kata。
- **镜像扫描 vs 运行时防护**：前者发现已知漏洞（静态），后者限制行为（动态），缺一不可。

## 常见误区

- 容器天然隔离，随便用 root 和 --privileged 跑也没事。
- 镜像构建时扫过一次漏洞就永久安全了。
- 开了只读文件系统(--read-only)容器就完全不能写任何数据。

## 面试速答

> 🎯 容器共享内核、隔离弱于 VM，加固=最小权限(非root/只读/cap-drop)+Seccomp(过滤 syscall)+AppArmor/SELinux+镜像扫描+secrets。强不可信多租户需 gVisor/Kata/VM 兜底。
