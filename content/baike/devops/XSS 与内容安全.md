# XSS 与内容安全

> 📌 **导航**：本文是 **XSS 与内容安全** 词条，属 [[Web安全攻防实战指南]] 子词条。

## 定义

**一句话定义：** XSS（跨站脚本）是攻击者把恶意脚本注入到其他用户会浏览的页面中、令其在受害者浏览器执行的漏洞；核心防御是"按输出上下文编码 + CSP + HttpOnly/SameSite"构成的纵深。

**通俗类比：** 像有人在公告栏贴了张会自己执行指令的纸——谁去看（打开页面）谁的浏览器就照做。防它的关键是"贴上去前先转义成普通文字"，而不是"规定公告栏只能贴纸"。

## 为什么需要它

Web 页面大量渲染用户输入；若把输入当"代码/标记"直接吐进 HTML，浏览器就会执行——可窃取 Cookie、伪造操作、挂马。XSS 是最高频的客户端注入，需要一套系统的内容安全策略而非零散补丁。

## 核心机制

- **三种类型**：反射型（恶意脚本在 URL 参数中被"反射"进响应、即时执行）、存储型（脚本入库，他人访问时加载执行，危害最广）、DOM 型（漏洞全在客户端 JS，如把 `location.hash` 未经处理写入 `innerHTML`，数据不经服务器）。
- **纵深防御**：① **输出编码**（最核心，按 HTML 正文/属性/JS/CSS/URL 各用对应转义）；② **CSP** 响应头限制可加载/执行的脚本源、禁内联；③ 输入白名单校验；④ 用 React/Vue 等默认转义的框架；⑤ Cookie 加 `HttpOnly`（禁 JS 读）、`Secure`、`SameSite`。

## 具体示例

把用户输入安全地当"文本"输出，而非拼进 HTML；Cookie 加 HttpOnly 断掉脚本窃取路径：

```php
echo htmlspecialchars($input, ENT_QUOTES, 'UTF-8');   // 按 HTML 上下文编码
// Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax
```

## 何时用与何时不用

- **用**：任何渲染用户可控内容到 HTML/JS/URL 的地方都要按上下文编码；对外站点再叠 CSP 做兜底。
- **不用**：别把"前端 JS 校验"当防线（可绕过）；纯服务端渲染、无用户输入注入点处不必强上 CSP（但通常无害）。

## 优劣与代价

✅ 纵深防御(编码+CSP+Cookie 标志+框架转义)相互补位，能显著压低 XSS 面。
✅ 输出编码成本低、可框架化统一实施。
⚠️ CSP 规则配置复杂、过严会误伤内联脚本/第三方资源。
⚠️ 只靠前端校验或只靠 CSP 都会留口子；DOM 型难被服务端 WAF 拦住。

## 与相关概念的区别

- **反射 vs 存储 vs DOM**：前者一次性、需诱导点击；后者持久化、自动波及所有访客；DOM 型不经过服务器、由前端 JS 触发。
- **输出编码 vs 输入校验**：编码防"输出被当代码"、是主防线；校验防"非法数据入库"，二者互补但都不能只靠一个。
- **XSS vs CSRF**：XSS 注入脚本盗用身份；CSRF 借浏览器自动带 Cookie 伪造操作（见 [[CSRF与SSRF]]）。

## 常见误区

- 前端用 JS 校验了输入格式，就能防住 XSS。
- 只要配置了 CSP，就不再做输出编码了。
- 存储型 XSS 只影响提交者自己，不会波及其他用户。

## 面试速答

> 🎯 XSS=把恶意脚本注入到他人浏览的页面执行，分反射/存储/DOM 型；防御纵深以"按输出上下文编码"为核心，配 CSP 限脚本源、HttpOnly/Secure/SameSite 护 Cookie、用会转义的框架。输入校验是补充不是主防线。
