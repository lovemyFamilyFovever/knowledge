# 注入类漏洞（SQL·命令·XXE）

> 📌 **导航**：本文是 **注入类漏洞** 词条，属 [[Web安全攻防实战指南]] 子词条。

## 定义

**一句话定义：** 注入类漏洞的共同本质是"用户输入被当成代码/指令执行"——典型有 SQL 注入（拼进语句）、OS 命令注入（拼进 shell）、XXE（XML 解析器允许外部实体）；根本防御是"把指令与数据分离"。

**通俗类比：** 像把顾客点的菜名直接写进厨房指令单——若菜名里塞了"顺便打开大门"，厨师照着做了。正确做法是菜名只当"数据"、指令模板固定，二者分开。

## 为什么需要它

只要把外部输入直接拼进解释器（SQL、shell、XML 解析），攻击者就能注入并执行非预期指令：拖库、绕过登录、读文件、命令执行、探测内网。注入长期居 OWASP 前列，是服务端最危险的一类漏洞。

## 核心机制

- **SQL 注入**：`WHERE u='$in' AND p='$pw'`，输入 `admin' --` 即注释掉密码校验；`UNION` 可拖其它表，甚至 `xp_cmdshell`/`LOAD_FILE`。**根治：参数化查询/预编译**（结构与数据分离，驱动自动转义），辅以存储过程、最小权限 DB 账号、ORM。
- **命令注入**：把输入拼进 `system()`/反引号，用 `;`、`|`、`$(...)` 追加命令；应改用数组化 exec、白名单参数、避免 shell 解释。
- **XXE**：解析 XML 时允许外部实体 → 读 `file:///etc/passwd`、SSRF、DoS；防御是**禁用外部实体解析**（或改 JSON）。

## 具体示例

参数化是 SQL 注入的根本解法——把值当参数传、永不拼进语句：

```python
# 有漏洞：拼接
cur.execute("SELECT * FROM u WHERE name='" + name + "'")
# 正确：参数化，结构与数据分离
cur.execute("SELECT * FROM u WHERE name=%s", (name,))
```

## 何时用与何时不用

- **用**：一切把外部输入送入解释器（SQL/shell/XML/LDAP）之处都要"分离 + 白名单 + 最小权限"。
- **不用**：别指望"过滤单引号/黑名单关键字"当主防线——变体太多、可绕过。

## 优劣与代价

✅ 参数化/预编译从结构上隔离指令与数据，比过滤可靠且性能可接受。
✅ 白名单 + 最小权限 + 禁外部实体，覆盖面广、可审计。
⚠️ 全面参数化需改造既有拼接代码、动态列名/排序等场景要另设白名单映射。
⚠️ 依赖 ORM/库的安全默认，误用原生接口仍可能重开缺口。

## 与相关概念的区别

- **参数化 vs 转义/过滤**：参数化从结构上隔离数据、最稳；手工转义/黑名单易漏。
- **SQLi vs 命令注入**：前者针对查询解释器、后者针对 OS shell，防御思路同为"别把输入当指令"。
- **XXE vs 普通解析错误**：XXE 是让解析器"去取外部资源"，危害等同 SSRF/文件读取，非仅解析慢。

## 常见误区

- 过滤掉单引号就能根治 SQL 注入。
- 用了 ORM 框架就绝对不会有注入。
- XXE 顶多让解析变慢一点，危害不大。

## 面试速答

> 🎯 注入类(SQL/命令/XXE)同源于"把用户输入当指令执行"：SQLi 用 admin' -- 绕登录、UNION 拖库；命令注入用 ; | 追加；XXE 借外部实体读文件/SSRF。根治统一是"指令与数据分离"——参数化查询、数组化 exec、禁用 XML 外部实体，配白名单与最小权限，别靠转义/黑名单。
