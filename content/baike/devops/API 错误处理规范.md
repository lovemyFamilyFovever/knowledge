# API 错误处理规范

> 📌 **导航**：本文是 **API 错误处理规范** 词条，属 [[API设计最佳实践]] 子词条。

## 定义

**一句话定义：** API 错误处理规范指用统一、机器可读的格式（典型如 RFC 7807 Problem Details）返回错误：稳定的错误码、正确的 HTTP 状态码、可读的标题/详情与可按类型编程处理的字段，且生产环境不外泄堆栈等敏感细节。

**通俗类比：** 像医院出具的标准化诊断单——病因（type）、诊断名（title）、严重程度（status）、具体说明（detail）都按固定栏填，不同医生（客户端）都能看懂、知道下一步怎么处理，而不是塞给你一张潦草便条。

## 为什么需要它

各家 API 各写各的错误体（有时一个字符串、有时随意结构），客户端只能靠猜和脆弱解析，难枚举、难本地化、难监控。统一错误格式让错误"可分类、可编程处理、可多语言、可观测"，并通过按环境控制详细度，既方便调试又不泄露内部信息。

## 核心机制

- **RFC 7807 Problem Details 标准字段**：`type`（标识问题类型的 URI，未必真可访问）、`title`（该类型简短描述）、`status`（HTTP 状态码，须与响应一致）、`detail`（本次具体情况）、`instance`（发生实例的标识），可扩展自定义字段。
- **错误分类**：401 认证 / 403 授权 / 400 校验 / 404 资源 / 429 限流 / 5xx 服务端，各有稳定 error code。
- **统一信封**：稳定字段 + 可选 `errors[]`（字段级校验明细）、`traceId`（串联日志）。
- **多语言与调试控制**：`message` 可按 locale 选择；仅 debug 模式返回堆栈/参数。

## 具体示例

一个符合 RFC 7807 的响应，客户端可按 `type`/`status` 稳定地分支处理：

```json
{
  "type": "https://api.example.com/problems/insufficient-funds",
  "title": "余额不足",
  "status": 403,
  "detail": "当前余额 50.00，交易需 100.00",
  "instance": "/accounts/12345/transactions/789"
}
```

## 何时用与何时不用

- **用**：任何对外/对内 HTTP API；尤其在 SDK、网关聚合、前端统一拦截、错误监控场景。
- **不用（弱化）**：纯内部、一次性脚本可简；但一旦形成公共契约就别再各写各的。

## 优劣与代价

✅ 错误可枚举、可编程处理、可本地化、可观测；契约稳定。
✅ 把"调试信息"与"对外信息"分离，安全可控。
⚠️ 需要全局异常处理与约定，团队要统一遵循。
⚠️ 过度嵌套的 details 反而难维护；type URI 设计要克制。

## 与相关概念的区别

- **HTTP 状态码 vs 错误体**：状态码给"类别"（4xx/5xx）、错误体给"机器可读细节"，两者都要、缺一不可。
- **`type` vs `code`**：`type` 是可文档化的问题类型 URI；很多团队另加稳定的字符串 `code` 便于客户端分支，二者互补。
- 与 [[RESTful API 设计]]：前者管"资源/动词/状态码"总体风格，本篇专管"出错了怎么标准化返回"。

## 常见误区

- HTTP 状态码给对了就够了，响应体里错误长什么样无所谓。
- 为了帮前端定位，生产环境的错误响应应直接返回异常堆栈。
- RFC 7807 的 type 字段必须是一个能真实访问到的 URL。

## 面试速答

> 🎯 API 错误处理 = 用统一机器可读格式（RFC 7807：type/title/status/detail/instance + 扩展）返回错误，配稳定 error code 与正确 HTTP 状态码，让客户端可按类型分支处理、可本地化、可监控；生产按环境屏蔽堆栈。状态码给类别、错误体给细节，缺一不可。
