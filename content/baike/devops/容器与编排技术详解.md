# 容器与编排技术详解

> 📌 **导航**：本文是 **容器与编排技术详解** 词条，属于 devops 术语集。相关枢纽：[[Docker容器化完全指南]]、[[Kubernetes云原生实战指南]]、[[Kubernetes深入]]、[[Web安全攻防实战指南]]、[[云服务详解]]。

## 定义

**一句话定义：** 容器把应用连同其依赖打包成共享主机内核、启动秒级的标准化镜像，编排系统则自动化地调度、扩缩和自愈成千上万个这样的容器。

**通俗类比：** 容器像标准化的"快递盒"，里面装着程序运行所需的一切；编排就是管理海量快递盒的自动化仓库系统——决定放哪个货架、坏了自动补、忙时加人手。

## 为什么需要它

容器解决了经典的"在我机器上能跑"：开发、测试、生产用同一个镜像，环境一致、启动快、比虚拟机轻得多。但当容器数量涨到几十上百、跨多台主机，谁来调度、实例挂了谁重启、流量变了谁扩容、彼此怎么发现和负载均衡？这就是编排要接管的大规模管理复杂度。

## 核心机制

- **容器的隔离与轻量**：靠 Linux 的 namespace（隔离视图）与 cgroup（限制资源）实现，共享宿主机内核，因此镜像小、秒级启动、单机可高密度运行。
- **镜像分层**：每条 Dockerfile 指令生成一层，可缓存、可复用，改一行不必重装全部依赖。
- **编排四件事**：调度（把 Pod 放到合适的节点）、自愈（挂了就重建）、伸缩（按负载增减副本）、服务发现与负载均衡（用稳定入口访问动态后端）。

## 具体示例

一份 Dockerfile 描述"基于 python:3.9-slim，装好依赖、带上代码、暴露 8000 端口并定义健康检查"，构建出的镜像在哪都跑出一样的环境；部署与扩缩则交给编排平台（见 [[Kubernetes深入]]）。

```dockerfile
FROM python:3.9-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
EXPOSE 8000
HEALTHCHECK CMD curl -f http://localhost:8000/health || exit 1
CMD ["python", "app.py"]
```

## 何时用与何时不用

- **用**：需要环境一致、快速交付、微服务拆分、弹性伸缩的云原生应用。
- **不用（容器）**：强隔离要求高的多租户内核级负载、依赖特定内核模块/GUI 的传统单体——虚拟机更合适。
- **不用（编排）**：只有一两个固定容器、不需伸缩与自愈——单跑 Docker 或 Compose 即可，别为一个小服务养一套 K8s。

## 优劣与代价

✅ 环境一致、启动快、密度高、天然适配微服务与弹性伸缩。
✅ 声明式编排带来自愈与滚动发布。
⚠️ 容器隔离弱于虚拟机，共享内核有逃逸面，需额外加固。
⚠️ 编排系统本身复杂、有运维成本与学习曲线。

## 与相关概念的区别

- **容器 vs 虚拟机**：容器共享宿主内核、更轻更薄；虚拟机带独立客户机内核、隔离更强但更重。
- **Docker vs Kubernetes**：Docker 构建并运行单个容器；Kubernetes 是跨主机编排大规模容器的平台。
- **Pod vs 容器**：Pod 是 K8s 最小调度单元，通常含一个容器，也可放多个紧密协作、共享网络的容器。
- **Sidecar vs Init Container**：Sidecar 与主容器并行运行提供辅助能力；Init Container 在主容器启动前跑完初始化任务即退出。

## 常见误区

- 容器和虚拟机是一回事，都只是把应用连系统打包起来。
- 用了 Docker 就自动解决了多机扩缩容与服务发现。
- Dockerfile 每加一行都会从头重装一遍全部依赖。

## 面试速答

> 🎯 容器把应用连依赖打包成共享内核、秒级启动的标准单元，解决"在我机器上能跑"；编排（K8s）再管成百上千容器的调度、自愈、伸缩与服务发现。
