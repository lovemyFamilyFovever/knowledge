# 基础设施即代码详解

> 📌 **导航**：本文是 **基础设施即代码详解** 词条，属于 devops 术语集。相关枢纽：[[Docker容器化完全指南]]、[[Kubernetes云原生实战指南]]、[[Kubernetes深入]]、[[Web安全攻防实战指南]]、[[云服务详解]]。

## 定义

**一句话定义：** 基础设施即代码（IaC）是用可版本化的代码文件来声明服务器、网络、数据库等基础设施，像管理应用代码一样管理环境的创建与变更。

**通俗类比：** 传统运维是亲自跑建材市场、一台台手搓服务器；IaC 是先画好图纸，再让机器人照图采购、施工、验收——图纸进 git，能重复盖出完全一致的楼。

## 为什么需要它

手点控制台会累积三类顽疾：环境不一致（测试能跑生产崩）、配置漂移（改一次没人记得改了啥）、重建困难（唯一那份"环境知识"在某人脑子里）。IaC 把环境变成代码：进版本控制可评审、可 `plan` 预览再 `apply`、可一键重建多套一致环境，把"运维知识"从个人经验变成团队资产。

## 做法

- **写**：用声明式 DSL 描述期望状态（要 3 台什么规格的机器、开哪些端口）。
- **审**：代码走 PR 评审，变更可追溯，替代口头和手点。
- **预览**：`terraform plan` 先算出将增删改哪些资源，人确认后再执行。
- **收敛**：`apply` 让真实环境逼近声明；控制器持续调和，漂移可被检测。
- 主流工具：Terraform / OpenTofu（供给 provisioning）、Ansible / Puppet / Chef（配置管理）、Pulumi（用通用语言写）。

## 具体示例

一份 Terraform 清单声明"在美西开一台 t2.micro 并打上名字标签"，`apply` 后云端即收敛到该状态——注意你只描述"要什么"，不写"先建 VPC 再建子网"这类步骤。

```hcl
provider "aws" { region = "us-west-2" }

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  tags          = { Name = "WebServer" }
}
```

## 何时用与何时不用

- **用**：多环境（dev/staging/prod）需一致、云资源频繁创建销毁、要审计与回滚基础设施变更。
- **不用**：一次性、几天就废弃的临时试验环境——写清单 + 配后端状态的成本可能高过手点。

## 优劣与代价

✅ 一致、可重复、可版本化、可评审，重建与灾备成本低。
✅ 与 GitOps 结合可让"提交即部署"、状态自动收敛。
⚠️ 引入学习曲线与状态管理（remote state、锁）等新复杂度。
⚠️ 一旦权限与密钥管理不当，自动化会成倍放大误操作的影响面。

## 与相关概念的区别

- **声明式 vs 命令式**：声明式说"要什么"（3 台服务器），命令式说"怎么做"（先建 VPC 再建子网）；前者由工具负责收敛。
- **Terraform vs Ansible**：Terraform 偏基础设施供给（声明式），Ansible 偏配置管理（过程式任务编排），常互补。
- **不可变 vs 可变基础设施**：不可变是更新时整台替换而非原地改，天然消除漂移；可变则原地 SSH 修改。
- **GitOps vs 传统 CI/CD**：GitOps 以 Git 为唯一真相源、由集群侧自动拉齐；传统 CI/CD 多靠流水线单向推送。

## 常见误区

- 用 IaC 就是把一堆 shell 脚本 ssh 上去挨台手动跑一遍。
- 线上出问题先手动改一下最快，回头再同步进代码不迟。
- 只要用了 Terraform 或 Ansible，就自动获得了不可变基础设施。

## 面试速答

> 🎯 IaC = 用可版本化的代码声明期望的基础设施，纳入 git、可 plan 预览、可重复 apply，从根上消灭手点控制台和配置漂移。
