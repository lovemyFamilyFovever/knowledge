# API设计最佳实践

> 📌 **导航**：本页是 **API 设计最佳实践** 枢纽。各主题已收敛到专条，本页只做索引与选型；重复内容不再展开。

## 定义

**一句话定义：** API 设计最佳实践是构建可长期演进的 HTTP 接口时应遵循的一组工程约定，涵盖资源与成熟度风格、版本管理、分页过滤排序、契约规范、认证授权与标准化错误处理。

**通俗类比：** 像为城市设计路牌系统——命名规范、分叉有版本、给错方向要说清楚（错误码）、外地人能按图索骥（契约），而不是每条街各立各的牌子。

## 为什么需要它

API 一旦发布就是契约，改不动、也退不回。设计得好，客户端稳定、服务端可持续演进；设计得差，则版本爆炸、错误五花八门、集成方各写各的适配。最佳实践把"如何对外承诺一套可长期维护的接口"沉淀为可复用的清单。

## 具体示例

一次设计评审的取舍顺序：先用 [[RESTful API 设计]] 定资源与状态码 → 用 [[OpenAPI 规范]] 把契约写成文档 → 预计会破坏性变更就按 [[API 分页与版本控制]] 选版本策略 → 用 [[OAuth 与 JWT]] 定鉴权 → 用 [[API 错误处理规范]] 统一出错时的返回形状。

## 何时用与何时不用

- **用**：任何对外或跨团队共享的 HTTP API；尤其需要 SDK、网关聚合、可观测与长期演进时。
- **不用**：纯内部一次性胶水调用可轻量，但一旦成为公共契约就应全面遵循，别"先糙着以后再说"。

## 优劣与代价

✅ 契约稳定、可演进、可生成客户端、错误可处理，降低集成与维护成本。
✅ 主题分层，各专条可独立深化。
⚠️ 过度设计（过早 vN、过度 HATEOAS）会增加复杂度与表面。
⚠️ 规范要靠团队纪律与网关/脚手架统一执行，否则形同虚设。

## 与相关概念的区别

- **本页 vs [[API设计]]（架构视角）**：架构侧偏"选哪种 API 风格"，本页从运维/交付视角串起版本、鉴权、错误等落地约定。
- **契约（OpenAPI）vs 风格（REST）**：一个把接口形式写死成机器可读文档，一个规定资源化设计与动词/状态码用法。

## 常见误区

- 只靠 HTTP 状态码就能表达所有错误，响应体里不必统一格式。
- API 版本维护得越多，就越灵活、越能兼容。
- 写了一份 OpenAPI 文档，就等于 API 设计做好了。

## 面试速答

> 🎯 API 设计最佳实践是"可长期演进的 HTTP 接口"清单：资源与状态码风格(REST/HATEOAS)、版本管理、分页过滤排序、OpenAPI 契约、OAuth/JWT 鉴权、RFC 7807 标准错误。一旦发布即契约，重在稳定、可演进、错误可编程处理。细节见各专条。
