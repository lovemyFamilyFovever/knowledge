## **1. 进程管理：操作系统的基本单元**

进程是操作系统进行资源分配和调度的基本单位。理解进程管理是理解内核的第一步。

### **1.1 进程状态机与生命周期**
一个进程从创建到消亡，会经历一系列状态转换。现代Linux内核中，进程状态（在`task_struct`中定义）主要包括：

- **TASK_RUNNING (R)**: 可运行状态。进程要么正在CPU上执行，要么在运行队列中等待调度。
- **TASK_INTERRUPTIBLE (S)**: 可中断睡眠。进程正在等待某个事件（如I/O完成、信号量），可以被信号唤醒。
- **TASK_UNINTERRUPTIBLE (D)**: 不可中断睡眠。与`S`类似，但不会被信号打断，通常用于等待必须不受干扰的I/O（如磁盘物理操作）。
- **__TASK_STOPPED (T)**: 停止状态。进程被信号（如`SIGSTOP`、`SIGTSTP`）暂停执行。
- **__TASK_TRACED (t)**: 被调试器等跟踪进程跟踪时的状态。
- **EXIT_ZOMBIE (Z)**: 僵尸进程。进程已终止，但其父进程尚未通过`wait()`系统调用回收其描述符，以保存退出状态。
- **EXIT_DEAD (X)**: 最终状态，资源被彻底回收。

**状态转换图示例**：
```
fork() -> [RUNNING] -> (等待事件) -> [SLEEPINT] -> (事件发生) -> [RUNNING]
         -> (收到SIGSTOP) -> [STOPPED] -> (收到SIGCONT) -> [RUNNING]
         -> (exit()) -> [ZOMBIE] -> (父进程wait()) -> [DEAD]
```

### **1.2 CFS（完全公平调度器）深度解析**
CFS是Linux默认的进程调度器，其设计哲学是“完全公平”，即理想模型下，所有可运行进程应获得相同比例的CPU时间。

**核心思想与数据结构**：
- CFS不再维护传统的时间片，而是使用**虚拟运行时间 (vruntime)** 来衡量一个进程的运行时间。`vruntime`的计算公式大致为：`vruntime += delta_exec * NICE_0_WEIGHT / weight`。其中`weight`与进程的nice值相关（nice值越低，权重越高，`vruntime`增长越慢，从而能获得更多的CPU时间）。
- 所有可运行的`task_struct`通过其成员`se`（`sched_entity`）组织在一颗**红黑树**中。红黑树的键值就是`vruntime`。CFS每次选择`vruntime`最小的进程（即红黑树最左节点）来执行，这保证了公平性。

**代码片段（内核简化）**：
```c
// 内核源码: kernel/sched/fair.c
static struct sched_entity *__pick_first_entity(struct cfs_rq *cfs_rq)
{
    struct rb_node *left = rb_first_cached(&cfs_rq->tasks_timeline);
    if (!left)
        return NULL;
    return rb_entry(left, struct sched_entity, run_node);
}

// 更新进程的vruntime
static void update_curr(struct cfs_rq *cfs_rq)
{
    struct sched_entity *curr = cfs_rq->curr;
    u64 now = rq_clock_task(rq_of(cfs_rq));
    u64 delta_exec = now - curr->exec_start;
    // ... 计算权重 ...
    curr->vruntime += calc_delta_fair(delta_exec, curr);
    // ...
}
```

**案例分析**：
假设有两个进程A（nice=0, 权重1024）和B（nice=5, 权重335）。当它们各运行一个真实时间片`delta_exec`后：
- A的`vruntime`增量： `Δ * 1024/1024 = Δ`
- B的`vruntime`增量： `Δ * 1024/335 ≈ 3.06Δ`
显然，B的`vruntime`增长更快，因此它会更快地被“追赶”，从而获得更少的CPU时间，这体现了nice值对公平性的调整。

### **1.3 进程间通信 (IPC)**
IPC是进程协作的基石。Linux提供多种机制：

1.  **管道 (Pipe)**：最古老的IPC。匿名管道（`pipe()`）用于具有亲缘关系的进程间；命名管道（FIFO）可用于任意进程。本质上是一个内核缓冲区，采用生产者-消费者模型。
    ```c
    int fd[2];
    pipe(fd); // fd[0]读，fd[1]写
    if (fork() == 0) {
        close(fd[0]); // 子进程关闭读端
        write(fd[1], “hello”, 5);
    } else {
        close(fd[1]); // 父进程关闭写端
        read(fd[0], buf, 5);
    }
    ```

2.  **消息队列**：允许进程以消息为单位传递数据，具有类型和优先级。相关系统调用：`msgget`, `msgsnd`, `msgrcv`。

3.  **共享内存**：最快的IPC。多个进程将同一块物理内存映射到各自的虚拟地址空间。需要同步机制（如信号量）来保护。
    ```c
    int shmid = shmget(IPC_PRIVATE, SIZE, 0666);
    char *shm = shmat(shmid, NULL, 0);
    strcpy(shm, “shared data”); // 写入
    // ... 其他进程通过shmat附加后可读取 ...
    shmdt(shm); // 分离
    ```

4.  **信号 (Signal)**：异步通知机制，用于通知进程发生了某个事件（如`SIGKILL`、`SIGSEGV`）。信号处理函数可以由用户自定义。

5.  **套接字 (Socket)**：不仅可用于网络通信，也可用于同一台机器上的进程间通信（Unix Domain Socket），功能强大且通用。

**深度案例：匿名管道的内核实现**
当你调用`pipe()`时，内核会创建一个`pipe_inode_info`结构体，并分配一个环形缓冲区（通常为64KB）。文件描述符`fd[0]`和`fd[1]`指向同一个`file`对象，但分别关联到`pipe_read`和`pipe_write`操作。写操作将数据复制到内核缓冲区，读操作从缓冲区复制数据。当缓冲区满时`write`阻塞，空时`read`阻塞。

## **2. 线程与并发：提升执行效率的利器**

### **2.1 用户态线程 vs. 内核态线程**
这是理解现代并发编程的关键。

- **内核级线程 (KLT)**：由内核直接管理和调度。创建、销毁、切换都通过系统调用，开销较大。Linux中的`pthread_create`默认创建的就是KLT，它通过`clone()`系统调用实现，与进程共享地址空间等资源。**优点**：当一个线程阻塞时（如进行I/O），内核可以调度同一进程的其他线程运行，充分利用多核。这是**一对一**模型。

- **用户级线程 (ULT)**：完全在用户空间实现，通过线程库（如早期的Green Threads）管理，内核对此无感知。创建、销毁、切换开销小，非常快。**致命缺点**：内核调度单位是进程。只要一个ULT阻塞（哪怕是I/O），整个进程就会被阻塞，导致该进程内的所有ULT都无法运行。这是**多对一**模型，现已少用。

- **混合模型**：结合二者优点。M个ULT映射到N个KLT上（M>N）。线程库在用户态管理ULT的调度，而内核负责KLT的调度。这提供了灵活性，但实现复杂。现代操作系统主要依赖KLT模型。

**案例分析**：
假设一个Web服务器进程有4个KLT（线程）。当一个线程因等待数据库响应而阻塞时，内核可以立即将CPU分配给该进程的另外3个就绪线程，继续处理其他请求。如果使用纯ULT，整个服务器将卡住。

### **2.2 线程同步原语**
同步的目的是协调对共享资源的访问，避免竞态条件。

1.  **互斥锁 (Mutex)**：最基础的同步原语。同一时刻只有一个线程可以持有锁。
    ```c
    pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
    pthread_mutex_lock(&lock); // 进入临界区
    // ... 访问共享资源 ...
    pthread_mutex_unlock(&lock); // 离开临界区
    ```
    *内核实现*：用户态`pthread_mutex`通常先尝试原子操作（自旋），失败后才通过`futex`系统调用陷入内核睡眠，这结合了自旋锁和睡眠锁的优点。

2.  **读写锁 (RWLock)**：允许多个读者同时持有锁，但写者独占。适用于读多写少的场景。
    ```c
    pthread_rwlock_t rwlock;
    pthread_rwlock_rdlock(&rwlock); // 读加锁
    pthread_rwlock_wrlock(&rwlock); // 写加锁
    ```

3.  **条件变量 (Condition Variable)**：用于线程间基于某个条件的等待/通知。必须与互斥锁配合使用。
    ```c
    pthread_mutex_lock(&lock);
    while (condition == false) { // 防止虚假唤醒
        pthread_cond_wait(&cond, &lock); // 原子地释放锁并等待
    }
    // ... 条件满足，执行操作 ...
    pthread_mutex_unlock(&lock);

    // 另一端
    pthread_mutex_lock(&lock);
    condition = true;
    pthread_cond_signal(&cond); // 唤醒一个等待线程
    pthread_mutex_unlock(&lock);
    ```

4.  **自旋锁 (Spinlock)**：在等待锁时，线程会忙循环（自旋），不释放CPU。适用于锁持有时间极短、且不希望发生上下文切换的场景（如内核中断处理中）。用户态编程中应谨慎使用。

5.  **原子操作 (Atomic Operations)**：通过CPU指令（如x86的`cmpxchg`）保证操作的不可分割性。是最底层的同步基石。
    ```c
    #include <stdatomic.h>
    atomic_int shared_counter = 0;
    atomic_fetch_add(&shared_counter, 1); // 原子加1
    ```

**深度案例：生产者-消费者问题（使用条件变量）**
```c
#define QUEUE_SIZE 10
int queue[QUEUE_SIZE];
int count = 0; // 当前元素数量
pthread_mutex_t mutex;
pthread_cond_t cond_producer, cond_consumer;

void *producer(void *arg) {
    while (1) {
        pthread_mutex_lock(&mutex);
        while (count == QUEUE_SIZE) { // 队列满，等待
            pthread_cond_wait(&cond_producer, &mutex);
        }
        queue[count++] = produce_item(); // 生产
        pthread_cond_signal(&cond_consumer); // 通知消费者
        pthread_mutex_unlock(&mutex);
    }
}

void *consumer(void *arg) {
    while (1) {
        pthread_mutex_lock(&mutex);
        while (count == 0) { // 队列空，等待
            pthread_cond_wait(&cond_consumer, &mutex);
        }
        int item = queue[--count]; // 消费
        pthread_cond_signal(&cond_producer); // 通知生产者
        pthread_mutex_unlock(&mutex);
        process_item(item);
    }
}
```
这个经典模型清晰地展示了互斥锁、条件变量和共享状态的协作关系。

## **3. 内存管理：构建虚拟世界**

内存管理是操作系统最复杂的子系统之一，它通过虚拟化技术，为每个进程提供独立、连续的地址空间，并负责高效的物理内存分配与回收。

### **3.1 虚拟内存与页表**
每个进程看到的地址是**虚拟地址**。CPU中的**内存管理单元 (MMU)** 负责将虚拟地址转换为物理地址。转换的核心是**页表 (Page Table)**。

- **分页**：虚拟地址空间和物理内存被划分为固定大小的单元（通常4KB），称为**页 (Page)** 和**页帧 (Frame)**。
- **多级页表**：为了节省存储页表本身所需的内存（一个32位进程就需要4MB来存一级页表），现代系统采用多级页表。x86-64使用**四级页表**：PGD -> PUD -> PMD -> PTE。
    - **PGD (Page Global Directory)**：顶级页目录。
    - **PUD (Page Upper Directory)**
    - **PMD (Page Middle Directory)**
    - **PTE (Page Table Entry)**：最终页表项，包含物理页帧号、存在位、读写权限、访问位等标志。

**虚拟地址解析示例（x86-64）**：
一个48位虚拟地址被拆分为：
`[PGD索引 (9位)] [PUD索引 (9位)] [PMD索引 (9位)] [PTE索引 (9位)] [页内偏移 (12位)]`
MMU通过CR3寄存器找到PGD基地址，然后像“查字典”一样，通过索引逐级查找，最终得到物理地址。

### **3.2 TLB (Translation Lookaside Buffer)**
每次地址转换都要访问4次内存，速度无法接受。TLB是MMU中的一个高速缓存，缓存最近使用的虚拟页到物理页帧的映射。
- **TLB命中**：直接获得物理地址，速度极快。
- **TLB未命中**：由硬件或操作系统（取决于架构）遍历页表，找到映射后存入TLB，然后重新执行转换。
- **上下文切换时**，TLB可能被刷新（或通过ASID标记区分不同进程的条目），这是切换开销的来源之一。

### **3.3 页面置换算法**
当物理内存不足时，内核需要选择一个页面换出（swap out）到磁盘，以便为新页面腾出空间。常用算法有：

- **LRU (Least Recently Used)**：置换最近最少使用的页面。理论上最优，但精确实现需要维护一个全局的页面访问链表，开销巨大。
- **时钟算法 (Clock)**：LRU的近似。所有页面组成一个环形链表，有一个“时钟指针”。页面有一个“访问位”。当需要置换时，指针扫描，将扫描到的页面的访问位清零。如果遇到一个访问位已经是0的页面，则置换它。这是现代系统的常用基础算法。
- **LFU (Least Frequently Used)**：置换访问频率最低的页面。可能由于历史热点页面而无法及时置换。

**内核实现：双链表策略 (Active/Inactive Lists)**
Linux内核采用更复杂的策略。维护两个链表：**活跃链表 (active_list)** 和 **非活跃链表 (inactive_list)**。
1.  新页面加入`inactive_list`头部。
2.  当页面被再次访问（在`inactive_list`中），它被提升到`active_list`。
3.  需要置换时，内核从`inactive_list`尾部选择页面进行回收。
4.  如果`active_list`过大，其尾部页面会被降级到`inactive_list`。
这种方式结合了访问频率和“老化”机制，高效地近似LRU。

### **3.4 NUMA (Non-Uniform Memory Access)**
在拥有多个CPU插槽的大型服务器上，每个CPU都有自己的本地内存，访问速度快。访问其他CPU的内存则需通过互联总线，速度慢。这就是NUMA架构。
- **内核支持**：Linux内核的NUMA调度器和内存分配器会尽力让进程在CPU上运行时，使用该CPU本地节点的内存。
- **`numactl`工具**：可以查看NUMA拓扑，并控制进程的内存分配策略。
    ```bash
    numactl --hardware # 显示NUMA拓扑
    numactl --cpubind=0 --membind=0 ./my_program # 将程序绑定到节点0的CPU和内存
    ```

## **4. 文件系统：数据的持久化组织**

文件系统是用户感知数据存储的接口，它在磁盘等块设备上组织数据和元数据。

### **4.1 VFS (Virtual File System) 层**
VFS是内核中的一个抽象层，它定义了一套通用的文件系统接口（`struct file_operations`, `struct inode_operations`等）。所有具体文件系统（ext4, XFS, Btrfs）都实现这些接口。

**关键数据结构**：
- **超级块对象 (`superblock`)**：代表一个已安装的文件系统，包含元数据信息。
- **索引节点对象 (`inode`)**：代表一个文件，包含文件的元数据（权限、大小、时间戳、数据块位置指针）。
- **目录项对象 (`dentry`)**：将文件名连接到`inode`，缓存在内存中以加速路径查找。
- **文件对象 (`file`)**：代表一个被进程打开的文件，包含文件偏移量、访问模式等。一个`inode`可以对应多个`file`对象（多个进程打开同一文件）。

**调用流程**：用户程序调用`read()` -> C库 -> `read`系统调用 -> VFS的`vfs_read()` -> 通过`file->f_op->read`调用具体文件系统的读方法。

### **4.2 主流文件系统比较**
1.  **ext4 (Fourth Extended Filesystem)**：
    - Linux长期默认文件系统，非常成熟稳定。
    - 使用**扩展区 (Extent)** 管理连续数据块，减少碎片。
    - 支持日志 (Journaling)，保证崩溃一致性。
    - 最大文件大小16TB，最大卷大小1EB。

2.  **XFS**：
    - 高性能文件系统，擅长处理大文件和高并发I/O。
    - 采用**分配组 (Allocation Group)** 并行化管理，减少锁竞争。
    - 使用B+树管理空闲空间和索引节点，扩展性极佳。
    - 是RHEL等发行版的默认选择。

3.  **Btrfs (B-tree File System)**：
    - 新一代“写时复制 (CoW)”文件系统，功能丰富。
    - **特性**：内建卷管理（LVM）、快照、校验和（保证数据完整性）、透明压缩、RAID支持。
    - 设计灵活，但复杂性高，曾一度被视为ext4的继任者，但稳定性仍需在严苛环境中验证。

### **4.3 日志机制 (Journaling)**
为防止因突然断电或系统崩溃导致文件系统元数据（或数据）不一致，日志文件系统引入了“日志”或“预写日志 (WAL)”。
- **工作原理**：
    1.  **写日志**：在修改文件系统元数据（如分配一个块）之前，先将“意图”（例如“准备将块A分配给inode B”）写入一个称为日志的特殊区域。
    2.  **提交**：当日志记录被安全写入磁盘后，才被认为操作完成。
    3.  **Checkpoint**：之后，在某个时刻，将真正的元数据修改写入文件系统主区域。
    4.  **恢复**：系统重启时，只需检查日志区域，重放或丢弃未完成的操作，即可快速恢复一致性。

- **数据模式**：
    - `journal`：元数据和数据都写日志，最安全但最慢。
    - `ordered`（默认）：只对元数据写日志，但保证数据在元数据日志提交前写入磁盘。
    - `writeback`：只对元数据写日志，数据和元数据顺序不保证，最快但风险较高。

## **5. I/O模型：连接世界的桥梁**

I/O模型定义了应用程序与操作系统内核交互以进行输入/输出的方式。

### **5.1 阻塞I/O (Blocking I/O)**
最简单的模型。当进程发起一个I/O系统调用（如`read`）后，如果数据未就绪，进程将被挂起，进入睡眠状态，直到数据被拷贝到用户空间。期间进程无法做任何事。

### **5.2 非阻塞I/O (Non-blocking I/O)**
通过设置套接字为`O_NONBLOCK`。`read`调用如果数据未就绪，不会阻塞，而是立即返回一个错误码（如`EAGAIN`）。进程需要不断地轮询内核，检查数据是否就绪。这会导致CPU空转，效率低下。

### **5.3 I/O多路复用 (I/O Multiplexing)**
允许单个线程监视多个文件描述符，直到其中一个或多个就绪。主要有三种API：
- **select/pselect**：使用位图表示fd集合，有最大fd数量限制（通常1024）。每次调用都需要将fd集合从用户态拷贝到内核态，并且内核需要遍历所有fd。
- **poll**：使用结构体数组，没有最大fd限制，但同样需要拷贝和遍历。
- **epoll**：Linux的高性能解决方案。
    - **`epoll_create`**：创建一个epoll实例。
    - **`epoll_ctl`**：向实例中添加、删除或修改要监控的fd。
    - **`epoll_wait`**：阻塞，直到有fd就绪，返回就绪的fd列表。
    - **关键优势**：通过回调机制，只将就绪的fd返回给用户，避免了无差别遍历。且fd集合保存在内核中，无需重复拷贝。

**epoll代码片段（LT模式 - 水平触发）**：
```c
int epfd = epoll_create1(0);
struct epoll_event ev, events[MAX_EVENTS];
ev.events = EPOLLIN;
ev.data.fd = listenfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, listenfd, &ev);

while (1) {
    int nfds = epoll_wait(epfd, events, MAX_EVENTS, -1);
    for (int i = 0; i < nfds; ++i) {
        if (events[i].data.fd == listenfd) {
            // 有新连接到来，accept...
            // 将新的connfd加入epoll监控
        } else {
            // 已有连接有数据可读
            handle_client(events[i].data.fd);
        }
    }
}
```

### **5.4 io_uring：Linux异步I/O的新纪元**
`io_uring` 是 Linux 5.1 引入的高性能、通用异步I/O框架。它旨在解决传统AIO的局限性，并提供统一的异步接口。

**核心设计**：
- **两个环形缓冲区 (Ring Buffer)**：
    - **提交队列 (Submission Queue, SQ)**：用户态程序将I/O请求（如“读fd=3的4096字节数据到buf地址”）放入SQ。
    - **完成队列 (Completion Queue, CQ)**：内核处理完请求后，将结果放入CQ。
- **零拷贝与无系统调用**：用户态和内核态共享内存。提交和收割操作通过修改共享内存中的索引完成，无需系统调用（在需要内核唤醒时才使用）。通过`io_uring_enter`系统调用进行批量提交和收割。

**使用步骤**：
1.  `io_uring_setup()`：初始化io_uring实例。
2.  通过`mmap`映射SQ和CQ到用户空间。
3.  填充SQE（Submission Queue Entry）描述I/O操作。
4.  更新SQ的tail指针，通知内核有新请求（可选`io_uring_enter`）。
5.  内核异步处理请求，并更新CQ。
6.  用户态检查CQ的head指针，获取已完成请求的结果。

**优势**：极高的吞吐量，减少了用户态-内核态切换和数据拷贝，是Linux下未来异步编程的基石。

## **6. 系统调用和中断处理**

### **6.1 系统调用**
系统调用是用户进程请求内核服务的唯一合法接口（除了异常和陷入）。

**执行流程（以x86-64为例）**：
1.  用户程序调用C库封装函数（如`read()`）。
2.  C库将系统调用号放入`rax`寄存器，参数放入`rdi`, `rsi`, `rdx`等寄存器。
3.  执行`syscall`指令。CPU从用户态（Ring 3）切换到内核态（Ring 0），并跳转到内核预设的入口点（`entry_SYSCALL_64`）。
4.  内核入口代码保存用户态现场，根据`rax`中的系统调用号，在**系统调用表 (`sys_call_table`)** 中查找对应的处理函数（如`sys_read`）。
5.  执行`sys_read`，进行权限检查、参数验证，并执行实际功能。
6.  将返回值放入`rax`。
7.  执行`sysret`或`iret`指令，恢复用户态现场，返回用户空间。

### **6.2 中断处理**
中断是硬件设备通知CPU有事件发生的电信号。分为：
- **硬中断**：由外部设备（如网卡、磁盘）产生。CPU立即打断当前执行流，跳转到中断描述符表 (IDT) 中注册的**中断服务程序 (ISR)**。
- **软中断**：由CPU指令（如`int 0x80`）或内核自身机制（如延迟的网络数据包处理）触发。

**中断处理流程**：
1.  CPU响应中断，保存当前上下文。
2.  根据中断号在IDT中找到对应的中断处理函数。
3.  进入中断上下文（不能睡眠）。
4.  执行**上半部 (Top Half)**：快速处理紧急、必须立即完成的工作（如从设备寄存器读取数据，应答中断）。
5.  调度**下半部 (Bottom Half)**：处理耗时的数据处理工作。下半部机制包括**软中断 (softirq)**、**tasklet**和**工作队列 (workqueue)**。下半部可以在更宽松的上下文中执行。

**网络包处理案例**：
1.  网卡收到数据包，通过DMA写入内存，然后触发一个硬中断。
2.  ISR被调用，仅做最少的工作：确认中断，将数据包挂在输入队列，并触发一个`NET_RX_SOFTIRQ`软中断。
3.  ISR返回，软中断在合适的时机被内核处理，负责将数据包从内核缓冲区传递到协议栈（如TCP/IP），最终唤醒阻塞在`recv()`上的用户进程。

## **7. 设备驱动模型**

设备驱动是内核中用于与特定硬件设备通信的代码。

### **7.1 Linux设备驱动模型 (Device Model)**
Linux采用面向对象的设备模型来统一管理设备、总线和驱动。

**核心数据结构**：
- **`struct device`**：代表一个硬件设备。包含设备名称、父设备、所属总线、驱动指针、电源管理状态等。所有设备链接在一个树状结构中（`/sys/devices`）。
- **`struct device_driver`**：代表一个设备驱动程序。包含驱动名称、所属总线、探测(`probe`)和移除(`remove`)函数等。
- **`struct bus_type`**：代表一种总线类型（如PCI, USB, I2C）。负责将设备与驱动进行匹配。

**工作流程**：
1.  **注册驱动**：驱动模块加载时，向总线注册一个`driver`。
2.  **注册设备**：当系统发现一个新设备（如PCI枚举）时，向总线注册一个`device`。
3.  **匹配**：总线遍历其下的所有设备和驱动，调用总线的`match()`方法（通常比较设备ID和驱动支持的ID表）来匹配设备和驱动。
4.  **探测**：匹配成功后，总线调用驱动的`probe()`函数。驱动在`probe`中初始化硬件，注册字符/块/网络设备等。

### **7.2 sysfs与uevent**
- **sysfs (`/sys`)**：一个虚拟文件系统，将内核设备模型的数据结构（设备、驱动、总线）以文件和目录的形式导出到用户空间。`udev`等工具通过读取sysfs信息来动态创建设备节点。
- **uevent**：当设备被添加或移除时，内核通过`netlink`套接字向用户空间发送`uevent`消息，触发`udev`规则，自动加载驱动、创建设备节点（如`/dev/sda`）、设置权限。

## **8. 容器与隔离：Namespace与Cgroups**

容器技术是轻量级的操作系统级虚拟化。

### **8.1 Namespace**
Namespace是Linux内核提供的资源隔离方案，它使得容器内的进程觉得自己拥有独立的全局资源。
- **PID Namespace**：隔离进程ID。容器内的进程有独立的PID 1（init进程），看不到容器外的进程。
- **Network Namespace**：隔离网络设备、IP地址、路由表、防火墙规则等。每个容器有独立的网络栈。
- **Mount Namespace**：隔离文件系统挂载点。容器有自己的根文件系统。
- **UTS Namespace**：隔离主机名和域名。
- **IPC Namespace**：隔离信号量、消息队列、共享内存。
- **User Namespace**：隔离用户和组ID，允许容器内的root映射为宿主机的非root用户。

**创建Namespace**：主要通过`clone()`和`unshare()`系统调用。
```c
// 使用clone创建一个在新PID和Network namespace中运行的子进程
int child_pid = clone(child_func, stack+STACK_SIZE,
                      CLONE_NEWPID | CLONE_NEWNET | SIGCHLD, NULL);
```

### **8.2 Cgroups (Control Groups)**
Cgroups用于限制、统计和隔离进程组的资源使用（如CPU、内存、I/O、网络带宽）。
- **子系统 (Subsystem)**：每种资源是一个子系统，如`cpu`、`memory`、`blkio`、`cpuset`。
- **层次结构 (Hierarchy)**：子系统组织成树状层次结构。
- **控制组 (cgroup)**：树中的一个节点，包含一组进程。通过在cgroup目录下设置参数文件（如`memory.limit_in_bytes`）来限制资源。

**案例：使用cgroup v2限制容器内存**
```bash
# 创建一个cgroup
mkdir /sys/fs/cgroup/my-container
# 限制内存使用为100MB
echo 104857600 > /sys/fs/cgroup/my-container/memory.max
# 将进程PID加入该cgroup
echo $PID > /sys/fs/cgroup/my-container/cgroup.procs
```
Docker、Kubernetes等容器平台在底层正是通过组合Namespace和Cgroups来实现容器的创建和资源管理。

## **9. 安全机制：内核的护城河**

### **9.1 SELinux (Security-Enhanced Linux)**
一个强制访问控制 (MAC) 系统。它为系统中的所有主体（进程）和客体（文件、套接字等）定义了安全上下文（如`user:role:type:level`），并制定了一套细粒度的策略规则，规定哪个类型的进程可以访问哪个类型的资源，**即使进程是root**。

**案例**：Web服务器进程（`httpd_t`类型）试图访问`/etc/shadow`文件（`shadow_t`类型）。SELinux策略规则可能拒绝此操作，即使进程是root，从而防止了权限提升攻击。

### **9.2 Seccomp (Secure Computing)**
Seccomp用于限制进程可以执行的系统调用。它可以大幅减少内核攻击面。
- **模式**：`SECCOMP_MODE_STRICT`（只允许`read`, `write`, `exit`）和`SECCOMP_MODE_FILTER`（允许自定义BPF过滤器）。
- **应用**：Chrome沙箱、容器运行时、某些数据库进程使用Seccomp来约束自身和子进程，即使被攻破，攻击者也无法滥用危险的系统调用（如`execve`, `ptrace`）。
