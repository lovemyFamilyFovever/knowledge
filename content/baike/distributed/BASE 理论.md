# BASE 理论

## 定义

**一句话定义：** BASE 理论是分布式系统中对 CAP 里"一致性 vs 可用性"权衡的一种实践指导思想,主张牺牲强一致以换取高可用,其三大含义为:基本可用(Basically Available)、软状态(Soft state)、最终一致(Eventual consistency)。

**通俗类比：** 像跨行转账——你转出后,对方账户不是"瞬间"到账(不强求实时一致),但系统保证"基本能用"(可提交、可查询),中间允许"到账中"这种过渡状态(软状态),并最终保证钱一定到(最终一致)。

> 多义说明:BASE 与 ACID(强一致事务)相对,是"最终一致"路线的经验总结,常与 CAP、PACELC 一起讨论。本文讲 BASE 三要素。

## 原理与机制

- **Basically Available(基本可用):** 出现故障时允许损失部分可用性(如响应变长、功能降级),但核心功能仍可用。
- **Soft state(软状态):** 允许系统存在中间状态(数据在多副本间同步过程中的不一致),且认为它不影响整体可用。
- **Eventual consistency(最终一致):** 经过一段时间后,所有副本最终达到一致状态。
- **与 CAP 的关系:** 当分区(P)不可避免时,BASE 倾向选择 AP(可用 + 分区容忍),以最终一致替代强一致。

## 关键组成

| 要素 | 含义 |
|------|------|
| 基本可用 | 故障时保核心、可降级 |
| 软状态 | 允许中间不一致状态 |
| 最终一致 | 一段时间后副本收敛 |
| 对照 ACID/CAP | 弱一致高可用路线 |

## 应用场景

- 互联网大规模分布式系统
- 电商订单/库存的最终一致处理
- 跨地域多活架构
- NoSQL(Dynamo / Cassandra 风格)、消息驱动的异步一致性

## 优点与局限

- 优点:高可用、高扩展、容忍分区与故障,适合互联网规模。
- 局限:一致性弱(可能读到旧值);业务需处理中间态与补偿;调试与对账复杂;不适合强一致场景(如金融核心账务需另设强一致环节)。

## 常见误区

- BASE ≠ 不要一致性:它要的是"最终一致",不是"不一致"。
- BASE 与 ACID 并非完全对立,可在不同环节混合使用。
- 软状态是"允许暂时不一致",不是"永远不一致"。
- 最终一致没有明确的时间上界。
