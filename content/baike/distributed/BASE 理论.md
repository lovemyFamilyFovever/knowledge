# BASE 理论


> 📌 **导航**：本文是 **BASE 理论** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** BASE 是对 CAP 里"可用 vs 强一致"权衡的工程路线，主张牺牲强一致换取高可用，三要素为基本可用、软状态、最终一致。

**通俗类比：** 像跨行转账——转出后对方不是"瞬间"到账，系统只保证基本可用、允许"到账中"的中间态，并最终一定到账。

> 多义说明：BASE 与 ACID（强一致事务）相对，是"最终一致"路线的经验总结，常与 CAP、PACELC 一起讨论。

## 为什么需要它

分区（P）在分布式里不可避免，硬守强一致（CP）会在网络抖动时让整体不可用。互联网规模下多数业务能接受"稍后一致"来换持续可用与水平扩展，BASE 就是这条 AP 路线的经验总结。

## 核心机制

- **基本可用（Basically Available）：** 故障时允许损失部分可用性（响应变长、非核心功能降级），但核心链路仍可提交、可查询。
- **软状态（Soft state）：** 允许副本同步过程中存在中间不一致状态，且认为它不破坏整体可用性。
- **最终一致（Eventual consistency）：** 停止新写入后经过一段时间，所有副本收敛到一致状态。
- **取舍方向：** P 不可避免时偏向 AP，用异步复制、消息队列、补偿与对账，把"每笔强一致"换成"最终一致"。

## 具体示例

电商下单扣库存：订单先落库即时返回"已下单"，库存与积分经消息异步扣减，短暂可能不一致，秒级内通过对账收敛——典型最终一致。

## 何时用与何时不用

- **用：** 读多写多、可容忍短暂不一致的高并发业务（社交、推荐、订单状态展示、跨地域多活）。
- **不用：** 金融核心账务、防超卖等必须线性一致的环节，应走强一致（CP / 分布式事务）。

## 优劣与代价

✅ 高可用、高扩展，容忍分区与故障，适合互联网规模。
⚠️ 一致性弱，可能读到旧值；业务须自行处理中间态、补偿与对账，调试复杂。

## 与相关概念的区别

vs [[CAP 定理]]：CAP 是"分区时一致与可用三选二"的不可能性结论，BASE 是 P 存在时选 AP 的工程落地路线；vs ACID 则是"每笔强一致"的相反取向。

## 常见误区

- BASE 就是不要一致性。
- 软状态意味着永远不一致。
- 最终一致保证在固定时间上界内完成。

## 面试速答

> 🎯 BASE = 基本可用 + 软状态 + 最终一致，是 CAP 里选 AP 的工程路线：牺牲强一致换高可用，靠异步复制与补偿对账收敛。
