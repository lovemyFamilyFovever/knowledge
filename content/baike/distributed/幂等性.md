# 幂等性

## 定义

**一句话定义：** 幂等性(Idempotency)指同一操作执行一次与执行多次对系统状态产生的影响相同;在分布式与网络场景中,它保证因重试、超时或消息重复投递而多次执行同一请求时,不会造成重复的副作用(如重复扣款)。

**通俗类比：** 像电梯按钮——按一次和连按十次,电梯来的效果一样(不会因此来十趟);而"取一次钱"若不具备幂等性,重试三次就可能被扣三次。

> 多义说明:幂等性在数学(f(f(x)) = f(x))、HTTP 语义(方法幂等)与消息/事务处理中含义相通但侧重不同;本文侧重工程(接口/消息)层面的幂等。

## 原理与机制

- **HTTP 语义:** GET、PUT、DELETE 被定义为幂等,POST 非幂等(需业务自行保证)。
- **常见实现手段:**
  - 幂等键(idempotency key)/唯一业务 ID:相同键的请求只生效一次。
  - 去重表 + 数据库唯一约束:重复插入被拒绝。
  - 乐观锁(版本号/CAS):仅当版本匹配才更新。
  - 状态机:只允许合法的状态迁移,重复请求被忽略。
  - 结果缓存:对重复请求直接返回上次结果。
- **消息场景:** at-least-once 投递必然产生重复,消费端须做幂等处理。

## 关键组成

| 手段 | 作用 |
|------|------|
| 幂等键 | 唯一标识一次逻辑操作 |
| 去重存储 | 记录已处理的键 |
| 唯一约束 | 数据库层面防重复写入 |
| 版本号 / 状态机 | 控制更新的合法性 |
| 结果缓存 | 重复请求返回一致结果 |

## 应用场景

- 支付、下单、转账等关键写接口
- 消息队列消费(重复投递)
- 分布式事务与失败重试
- 网络请求重试、API 网关

## 优点与局限

- 优点:保障重试安全、防止重复副作用、显著提升系统鲁棒性。
- 局限:需额外的存储与逻辑(幂等键管理);设计复杂度上升;幂等记录需过期清理;跨服务最终一致仍需其他机制配合。

## 常见误区

- 幂等 ≠ "只执行一次",而是"多次执行对状态的影响等同于一次"。
- 查询通常天然幂等,但写操作往往需要显式设计才能幂等。
- 幂等键必须全局唯一并有生命周期管理,否则会误判或占用膨胀。
- HTTP GET "幂等"指不改变服务端状态,并非"每次返回内容完全相同"。
