# 幂等性


> 📌 **导航**：本文是 **幂等性** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 幂等性指同一操作执行一次与执行多次对系统状态产生的影响相同；在分布式网络里，它保证因重试、超时或消息重复投递而多次执行同一请求时，不会产生重复副作用（如重复扣款）。

**通俗类比：** 像电梯按钮——按一次和连按十次，电梯来的效果一样（不会来十趟）；而"取一次钱"若不具备幂等性，重试三次就可能被扣三次。

> 多义说明：幂等在数学 f(f(x))=f(x)、HTTP 方法语义与消息 / 事务处理中含义相通但侧重不同；本文侧重工程（接口 / 消息）层面的幂等。

## 为什么需要它

网络超时就必须重试，消息用 at-least-once 就必然重复投递——于是同一个"扣款"请求可能被执行多次。幂等性让重试变得安全：无论执行几次，系统状态等同于执行一次，从根上防止重复下单、重复扣款。

## 核心机制

- **HTTP 语义：** GET、PUT、DELETE 定义上幂等，POST 非幂等、需业务自行保证。
- **实现手段：** 幂等键 / 唯一业务 ID（相同键只生效一次）、去重表 + 数据库唯一约束（重复插入被拒）、乐观锁版本号 / CAS（版本匹配才更新）、状态机（只允许合法迁移、重复请求忽略）、结果缓存（重复请求直接返回上次结果）。
- **消息场景：** at-least-once 投递必然产生重复，消费端必须做幂等处理（配合去重键 / 状态判断）。

## 具体示例

支付回调：带 idempotency key 调扣款，服务端先查该键是否已处理、命中则直接返回上次结果；配合订单状态机"待支付 → 已支付"只允许一次合法迁移，重复回调不会二次扣款。

## 何时用与何时不用

- **用：** 支付、下单、转账等关键写接口；MQ 消费、失败重试、API 网关、对外幂等 Token。
- **不用：** 纯查询天然幂等、无需额外设计；一次性、无副作用且可容忍重复的操作不必强加幂等开销。

## 优劣与代价

✅ 保障重试安全、防止重复副作用、显著提升系统鲁棒性。
⚠️ 需额外存储与逻辑（幂等键管理、去重表），幂等记录要过期清理；跨服务最终一致仍需其他机制配合。

## 与相关概念的区别

vs 分布式事务：幂等解决"同一请求重复执行"的副作用，分布式事务解决"多操作同成同败"，二者常配合——如 [[Saga 与 TCC]] 的 Confirm / Cancel 就必须幂等。

## 常见误区

- 幂等就是"请求只会被执行一次"。
- GET 幂等意味着每次返回的内容完全相同。
- 写操作不用专门设计也能天然幂等。

## 面试速答

> 🎯 幂等 = 同一操作执行一次和多次对系统状态影响相同，让重试安全；靠幂等键 / 唯一约束 / 乐观锁 / 状态机 / 结果缓存实现，MQ at-least-once 消费必须做幂等。
