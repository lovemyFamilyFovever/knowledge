# API网关

> 📌 **导航**：本文是 **API网关** 词条，由 [[微服务治理术语百科]] 拆分而来。

## 定义

**一句话定义：** API 网关是微服务对外的统一入口，集中承担路由转发、认证鉴权、限流熔断、协议转换与日志监控等横切能力，让客户端不必直连众多后端服务。

**通俗类比：** 像机场的值机 + 安检大厅：所有乘客（请求）都经此统一核验身份（认证）、控制人流（限流）、分配登机口（路由），不必每个登机口各设一道安检。

## 为什么需要它

若每个服务各自实现认证、限流、日志、跨域，会重复造轮子且策略难统一。网关把这些横切关注点收敛到一处，客户端只面对一个入口，后端拓扑对调用方透明，安全与流量策略集中可管。

## 核心机制

- **路由与转发：** 按路径 / 头 / 权重把请求映射到后端服务，常配服务发现做动态路由（如 `lb://order-service`）。
- **横切能力：** 统一认证鉴权、限流（令牌桶 / 配额）、熔断降级、请求改写、协议转换、灰度分流。
- **可观测：** 在边界统一采集访问日志、指标与链路追踪起点（见 [[可观测性工程实战]]）。
- **典型实现：** Spring Cloud Gateway（响应式、Java）、Kong（基于 Nginx / OpenResty、Lua 插件）、Zuul 1.x（Servlet 阻塞，已少用）。

## 具体示例

`/api/orders/**` 经网关 `StripPrefix` 后按 `lb://order-service` 负载均衡转发到订单服务，同时用 Redis 令牌桶按用户限流、超阈值返 429，并在网关层统一注入 traceId——这些都不用写进业务服务。

## 何时用与何时不用

- **用：** 对外 API 统一入口、南北向流量治理、跨切面（认证 / 限流 / 日志）集中落地。
- **不用：** 服务与服务之间的东西向调用不是网关职责（那是服务网格 / 客户端负载均衡，见 [[服务网格]]）；内部纯 RPC 链路不必强行过网关。

## 优劣与代价

✅ 统一入口、横切关注点集中、后端拓扑透明、便于安全与灰度治理。
⚠️ 网关自身是单点、需高可用；所有流量过境带来转发与性能开销；规则堆多了会让网关变成难以维护的"上帝组件"。

## 与相关概念的区别

vs 服务网格：网关管南北向（外部 → 集群）入口流量，网格管东西向（服务间）流量，二者常并存；vs 负载均衡：LB 只做实例分发，网关在其上再加认证 / 限流 / 路由 / 协议转换等应用层能力。

## 常见误区

- 所有请求（含服务之间的调用）都必须经过 API 网关。
- 有了网关就不用再做服务级的限流和熔断。
- 网关和服务网格是同一个东西。

## 面试速答
