# 分布式锁


> 📌 **导航**：本文是 **分布式锁** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 分布式锁让多个进程 / 机器跨节点协调对共享资源的互斥访问，保证同一时刻只有一个客户端持锁，避免并发操作导致数据不一致。

**通俗类比：** 像多人共用一间会议室、门口只挂一把钥匙：拿到钥匙才能进、用完挂回，即使大家不在同一栋楼也不会同时挤进去抢白板。

> 多义说明：单机锁（synchronized / mutex）只在单进程内有效，跨节点互斥要靠分布式锁，常见实现基于 Redis、ZooKeeper、etcd 或数据库。

## 为什么需要它

多实例部署时 synchronized / ReentrantLock 只在单进程内生效、跨不了进程。防超卖、定时任务去重、缓存击穿重建等临界区，都需要一把全网唯一、能在持锁者崩溃后自动释放的锁来保证互斥。

## 核心机制

- **核心要求：** 互斥（同一时刻仅一个持有）、防死锁（持锁者崩溃能自动释放）、可重入、高性能与高可用。
- **Redis 实现：** 用 `SET key val NX PX ttl` 一步原子地"加锁 + 设过期"，value 存唯一持有者 token；释放时用 Lua 脚本"比对 token 再删"以免误删他人锁；业务耗时不可控时配看门狗自动续期（如 Redisson）。Redlock 用多个独立实例投票降低单点风险，正确性有争议。
- **ZooKeeper / etcd 实现：** 临时顺序节点 + watch，或 lease + revision；会话断开自动释放，天然处理客户端失联。
- **难点与对策：** 网络分区、时钟漂移、GC 停顿会造成"锁已过期但持有者仍以为持有"，用 fencing token（单调递增令牌）让过期持有者的写入被下游拒绝。

## 具体示例

秒杀扣库存：抢到 `order:lock:{id}`（SET NX PX + 唯一 token）才执行扣减，finally 用 Lua 比对 token 再删；若处理耗时可能超过 TTL，Redisson 看门狗在持锁期间周期性续期，避免锁提前失效被他人抢占。

## 何时用与何时不用

- **用：** 跨节点的临界区互斥——防超卖、分布式定时任务去重、缓存击穿重建、选主兜底。
- **不用：** 单进程内用本地锁即可；能用无锁方案（CAS、幂等、分片串行化）解决时，别引入锁这层依赖与延迟。

## 优劣与代价

✅ 提供跨节点互斥，是实现关键并发控制的手段。
⚠️ 引入额外依赖与延迟；正确性依赖时钟 / 网络假设；Redis 主从切换可能丢锁；易出死锁 / 误删 / 续期 bug。

## 与相关概念的区别

vs 单机锁（synchronized）：后者仅单进程有效，分布式锁要跨网络协调、还要处理网络分区与时钟问题；vs [[一致性算法]]：强一致选主靠共识，分布式锁常借用 ZooKeeper / etcd 的共识能力来实现。

## 常见误区

- 用 SETNX + EXPIRE 两步来加锁是安全的。
- 释放锁时直接 delete、不必校验持有者。
- 只要用了 Redlock 就绝对安全。

## 面试速答

> 🎯 分布式锁 = 跨节点互斥一把锁：Redis 用 SET NX PX + token + Lua 校验释放 + 看门狗续期，或 ZK/etcd 临时节点；难点是分区 / 时钟 / GC，用 fencing token 兜底，Redlock 有争议。
