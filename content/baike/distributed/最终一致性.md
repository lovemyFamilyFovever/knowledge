# 最终一致性

## 定义

**一句话定义：** 最终一致性(Eventual Consistency)是分布式系统的一种一致性模型,它允许数据写入后各副本暂时不一致,但保证在没有新更新的前提下,经过一段时间后所有副本最终会收敛到相同的值,以换取更高的可用性与性能。

**通俗类比：** 像给多个朋友群发同一条消息——不是所有人同一瞬间收到,有人快有人慢;但只要不再有新的修改,过一会儿大家看到的内容最终会一致。

> 多义说明:最终一致性是**弱一致性**的一种,与强一致性(线性一致)相对;它是 BASE 理论中的 "E",常见于 AP 系统(参见 [[CAP 定理]])。本文讨论该模型及其变体。

## 原理与机制

- **动机:** 强一致(如多数派写确认)会牺牲可用性与延迟;最终一致允许副本异步复制,使读写更快、可用性更高。
- **收敛机制:** 异步复制 + 冲突解决,常见手段有读修复(read repair)、反熵(anti-entropy)、向量时钟、最后写入胜出(LWW)、以及无冲突复制数据类型(CRDT)。
- **以客户端为中心的变体:** 因果一致性、读己之写(read-your-writes)、单调读(monotonic reads)、会话一致性等。

## 关键组成

| 组成 | 作用 |
|------|------|
| 异步复制 | 副本间延迟同步 |
| 冲突解决 | LWW / 向量时钟 / CRDT |
| 读修复 / 反熵 | 主动发现并修正不一致 |
| 收敛保证 | 无新写入时最终一致 |

## 应用场景

- DNS、Cassandra / DynamoDB 等 AP 数据库
- 多主复制与跨地域数据同步
- 缓存系统、社交动态、商品浏览计数等可容忍短暂不一致的场景

## 优点与局限

- 优点:高可用、低延迟、高吞吐,天然适合跨地域部署。
- 局限:可能读到旧值(不适合强一致场景,如账户余额);冲突解决复杂;开发者需理解一致性语义;问题定位与调试困难。

## 常见误区

- 最终一致 ≠ 永远不一致:它保证无新写入时副本会收敛。
- 最终一致 ≠ 毫无一致性:还有因果一致、会话一致等更强的变体。
- 它不适合所有场景:金融账务等通常要求强一致。
- "最终"没有明确的时间上界,取决于系统实现与网络状况。
