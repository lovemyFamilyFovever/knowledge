# 负载均衡


> 📌 **导航**：本文是 **负载均衡** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 负载均衡把进入系统的请求或工作负载按一定策略分发到多个后端服务器（或资源）上，用以避免单点过载、提升整体吞吐与可用性，并支撑水平扩展。

**通俗类比：** 像银行大厅的叫号引导员——客人（请求）来了，引导员看哪个窗口（服务器）空闲就把人引过去，避免所有人挤在一个窗口排长队，同时让多个窗口都在干活。

> 多义说明：负载均衡可指硬件设备、软件（Nginx / HAProxy / LVS）、云服务 LB，也包括客户端负载均衡；按 OSI 层次分四层（传输层）与七层（应用层）。

## 为什么需要它

单台服务器扛不住大流量，也会成为单点。负载均衡把流量摊到后端服务器池，既提升总吞吐与可用性、支持水平扩展，又能在某节点故障时自动摘除，并用统一 VIP 对外隐藏后端拓扑。

## 核心机制

- **调度算法：** 轮询、加权轮询、最少连接、IP 哈希（利于会话保持）、随机、一致性哈希等。
- **工作层次：** L4 基于 IP / 端口转发（性能高、不解析内容）；L7 基于 URL / Header / Cookie（更灵活、可做内容路由）。
- **健康检查：** 周期探测后端存活，自动摘除故障节点、恢复后再纳入。
- **会话保持：** 将同一用户请求固定到同一后端以应对有状态服务（现代更推荐无状态 + 分布式会话）。

## 具体示例

Nginx upstream 配 least_conn 把请求发到连接最少的后端，配合 max_fails / fail_timeout 健康摘除；对外只有一个 VIP，用户无感地在多台应用服务器间分摊，某台宕机自动跳过。

## 何时用与何时不用

- **用：** Web / API 流量分发、微服务网关、数据库读写分离、CDN / GSLB、高可用与容灾入口。
- **不用：** 单实例、无分发需求时不必硬加；它只分发流量，不能替你完成扩容或数据分片。

## 优劣与代价

✅ 提升吞吐与可用性、支持水平扩展、实现故障转移、对外隐藏后端拓扑。
⚠️ 负载均衡器自身可能成瓶颈 / 单点（需再为它做高可用）；会话保持增加复杂度；L7 解析带来额外开销。

## 与相关概念的区别

vs 一致性哈希：那是一种"按 key 稳定映射到节点"的算法，可作为负载均衡的调度策略之一；vs [[服务发现]]：负载均衡决定"请求发给哪个实例"，服务发现提供"有哪些实例可选"。

## 常见误区

- 有负载均衡就等于高可用。
- 负载均衡就是自动扩容。
- 轮询永远是最优调度算法。

## 面试速答

> 🎯 负载均衡 = 按策略（轮询 / 加权 / 最少连接 / IP 哈希 / 一致性哈希）把请求摊到后端池，分 L4（IP/端口、快）与 L7（URL/Header、灵活），配健康检查与 VIP 隐藏拓扑、支撑水平扩展与故障转移。
