# 分布式缓存


> 📌 **导航**：本文是 **分布式缓存** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 分布式缓存把缓存数据分片存储到多个节点、通过一致性哈希等手段横向扩展，就近提供热点数据，以降低后端存储压力与访问延迟。

**通俗类比：** 像连锁便利店把常买商品分散囤在各门店（节点），顾客就近取货，不必每次跑中央仓库（数据库）；某门店缺货或新开也只影响周边顾客。

> 多义说明：本文讲分布式缓存系统（Redis Cluster、Memcached 集群），区别于进程内本地缓存（Caffeine、Guava）；生产中常二者结合成多级缓存。

## 为什么需要它

单机内存与带宽有上限，热点数据全压数据库会打穿后端。把缓存做成可横向扩展的一层，既就近加速读、又用分片与副本扛住单点，是高并发读多写少系统的标配。

## 核心机制

- **一致性哈希：** 节点与 Key 都映到 0~2^32 的环上、Key 归顺时针首个节点；增删节点只影响相邻一段（虚拟节点纠偏），避免取模 `hash % N` 在扩缩容时大面积迁移。
- **分片与路由：** 客户端分片（简单但需感知拓扑）、代理分片（Proxy 路由、Proxy 需高可用）、Redis Cluster（`CRC16(key) mod 16384` 映射到 16384 个哈希槽、槽分给各节点，节点间用 Gossip 同步状态并自动故障转移）。
- **读写策略：** Cache-Aside 最常用——读未命中回源并回填、写时更新库并删除（而非更新）缓存；Read/Write-Through 由缓存层负责回源落库；Write-Behind 先写缓存、异步批量落库，吞吐高但可能丢数据。
- **稳定性三问题：** 穿透 = 查根本不存在的数据、缓存和库都没有，请求直达 DB（布隆过滤器、空值短 TTL）；击穿 = 单个热点 Key 过期瞬间大量并发回源（互斥锁 / 单飞重建、逻辑过期）；雪崩 = 大量 Key 同时过期或缓存宕机（过期加随机抖动、高可用集群、多级缓存限流）。

## 具体示例

商品详情页：读走 Cache-Aside（先查 Redis、未命中回 MySQL 并回填，TTL 加随机抖动防雪崩）；Redis Cluster 用 16384 槽分到多节点、某节点宕机由其副本自动接管；热点 SKU 用互斥锁防击穿。

## 何时用与何时不用

- **用：** 高并发读多写少（商品详情、会话、排行榜）、需就近降延迟、限流计数与临时数据暂存。
- **不用：** 强一致写场景（缓存反成一致性负担）；数据量小或访问极低频时，本地缓存或直连库更省。

## 优劣与代价

✅ 显著降延迟与后端负载、可横向扩展、提升吞吐与可用性。
⚠️ 引入缓存与数据库的双写一致性难题；要处理穿透 / 击穿 / 雪崩；内存成本高、数据易失（需持久化 / 副本兜底）。

## 与相关概念的区别

vs 本地缓存（Caffeine）：本地缓存零网络、最快但各节点各自为战、易不一致，分布式缓存全局共享、可分片扩展，二者常组多级缓存；vs [[一致性哈希]]：那是分片路由的算法手段，本文是使用它的缓存系统。

## 常见误区

- 更新数据时应"更新"缓存而不是删除缓存。
- 加了缓存就再也不会有数据库压力。
- 布隆过滤器能准确判定一个 Key 一定存在。

## 面试速答

> 🎯 分布式缓存 = 多节点分片 + 一致性哈希 / 哈希槽横向扩展，配 Cache-Aside 读写与穿透 / 击穿 / 雪崩对策；核心权衡是性能与可用性 vs 缓存—数据库一致性。
