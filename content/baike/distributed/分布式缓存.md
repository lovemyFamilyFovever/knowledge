# 分布式缓存

## 定义

**一句话定义：** 分布式缓存是把缓存数据分散存储在多个节点上、通过分片与一致性哈希等手段横向扩展的缓存系统，用以就近提供热点数据、降低后端存储压力与访问延迟。

**通俗类比：** 就像连锁便利店把常买的商品分散囤在各个门店（节点），顾客就近取货，不必每次都跑到中央仓库（数据库）；某个门店缺货或新开，也只影响它周边的顾客。

> 多义说明：本文讨论**分布式缓存系统**（如 Redis Cluster、Memcached 集群），区别于进程内的**本地缓存**（如 Caffeine、Guava Cache）；生产中常二者结合形成多级缓存。

## 原理与机制

### 一致性哈希

```
        0 -------- 2^32-1 环形哈希空间
           NodeA      NodeB      NodeC
              Key1       Key2
（Key 顺时针找到的第一个节点即归属节点）
```

- 节点加入 / 离开时，只影响环上**相邻**的一小段 Key，避免普通取模（hash % N）在扩缩容时的**大面积数据迁移**。
- **虚拟节点（vnode）**：每个物理节点映射为环上多个虚拟点，使数据分布更均匀，解决数据倾斜。

### 缓存分片

| 方案 | 原理 | 特点 |
|------|------|------|
| 客户端分片 | 客户端计算分片位置 | 简单、无中间层，但客户端需感知拓扑 |
| 代理分片 | 由 Proxy 路由 | 客户端简单、灵活，Proxy 需高可用 |
| Redis Cluster | **16384 个哈希槽** + Gossip 协议 | 服务端自动分片与故障转移，去中心化 |

> 说明：Redis Cluster 用 `CRC16(key) mod 16384` 把键映射到 **16384 个槽（slot）**，槽再分配到各节点；节点间通过 **Gossip** 协议同步集群状态——原文档只写「Gossip」不够完整，已补充哈希槽机制。

### 读写策略

- **Cache-Aside（旁路缓存，最常用）**：读时先查缓存、未命中回源并回填；写时更新数据库并删除（而非更新）缓存。
- **Read/Write-Through**：应用只与缓存交互，由缓存层负责回源与落库。
- **Write-Behind（写回）**：先写缓存、异步批量落库，吞吐高但可能丢数据。

## 关键组成

| 组成 | 作用 |
|------|------|
| 缓存节点 | 存储热点数据（内存为主） |
| 分片 / 路由 | 决定 Key 落在哪个节点 |
| 复制 / 高可用 | 主从、哨兵或集群故障转移 |
| 过期与淘汰 | TTL + LRU/LFU 等淘汰策略控制内存 |

## 应用场景

- 高并发读多写少场景（商品详情、会话、热点排行榜）减轻数据库压力。
- 降低跨地域访问延迟（配合 CDN / 多级缓存）。
- 分布式会话、限流计数、临时数据暂存。

## 优点与局限

- 优点：显著降低延迟与后端负载、可横向扩展、提升系统吞吐与可用性。
- 局限：引入**缓存与数据库的一致性**难题；需处理穿透 / 击穿 / 雪崩等稳定性风险；内存成本与数据易失（需持久化 / 副本兜底）。

## 常见误区（缓存三大问题）

- **缓存穿透**：查询**根本不存在**的数据，缓存与库都无 → 请求持续打到数据库。对策：布隆过滤器、对空结果做短 TTL 缓存。
- **缓存击穿**：某个**热点 Key 过期**瞬间，大量并发同时回源打库。对策：互斥锁 / 单飞（singleflight）重建、热点 Key 逻辑过期不真删。
- **缓存雪崩**：**大量 Key 同时过期**或缓存整体宕机，请求洪峰压垮数据库。对策：过期时间加随机抖动、缓存集群高可用、多级缓存与限流降级。
- 另有**双写一致性**：先更库再删缓存 + 延迟双删等策略，仍需容忍短暂不一致（最终一致）。
