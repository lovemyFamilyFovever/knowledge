## 1. CAP 定理（一致性 / 可用性 / 分区容错）

**一句话定义：** 分布式系统在发生网络分区（P）时，无法同时保证一致性（C）与可用性（A），只能在二者间取舍。

> 📎 已有专门词条：[[CAP 定理]]（含 PACELC 扩展、CP/AP 系统举例、常见误区）。要点速记：分区容错 P 在分布式下必选，故实际是「C 与 A 二选一」——ZooKeeper 偏 CP、Eureka 偏 AP。

---

## 2. BASE 理论（基本可用 / 软状态 / 最终一致性）

### 一句话定义

BASE 是 CAP 中「AP」方案的工程化延伸：**基本可用**（Basically Available）、**软状态**（Soft State）、**最终一致性**（Eventually Consistent）——在保证系统基本可用的前提下，允许中间状态存在，最终达到一致。

### 通俗类比

你在电商下单后系统立即显示「下单成功」（基本可用），订单状态从「待处理」逐步流转到「已发货」「已完成」（软状态），各系统数据不会瞬间全部同步，但最终会一致（最终一致性）。

### 具体示例

```java
// 软状态示例：订单状态流转，允许中间态存在
public enum OrderStatus {
    CREATED,      // 刚创建（软状态，尚未支付）
    PAID,         // 已支付
    SHIPPED,      // 已发货
    COMPLETED     // 最终一致
}
```

### 为什么需要它

互联网场景对可用性要求极高，强一致（ACID）在分布式下代价过大。BASE 提供了「牺牲强一致、换取高可用」的实践指导，是大多数互联网系统的默认取向。

### 与 CAP / ACID 的关系

| 概念 | 定位 | 取向 |
|------|------|------|
| CAP | 理论边界（能力上限） | 分区时 C/A 二选一 |
| ACID | 单机事务的强一致模型 | 强一致 |
| BASE | CAP 中 AP 的工程落地 | 最终一致、高可用 |

## 3. 分布式锁（Redis / ZooKeeper / Redlock）

### 一句话定义

分布式锁是在多个进程 / 机器之间协调对共享资源的**互斥访问**的机制，确保同一时刻只有一个客户端能操作特定资源。

### 通俗类比

就像公司只有一间会议室、一把钥匙：你拿到钥匙（获取锁）才能进去开会，用完归还（释放锁），别人才能用。分布式锁就是让多台服务器去竞争同一把「钥匙」。

### 具体示例（Redis，含正确释放姿势）

```java
String lockKey = "order:lock:" + orderId;
String token = UUID.randomUUID().toString();   // 唯一标识，避免误删他人的锁
Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, token, 30, TimeUnit.SECONDS);  // SET key val NX EX，原子加锁

if (Boolean.TRUE.equals(locked)) {
    try {
        processOrder(orderId);
    } finally {
        // 释放锁必须「先判断是自己的再删」，用 Lua 保证原子性
        String lua = "if redis.call('get', KEYS[1]) == ARGV[1] "
                   + "then return redis.call('del', KEYS[1]) else return 0 end";
        redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class),
                Collections.singletonList(lockKey), token);
    }
}
```

> 说明：常见错误写法 `finally { redisTemplate.delete(lockKey); }` 有两个隐患——① 未抢到锁时也会执行删除；② 若业务耗时超过 TTL、锁已过期并被他人持有，会**误删他人的锁**。正确做法：加锁时写入唯一 token，释放时用 Lua「比对 token 再删」。若业务耗时不可控，应使用带**看门狗自动续期**的实现（如 Redisson）。

### 为什么需要它

多实例部署时，单机锁（`synchronized`/`ReentrantLock`）无法跨进程生效，需要分布式锁来解决跨节点的并发互斥（如防止超卖、定时任务重复执行）。

### Redis vs ZooKeeper vs Redlock

| 方案 | 实现原理 | 优点 | 缺点 |
|------|----------|------|------|
| Redis | `SET NX EX` | 高性能 | 主从切换可能丢锁、TTL 与业务耗时难匹配 |
| ZooKeeper | 临时顺序节点 + Watch | 强一致、会话断开自动释放 | 性能较低 |
| Redlock | 多个独立 Redis 实例多数派 | 降低单点风险 | 实现复杂、正确性有争议（见下方误区） |

### 常见误区

- 加锁不设过期时间 → 持锁进程崩溃会造成**死锁**；但 TTL 设太短又可能在业务完成前失效。需配合续期（看门狗）。
- 释放锁不校验持有者 → 误删他人锁（见上方 Lua 修正）。
- 迷信 Redlock「绝对安全」：Martin Kleppmann 与 antirez 曾就其在时钟漂移 / GC 停顿下的安全性公开争论，强正确场景建议用带 fencing token 的方案或 ZooKeeper/etcd。
