# 分布式基础术语百科

> 本文档涵盖分布式系统中最核心的基础概念，帮助开发者建立扎实的分布式知识体系。

---

## 1. CAP定理（一致性/可用性/分区容错）

### 一句话定义
分布式系统最多只能同时满足一致性（C）、可用性（A）、分区容错性（P）中的两个。

### 通俗类比
想象一个银行ATM机网络：如果北京和上海的服务器断网了（分区），你是让北京用户暂时取不到钱（牺牲可用性保一致性），还是让两边都能取但数据可能不一致（牺牲一致性保可用性）？CAP定理告诉我们，分区发生时必须二选一。

### 具体示例
```
// CP系统：ZooKeeper（牺牲可用性保一致性）
// 节点挂掉后，整个集群不可用直到恢复

// AP系统：Eureka（牺牲一致性保可用性）
// 各节点数据可能不一致，但服务始终可用
```

### 为什么需要它
CAP定理是分布式系统设计的理论基础，帮助架构师在设计时做出明确的取舍决策，而不是试图"既要又要"。

### 与相关术语的对比和区分
| 特性 | CAP | PACELC |
|------|-----|--------|
| 关注点 | 分区时的取舍 | 无分区时的取舍 |
| 扩展性 | 三选二 | 进一步考虑延迟与一致性 |

## 2. BASE理论（基本可用/软状态/最终一致性）

### 一句话定义
BASE理论是CAP中AP方案的延伸：基本可用（Basically Available）、软状态（Soft State）、最终一致性（Eventually Consistent）。

### 通俗类比
你在淘宝下单后，系统立即显示"下单成功"（基本可用），订单状态从"待处理"逐步变为"已发货"（软状态），最终变成"已完成"（最终一致性）——数据不会立刻全部同步，但最终会达到一致。

### 具体示例
```java
// 软状态示例：订单状态流转
public enum OrderStatus {
    CREATED,      // 刚创建（软状态）
    PAID,         // 已支付
    SHIPPED,      // 已发货
    COMPLETED     // 最终一致
}
```

### 为什么需要它
互联网场景对可用性要求极高，BASE理论提供了在保证基本可用的前提下，通过最终一致性来实现高可用的实践指导。

### 与相关术语的对比和区分
- **CAP**：理论基础，描述系统能力边界
- **BASE**：实践指导，描述具体实现策略
- BASE是CAP中AP方案的工程化落地

## 3. 分布式锁（Redis实现/ZooKeeper实现/Redlock）

### 一句话定义
分布式锁是在多个进程/机器间协调互斥访问共享资源的机制，确保同一时刻只有一个客户端能操作特定资源。

### 通俗类比
就像公司只有一个会议室钥匙，你拿到钥匙（获取锁）才能进去开会，别人要等你用完归还（释放锁）。分布式锁就是多台服务器竞争同一把"钥匙"。

### 具体示例
```java
// Redis分布式锁实现
String lockKey = "order:lock:" + orderId;
try {
    // 尝试获取锁，30秒自动过期
    boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", 30, TimeUnit.SECONDS);
    if (locked) {
        // 执行业务逻辑
        processOrder(orderId);
    }
} finally {
    // 释放锁
    redisTemplate.delete(lockKey);
}
```

### 为什么需要它
多实例部署时，传统单机锁无法跨进程生效，分布式锁解决了并发场景下的数据一致性问题。

### Redis vs ZooKeeper vs Redlock
| 方案 | 实现原理 | 优点 | 缺点 |
|------|----------|------|------|
| Redis | SETNX | 高性能 | 有锁失效风险 |
| ZooKeeper | 临时顺序节点 | 强一致 | 性能较低 |
| Redlock | 多Redis实例 | 高可用 | 实现复杂 |

## 4. 分布式事务（2PC/3PC/TCC/Saga/本地消息表）

### 一句话定义
分布式事务是保证跨多个数据库/服务的操作要么全部成功、要么全部回滚的机制。

### 通俗类比
你在网上买书和CD，来自两个店铺。系统要么两个都扣款成功发货，要么都不发货退款——这就是分布式事务要保证的"原子性"。

### 具体示例
```java
// TCC模式：Try-Confirm-Cancel
public interface OrderTccService {
    // 阶段1：预留资源
    @Try
    void tryDeductStock(Long orderId);
    // 阶段2：确认扣减
    @Confirm
    void confirmDeductStock(Long orderId);
    // 阶段3：回滚释放
    @Cancel
    void cancelDeductStock(Long orderId);
}
```

### 为什么需要它
微服务架构下，业务数据分散在多个服务和数据库中，无法用单机事务保证一致性。

### 各方案对比
| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|----------|
| 2PC | 强 | 低 | 中 | 传统数据库 |
| TCC | 强 | 中 | 高 | 金融业务 |
| Saga | 最终 | 高 | 中 | 长事务 |
| 本地消息表 | 最终 | 高 | 低 | 异步场景 |

## 5. 分布式ID生成（雪花算法/UUID/Leaf/号段模式）

### 一句话定义
分布式ID生成是在多节点环境下全局唯一地生成标识符的方案。

### 通俗类比
就像全国身份证号码系统，每个人都有唯一号码，无论在哪个城市办理业务都不会重复。

### 具体示例
```java
// 雪花算法ID结构（64位）
// | 1位符号 | 41位时间戳 | 10位机器ID | 12位序列号 |
public long nextId() {
    long timestamp = System.currentTimeMillis();
    long sequence = (timestamp - lastTimestamp) << 12 | workerId << 12 | sequence;
    return sequence;
}
```

### 为什么需要它
数据库自增ID在分库分表后会重复，UUID无序且太长，需要全局唯一且有序的ID方案。

### 方案对比
| 方案 | 唯一性 | 有序性 | 性能 | 依赖 |
|------|--------|--------|------|------|
| UUID | 全局 | 无序 | 高 | 无 |
| 雪花算法 | 全局 | 递增 | 高 | 时钟 |
| Leaf | 全局 | 递增 | 高 | 数据库/号段 |
| 号段模式 | 全局 | 递增 | 中 | 数据库 |

## 6. 分布式配置中心（Apollo/Nacos/Spring Cloud Config）

### 一句话定义
分布式配置中心是集中管理所有服务配置信息，支持动态更新和版本管理的平台。

### 通俗类比
就像酒店的中央控制系统，前台可以统一调整所有房间的空调温度，而不需要逐个房间去手动调节。

### 具体示例
```yaml
# Nacos配置示例
spring:
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        data-id: order-service.yml
        group: DEFAULT_GROUP
        file-extension: yml
```

### 为什么需要它
配置散落在各个服务中，修改需要重启，无法快速响应运营需求变更。

### 三大配置中心对比
| 特性 | Apollo | Nacos | Spring Cloud Config |
|------|--------|-------|---------------------|
| 动态更新 | 支持 | 支持 | 需Refresh |
| 管理界面 | 完善 | 完善 | 无 |
| 多环境 | 支持 | 支持 | 支持 |
| 配置回滚 | 支持 | 支持 | 不支持 |

## 7. 服务注册与发现（Eureka/Consul/Nacos/ZooKeeper）

### 一句话定义
服务注册与发现是微服务架构中服务实例自动注册到注册中心，消费者从注册中心获取可用实例列表的机制。

### 通俗类比
就像外卖平台的餐厅入驻：餐厅注册上线（服务注册），顾客搜索时看到附近可用的餐厅列表（服务发现），餐厅下线后自动从列表消失。

### 具体示例
```java
// Spring Cloud + Nacos 注册发现
@FeignClient(name = "order-service")
public interface OrderServiceClient {
    @GetMapping("/api/orders/{id}")
    OrderDTO getOrder(@PathVariable Long id);
}

// 消费者无需知道具体IP，只需服务名即可调用
```

### 为什么需要它
微服务实例动态扩缩容，手动维护地址列表不现实，需要自动化的服务发现机制。

### 四大注册中心对比
| 特性 | Eureka | Consul | Nacos | ZooKeeper |
|------|--------|--------|-------|-----------|
| CAP | AP | CP | AP/CP | CP |
| 健康检查 | 心跳 | HTTP/TCP | 心跳/TCP | 会话 |
| 雪崩保护 | 有 | 无 | 有 | 无 |
| 语言 | Java | 多语言 | 多语言 | Java |
