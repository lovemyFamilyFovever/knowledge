# Saga 与 TCC

## 定义

**一句话定义：** Saga 与 TCC 是两种解决分布式事务(跨服务/跨库一致性)的模式——Saga 把长事务拆成一串本地事务,每步都有对应的补偿操作,失败时逆序补偿回滚;TCC(Try-Confirm-Cancel)把每个操作分为"预留资源(Try)、确认(Confirm)、取消(Cancel)"三阶段,以实现最终一致。

**通俗类比：** Saga 像订一趟多段旅行——依次订机票、酒店、租车(每步本地事务),若租车失败,就按相反顺序取消已订的酒店和机票(补偿);TCC 像买东西先"冻结"库存和余额(Try),都 OK 再"真正扣减"(Confirm),有一方不行就"解冻"(Cancel)。

> 多义说明:二者都是"柔性事务 / 最终一致"方案(区别于 XA / 2PC 的强一致两阶段提交)。本文对比 Saga 与 TCC。

## 原理与机制

- **Saga:**
  - 编排式(orchestration,中央协调器指挥各步)vs 协同式(choreography,各服务通过事件驱动)。
  - 正向执行 T1 → T2 → … → Tn;某步失败则逆序执行补偿 C(n−1) → … → C1。
- **TCC:**
  - Try:预留/冻结资源(如冻结库存、预授权金额);
  - Confirm:所有 Try 成功则真正提交(扣减);
  - Cancel:任一 Try 失败则释放预留。
- **共同要求:** 业务操作需幂等、可补偿/可取消,达成最终一致(非强一致隔离)。

## 关键组成

| 组成 | 说明 |
|------|------|
| Saga 本地事务 + 补偿 | 正向执行与逆向补偿 |
| 编排 / 协同 | 中央协调 vs 事件驱动 |
| TCC 三阶段 | Try / Confirm / Cancel |
| 幂等 | 应对重试与重复 |
| 最终一致 | 一致性目标 |

## 应用场景

- 电商下单(订单—库存—支付)
- 跨服务的长流程业务
- 微服务数据一致性
- 旅行/预订类多步骤业务

## 优点与局限

- 优点:不长时间锁定资源、跨服务可扩展、性能优于 2PC、达成最终一致。
- 局限:无强隔离(中间态可见);补偿/取消逻辑复杂;要求幂等;一致性是"最终"而非"实时";调试困难。

## 常见误区

- Saga / TCC 是最终一致,不提供 ACID 的强隔离(中间状态可能被读到)。
- 补偿 ≠ 简单回滚:它是业务层面的反向操作,可能已产生副作用需处理。
- 每个操作必须幂等(可能被重试)。
- TCC 的 Try 要真正"预留"资源,否则会超卖。
