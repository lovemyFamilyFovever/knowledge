# Saga 与 TCC


> 📌 **导航**：本文是 **Saga 与 TCC** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** Saga 与 TCC 是两种柔性分布式事务模式——Saga 把长事务拆成一串本地事务、每步配补偿、失败逆序回滚；TCC 把每个操作分成 Try 预留、Confirm 确认、Cancel 取消三阶段。

**通俗类比：** Saga 像订多段旅行：依次订机票、酒店、租车，租车失败就逆序取消已订项；TCC 像购物先冻结库存和余额（Try），都 OK 再真正扣减（Confirm），一方不行就解冻（Cancel）。

> 多义说明：二者都是"柔性事务 / 最终一致"方案，区别于 XA / 2PC 的强一致两阶段提交。

## 为什么需要它

跨服务 / 跨库的业务（下单—扣库存—支付）没法用一个本地事务包住。2PC 会长时间锁资源、协调者单点、吞吐低，Saga 与 TCC 用"每步本地提交 + 补偿 / 取消"换可扩展与高吞吐，代价是只保证最终一致。

## 核心机制

- **Saga：** 正向 T1→T2→…→Tn，某步失败则逆序执行补偿 C(n-1)→…→C1。分编排式（中央协调器指挥各步）与协同式（服务间事件驱动）。
- **TCC：** Try 预留 / 冻结资源（冻结库存、预授权金额）→ 全部 Try 成功则 Confirm 真正扣减 → 任一失败则 Cancel 释放预留。
- **共同要求：** 操作幂等、可补偿 / 可取消，目标是最终一致而非强隔离。

## 具体示例

下单减库存：Saga 路径先建订单、再扣库存、最后扣款，扣款失败就逆序"退款补偿"；TCC 路径 Try 冻结库存与余额，都成功再 Confirm 扣减，任一失败 Cancel 解冻。

## 何时用与何时不用

- **用：** 跨服务长流程、对吞吐敏感、可接受中间态的业务（电商下单、预订类多步骤流程）。
- **不用：** 要求强隔离 / 实时一致的少量核心账务，宁可上 2PC 或单库事务；补偿逻辑无法正确编写时也别硬套。

## 优劣与代价

✅ 不长时间锁资源、跨服务可扩展、吞吐优于 2PC。
⚠️ 无强隔离、中间态可见；补偿 / 取消逻辑复杂；强制要求幂等；调试困难。

## 与相关概念的区别

vs 2PC/XA：二者是强一致同步协议、锁资源直到全局提交，Saga / TCC 是异步柔性方案、只保证最终一致；Saga vs TCC：Saga 事后补偿、隔离性更弱，TCC 事前预留资源、隔离性更强但侵入业务、要写 Try/Confirm/Cancel 三套接口。

## 常见误区

- Saga / TCC 能提供和 ACID 一样的强隔离。
- 补偿就是把数据库事务简单回滚。
- TCC 的 Try 阶段不必真正预留资源。

## 面试速答

> 🎯 Saga = 本地事务链 + 失败逆序补偿，TCC = Try 预留 / Confirm 提交 / Cancel 取消；都靠幂等换可扩展与高吞吐，只保最终一致、无强隔离，区别于 2PC。
