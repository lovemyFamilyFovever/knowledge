# 分布式存储术语百科


> 📌 **导航**：本文是 **分布式存储术语百科** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

> 本文档是分布式**存储**核心概念的合集：数据分片、副本、共识协议、Gossip 与各种一致性模型。已有专门词条的共识算法（Raft/Paxos/ZAB）只保留要点并双链过去，其余术语在此详解。

## 1. 数据分片（Hash 分片 / 范围分片 / 一致性哈希）

### 一句话定义

数据分片（Sharding/Partitioning）是把大规模数据按规则拆分到多个存储节点上的技术，是存储**水平扩展**的基础。

### 通俗类比

就像图书馆按拼音首字母把书分到不同楼层：A–F 在一楼、G–M 在二楼……查找时直奔对应楼层，不必翻遍整个图书馆。

### 具体示例

```java
// Hash 分片
int shardIndex = hash(userId) % shardCount;
// userId=1001, hash=5768, shardCount=16 → 5768 % 16 = 8，路由到第 8 个分片

// 一致性哈希：节点增减只影响环上相邻的一小段 Key（详见 [[分布式缓存]]）
```

### 为什么需要它

单机存储容量与性能有上限；分片后数据分散到多节点，可大幅提升总容量与读写吞吐，并支持按需扩容。

### 分片策略对比

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| Hash 分片 | 按 key 哈希取模 | 数据分布均匀 | 扩容需大规模迁移 |
| 范围分片 | 按 key 区间划分 | 范围查询高效 | 易产生写热点 |
| 一致性哈希 | 哈希环 + 虚拟节点 | 扩缩容迁移量小 | 实现较复杂 |

## 2. 数据副本（主从 / 多主 / 无主复制）

### 一句话定义

数据副本（Replication）是把同一份数据复制到多个节点，以提高**可靠性**（容错）与**读性能**（就近读、分担读压力）。

### 通俗类比

就像重要文件复印多份、分存不同地点——即使一处失火，其他地方仍有备份。

### 具体示例

```sql
-- MySQL 主从复制：主库写、从库读（读写分离）
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='192.168.1.100',
  SOURCE_USER='repl',
  SOURCE_AUTO_POSITION=1;   -- 基于 GTID 自动定位
```

### 为什么需要它

单点故障会导致不可用与数据丢失；副本提供冗余，主从分离还能提升读吞吐，多副本 + 共识可实现高可用故障转移。

### 副本策略对比

| 类型 | 写入点 | 一致性 | 可用性 | 典型场景 |
|------|--------|--------|--------|----------|
| 主从（单主） | 单一主节点 | 强（同步）/ 弱（异步） | 中 | 读多写少、MySQL 主从 |
| 多主 | 多个主节点可写 | 弱（需解冲突） | 高 | 多机房、多活 |
| 无主 | 任意节点可读写 | 可调（Quorum） | 最高 | Dynamo/Cassandra 系 |

> 注意：异步复制存在**主从延迟**，主库宕机可能丢失未同步的数据；多主需处理**写冲突**（如 last-write-wins、向量时钟）。

## 3. Raft 共识算法（Leader 选举 / 日志复制 / 安全性）

**一句话定义：** Raft 是一种以「易理解」为设计目标的共识算法，通过 Leader 选举与日志复制让集群对数据变更达成一致。

> 📎 已有专门词条：[[一致性算法]]（含 Raft 的 Leader 选举、日志复制、安全性与角色表）。要点：Follower→Candidate→Leader 三态、任期 term、多数派提交、只有日志足够新者才能当选。

---

## 4. Paxos 算法（Basic Paxos / Multi-Paxos）

**一句话定义：** Paxos 是解决分布式共识的经典算法，通过 Prepare/Accept 两阶段在多数派间就某个值达成一致。

> 📎 详见：[[一致性算法]]。要点：Proposer/Acceptor/Learner 三角色；Basic Paxos 决议单值，Multi-Paxos 通过稳定 Leader 省去每次 Prepare、决议连续多值（性能更高）。

---

## 5. ZAB 协议（ZooKeeper Atomic Broadcast）

**一句话定义：** ZAB 是 ZooKeeper 使用的原子广播协议，基于主从架构保证数据的**顺序一致性**与崩溃恢复。

> 📎 与 Paxos/Raft 的对比见 [[一致性算法]]。ZAB 关键点：Leader 选举优先选 **ZXID 最大**（数据最新）者；写操作由 Leader 以类 2PC 方式广播、多数派确认后提交。ZXID 为 64 位——高 32 位 epoch（Leader 代次）、低 32 位 counter（事务计数），共同保证全局有序。

---

## 6. Gossip 协议（最终一致 / 反熵 / 谣言传播）

### 一句话定义

Gossip 是一种**去中心化**的信息传播协议：节点周期性地随机选取若干节点交换状态，经多轮扩散最终使全集群收敛一致。

### 通俗类比

就像谣言传播：你告诉 3 个朋友，每人再告诉 3 个，很快全村都知道——不是立刻，但最终所有人都会知道。

### 具体示例

```
// 每轮随机选若干节点推送自身状态
Node A -> [B, F, H]：{A: v1}
Node B -> [C, D, A]：{A: v1, B: v2}
// 多轮后所有节点状态收敛
// Cassandra：每秒随机选节点交换心跳与元数据；Redis Cluster 也用 Gossip 同步槽位
```

### 为什么需要它

中心化架构有单点瓶颈；Gossip 去中心化、容错强、扩展性好，适合大规模、成员动态变化的集群（成员探活、元数据同步）。

### 传播变体

| 变体 | 机制 | 用途 |
|------|------|------|
| 反熵（anti-entropy） | 周期性全量比对修复 | 数据最终一致修复 |
| 谣言传播（rumor） | 事件驱动、有热度衰减 | 状态/事件快速通知 |
| 推拉结合 | 双向交换 | 提高收敛效率 |

> 代价：Gossip 收敛需要时间（**最终一致**而非强一致），且消息有冗余开销；节点数越多收敛越慢。

## 7. 一致性模型（强一致 / 最终一致 / 线性 / 顺序 / 因果）

分布式系统按「读写可见性与顺序」的保证强弱，形成一个一致性模型谱系。本节统一梳理，避免逐条重复。

### 强一致 vs 最终一致

- **强一致性**：写入后，任意读操作都能**立即**读到最新值（如 ZooKeeper 写后读）。代价是延迟高、可用性低。
- **最终一致性**：写入后允许短暂不一致，经过一段时间后所有副本**最终**收敛到最新值（如 DNS、CDN）。代价低、可用性高。

### 线性一致 vs 顺序一致

- **线性一致性（Linearizability）**：每个操作看起来在其调用与响应之间的某一刻**原子生效**，且这些时刻**尊重真实时间顺序**——若写在真实时间上先于读完成，读必须看到该写。是最强的单对象一致性。
- **顺序一致性（Sequential Consistency）**：只要求所有操作存在一个**全局顺序**、且与各进程的程序顺序一致，但**不要求**尊重跨进程的真实时间。

> 关系：**线性一致性 ⇒ 顺序一致性**，反之不成立（线性一致多了「实时」约束，更强、代价更高）。

### 客户端侧（会话级）一致性

| 模型 | 保证 | 典型实现 |
|------|------|----------|
| Read-Your-Writes | 总能读到自己刚写入的值 | 写后强制读主 / 会话粘滞 |
| Monotonic Reads | 不会读到「时间倒流」的旧值 | 固定读同一副本 |
| Consistent Prefix | 读到的因果顺序不乱（先因后果） | 分区内有序 |
| 会话一致性 | 同一会话内满足 Read-Your-Writes | 会话内绑定节点 |
| 因果一致性 | 有因果关系的操作顺序全局一致 | 向量时钟 / 依赖跟踪 |

### 一致性模型总览

| 模型 | 保证强度 | 性能/可用性 | 适用场景 |
|------|----------|-------------|----------|
| 线性一致性 | 最强 | 低 | 分布式锁、选主、金融余额 |
| 顺序一致性 | 强 | 中 | 需全局序但可放松实时 |
| 因果一致性 | 中 | 中 | 社交评论、协作编辑 |
| 最终一致性 | 弱 | 高 | DNS、CDN、点赞计数 |

## 8. Quorum 机制（NWR 策略）

### 一句话定义

Quorum 通过 **N**（副本总数）、**W**（写成功的副本数）、**R**（读涉及的副本数）三个参数，在一致性与可用性之间调节权衡。

### 通俗类比

就像班级表决：全班 N 人，规定至少 W 人同意才算通过、至少 R 人确认才算数——只要 W 与 R 有交集，就能保证「表决结果」被读到。

### 具体示例

```
N = 3, W = 2, R = 2  →  W + R = 4 > N = 3
// W+R > N 保证读写副本必有交集 → 能读到最新写入（强一致倾向）
// W+R ≤ N 则可能读到旧值，但可用性更高（允许更多节点故障）
```

### 为什么需要它

通过调整 NWR，可在同一套存储上灵活权衡：偏一致（W、R 大）还是偏可用（W、R 小）。

### NWR 策略对比

| 策略 | N | W | R | W+R>N | 倾向 |
|------|---|---|---|-------|------|
| 强一致 | 3 | 3 | 1 | 是 | 一致性（写慢） |
| 平衡 | 3 | 2 | 2 | 是 | 兼顾 |
| 高可用 | 3 | 1 | 1 | 否 | 可用性（可能读旧值） |

> 注意：`W+R>N` 只保证读写副本有交集，若不做版本比较（如向量时钟）或读到多个版本不取最新，仍可能读到旧值；NWR 是「必要非充分」条件。
