# 服务发现


> 📌 **导航**：本文是 **服务发现** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 服务发现(Service Discovery)是微服务架构中动态定位服务实例网络地址(IP/端口)的机制;由于实例会随扩缩容、故障、部署而不断变化,服务发现让调用方无需硬编码地址即可找到可用的服务实例。

**通俗类比：** 像用打车软件叫车——你不必记住每个司机的电话和位置,平台(注册中心)实时掌握哪些司机在线、在哪;你只说"我要打车",平台就帮你匹配到当前可用的司机。

> 多义说明:分为**客户端发现**(调用方查询注册中心并自行负载均衡)与**服务端发现**(经负载均衡器/网关转发);本文综述。

## 原理与机制

- **服务注册:** 实例启动时把地址注册到注册中心(如 Nacos、Consul、Eureka、etcd、ZooKeeper),并周期性发送心跳续约。
- **健康检查:** 注册中心探测并剔除失联或不健康的实例。
- **查询与调用:** 客户端发现下,调用方从注册中心拉取/订阅实例列表,本地负载均衡后直连;服务端发现下,经网关/LB 转发。
- 常与负载均衡、熔断、DNS 或 Kubernetes Service 配合使用。

## 关键组成

| 组成 | 作用 |
|------|------|
| 服务注册中心 | 保存服务与实例映射 |
| 注册 / 注销 | 实例上下线登记 |
| 心跳与健康检查 | 维持实例有效性 |
| 实例列表订阅 | 调用方获取可用实例 |
| 客户端 / 服务端发现 | 两种定位与转发模式 |

## 应用场景

- 微服务与云原生架构
- Kubernetes Service / Endpoints
- 服务网格(Service Mesh)
- 动态扩缩容与多实例高可用环境

## 优点与局限

- 优点:解耦地址与调用、支持动态扩缩容与故障转移、无需硬编码。
- 局限:注册中心本身需高可用(否则成单点);网络分区下面临一致性/可用性权衡(AP 或 CP 注册中心);引入额外组件与运维复杂度。

## 常见误区

- 服务发现 ≠ DNS:可用 DNS 实现,但现代方案多用注册中心 + 健康检查。
- 注册中心有 AP(如 Eureka)与 CP(如 etcd/ZooKeeper)之分(见 CAP 权衡)。
- 客户端发现需自带负载均衡逻辑。
- 服务发现 ≠ 服务网格:后者还包含流量治理与 sidecar 代理。
