# 服务发现


> 📌 **导航**：本文是 **服务发现** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 服务发现是微服务架构中动态定位服务实例网络地址（IP / 端口）的机制——实例随扩缩容、故障、部署不断变化，它让调用方无需硬编码地址即可找到可用实例。

**通俗类比：** 像用打车软件叫车——你不必记住每个司机的电话和位置，平台（注册中心）实时掌握谁在线、在哪；你说"我要打车"，平台就帮你匹配当前可用司机。

> 多义说明：分客户端发现（调用方查询注册中心并自行负载均衡）与服务端发现（经负载均衡器 / 网关转发）；本文综述。

## 为什么需要它

微服务实例数随扩缩容和发布不断变化，写死 IP / 端口既没法扩容也扛不住故障。服务发现把"服务名 → 当前可用实例列表"做成动态可查的一层，让调用方与实例解耦、支持自动故障转移。

## 核心机制

- **服务注册：** 实例启动时把地址注册到注册中心（Nacos、Consul、Eureka、etcd、ZooKeeper），并周期性发送心跳续约。
- **健康检查：** 注册中心探测并剔除失联或不健康的实例。
- **查询与调用：** 客户端发现下，调用方从注册中心拉取 / 订阅实例列表、本地负载均衡后直连；服务端发现下经网关 / LB 转发（如 Kubernetes Service + kube-proxy）。
- 常与负载均衡、熔断、DNS 配合使用。

## 具体示例

Spring Cloud：order-service 用 `@FeignClient(name="inventory-service")` 调用，由 Eureka / Nacos 拿到库存服务当前健康实例列表、客户端负载均衡直连；库存实例下线后心跳超时被摘除，调用方自动避开。

## 何时用与何时不用

- **用：** 微服务与云原生架构、动态扩缩容与多实例高可用、服务网格与 Kubernetes Service。
- **不用：** 固定少量、拓扑稳定的服务用配置或 DNS 即可，别为一堆静态服务引入注册中心这层运维成本。

## 优劣与代价

✅ 解耦地址与调用、支持动态扩缩容与故障转移、无需硬编码。
⚠️ 注册中心自身需高可用否则成单点；分区下面临一致 / 可用取舍（AP 或 CP 注册中心）；引入额外组件与运维复杂度。

## 与相关概念的区别

vs DNS：可用 DNS 实现，但现代方案用注册中心 + 健康检查，能秒级摘除坏实例，DNS 受 TTL 缓存而滞后；vs [[服务网格]]：网格在发现之上再加 Sidecar 代理与东西向流量治理，见 [[微服务治理术语百科]]。

## 常见误区

- 服务发现就是 DNS 解析。
- 注册中心不存在一致性与可用性的取舍。
- 服务发现就等于服务网格。

## 面试速答

> 🎯 服务发现 = 动态维护"服务名 → 可用实例"：实例注册 + 心跳续约、注册中心健康检查剔除失联，调用方走客户端发现（本地负载均衡直连）或服务端发现（网关 / LB 转发）。
