# 服务网格


> 📌 **导航**：本文是 **服务网格** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 服务网格（Service Mesh）是一个专门处理服务间通信的基础设施层，通常以与应用一起部署的 Sidecar 代理实现，把流量治理、安全与可观测性从业务代码下沉到基础设施、对应用透明。

**通俗类比：** 像一座城市的交通系统——每辆车（服务）不必自己研究路线、红绿灯与收费，交给统一的道路与信号系统（网格）调度即可；换任何品牌的车都不影响通行规则。

> 多义说明：服务网格特指基础设施层的服务间通信治理，与嵌在业务进程内的 SDK 方案（如早期 Spring Cloud Netflix）是两种思路；也别与管南北向入口的 API 网关混为一谈。

## 为什么需要它

微服务一多，重试 / 熔断 / 限流 / mTLS / 追踪这些横切逻辑若塞进每个服务的 SDK，会语言绑定、升级困难、各处不一致。把通信治理抽成独立基础设施层，业务代码零改动即可统一治理，多语言栈尤其受益。

## 核心机制

- **数据面：** 一组 Sidecar 代理（最常见 Envoy），与应用容器同 Pod 部署，拦截并转发进出流量，执行路由、负载均衡、重试、熔断、mTLS 加密、指标采集，应用无感知。
- **控制面：** 统一下发配置、证书与策略（如 Istio 的 istiod——自 1.5 起把原 Pilot / Citadel / Galley 合并为单一二进制，简化部署运维）。
- **透明接管：** 通过 iptables / eBPF 把流量重定向到 Sidecar，使所有服务间流量都经过它，从而提供流量管理、mTLS 安全与全链路可观测三大能力。

## 具体示例

Istio + Envoy：给"订单 → 库存"的调用配 VirtualService 做 90/10 金丝雀分流、开启 mTLS 双向认证，业务代码不改一行，流量与加密都由 Sidecar 接管。

## 何时用与何时不用

- **用：** 大规模微服务 / Kubernetes 集群的服务间通信治理、多语言技术栈要语言无关治理、零信任 mTLS、统一可观测与灰度发布。
- **不用：** 小规模系统常属过度设计（Sidecar 带来资源与延迟开销）；单一语言、治理需求简单时用框架 SDK 更省。

## 优劣与代价

✅ 治理与业务代码解耦、语言无关、可独立升级，统一提供 mTLS / 可观测 / 流量控制，降低应用侧复杂度。
⚠️ 每个服务多一个 Sidecar、带来资源与延迟；控制面本身需高可用、运维复杂；对小系统易过度设计（Sidecar-less / Ambient Mesh 是降开销的演进方向）。

## 与相关概念的区别

vs API 网关：网关管南北向（外部 → 集群）入口流量，网格管东西向（服务间）流量，二者常并存；vs SDK 方案：SDK 把治理嵌进业务进程（语言相关），网格下沉到基础设施（语言无关）。见 [[微服务治理术语百科]]。

## 常见误区

- 服务网格就是 API 网关。
- 上了服务网格就是零成本。
- 服务网格和微服务框架 SDK 是一回事。
