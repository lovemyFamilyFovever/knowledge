# 服务网格


> 📌 **导航**：本文是 **服务网格** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 服务网格（Service Mesh）是一个专门处理**服务间通信**的基础设施层，通常以与应用一起部署的 Sidecar 代理实现，把流量治理、安全与可观测性从业务代码中下沉到基础设施，对应用透明。

**通俗类比：** 就像一座城市的交通系统——每辆车（服务）不必自己研究路线、红绿灯与收费，交给统一的道路与信号系统（网格）调度即可；换任何品牌的车都不影响通行规则。

> 多义说明：服务网格特指「**基础设施层**的服务间通信治理」，与运行在业务进程内的 SDK 方案（如早期 Spring Cloud Netflix）是两种不同思路；也不要与南北向流量入口的 **API 网关**混为一谈（网格主要管东西向的服务间流量）。

## 原理与机制

- **数据面（Data Plane）**：由一组 **Sidecar 代理**（最常见为 Envoy）构成，与应用容器同 Pod 部署，拦截并转发应用的进出流量，执行路由、负载均衡、重试、熔断、mTLS 加密、指标采集等。
- **控制面（Control Plane）**：负责下发与统一管理数据面的配置、证书与策略（如 Istio 的 istiod）。
- **透明接管**：通过 iptables/eBPF 等把流量重定向到 Sidecar，应用无需改代码。

```
Sidecar 模式（数据面）：
[App Container] <-> [Envoy Sidecar] -> 网络 <-> [Envoy Sidecar] <-> [App Container]
所有服务间流量都经过 Sidecar，实现：
- 流量管理（路由 / 负载均衡 / 重试 / 熔断）
- 安全（mTLS 双向认证、授权策略）
- 可观测（指标 / 日志 / 分布式追踪）
```

```
Istio 控制面演进：
早期（< 1.5）：Pilot(配置下发) + Citadel(证书) + Galley(配置校验) 分立
1.5 起（2020）：合并为单一二进制 istiod，简化部署与运维
```

> 说明：原文档列出的 Pilot / Citadel / Galley 是 Istio 1.5 之前的组件划分；自 Istio 1.5 起，三者已合并为 **istiod**（统一控制面）。数据面主流仍是 Envoy。

## 关键组成

| 组成 | 作用 |
|------|------|
| Sidecar 代理（数据面） | 拦截并处理服务间流量，执行治理策略 |
| 控制面（如 istiod） | 下发配置、管理证书与策略 |
| 服务发现 | 感知后端实例与拓扑 |
| 遥测采集 | 输出指标 / 日志 / 追踪到可观测系统 |
| 策略引擎 | 访问控制、限流、mTLS 等 |

## 应用场景

- 大规模微服务 / Kubernetes 集群的服务间通信治理（代表实现：Istio、Linkerd、Consul Connect）。
- 多语言技术栈下需要**语言无关**的统一治理（避免为每种语言维护 SDK）。
- 零信任安全（服务间强制 mTLS）、灰度发布 / 金丝雀、全链路可观测。

## 优点与局限

- 优点：治理能力与业务代码解耦、语言无关、可独立升级；统一提供 mTLS、可观测与流量控制；降低应用侧复杂度。
- 局限：每个服务多一个 Sidecar，带来**资源开销与延迟**；引入额外运维复杂度（控制面本身需高可用）；对小规模系统常属过度设计。近年也出现 **Sidecar-less / Ambient Mesh** 等降低开销的演进方向。

## 常见误区

- 服务网格 ≠ API 网关：网关主要处理**南北向**（外部→内部）流量，网格主要处理**东西向**（服务间）流量，二者常并存。
- 服务网格 ≠ 微服务框架 SDK：SDK 把治理逻辑嵌入业务进程（语言相关），网格把它下沉到基础设施（语言无关）。
- 以为上了网格就「零成本」：Sidecar 有性能与运维代价，需评估收益是否值得。
