# 限流

## 定义

**一句话定义：** 限流(Rate Limiting)是通过控制单位时间内允许通过的请求数量(或速率)来保护系统免受突发流量/过载冲击的机制;超过阈值的请求被拒绝、排队或降级处理,以保证核心服务稳定。

**通俗类比：** 像景区限制每小时入园人数——人太多会挤爆、体验崩坏,于是在门口按速率放行,超出的先排队或改约;宁可让少数人等,也不让整体瘫痪。

> 多义说明:限流可作用在网关、服务、接口、用户/IP 等维度;常与熔断、降级并称"服务治理三板斧"。本文综述。

## 原理与机制

- **常见算法:**
  - 计数器 / 固定窗口:简单,但窗口边界可能出现突刺。
  - 滑动窗口:平滑边界问题。
  - 漏桶(leaky bucket):恒定速率流出,削峰但不允许突发。
  - 令牌桶(token bucket):匀速发令牌,允许桶容量内的一定突发,最常用。
- **维度:** 全局 / 单机,按用户 / IP / 接口 / 租户。
- **超限处理:** 拒绝(返回 429 Too Many Requests)、排队、或走降级逻辑。

## 关键组成

| 组成 | 作用 |
|------|------|
| 限流算法 | 计数器/滑动窗口/漏桶/令牌桶 |
| 阈值与窗口 | 允许的速率与统计周期 |
| 限流维度 | 全局/单机、用户/接口等 |
| 超限处理 | 拒绝 / 排队 / 降级 |

## 应用场景

- API 网关与开放平台的配额控制
- 防刷、防爬、防恶意请求
- 秒杀/抢购的削峰填谷
- 保护下游依赖、保障多租户公平性

## 优点与局限

- 优点:保护系统不被打垮、平滑流量、保障核心链路、防止资源被少数用户耗尽。
- 局限:阈值难定(过严误伤、过松无效);分布式限流需跨节点协调(一致性与性能权衡);可能影响正常用户体验;需配合监控动态调整。

## 常见误区

- 限流 ≠ 熔断:限流控制入口速率,熔断是下游故障时快速失败。
- 令牌桶允许突发(桶内积攒的令牌),漏桶不允许。
- 单机限流在多实例部署下总量会成倍放大,需分布式限流(如 Redis + Lua 或网关统一)。
