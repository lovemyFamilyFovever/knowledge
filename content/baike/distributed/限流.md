# 限流


> 📌 **导航**：本文是 **限流** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 限流通过控制单位时间内允许通过的请求数量（速率）来保护系统免受突发流量 / 过载冲击，超过阈值的请求被拒绝、排队或降级处理，以保证核心服务稳定。

**通俗类比：** 像景区限制每小时入园人数——人太多会挤爆、体验崩坏，于是在门口按速率放行，超出的先排队或改约；宁可让少数人等，也不让整体瘫痪。

> 多义说明：限流可作用在网关、服务、接口、用户 / IP 等维度，常与熔断、降级并称"服务治理三板斧"。

## 为什么需要它

流量有突发尖峰（秒杀、热点事件、爬虫刷接口），远超系统承载时会被直接打垮。限流把入口速率约束在系统可承受范围内，宁可拒绝 / 排队一部分，也要保住核心链路不被冲垮、保证多租户公平。

## 核心机制

- **算法：** 计数器 / 固定窗口（简单，但窗口边界易出突刺）、滑动窗口（平滑边界）、漏桶（恒定速率流出，削峰但不允许突发）、令牌桶（匀速发令牌、允许桶容量内一定突发，最常用）。
- **维度：** 全局 / 单机、按用户 / IP / 接口 / 租户。
- **超限处理：** 拒绝（返回 429 Too Many Requests）、排队、或走降级逻辑。

## 具体示例

开放 API 每用户每秒 100 次：网关用令牌桶（Guava RateLimiter / Sentinel）按用户维度发令牌，取到才转发、取不到返回 429；多实例部署时把令牌计数放 Redis + Lua 做分布式限流，避免单机各限各的导致总量翻倍。

## 何时用与何时不用

- **用：** API 网关 / 开放平台配额、防刷防爬、秒杀削峰填谷、保护下游依赖、保障多租户公平性。
- **不用：** 内部低流量、资源充裕的路径不必层层限流；限流只控速率，不能替代扩容解决长期容量不足。

## 优劣与代价

✅ 保护系统不被打垮、平滑流量、保障核心链路、防止资源被少数用户耗尽。
⚠️ 阈值难定（过严误伤、过松无效）；分布式限流需跨节点协调、有一致性与性能权衡；会影响正常用户体验；需配合监控动态调整。

## 与相关概念的区别

vs [[熔断与降级]]：限流控制入口速率（防过载），熔断在下游故障时快速失败（防级联），降级是过载 / 故障时的兜底返回——三者目的不同、常配合。

## 常见误区

- 限流和熔断是一回事。
- 单机限流在多实例部署下就能控住全局总量。
- 漏桶算法允许突发流量通过。

## 面试速答

> 🎯 限流 = 控单位时间请求速率护系统：令牌桶（允许一定突发、最常用）/ 漏桶（恒定削峰）/ 固定与滑动窗口；按用户 / IP / 接口分维度，超限返 429 或降级，多实例要分布式限流（Redis + Lua / 网关）。
