# CAP 定理


> 📌 **导航**：本文是 **CAP 定理** 词条，属于 distributed 术语集。相关枢纽：[[BASE 理论]]、[[CAP 定理]]、[[MapReduce]]、[[Saga 与 TCC]]、[[一致性哈希]]。

## 定义

**一句话定义：** 分布式存储在网络分区 P 不可避免时，一致性 C 与可用性 A 不可兼得——分区真的发生时只能二选一。

**通俗类比：** 两家分店通讯中断：要么停业等能核对库存（保 C 弃 A），要么各卖各的事后对账（保 A 弃 C）——链路既然断了，就无法既实时同步又照常营业。

> 多义说明：此处 C 指线性/强一致，A 指每个未故障节点都对请求给出非错误响应，P 指分区下系统仍运作。CAP 的 C 不等于 ACID 的 C。

## 为什么需要它

网络会断、会丢包，分区在跨节点系统里无法根除。CAP 把"分区真的发生时，一致与可用只能选一个"这条硬约束讲清楚，为架构选型提供不可回避的取舍框架。

## 核心机制

- P 不可避免 → 实际权衡落在 C 与 A 之间：
  - **CP：** 分区时拒绝可能返回旧值的请求（弃 A 保 C），如基于强一致共识的存储。
  - **AP：** 分区时继续响应但可能返回旧数据（弃 C 保 A），事后靠最终一致收敛。
- **无分区时** C 与 A 可同时满足。
- **延伸 PACELC：** 分区时权衡 A/C，否则（E）在延迟（L）与一致（C）间再权衡，补上 CAP 未覆盖的正常期权衡。

## 具体示例

注册中心选型：ZooKeeper / etcd 偏 CP，分区时少数派不可写以杜绝脑裂；Eureka 偏 AP，分区时仍允许注册与发现，代价是可能返回过期实例。

## 何时用与何时不用

- **用：** 多副本存储 / 共识系统的设计与选型讨论，界定分区发生时的一致性—可用性取舍。
- **不用：** 把它当成日常延迟指标（那是 PACELC 的 L），或在单机 / 无分区场景强行套用。

## 优劣与代价

✅ 给出简洁、不可回避的分布式取舍框架，指导选型。
⚠️ 易被过度简化——C/A 是程度问题而非绝对二元；只刻画分区时刻，忽略正常态延迟。

## 与相关概念的区别

vs ACID 的 C：CAP 的 C 讲副本间数据一致（线性一致），ACID 的 C 讲事务不破坏约束，不是一回事；vs [[BASE 理论]]：BASE 是承认 P 后选 AP 的工程落地路线。

## 常见误区

- CAP 允许在 C、A、P 里自由挑其中两个。
- CAP 的"一致性"就是 ACID 的"一致性"。
- CAP 认为 C 与 A 永远不可能同时满足。

## 面试速答

> 🎯 CAP：分区 P 不可避免，分区发生时一致 C 与可用 A 二选一（CP 弃可用、AP 弃一致），无分区时可兼得；PACELC 再补正常态延迟权衡。
> 🔍 追问：为什么说 P 几乎必选、权衡实际落在 C/A？
> 🔍 追问：CAP 的 C 和 ACID 的 C 差在哪？
