# 分布式事务

## 定义

**一句话定义：** 分布式事务是指跨多个数据源、服务或节点的事务，需要在部分参与者可能失败、网络可能不可靠的情况下，保证这组操作要么整体生效、要么整体不生效（或达到约定的最终一致）。

**通俗类比：** 就像跨行转账——你的账户（服务 A）扣款和对方账户（服务 B）入账必须同成同败；不能出现「钱扣了却没到账」，也不能「没扣钱却到账了」。

> 多义说明：分布式事务分**强一致（刚性事务）**与**最终一致（柔性事务）**两大类——前者如 2PC/3PC/XA，追求任意时刻一致但性能与可用性差；后者如 TCC、Saga、消息事务，牺牲强一致换取高可用与高吞吐（对应 BASE 理念）。

## 原理与机制

### 2PC（两阶段提交）

```
阶段一 Prepare：
  协调者 -> 参与者A：Prepare（A 执行事务、锁定资源、写 undo/redo，回 Yes/No）
  协调者 -> 参与者B：Prepare（B 同上）
阶段二 Commit/Rollback：
  全部 Yes -> 协调者发 Commit -> A、B 提交并释放锁
  任一 No  -> 协调者发 Abort  -> A、B 回滚并释放锁
```
> 修正：原文档 ASCII 中「叔与者B」应为「参与者B」。

**问题**：同步阻塞（Prepare 后参与者一直持锁等待）、协调者单点故障、阶段二网络异常时可能数据不一致。

### 3PC（三阶段提交）

在 2PC 前增加 **CanCommit** 阶段，并为参与者引入**超时机制**，缓解阻塞；但在网络分区下仍无法完全避免不一致，工程中使用较少。

### TCC（Try-Confirm-Cancel）

```
Try:     预留资源（如冻结库存 / 预扣额度）
Confirm: 确认执行（扣减已冻结的库存）——需幂等
Cancel:  取消（释放冻结的库存）——需幂等
```
业务侵入性强（每个操作要拆成三个），但一致性由业务层精确控制，性能好。

### Saga

```
正向：T1 -> T2 -> T3（每步都是本地事务）
若 T3 失败：执行补偿 C2 -> C1（回滚已完成步骤的副作用）
```
适合长事务、跨服务流程；无隔离性（中间状态对外可见），需处理补偿与幂等。

### 本地消息表 / 事务消息（最终一致）

```
1. 业务操作 + 写消息表，在同一个本地事务中提交（保证原子）
2. 后台轮询消息表 / 或用 MQ 事务消息（如 RocketMQ），投递到下游
3. 下游消费并处理，成功后确认；失败则重试（下游需幂等）
```

## 关键组成（方案对比）

| 方案 | 一致性 | 性能 | 业务侵入 | 典型场景 |
|------|--------|------|----------|----------|
| 2PC / XA | 强一致 | 低（同步阻塞） | 低 | 传统数据库跨库事务 |
| 3PC | 强一致 | 低 | 低 | 理论改进，少用 |
| TCC | 最终一致 | 高 | **高**（写三方法） | 资金、库存等核心交易 |
| Saga | 最终一致 | 高 | 中（写补偿） | 长流程、跨服务编排 |
| 本地消息表 / 事务消息 | 最终一致 | 高 | 中 | 异步解耦、通知类 |

## 应用场景

- 电商下单（扣库存 + 创建订单 + 扣款跨多个服务）。
- 跨库 / 跨服务的数据一致性、金融交易、订单履约流程编排。
- 微服务拆分后原单体本地事务被打破的场景。

## 优点与局限

- 优点（强一致方案）：语义清晰、任意时刻一致；（柔性方案）：高可用、高吞吐、契合微服务。
- 局限：强一致方案性能差、协调者易成瓶颈 / 单点；柔性方案需保证**幂等**、处理补偿与最终一致的中间态，业务复杂度上升。

## 常见误区

- 以为 2PC「万无一失」：阶段二若协调者宕机或部分 Commit 消息丢失，参与者会陷入阻塞或不一致。
- 忽视**幂等**：TCC 的 Confirm/Cancel、消息消费都可能被重复触发，必须幂等（见 [[幂等性]]）。
- 强一致与最终一致不分场景乱用：核心资金可用 TCC 求较强一致，通知类用消息求最终一致即可。
- 混淆 CAP/BASE：分区容错（P）必选，通常在 C 与 A 间权衡；BASE（基本可用、软状态、最终一致）是对强一致的工程化让步。
