# 配置中心

> 📌 **导航**：本文是 **配置中心** 词条，由 [[微服务治理术语百科]] 拆分而来。

## 定义

**一句话定义：** 配置中心集中管理各微服务的配置项，支持不重启动态更新、版本管理、灰度下发与一键回滚，把散落在各服务里的配置收敛为一个统一可控的配置源。

**通俗类比：** 像酒店的中央空调总控——前台一处调温即可覆盖各房间（动态下发），能查看历史设定（版本），也能先试调某几层看效果（灰度）。

## 为什么需要它

配置散在几十个服务里、改动要重启、难以快速响应运营与安全变更、也没法版本回滚。配置中心把配置外置、集中管理、推送生效，让"改配置"像"改数据"一样即时、可控、可追溯。

## 核心机制

- **动态刷新：** 客户端通过长轮询 / 订阅感知配置变更并热更新，无需重启（Spring `@RefreshScope`、`@Value` 重新绑定）。
- **版本与灰度：** 配置按 namespace / group / key 组织，保留历史版本，支持灰度发布与一键回滚。
- **多环境隔离：** dev / test / prod 用 namespace 分开，避免误改。
- **典型实现：** Apollo（推送、灰度、权限强）、Nacos（配置 + 注册一体）、Spring Cloud Config（依托 Git + Bus 刷新）。

## 具体示例

把下单超时 `order.timeout` 交给 Nacos：运营改值后 `@RefreshScope` Bean 热生效、无需重启；发版前先在灰度命名空间对 10% 实例下发验证，OK 再全量，出问题一键回滚到旧版本。

## 何时用与何时不用

- **用：** 服务众多、配置需频繁热更、要版本 / 灰度 / 回滚、跨环境隔离。
- **不用：** 单服务或极少变更的配置用环境变量 / 配置文件即可；密钥、口令等敏感值应走专用密管（KMS / Vault），而非明文放配置中心。

## 优劣与代价

✅ 集中治理、热更新免重启、版本可回滚、灰度可控。
⚠️ 引入额外组件与其可用性依赖（配置中心不可用时要能降级读本地快照）；动态刷新对连接池等重资源不友好；权限与审计需配套。

## 与相关概念的区别

vs 服务注册中心：Nacos 等常两者合一，但"配置下发"与"服务实例上下线登记"职责不同（见 [[服务发现]]）；vs 环境变量 / 启动参数：那些须重启才生效、无版本与灰度能力。

## 常见误区

- 在配置中心改完值，所有 Bean 就立刻自动生效、无需做任何热刷新适配。
- 密钥、密码直接放配置中心明文管理最省事。
- 配置中心和注册中心是同一个东西、装一个就够。

## 面试速答

> 🎯 配置中心集中管微服务配置、支持不重启热更新（@RefreshScope）+ 版本 / 灰度 / 回滚 + 多环境 namespace 隔离，典型 Apollo / Nacos / Spring Cloud Config；与注册中心职责不同，密钥应走 KMS 而非明文配置。
