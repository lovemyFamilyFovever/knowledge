# 微服务治理术语百科

> 本文档是微服务**服务治理**核心概念的合集：注册发现、熔断、限流、降级、链路追踪、配置中心、网关、灰度发布。已有专门词条的主题（负载均衡、服务网格）只保留一句话定义并双链过去，避免重复维护。

---

## 1. 服务注册与发现模式

### 一句话定义

服务注册与发现是微服务间**动态感知彼此存在**的机制，实现服务实例的自动注册、健康检查与地址查询。

### 通俗类比

就像外卖平台：商家入驻（注册），平台实时监控商家是否在线（健康检查），用户搜索时展示附近可用商家（发现）。

### 具体示例

```java
// 服务注册（Spring Cloud 启用服务发现）
@SpringBootApplication
@EnableDiscoveryClient
public class OrderServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }
}

// 服务发现（声明式调用，无需知道具体 IP）
@FeignClient(name = "inventory-service")
public interface InventoryClient {
    @PostMapping("/api/inventory/deduct")
    Result deduct(@RequestBody DeductDTO dto);
}
```

### 为什么需要它

微服务实例动态扩缩容、IP 频繁变化，手动维护地址列表不现实，需要自动化的注册与发现机制。

### 三种发现模式对比

| 模式 | 代表 | 特点 |
|------|------|------|
| 客户端发现 | Eureka + 客户端负载均衡 | 客户端自行选实例、少一跳 |
| 服务端发现 | 负载均衡器 + Consul | 中心化选实例，客户端无感 |
| DNS 发现 | CoreDNS + Kubernetes | 基于 DNS 解析，跨语言友好 |

> 注：Netflix Ribbon 已进入维护模式，Spring Cloud 现默认用 **Spring Cloud LoadBalancer** 替代客户端负载均衡。

## 2. 负载均衡（客户端 / 服务端 / 代理）

**一句话定义：** 将请求按策略分发到多个服务实例，以提升整体吞吐与可用性、避免单实例过载。

> 📎 已有专门词条：[[负载均衡]]（含 L4/L7、调度算法、健康检查、会话保持、VIP 及常见误区）。常见策略速记：轮询、加权轮询、随机、最少连接、IP 哈希（会话保持）、一致性哈希。

## 3. 熔断器模式（Hystrix / Resilience4j / Sentinel）

### 一句话定义

熔断器（Circuit Breaker）在下游故障时**快速失败**并暂时切断调用，防止故障沿调用链级联放大（雪崩），并在恢复后自动闭合。

### 通俗类比

就像家庭电路的保险丝 / 空气开关：电流过大时自动跳闸（熔断），避免烧毁整个电路；故障排除后再合闸恢复。

### 状态机

```
Closed（正常放行，统计失败率）
  └─失败率超阈值→ Open（直接拒绝/走降级，不再调用下游）
                    └─等待冷却时间→ Half-Open（放少量试探请求）
                                      ├─成功→ 回到 Closed
                                      └─失败→ 回到 Open
```

### 具体示例

```java
// Resilience4j 熔断器 + 降级
@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallback")
public Result deductInventory(DeductDTO dto) {
    return inventoryClient.deduct(dto);
}

public Result fallback(DeductDTO dto, Throwable t) {
    return Result.fail("库存服务暂时不可用，请稍后重试");
}
```
```yaml
resilience4j.circuitbreaker:
  instances:
    inventoryService:
      slidingWindowSize: 100
      failureRateThreshold: 50        # 失败率达 50% 触发熔断
      waitDurationInOpenState: 10s    # Open 后冷却 10s 进入 Half-Open
```

### 为什么需要它

一个服务故障可能导致整条调用链线程 / 资源被占满而级联崩溃；熔断器通过快速失败与降级，隔离故障、保护系统整体稳定。

### 三大实现对比

| 特性 | Hystrix | Resilience4j | Sentinel |
|------|---------|--------------|----------|
| 维护状态 | 停止维护（2018 起维护模式） | 活跃 | 活跃 |
| 隔离方式 | 线程池 / 信号量 | 信号量（Bulkhead） | 并发线程数 / 信号量 |
| 限流能力 | 不内置 | 内置 RateLimiter 模块 | 内置（核心能力） |
| 控制台 | Hystrix Dashboard | 无（需配 Micrometer） | Sentinel Dashboard |

> 修正：原文档称「Hystrix 不支持信号量、Resilience4j 不支持限流」有误——Hystrix 支持线程池与信号量两种隔离，Resilience4j 提供独立的 RateLimiter 限流模块。

## 4. 限流（令牌桶 / 漏桶 / 滑动窗口 / RateLimiter）

### 一句话定义

限流是控制单位时间内的请求速率，超出阈值的请求被拒绝或排队，以防止系统被突发流量压垮。

### 通俗类比

就像高速公路入口的匝道信号灯：无论主路外有多少车，每次只放行固定数量，确保主路车流平稳。

### 具体示例

```java
// 令牌桶（Guava RateLimiter）
RateLimiter rateLimiter = RateLimiter.create(100); // 每秒 100 个令牌
if (rateLimiter.tryAcquire()) {
    processRequest(request);          // 拿到令牌，放行
} else {
    throw new RateLimitException("请求过于频繁");
}

// Sentinel 声明式限流
@SentinelResource(value = "orderCreate", blockHandler = "blockHandler")
public Result createOrder(OrderDTO dto) {
    return orderService.create(dto);
}
```

### 为什么需要它

突发流量（秒杀、热点事件）可能瞬间耗尽资源；限流把请求控制在系统可承受范围内，是稳定性保护的第一道闸门。

### 限流算法对比

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 令牌桶 | 按速率生成令牌，取到才放行 | 允许一定突发 | 实现较复杂 |
| 漏桶 | 请求入桶、固定速率流出 | 流量平滑 | 不允许突发 |
| 滑动窗口 | 统计滚动窗口内请求数 | 精确、缓解临界 | 内存消耗较大 |
| 固定窗口 | 统计固定时间窗口 | 简单 | 窗口临界点可能翻倍 |

## 5. 降级策略（自动 / 手动 / 读 / 写降级）

### 一句话定义

降级是在系统压力过大或依赖不可用时，**主动关闭或简化非核心功能**，以保障核心业务可用的策略。

### 通俗类比

就像商场人流过大时，先关闭餐饮娱乐区（非核心），只保留主通道与收银（核心），加快疏散、避免踩踏。

### 具体示例

```java
// 自动降级：按系统指标触发
@EventListener
public void onHighLoad(SystemLoadEvent event) {
    if (event.getCpuUsage() > 80) {
        featureToggle.disable("recommendation"); // 关闭非核心推荐
        enableCacheOnlyMode();                   // 降级为只读缓存
    }
}

// 手动降级：控制台一键开关
@PostMapping("/admin/degrade")
public Result manualDegrade(@RequestParam String service) {
    degradeService.activate(service);
    return Result.ok("已降级");
}
```

### 为什么需要它

与其让系统在过载时全面崩溃，不如牺牲非核心功能（推荐、评论、部分查询）保住核心链路（下单、支付）。

### 降级策略对比

| 策略 | 触发方式 | 适用场景 |
|------|----------|----------|
| 自动降级 | 系统指标（CPU/RT/错误率） | 可预测的过载 |
| 手动降级 | 人工开关（预案） | 突发/不可预测故障 |
| 读降级 | 读走缓存/默认值 | 读压力大 |
| 写降级 | 异步化/削峰 | 写压力大 |

## 6. 链路追踪（Jaeger / Zipkin / SkyWalking / OpenTelemetry）

### 一句话定义

链路追踪（Distributed Tracing）记录一次请求在分布式系统中流经各服务的**完整调用链**，用于定位性能瓶颈与故障点。

### 通俗类比

就像快递物流追踪：从下单到发货、中转、派送，每个环节都有记录，你能看到包裹当前卡在哪一步。

### 核心概念

- **Trace**：一次完整请求的全局链路，由唯一 TraceId 标识。
- **Span**：链路中的一个工作单元（一次方法调用 / 一次 RPC），含开始时间、耗时、标签，Span 之间有父子关系。
- 通过在各服务间透传 TraceId/SpanId（如 W3C Trace Context、B3 头）串联全链路。

### 具体示例

```java
// OpenTelemetry 手动创建 Span
Tracer tracer = GlobalOpenTelemetry.getTracer("order-service");
Span span = tracer.spanBuilder("createOrder").startSpan();
try (Scope scope = span.makeCurrent()) {
    // 业务逻辑（子调用自动挂到当前 Span 下）
} finally {
    span.end();
}
```

### 为什么需要它

微服务调用链复杂，一次请求可能跨十几个服务；链路追踪帮助快速定位「慢在哪、错在哪」，是可观测性三大支柱之一（Metrics / Logging / Tracing）。详见 [[可观测性工程实践]]。

### 主流工具对比

| 特性 | Jaeger | Zipkin | SkyWalking | OpenTelemetry |
|------|--------|--------|------------|---------------|
| 定位 | 追踪系统 | 追踪系统 | APM 全家桶 | 标准 + SDK（非后端） |
| 语言支持 | 多语言 | 多语言 | Java 优先、多语言 | 多语言 |
| 存储/UI | 有 UI | 有 UI | 有 UI | 无（需配后端与 UI） |
| 现状 | CNCF 毕业 | 早期主流 | 国内广泛 | 事实标准（融合 OpenTracing/OpenCensus） |

## 7. 配置中心（动态配置 / 版本管理 / 灰度发布）

### 一句话定义

配置中心集中管理各微服务的配置，支持**动态更新**（不重启生效）、版本管理、灰度发布与回滚。

### 通俗类比

就像酒店中央空调系统：前台可统一调整所有房间温度（动态配置），能查看历史设置（版本管理），也能先调部分楼层试效果（灰度）。

### 具体示例

```yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        namespace: prod
        group: DEFAULT_GROUP
        data-id: order-service.yml
```
```java
@RefreshScope            // 配置变更时自动刷新 Bean
@RestController
public class ConfigController {
    @Value("${order.timeout:30}")
    private int orderTimeout;   // 配置热更新后生效
}
```

### 为什么需要它

配置散落在各服务、修改需重启，无法快速响应运营与安全变更；配置中心实现集中管理与动态下发。

### 配置中心能力对比

| 能力 | Apollo | Nacos | Spring Cloud Config |
|------|--------|-------|---------------------|
| 动态更新 | 支持（推送） | 支持 | 需配合 Bus/Refresh |
| 版本管理 | 支持 | 支持 | 依赖 Git |
| 灰度发布 | 支持 | 支持 | 不支持 |
| 配置回滚 | 支持 | 支持 | 依赖 Git |

## 8. API 网关（路由 / 认证 / 限流 / 日志 / 转换）

### 一句话定义

API 网关是微服务架构的**统一入口**，负责路由转发、安全认证、流量控制、协议转换与日志监控等横切能力。

### 通俗类比

就像机场安检与值机大厅：所有乘客（请求）都经此统一核验身份（认证）、控制人流（限流）、分配登机口（路由）。

### 具体示例

```yaml
# Spring Cloud Gateway 路由 + 限流
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200
```

### 为什么需要它

微服务对外暴露众多接口，需要统一入口做安全管控、流量治理与协议适配，避免每个服务重复实现这些横切关注点。

### 主流网关对比

| 特性 | Spring Cloud Gateway | Kong | Zuul(1.x) |
|------|---------------------|------|-----------|
| 模型 | 响应式（Netty/WebFlux） | 基于 Nginx/OpenResty | Servlet 阻塞 |
| 扩展 | 过滤器/插件 | Lua 插件 | 过滤器 |
| 语言 | Java | Lua | Java |
| 现状 | 活跃 | 活跃 | 维护模式 |

### 与服务网格的关系

网关处理**南北向**（外部→集群）流量；服务网格处理**东西向**（服务间）流量，二者常并存。详见 [[服务网格]]。

## 9. 服务网格（Service Mesh / Istio / Envoy）

**一句话定义：** 处理服务间通信的**基础设施层**，通过 Sidecar 代理把流量治理、安全与可观测性从业务代码下沉到基础设施。

## 10. 灰度发布（金丝雀 / 蓝绿 / A-B 测试）

### 一句话定义

灰度发布是把新版本**逐步**放量给部分用户，验证无问题后再全量的部署策略，以控制风险、支持快速回滚。

### 通俗类比

就像餐厅试菜：新菜先给少数 VIP 试吃（金丝雀），反馈良好再上正式菜单；或同时备两套厨房随时切换（蓝绿）。

### 具体示例

```yaml
# 金丝雀：按权重分流（Nginx）
upstream order-service {
    server 192.168.1.101:8080 weight=90; # 旧版本 90%
    server 192.168.1.102:8080 weight=10; # 新版本 10%
}
```

### 为什么需要它

一次性全量发布风险高；灰度发布把影响面控制在小流量内，发现问题可快速回滚，降低发布事故。

### 发布策略对比

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 金丝雀 | 小比例流量先行验证 | 风险低 | 验证周期较长 |
| 蓝绿 | 两套环境整体切换 | 回滚快 | 资源占用翻倍 |
| A/B 测试 | 按用户特征分流对比 | 数据驱动、精准 | 实现复杂 |
| 滚动更新 | 分批替换实例 | 平滑、资源省 | 回滚相对慢 |

## 常见误区（跨术语）

- **熔断 vs 限流 vs 降级**：限流控制**入口速率**（防过载）；熔断切断**对故障下游的调用**（防级联）；降级是**兜底返回**（保核心）。三者常配合使用，不可混为一谈。
- 以为 Hystrix 仍是首选：Hystrix 已于 2018 年进入维护模式，新项目多选 Resilience4j 或 Sentinel。
- 网关与服务网格职责混淆：网关管南北向入口流量，网格管东西向服务间流量。
