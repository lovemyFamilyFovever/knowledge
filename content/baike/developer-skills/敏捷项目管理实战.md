# 敏捷项目管理实战

> 📌 **导航**：本页是 **敏捷项目管理实战** 枢纽，索引 7 个子词条；工程实践（TDD/结对/CI-CD）双链到已有专条。

## 定义

**一句话定义：** 敏捷项目管理是以 [[敏捷宣言与原则]] 为价值观、以 Scrum/看板等框架为载体，通过短迭代、持续反馈与回顾改进来交付价值的研发管理方法体系。

**通俗类比：** 像一支定期对齐的桨乐队——不靠一个人喊号子从头划到尾，而是一桨一段、看水况随时调整方向，越划越顺。

## 为什么需要它

需求不确定、环境多变时，"一次规划到底"的瀑布式管理会不断返工、错失反馈。敏捷用短周期交付 + 频繁检视，把风险切碎、把纠偏提前，让团队在变化中持续产出可用价值；并通过回顾把"过程本身"也纳入改进。

## 核心机制

方法论按用途分层，各自成条：

| 子词条 | 管什么 |
|---|---|
| [[敏捷宣言与原则]] | 价值观与取舍罗盘 |
| [[Scrum框架]] | 角色/事件/工件的迭代框架 |
| [[看板方法]] | 连续流 + WIP 限制 + 流动度量 |
| [[用户故事与敏捷估算]] | 需求切片(INVEST/验收)与规模估算 |
| [[需求梳理与优先级]] | Backlog 维护与优先级(MoSCoW/Kano/拆分) |
| [[迭代与回顾]] | 计划→站会→评审→回顾闭环 |
| [[规模化敏捷框架]] | 多团队协同(SAFe/LeSS/Nexus/Spotify) |

支撑敏捷落地的工程实践另有专条：测试见 [[测试驱动开发]]、协作见 [[结对编程]]、交付管道见 [[CI 与 CD]]。

## 具体示例

一次典型迭代：用 [[需求梳理与优先级]] 备好有序 Backlog → [[Scrum框架]] 的计划会按 [[用户故事与敏捷估算]] 选入本周故事 → 每日 [[迭代与回顾]] 站会同步、以 [[CI 与 CD]]/[[测试驱动开发]] 保障质量 → 评审演示增量、回顾改进流程。流程框架与工程实践缺一不可。

## 何时用与何时不用

- **用**：需求持续演进、需要快速反馈与跨职能协作的研发团队；组织级用规模化框架对齐。
- **不用**：需求极稳定、强合规/安全关键、变更成本极高的场景可偏重前置设计；也不要"只上仪式、不建工程实践"的形式主义敏捷。

## 优劣与代价

✅ 短反馈、拥抱变化、聚焦价值、持续改进，激发自组织。
✅ 框架与实践组合灵活（Scrum/看板/Scrumban 按场景选）。
⚠️ 易沦为"站会+看板"的形式敏捷，缺 TDD/CI 支撑则质量与速度双输。
⚠️ 规模化框架有治理复杂度与官僚化风险。

## 与相关概念的区别

- **敏捷 vs Scrum/看板**：敏捷是理念，Scrum/看板是其落地框架（见上表）。
- **流程方法 vs 工程实践**：敏捷管理解决"怎么组织协作与交付"；TDD、结对、持续集成解决"怎么把代码做对做稳"，二者互补。

## 常见误区

- 开了每日站会、贴了看板，团队就自动敏捷了。
- 敏捷不需要任何文档和计划，全靠临场发挥。
- 用了 Scrum 就不需要测试驱动、持续集成等工程实践。

## 面试速答

> 🎯 敏捷项目管理=以敏捷宣言为价值观、Scrum/看板为载体，短迭代 + 频繁反馈 + 回顾改进交付价值。子域涵盖：宣言原则、Scrum、看板、用户故事与估算、需求梳理与优先级、迭代回顾、规模化(SAFe/LeSS/Nexus)。须配 TDD/结对/CI-CD 等工程实践，否则沦为形式敏捷。
