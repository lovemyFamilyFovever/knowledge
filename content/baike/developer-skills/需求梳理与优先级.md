# 需求梳理与优先级

> 📌 **导航**：本文是 **需求梳理与优先级** 词条，属 [[敏捷项目管理实战]] 子词条。

## 定义

**一句话定义：** 需求梳理（Backlog Refinement）是持续把产品待办列表维护成"适度详细、已估算、已排序、涌现演进"的有序清单的活动；优先级排序则用 MoSCoW、价值×复杂度、Kano 等方法决定先做什么。

**通俗类比：** 像整理一张不断变长的购物清单——不只是记要买什么，还要按"必须/想要"分级、把含糊的条目问清楚、把大件拆成小件，让下次出门能高效扫货。

## 为什么需要它

Backlog 若乱、粗、无优先级，Sprint 计划就会临时扯皮、团队被迫自己猜优先级。持续梳理把高层主题逐层细化到可交付的故事并排序，让"下一步做什么"始终明确，也让产品愿景能落地为有序的可执行条目。

## 核心机制

- **DEEP 原则**：Detailed appropriately 适度详细、Emergent 涌现、Estimated 已估算、Prioritized 已排序。
- **三层结构**：史诗/主题（季度级）→ 特性（月级）→ 用户故事（周级）。
- **优先级方法**：MoSCoW（Must/Should/Could/Won't）；价值×复杂度矩阵（先做高价值低复杂度的"快速收益"）；Kano 模型（基本型/期望型/兴奋型）。
- **拆分模式**：按工作流步骤、按业务规则、按数据类型、按边界条件等把一个故事切成多个可独立交付的小故事。

## 具体示例

把"完整结账流程"按工作流步骤拆成可独立交付的小故事：

```
结账流程 → 输入收货地址 / 选择配送方式 / 输入支付信息 / 确认下单
价值×复杂度矩阵：
        低复杂度        高复杂度
高价值  快速收益(先做)   战略投资(计划做)
低价值  填充项          避免/重构
```

## 何时用与何时不用

- **用**：Backlog 庞大、需求含糊、多个干系人争抢优先级、Sprint 计划频繁超时。
- **不用（节制）**：把所有条目都细化到同一颗粒度是浪费——远期条目本就该粗、近期才细（适度详细）。

## 优劣与代价

✅ 让优先级透明、需求可执行、减少计划期扯皮。
✅ 拆分出小而可交付的故事，改善流动与反馈。
⚠️ 梳理是持续活动，一次性"倒完再说"会迅速失效。
⚠️ 无客观优先级方法时，易被嗓门最大者主导。

## 与相关概念的区别

- **需求梳理 vs Sprint 计划**：梳理持续改进整个 Backlog 的成熟度；Sprint 计划是从中挑选本次要做的子集。
- **MoSCoW vs Kano**：MoSCoW 直接给优先级档位；Kano 按"满意度影响"分类需求性质，辅助定序。
- **史诗/特性/故事**：粒度从粗到细的不同层级，非三种不同东西。

## 常见误区

- Backlog 里每条需求都该写到同样详细、能直接开工。
- 优先级就是按"谁提的需求谁嗓门大"来排。
- 梳理会是把 Backlog 全部重新估一遍就结束的一次性活动。

## 面试速答

> 🎯 需求梳理=持续让 Backlog 满足 DEEP(适度详细/涌现/已估算/已排序)，按史诗→特性→故事分层；优先级用 MoSCoW、价值×复杂度矩阵、Kano(基本/期望/兴奋)；大故事按工作流/业务规则/数据类型拆成可独立交付的小故事。让"下一步做什么"始终明确。
