# 声明式风格与惰性求值

> 📌 **导航**：本文是 **声明式风格与惰性求值** 词条，属 [[函数式编程（Functional Programming）概念]] 子词条。基础概念见 [[函数式编程基础]]。

## 定义

**一句话定义：** 声明式风格关注"要什么结果"而非"怎么一步步算"（用 map/filter/reduce 描述数据转换）；惰性求值是"不到需要时不算"——表达式延迟到真正取其值时才计算。二者共同构成函数式代码"简洁 + 可处理无限序列"的风格底座。

**通俗类比：** 命令式像逐步报导航路线（左转、直行、右转），声明式像只说目的地；惰性求值像外卖——下单那一刻才开始做，不是提前全做好摆着。

## 为什么需要它

一步步写循环与状态变更，代码冗长且易在细节出错；声明式把"意图"直接表达出来，读起来更接近问题本身、也更易并行与优化。急切求值则要为"暂时用不到的中间结果"预付全部内存与计算；惰性求值把计算推迟，得以优雅处理无限序列与大数据流，并天然支撑短路、记忆化。

## 核心机制

- **声明式 vs 命令式**：命令式控制流程（for/while/if 改状态），声明式描述转换（`filter(偶数)`、SQL `SELECT ... WHERE`），隐藏"怎么做"。
- **惰性求值的落地**：Haskell 默认惰性；Python 生成器 `yield`、`range`/生成器表达式；JS 的 `function*`/迭代器协议；各语言的 `map/filter` 惰性视图（如 Rust 迭代器 `.iter().map().filter()` 不 `collect` 就不算）。
- **按需消费**：`next()`/迭代器一次产一个值，可表达无限序列（斐波那契流）而不耗尽内存。
- **与引用透明协同**：惰性成立的前提是纯/引用透明（[[函数式编程基础]]），否则"延后算"会因副作用产生歧义。

## 具体示例

惰性生成斐波那契流，只按需产出：

```python
def fib():
    a, b = 0, 1
    while True:
        yield a          # 惰性：next() 时才计算
        a, b = b, a + b

g = fib()
first = [next(g) for _ in range(5)]  # [0,1,1,2,3]，不必算完无穷
```

## 何时用与何时不用

- **用**：数据清洗/转换管道、SQL/声明式配置、需要处理无限流或超大序列、想少写样板循环时用声明式 + 惰性。
- **不用**：需要即时错误定位（惰性会推迟报错、难追栈）、或在严格求值语言里硬造惰性徒增心智；性能敏感且每项都要算时，急切 + 向量化可能更快。

## 优劣与代价

✅ 声明式更简洁、可读、易组合、便于并行与优化；惰性省内存、可表达无限序列、支持短路。
✅ 与纯函数/引用透明契合，行为可预测。
⚠️ 惰性使错误发生点远离原因、调试与性能剖析更难（Haskell 空间泄漏即此类）。
⚠️ 过度声明式/层层惰性对新人不直观，隐藏了实际计算成本。

## 与相关概念的区别

- **声明式 vs 函数式**：函数式是一种声明式风格，但声明式还含 SQL、HTML、CSS、逻辑编程等，不等于函数式。
- **惰性 vs 急切求值**：惰性按需算（生成器、Haskell）、急切立即算（Python 列表字面量、多数命令式语言）。
- **惰性求值 vs 记忆化**：前者决定"何时算"，后者决定"算过的复用"，常配合使用。

## 常见误区

- 声明式编程就等于函数式编程，两者是一回事。
- 惰性求值一定更快，因为它省掉了不需要的计算。
- 生成器/惰性流会把整个序列先算好再逐个返回。

## 面试速答

> 🎯 声明式=描述"要什么"(map/filter/SQL)而非"一步步怎么做"，更简洁易并行；惰性求值=用到才算(生成器 yield、Haskell)，能扛无限序列与大数据流、省内存。惰性以引用透明为前提，代价是报错点远离原因、调试与性能更难。声明式比函数式更广(含 SQL/CSS)。
