# 编译原理与解释器实现

> 📌 **导航**：本页是 **编译原理** 枢纽。各阶段已立/双链专条；本页给总览与"动手造语言"串讲。

## 定义

**一句话定义：** 编译是把源码逐阶段翻译：词法→语法→语义→中间表示→优化→代码生成；解释器则以不同方式（树遍历/字节码/[[即时编译]]）执行同一程序——本页总览全流水线并串起动手构建。

**通俗类比：** 像一条翻译流水线：先断词（词法）、再析句（语法）、校验语义（类型/作用域）、转成中间稿（IR）、润色（优化）、最后落地成目标语（机器码）；解释器则"边听边译"。

## 为什么需要它

现代语言运行靠这套分层：把"语言"与"目标机器"解耦（IR + 前端/后端）、把正确性前置（语法/语义检查）、用统一优化提性能。懂全貌才能读懂 clang/LLVM/JVM/各脚本引擎，也才能自己造 DSL 或小语言。

## 核心机制

流水线各阶段归口（前后端多已建专条）：

| 阶段 | 归口 |
|---|---|
| 词法：字符流→token | [[词法分析]] |
| 语法：token→AST | [[语法分析]]、[[抽象语法树]] |
| 语义：符号表/类型检查 | [[语义分析]] |
| 中间表示：三地址/SSA/LLVM IR | [[中间表示]] |
| 优化：机器无关变换 | [[编译优化]] |

| 运行期执行：字节码 + JIT | [[即时编译]] |

架构总览：经典多趟编译器 = 前端(词法/语法/语义) + 中端(IR+优化) + 后端(代码生成)；M+N 解耦语言与平台。实战构建语言：可先做树遍历解释器（最快见效），再优化为 AST 编译→字节码→JIT（[[即时编译]]），逐步逼近真实引擎。

## 具体示例

一个最小 pipeline 的心智：`let x = 1 + 2*3;` 依次经 词法（token）→ 语法/AST（乘法挂加法右侧，见 [[抽象语法树]]）→ 语义（x 类型 int）→ IR（三地址）→ 优化（常量折叠成 7，见 [[编译优化]]）→ 代码生成（落地指令）。

## 何时用与何时不用

- **用**：设计语言/DSL、优化运行时、理解并扩展编译器/虚拟机、做静态分析工具。
- **不用**：简单脚本用现成解释器即可，无需自研编译管线；性能不敏感处别过度优化。

## 优劣与代价

✅ 分层 + IR 让语言与硬件解耦、优化可复用、正确性可前置。
✅ 从解释器到 JIT 有清晰演进路径，便于按需取舍开发速度/运行速度。
⚠️ 完整编译链工程量大、各阶段皆有 NP 难（寄存器分配/优化）近似。
⚠️ 调试跨阶段（IR/优化后行为漂移）成本高。

## 与相关概念的区别

- **编译 vs 解释 vs [[即时编译]]**：编译期整体翻成机器码、解释器逐条执行、JIT 运行时按需编译缓存。
- **前端 vs 后端**：前端懂"语言"、后端懂"目标机"，中间以 [[中间表示]] 相接。
- 与 [[操作系统内核原理]]：编译器是工具链，OS 管运行资源，别混。

## 常见误区

- 编译器和解释器是互斥的两类东西（多数现代引擎两者兼有）。
- 中间表示只是可选的一步、没有实际收益。
- 优化一定让程序更快且行为不变（激进优化对 UB 有前提）。

## 面试速答

> 🎯 编译流水线：词法→语法(AST)→语义(符号/类型)→IR→优化→代码生成；解释器按 树遍历/字节码/[[即时编译]] 执行。多趟架构以 IR 解耦前端(语言)与后端(机器)，达 M+N 复用与统一优化；LLVM 是这套的工程化基座。动手造语言宜从树遍历解释器起步、再演进到字节码+JIT。
