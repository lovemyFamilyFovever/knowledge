# 并发与并行及线程模型

> 📌 **导航**：本文是 **并发与并行及线程模型** 词条，属 [[并发编程模式与实践]] 子词条。线程/协程实体见 [[线程]]、[[协程]]。

## 定义

**一句话定义：** 并发是"多个任务在同一时段交替推进"（一个 CPU 也能靠切换做到），并行是"多个任务真正同时执行"（需多核）；线程模型（1:1 / N:1 / M:N）决定用户线程如何映射到内核线程、由谁调度。

**通俗类比：** 并发像一人轮流照看几口锅（看起来同时在忙、实则切换）；并行像多人各看一口锅。线程模型则是"这几个人是各有专职（1:1）还是共用一个师傅（N:1）还是多对多"的安排。

## 为什么需要它

混淆并发与并行会误判"要不要多核才有用""异步能否加速 CPU 密集"；选错线程模型则决定切换开销、能否利用多核、一个阻塞是否拖垮整批任务。理解模型是设计并发与评估吞吐的前提。

## 核心机制

- **并发 vs 并行**：并发=结构上管理多任务（靠调度/事件循环交替），并行=执行上同时推进（多核真并发）。单核可并发不并行；I/O 密集靠并发即可，CPU 密集才需并行。
- **线程映射模型**：1:1（每用户线程一个内核线程，OS 调度、能利用多核、阻塞一个不影响其他，但切换/创建贵，Linux `pthread`）；N:1（用户态调度、极轻量、但一个阻塞阻塞整个进程、无法多核，旧 Green Threads）；M:N（多用户线程映射到少数内核线程、兼顾但实现复杂、需 runtime 调度，如 Go 的 GMP、Java 虚拟线程方向）。
- 关系：协程（[[协程]]）多落在 N:1 或 M:N，是"用户态轻量执行单元"。

## 具体示例

I/O 密集与 CPU 密集的取舍：

```text
I/O 密集：单线程事件循环/协程 并发即可打满等待期，不必多线程
CPU 密集：需真并行（多核 + 1:1/M:N 线程 或 数据并行），仅靠并发不加速
```

## 何时用与何时不用

- **用**：据任务性质选模型——重 I/O 高并发→协程/事件循环或线程池；重计算→多线程/进程数据并行；追求可扩展到多核→1:1 或 M:N。
- **不用**：别指望单核或多线程"并发"加速纯 CPU；别在大量短任务上滥用重 1:1 线程（切换/内存成本），可用 M:N/协程或池化。

## 优劣与代价

✅ 分清真并发需求与"只是等待"，避免过度并行或线程爆炸。
✅ M:N/协程以低切换成本支撑海量并发。
⚠️ 1:1 简单但线程重；N:1 轻但一阻塞全停、吃不到多核。
⚠️ M:N 调度器复杂，易出现"系统调用阻塞钉住 OS 线程"等坑。

## 与相关概念的区别

- **并发 vs 并行**：前者是"结构/交替推进"、后者"时间上真同时"；并行常是并发在多核上的实现。
- **1:1 vs N:1 vs M:N**：内核调度、能否多核、阻塞影响范围、切换成本各异。
- 线程实体细节见 [[线程]]、协程见 [[协程]]。

## 常见误区

- 多线程一定比单线程快。
- 并发和并行是同一个概念的两种叫法。
- 只要线程数加得够多，CPU 密集任务吞吐就线性上升。

## 面试速答

> 🎯 并发=多任务同一时段交替推进（单核亦可），并行=多核真同时执行；1:1(内核调度、能多核、阻塞隔离、但切换贵)、N:1(极轻、一阻塞全停、吃不到多核)、M:N(Go GMP/虚拟线程式，兼顾但复杂)决定映射与调度。I/O 密集靠并发/协程、CPU 密集才需并行；多线程≠更快。
