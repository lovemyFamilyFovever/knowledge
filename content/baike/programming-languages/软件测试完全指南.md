# 软件测试完全指南


> 📌 **导航**：本文是 **软件测试完全指南** 词条，属于 programming-languages 术语集。相关枢纽：[[Go语言核心]]、[[Python高级编程完全指南]]、[[Rust系统编程入门到精通]]、[[Rust编程基础]]、[[TypeScript深入]]。

## 定义

**一句话定义：** 软件测试是用可自动重复执行的用例，按单元、集成、端到端三层的金字塔比例，持续验证代码行为是否符合预期的工程实践。

**通俗类比：** 像盖楼验收：先逐块砖抽检强度（单元），再验收水电管线是否接通（集成），最后请人从大门一路住到顶层（端到端）——砖检最便宜、次数最多，整楼入住体验最贵、次数最少。

## 为什么需要它

缺陷发现得越晚，修复成本越高：单元层失败直接指向一个函数，端到端层失败可能横跨五个服务。没有分层策略的团队通常滑向"冰淇淋锥"——大量手工点测压着一层脆弱的 UI 自动化，跑得慢、红灯随机、改一次界面要重写半个套件，最后测试被人肉取代，质量退回凭感觉。金字塔给的不是技术选型而是一条经济学结论：把预算压在便宜、快、定位准的底层，顶层只守关键业务流。

## 核心机制

### 测试金字塔

三层自动化用例的规模比例约 70 / 20 / 10（Mike Cohn, 2009）。越往下越快、越多、越便宜、失败定位越精确；越往上越慢、越少、越贵、越接近真实用户但越难归因。倒过来的"冰淇淋锥"是公认反模式：手工测试与 E2E 占大头、几乎没有单元，反馈周期长到没人再看。

### 三层职责

- **底层 单元测试**：测函数与方法，毫秒级，用 mock / stub / fake 隔离数据库、网络与时间，是重构与 TDD 的安全网。
- **中层 集成测试**：把真实模块拼起来测接缝——数据库、消息队列、外部 API，通常用一次性容器提供真实依赖。
- **顶层 端到端测试**：起真实浏览器跑完整用户流，秒级且天然脆弱，所以数量必须压到最低、只覆盖关键路径。

### 测试先行方法论

三层解决"测哪里"，方法论解决"什么时候写"。**TDD** 走红-绿-重构：先写一个会失败的测试，再补最少代码让它通过，最后改结构不改行为。**BDD** 用 Gherkin 的 Given-When-Then 把验收标准写成业务和开发共读的可执行规格。**ATDD** 更靠前，在动手前就把"什么算做完"谈成自动化验收测试。

## 具体示例

单元层：AAA 三段式加参数化，异常路径也各占一条用例。

```python
import pytest

@pytest.mark.parametrize("price,rate,want", [(100, 0.1, 90.0), (100, 0, 100.0)])
def test_discount(price, rate, want):
    assert round(price * (1 - rate), 2) == want

def test_negative_price_rejected():
    with pytest.raises(ValueError):
        calculate_discount(-10, 0.1)
```

集成层：不 mock 数据库，起一次性真实容器，测完即销毁。

```java
@Container
static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:13")
        .withDatabaseName("testdb").withInitScript("init.sql");
```

| 层次 | 速度 | 失败定位 | 占比 |
|---|---|---|---|
| 单元 | 毫秒 | 精确到函数 | ~70% |
| 集成 | 秒 | 精确到接缝 | ~20% |
| 端到端 | 十秒级 | 只知流程断了 | ~10% |

## 何时用与何时不用

- **分层都要有**：只要仓库里有业务逻辑就该有单元层；接了数据库或第三方 API 就要补集成层；有用户界面就要留少量端到端守关键流。
- **从零起步先补单元**：老仓库测试为零时，从纯逻辑函数下手，别一上来铺 E2E——那是把最贵的工具用在最不该用的地方。
- **不必追求全覆盖**：给琐碎 getter 硬凑测试、给每层都定 90% 覆盖率指标，只会产出没有断言价值的负债。
- **不适用**：一次性脚本、纯数据搬运、探索期原型——写测试的成本高于它替你避免的返工。

## 优劣与代价

✅ 底层测试快、定位准，构成回归安全网，让重构与持续集成真正可行。
✅ 按比例分配预算，CI 时长可控，红灯可信。
⚠️ 测试既是资产也是负债：用例越多，接口一变要同步改的越多。
⚠️ 过度 mock 会让测试与现实脱节，全绿套件照样掩盖真实的集成故障。
⚠️ 端到端层天然脆：框架的自动等待治的是时序，治不了测试数据污染与环境漂移。

## 与相关概念的区别

- **测试 vs 调试**：测试发现缺陷存在、可自动化可重复；调试定位并修复根因、是一次性诊断。
- **TDD vs BDD vs ATDD**：TDD 是开发者的实现节奏（单元粒度）；BDD 是跨角色的行为描述（Gherkin 可读规格）；ATDD 把验收判据前置到需求阶段。
- **自动化 vs 手工探索测试**：手工探索能发现自动化想不到的问题但不可重复、不随代码演进，两者互补而非替代。
- **覆盖率 vs 质量**：覆盖率衡量代码被执行到多少，不代表断言充分或行为正确。

## 常见误区

- 测试金字塔应该倒过来写：E2E 最接近真实用户，所以占比要最大。
- 单元测试覆盖率达到 100%，就说明代码没有 bug 了。
- 集成测试把所有依赖都 mock 掉，就等于又快又稳、可以替代真实集成。

## 面试速答

> 🎯 软件测试按金字塔分层：单元约 70%（毫秒级、隔离依赖、定位准）、集成约 20%（Testcontainers 起真实依赖验接缝）、E2E 约 10%（Playwright/Cypress 守关键用户流）。TDD 走红-绿-重构，BDD 用 Gherkin 写可执行规格，ATDD 把验收判据前置；反模式是冰淇淋锥。
