# 抽象语法树

> 📌 **导航**：本文是 **抽象语法树** 词条，属于 programming-languages 术语集。相关枢纽：[[Go语言核心]]、[[Python高级编程完全指南]]、[[Rust系统编程入门到精通]]、[[Rust编程基础]]、[[TypeScript深入]]。

## 定义

**一句话定义：** 抽象语法树（Abstract Syntax Tree, AST）是源代码语法结构的一种树状中间表示，树的每个节点代表代码中的一种构造（如表达式、语句、声明），它省略了对语义无关的细节（如括号、分号），便于后续分析与转换。

**通俗类比：** 像把一句话拆成主谓宾的"句子结构树"——去掉标点等表面符号，只保留"谁—做什么—对谁"的结构骨架，方便机器理解句子的真正构造。

## 为什么需要它

源文本是给"人从前往后读"的线性序列，而程序逻辑是"有层次、可嵌套"的结构。AST 把这层结构显式化：括号和优先级被"消化"进树的形状，类型检查、代码生成、优化、重构都能用统一的"遍历节点"模型来处理，而不必反复和字符串、标点较劲。它是编译前端与代码工具链的共同底座。

## 核心机制

- **编译前端流程**：源代码 → 词法分析（token 流）→ 语法分析（按文法构建 AST）→ 语义分析（类型检查、符号解析，常在 AST 上"装饰"信息）。
- **构建方式**：语法分析器（递归下降、LL、LR 等）依据文法规则把 token 组织成树。
- **使用方式**：以 visitor 模式遍历 AST，完成类型检查、代码生成、优化、格式化、静态分析与转译。

## 具体示例

表达式 `3 + 4 * 5` 的 AST 只有两个运算节点；括号与优先级不占节点，而是体现在"乘法是加法的右子树"这一形状里：

```
BinaryExpr(+)
├─ Number(3)
└─ BinaryExpr(*)
   ├─ Number(4)
   └─ Number(5)
```

## 何时用与何时不用

- **用**：编译器与解释器前端、代码格式化（Prettier）、静态检查（ESLint）、转译（Babel / TypeScript→JS）、IDE 重构与代码生成、模板引擎。
- **不用（换表示）**：需要逐字符还原原文（如精确打印、保留注释格式）时用 CST/带位置的源映射更合适；只判断"单词是否合法"时根本不需要建到树。

## 优劣与代价

✅ 结构清晰、与源文本解耦，便于分析与变换，是编译与工具链的核心中间表示。
✅ 遍历 + 装饰即可承载类型、作用域、符号等语义信息。
⚠️ 构建依赖正确的文法与语法分析器。
⚠️ 大文件的 AST 内存开销大；不同语言 / 工具的 AST 结构互不统一。

## 与相关概念的区别

- **AST vs CST**：AST 省略括号、分号等非语义细节；具体语法树 CST 保留全部语法与表面记号。
- **AST vs token 流**：token 是叶子级词法单元（线性），AST 是其上的结构化树。
- **AST vs IR / 字节码**：AST 贴近源语言的语法，IR / 字节码贴近机器执行，是更" lowered "的中间表示。

## 常见误区

- AST 保留了括号、分号等全部源文本细节。
- AST 就是 IR / 字节码，可以直接拿去执行。
- AST 就是词法分析产出的 token 流。
