# 消息传递并发：CSP 与 Actor

> 📌 **导航**：本文是 **消息传递并发：CSP 与 Actor** 词条，属 [[并发编程模式与实践]] 子词条。协程见 [[协程]]，语言实现见 [[Go并发与内存模型]]、[[Rust 并发与异步]]。

## 定义

**一句话定义：** 消息传递并发以"不共享内存、靠传消息协调"避免锁——CSP 强调"进程经 channel 通信、由通信决定顺序"，Actor 模型则让每个对象拥有私有状态与邮箱、只靠收发消息交互。

**通俗类比：** 与其多人围着一张桌子抢着改（共享内存+锁），不如各坐各屋、要合作就"递条子"（channel/邮件）；谁也不碰谁的桌面，自然少打架。

## 为什么需要它

共享可变 + 锁带来竞态、死锁、可扩展瓶颈。消息传递把状态归属单一处理者、用通信代替抢锁：CSP 让并发由 channel 收发次序自然编排，Actor 让状态私有、天然适合分布式与容错（监督树）。把协调成本从"锁"移到"消息"。

## 核心机制

- **CSP**：并发实体通过 typed channel 通信，"不要通过共享内存来通信，而要通过通信来共享内存"（Go 口号）。channel 有缓冲/无缓冲语义、`select` 多路、由通信同步。
- **Actor**：进程有私有状态 + 邮箱，收消息才处理、可 spawn/发信；位置透明（本地/远程同接口）；失败由"监督者"重启（let it crash，Erlang/Akka）。
- **协程为承载**（[[协程]]）：Goroutine/Kotlin 协程/asyncio 任务常作为 CSP/Actor 的轻量执行体。
- **背压与死锁仍在**：无缓冲 channel 无接收者会阻塞、环形等待可死锁——不是银弹。

## 具体示例

Go 用 channel + select 做扇入与超时（CSP 式编排）：

```go
select {
case r := <-resultCh:  use(r)
case <-time.After(t):  timeout()
}
```

## 何时用与何时不用

- **用**：流水线/扇出扇入、事件流、监督式有状态服务、分布式（Actor）优先消息传递；与锁共享按场景混用。
- **不用**：简单读多写少的共享结构直接读写锁/原子更短；纯 CPU 数据并行用并行循环而非堆 channel。

## 优劣与代价

✅ 消除大量锁与共享竞态、组合性好、Actor 天然分布式与容错。
✅ 以协程承载时并发成本低、代码接近顺序风格。
⚠️ 通道容量/时序设计不当易死锁、背压或 goroutine 泄漏。
⚠️ 大量小消息有拷贝/调度开销；调试跨消息因果链难。

## 与相关概念的区别

- **CSP vs Actor**：CSP 通道是一等公民、通信显式定向；Actor 以"邮箱+发送者位置透明"为中心、发送即忘。二者常混用。
- **消息传递 vs 共享内存加锁**（[[同步原语与无锁并发]]）：前者传所有权/消息、后者抢锁改同一份。
- 与 Go/Rust 具体实现见 [[Go并发与内存模型]]、[[Rust 并发与异步]]。

## 常见误区

- 用了 channel/Actor 就绝不会死锁。
- Actor 模型必须靠共享内存对象才能通信。
- 无缓冲 channel 发送后会立即返回。

## 面试速答

> 🎯 消息传递并发避免共享+锁：CSP(Go：进程经 typed channel 通信、select 多路、"通过通信共享内存")与 Actor(私有状态+邮箱、位置透明、监督树容错，Erlang/Akka)，多以协程承载。收益少锁少竞态、可分布式；代价是通道时序/容量设计与背压调试。
