# 调试与性能分析

> 📌 **导航**：本文是 **调试与性能分析** 词条，属于 tools 术语集。相关枢纽：[[包管理器与构建工具]]、[[容器化与Docker]]、[[版本控制与Git深入]]、[[调试与性能分析]]。

## 定义

**一句话定义：** 调试是定位并修复程序中错误的过程，性能分析（profiling）则度量程序的时间、内存与资源开销、找出瓶颈，二者共同保障软件的正确性与性能。

**通俗类比：** 调试像医生看病——观察症状（bug 表现）、做检查（断点 / 日志）、下诊断（找根因）、开药（改代码）；性能分析像做体检，用数据告诉你哪块"器官"最耗资源。

## 为什么需要它

靠盯着代码瞎猜，既慢又容易改错地方；把生产代码塞满 print 调试又吵又难维护。调试工具让你"停在案发现场"看变量与调用栈；而性能层面，盲目优化可能改了个不重要的地方，profiling 用真实数据把火力对准真正的热点，避免"过早优化是万恶之源"。

## 做法

- **调试手段**：打印调试（临时快速）、断点调试（IDE / pdb / `debugger;`，推荐）、条件断点（仅特定条件暂停）、分级别日志（debug/info/warning/error/critical 各司其职，生产可按级别过滤）。
- **性能分析**：CPU profiler 找热点函数、内存 profiler 看分配与泄漏，配合火焰图 / 调用树。
- **排查思路**：从现象定位资源类型——内存涨、CPU 满、CPU 低但慢、卡死，各对应不同工具与假设。

## 具体示例

断点比满屏 print 高效得多，命中即可看上下文变量与调用栈：

```python
# Python 内置断点（等价 import pdb; pdb.set_trace()）
breakpoint()

# JavaScript：浏览器 DevTools 会在此暂停
debugger;
```

| 性能问题 | 症状 | 排查方向 |
|----------|------|----------|
| 内存泄漏 | 内存持续增长 | 内存分析工具看引用链 |
| CPU 密集 | CPU 占用 100% | profiler 找热点函数 |
| I/O 阻塞 | 响应慢但 CPU 低 | 看等待时间 / 慢查询 |
| 死锁 | 程序卡住 | 线程 dump 分析 |
| N+1 查询 | 数据库查询过多 | SQL 日志 / ORM 分析 |

| 工具 | 语言 | 用途 |
|------|------|------|
| Chrome DevTools | JS | 前端性能、网络、内存 |
| cProfile / memory_profiler | Python | CPU / 内存分析 |
| pprof | Go | CPU / 内存 / 阻塞分析 |
| perf / strace | Linux | 系统级性能 / 系统调用跟踪 |

## 何时用与何时不用

- **用**：任何非显而易见的缺陷、性能未达标、内存/延迟异常；上线前用 profiling 建性能基线。
- **不用**：别对没测出瓶颈的代码做微优化；别把 `print`/`debugger`/断点残留提交进生产。

## 优劣与代价

✅ 断点 / 单步 / 条件断点高效定位根因，优于盲猜。
✅ profiling 让优化有的放矢，避免过早优化。
⚠️ 重型 profiler 本身有开销，可能改变时序、掩盖竞态。
⚠️ 生产环境调试受限，需依赖日志与可观测性工具。

## 与相关概念的区别

- **调试 vs 性能分析**：调试解决"对不对"（找 bug），性能分析解决"快不快、省不省"（找瓶颈）。
- **打印调试 vs 断点调试**：print 轻量但污染代码、看不到完整调用栈；断点可暂停观察状态、条件触发更精准。
- **日志级别 vs 调试断点**：日志是"事后回看"的持久痕迹，断点是"当场暂停"的交互式检查。

## 常见误区

- 性能优化凭直觉直接改就行，不必先做 profiling 测量。
- 线上排查最方便的做法就是到处加 print、把日志全开到最详细。
- 程序卡住了就一定是死锁。

## 面试速答

> 🎯 调试 = 用断点 / 单步 / 日志定位并修复缺陷；性能分析 = 用 cProfile / pprof / DevTools 度量时间与内存、找热点函数。原则：先复现、用数据定位真瓶颈再优化，而非凭直觉。
