## 1. RAG（检索增强生成）

**一句话定义：** 先从知识库中检索相关信息，再把检索结果喂给大模型，让它基于真实数据生成回答。

**通俗类比：** 就像开卷考试——先翻书找到相关章节（检索），再用自己的话组织答案（生成），比闭卷考试（纯LLM）准确得多。

**具体示例：**
```
用户问题： "我们公司的年假政策是什么？"

纯 LLM 回答： "一般公司年假5-15天..."（瞎编，不知道具体公司政策）

RAG 流程：
  1. 检索：从公司知识库找到《员工手册-假期管理》
  2. 提取：第12条 - "入职满1年享5天年假，满5年享10天..."
  3. 生成：基于真实文档回答 "根据公司政策，入职满1年享有5天年假..."
```

**为什么需要它：** 解决 LLM 知识过时、幻觉、缺少私有数据三大问题。

**RAG 完整流程图：**
```
用户提问
    ↓
┌───────────────────┐
│   查询处理层       │
│  (Query Rewrite)  │
└─────────┬─────────┘
          ↓
┌───────────────────┐     ┌─────────────────┐
│   检索层           │ ←→  │   向量数据库     │
│  (Retrieval)      │     │  (Milvus等)     │
└─────────┬─────────┘     └─────────────────┘
          ↓
┌───────────────────┐
│   重排序层         │
│  (Rerank)         │
└─────────┬─────────┘
          ↓
┌───────────────────┐     ┌─────────────────┐
│   生成层           │ ←→  │   LLM           │
│  (Generation)     │     │  (GPT-4等)      │
└─────────┬─────────┘     └─────────────────┘
          ↓
       最终答案
```

## 2. 检索（Retrieval）

**一句话定义：** 根据用户的问题，从大量文档中快速找到最相关的片段。

**通俗类比：** 就像图书馆的检索系统——你输入关键词，它告诉你哪些书的哪些章节最相关。

**具体示例：**
```
知识库： 10万篇公司内部文档

用户查询： "如何申请远程办公？"

检索过程：
  Step 1: 将查询转为向量 [0.12, -0.34, ...]
  Step 2: 在向量数据库中搜索相似向量
  Step 3: 返回 Top-5 最相关的文档片段

检索结果：
  1. 《远程办公管理办法》第3条 - 相关度 0.95
  2. 《员工手册》第8章 - 相关度 0.87
  3. 《IT设备使用指南》- 相关度 0.72
  ...
```

**为什么需要它：** LLM 的知识有截止日期且无法访问私有数据，检索让它能实时获取最新、最相关的信息。

---

## 3. 重排序（Rerank）

**一句话定义：** 对检索结果进行二次排序，把真正最相关的内容排到前面。

**通俗类比：** 就像图书管理员初次检索找到100本书，然后仔细翻阅后告诉你"其实这5本才是你真正需要的"。

**具体示例：**
```
初始检索结果（语义搜索）：
  1. 关于年假的文章A（相关度0.85）
  2. 关于调休的文章B（相关度0.82）
  3. 年假申请流程C（相关度0.80）  ← 其实这个最相关
  4. 请假制度文章D（相关度0.78）

Rerank 后（交叉编码器精排）：
  1. 年假申请流程C（相关度0.96）  ← 提到前面了
  2. 关于年假的文章A（相关度0.91）
  3. 请假制度文章D（相关度0.85）
  4. 关于调休的文章B（相关度0.60）
```

**为什么需要它：** 初始检索（向量搜索）速度快但精度有限，Rerank 用更精细的模型重新打分，显著提升结果质量。

**与相关术语的对比：**
- Rerank vs 初始检索：初始检索是"广撒网"，Rerank 是"精选"
- Rerank vs Top-K：Top-K 只取前K个，Rerank 是对所有结果重新排序

## 4. 向量数据库（Pinecone/Milvus/ChromaDB/Weaviate）

**一句话定义：** 专门存储和检索向量（数字数组）的数据库，能快速找到"最相似"的内容。

**通俗类比：** 就像一个超级图书馆的索引系统，不是按书名/作者检索，而是按"意思"检索——你说"关于健康的书"，它给你找所有讲健康的书。

**具体示例：**
```python
# 以 ChromaDB 为例
import chromadb

client = chromadb.Client()
collection = client.create_collection("my_docs")

# 存入文档及其向量
collection.add(
    documents=["年假申请流程", "远程办公政策", "报销制度"],
    ids=["doc1", "doc2", "doc3"]
)

# 语义搜索
results = collection.query(
    query_texts=["怎么休假"],
    n_results=2
)
# 返回：["年假申请流程", "报销制度"]（按相关度排序）
```

**主流向量数据库对比：**

| 数据库 | 类型 | 特点 | 适用场景 |
|--------|------|------|----------|
| Pinecone | 云服务 | 免运维，开箱即用 | 快速上线，不想运维 |
| Milvus | 开源 | 功能强大，可扩展 | 大规模生产环境 |
| ChromaDB | 开源 | 轻量级，Python友好 | 原型开发，小项目 |
| Weaviate | 开源 | GraphQL API，多模态 | 需要复杂查询 |

**为什么需要它：** 传统数据库只能精确匹配，向量数据库能做"语义相似度"搜索，是 RAG 的核心基础设施。

## 5. 语义搜索

**一句话定义：** 基于文本的"含义"而不是"字面匹配"进行搜索。

**通俗类比：** 你搜"怎么让心情变好"，语义搜索能找到"缓解焦虑的方法"，即使没有一个字重复。

**具体示例：**
```
用户搜索： "电脑开不了机"

关键词搜索（传统）：
  ✓ "电脑开不了机怎么办"
  ✗ "笔记本无法启动"（没命中关键词）
  ✗ "按下电源键没反应"（没命中关键词）

语义搜索：
  ✓ "电脑开不了机怎么办"（语义完全匹配）
  ✓ "笔记本无法启动"（含义相同）
  ✓ "按下电源键没反应"（描述同一问题）
  ✗ "电脑配置推荐"（虽然有"电脑"但含义不同）
```

**为什么需要它：** 传统关键词搜索依赖字面匹配，语义搜索理解含义，能找到字面不同但意思相同的内容。

**与相关术语的对比：**
- 语义搜索 vs 关键词搜索：语义搜索理解含义，关键词搜索匹配字面
- 语义搜索 vs 混合搜索：混合搜索结合两者优点，效果最好

## 6. 关键词搜索（BM25）

**一句话定义：** 基于词频和文档频率的经典文本检索算法，计算查询词与文档的匹配程度。

**通俗类比：** 就像在 Word 里用 Ctrl+F 搜索，但更智能——它会考虑词出现的频率和稀有程度。

**具体示例：**
```
文档集合：
  D1: "Python 是一种编程语言"
  D2: "Python 用于机器学习"
  D3: "Java 也是一种编程语言"

查询： "Python 编程"

BM25 计算：
  D1: "Python"出现1次 + "编程"出现1次 → 得分 2.3
  D2: "Python"出现1次 + "编程"出现0次 → 得分 1.1
  D3: "Python"出现0次 + "编程"出现1次 → 得分 0.8

结果：D1 > D2 > D3
```

**为什么需要它：** BM25 在精确匹配场景（如专有名词、编号搜索）中效果很好，与语义搜索互补。

**与相关术语的对比：**
- BM25 vs 向量搜索：BM25 精确匹配快，向量搜索语义理解强
- BM25 vs TF-IDF：BM25 是 TF-IDF 的改进版，效果更好

---

## 7. 混合检索

**一句话定义：** 同时使用关键词搜索和语义搜索，综合两者的优点得到最佳结果。

**通俗类比：** 就像找餐厅——既看点评网站的评分（语义匹配），又看菜单上有没有你想吃的菜（关键词匹配），综合两个渠道做决定。

**具体示例：**
```
用户查询： "Python机器学习入门教程"

混合检索策略：
  关键词搜索（BM25）：
    ✓ "Python机器学习入门"（完全匹配）
    ✓ "Python ML教程"（部分匹配）

  语义搜索（向量）：
    ✓ "Python人工智能基础课程"（语义相似）
    ✓ "机器学习零基础学Python"（语义相似）

  融合排序（RRF算法）：
    综合两个结果集，得分高的排前面

最终结果：
  1. "Python机器学习入门"（两者都高分）
  2. "Python人工智能基础课程"（语义高分）
  3. "机器学习零基础学Python"（语义高分）
  4. "Python ML教程"（关键词高分）
```

**为什么需要它：** 单一搜索方式各有短板，混合检索取长补短，是生产环境的最佳实践。

## 8. 文档分块（Chunking）

**一句话定义：** 把长文档切成适当大小的片段，便于检索和处理。

**通俗类比：** 就像把一本厚书拆成一张张卡片，每张卡片包含一个完整的知识点，方便快速查找。

**具体示例：**
```
原始文档： 一篇5000字的《公司年假政策》

分块策略对比：

固定长度分块（512字）：
  Chunk 1: 第1-512字（可能切断句子）
  Chunk 2: 第513-1024字
  ...

语义分块：
  Chunk 1: "年假天数规定"段落（300字）
  Chunk 2: "年假申请流程"段落（400字）
  Chunk 3: "年假特殊情况"段落（350字）

递归分块（推荐）：
  先按章节 → 再按段落 → 最后按句子
  确保每个 chunk 语义完整
```

**分块大小建议：**
```
小模型（4K上下文）：  256-512 Token/chunk
大模型（128K上下文）：512-1024 Token/chunk
重叠（Overlap）：     50-100 Token（保证上下文连贯）
```

**为什么需要它：** 太大的 chunk 检索不精确，太小的 chunk 缺少上下文，合适的分块策略直接影响 RAG 效果。

## 9. Embedding 模型选择

**一句话定义：** 把文本转换成向量的模型，不同的 Embedding 模型对检索效果影响巨大。

**通俗类比：** 就像翻译官——好的翻译官能把中文精准翻译成英文（向量），差的翻译会丢失信息。

**具体示例：**
```
主流 Embedding 模型对比：

OpenAI text-embedding-3-small
  维度：1536
  特点：效果好，API调用，有成本
  适合：快速上线，不想自建

BGE-large-zh-v1.5（智源）
  维度：1024
  特点：中文效果极佳，开源免费
  适合：中文场景，可自部署

GTE-large（阿里）
  维度：1024
  特点：多语言支持，性价比高
  适合：多语言场景

M3E（Moka AI）
  维度：768
  特点：轻量级，中文优化
  适合：资源有限的场景
```

**为什么需要它：** Embedding 模型的质量直接决定检索的准确性，是 RAG 系统中最关键的选型之一。

## 10. 检索评估指标（Recall@K/MRR/NDCG）

**一句话定义：** 一套量化评估检索系统好坏的指标，告诉你"找到的内容有多准"。

**通俗类比：** 就像考试评分——Recall@K 是"前K个答案中包含了几个正确答案"，MRR 是"第一个正确答案排第几"。

**具体示例：**
```
场景： 从100篇文档中检索与"年假政策"相关的5篇

实际相关文档：D1, D3, D7, D15, D22

检索结果：D1, D5, D3, D8, D7

评估：
  Recall@5 = 3/5 = 0.6
  （前5个结果中找到了3个相关文档）

  MRR = 1/1 + 1/3 + 1/5 = 1.53
  （第一个正确答案排第1，第二个排第3，第三个排第5）

  NDCG@5 = 0.85
  （考虑了排序质量，相关文档排越前得分越高）
```

**指标含义对照：**
```
Recall@K：  前K个结果覆盖了多少相关文档？（关注"找到多少"）
MRR：       第一个正确结果排在第几位？（关注"排第几"）
NDCG：      结果的排序质量如何？（关注"排得好不好"）
Precision： 前K个结果中有多少是真正相关的？（关注"有多少是对的"）
```

**为什么需要它：** 没有量化指标就无法评估和优化检索系统，是 RAG 迭代改进的基础。

## 11. 查询改写（Query Rewriting）

**一句话定义：** 把用户的原始查询优化成更适合检索的形式。

**通俗类比：** 就像你问图书管理员一个模糊的问题，管理员先帮你理清思路再去找书。

**具体示例：**
```
原始查询： "那个东西怎么弄"
改写后：   "如何配置VPN连接"

原始查询： "Python报错"
改写后：   "Python TypeError错误解决方法"

改写策略：
  1. 补充上下文：添加领域关键词
  2. 拆分子查询：把复杂问题拆成多个简单查询
  3. 假设性文档生成（HyDE）：让LLM先生成一个假想答案，用答案去检索
```

**为什么需要它：** 用户的查询往往口语化、模糊，直接检索效果差，改写后能显著提升检索质量。

## 12. 多轮检索

**一句话定义：** 在对话场景中，根据上下文历史进行多轮迭代检索，逐步精确答案。

**通俗类比：** 就像和专家多轮对话——第一轮宽泛了解，第二轮深入细节，第三轮精准定位。

**具体示例：**
```
对话历史：
  用户第1轮： "你们有什么课程？"
  助手第1轮： "我们有Python、Java、AI等课程。"

  用户第2轮： "AI课程多少钱？"  ← 需要结合上轮上下文
  助手第2轮：检索"AI课程 价格" → "AI课程3999元。"

  用户第3轮： "有没有折扣？"  ← 需要结合前两轮
  助手第3轮：检索"AI课程 折扣 优惠" → "目前有早鸟价8折。"

挑战：第3轮的"折扣"是指AI课程的折扣，不是泛指
```

**为什么需要它：** 多轮对话中，用户的后续问题往往省略了前面提到的主体，需要结合上下文才能正确检索。

## RAG 系统架构总览

```
┌─────────────────────────────────────────────────────┐
│                    用户界面层                         │
│              (Web/App/API)                          │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│                  对话管理层                           │
│         (多轮对话 / 上下文维护 / 查询改写)           │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│                    检索层                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐          │
│  │ 关键词搜索│  │ 语义搜索  │  │  混合检索 │          │
│  │  (BM25)  │  │(向量搜索) │  │  (融合)   │          │
│  └──────────┘  └──────────┘  └──────────┘          │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│                   重排序层                            │
│              (Cross-Encoder Rerank)                 │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│                    生成层                             │
│    (Prompt组装 + LLM生成 + 引用溯源)                │
└──────────────────────┬──────────────────────────────┘
                       ↓
                  最终回答
```
