## 1. Prompt Engineering（提示词工程）

**一句话定义：** 通过设计和优化输入给 AI 的提示词，让模型输出更好结果的技术。

**通俗类比：** 就像你和一个聪明但需要明确指令的助手沟通——你说得越清楚、越有结构，它做得越好。

**具体示例：**
```
差的 Prompt：  "写个东西"

好的 Prompt：
  "请写一篇300字的技术博客，主题是'为什么Python适合初学者'，
   要求：1.语言通俗 2.包含3个理由 3.每个理由配代码示例 4.结尾给学习建议"
```

**为什么需要它：** 同一个模型，不同的 Prompt 可以得到天壤之别的结果。

**Prompt 设计原则（RCIEF）：**
- Role（角色）：给模型一个角色身份
- Context（上下文）：提供背景信息
- Instruction（指令）：明确要做什么
- Example（示例）：给出参考样例
- Format（格式）：指定输出格式

## 2. Zero-shot / Few-shot / One-shot

**一句话定义：** 指在 Prompt 中给模型示例的数量——零个、几个、或一个。

**通俗类比：** Zero-shot = 裸考，One-shot = 做一道例题再考，Few-shot = 做几道例题再考。

**具体示例：**
```
Zero-shot：
  "判断情感：'这家店太好吃了' → "

One-shot：
  "判断情感：'服务态度差' → 负面；'这家店太好吃了' → "

Few-shot：
  "判断情感：'服务态度差' → 负面；'环境优美' → 正面；
   '价格合理' → 正面；'这家店太好吃了' → "
```

**为什么需要它：** Few-shot 能显著提升模型在特定任务上的表现。

**与相关术语的对比：**
- Few-shot vs 微调：Few-shot 是临时给示例，微调是永久改变模型行为

## 3. Chain-of-Thought（CoT，思维链）

**一句话定义：** 让模型一步步推理而不是直接给答案，显著提升复杂问题的解决能力。

**通俗类比：** 就像做数学题时写出解题步骤——不是直接写答案，而是一步步推导。

**具体示例：**
```
问题： 小明有5个苹果，给了小红2个，又买了3个，最后有几个？

CoT 推理：
  "让我一步步思考：
   1. 小明开始有 5 个苹果
   2. 给了小红 2 个：5 - 2 = 3 个
   3. 又买了 3 个：3 + 3 = 6 个
   答案：6 个"
```

**为什么需要它：** CoT 让模型的推理过程透明化，大幅减少计算类任务的错误率。

---

## 4. Tree-of-Thought（ToT，思维树）

**一句话定义：** 让模型像下棋一样探索多条推理路径，选择最优方案。

**通俗类比：** 就像在迷宫中探索——不是只走一条路，而是同时探索多条路，哪条走得通走哪条。

**具体示例：**
```
问题： 用4个4通过加减乘除得到24

思维树探索：
                    [开始：四个4]
                   /     |      \
            [4+4=8]   [4×4=16]  [4/4=1]
           /    \       |        \
     [8+4=12] [8×4=32] [16+4=20] [1×4=4]
       |                  |
    [12+4=16]          [20+4=24✓] ← 找到答案！
```

**与相关术语的对比：** CoT 是一条直线推理，ToT 是多条路径探索。

---

## 5. ReAct（Reasoning + Acting）

**一句话定义：** 让模型交替进行"推理"和"行动"——先思考该做什么，再执行动作，然后观察结果。

**通俗类比：** 就像你用导航开车——先想"我要去哪"（推理），再"开车出发"（行动），看到"前方堵车"（观察），再"换个路线"（推理）。

**具体示例：**
```
用户： "帮我查北京今天天气，告诉我适不适合跑步"

ReAct 流程：
  Thought 1: 我需要先查询北京的天气信息
  Action 1: search("北京今天天气")
  Observation 1: 北京今天晴，25°C，微风

  Thought 2: 天气不错，温度适中，适合户外跑步
  Action 2: reply("今天北京天气晴朗，25°C，非常适合跑步！")
```

**为什么需要它：** ReAct 让 AI 能使用外部工具，而不只是"纸上谈兵"。

---

## 6. Agent（智能体）

**一句话定义：** 能自主感知环境、做出决策、使用工具、完成任务的 AI 系统。

**通俗类比：** 就像一个能独立工作的员工——不只是回答问题，还能自己找资料、写代码、完成整个项目。

**具体示例：**
```
用户： "帮我分析竞品，写一份分析报告"

Agent 执行：
  1. 分解任务：搜索竞品 → 收集数据 → 分析优劣势 → 撰写报告
  2. 使用工具：调用搜索引擎 → 爬取产品页 → 代码分析数据 → 生成报告
  3. 交付成果：完整的竞品分析报告（含图表）
```

**Agent 架构图：**
```
用户输入 → 规划模块(任务分解) → 执行模块(调用工具) → 记忆模块(短期/长期) → 最终输出
```

---

## 7. Tool Use（工具使用）

**一句话定义：** 让 AI 调用外部工具（API、搜索引擎、代码执行器等）来完成自身无法完成的任务。

**通俗类比：** 就像人使用工具——AI 自己算不了大数，但可以调用计算器；自己上不了网，但可以调用搜索引擎。

**具体示例：**
```
用户： "今天美元兑人民币汇率是多少？"

AI 自身： 知识截止到2024年，不知道今天的汇率
使用工具：调用 exchange_rate_api.get("USD", "CNY") → 返回 7.2456
最终回答： "今天美元兑人民币汇率是 7.2456"
```

**为什么需要它：** 工具使用让 AI 的能力从"知道"扩展到"能做"。

---

## 8. Function Calling（函数调用）

**一句话定义：** AI 模型根据用户需求，自动生成调用外部函数的参数，并执行函数获取结果。

**通俗类比：** 就像你告诉助理"帮我订明天去上海的机票"，助理知道要调用订票系统的哪些参数。

**具体示例：**
```python
# 定义可用函数
functions = [{
    "name": "get_weather",
    "description": "获取指定城市的天气",
    "parameters": {
        "type": "object",
        "properties": {
            "city": {"type": "string", "description": "城市名"},
            "date": {"type": "string", "description": "日期"}
        }
    }
}]

# 模型自动决定调用参数
# 返回: {"name": "get_weather", "arguments": '{"city": "北京", "date": "2024-01-15"}'}
```

**与相关术语的对比：** Function Calling 是 Tool Use 的一种具体实现方式。

---

## 9. Planning（规划）

**一句话定义：** Agent 把复杂任务拆解成可执行的子任务，并确定执行顺序的能力。

**通俗类比：** 就像项目经理做项目计划——把大项目拆成小任务，安排先后顺序。

**具体示例：**
```
需求： "帮我写一篇关于AI的技术博客"

规划结果：
  Step 1: [搜索] 调研 AI 最新动态
  Step 2: [大纲] 制定文章结构
  Step 3-6: [写作] 各部分可并行撰写
  Step 7: [整合] 检查逻辑连贯性
  Step 8: [优化] 润色文字
```

**为什么需要它：** 没有规划能力的 Agent 只能处理简单任务，规划让它能处理复杂的多步骤任务。

---

## 10. Memory（记忆）

**一句话定义：** Agent 保存和检索历史信息的能力，包括短期记忆（当前对话）和长期记忆（跨会话经验）。

**通俗类比：** 短期记忆 = 工作台上的便签，长期记忆 = 文件柜里的档案。

**具体示例：**
```
短期记忆：当前对话中的上下文（会话结束清空）
长期记忆：用户档案数据库（持久化存储，跨会话可用）
  张三：职业=程序员，常用语言=Python，偏好=简洁回答
  下次对话时检索记忆，提供个性化服务
```

**为什么需要它：** 没有记忆的 Agent 每次对话都从零开始，有了记忆才能提供个性化服务。

---

## 11. Multi-Agent 系统（多智能体系统）

**一句话定义：** 多个专业化的 Agent 协同工作，各司其职完成复杂任务。

**通俗类比：** 就像一个公司团队——产品经理、设计师、开发、测试各负责不同部分。

**具体示例：**
```
任务：开发一个电商网站

Agent 团队：
  产品经理 Agent → 分析需求，制定功能列表
  设计师 Agent → 设计界面原型
  开发工程师 Agent → 编写代码
  测试工程师 Agent → 编写测试用例
  协调者 Agent → 分配任务，跟进进度
```

**为什么需要它：** 单个 Agent 能力有限，Multi-Agent 通过分工协作处理更复杂的任务。

## 12. Prompt 模板

**一句话定义：** 预先设计好的 Prompt 结构，可以重复使用并填入不同内容。

**通俗类比：** 就像公文模板——格式固定，每次只需填入具体内容。

**常见模板示例：**
```python
# 角色扮演模板
SYSTEM_PROMPT = """
你是一位{role}，擅长{skill}。
请用{tone}的语调回答问题。
回答时请遵循：1.{principle_1} 2.{principle_2} 3.{principle_3}
"""

# 分类任务模板
CLASSIFY_PROMPT = """
请将以下文本分类到给定的类别中。
类别：{categories}
文本：{text}
请输出分类结果和置信度。
"""
```

## 13. 系统提示词（System Prompt）

**一句话定义：** 预先设定的隐藏指令，定义 AI 的角色、行为规则和限制。

**通俗类比：** 就像员工入职时收到的"工作手册"——规定了什么能做、什么不能做。

**具体示例：**
```
System Prompt：
  你是一个专业的医疗健康助手。
  你的角色：回答用户关于健康、疾病、用药的问题。
  规则：
  1. 你不是医生，不能替代专业医疗建议
  2. 不确定时说"请咨询医生"
  3. 不推荐具体药物剂量
  4. 危急情况建议立即就医
```

**为什么需要它：** System Prompt 是控制模型行为的第一道防线，确保输出安全、合规。

---

## 14. 输出格式控制（JSON Mode）

**一句话定义：** 强制模型输出特定格式（如 JSON），便于程序解析和后续处理。

**通俗类比：** 就像填表格——不是让你自由发挥写作文，而是按照固定格式填写信息。

**具体示例：**
```
普通输出（格式不可控）：
  "张三，28岁，工程师，北京"

JSON Mode 输出（格式固定）：
  {
    "name": "张三",
    "age": 28,
    "job": "工程师",
    "city": "北京"
  }

OpenAI JSON Mode 调用：
  response = openai.ChatCompletion.create(
      model="gpt-4",
      messages=[...],
      response_format={"type": "json_object"}
  )
```

**为什么需要它：** 程序需要结构化数据才能进一步处理，JSON Mode 让 LLM 输出可被程序直接解析。

## Prompt 工程最佳实践

```
1. 明确角色： "你是一个Python专家"
2. 提供上下文： "我正在开发一个Web应用"
3. 给出示例： Few-shot 比 Zero-shot 效果好
4. 要求推理： 使用 CoT 提升准确率
5. 指定格式： JSON/Markdown/列表 等
6. 设置限制： "不超过100字" "只回答技术问题"
7. 迭代优化： 根据输出不断调整 Prompt
```
