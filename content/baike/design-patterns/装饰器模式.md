# 装饰器模式

> 📌 **导航**：本文是 **装饰器模式** 词条，属 [[结构型模式（Structural Patterns）]] 子词条。

## 定义

**一句话定义：** 装饰器模式在不改变原对象接口的前提下，动态地给对象叠加额外职责；就扩展功能而言，它比继承更灵活。

**通俗类比：** 穿衣服——T 恤外加外套、外套外加羽绒服，每加一层多一项功能（保暖、防水、防风），而"你"这个被装饰对象的身份始终不变。

## 为什么需要它

要给一个类加新功能，用继承会得到大量"子类 = 原类 + 某组合功能"，M 种组合就要 M 个子类，且编译期就定死。装饰器让"被装饰对象"和"装饰器"实现同一接口、层层包裹，在运行期任意组合叠加，避免类爆炸，符合开闭。

## 核心机制

- **Component（抽象构件）**：装饰器与被装饰对象都实现它——这样才能相互替换、层层嵌套。
- **ConcreteComponent**：被装饰的原始对象。
- **Decorator（抽象装饰器）**：持有 Component 引用并实现 Component 接口。
- **ConcreteDecorator**：在委托 Component 的基础上追加职责。
调用时 `new MilkDecorator(new SimpleCoffee())` 逐层包裹，请求沿嵌套链传递。

## 具体示例

咖啡加料：每个装饰器实现同一 `Coffee` 接口、持有内层 `coffee` 并在其结果上叠加：

```python
class SimpleCoffee(Coffee):
    def cost(self): return 10
class MilkDecorator(Coffee):                       # 装饰器
    def __init__(self, coffee): self._c = coffee
    def cost(self): return self._c.cost() + 3      # 委托 + 追加
coffee = MilkDecorator(SimpleCoffee())             # 层层包裹
```

## 何时用与何时不用

- **用**：需要在运行期可叠加、可撤销地扩展对象功能；经典如 Java I/O（`BufferedInputStream` 装饰 `FileInputStream`）、Web 中间件的逐层包装。
- **不用**：功能固定、单层即可用继承更直接；装饰层数过多会让调试与阅读变难。

## 优劣与代价

✅ 比继承灵活（运行时组合、任意叠加），避免类爆炸，符合开闭。
✅ 被装饰对象与装饰器解耦，可自由搭配。
⚠️ 产生许多小对象、层层嵌套使调试困难、装饰顺序可能影响结果。

## 与相关概念的区别

- **装饰器 vs 代理**（[[代理模式]]）：结构几乎相同，意图相反——装饰器**增强功能**、不改接口；代理**控制对目标的访问**（何时/是否/以何权限）。
- **GoF 装饰器 vs Python `@decorator`**：Python 的 `@` 是函数/类包装的**语法糖**，与"装饰器与被装饰对象实现同一接口、可层层替换"的 GoF 结构神似而形不同，不能直接划等号。

## 常见误区

- 只要写了个 `@decorator`，就等同于 GoF 的装饰器模式。
- 装饰器不必实现 Component 接口也能层层包裹。
- 装饰器和代理是一回事，只是名字不同。

## 面试速答

> 🎯 装饰器 = 不改变对象接口的前提下，靠"装饰器与被装饰对象实现同一接口、层层委托"动态叠加职责，比继承灵活、避免类爆炸（如 Java I/O）。与代理结构相似但意图相反：装饰器增强功能、代理控制访问。
