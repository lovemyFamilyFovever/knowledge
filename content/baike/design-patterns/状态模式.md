# 状态模式

> 📌 **导航**：本文是 **状态模式** 词条，属 [[行为型模式（Behavioral Patterns）]] 子词条。

## 定义

**一句话定义：** 状态模式允许对象在其内部状态改变时改变行为，对外看起来就像改变了它的类。

**通俗类比：** 游戏角色——同一角色在"正常"下可跑、"受伤"下只能走、"眩晕"下不能动；行为随状态而变，而不是靠一堆 `if 状态==...`。

## 为什么需要它

当一个对象的行为强依赖它的状态、且状态多、转换规则复杂（订单、审批流、TCP 连接、游戏角色），用散落的 `if-else`/`switch` 判断状态会让代码臃肿、状态迁移隐晦。状态模式把每个状态的行为封进独立 State 类，转换规则内聚到状态里，主对象（Context）只把行为委托给当前状态。

## 核心机制

- **State**：声明与某状态相关的行为。
- **ConcreteState**：实现该状态下的行为，并决定何时切换到其他状态。
- **Context**：持有当前 State 引用，把请求委托给它。
- 状态切换由 State 内部驱动（如处理后把 `context.state` 改为下一状态），使状态机显式化。

## 具体示例

Context 把 `move()` 委托给当前状态，状态自身决定下一状态：

```python
class NormalState(State):
    def handle(self, ctx):
        print("正常: 可移动"); ctx.state = RunningState()   # 内部切换

class Character:                       # Context
    def __init__(self): self.state = NormalState()
    def move(self): self.state.handle(self)   # 委托给当前状态
```

## 何时用与何时不用

- **用**：对象行为强依赖状态、状态多且转换复杂；想消除散落的大型条件分支、把状态机显式化。
- **不用**：状态很少或转换极简单时，简单枚举 + 分支反而更清晰，别引入一堆 State 类。

## 优劣与代价

✅ 把状态相关行为局部化到各 State 类、消除庞杂条件分支、转换显式、新增状态符合开闭。
⚠️ 状态很少时属过度设计。
⚠️ 状态类间存在依赖（一个状态要知道下一个状态），转换逻辑可能分散。

## 与相关概念的区别

- **状态 vs 策略**（[[策略模式]]）：

| 对比项 | 状态 | 策略 |
|---|---|---|
| 切换主体 | 对象内部自动切换 | 客户端主动切换 |
| 实现间关系 | 各状态有转换关系 | 各策略互不相关 |

- 二者结构几乎相同（Context 持一个可换的对象），差别在**谁决定切换**与**各实现是否彼此关联**。

## 常见误区

- 状态模式和策略模式结构一样，所以用途也一样。
- 状态模式里每次状态切换都必须由客户端显式指定新状态。
- 有了状态模式，对象的字段值就不能再影响行为了。

## 面试速答

> 🎯 状态 = 对象行为随内部状态改变而改变、把每个状态的行为封进独立 State 类、转换由状态内部驱动，消除大段 `if 状态==` 判断。与策略结构像：策略由客户端主动选、状态由对象内部自动切换，且状态间有转换关系。
