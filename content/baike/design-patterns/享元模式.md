# 享元模式

> 📌 **导航**：本文是 **享元模式** 词条，属 [[结构型模式（Structural Patterns）]] 子词条。

## 定义

**一句话定义：** 享元模式运用共享技术，让大量细粒度对象复用同一份公共状态，从而高效支撑海量对象。

**通俗类比：** 字体渲染——屏幕上显示上千个"中"字，但字体文件里只存一份"中"的字形数据，所有"中"共享它；每个字的位置、颜色等差异由外部临时传入。

## 为什么需要它

某些场景对象数量极其庞大（文档里的每个字符、游戏里的每颗粒子、棋盘上的每枚棋子），逐个新建会耗尽内存。若这些对象的大部分状态是相同的、可共享的，就用享元把"公共部分"存一份共享，"随场景变化的部分"外置传入，从而以极少实例支撑海量对象。

## 核心机制

关键是把状态拆成两类：

- **内在状态（intrinsic）**：存于享元内部、可共享、不随场景变（如字形）。
- **外在状态（extrinsic）**：随场景变化、由客户端在调用时传入（如坐标、颜色）。

角色：Flyweight（接收外在状态的接口）、ConcreteFlyweight（持有内在状态）、FlyweightFactory（创建并缓存享元，保证相同内在状态只存一份）。

## 具体示例

工厂按字体名缓存享元，相同内在状态只建一次；渲染时把"字符"当外在状态传入：

```python
class FlyweightFactory:
    _fonts = {}
    @classmethod
    def get_font(cls, name):
        if name not in cls._fonts:
            cls._fonts[name] = FontFlyweight(name)   # 相同内在状态只建一次
        return cls._fonts[name]
# 请求 5 次、只创建 2 个（Arial / Times），其余复用
```

## 何时用与何时不用

- **用**：对象数量巨大且大部分状态可共享（文本编辑器字形、游戏粒子与地图块、`Integer.valueOf(-128~127)` 缓存）。前提：内在状态能提取且可共享、外在状态能由外部传入。
- **不用**：对象数量本就不大、或状态几乎都随场景变（无可共享内在状态）时，享元只增加复杂度。

## 优劣与代价

✅ 大幅减少内存中相似对象的实例数，降低内存与创建开销。
✅ 与工厂结合可集中管理共享。
⚠️ 内在/外在状态分离使代码复杂化。
⚠️ 享元被多方共享，若误把内在状态改为可变，会引发串改与线程安全问题。

## 与相关概念的区别

- **享元 vs 单例**（[[创建型模式（Creational Patterns）]]）：单例保证全局唯一一个实例；享元是"按内在状态共享一批实例"（一个工厂管一组）。
- **享元 vs 对象池**（[[对象池模式]]）：池是借出—独占—归还；享元是只读共享、同一实例被多方同时使用。
- **享元 vs 缓存**：普通缓存未必区分内/外在状态，享元强调共享不变部分、外置可变部分。

## 常见误区

- 享元就是缓存或单例，换个名字而已。
- 享元对象既然被共享，就可以随时修改它的内部状态。
- 只要对象多，就一定能用享元省内存。

## 面试速答

> 🎯 享元 = 用共享技术支持海量细粒度对象：把状态分成"可共享的内在状态"（存享元内，如字形）与"随场景变的外在状态"（外部传入，如坐标），相同内在状态只建一份。与单例/对象池不同——它共享一批只读实例。
