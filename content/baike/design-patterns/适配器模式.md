# 适配器模式

> 📌 **导航**：本文是 **适配器模式** 词条，属 [[结构型模式（Structural Patterns）]] 子词条。

## 定义

**一句话定义：** 适配器模式把一个已有类的接口，转换成客户端期望的另一种接口，使原本因接口不兼容而无法协作的类能够一起工作。

**通俗类比：** 电源转换插头——中国两脚扁插去欧洲圆孔插座用不了，中间加个转换器即可，插头和插座都不用改造自己。

## 为什么需要它

系统里常有"功能是对的、接口对不上"的类：遗留模块、第三方 SDK。直接改它们往往不现实（无源码、风险高、影响其他调用方）。适配器在中间做一层翻译，让客户端按自己期望的接口调用，被适配者保持原样，双方解耦。

## 核心机制

三个角色：Target（客户端期望的接口）、Adaptee（已存在、接口不兼容的类）、Adapter（实现 Target，内部持有或继承 Adaptee，把 Target 调用转成 Adaptee 调用）。两种实现方式：

- **对象适配器**：Adapter 组合一个 Adaptee 实例并委托它——更灵活，可适配 Adaptee 及其子类，主流。
- **类适配器**：Adapter 直接继承 Adaptee 并实现 Target——能重写 Adaptee 行为，但 Java 单继承下只能适配一个类、耦合更紧。

## 具体示例

对象适配器用组合把旧接口 `print_old` 翻译成目标接口 `print_new`，不改旧类一行代码：

```python
class OldPrinter:                       # Adaptee（保持原样）
    def print_old(self, t): return f"旧式打印: {t}"

class PrinterAdapter:                   # 实现 Target、委托 Adaptee
    def __init__(self, old): self._old = old
    def print_new(self, t): return self._old.print_old(t)
```

## 何时用与何时不用

- **用**：整合遗留系统 / 第三方库、把多套异构 SDK 统一成同一内部接口、把已存在的类接入新抽象体系。
- **不用**：从零设计时本就能定义合适的接口，别为已有兼容问题硬造适配层，徒增调用链与理解成本。

## 优劣与代价

✅ 复用现有实现、对 Adaptee 零侵入、提升透明性与复用。
✅ 让不兼容的两端各不改自己即可协作。
⚠️ 系统多出适配器层，用多了调用链变绕、可读性下降。
⚠️ 类适配器受单继承限制、与 Adaptee 耦合更紧。

## 与相关概念的区别

- **适配器 vs 桥接**（[[桥接模式]]）：适配器是**事后**弥补两个已存在的不兼容接口；桥接是**设计期**就把抽象与实现两个维度分开以便各自扩展。
- **适配器 vs 装饰器**（[[装饰器模式]]）：适配器**改变接口**（转成另一种）；装饰器**不改接口**、只叠加职责。

| 类型 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| 类适配器 | 继承 Adaptee | 可重写 Adaptee 方法 | 单继承只能适配一个类、耦合紧 |
| 对象适配器 | 组合 Adaptee | 可适配其子类、更灵活 | 无法直接重写 Adaptee 方法 |

## 常见误区

- 适配器模式需要修改被适配类（Adaptee）自身的源代码。
- 适配器和桥接是一回事，都是让接口配合起来。
- 适配器只能靠编译期继承 Adaptee 来实现。

## 面试速答

> 🎯 适配器 = 把已有类的接口转成客户端期望的接口，让不兼容的类协同、双方都不改自己；分对象适配器（组合委托，主流）与类适配器（继承）。它与桥接的区别在动机与时机：适配是事后弥补不兼容。
