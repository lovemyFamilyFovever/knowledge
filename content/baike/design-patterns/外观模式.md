# 外观模式

> 📌 **导航**：本文是 **外观模式** 词条，属 [[结构型模式（Structural Patterns）]] 子词条。

## 定义

**一句话定义：** 外观模式为子系统中的一组接口提供一个统一的高层接口，使子系统更易使用、并降低客户端与其内部细节的耦合。

**通俗类比：** 去医院看病不必自己跑挂号、缴费、检查、取药每个窗口——导诊台（外观）把整套流程串起来，一个入口搞定。

## 为什么需要它

一个子系统往往由许多协作的类组成，客户端若直接和这些内部类打交道，会耦合大量细节、牵一发动全身。外观提供一个"简化入口"，把常见用法封装成一两个高层方法，客户端只依赖外观，子系统内部可以自由演化。

## 核心机制

- **Facade（外观）**：知晓各子系统职责，把客户端请求委派给合适的子系统对象，编排调用顺序。
- **Subsystem（子系统类）**：实现具体功能；它们可以不知道 Facade 的存在（单向依赖）。
- 外观只是"便捷入口"，并不禁止高级用户绕过它直接使用子系统类——这是它与"强制封装"的关键区别。

## 具体示例

`ComputerFacade.start()` 把 CPU/内存/硬盘的启动顺序编排成一个方法，客户端只调一处：

```python
class ComputerFacade:                  # 外观
    def __init__(self): self.cpu, self.mem, self.disk = CPU(), Memory(), HardDrive()
    def start(self):
        self.cpu.freeze(); self.disk.read(); self.mem.load(); self.cpu.execute()

ComputerFacade().start()               # 客户端只调一个方法
```

## 何时用与何时不用

- **用**：给复杂子系统一个简单入口（SDK 封装、分层架构的 Service 门面、遗留系统统一接口）、解耦客户端与子系统内部、便于子系统独立演化。
- **不用**：客户端本就需要精细控制各子系统能力时，强加一层统一入口反而碍事；也别让外观膨胀成"上帝类"。

## 优劣与代价

✅ 使用简单，客户端与子系统解耦，符合迪米特法则（最少知道）。
✅ 子系统内部可自由重构而不影响客户端。
⚠️ 外观可能膨胀成大杂烩；它是"简化入口"而非"强制封装"，不能阻止客户端绕过。

## 与相关概念的区别

- **外观 vs 中介者**（[[行为型模式（Behavioral Patterns）]]）：外观简化"客户端→子系统"的**单向**调用；中介者协调"多个同僚对象"之间的**多向**交互。
- **外观 vs 适配器**（[[适配器模式]]）：外观**简化**一整套接口为易用高层接口；适配器只是把一个接口**转换**成另一个接口，不改功能。

## 常见误区

- 加了外观模式，客户端就不能再直接访问子系统了。
- 外观和中介者都是"中间层"，可以互相替代。
- 外观层应该把系统所有功能都聚合进去，越全越好。

## 面试速答

> 🎯 外观 = 给一组子系统接口提供统一高层入口，客户端只依赖外观、与内部细节解耦，子系统可独立演化。它是"简化入口"不禁止绕过，别膨胀成上帝类。与中介者区别：外观是单向调用、中介者协调多向交互。
