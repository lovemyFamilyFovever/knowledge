# 建造者模式

> 📌 **导航**：本文是 **建造者模式** 词条，属 [[创建型模式（Creational Patterns）]] 子词条。

## 定义

**一句话定义：** 建造者模式把一个复杂对象的构建过程与其最终表示分离，使同样的分步构建流程能产出不同的表示；实践中也常用它的链式 API 优雅地处理多个可选参数。

**通俗类比：** 点奶茶——选杯型 → 选糖度 → 选加料 → 选温度 → 出杯。每步独立、顺序可控，不必理解后厨完整配方，只要一步步表达需求就能定制出成品。

## 为什么需要它

当一个对象有很多可选字段，用重载构造函数会陷入"伸缩构造函数"：参数列表又长又难读、还极易传错顺序。建造者把"收集参数"和"装配对象"分开，让调用方链式、具名地设置参数，最后 `build()` 一次性产出（通常不可变的）对象；同一套分步流程还能复用出不同表示。

## 核心机制

- **GoF 经典四角色**：Builder（声明构建步骤）、ConcreteBuilder（实现步骤并持有产物）、Director（按固定顺序调用步骤，封装"构建流程"）、Product（被构建的复杂对象）。
- **现代流式变体**：省略 Director，由 Builder 自身提供链式 `xxx()` 方法并直接 `build()`（即《Effective Java》Item 2 的写法），主要用于解决多可选参数。
- 要点：`build()` 应用已收集的参数**新建**一个不可变 Product，而非反复返回同一个可变对象。

## 具体示例

链式调用按名设参，`build()` 收敛为不可变成品，可读性远超一长串位置参数：

```java
Computer pc = new Computer.Builder()
    .cpu("i9-13900K").ram("32GB").storage("1TB SSD")
    .build();   // build() 用收集好的参数 new 一个不可变 Computer
```

## 何时用与何时不用

- **用**：对象含大量可选参数、构建过程复杂需分步或按序装配、需要产出不可变对象、同一流程要出不同表示（文档构建为 HTML/PDF）。
- **不用**：参数很少、对象简单时写 Builder 属于过度设计。

## 优劣与代价

✅ 分步构建、参数具名可读，天然支持可选参数与默认值。
✅ 构建过程与表示解耦，便于构造不可变对象。
⚠️ 要多写 Builder 类，代码量增加。
⚠️ 对简单对象是过度设计；GoF 的 Director 在多数现代场景可省。

## 与相关概念的区别

- **建造者 vs 工厂方法 / 抽象工厂**：工厂回答"造哪种对象"、通常一步返回；建造者回答"这么复杂的对象怎么一步步造出来"、分多步再 `build()`。
- **流式 Builder vs 普通链式 setter**：关键在"分步收集 + 最后一次性 build 产出（常不可变）"，而非每步返回 `this` 的可变设置器。

## 常见误区

- 任何返回 this 的链式 setter 都算建造者模式。
- Builder 内部持有并反复返回同一个可变 Product 才是正确写法。
- GoF 建造者模式必须包含 Director 角色才能用。

## 面试速答

> 🎯 建造者 = 把复杂对象的构建过程与表示分离、分步收集参数最后 build() 产出（通常不可变）；专治"多可选参数"的伸缩构造函数。GoF 版含 Director，日常多用《Effective Java》式链式 Builder。
