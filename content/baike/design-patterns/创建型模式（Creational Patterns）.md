# 创建型模式（Creational Patterns）

> 📌 **导航**：本页是 **创建型模式** 枢纽，索引其 5 个子词条；各子模式的定义、代码与误区已拆出，本页只讲"是什么家族、怎么选"。

## 定义

**一句话定义：** 创建型模式关注对象的创建机制，把"创建什么对象、由谁创建、何时创建"从业务代码中解耦出来，让系统依赖抽象而非具体类，从而更容易扩展、替换与测试。

**通俗类比：** 像一套"只下订单、不亲手造"的规矩——你只声明"要什么"，至于"具体怎么造、造哪一种"交给专门的创建方去操心。

## 为什么需要它

直接 `new 具体类` 会把"依赖哪个实现"写死在调用处，一旦要换实现或加新类型就得改一片，违背开闭原则与依赖倒置。创建型模式把"实例化的知识"集中收口，带来四个共同收益：解耦创建与使用、封装创建复杂度、支持开闭扩展、控制实例的数量与生命周期。"设计模式"由 GoF 1994 年《设计模式》系统化，23 种按目的分为创建 / 结构 / 行为三类，创建型即其中一支。

## 核心机制

GoF 的 5 种创建型模式，加工程实践中常并列讨论的对象池（非 GoF），各自负责的"创建问题"如下：

| 子词条 | 解决什么 | 何时选它 |
|---|---|---|
| [[单例模式]] | 全局唯一实例 + 统一访问点 | 连接池 / 配置 / 日志器等只能有一份的资源 |
| [[工厂模式（工厂方法与抽象工厂）]] | 把"造哪种 / 造哪族"延迟到子类或工厂 | 具体类型由子类决定，或需整族平台切换 |
| [[建造者模式]] | 分步构建复杂对象、参数具名可读 | 可选参数多、构建流程复杂、要产出不可变对象 |
| [[原型模式]] | 复制已有对象而非从头 new | 对象创建昂贵、或需要与当前状态相同的副本 |
| [[对象池模式]]（非 GoF） | 借还复用昂贵对象并控制上限 | 重量级资源（连接 / 线程）高频借还 |

这些模式共享同一前提——把创建收敛到一处、调用方只认抽象；具体每种怎么落地见各子词条，本页不重复其定义。

## 具体示例

选型可顺着"要解决哪类创建问题"走一遍：全 App 只需一份配置对象 → [[单例模式]]；同一接口下"造 MySQL 还是 Postgres 方言"交给子类 → [[工厂模式（工厂方法与抽象工厂）]]；要把一整套控件从 Windows 风格换成 Mac 风格 → 抽象工厂；构造一个参数很多的 HTTP 请求对象 → [[建造者模式]]；从一张模板批量派生几乎相同的报表实例 → [[原型模式]]；频繁建立 / 关闭 TCP 连接 → [[对象池模式]]。

## 何时用与何时不用

- **用**：当"对象如何创建"本身是易变点或复杂点——类型运行时才定、参数繁多、需要受控复用或全局唯一。
- **不用**：创建很直接时就用普通构造器，别为模式而模式徒增抽象层；且多数框架（如 Spring 的 IoC 容器）已替你实现了工厂与单例，能复用就别手写。

## 优劣与代价

✅ 解耦创建与使用，面向抽象编程，便于扩展替换与测试。
✅ 把分散的实例化逻辑收口到一处，降低局部改动引发的连锁修改。
⚠️ 引入抽象层与样板代码，增加理解与调试成本，过度套用反而难读。
⚠️ 单例还额外带来全局隐式状态与可测性问题（详见子词条）。

## 与相关概念的区别

- **创建型 vs 结构型**（[[结构型模式（Structural Patterns）]]）：前者管"怎么造对象"，后者管"怎么把类与对象组合成更大结构"。
- **创建型 vs 行为型**（[[行为型模式（Behavioral Patterns）]]）：后者管对象之间的职责分配与通信，与"创建"正交。
- 五种创建型之间则按"管单个对象 / 一族对象 / 分步构建 / 复制 / 复用"各有侧重，见上方索引表。

## 常见误区

- 任何需要全局共享的东西都应该写成单例。
- 工厂方法和抽象工厂是一回事，只是叫法不同。
- 代码里用了设计模式，质量就一定更高。

## 面试速答

> 🎯 创建型模式 = 把对象的"怎么造"从业务解耦、依赖抽象而非具体类。GoF 五种（单例 / 工厂方法 / 抽象工厂 / 建造者 / 原型）加工程常见的对象池，分别管唯一实例、造哪种或哪族、分步构建、复制、复用。
