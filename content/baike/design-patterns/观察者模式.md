# 观察者模式

> 📌 **导航**：本文是 **观察者模式** 词条，属 [[行为型模式（Behavioral Patterns）]] 子词条。

## 定义

**一句话定义：** 观察者模式定义对象间一对多的依赖，当一个对象（主题）状态改变时，所有依赖它的对象（观察者）都自动收到通知并更新。

**通俗类比：** 微信公众号——你关注某个号（订阅），它每次发文（状态变化）就推送给你，号主不必知道具体是谁在看。

## 为什么需要它

一个变化常要触发多个互不相关的后续动作（下单后：发邮件、记日志、加积分）。若发起方硬编码这些动作，就会和每个下游紧耦合、加一个动作改一处。观察者让主题只维护"订阅者列表 + notify"，新增观察者不改主题，实现松耦合的事件驱动。

## 核心机制

- **Subject**：维护观察者列表，提供 `attach` / `detach` / `notify`。
- **Observer**：声明 `update`；收到通知后更新自身（常回查主题取新状态）。
- 经典 GoF 中主题**直接持有**观察者引用并通知；**发布—订阅**则多一个事件通道解耦，发布者与订阅者互不感知（下表对比）。

## 具体示例

主题在状态变化时逐个通知已注册观察者：

```python
class Subject:
    def __init__(self): self._obs = []
    def attach(self, o): self._obs.append(o)
    def notify(self, ev):
        for o in self._obs: o.update(ev)     # 一对多广播

class Logger:                                # Observer
    def update(self, ev): print("记录", ev)
```

## 何时用与何时不用

- **用**：GUI 事件、消息/领域事件、配置热更新广播、一个变化需触发多个解耦动作。
- **不用**：观察者很少或通知顺序/时机需严格控制时；通知链过长易雪崩、难调试。

## 优劣与代价

✅ 主题与观察者松耦合、支持广播、新增观察者符合开闭。
✅ 天然支撑事件驱动与响应式。
⚠️ 通知顺序不应被依赖；观察者过多时通知开销大。
⚠️ 链式更新可能引发难以追踪的连锁反应。

## 与相关概念的区别

- **观察者 vs 中介者**（[[中介者模式]]）：观察者是一对多的**单向广播**（主题→观察者）；中介者收敛多个同僚间的**多向**交互。
- **观察者 vs 发布—订阅**：

| 对比项 | 观察者 | 发布—订阅 |
|---|---|---|
| 耦合 | 主题直接持有观察者 | 经消息通道，双方互不感知 |
| 通知 | 主题直接推 | 发到通道、再分发给订阅者 |

## 常见误区

- 观察者模式和发布—订阅是一回事，没有耦合度差别。
- 主题通知观察者时，观察者之间一定有固定的先后顺序。
- 用了观察者模式，被观察者就必须知道每个观察者的具体类型。
