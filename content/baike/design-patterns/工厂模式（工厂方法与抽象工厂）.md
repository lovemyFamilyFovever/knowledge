# 工厂模式（工厂方法与抽象工厂）

> 📌 **导航**：本文是 **工厂模式** 词条，属 [[创建型模式（Creational Patterns）]] 子词条，合并工厂方法与抽象工厂两种 GoF 模式并对照简单工厂。

## 定义

**一句话定义：** 工厂模式把"实例化哪一种具体类型"从调用方解耦出去——工厂方法用一个创建接口、由子类决定造哪个类，抽象工厂则通过一个接口一次造出"一整族"相互关联的产品。

**通俗类比：** 工厂方法像连锁快餐的"区域经理"——总部只定流程，具体卖汉堡还是炸鸡由各分店（子类）决定；抽象工厂像"整体装修风格供应商"——选定北欧风，地板、沙发、灯具就成套配套地一起给你。

## 为什么需要它

调用方若直接 `new 具体类`，就把"依赖哪个实现"写死了，换实现、加新类型都得改调用处，违背开闭原则与依赖倒置。工厂把创建逻辑收口，让调用方只依赖抽象产品，新增类型时尽量只加不改。

## 核心机制

- **简单工厂（非 GoF）**：一个工厂类按参数分支决定造哪个产品；新增产品要改工厂分支，违反开闭原则。
- **工厂方法**：声明创建接口，把实例化延迟到子类；一个"产品等级"，新增产品 = 新增一个 Creator 子类（符合开闭）。
- **抽象工厂**：一个工厂暴露多个创建方法，产出"一族"相关/依赖的产品；关键区分产品族（同一工厂成套出品）与产品等级（同一抽象的不同实现）。

## 具体示例

工厂方法把"造哪种 Button"延迟到子类：

```python
class Dialog(ABC):                       # Creator
    def render(self): self.create_button().click()
    @abstractmethod
    def create_button(self) -> Button: ...   # 工厂方法
class WinDialog(Dialog):
    def create_button(self): return WinButton()
```

抽象工厂一次产出一族配套控件，换工厂即整族替换：

```python
class UIFactory(ABC):                    # 抽象工厂
    def create_button(self): ...
    def create_checkbox(self): ...
class WinFactory(UIFactory):
    def create_button(self): return WinButton()
    def create_checkbox(self): return WinCheckbox()
```

## 何时用与何时不用

- **工厂方法**：只需创建"单个产品等级"，且由子类/运行时决定具体类型（日志 Appender、数据库方言）。
- **抽象工厂**：需要在多套"风格/平台/供应商"之间整体切换、且要强制一组对象配套使用（跨平台 UI、支付渠道套件）。
- **别过度**：产品少、不常扩展时简单工厂就够；抽象工厂对"新增产品等级"扩展很痛苦。

## 优劣与代价

✅ 调用方与具体类彻底解耦，只依赖抽象产品。
✅ 工厂方法对"新增产品"符合开闭；抽象工厂保证同族一致性、杜绝错误混搭。
⚠️ 工厂方法每加一种产品就多一个工厂子类，类数量成对增长。
⚠️ 抽象工厂新增产品等级要改抽象接口及全部具体工厂，违反开闭。

## 与相关概念的区别

| 对比项 | 简单工厂（非 GoF） | 工厂方法 | 抽象工厂 |
|---|---|---|---|
| 产品维度 | 单个等级 | 单个等级 | 一族（多个等级） |
| 创建方式 | 一个工厂按参数分支 | 每个产品一个工厂子类 | 一个工厂产整族 |
| 扩展方式 | 新增产品=改工厂 | 新增产品=加子类 | 新增族=加工厂；新增等级=改所有工厂 |
| 符合开闭 | 否 | 是 | 对族是、对等级否 |

- **抽象工厂 vs 工厂方法**：前者造"一族相关"产品，后者造"单个"产品；抽象工厂内部常用多个工厂方法实现。

## 常见误区

- 简单工厂就是 GoF 的工厂方法模式。
- 抽象工厂对"新增产品等级"也天然符合开闭原则。
- 工厂方法每次调用必须返回一个全新的对象。

## 面试速答

> 🎯 工厂方法=一个产品等级、由子类延迟决定造哪个（新增=加子类，符合开闭）；抽象工厂=一个接口造"一族"配套产品（换工厂即整族替换，但对新增产品等级扩展痛苦）；简单工厂按参数分支、非 GoF 且违开闭。
