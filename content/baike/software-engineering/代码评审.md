# 代码评审

> 📌 **导航**：本文是 **代码评审** 词条，属于 software-engineering 术语集。相关枢纽：[[01-开发流程]]、[[02-版本控制]]、[[03-代码质量]]、[[04-CI CD]]、[[05-项目管理]]。

## 定义

**一句话定义：** 代码评审（Code Review）是在代码合入主干前，由其他开发者系统性地检查源代码的过程，目的是发现缺陷、保证质量与一致性、促进知识共享，并提升整体可维护性；常见形式为拉取请求（PR / MR）评审。

**通俗类比：** 像论文发表前的同行评议——作者把稿子交给同行审读，指出问题、提出改进，通过后才发表（合入）；既保证质量，也让同行了解彼此的工作。

## 为什么需要它

单人写码必有盲区：逻辑漏洞、坏设计、安全隐患，作者自己往往看不见；而且知识若只锁在一个人脑子里，就是团队风险。代码评审引入第二双眼睛，把缺陷挡在合入之前、统一风格与设计、传播知识、建立集体所有权——它是低成本、高杠杆的质量与协作手段。

## 做法

- **流程**：提交 PR/MR → 评审者读 diff 留评论 → 作者修改 → 达成一致后合并，常配合 CI（测试 / 静态检查）门禁。
- **关注点**：正确性、可读性、设计与架构、测试覆盖、安全、性能、边界条件。
- **好实践**：小步提交（小 PR 更易评审）、清单化检查、自动化先行、建设性沟通、对事不对人。

| 组成 | 说明 |
|------|------|
| PR / MR | 评审的载体 |
| diff 与评论 | 逐行讨论 |
| 评审清单 | 系统性检查项 |
| CI 门禁 | 自动化测试 / 检查 |

## 具体示例

同样指出问题，评论的语气和指向决定了评审是协作还是伤人——应就代码提具体风险与替代方案：

```
❌ "这写的什么，重写。"
✅ "并发下 counter 可能丢更新，建议改用原子操作或加锁。"
```

## 何时用与何时不用

- **用**：团队协作、开源项目、需要防缺陷流入主干、新人培养与知识传播。
- **不用（降级）**：紧急热修复可在事后补评审；纯机械改动（版本 bump、格式化）可放宽，但不等于取消质量门禁。

## 优劣与代价

✅ 提升质量与一致性、及早发现缺陷、促进知识共享与集体所有权。
✅ 与 CI/静态检查互补，形成合入门禁。
⚠️ 耗时、可能成瓶颈，异步反馈有延迟。
⚠️ 效果高度依赖评审者水平与团队文化，流于形式则无效。

## 与相关概念的区别

- **评审 vs 自动化测试**：评审靠人判断设计与语义、测逻辑之外的坏味道；测试跑可执行断言。二者互补，谁也替代不了谁。
- **评审 vs 结对编程**：评审是异步 / 事后把关，结对是实时共同编写。
- **小 PR vs 大 PR**：PR 越小，评审注意力越集中、往返越快，大 PR 常沦为"橡皮图章"。

## 常见误区

- 代码评审就是资深工程师给新人挑刺、追责。
- 有了严格的代码评审，就不需要自动化测试了。
- PR 攒得越大越省事，一批改动一起评审最高效。

## 面试速答

> 🎯 代码评审 = 代码合入主干前由他人系统检查源码，发现缺陷、保证质量一致性、促进知识共享；主流是 PR/MR 评审，配合 CI/静态检查门禁，讲究小步提交、建设性沟通、对事不对人。
