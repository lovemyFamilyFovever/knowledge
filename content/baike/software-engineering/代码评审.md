# 代码评审


> 📌 **导航**：本文是 **代码评审** 词条，属于 software-engineering 术语集。相关枢纽：[[01-开发流程]]、[[02-版本控制]]、[[03-代码质量]]、[[04-CI CD]]、[[05-项目管理]]。

## 定义

**一句话定义：** 代码评审(Code Review)是在代码合入主干前,由其他开发者系统性地检查源代码的过程,目的是发现缺陷、保证质量与一致性、促进知识共享,并提升整体可维护性;常见形式为拉取请求(PR / MR)评审。

**通俗类比：** 像论文发表前的同行评议——作者(提交者)把稿子交给同行(评审者)审读,指出问题、提出改进,通过后才发表(合入);既保证质量,也让同行了解彼此的工作。

> 多义说明:形式有正式(结对/会议评审,如 Fagan 检视)与轻量(基于工具的异步 PR 评审);本文以主流的 PR / MR 评审为主。

## 原理与机制

- **流程:** 开发者提交 PR/MR → 评审者阅读 diff、留评论 → 作者修改 → 达成一致后合并;常配合 CI(测试/静态检查)门禁。
- **关注点:** 正确性、可读性、设计与架构、测试覆盖、安全、性能、风格一致、边界条件。
- **实践:** 小步提交(小 PR 更易评审)、清单化检查、建设性沟通、自动化(linter / CI)先行。

## 关键组成

| 组成 | 说明 |
|------|------|
| PR / MR | 评审的载体 |
| diff 与评论 | 逐行讨论 |
| 评审清单 | 系统性检查项 |
| CI 门禁 | 自动化测试/检查 |
| 批准与合并 | 通过后的动作 |

## 应用场景

- 团队协作开发
- 开源项目
- 质量保障、减少缺陷流入主干
- 新人培养与知识传播

## 优点与局限

- 优点:提升代码质量与一致性、及早发现缺陷、促进知识共享与集体所有权。
- 局限:耗时(评审与往返)、可能成为瓶颈、依赖评审者水平与团队文化、异步评审反馈有延迟、流于形式则无效。

## 常见误区

- 代码评审不是"挑刺/追责",应建设性、对事不对人。
- 评审不能替代自动化测试(二者互补)。
- PR 过大难以有效评审,应拆小。
- 评审关注的不只是风格,更是正确性、设计与安全。
