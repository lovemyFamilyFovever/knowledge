# 构建流水线与 CI/CD 工具

> 📌 **导航**：本文是 **构建流水线与 CI/CD 工具** 词条，属于 software-engineering 术语集。相关枢纽：[[04-CI CD]]、[[CI 与 CD]]、[[容器与编排技术详解]]、[[03-代码质量]]。

## 定义

**一句话定义：** 构建流水线是把"提交 → 构建 → 测试 → 产出制品 → 部署验证"编排成**可重复、可审计、失败即停**的自动化链路；Jenkins、GitHub Actions、GitLab CI 等工具是它的承载形态，差别主要在配置方式、执行环境隔离与生态耦合点。

**通俗类比：** 像工厂流水线的工位与传送带：每个工位只干一件事、上一件不合格就别往下传；换一条产线（换工具）不该改变工序本身。

## 为什么需要它

手工发布的问题不是"累"，而是**不可复现**：谁在什么机器上执行了哪几步、顺序对不对、用的依赖版本是什么，事后无从追溯。流水线把这套动作固化成声明式配置，进而是三个硬收益：任何一次产物都能追溯到具体 commit、失败发生在工作日白天而不是发布窗口、以及团队可以用同一套定义同时跑在 PR 检查与生产发布上。

## 核心机制

- **触发**：push / PR / 定时 / 手工；并发控制（同分支排队、旧任务取消）能显著省机时。
- **阶段编排**：装依赖 → 静态检查与单测 → 构建产物 → 集成与端到端 → 发布。**由快到慢、由便宜到昂贵**排序，让失败尽量早。
- **缓存与隔离**：依赖缓存与 Docker 容器化执行环境是构建提速与"本地能跑"两件事的关键；环境不隔离会把机器状态混进构建结果。
- **制品与晋级**：一次构建产出一个不可变版本（带 git sha 的镜像/包），推入制品库，之后只是**同一件制品在不同环境间晋级**，而不是每环境重新构建一次。
- **凭据治理**：密钥从流水线变量/密管服务注入，绝不落仓；最小权限，按环境分角色。

| 工具 | 配置形态 | 典型特点 |
|---|---|---|
| Jenkins | Pipeline as code（Groovy） | 插件生态最全、自运维、维护成本高 |
| GitHub Actions | 仓库内 YAML + Marketplace | 与 PR/Issue 同仓耦合、托管 runner 省心 |
| GitLab CI | 仓库内 `.gitlab-ci.yml` | 与代码托管、制品库、环境管理一体 |

## 具体示例

一次构建、多处晋级，是制品化的核心习惯：

```yaml
jobs:
  build:
    script:
      - docker build -t registry.example.com/app:$CI_COMMIT_SHORT_SHA .
      - docker push registry.example.com/app:$CI_COMMIT_SHORT_SHA
  deploy-staging:
    needs: build
    script: [ deploy app:$CI_COMMIT_SHORT_SHA to staging ]
  deploy-prod:
    needs: deploy-staging
    when: manual            # 持续交付：留人工审批这一步
```

同一镜像依次进 staging 与 prod，避免"为生产重新构建一次"引入差异——这类差异正是"测试环境好好的、上线就炸"的常见根因。

## 何时用与何时不用

- **用**：任何多人协作且需重复发布的项目；需要构建可追溯与合规审计；多环境一致性要求高。
- **注意成本**：托管执行环境按并发与时长计费，重依赖项目要配缓存与矩阵裁剪，否则账单与等待时间一起涨；自运维 Jenkins 则要预留专人维护插件与安全补丁。
- **不用**：一次性脚本或极低频交付，用手工或简单 CI 即可；核心链路缺自动化测试时先补测试，别先搭复杂流水线。

## 优劣与代价

✅ 交付过程从口口相传变成可读、可 diff、可回放的代码。
✅ 失败早暴露且定位到具体阶段，减少深夜排障。
⚠️ 流水线自身是需维护的基础设施：慢、脆、常红会让团队绕过它。
⚠️ 平台锁定风险：Groovy、Actions 语法与 GitLab CI 互不兼容，迁移需要重写。

## 与相关概念的区别

- **流水线 vs CI/CD**：CI/CD 是实践与目标（见 [[CI 与 CD]]），流水线是其载体；同一套 CI/CD 可以跑在不同工具上。
- **构建 vs 打包 vs 制品**：构建产出可执行物，打包把配置与密钥注入，制品是那件**可晋级、可回滚**的最终产物。
- **YAML 与脚本式**：声明式（Actions/GitLab）门槛低、易读，复杂逻辑易退化成内嵌 shell；脚本式（Jenkinsfile）可表达复杂控制流，也更难维护。
- **持续部署 vs 自动部署**：流水线里加个 deploy 步骤只是自动部署，持续部署还需要环境隔离、健康检查与自动回滚闭环。

## 常见误区

- 装个 Jenkins 就等于拥有了 CI/CD。
- 每个环境都重新构建一次镜像更保险。
- 流水线越复杂越先进，阶段越多质量越有保障。

## 面试速答

> 🎯 流水线把构建-测试-发布编排成失败即停的可复现链路，阶段按由快到慢排列、环境用容器隔离；核心习惯是一次构建产出不可变制品、同一制品跨环境晋级，工具差异主要在配置形态与生态耦合。
