# 02-版本控制

> 📌 **导航**：本页是 **版本控制与 Git 协作流程** 枢纽（原 14 术语汇编收敛而来）。各命令/概念的机制、示例与误区已在 [[版本控制与Git深入]][[Git高级用法]][[代码评审]] 等专条承载，本页只做"版本控制术语地图"索引，不重复。

## 定义

**一句话定义：** 版本控制用一套"记录变更、管理并行、可回滚"的系统（Git 为代表）保存代码历史；本枢纽把 Git 的 14 个常用术语（工作流/分支合并/协作评审）归位到各自的深入专条。

**通俗类比：** 像给代码装上"时光机 + 多分支平行宇宙"：任何时刻能回到过去（历史）、能开分叉各自演进再合流（分支/合并），合流前还要互相审一遍（PR/评审）。

## 为什么需要它

多人协作、反复试错、随时可回退——这些是软件工程的刚需，版本控制系统正是为此而生。但 Git 术语庞杂（三区、merge/rebase、冲突、PR、Flow…），散写易与已有的 [[版本控制与Git深入]] 重复。把术语收敛成"概念→专条"地图，读者按需求直达，汇编本身不再二次承载。

## 具体示例

一次典型 Git 协作闭环（细节与坑见 [[版本控制与Git深入]]）：

```bash
git checkout -b feat/x     # 开分支
git add -p && git commit   # 挑选暂存并提交
git pull --rebase          # 同步并把本地提交搬到最新基上
# 推分支 → 开 PR → 代码评审 → 合并（见 [[代码评审]]）
```

## 何时用与何时不用

- **用**：任何多人/需历史/需回滚的代码项目都用 Git；小改动走 trunk/短分支 + PR，长期并行大特性用特性分支（策略见 [[版本控制与Git深入]]）。
- **不用**：频繁变大的二进制资产别裸进仓库（用 LFS）；公共分支慎用改写历史的 `rebase`。版本控制的"用不用"几乎不是问题，问题在"用哪种分支策略与评审纪律"。

## 优劣与代价

✅ Git 分布式、离线可用、分支廉价、历史可完整追溯与回滚；配 PR/评审形成质量闸门。
✅ 术语各归专条后，学习与排查路径清晰。
⚠️ 命令语义多、`reset`/`rebase` 心智门槛高、易误用改写他人历史。
⚠️ 大仓库/大文件性能下降；流程（Git Flow）过重会拖慢小团队。

## 与相关概念的区别

- **merge vs rebase**：保留真实分叉 vs 改写线性历史——见 [[版本控制与Git深入]]。
- **Git Flow vs Trunk Based**：多长期分支（main/develop/hotfix）vs 常可部署的 main + 短分支。
- **版本控制 vs 代码评审**：前者管历史与并行（本页），后者管合入前质量（[[代码评审]]）。
- **基础操作 vs 进阶**：日常命令在 [[版本控制与Git深入]]，`rebase -i`/`bisect`/`worktree`/`submodule`/hooks 在 [[Git高级用法]]。

## 常见误区

- 把已提交进仓库的 `.env` 再写进 `.gitignore`，密钥就从历史里消失了。
- 公共分支上随手 `rebase` 改写历史，对别人没影响。
- 有了分支和 PR 就自动不需要代码评审纪律了。

## 面试速答

> 🎯 版本控制=记录变更、管理并行、可回滚。Git 三区模型(工作区→暂存→仓库)；分支廉价，merge 保分叉、rebase 改线性；冲突手工裁决；协作走 分支→PR/MR→[[代码评审]]→合并；策略 Git Flow vs 主干开发择规模。进阶 rebase-i/bisect/hooks 见 [[Git高级用法]]。
