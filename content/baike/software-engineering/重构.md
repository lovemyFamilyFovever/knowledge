# 重构

> 📌 **导航**：本文是 **重构** 词条，属于 software-engineering 术语集。相关枢纽：[[01-开发流程]]、[[02-版本控制]]、[[03-代码质量]]、[[04-CI CD]]、[[05-项目管理]]。

## 定义

**一句话定义：** 重构（Refactoring）是在不改变软件外部可观察行为的前提下，对代码内部结构进行调整与改善的过程，目的是提升可读性、可维护性与可扩展性、消除"代码坏味道"（code smell），降低后续修改的成本。

**通俗类比：** 像整理一间能用但杂乱的房间——不改变房间的功能（还是住人），而是把物品归类、动线理顺、扔掉冗余，让日后找东西和打扫都更省事；行为不变，内部更清爽。

## 为什么需要它

代码会随需求反复修改而腐化：重复、过长函数、大类、霰弹式改动的坏味道越堆越多，每加一个功能都更贵。重构专门偿还这类结构成本，让代码持续保持"好改"的状态，从而为后续新功能铺路、减少 bug 温床——它是维持长期开发速度而非短期产出的手段。

## 做法

- **前提**：有自动化测试保障"前后行为一致"，小步进行、频繁提交。
- **常见手法（Fowler 归纳）**：提炼函数（Extract Method）、重命名、消除重复（DRY）、以多态取代条件表达式、引入参数对象、分解大类等。
- **识别时机**：出现坏味道（重复代码、过长函数、过大类、霰弹式修改、依恋情结等）。
- **工具支持**：IDE 的自动重构（重命名、提炼、内联）基于 AST 保证安全（见 [[抽象语法树]]）。

## 具体示例

把散落在多处的资格判断提炼成一个具名谓词，逻辑分毫未变，可读性与复用性却显著提升：

```python
# 重构前：同一判断散落各处
if user.age >= 18 and user.kyc_ok: ...
# 重构后：提炼为具名函数，行为不变
def is_eligible(user): return user.age >= 18 and user.kyc_ok
```

## 何时用与何时不用

- **用**：遗留代码改善、持续保持代码健康、为新增功能铺路、偿还技术债、代码评审后的改进。
- **不用**：完全没有测试保护时贸然做大重构（风险高）；结构尚可却为"好看"频繁扰动、拖累进度——按收益决定，不做无谓 churn。

## 优劣与代价

✅ 提升可维护性与可读性、降低长期成本、减少 bug 温床、便于扩展。
✅ 让"代码坏味道"及时被清偿，避免滚成技术债。
⚠️ 短期不产出新功能，需与业务节奏权衡投入。
⚠️ 缺测试时重构有回归风险，大规模重构成本高。

## 与相关概念的区别

- **重构 vs 重写**：重构小步、行为不变、风险低；重写推倒重来、常改变行为、风险大得多。
- **重构 vs 改功能**：重构明确不改外部可观察行为，一旦改了行为那叫"修改功能"。
- **重构 vs 性能优化**：性能优化可能刻意改变实现甚至行为以提速；重构以结构清晰为主，不以跑得快为目标。

## 常见误区

- 重构就是顺手改改逻辑，让程序跑出不一样但更好的结果。
- 重构等于重写，干脆推倒重来更彻底。
- 没测试也能放心大胆重构，回头再补也一样。

## 面试速答

> 🎯 重构 = 在不改变外部可观察行为前提下改善代码内部结构，消除坏味道、提升可维护性；靠自动化测试护航、小步频繁提交，用提炼函数、重命名、消重、多态取代条件等手法。
