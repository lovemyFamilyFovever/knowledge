# 重构


> 📌 **导航**：本文是 **重构** 词条，属于 software-engineering 术语集。相关枢纽：[[01-开发流程]]、[[02-版本控制]]、[[03-代码质量]]、[[04-CI CD]]、[[05-项目管理]]。

## 定义

**一句话定义：** 重构(Refactoring)是在不改变软件外部可观察行为的前提下,对代码内部结构进行调整与改善的过程,目的是提升可读性、可维护性与可扩展性、消除"代码坏味道"(code smell),降低后续修改的成本。

**通俗类比：** 像整理一间能用但杂乱的房间——不改变房间的功能(还是住人),而是把物品归类、动线理顺、扔掉冗余,让日后找东西和打扫都更省事;行为不变,内部更清爽。

> 多义说明:重构 ≠ 重写(rewrite,推倒重来)≠ 性能优化 ≠ 新增功能;重构强调"外部行为不变、内部结构改善"。本文取此含义。

## 原理与机制

- **前提:** 有测试保障(重构前后行为一致,靠自动化测试验证),小步进行、频繁提交。
- **常见手法(Martin Fowler 归纳):** 提炼函数(Extract Method)、重命名、消除重复(DRY)、以多态取代条件表达式、引入参数对象、分解大类等。
- **识别时机:** 出现"代码坏味道"(重复代码、过长函数、过大类、霰弹式修改、特性依恋等)。
- **工具支持:** IDE 的自动重构(重命名、提炼、内联)基于 AST(见 [[抽象语法树]])保证安全。

## 关键组成

| 组成 | 说明 |
|------|------|
| 行为不变约束 | 重构的核心前提 |
| 测试保障 | 验证行为一致 |
| 代码坏味道 | 触发重构的信号 |
| 重构手法 | 提炼/重命名/内联等 |
| 小步提交 | 降低风险 |
| IDE / 工具 | 基于 AST 的安全重构 |

## 应用场景

- 遗留代码改善
- 持续保持代码健康
- 为新增功能铺路
- 偿还技术债、代码评审后的改进

## 优点与局限

- 优点:提升可维护性与可读性、降低长期成本、减少 bug 温床、便于扩展。
- 局限:短期不产生新功能(需权衡投入);缺乏测试时重构有风险;大规模重构成本高;可能与开发进度冲突。

## 常见误区

- 重构不改变外部行为(改变行为属于"修改功能")。
- 重构需测试护航,否则可能引入回归。
- 重构 ≠ 重写(重写风险大得多)。
- "以后有空再重构"往往导致技术债累积,宜持续小步重构。
