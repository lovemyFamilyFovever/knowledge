# 04-CI/CD


> 📌 **导航**：本文是 **04-CI/CD** 枢纽页。原 14 节里，CI/CD 概念与流水线工具各拆为独立词条，蓝绿 / 金丝雀 / 滚动更新归口 [[蓝绿部署与灰度发布]]，自动化测试归口测试子域专条；制品、环境、特性开关留在本页。

## 定义

**一句话定义：** CI/CD 是一条把变更安全推向生产的自动化主干——**CI** 让每次提交都被构建与测试验证，**CD** 让验证过的产物可自动晋级到各环境；制品、环境与特性开关是支撑这条主干不失控的三块地基。

**通俗类比：** 像机场行李系统：值机时贴条码（提交与制品标识）、经分拣传送带自动到指定转盘（流水线与环境晋级），特殊行李改走人工通道（审批、开关）；一旦某件行李卡住，整条线立刻报警而不是等航班起飞才发现少了一件。

本页是**枢纽页**：给出各环节的分工与归口，概念本体与工具细节走下表双链。

## 为什么需要它

代码写出来不值钱，"能反复、低风险地把它送到用户手上"才值钱。缺了这条自动化主干，团队会同时掉进两个坑：集成被推迟成两周一次的大合并，冲突与语义漂移在暗处积累；发布变成一场靠记忆和运气的仪式，深夜手工执行清单、环境之间靠人比对。CI/CD 把这两件事从"偶发大事件"改造成"高频小动作"——**频率本身就是安全机制**，因为重复才会被自动化、被监控、被回滚演练。

## 核心机制

### 主干上的四个环节

| 环节 | 保证什么 | 归口 |
|---|---|---|
| 集成与验证 | 主干随时可构建、测试通过 | [[CI 与 CD]] |
| 流水线编排 | 失败即停、可复现、可审计 | [[构建流水线与 CI-CD 工具]] |
| 质量门禁 | 测试、静态检查、评审卡住入口 | [[单元测试]]、[[集成测试]]、[[E2E 测试]]、[[代码评审]] |
| 部署放量 | 灰度节奏与回滚能力 | [[蓝绿部署与灰度发布]] |

四个环节缺一环，"自动化"就会变成缺陷放大器：测试不牢，CI 只是快速产出红灯；没有放量与回滚，自动部署等于自动把故障推到全量。

### 三块支撑地基

**制品**是构建产出的不可变物（JAR、镜像、包），必须带可追溯标识（git sha / 版本）并存入制品库，后续只是**同一件制品跨环境晋级**，绝不为每个环境重新构建——重构建引入的差异正是"测试环境好好的、上线就炸"的头号根因。
**环境管理**要求环境差异外置为配置（同一镜像跑在 staging 与 prod），且能按需重建（不可变基础设施，见 [[容器与编排技术详解]]）。
**特性开关**把"是否可见"从发布时刻解耦出来，让部署与发布成为两件事，从而支持渐进放量、A/B 与不重新部署的秒级止血。

### 交付节奏的选择

主干可发布 → 人工审批发布 = 持续交付；连发布也自动 = 持续部署，前提是灰度与回滚已到位。有合规审批或需要挑发布时点的业务应停在持续交付，不必把"全自动"当默认目标。

## 具体示例

最小可用的主干节奏：小步提交 → 触发流水线 → 便宜检查在前、昂贵检查在后 → 产出带 sha 的镜像 → 自动进 staging → 人工批准进 prod → 出问题先关开关再回滚。

```text
push → lint(10s) → unit(1m) → build+push artifact:sha(3m)
     → e2e(8m) → deploy:staging(2m) → [approval] → deploy:prod(canary 5%→50%→100%)
```

关键在于**开关先于回滚**：新功能出问题第一动作是关掉特性开关（秒级），回滚版本是分钟级的兜底。

## 何时用与何时不用

- **用**：多人协作或需定期发布就必须要 CI；有审计与可追溯要求时制品化；变更频繁、需按人群放量的 C 端业务再谈持续部署。
- **先补再说**：没有自动化测试的核心路径、构建红灯长期无人管——这两种情况下先搭复杂流水线只会放大混乱。
- **不必**：一次性脚本、极低频内部分发物；把整条链路手工化反而更省钱时，就别为了"有 CI/CD"而搭。

## 优劣与代价

✅ 集成与发布风险被切成小段，问题在提交后几分钟内暴露，而不是发布窗口。
✅ 制品与流水线让"这次上线到底装了什么"变成可回答的事实。
⚠️ 流水线是需持续维护的基础设施：慢、脆、常红会诱发绕过，反而掩盖真实问题。
⚠️ 自动化程度越高，人工刹车越少；缺灰度与回滚时，持续部署是净负收益。

## 与相关概念的区别

- **CI vs CD**：CI 管"改动合进来是否可信"，CD 管"可信的改动能否安全到生产"。
- **部署 vs 发布**：部署替换线上版本，发布决定谁能用上；特性开关正是把两者解耦的手段。
- **持续交付 vs 持续部署**：唯一差别是部署到生产前要不要人按按钮（见 [[CI 与 CD]]）。
- **CI/CD vs [[蓝绿部署与灰度发布]]**：前者是主干，后者是主干末端的部署策略选项。
- **流水线 vs 脚本**：脚本能跑但不保证可复现与可审计，流水线要求声明式、幂等、失败即停。

## 常见误区

- 装好 Jenkins 就等于拥有了 CI/CD。
- 流水线阶段越多，交付质量就越有保障。
- 有了特性开关就不需要回滚方案了，两者可以互相替代。

## 面试速答

> 🎯 CI/CD 主干是集成验证 → 流水线编排 → 质量门禁 → 部署放量，靠不可变制品跨环境晋级、环境差异外置、特性开关解耦部署与发布；测试不牢就别开持续部署，否则等于自动化地把故障推向全量。
