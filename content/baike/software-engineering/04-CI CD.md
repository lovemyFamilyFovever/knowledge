# 04-CI/CD


> 📌 **导航**：本文是 **04-CI/CD** 词条，属于 software-engineering 术语集。相关枢纽：[[01-开发流程]]、[[02-版本控制]]、[[03-代码质量]]、[[04-CI CD]]、[[05-项目管理]]。

本章介绍持续集成和持续交付的核心概念和工具，帮助你理解如何自动化软件构建、测试和部署。

## CI（持续集成）

**一句话定义**：持续集成是一种开发实践，团队频繁地将代码集成到共享仓库，每次集成都通过自动化构建和测试验证。

**通俗类比**：就像团队成员频繁提交作业，老师每次都能快速批改并反馈。

**具体示例**：开发者每天多次将代码推送到主分支，每次推送后自动运行单元测试和构建。

**为什么需要它**：CI早期发现集成问题，减少合并冲突，提高代码质量，加快交付速度。

**与相关术语的对比和区分**：与传统的后期集成相比，CI更频繁，问题发现更早。

## CD（持续交付）

**一句话定义**：持续交付是CI的扩展，确保代码随时可以部署到生产环境，但需要手动触发部署。

**通俗类比**：就像产品已经包装好，随时可以发货，但需要客户下单才发货。

**具体示例**：每次构建都生成可部署的制品，但需要手动批准才能部署到生产环境。

**为什么需要它**：持续交付确保了软件的可发布性，减少了发布风险，提高了发布频率。

**与相关术语的对比和区分**：与持续部署相比，持续交付需要手动触发部署。

## CD（持续部署）

**一句话定义**：持续部署是持续交付的扩展，每次通过测试的代码变更都自动部署到生产环境。

**通俗类比**：就像自动售货机，付款后商品自动出货。

**具体示例**：代码合并到主分支后，自动构建、测试并部署到生产环境。

**为什么需要它**：持续部署实现了完全自动化的交付，加快了反馈循环，提高了效率。

**与相关术语的对比和区分**：与持续交付相比，持续部署是完全自动化的。

## 构建流水线（Pipeline）

**一句话定义**：构建流水线是自动化构建、测试和部署的一系列阶段，每个阶段在前一个阶段成功后执行。

**通俗类比**：就像工厂的生产线，每个工位完成特定任务，产品逐步完成。

**具体示例**：代码提交 → 编译 → 单元测试 → 集成测试 → 部署到测试环境 → 部署到生产环境。

**为什么需要它**：构建流水线自动化了交付流程，确保了质量，减少了人为错误。

**与相关术语的对比和区分**：与简单的构建脚本相比，构建流水线更结构化和可视化。

## 自动化测试

**一句话定义**：自动化测试是使用工具自动执行测试用例，验证软件功能和性能。

**通俗类比**：就像自动阅卷机，快速批改大量试卷。

**具体示例**：使用Selenium进行UI测试，使用JUnit进行单元测试。

**为什么需要它**：自动化测试提高了测试效率，减少了回归错误，支持快速迭代。

**与相关术语的对比和区分**：与手动测试相比，自动化测试更快速、可靠和可重复。

## Jenkins

**一句话定义**：Jenkins是一个开源的自动化服务器，用于构建、测试和部署软件。

**通俗类比**：就像一个智能管家，自动处理各种家务。

**具体示例**：配置Jenkins管道，自动构建Java项目并运行测试。

**为什么需要它**：Jenkins提供了丰富的插件和灵活的配置，支持各种开发环境和工具。

**与相关术语的对比和区分**：与GitHub Actions相比，Jenkins更老牌，功能更丰富，但配置更复杂。

## GitHub Actions

**一句话定义**：GitHub Actions是GitHub提供的CI/CD平台，允许你在GitHub仓库中直接定义自动化工作流。

**通俗类比**：就像智能手机的自动化功能，可以设置各种自动化任务。

**具体示例**：在GitHub仓库中创建`.github/workflows/main.yml`文件，定义构建和测试流程。

**为什么需要它**：GitHub Actions与GitHub深度集成，配置简单，支持多种触发事件。

**与相关术语的对比和区分**：与Jenkins相比，GitHub Actions更轻量级，与GitHub集成更好。

### GitHub Actions YAML示例

```yaml
name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    
    steps:
    - uses: actions/checkout@v2
    
    - name: Setup Node.js
      uses: actions/setup-node@v2
      with:
        node-version: '14'
        
    - name: Install dependencies
      run: npm install
      
    - name: Run tests
      run: npm test
      
    - name: Build
      run: npm run build
      
    - name: Deploy to production
      if: github.ref == 'refs/heads/main'
      run: |
        # 部署脚本
        echo "Deploying to production..."
```

## GitLab CI

**一句话定义**：GitLab CI是GitLab提供的CI/CD平台，通过`.gitlab-ci.yml`文件定义自动化工作流。

**通俗类比**：就像GitLab的内置助手，自动处理构建和部署。

**具体示例**：在GitLab项目中创建`.gitlab-ci.yml`文件，定义构建、测试和部署阶段。

**为什么需要它**：GitLab CI与GitLab深度集成，提供了完整的DevOps平台。

**与相关术语的对比和区分**：与GitHub Actions相比，GitLab CI更侧重于整个DevOps生命周期。

## 制品（Artifact）

**一句话定义**：制品是构建过程产生的可部署输出，如JAR、WAR、Docker镜像等。

**通俗类比**：就像工厂生产的产品，可以分发和使用。

**具体示例**：构建后生成的`app.jar`文件，或Docker镜像`myapp:latest`。

**为什么需要它**：制品标准化了构建输出，便于分发、部署和版本管理。

**与相关术语的对比和区分**：与源代码相比，制品是可执行的，不包含源代码。

## 环境管理

**一句话定义**：环境管理是创建、配置和维护开发、测试、生产等环境的过程。

**通俗类比**：就像管理多个实验室，每个实验室有不同配置和用途。

**具体示例**：使用Docker Compose管理开发环境，使用Kubernetes管理生产环境。

**为什么需要它**：环境管理确保了环境的一致性，减少了“在我机器上能运行”的问题。

**与相关术语的对比和区分**：与基础设施即代码相比，环境管理更关注环境本身。

## 蓝绿部署（Blue-Green）

**一句话定义**：蓝绿部署是使用两个相同生产环境的部署策略，一个活跃（蓝），一个备用（绿），通过切换流量实现零停机部署。

**通俗类比**：就像有两个舞台，一个在演出，一个准备就绪，可以无缝切换。

**具体示例**：新版本部署到绿色环境，测试通过后，将流量从蓝色切换到绿色。

**为什么需要它**：蓝绿部署实现了零停机部署，减少了发布风险，支持快速回滚。

**与相关术语的对比和区分**：与滚动更新相比，蓝绿部署需要双倍资源，但切换更简单。

## 金丝雀发布（Canary）

**一句话定义**：金丝雀发布是逐步将新版本部署给一小部分用户，监控无问题后逐步扩大部署范围的策略。

**通俗类比**：就像煤矿工人用金丝雀检测有毒气体，先让少量用户试用。

**具体示例**：将5%的流量导向新版本，监控错误率，逐步增加到100%。

**为什么需要它**：金丝雀发布减少了发布风险，允许在影响所有用户前发现问题。

**与相关术语的对比和区分**：与蓝绿部署相比，金丝雀发布更渐进，风险更低。

## 滚动更新

**一句话定义**：滚动更新是逐步用新版本替换旧版本的部署策略，确保在任何时候都有部分实例在运行。

**通俗类比**：就像军队换岗，一个士兵接替另一个士兵，确保岗位始终有人。

**具体示例**：在Kubernetes中，滚动更新策略逐步替换Pod。

**为什么需要它**：滚动更新平衡了部署速度和系统可用性，适用于大规模应用。

**与相关术语的对比和区分**：与蓝绿部署相比，滚动更新不需要额外资源，但部署时间更长。

## 特性开关（Feature Flag）

**一句话定义**：特性开关是控制功能是否可见或启用的配置项，允许在不重新部署的情况下启用或禁用功能。

**通俗类比**：就像电灯开关，可以随时打开或关闭。

**具体示例**：使用环境变量或配置服务控制新功能是否对用户可见。

**为什么需要它**：特性开关支持渐进式发布、A/B测试和快速回滚，降低了发布风险。

**与相关术语的对比和区分**：与代码分支相比，特性开关更灵活，不需要代码合并。
