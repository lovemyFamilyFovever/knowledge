# 里程碑与发布计划

> 📌 **导航**：本文是 **里程碑与发布计划** 词条，属 [[05-项目管理]] 子词条。目标度量见 [[OKR与KPI]]，交付流水线见 [[04-CI CD]]。

## 定义

**一句话定义：** 里程碑是项目中标志阶段成果的时间检查点（如 Alpha/Beta/GA）；发布计划是"哪个版本、何时、交付哪些功能"的排布，把多个迭代编排成对用户可交付的一次上线。

**通俗类比：** 里程碑像长途旅行的"重要路牌/加油站"，发布计划像"这一趟到底带哪几件行李、几点发车"。

## 为什么需要它

单看迭代容易"只见树木"——团队忙却不知整体是否朝交付推进。里程碑提供可对外承诺的检查点，让干系人跟踪进度、评估成果；发布计划把优先级、依赖与容量编排到具体版本，协调开发、测试、市场同步，避免"做完一堆但凑不成一次可交付"。

## 核心机制

- **里程碑**：需求确认、设计冻结、Alpha（内部可用）、Beta（外部试用）、RC、GA/正式发布等关键节点；标志"多任务汇聚完成"的可验证事件。
- **发布计划**：从产品待办（见 [[需求梳理与优先级]]）按价值+依赖+容量选范围，映射到若干 Sprint，定发布日期（固定节奏 release train 或按就绪 ship）。
- **版本策略**：语义化版本（MAJOR.MINOR.PATCH）、发布分支/RC、发布说明（changelog）；发布内容与部署方式解耦（见 [[04-CI CD]]）。
- **与进度联动**：里程碑达成用燃尽/燃起趋势预测风险（见 [[燃尽图与燃起图]]）。

## 具体示例

一次 v2.0 发布的编排：

```
里程碑：需求确认 → 设计冻结 → Alpha(内部) → Beta(100客户) → RC → GA
发布范围：登录改造 + 支付重构 + 报表优化（按价值/依赖排序）
发布节奏：每 2 个 Sprint 一个 release train；GA 前锁发布分支跑回归
```

## 何时用与何时不用

- **用**：需对外承诺日期/版本、跨团队协调上线、合规或市场联动（发布会、活动）时——里程碑 + 发布计划是刚需。
- **不用**：纯持续部署、小步快改的产品可弱化"大版本"，用 [[04-CI CD]] 的频繁发布 + 特性开关替代重型发布计划；也别为凑里程碑日期而塞未就绪功能。

## 优劣与代价

✅ 里程碑给全局节奏与承诺、利于干系人协同与风险暴露；发布计划把零散迭代收敛成可交付价值。
✅ 版本化+changelog 让交付可追溯、可回退。
⚠️ 固定里程碑易造成"压哨赶工/降质保日期"或"为凑日期塞半成品"。
⚠️ 大发布集成风险高（批量改动一起上），与"小步发布"取向存在张力。

## 与相关概念的区别

- **里程碑 vs 任务**：里程碑是标志阶段完成的事件点（无工期、看达成），任务是可执行工作项。
- **发布计划 vs Sprint 计划**：发布跨多迭代、定"何时给什么"；Sprint 计划只管单迭代内做什么。
- **发布 vs 部署**：发布=让功能对用户可用（业务事件）；部署=把构建放到环境（技术事件），可用特性开关解耦（见 [[04-CI CD]]、[[蓝绿部署与灰度发布]]）。

## 常见误区

- 里程碑一旦定下日期就绝不能动，只能靠砍质量赶工。
- 发布计划和 Sprint 计划是一回事。
- 部署了就是发布了，用户一定能用上。

## 面试速答

> 🎯 里程碑=标志阶段成果的不可分解时间点(需求确认/Alpha/Beta/RC/GA)，供干系人跟踪与暴露风险；发布计划=把多个迭代按价值+依赖+容量编排成"哪个版本何时给哪些功能"、协调开发测试市场。发布(业务可用)≠部署(技术上线)，可用特性开关解耦；固定日期里程碑防压哨赶工、别塞未就绪功能。
