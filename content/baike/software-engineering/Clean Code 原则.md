# Clean Code 原则

> 📌 **导航**：本文是 **Clean Code 原则** 词条，属于 software-engineering 术语集。相关枢纽：[[01-开发流程]]、[[02-版本控制]]、[[03-代码质量]]、[[04-CI CD]]、[[05-项目管理]]。

## 定义

**一句话定义：** Clean Code 原则是 Robert C. Martin 在《Clean Code》(2008) 中整理的一组实践准则——有意义的命名、短小且只做一件事的函数、少而准的注释、不吞错误的异常处理——目标是让代码**读起来像一篇写得清楚的文章**，因为软件的成本几乎全在改动与阅读，而非初次编写。

**通俗类比：** 两种写法都能跑，就像两种笔记都记下了内容：一种是别人（和三个月后的你）翻开就能照做，另一种需要当场重新推导一遍。Clean Code 选前者。

## 为什么需要它

代码写成后被读的次数远多于被改写的次数，而项目的钱大多花在"改已有的"上：加需求、修 bug、做迁移。糟糕的写法不会报错，只会把每次改动的时间与风险不断加码，直到没人敢动。Clean Code 的主张是把**阅读成本**当成第一优化目标——命名到位、函数小、抽象层次一致，读者就能顺着意图往下走，而不必在脑中重放执行栈。

## 核心机制

- **命名**：名字说明它为什么存在、做什么、怎么用；避免缩写与语境词（`data`、`info`、`tmp`、`handle`）；同概念全库同词。
- **函数**：短小；**只做一件事**；参数越少越好，超过三个应考虑收进对象；不用布尔开关让一个函数做两件事。
- **注释**：注释是"表达失败的补救"——能用代码说清的（改名、提炼函数）就别写注释；该写的是意图、约束与取舍，不要复述代码在做什么。
- **错误处理**：抛异常而非返回 `null` /  magic number；错误路径与主路径分开。
- **边界与对象**：隔离第三方 API，别让它泄漏到业务层；优先不可变与明确的对象，少用继承堆叠。
- **测试**：测试也讲究整洁——一个测试一个概念，断言清晰，快、独立、可重复。

| 主题 | 反面写法 | Clean 写法 |
|---|---|---|
| 命名 | `d = 30` | `elapsed_days = 30` |
| 函数 | 60 行校验 + 计算 + 落库 | 三个各做一件事的函数 |
| 注释 | `// 是否成年` | `is_adult = user.age >= ADULT_AGE` |
| 错误 | 返回 `-1` 表示失败 | 抛出带原因的异常 |

## 具体示例

同一个判断，差别不在功能而在读者要不要停下来想：

```python
def check(u):                                   # 名字不说做什么，魔法数 18 无出处
    if u and u.a > 18: return True
    return False

ADULT_AGE = 18
def is_adult(user):                             # 前置校验用卫语句，主路径只剩一行意图
    return user is not None and user.age > ADULT_AGE
```

## 何时用与何时不用

- **用**：任何会被别人或未来的你改动的代码；团队规范与评审的共同语言；重构时的判断依据。
- **不用**：一次性脚本、探索草稿、原型验证——这些地方整洁的收益还抵不上时间成本；也不要为了"看着 Clean"在上量前就抽出五层抽象，**先让它跑对、再让它清晰、最后才让它通用**。

## 优劣与代价

✅ 显著降低阅读与改动成本，让重构可持续，评审有共识基线。
✅ 不依赖特定语言或框架，迁移性强。
⚠️ 多数规则有例外，机械套用会得到碎片化的微函数与过度抽象，反而更难读。
⚠️ 缺乏强制力：格式能被 linter 管住，"只做一件事"不能，只能靠评审与文化维持。

## 与相关概念的区别

- **Clean Code vs 代码规范**：规范是可自动检查的风格约定（缩进、命名格式），违规工具能拦；Clean Code 关心设计意图，工具看不见。
- **Clean Code vs [[设计原则]]（SOLID/DRY/KISS/YAGNI）**：原则给方向，Clean Code 给到函数与命名粒度的落地手法，两者是同一条链的上下层。
- **Clean Code vs [[代码异味]]**：前者是目标与准则，后者是偏离时的征兆。
- **整洁 vs 简短**：把三行合成一行嵌套表达式通常更短也更难读，Clean 不等于紧凑。

## 常见误区

- 遵循 Clean Code 就是把函数拆得越短越好，越短越高级。
- 代码写得足够整洁，就不需要写测试也不需要再重构了。

## 面试速答

> 🎯 Clean Code（Robert Martin, 2008）= 以"可被轻松阅读与改动"为第一目标的准则：名字说清意图、函数短小且只做一件事、注释解释"为什么"而非"做什么"、抛异常不返 null；多数规则有例外，别为整洁过度抽象。
