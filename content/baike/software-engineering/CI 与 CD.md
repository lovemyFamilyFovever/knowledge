# CI 与 CD

> 📌 **导航**：本文是 **CI 与 CD** 词条，属于 software-engineering 术语集。相关枢纽：[[04-CI CD]]、[[01-开发流程]]、[[蓝绿部署与灰度发布]]、[[构建流水线与 CI-CD 工具]]、[[代码评审]]。

## 定义

**一句话定义：** CI（持续集成）是频繁合码、每次合码都跑自动化构建与测试，让集成问题当天暴露；CD 是它之后的两件事——**持续交付**保证"任何时刻主干都处于可发布状态"，**持续部署**再把发布这一步也自动化掉，中间不需要人来点按钮。

**通俗类比：** CI 像每天练琴并录像回听，错音当场发现；持续交付是随时能上台的曲子；持续部署则是琴房直通音乐厅——不用等经纪人排期。

## 为什么需要它

软件的价值只有到用户手里才算兑现，而"集成"与"发布"这两处正是最常被推迟、又最容易出事的环节。攒两周大合并会把冲突堆成没人敢碰的泥潭；发布靠人工执行手册，就会在深夜、在人手不足时出错。CI 把集成成本从"一周一次的大爆炸"压成"一天多次的小步验证"，CD 则把发布从一次高风险事件变成重复次数极多、因而可被自动化和监控压平的低风险动作。

## 核心机制

| 实践 | 保证什么 | 关键约束 |
|---|---|---|
| CI 持续集成 | 主干随时可构建、测试通过 | 分支活不过一天；构建红灯即停线 |
| 持续交付 CD | 任一刻都可安全发布 | 发布仍需人工审批（合规/时点考量） |
| 持续部署 CD | 变更自动一路到生产 | 必须有测试金字塔 + 特性开关 + 快速回滚兜底 |

三者是**递进关系**：没有可靠的 CI 就谈不上持续交付，没有自动化测试与可回滚的部署策略就绝不该开持续部署。落地形态是一条[[构建流水线与 CI-CD 工具|流水线]]：提交触发 → 构建 → 测试 → 产出可部署[[04-CI CD|制品]] → 逐级晋升环境 → 部署与验证 → 失败回滚。

## 具体示例

```yaml
name: ci
on: { push: { branches: [main] } }
jobs:
  verify:
    steps:
      - { uses: actions/checkout@v4 }
      - run: npm ci                 # 锁文件保证构建可复现
      - run: npm run lint && npm test
      - run: npm run build && npm run package
```

关键在于**顺序即策略**：便宜的检查（格式、单测）放前面，昂贵的（端到端、性能）放后面，任何一步失败都立即中断——CI 的价值不在跑完，而在快速否证。

## 何时用与何时不用

- **用**：只要代码会被多人协作或需要定期发布，CI 就是底线；有合规审批或需要选发布时点，停在持续交付；面向 C 端、变更频繁且已具备自动化测试、灰度与回滚能力时，再上持续部署。
- **别硬上**：单文件脚本、一次性交付物、无自动化测试的老代码——先把测试补到关键路径上，再谈 CD。
- **注意**：流水线本身也要维护；测试不稳定时 CI 会退化成"看运气变绿"的仪式，反而掩盖问题。

## 优劣与代价

✅ 集成与发布风险被切成小段，问题发现时点从"发布前"提前到"提交后几分钟"。
✅ 发布自动化后可重复、可监控、可回滚，深夜发布的人为失误大幅减少。
⚠️ 需要投入构建时长、机器成本与测试资产，慢 CI 会诱发"先合再说"的绕行。
⚠️ 持续部署会把缺陷也自动化推向生产，缺少灰度与回滚时是纯粹的负资产。

## 与相关概念的区别

- **持续交付 vs 持续部署**：区别只在"部署这一步要不要人按按钮"，两者都要求主干随时可发布。
- **CI vs 代码评审**：CI 是机器判定（能不能构建、测试是否通过），[[代码评审]] 是人判定（设计、可读性、意图），互为补位。
- **CI/CD vs [[蓝绿部署与灰度发布]]**：CI/CD 是"把变更安全地推出去"的整条流水线，蓝绿/金丝雀/滚动是流水线末端**部署策略**的具体选项。
- **自动化部署 vs 自动化发布**：前者替换版本，后者还包含按人群逐步放量与观察决策。

## 常见误区

- 有了 CI 就自动等于实现了持续交付。
- 流水线跑通就说明软件已经可以无人值守地上生产。
- 持续部署比持续交付更先进，所以所有团队都该往它演进。

## 面试速答

> 🎯 CI 是频繁合码加每次自动构建测试，把集成问题压到当天；CD 分两层：持续交付保证主干随时可发布但仍由人审批，持续部署连发布也自动化，前提是测试金字塔、灰度与快速回滚到位。
