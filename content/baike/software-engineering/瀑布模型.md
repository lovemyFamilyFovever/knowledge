# 瀑布模型

> 📌 **导航**：本文是 **瀑布模型** 词条，属 [[01-开发流程]] 子词条。现代迭代式方法见 [[敏捷宣言与原则]]、[[Scrum框架]]。

## 定义

**一句话定义：** 瀑布模型是一种线性顺序的软件开发过程模型——需求→设计→实现→验证→维护逐阶段推进，每阶段有明确交付物与评审关口，前一阶段完成（"冻结"）才进入下一阶段，像水往低处流般单向。

**通俗类比：** 像造房子：先画全图纸、再打地基、再砌墙、最后装修，一步完工才进下一步，很少回头改地基。

## 为什么需要它

在需求稳定、变更代价高、合规文档要求强的领域（政府、航空、医疗、外包合同），瀑布带来阶段可计划、进度可度量、交付物清晰、职责边界明确——便于合同验收与风险前置。它是软件工程的"经典基线"，理解它才能看懂后续迭代/增量/敏捷为何要取而代之。

## 核心机制

- **阶段线性序列**：需求分析 → 系统设计 → 编码实现 → 测试验证 → 部署 → 运维，阶段间以文档交接。
- **阶段关口（Stage-Gate）**：每阶段末评审通过才放行，产出物冻结基线，变更走正式变更控制。
- **前置规划**：范围/工期/成本在早期锁定，强调完整的需求规格说明书（SRS）与设计文档。
- **与其他模型的区别**：增量模型分批交付可用版本、螺旋模型按风险驱动多轮迭代、敏捷则短迭代持续反馈（见 [[敏捷宣言与原则]]、[[迭代与回顾]]）。
- **变体**：V 模型把每个开发阶段对应一个测试层级，缓解"测试太晚"。

## 具体示例

需求分析 → 系统设计 → 编码 → 测试 → 部署 → 维护（单向、阶段冻结）：

```
需求 ──评审──▶ 设计 ──评审──▶ 编码 ──评审──▶ 测试 ──▶ 部署 ──▶ 维护
        (每道关口冻结上一阶段交付物，变更需走变更控制委员会)
```

## 何时用与何时不用

- **用**：需求明确且稳定、技术成熟、强监管/需完整文档与验收、一次性交付的大型或安全关键系统。
- **不用**：需求模糊易变、创新/互联网产品、需快速验证市场时——晚发现的重大需求错误会让"回头成本"爆炸，应选迭代式（[[Scrum框架]]、[[看板方法]]）。

## 优劣与代价

✅ 结构清晰、易计划与度量、文档完备、职责与验收边界明确，适合合同制与安全关键场景。
✅ 风险前置（需求/设计阶段早暴露），利于大规模团队协调。
⚠️ 变更成本高、反馈周期长，到测试阶段才暴露问题常代价巨大。
⚠️ "过早冻结需求"易做出"符合文档却不符合用户"的产品；进度看似可控实则末尾风险集中。

## 与相关概念的区别

- **瀑布 vs 敏捷**：线性单阶段大交付 vs 迭代增量小步快跑——见 [[敏捷宣言与原则]]。
- **瀑布 vs 增量**：一次性整体交付 vs 分多个可用版本逐步交付。
- **瀑布 vs 螺旋**：文档驱动顺序推进 vs 风险驱动、每轮评估再走。
- **瀑布 vs V 模型**：V 模型是瀑布的"测试对应"强化版，每阶段配一级验证。

## 常见误区

- 瀑布模型就是"落后、该被淘汰"的方法，没有任何适用场景。
- 选了瀑布就可以完全不理会需求变更，不必走变更控制。
- 瀑布开发到测试阶段才第一次真正"验证"产品，之前都不算。

## 面试速答

> 🎯 瀑布=需求→设计→实现→验证→维护的线性阶段模型，每阶段冻结交付物、关口评审放行、变更走正式控制。适合需求稳定、强文档合规、安全关键的一次性交付；痛点是变更贵、反馈晚、末尾风险集中。与增量/螺旋/敏捷的对立轴是"线性大交付 vs 迭代小步反馈"。
