# 缺陷生命周期与风险管理

> 📌 **导航**：本文是 **缺陷生命周期与风险管理** 词条，属 [[05-项目管理]] 子词条。缺陷的验证手段见 [[单元测试]] 与测试子域。

## 定义

**一句话定义：** 缺陷生命周期是一个 Bug 从发现到关闭的状态流转（新建→确认→分配→修复→验证→关闭）；风险管理是提前识别、评估、应对项目潜在风险以减小负面影响的过程——前者管"已发生的问题"，后者管"可能发生的问题"。

**通俗类比：** 缺陷生命周期像病人就医流程（挂号→确诊→治疗→复诊→出院）；风险管理像出门前看天气、备伞——问题还没发生就先设防。

## 为什么需要它

没有统一 Bug 流转，缺陷会漏修、重复、无人认领或"改了没验就关"。状态机让每个 Bug 有责任人和可追踪路径，保证质量闭环。而项目失败多源于早期没当回事的风险（关键人离职、技术选型踩坑、需求大改），系统化风险管理把"意外"变成"有预案的已知项"。

## 核心机制

- **缺陷状态机**：New→Open(确认有效)→Assigned→Fixed→Retest/Verified→Closed；分支含 Rejected(非缺陷/重复)、Reopened(验证不通过)、Deferred(延后)、按严重级别(Severity)与优先级(Priority)排序。
- **风险流程**：识别→分析(概率×影响打分/排序)→应对策略(规避/转移/减轻/接受)→监控(风险登记册 Risk Register 滚动更新)。
- **风险 vs 问题**：风险=尚未发生、可预防；问题=已发生、要处置（问题常回灌成经验教训，见 [[迭代与回顾]]）。
- **工具承载**：Jira/禅道等跟踪缺陷流转与风险条目；严重度、SLA、回归关联测试。

## 具体示例

```
缺陷流转：New → Open(复现有效) → Assigned → Fixed → Verified → Closed
                                        └→ Rejected(非缺陷)   └→ Reopened(验证失败)
风险登记：[技术]新框架不熟  概率中×影响高 → 减轻：先做技术预研 Spike + 备选方案
```

## 何时用与何时不用

- **用**：任何多人交付都应有缺陷状态机与风险登记册；尤其安全/合规、对外 SLA、复杂集成项目——风险预案和缺陷闭环是质量底线。
- **不用**：别把流程官僚化——单人小项目用简单清单即可，过度定义状态机反而增加维护成本；风险管理也不是写一份表就完，需每个迭代复审更新。

## 优劣与代价

✅ 缺陷闭环保证"发现即被跟踪到验证"，减少漏修与"假修复"；风险前置降低意外与救火。
✅ 严重度/优先级排序让有限精力投到最该修的点。
⚠️ 状态机过重会拖慢处理、产生"填表"负担；指标(缺陷率)可能被 gaming。
⚠️ 风险识别依赖团队视野，易漏"未知的未知"；登记册不更新=形同虚设。

## 与相关概念的区别

- **风险 vs 问题（Issue）**：未来可能发生 vs 已经发生；分别走"应对预案"与"处置"。
- **缺陷 vs 需求**：缺陷=期望行为的偏离；需求=期望具备的功能（见 [[需求梳理与优先级]]）。
- **Severity vs Priority**：严重度=技术影响大小（崩溃/数据错误），优先级=业务排期紧急度，二者可不一致。

## 常见误区

- 开发者改完代码就把 Bug 关闭，不需要测试再验证。
- 严重度高的缺陷一定优先级也最高。
- 风险管理就是项目开始时填一张风险表交差。

## 面试速答

> 🎯 缺陷生命周期=Bug 状态流转(新建→确认→修复→验证→关闭，含 Rejected/Reopened 分支)，按 Severity/Priority 排序、改完必须验证再关。风险管理=识别→评估(概率×影响)→规避/转移/减轻/接受→风险登记册滚动更新。风险是"未发生可预防"、问题是"已发生要处置"。
