# 圈复杂度

> 📌 **导航**：本文是 **圈复杂度** 词条，属于 software-engineering 术语集。相关枢纽：[[01-开发流程]]、[[02-版本控制]]、[[03-代码质量]]、[[04-CI CD]]、[[05-项目管理]]。

## 定义

**一句话定义：** 圈复杂度（Cyclomatic Complexity）是 Thomas McCabe 1976 年提出的代码量化指标，等于控制流图中独立路径的条数，经验法则为"判定节点数 + 1"，用来预测理解与测试这段代码要花多大力气。

**通俗类比：** 像数一段路的岔口：每多一个 if / 循环就多一个岔口，岔口越多，要把所有走法都跑一遍的遍数就越多，认路的成本也越高。

## 为什么需要它

"这段代码太复杂"是主观判断，团队里谁也说服不了谁，于是复杂函数只能靠资深者的直觉来拦。圈复杂度把"复杂"变成一个可计算、可门禁的数字：它直接对应独立路径数，也就对应**最少需要多少条测试用例才能覆盖所有分支**，同时是最早暴露"一个函数想干太多事"的量化信号。有了它，CI 才能对新增代码设阈值，重构才有优先级依据。

## 计算逻辑

- **公式**：V(G) = E − N + 2P（边数 − 节点数 + 2 × 连通分量数），对单个函数 P=1。
- **捷径**：从 1 起计，每个 `if`、`for`、`while`、`case`、`catch`、以及 `&&` / `||` / 三元等短路布尔判定各 +1。
- **常用分档**：1–10 结构简单、随测试覆盖；11–20 复杂、需评审；21–50 风险高、难测难改；>50 不可维护。

| 区间 | 含义 | 建议 |
|---|---|---|
| 1–10 | 可测可维护 | 正常 |
| 11–20 | 一次改动多个分支 | 加评审 |
| 21–50 | 测试组合爆炸 | 安排重构 |
| > 50 | 事实上的黑盒 | 拆分前禁止新增依赖 |

## 具体示例

同一逻辑，判定嵌套与提前返回的 V(G) 都是 4，但后者好读得多；把判定搬进配置表才能真正降下来：

```python
def ship_days(region, vip):          # V(G)=3：+1 起点，region、vip 各一处判定
    if region == "cn":
        return 1 if vip else 3
    return 7

RULES = {("cn", True): 1, ("cn", False): 3}
def ship_days_v2(region, vip):       # V(G)=1：查表兜底
    return RULES.get((region, vip), 7)
```

## 何时用与何时不用

- **用**：CI 给新增/改动代码设增量阈值（radon、gocyclo、Sonar 的 "new code" 门禁）；排序重构候选；反推单元测试最少用例数。
- **不用**：拿它当唯一质量指标——纯查表函数可能很低却仍难懂，一个 V(G)=3 的嵌套三元照样是坏代码；也不要为了刷分把拆出的函数塞满样板，那只是把复杂度挪到了调用点。

## 优劣与代价

✅ 客观、可自动计算、与分支覆盖下限直接挂钩，适合当门禁与优先级排序。
⚠️ 只度量控制流：命名、耦合、抽象层次一概看不见。
⚠️ 阈值一刀切会催生"为过线而拆"的伪重构，指标降了、可读性反而更差。

## 与相关概念的区别

- **圈复杂度 vs 代码行数**：行数只量长度，圈复杂度量分支组合；同样 20 行，线性与嵌套的测试成本差一个量级。
- **圈复杂度 vs 认知复杂度**：后者（SonarSource）额外惩罚嵌套深度与控制结构组合，更贴近阅读体感，但不可由路径数推导。
- **圈复杂度 vs [[代码异味]]**：一个是量化指标，一组是人工可辨的征兆，后者常是前者的成因。

## 常见误区

- 圈复杂度低，就说明这段代码质量合格、不需要重构。
- 只要测试覆盖率够高，圈复杂度是多少都无所谓。

## 面试速答

> 🎯 圈复杂度 = 控制流图独立路径数，V(G)=E−N+2，实操按"判定节点数 +1"估算；它给出分支测试的用例下限，1–10 尚可、>20 就该重构，降它靠卫语句与查表分解。
