# 需求工程

> 📌 **导航**：本文是 **需求工程** 词条，属于 software-engineering 术语集。相关枢纽：[[01-开发流程]]、[[02-版本控制]]、[[03-代码质量]]、[[04-CI CD]]、[[05-项目管理]]。

## 定义

**一句话定义：** 需求工程（Requirements Engineering）是软件工程中系统地获取、分析、记录、验证和管理用户与系统需求的过程，目标是准确理解"要做什么"并达成共识，为设计与实现提供可靠依据。

**通俗类比：** 像盖房子前先跟业主反复确认"要几室几厅、给谁住、预算多少、有哪些硬性要求"，并写成图纸和清单——这步没搞清，后面盖得再快也可能是错的房子。

## 为什么需要它

软件工程里最贵的错误，是"辛辛苦苦做出来一个没人要的东西"。缺陷发现得越晚、修复成本越高，而需求阶段的错正是最上游的错。需求工程的价值就在于把"到底要做什么"尽早问清、写清、验证清并达成共识，从源头减少返工，也为后续测试与追溯提供依据。

## 做法

- **获取（elicitation）**：访谈、问卷、观察、原型、用户故事。
- **分析**：澄清冲突、排定优先级、建模（用例、数据流、原型）。
- **规格说明**：写成需求文档 / SRS、用户故事与验收标准。
- **验证**：评审、原型确认，确保需求正确、完整、可实现。
- **管理**：变更控制、可追溯性（traceability）、版本管理。

| 组成 | 说明 |
|------|------|
| 功能 / 非功能需求 | 做什么 / 约束条件 |
| 获取方法 | 访谈、问卷、原型等 |
| SRS / 用户故事 | 记录与共识载体 |
| 追溯与变更管理 | 需求全生命周期管理 |

## 具体示例

一条用户故事"作为买家，我希望能按价格从低到高排序商品，以便快速找到便宜货"，配上验收标准"当选择升序时，结果按单价递增排列"——它只讲"要什么、为谁、怎么算验收"，不规定用哪种排序算法或技术栈。

## 何时用与何时不用

- **用**：所有软件项目的起点；敏捷里体现为用户故事与验收标准，传统项目写成 SRS；需求频繁变更时尤其需要变更管理。
- **不用**：需求极少、干系人就是开发者本人的自用小工具——可轻量化，但"讲清要什么"这一步不会消失。

## 优劣与代价

✅ 减少返工与误解、对齐各方期望、为测试与追溯提供依据。
✅ 把最上游、最贵的缺陷在早期拦截。
⚠️ 需求难以一次穷尽、会随认知演变。
⚠️ 干系人之间常有冲突，书面需求与真实意图存在差距，变更管理成本高。

## 与相关概念的区别

- **需求 vs 解决方案**：需求讲"做什么 / 为什么"（what/why），方案讲"怎么做"（how）——把技术选型写进需求是常见误区。
- **功能需求 vs 非功能需求**：功能说系统能做什么，非功能说性能 / 安全 / 可用性等质量约束，二者都关键。
- **需求获取 vs 需求管理**：前者是"挖出并写下"，后者是"变更、追溯与达成一致"。

## 常见误区

- 需求就该直接写"用某数据库、某框架实现"，把怎么做一起定了。
- 只要功能需求都满足，性能、安全等非功能需求可有可无。
- 需求评审定稿后就该冻结，尽量不再变动。

## 面试速答

> 🎯 需求工程 = 系统地获取、分析、记录、验证与管理需求，讲清"做什么 / 为什么"并达成共识；分功能与非功能需求，覆盖获取→分析→规格(SRS/用户故事)→验证→变更管理，越早纠错越省。
