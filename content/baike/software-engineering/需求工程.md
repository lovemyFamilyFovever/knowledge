# 需求工程

## 定义

**一句话定义：** 需求工程(Requirements Engineering)是软件工程中系统地获取、分析、记录、验证和管理用户与系统需求的过程,目标是准确理解"要做什么"并达成共识,为设计与实现提供可靠依据。

**通俗类比：** 像盖房子前先跟业主反复确认"要几室几厅、给谁住、预算多少、有哪些硬性要求",并写成图纸和清单(需求文档)——这步没搞清,后面盖得再快也可能是错的房子。

> 多义说明:需求分功能需求(系统做什么)与非功能需求(性能/安全/可用性等约束);过程含获取、分析、规格说明、验证、管理。本文综述。

## 原理与机制

- **需求获取(elicitation):** 访谈、问卷、观察、原型、用户故事。
- **需求分析:** 澄清冲突、排定优先级、建模(用例、数据流、原型)。
- **规格说明(specification):** 写成需求文档 / SRS、用户故事与验收标准。
- **验证(validation):** 评审、原型确认,确保需求正确、完整、可实现。
- **管理:** 变更控制、可追溯性(traceability)、版本管理。

## 关键组成

| 组成 | 说明 |
|------|------|
| 功能 / 非功能需求 | 做什么 / 约束条件 |
| 获取方法 | 访谈、问卷、原型等 |
| 需求规格(SRS/用户故事) | 记录与共识载体 |
| 验证 | 评审与确认 |
| 追溯与变更管理 | 需求全生命周期管理 |

## 应用场景

- 软件开发全周期的起点
- 敏捷的用户故事与验收标准
- 传统 SRS 文档
- 需求变更频繁的迭代管理

## 优点与局限

- 优点:减少返工与误解、对齐各方期望、为测试与追溯提供依据。
- 局限:需求难以一次穷尽(会演变);干系人之间可能冲突;书面需求与真实意图有差距;管理变更成本高。

## 常见误区

- 需求 ≠ 解决方案:需求讲"做什么/为什么",方案讲"怎么做"。
- 需求会演变,需要管理变更,而非一味冻结。
- 非功能需求(性能/安全)同样关键,却常被忽视。
- 需求错误在后期修复代价极高(越早发现越省)。
