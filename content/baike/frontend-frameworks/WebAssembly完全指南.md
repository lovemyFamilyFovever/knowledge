# WebAssembly完全指南


> 📌 **导航**：本文是 **WebAssembly完全指南** 词条，属于 frontend-frameworks 术语集。相关枢纽：[[GraphQL从入门到精通]]、[[WebAssembly完全指南]]、[[Web性能优化]]、[[现代前端工程化完全指南]]。

## 定义

**一句话定义：** WebAssembly（Wasm）是 W3C 标准的、面向基于栈的虚拟机的可移植二进制指令格式，以线性内存加边界检查换取体积小、加载快、执行接近原生且天然沙箱；本页是它的能力索引枢纽，把指令集与内存模型、JS 互操作、WASI 与非浏览器运行时拆成三个子词条，多语言工具链并入基础条、浏览器落地场景在本页内联。

**通俗类比：** 像一种通用集装箱：Rust/C++/Go 是各地工厂，货装成同一规格（.wasm）后，任何带吊机的港口——浏览器 Worker、WASI 命令行、宿主插件位——都能直接卸货运行，不必按港口重新生产；本页是港口导览图，箱里具体装什么在各子词条。

## 为什么需要它

JS 是动态类型，运行时要靠猜测类型与反复去优化来提速，重计算（图像滤镜、编解码、仿真、编辑器内核）无论怎么写都受语言形态限制；原生代码快，却没有一种可移植、可安全嵌入页面的交付形态。Wasm 补的正是这个缺口：编译期把优化做完，交付单一字节码，运行时省掉猜类型那一层，沙箱又是内建的。但它的抽象机不含对象、字符串、GC 与异常，也碰不到 DOM，一切复杂数据都要在边界上手工编排——所以面试真正的考点不是"它快不快"，而是"什么时候值得用、边界怎么跨、离开浏览器怎么办"。这三问分别由下面三个子词条承载，本页只负责把它们串成一条选型主线。

## 核心机制

能力可排成一条主线：**产出字节码 → 装载运行 → 与宿主换数据 → 走出浏览器 → 在页面里落地**，前四段各归子词条，末段与性能账在本页内联。下表负责"有什么、去哪看"，编号项只讲"为什么这样选"。

1. **价值不在"快"而在"可移植的原生"**：编译期优化（`-O3`、LTO、`-msimd128`）留在源语言侧，交付的仍是同一份字节码，浏览器不必理解 Rust 或 C++，只认栈式指令与线性内存；这条分工让内存模型成为硬约束而不是实现细节，展开见 [[Wasm 线性内存与模块结构]]（优化通识见 [[编译优化]]）。
2. **边界上只有数字，复杂数据是双方约定的内存布局**：参数与返回值限四种数值类型，字符串要"4 字节长度头 + UTF-8"、大数组要 allocate/deallocate 配对与批量视图拷贝，或让 wasm-bindgen、Emscripten 生成胶水；跨界调用本身有固定开销，循环必须留在 Wasm 内侧，协议与陷阱归 [[Wasm 与 JavaScript 互操作]]。
3. **换一套授权就能离开浏览器**：DOM 与操作系统 API 都不在 Wasm 能力里，WASI 用能力式模型把宿主愿意给的那部分目录、环境变量与参数显式递进沙箱，未授权即失败；WASI 尚未覆盖的部分由宿主用 Linker 自定义函数补足，机制见 [[WASI 与非浏览器运行时]]。
4. **落地形态收敛为"重计算 + 已有原生库"**：本页内联的像素回路是典型——批量喂进 Wasm 内存、一次调用算完整块、再取回视图交给 canvas；纯 DOM 操作与常规业务逻辑没有收益，性能账要先量再算（见 [[Web性能优化]]·[[JS执行性能]]，绘制侧成本见 [[图形渲染管线]]）。

## 具体示例

原稿 §5 的图像编辑器把整条链路走通了一遍：Rust 侧用 `#[wasm_bindgen]` 暴露一个持有 RGBA 缓冲的编辑器对象，构造时按宽×高×4 预分配，对外只给载入像素、按类型施加滤镜（模糊、亮度、复古色调共用同一入口）与把像素首地址交回 JS 三类方法；实时模式下逐帧把视频画面画进 canvas、`getImageData` 取像素、一次调用完成灰度化、再 `putImageData` 回去。三个细节值得记：像素一直留在 Wasm 内存里以指针交换，每帧只有一次跨界调用，结果靠视图零拷贝读回。CPU 密集的另一路是 Go：编译后经官方 `wasm_exec.js` 实例化、注册成全局函数即可调用蒙特卡洛估 π 这类任务，goroutine 在 Wasm 里仍可用（工具链对照见 [[Wasm 线性内存与模块结构]]）。

## 何时用与何时不用

- **用**：计算密集且数据是数字块（像素、采样、矩阵、顶点）；已有成熟 C/C++/Rust 库要原样搬进页面或边缘进程；需要同一份核心逻辑同时服务浏览器与非浏览器宿主（见 [[WASI 与非浏览器运行时]]）。
- **不用**：交互与 DOM 编排为主、算得少；数据以对象/字符串为主且小量频繁跨边界——胶水与编码成本会吃光收益；团队没有能力承担内存布局与调试成本时，先做 [[JS执行性能]] 与 [[资源加载优化]] 这类更便宜的优化。

## 优劣与代价

✅ 体积小、加载快、执行接近原生，且性能可预测：不受 JS 类型猜测与去优化影响，沙箱与边界检查内建。
✅ 一次编译多处运行：同一字节码覆盖浏览器、Worker、WASI 运行时与嵌入式宿主，多语言生态都能接进来。
⚠️ 边界是手写协议：内存布局、指针生命周期、视图过期都成为应用的责任，出错表现为静默数据错乱。
⚠️ 拿不到全部能力：无 DOM、GC 与异常要靠模块自带运行时，向量化与线程仍受提案范围限制，调试与 profiling 工具链弱于 JS。

## 与相关概念的区别

- **vs [[现代前端工程化完全指南]]**：那边管构建与交付链路，Wasm 只是其中一种可被打包的产物形态；本页管这份产物怎么运行、怎么与页面协作。
- **vs [[Web性能优化]]**：那套是页面整体预算（加载、渲染、脚本），Wasm 是"把某段计算换执行形态"的单点手段，不能替代资源与渲染侧优化。
- **vs [[前端框架核心概念]]**：框架决定组件与渲染时机，Wasm 决定某段计算在哪个抽象机上跑；两者正交，框架侧集成见 [[Next.js全栈开发实战]]。
- **vs TypeScript / Babel 这类"编译到 JS"**：那类产物仍跑在 JS 引擎的语义里；Wasm 换的是指令集与内存模型这一层。

## 常见误区

- 以为 WebAssembly 会取代 JavaScript，它没有 DOM 与网络能力，只能靠导入函数回调宿主。
- 以为把函数改成 Wasm 就一定更快，忽略每帧/每元素一次的跨界调用开销反而可能更慢。
- 以为 Wasm 模块天然安全所以内存操作不必谨慎，越界会 trap 但踩自己的堆区没有任何护栏。

## 面试速答

> 🎯 Wasm 是栈式虚拟机的可移植二进制格式：线性内存加边界检查、只有四种数值类型，靠导出/导入函数与 JS 双向调用，WASI 让它走出浏览器；适用重计算与已有原生库，边界协议是主要代价。

> 🔍 追问：为什么必须有线性内存？——它给出一致且可验证的访存模型，又能被宿主映射成 ArrayBuffer 供两侧直接读写。
> 🔍 追问：JS 字符串怎么传进去？——TextEncoder 编码后按"4 字节小端长度 + 内容"写入，返回指针与长度；或由绑定层代劳。
