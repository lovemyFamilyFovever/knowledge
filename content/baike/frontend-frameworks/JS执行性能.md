# JS执行性能

> 📌 **导航**：[[Web性能优化]] 子词条。

## 定义

**一句话定义：** 让主线程不被长任务占用，使用户交互能在帧预算内得到响应。

**通俗类比：** 单窗口餐厅：一单菜做太久，整队人都卡住。

## 为什么需要它

JS 与渲染共用主线程：一个 500ms 长任务 = 用户点击后肉眼可见的卡顿，INP 直接超标。交互响应的上限由主线程空闲程度决定。

## 核心机制

四个动作，全围绕"别让主线程一次忙太久"：

① **先度量**：Performance 面板 / Long Tasks API 找出长任务是谁、在哪，不盲优化；
② **切**：长任务切小块，块间让出主线程（setTimeout(0)、scheduler.yield、requestIdleCallback 闲时插空）；
③ **移**：CPU 密集（解析、编码、大数组计算）移 Web Worker，主线程只 postMessage 收结果；
④ **延**：非紧急逻辑（埋点上报、预取）放到空闲或可见之后。

## 具体示例

加购按钮卡 800ms：归因到一段同步算价+校验长任务；切块并闲时执行后 INP 从 800ms 降到 120ms。

## 何时用 / 何时不用

- **用**：交互响应慢、存在计算密集逻辑。
- **不用**：主线程已足够空闲（瓶颈可能在网络或渲染，别错治）。

## 优劣与代价

✅ 直接作用于 INP，用户感知最强。
✅ Worker 与调度 API 生态成熟。
⚠️ Worker 通信有序列化成本且不能碰 DOM。
⚠️ 切块粒度需调：过细增加调度开销，过粗仍卡。

## 与相关概念的区别

vs [[CSS渲染性能]]：后者的药是"把变化推到渲染管线后面"，本词条的药是"别让主线程一次忙太久"；二者同治帧率与 INP，作用于同一条管线的不同半段。

## 常见误区

- requestIdleCallback 随处可用（兼容不全，需回退）。
- Web Worker 是免费午餐。
- setTimeout(0) 是精确调度（它只是排入宏任务，让出时机不可控）。

## 面试速答

> 🎯 JS 执行性能 = 保护主线程：度量长任务 → 切块让出、重活移 Worker、非急延后闲时；指标落在 INP。
