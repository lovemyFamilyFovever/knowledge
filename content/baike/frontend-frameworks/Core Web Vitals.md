# Core Web Vitals

> 📌 **导航**：[[Web性能优化]] 子词条。

## 定义

**一句话定义：** Core Web Vitals 是 Google 提出的、衡量真实用户体验的三项场指标：LCP 管加载、INP 管交互响应、CLS 管视觉稳定。

**通俗类比：** 页面的"体温、脉搏、血压"——三项体征，任何一项异常都说明该就医。

## 为什么需要它

实验室指标（如 load 时间）与真实用户在低端机、弱网下的体验严重脱节；行业缺一套统一、可横向比较的场口径，Google 将其与搜索排名挂钩后，"体验"第一次变得可量化、可考核。

## 计算逻辑

- **LCP**：开始加载 → 视口内最大内容块渲染完成的时间，良好 ≤2.5s；慢通常怪大图或渲染阻塞资源。
- **INP**：全页所有交互延迟的高百分位统计（点击到下一帧绘制），良好 ≤200ms；慢怪主线程长任务。2024 年 3 月起正式取代 FID。
- **CLS**：所有意外布局偏移的累计分数，良好 ≤0.1；高怪元素没预留尺寸或异步插内容。

场数据来自真实用户监控（CrUX / RUM），按 **75 分位**评判——保证"四分之三的访问都达标"，不被平均值骗。

## 具体示例

同一页面 Lighthouse 跑 LCP 1.8s，场 75 分位 3.4s：归因发现低端安卓+弱网用户拖了后腿——实验室的理想网络代表不了他们。这就是结论必须看场分位的原因。

## 何时用 / 何时不用

- **用**：作为北极星指标、版本回归红线（性能预算）、SEO 自查。
- **不用**：作为唯一优化目标——为指标"刷分"而牺牲真实业务体验是本末倒置。

## 优劣与代价

✅ 统一语言：产品、前端、SEO 说同一套数字。
✅ 场+分位口径避免被平均值和实验室环境欺骗。
⚠️ 只覆盖体验三面，不能替代转化、留存等业务指标。
⚠️ 场数据依赖真实流量，冷启动站点只能先看实验室指标，结论要打折。

## 与相关概念的区别

- **vs Lighthouse 实验室指标**：lab 是"理想环境体检"，field 是"日常穿戴监测"；互补，但排名与验收看 field。
- **vs RUM**：RUM 是数据采集手段，CWV 是其上的指标定义。

## 常见误区

- Lighthouse 分高，Core Web Vitals 就一定达标。
- FID 仍是现行交互响应指标。
- CLS 只由图片引起。

## 面试速答

> 🎯 CWV = LCP(加载≤2.5s) + INP(交互≤200ms，2024 取代 FID) + CLS(稳定≤0.1)，真实用户数据按 75 分位评判；是 SEO 与体验的共同北极星。
