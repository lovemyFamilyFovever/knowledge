# Next.js全栈开发实战


> 📌 **导航**：本文是 **Next.js全栈开发实战** 词条，属于 frontend-frameworks 术语集。相关枢纽：[[GraphQL从入门到精通]]、[[WebAssembly完全指南]]、[[Web性能优化]]、[[现代前端工程化完全指南]]。

## 定义

**一句话定义：** Next.js 是基于 React 的全栈框架，App Router 用"文件约定"把路由、布局、加载与错误组织成一棵树，并以 React Server Components 为底座统一渲染策略、数据获取与缓存；本页是它的能力索引枢纽，把 App Router 与渲染、RSC 与数据获取、缓存与再验证、中间件与 i18n 拆为子词条，图片字体 / 认证 / 部署 / ORM / SaaS 实战归口既有专条。

**通俗类比：** 像一栋按楼层图纸自动装配的大楼——每层放一块写好的牌子（layout/page/loading），框架据此把"这段工厂预制、那段现浇、哪段住户自装"（SSG/SSR/CSR）分派清楚；本页是电梯导览图，各层详细做法在对应子词条。

## 为什么需要它

React 只给视图层，路由、渲染时机、数据获取、缓存失效、边缘拦截、静态资源优化全要自己拼，且这些决定彼此耦合——选错渲染策略直接影响首屏、SEO 与服务器成本。App Router 用"约定优于配置"把这条耦合链收成连贯心智：默认全在服务器渲染、能留服务器就留服务器，交互才下探到客户端，缓存与再验证一体化。正因这套能力多且各有独立机制，才拆成子词条分别承载，本页负责把它们串成一条选型主线。

## 核心机制

能力可排成一条主线：**路由与渲染 → 组件边界与数据 → 缓存一致性 → 边缘与国际化 → 性能与运维**，前四段各成子词条，末段归口既有 done 专条。下表负责"有什么、去哪看"，编号项只讲"为什么这样选"。

1. **一次渲染决策贯穿全局**：Next.js 所有取舍都源于"这段 UI 该在构建时、请求时还是浏览器里生成"，App Router 把该决策交给每个组件用文件与指令就地声明而非全局配置，选错直接决定首屏、SEO 与服务器成本，展开见 [[Next.js App Router 与渲染策略]]。
2. **服务器优先的组件心智**：page 默认是 Server Component，交互与浏览器 API 才用 `'use client'` 下探到客户端边界，这条"能留服务器就留服务器"是与传统 SPA 的分水岭，机制与序列化边界单列 [[React Server Components 与数据获取]]（React 本体见 [[React深入]]）。
3. **缓存即正确性而非仅性能**：三层缓存把"快"和"陈旧"绑死，改了库不触发再验证用户会读到旧 HTML——revalidatePath/revalidateTag 是一致性开关，这类 bug 比慢更致命，细节归 [[Next.js 缓存与再验证]]。
4. **横切能力一律归口、不重复造**：图片/字体/认证/部署/ORM/SaaS 都不是 Next.js 独有机制，本页只把 [[图片优化]]·[[字体优化]]·[[认证与安全实践]]·[[Docker容器化完全指南]]·[[SaaS产品技术架构]] 等既有 done 专条接进来，避免与 [[Web性能优化]] 家族重复承载。

## 具体示例

一个商品详情页的典型接线：`app/products/[id]/page.tsx` 默认在服务器 `await` 数据库取数（SSR 或配 `revalidate` 走 ISR），首屏图用 `next/image` 带 `priority` 压低 LCP（见 [[图片优化]]），价格与"加入购物车"这类交互被隔离成一个最小的 `'use client'` 按钮嵌进服务端组件，写操作走 Server Action 并在成功后 `revalidatePath('/products')`——渲染、数据、缓存、优化四条线在一次请求里各归其位。

## 何时用与何时不用

- **用**：要 SEO 与首屏性能、要同时掌控静态与动态渲染、要一体化数据/缓存/边缘、React 全栈单体或中小 SaaS（见 [[SaaS产品技术架构]]）。
- **不用**：纯客户端交互后台用 Vite + SPA 更轻；非 React 技术栈；团队尚不熟 RSC 心智时，先从小范围 App Router 页面试点。

## 优劣与代价

✅ 一套约定统一了路由/渲染/数据/缓存/资源优化，服务器优先显著减少客户端 JS 与瀑布请求。
✅ ISR/PPR 让"静态的快"与"动态的新"在同页共存，边缘中间件把重定向/鉴权前移到请求早期。
⚠️ RSC 心智陡：`'use client'` 边界、序列化限制、三层缓存与再验证是常见踩坑点，调试成本高于传统 SPA。
⚠️ 版本迭代快（App Router/PPR 仍在演进），锁版本与跟官方文档的成本要计入（本指南原稿止于 Next.js 14）。

## 与相关概念的区别

- **vs [[前端框架核心概念]]**：那里讲 SSR/SSG/CSR/hydration 的框架无关定义，本页承载 Next.js 用哪些文件与 API 把它们落地。
- **vs [[React深入]]**：React 是视图库、不含路由/服务端渲染/缓存；Next.js 是在其上的全栈框架。
- **vs [[现代前端工程化完全指南]]**：那边管构建/包管理/规范等交付链路，这边管运行期架构。

## 常见误区

- 以为 App Router 下所有组件都能用 useState/useEffect，忽略默认是 Server Component、交互必须先划 `'use client'` 边界。
- 把"用了 Next.js"当成"一定很快"，不做渲染策略选型与图片/字体优化，首屏照样被瀑布请求和大 JS 拖垮。
- 改了数据库却不显式触发再验证，误以为 Next.js 缓存会自动更新，结果用户长期读到旧页面。

## 面试速答

> 🎯 Next.js 以 App Router 文件约定组织路由树、以 RSC 为底座统一渲染/数据/缓存；核心取舍是某段 UI 何时出 HTML、改了数据如何再验证，图片字体认证部署一律归口既有专条。
