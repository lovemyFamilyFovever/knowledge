# WASI 与非浏览器运行时

> 📌 **导航**：本文是 **WASI 与非浏览器运行时** 词条，属于 frontend-frameworks 术语集。相关枢纽：[[WebAssembly完全指南]]。

## 定义

**一句话定义：** WASI（WebAssembly System Interface）是 WebAssembly 的标准化系统接口，让模块不依赖浏览器也能安全访问操作系统能力：模块用导入段声明要什么，宿主按"能力"显式授予哪些目录、环境变量与参数，未授予的一律访问不到，因此同一份 .wasm 可跨运行时、跨操作系统搬。

**通俗类比：** 像给外包工作室发门禁卡：卡上不含工具，只写明"这几间房可进"；屋里做得出同样的成品，但撬不开没授权的门。

## 为什么需要它

Wasm 与外界打交道原本只有一条路：宿主在 importObject 里递函数进来。这很适合浏览器（宿主是 JS，DOM 与网络都在它手里），但想让 Wasm 独立跑成 CLI 工具或插件系统时，每个宿主都自造一套导入函数，"一次编译到处运行"就退化成"一次编译到处重写胶水"。WASI 把时钟、参数、环境变量、标准流与文件描述符标准化成一组约定好的导入。

## 核心机制

三条原则解释了它所有取舍：**能力安全性**（只能访问被明确授予的能力）、**可移植性**（同一份二进制在不同实现里跑）、**沙箱隔离**（每个程序跑在自己的沙箱中）。日常操作上的差别就是下表几种能力的授权方式：

| 能力 | 浏览器里 | WASI 运行时里 |
|---|---|---|
| 参数 / 环境变量 / 标准流 | 无对应概念 | `WasiCtxBuilder` 的 args / env / inherit_stdio |
| 文件系统 | 只能经宿主导入回调 | `std::fs` 可用，但只在 `--dir` 预开的目录内有效 |
| 网络 | 只能经宿主导入回调 | 支持仍有限，靠 WASI Socket 提案扩展（原稿标注实验性） |
| 自定义宿主函数 | importObject 里的 JS 函数 | `Linker::func_wrap` 注册供模块调用 |
| 退出方式 | 返回给 JS 调用方 | 进程退出码（如参数不足时 `exit(1)`） |

- **命令行运行即授权**：目标三元组换成 `wasm32-wasi` 编好之后，`wasmtime run --dir=. --env=RUST_LOG=debug app.wasm input.txt` 里那两个参数就是这次运行的全部能力，`wasmedge --dir=:. ...` 是同构的另一实现。预开之后标准库照常可用（`read_dir` 读元数据、BufReader 逐行处理大文件、`File::create` 写出），未预开则再正常的 `fs::read_to_string` 也失败。
- **嵌入宿主补未标准化的能力**：`Engine` 加载 `Module`，`Linker` 挂上 WASI 后用 `func_wrap("host", "get_system_info", ...)` 追加自定义函数，最后从 `_start` 入口调用——这是把 Wasm 当插件系统时的标准形态。

## 具体示例

一个最短的 WASI 程序把"被拒"与"可用"摆在同一屏：收集 `env::args`，不足就往 stderr 打用法并 `exit(1)`；否则 `fs::read_to_string(filename)` 原样写到 stdout，再读 `RUST_LOG`、用 `SystemTime::now()` 打时间戳。同一份字节码，带 `--dir=.` 正常，去掉它就只有那次读取失败。

## 何时用与何时不用

- **用**：要把一段逻辑做成跨环境插件、CLI 或边缘函数，既要沙箱隔离又能读文件与参数；宿主侧要嵌入不受信任的扩展代码并划定权限。
- **不用**：目标就是页面里的图像处理，浏览器才是唯一宿主（走 importObject 即可，见 [[Wasm 与 JavaScript 互操作]]）；需要稳定网络与完整 POSIX 语义的传统服务进程。

## 优劣与代价

✅ 能力显式授予、未授权即失败，宿主可按最小权限跑第三方编译产物。
✅ 与浏览器共用同一份字节码，差异只在运行时与授权清单。
⚠️ 覆盖面有限：网络等能力仍在提案阶段，实验特性要按运行时与版本核对（原稿标注实验性）。
⚠️ "换台机器就能跑"的前提是两边实现同一套 WASI 版本，跨运行时差异与调试工具链要计入成本。

## 与相关概念的区别

- **vs Node 的 fs / process**：那些是宿主直接暴露的 API，权限等同当前进程；WASI 的每次系统调用都要先出现在被授予的清单里。
- **vs 容器 / 虚拟机**：容器靠内核与命名空间隔离、跑本机架构二进制；WASI 在字节码层裁剪能力，启动与体积代价低得多（隔离手段见 [[容器隔离与内核安全]]）。

## 常见误区

- 以为 WASI 提供完整 POSIX，`File::open` 能打开机器上任意路径。
- 以为模块上了 WASI 就能自己监听端口跑 HTTP 服务，把网络当成已标准化的能力。
- 以为宿主自定义函数只有浏览器那一种写法，非浏览器场景必须先等 WASI 提案落地。

## 面试速答

> 🎯 WASI 把时钟、参数、环境变量、标准流与文件描述符标准化成一组导入契约，宿主按能力显式授予（`--dir`/`--env`），未授权即失败；同一份 .wasm 因此能在 Wasmtime/WasmEdge 与浏览器之间搬。

> 🔍 追问：和 importObject 的本质区别？——同为"宿主填导入"，WASI 把这组导入做成了公共标准。
> 🔍 追问：WASI 没覆盖的能力怎么办？——宿主侧用 Linker 的 func_wrap 注册自定义函数。
