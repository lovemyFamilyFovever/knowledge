# Wasm 线性内存与模块结构

> 📌 **导航**：本文是 **Wasm 线性内存与模块结构** 词条，属于 frontend-frameworks 术语集。相关枢纽：[[WebAssembly完全指南]]。

## 定义

**一句话定义：** WebAssembly 是面向"基于栈的虚拟机"的二进制指令格式（W3C 标准、主流浏览器厂商共同支持）：指令只操作 i32/i64/f32/f64 四种数值类型，数据住在一块可增长的线性内存里，程序以模块为单位按类型/函数/内存/表/导入导出分节声明。

**通俗类比：** 像一台只认识"摞盘子"的极简机器：运算永远是"摞上盘子、把最上面两个拿走换成结果"；盘子架是一整条带编号的传送带，只能按编号伸手取，越界立刻停机。

## 为什么需要它

选栈式而非 x86 那套寄存器式，是为了编码短、免寄存器分配、任何架构都能一致地验证与执行；字节码密度不如原生，但优化不在这一层做——工具链在编译期就把 `-O3`、LTO、SIMD 做完。内存用"连续字节数组 + 显式 load/store"而非复用虚拟地址空间，换来两件事：这段内存能被宿主映射成 ArrayBuffer 供两侧读写，且每个访存点都有天然的边界检查。

## 核心机制

栈式求值没有操作数，一切靠栈：连 `(2 + 3) * 4` 都是五次压栈出栈——压 2、压 3、`i32.add` 弹出两个压回 5、压 4、`i32.mul` 得 20。指令共约 200 条，覆盖算术、比较、控制流与访存，函数签名统一由类型节声明。

- **线性内存**：64KB 为一页，声明给出初始与上限页数（`(memory (export "memory") 1 10)` 即至多 10 页），读写只走 `i32.load` / `i32.store` 并由运行时越界检查，这就是它的安全特性。
- **段结构与实例化**：类型节存签名、函数节存函数体、内存节存内存、表节存间接调用所需的函数引用，导入/导出节对接宿主；实例化即"给齐导入、留下导出"，此后 `exports.add(3, 5)` 与普通调用无异。

三条工具链产出同一份字节码，差别只在胶水由谁生成：

| 源语言 | 目标与工具 | 绑定与构建约定 |
|---|---|---|
| Rust | `wasm32-unknown-unknown` + wasm-pack | `#[wasm_bindgen]`；`crate-type = ["cdylib"]`、release 开 `lto` |
| C++ | Emscripten（emsdk）+ `emcc` | `EMSCRIPTEN_BINDINGS` 注册类与方法；`--bind -O3`、`-msimd128`、`USE_PTHREADS` |
| Go | `GOOS=js GOARCH=wasm` + `go build` | `syscall/js` 注册全局函数；需官方 `wasm_exec.js`，`main` 末尾 `select {}` 保活 |

## 具体示例

一个最小模块把上述结构全用上：从宿主导入 `console.log`（只收一个 i32）、导出 `add`（两个 i32 入一个 i32 出）、再导出一块 1 页内存。宿主 `WebAssembly.instantiate(bytes, { console: { log } })` 后拿到可调用的 `exports.add` 与 `exports.memory`——一块能被 TypedArray 包裹的字节区。

## 何时用与何时不用

- **用**：要精确掌控数据布局与内存复用；要把非 JS 语言的既有库搬进浏览器或另一进程；看中的是可验证、可流式加载、跨架构同一份字节码。
- **不用**：只有几个字符串和对象来回的轻逻辑，边界协议与胶水体积会吃光收益；要直接操作 DOM 的部分必须留在 JS 侧以导入函数回调（见 [[Wasm 与 JavaScript 互操作]]）。

## 优劣与代价

✅ 四种数值类型加显式访存，运行时先流式验证再执行，跳过 JS 猜类型那一层，重计算接近原生（账怎么算见 [[JS执行性能]]）。
✅ 单一字节码承接多条工具链：同一模块既能在浏览器实例化，也能在 WASI 运行时跑（见 [[WASI 与非浏览器运行时]]）。
⚠️ 没有引用类型与托管堆，复杂结构自己编排，还要背自带运行时的体积。
⚠️ 指针与长度全靠约定，越界直接 trap，写错下标则踩坏自己的堆区。

## 与相关概念的区别

- **vs [[编译原理与解释器实现]]·[[编译优化]]**：Wasm 只是"目标格式 + 一台抽象栈机"，前端与各遍优化都在各语言编译期做完。
- **vs x86/ARM 原生码**：不暴露真实寄存器与地址空间，故可验证、可沙箱、可跨架构，但向量化止步于 SIMD 提案那组指令。
- **vs [[内存管理]]**：Wasm 侧没有托管堆，GC 只能由模块自己在线性内存里实现。

## 常见误区

- 以为 WebAssembly 是一门可以像 JS 那样直接写页面业务逻辑的编程语言。
- 以为把 JS 对象或字符串当参数传给导出函数就行，不必处理四种数值类型之外的编码。
- 以为 memory 的 ArrayBuffer 视图一次取好就一直有效，不需要随内存增长重新获取。

## 面试速答

> 🎯 Wasm 是栈式虚拟机的二进制指令格式：约 200 条指令、只有 i32/i64/f32/f64；数据住在 64KB 页、可增长且有上限的线性内存里，显式 load/store 加越界检查；模块按类型/函数/内存/表/导入导出分节。

> 🔍 追问：为什么用栈式而非寄存器式？——编码短、免寄存器分配、验证规则简单。
> 🔍 追问：三条工具链的实质差别？——产物同一，只在绑定层：wasm-bindgen、Emscripten 绑定、Go 的 wasm_exec.js。
