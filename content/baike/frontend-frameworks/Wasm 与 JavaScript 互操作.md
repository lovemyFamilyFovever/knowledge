# Wasm 与 JavaScript 互操作

> 📌 **导航**：本文是 **Wasm 与 JavaScript 互操作** 词条，属于 frontend-frameworks 术语集。相关枢纽：[[WebAssembly完全指南]]。

## 定义

**一句话定义：** Wasm 与 JS 只靠三样东西通信——模块的导出函数、模块的导入函数、一块双方共享的线性内存；能直接传递的只有四种数值类型，所以字符串与数组必须先在内存里按约定排布、再以"指针 + 长度"跨边界，或者交给绑定层生成胶水。

**通俗类比：** 像两国之间没有共用电话线，只有一条传送带：传话得先把信放进某个箱子（写进内存），再告诉对方"几号箱、多长"。

## 为什么需要它

Wasm 的抽象机器刻意不含对象模型、字符串、GC 与异常，为的是能被快速验证、接近原生地执行，于是富类型交互全推到边界上由应用承担。这件事决定成败：跨界一次的固定开销不大，但"每像素调一次""每次写入都重编码一遍"会把重计算省下的时间全吐回去——下面所有模式的共同目标只有一个：把调用次数压到常数级，把数据留在原地。

## 核心机制

两个方向共用一张契约：JS 侧 `WebAssembly.instantiate(bytes, importObject)` 把导入函数递进去、由模块导入段声明签名；导出段声明的名字落在 `instance.exports` 上，可直接 `exports.matrixMultiply(a, b, 100)`。Wasm 侧要取数据、绘图、发请求，一律 `call` 那些导入回来的 JS 函数（先 `call $fetch` 再 `call $render`），因为它自己既没有 DOM 也没有网络栈。

标量之外的复杂数据跨边界只有四条路：

| 传法 | 谁腾内存 | 适用与代价 |
|---|---|---|
| 长度前缀手写 | 调用方挑偏移 | 字符串进出；偏移全靠约定，不写下来就互相踩 |
| 分配器配对 | 模块导出 `allocate`/`deallocate` | 大数组、批量张量；忘记释放即泄漏 |
| 绑定层 | wasm-bindgen / `EMSCRIPTEN_BINDINGS` | 类、结构体、异常都能传；代价是产物体积上升 |
| 共享内存 | 一块 `shared: true` 的 memory | 主线程与 Worker 免复制；竞态要自己管 |

- **视图必须现取**：内存可增长、`memory.buffer` 会变，所以每次读写前按当前 buffer 重建 TypedArray 视图，`deallocate` 之后旧视图更不能再碰。
- **批量是全部理由**：批量 `set` 与逐元素写入的差距是数量级的，同理内层循环要留在 Wasm 内侧，边界上只求一次调用；跨线程时 C++ 侧对应 `-msimd128` 与 `USE_PTHREADS`/`PTHREAD_POOL_SIZE`（内存序的一般模型见 [[线程与同步]]）。

## 具体示例

字符串是最小切片：`TextEncoder` 编码后，把字节长度以小端序写进 4 字节槽、内容紧随其后，返回值即约定好的起始地址，读时反向。指针交换同理——Rust 侧 `#[wasm_bindgen]` 标注的方法只能收整数，所以图像处理器把 RGBA 缓冲留在 Wasm 内存里、只把首地址以 `*const u8` 交回，JS 用 `new Uint8ClampedArray(memory.buffer, ptr, w * h * 4)` 包成视图喂给 `ImageData`。本质都是"数据不动、只传地址"（工具链接口见 [[Wasm 线性内存与模块结构]]）。

## 何时用与何时不用

- **用**：计算密集且数据本身是数字块（像素、采样、矩阵、顶点）——一次搬运、一次调用、内部循环；需要并发时用共享内存把同一块 buffer 递给 Worker。
- **不用**：数据以对象/字符串为主且逐条小量交互，胶水与编码成本高于收益；频繁回调 DOM 的交互逻辑留在 JS 侧更短（页面整体预算见 [[Web性能优化]]）。

## 优劣与代价

✅ 边界契约极小（只有数字与一块内存），所以验证快、执行快，重计算能拿住原生级性能。
✅ 同一份字节码可在浏览器、Worker 与 WASI 运行时之间搬，共享内存让多核利用成为可能（见 [[WASI 与非浏览器运行时]]）。
⚠️ 手工协议是越界之外的第二处踩坑面：偏移重叠、忘记释放、视图过期都表现为静默数据错乱。
⚠️ 绑定层在藏起协议的同时也藏起了成本，容易写出"看起来一行、实际每帧拷一次内存"的代码。

## 与相关概念的区别

- **vs [[JS执行性能]]**：那篇管 JS 自身怎么写不掉帧；本条管计算搬去 Wasm 后边界上多出的那笔账——搬错反而更慢。
- **vs [[内存管理]]**：通用回收策略在那里，这里只有"谁分配、谁释放"的显式配对。

## 常见误区

- 以为 `exports.f(someObject)` 能把 JS 对象直接传进 Wasm。
- 以为跨界调用零成本，于是把内层循环留在 JS 里逐像素调用 Wasm 函数。
- 以为有了 `shared: true` 的内存就自动线程安全，不需要自己安排同步。

## 面试速答

> 🎯 通道只有导出函数、导入函数与一块共享线性内存，跨边界只传四种数值：字符串走"长度头 + UTF-8"，大数组走 allocate + 视图批量 set，Worker 靠 shared memory 免复制；关键是压调用次数、把循环留在 Wasm 里。

> 🔍 追问：为什么字符串不能直接传？——抽象机没有字符串与引用类型，加了会拖慢验证并破坏可移植性。
> 🔍 追问：何时让绑定层代劳？——要传结构体、类实例或异常时用 wasm-bindgen / Emscripten，代价是体积与可读性。
