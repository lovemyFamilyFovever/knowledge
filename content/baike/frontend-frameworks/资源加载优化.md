# 资源加载优化

> 📌 **导航**：[[Web性能优化]] 子词条。

## 定义

**一句话定义：** 在"页面要的东西不变"的前提下，重排和精简资源的获取与执行顺序——关键的先拿、不关键的晚拿、能拆的拆、能懒的懒。

**通俗类比：** 搬家：先运当晚要用的床头物品，家具下单晚点到，别把整栋房子一次扛走。

## 为什么需要它

浏览器默认"文档里先引用谁就先拿谁"，与真实首屏需求错位：字体发现得晚、JS 阻塞渲染、首屏下图与主图抢带宽。默认顺序与真实需求之间的差，就是本词条要填的坑。

## 核心机制

一切手段围绕一个概念——**关键渲染路径**：首屏渲染所需的最短资源链。三个动作：

1. **重排**：preload 告诉浏览器"现在就拿这个"（as 指明类型），preconnect / dns-prefetch 提前建连接，fetchpriority 微调同类资源优先级；
2. **精简**：路由级代码分割（动态 import）只发当前页 JS，Tree Shaking 在构建期删未用导出，压缩减小字节；
3. **延后**：非关键 CSS 异步化，首屏下图 loading="lazy" 或 IntersectionObserver 精确懒加载，prefetch 猜下一页并闲时预取。

```html
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">
<img src="/lazy.jpg" loading="lazy" decoding="async" alt="">
```

上面两行就是实践中最常用的重排与延后手法本身。

## 具体示例

首屏实际只需要主 CSS 和主图，但 head 里还挂三个统计 SDK：SDK 改 async、主图 preload+high、路由动态 import → 首屏资源请求 14 → 4，LCP 随之下降。

## 何时用 / 何时不用

- **用**：首屏资源明显可精简/重排；bundle 随业务膨胀。
- **不用**：资源本身已极小（优化空间小于监控成本）。

## 优劣与代价

✅ 低风险高回报，多数手段可渐进叠加。
✅ 代码分割同时改善可维护性（以路由为单位）。
⚠️ preload 滥用浪费带宽，甚至挤占关键资源。
⚠️ Tree Shaking 依赖 ESM 与 sideEffects 配置正确，配错静默失效。

## 与相关概念的区别

- **preload vs prefetch**：前者"本页必用、立即拿"，后者"下页可能用、闲时拿"；把后者误用成 preload 会挤占本页带宽。
- **代码分割 vs Tree Shaking**：前者"拆开放、按需加载"（运行时），后者"删死代码"（构建期），互补不互替。

## 常见误区

- 什么都 preload 就等于快。
- Tree Shaking 对任何包都自动生效。
- 懒加载一定省流量（首屏图被 lazy 反而拖慢 LCP）。

## 面试速答

> 🎯 资源加载优化 = 缩短关键渲染路径：preload/preconnect 重排、代码分割/Tree Shaking 精简、async/lazy/prefetch 延后；核心是让加载顺序对齐首屏需求。
