# 组件化与微前端

> 📌 **导航**：本文是 **组件化与微前端** 词条，属于 frontend-concepts 术语集。相关枢纽：[[前端框架核心概念]]、[[前端工程化核心概念]]。

## 定义

**一句话定义：** 组件化把一个界面拆成封装了结构 / 样式 / 逻辑、可独立复用与测试的 UI 单元；微前端把同一思想放大到应用级，让多个可独立开发部署的子应用运行时组装成整体——两者是"分而自治、合而呈现"在不同尺度上的同一答案。

**通俗类比：** 组件是乐高积木，微前端是几家用不同模具造出来的积木城，靠统一的接口板（路由激活、样式隔离、共享依赖）拼在一起。

## 为什么需要它

单文件写整页时，改一处怕碰另一处、复用靠复制粘贴。组件化用"封装 + 组合"让 UI 可分头开发、独立测试；当规模再涨到多团队协作、技术栈不一致、要求各自独立上线时，组件级拆分已不够，微前端把边界上移到"可独立部署的子应用"，解的是组织与交付问题。

## 核心机制

- **组件的自治边界是"props 进、事件出"**：父用 props 下发数据、子用回调上抛事件，谁都不直接碰对方内部——这条契约在 React（JSX + children）、Vue（props + slot + emit，见 [[Vue3核心]]）、Angular（@Input/@Output + DI 服务）里换了写法却没换本质。
- **模块化不等于组件化**：模块化拆的是 JS 代码（函数 / 类，见 [[JavaScript 模块化（CommonJS·ES Modules·AMD）]]），组件化拆的是视图；一个组件常跨多个模块，一个模块也可以不含任何组件，别把两个维度混谈。
- **微前端解的是组织与部署，不是渲染性能**：多团队、异构技术栈、独立上线才是它的应用场景——qiankun 按路由激活子应用并做沙箱隔离，Module Federation 在运行时共享依赖（如 react 设 singleton 避免双实例）；小项目上微前端只会把一次构建拆成一堆跨域加载与隔离开销，iframe 是最原始方案但通信与样式隔离最差。

## 具体示例

```jsx
// 组件：props 进、事件出，父不碰子内部
function TodoItem({ text, onToggle }) {
  return <li onClick={onToggle}>{text}</li>;
}
// 微前端：主应用按路由挂载可独立部署的子应用
registerMicroApps([{ name: "vueApp", entry: "//localhost:8081", activeRule: "/vue" }]);
```

## 何时用与何时不用

- **组件化**：几乎所有前端界面都该组件化——判断粒度的标准是"是否有第二处复用、是否能独立测试、是否对应一个可命名的 UI 概念"，三者皆否就别硬拆。
- **微前端**：仅在多团队共编一个大前端、需独立部署或渐进迁移遗留系统时上；单团队单产品用它，成本远大于收益。

## 优劣与代价

✅ 组件提升复用、可测性与并行开发；微前端让各子应用按自己的节奏独立上线、技术栈异构。
✅ 边界即契约，缩小改动的影响面。
⚠️ 过度组件化产出只在一处用、props 层层透传的碎片组件，读起来比一坨还累。
⚠️ 微前端要额外解决样式隔离、全局状态共享、公共依赖去重、路由协调，运行时复杂度显著上升。

## 与相关概念的区别

- **vs [[前端框架核心概念]]**：枢纽讲跨框架的机制总纲与选型表，本条只聚焦"拆分"这一机制在组件 / 应用两个尺度上的落地。
- **vs [[前端路由]]**：微前端的 activeRule 依赖路由寻址，但路由是通用的 URL→视图，本条是跨子应用的编排与隔离。
- **vs [[前端工程化核心概念]]**：Monorepo、包管理那套仓库组织手段常被微前端用到，但那是"代码放哪、怎么构建"，不是运行时组合。

## 常见误区

- 把"拆得越细"当"组件化越好"，产出一堆单次使用、props 深透传的碎片组件。
- 为了微前端而微前端，单团队单产品也上 qiankun，白白背上构建与运行时隔离成本。
- 用全局 CSS 选择器给组件命名，跨组件 / 跨子应用相互污染（作用域隔离判据见 [[CSS 预处理与模块化（Sass·Less·CSS Modules）]]）。

## 面试速答

> 🎯 组件化把界面拆成封装结构/样式/逻辑、props 进事件出的可复用 UI 单元；微前端是同一思想放大到应用级，多团队独立开发部署、运行时按路由（qiankun）或共享依赖（Module Federation）组装，解的是组织与交付而非渲染性能。
