# 前端状态管理

> 📌 **导航**：本文是 **前端状态管理** 词条，属于 frontend-concepts 术语集。相关枢纽：[[前端框架核心概念]]、[[React深入]]、[[Vue3核心]]。

## 定义

**一句话定义：** 前端状态管理是把跨组件共享的数据集中到一处、以可预测的方式修改与订阅的机制，用来终结"同一份数据在多个组件各存一份、改一处漏一处"的失控。

**通俗类比：** 像公司的唯一台账——各部门（组件）不各记小账，都读写同一本，改一次全体同步，不会出现销售改了库存、仓库还按旧数发货。

## 为什么需要它

组件各自持有局部状态时，共享数据只能靠 props 逐层下传（prop drilling）：中间组件不关心这个值却要一路转发，跨分支的组件更是拿不到。集中式 store 把"数据在哪"与"谁要用"解耦，任何组件订阅同一份真相，改一次所有订阅者同步更新。

## 核心机制

- **先问要不要全局，再选怎么全局**：一处用就留组件局部状态（React 的 useState、Vue 的 ref），多处读且必须同步才上全局；介于两者之间的是服务端缓存——数据本属于后端，交给数据层管理，别复制进全局 store 再手写同步。
- **Redux 的价值不是"能存数据"而是"改数据只有一条路"**：单一 store + 派发 action + 纯函数 reducer 把副作用挡在 reducer 外，任何变更可回放、可时间旅行调试；代价是样板多、心智重，数据流越显式越好查也越啰嗦。
- **响应式 store 把"通知谁"交给依赖追踪**：Pinia / MobX 直接改 state，由响应式系统（[[Vue3核心]] 的 Proxy）算出该更新哪些订阅者，写起来像操作普通对象；代价是数据流向不再显式，大团队要靠约定把 mutation 收口。

## 具体示例

```javascript
// Redux：变更 = 派发 action，reducer 必须是纯函数
dispatch({ type: "todo/add", payload: text });
function reducer(state = [], action) {
  return action.type === "todo/add" ? [...state, action.payload] : state;
}
// Pinia：直接改，依赖追踪负责通知订阅者
store.addTodo("学习状态管理"); // action 内 this.todos.push(...)
```

## 何时用与何时不用

- **用**：主题 / 登录态 / 购物车这类"多处读、改了要全同步"的跨组件状态；或需要可回放调试的复杂交互流程。
- **不用**：只在单组件内使用的状态、可从 URL 或 props 派生的值（派生态存两份就会漂移）、以及本质属于后端的数据（交给请求层缓存，见 [[前端构建优化策略]] 的按需加载侧配合）。

## 优劣与代价

✅ 单一数据源消除多副本不一致，订阅更新替代层层透传。
✅ 显式 action（Redux 类）让变更可审计、可撤销，测试友好。
⚠️ 全局 store 是耦合点：字段一改可能波及一片订阅者，命名与分片要提前规划。
⚠️ 引入库有体积与心智成本，小项目用框架自带的 provide/inject 或 Context 往往够。

## 与相关概念的区别

- **vs [[React深入]] 的 Hooks**：useState / useReducer 是组件内的局部状态原语，Context 解决"透传"但不解决"变更可预测"；本条讲的是跨组件的全局数据流方案。
- **vs [[前端框架核心概念]]**：那条是"共享状态"这一维度在三家框架的对照表，本条是这一机制本身的选型判据与两种范式（单向 vs 响应式）。

## 常见误区

- 把任何稍共享的数据都塞进全局 store，组件卸载后状态还在、下次进来读到脏数据。
- 在 reducer 里直接 mutation（`state.push`）破坏不可变约定，视图因引用未变而不更新。
- 混淆"客户端状态"与"服务端缓存"，手写一遍本可交给数据层负责的同步与失效逻辑。

## 面试速答

> 🎯 状态管理解"共享数据怎么流"：先判断是否真需全局，再在单向数据流（Redux，变更走 action、可回放但样板多）与响应式 store（Pinia/MobX，直接改、依赖追踪通知）间取舍；局部态用 useState/ref，别把服务端数据复制进 store。
