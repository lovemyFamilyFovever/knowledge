# 前端构建优化策略

> 📌 **导航**：本文是 **前端构建优化策略** 词条，属于 frontend-concepts 术语集。相关枢纽：[[前端工程化核心概念]]、[[前端工程化]]。

## 定义

**一句话定义：** 构建优化是"产物离开构建机之前"的一切收敛手段：tree shaking 删掉没用的代码、code splitting 把一次下载切成按需的块、压缩与 CDN 缩短传输路径、构建缓存缩短等待——目标是更小更快，不是配置更花哨。

**通俗类比：** 像搬家：先扔掉不要的东西（tree shaking），再分类打包（code splitting），最后选最快的路线（压缩、CDN、构建缓存）——四件事互相独立，漏一件就只有那一件的症状。

## 为什么需要它

用户感知的加载速度直接影响体验与转化，而首屏要下载的字节数与请求数几乎都在构建期定死。构建优化是性能优化的第一道防线：等产物上线再靠运行时补救，能动的空间已经很小。

## 核心机制

| 手段 | 解决什么 | 关键前提 / 做法 | 生效阶段 |
|---|---|---|---|
| Tree Shaking | 未使用代码进包 | 必须 ES Modules；`sideEffects: false`；`lodash-es` 而非整包 `lodash` | 构建期 |
| Code Splitting | 一次下载过大 | 路由级 `React.lazy(() => import(...))`；`cacheGroups` 按 `node_modules` 切 vendor | 构建期 + 运行时按需 |
| 压缩 | 传输体积 | gzip / brotli 在 Nginx 侧开启；JS/CSS minify | 部署期 |
| 构建加速 | CI 与本地等待 | 文件系统缓存；收窄 `resolve.extensions` 与 loader 的 exclude | 构建期 |
| CDN 与产物分析 | 分发路径、"到底谁占体积" | 静态资源挂 CDN；先跑 bundle 分析再决策 | 部署期 / 诊断 |

- **tree shaking 的前提是静态可分析的模块结构**：`import { pick } from "lodash-es"` 能逐符号删除，`import _ from "lodash"` 只能整包进产物；能力来自 ES Modules 的编译期声明（语义见 [[JavaScript 模块化（CommonJS·ES Modules·AMD）]]），依赖是 CommonJS 时再激进的配置也摇不动。
- **拆包不是越多越好**：更多块换来按需加载，也换来更多请求与更差的缓存命中——公共模块一变，引用它的块哈希全失效，所以 `cacheGroups` 粒度要跟发版节奏对齐，而 `[contenthash]` 的作用正是让未变动块留住缓存。
- **顺序要"先量再改"**：bundle 分析先定位体积来源，再决定删依赖、拆路由还是换格式；传输与渲染侧的收益不在本条口径内。

## 具体示例

```javascript
// 1. 依赖侧：可摇 vs 整包
import { pick } from "lodash-es";   // ✅ 只进用到的函数
import _ from "lodash";             // ❌ 整库入包
// package.json: { "sideEffects": false }
// 2. 路由级拆包
const Home = React.lazy(() => import("./pages/Home"));
// 3. vendor 切分与构建缓存（Webpack）
optimization: { splitChunks: { chunks: "all", cacheGroups: {
  vendor: { test: /[\\/]node_modules[\\/]/, name: "vendors", chunks: "all" } } } },
cache: { type: "filesystem" },
// 4. 传输与诊断：Nginx 开 gzip/brotli；npx webpack-bundle-analyzer stats.json
```

## 何时用与何时不用

- **用**：首屏包体积已成瓶颈（有 bundle 分析图作证）、构建时间拖累 CI、或路由间代码重合度低可按路由切块。
- **不用**：产物只有几十 KB 的小站（拆包的请求成本可能反而更慢）；瓶颈在服务端响应或渲染时，继续压构建只是原地打转。

## 优劣与代价

✅ 构建期收益一次配置长期有效，且不动业务代码结构。
✅ "先分析再优化"的路径可复述，能避免为优化而优化的配置膨胀。
⚠️ 过度拆块会把下载变成请求风暴，并让缓存收益打折。
⚠️ `sideEffects` 声明错了会把真正需要的样式当副作用删掉，这类 bug 只在生产构建复现。

## 与相关概念的区别

- **vs [[资源加载优化]]**：本条在构建期定下字节数与块数，那条决定这些字节到达浏览器后怎么排优先级，两段互补不可替代。
- **vs [[代码规范与转换工具链（Babel · ESLint · PostCSS）]]**：转译为兼容性服务，优化为体积与速度服务；同一份 polyfill 既是前者的产物也是后者的成本。

## 常见误区

- 以为用了 Vite 或 Webpack 就自动 tree shaking，不看依赖是否满足 ESM 与副作用声明。
- 把拆包当万能药，切出几十个小块后才发现瓶颈是一张未压缩的图。
- 只在开发模式验证优化效果，而开发与生产构建的产物口径根本不同。

## 面试速答

> 🎯 构建优化四条独立线：tree shaking（要 ESM + sideEffects 声明）、code splitting（路由级 import 加 vendor cacheGroup）、传输压缩（gzip/brotli + CDN）、构建缓存（filesystem）。先分析再动手。
