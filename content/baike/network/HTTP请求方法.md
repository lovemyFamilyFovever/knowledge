# HTTP请求方法

> 📌 **导航**：本文是 **HTTP请求方法** 词条，由 [[HTTP协议]] 拆分而来。

## 定义

**一句话定义：** HTTP 方法是请求报文里声明"对资源做什么操作"的动词——GET 取、POST 建、PUT 全量替换、PATCH 部分更新、DELETE 删，配合 HEAD / OPTIONS，并以"安全"与"幂等"两个属性约束其语义。

**通俗类比：** 像对图书馆的书下指令：GET 是查阅不动原书、POST 是交一本新书、PUT 是整本替换、PATCH 是只改几页、DELETE 是从架上撤下。

## 为什么需要它

REST 风格用"统一资源 + 方法"表达意图。方法选得对，缓存、鉴权、日志、网关与浏览器 CORS 预检才能按语义正确处理——比如 GET 可缓存、POST 不可、OPTIONS 供预检。

## 核心机制

- **GET：** 读资源，安全且幂等，参数在 URL、可缓存。
- **POST：** 创建 / 提交，非幂等非安全（重复提交可能建多条）。
- **PUT：** 对目标 URI 全量替换，幂等（多次结果一致）。
- **PATCH：** 部分更新，通常非幂等。
- **DELETE：** 删除，幂等（删多次终态相同）。
- **HEAD / OPTIONS：** HEAD 只要响应头（探活 / 校验）、OPTIONS 查询支持的动词、供 CORS 预检。

| 方法 | 安全 | 幂等 | 典型用途 |
|---|---|---|---|
| GET | 是 | 是 | 查询 |
| POST | 否 | 否 | 创建 |
| PUT | 否 | 是 | 全量替换 |
| PATCH | 否 | 否 | 部分更新 |
| DELETE | 否 | 是 | 删除 |

## 具体示例

只改用户邮箱应发 `PATCH /users/1 {"email":"..."}`；若误用只带 email 的 PUT，会把 phone 等字段清空（PUT 是全量替换）。重复点"提交订单"用 POST 会建多单，须靠 [[幂等性]] 令牌去重。

## 何时用与何时不用

- **用：** 设计 RESTful API、判断可缓存性与副作用时，按语义选方法。
- **不用：** 非 CRUD 的复杂动作（如"支付"）可 POST 到子资源；别用 GET 传敏感数据（会进 URL 与日志）。

## 优劣与代价

✅ 语义清晰，利于缓存、鉴权、中间件与文档按动词自动化处理。
⚠️ 幂等 / 安全是"约定"、须后端真正保证；浏览器表单原生只有 GET / POST，PUT / DELETE 常需经 fetch / AJAX 或 method override。

## 与相关概念的区别

vs 幂等（[[幂等性]]）：幂等是"执行多次 = 一次"的性质，方法语义只是建议如何满足它；vs [[HTTP 状态码]]：方法表达"要做什么"、状态码表达"做得怎样"。

## 常见误区

- GET 和 POST 没有本质区别，可以随便用。
- PUT 和 PATCH 都是更新、完全一样。
- 方法声明了幂等，后端就一定幂等。
