# TCP粘包与拆包

> 📌 **导航**：本文是 **TCP粘包与拆包** 词条，由 [[TCP深入]] 拆分而来。

## 定义

**一句话定义：** TCP 是面向字节流的协议、没有消息边界，应用层多次 send 的数据可能被合并（粘包）或拆分（拆包）后到达，须由应用层用定长 / 分隔符 / 长度前缀等方式自行分帧。

**通俗类比：** 像把几封信塞进同一根管道连续流出：对方可能一次收到三封拼在一起（粘包），也可能一封信被切成两半分两次到（拆包）——管道只保证"字节按序到"，不保证"一封一封到"。

## 为什么需要它

TCP 的交付单位是字节流而非报文，它只保证有序可靠、不保留 send 的边界。凡是有"消息"语义的协议都必须自己划边界，否则接收方无法从流里正确切出一条条消息。

## 核心机制

- **定长：** 每条消息固定长度、不足补齐；简单，但可能浪费或受最大长度限制。
- **分隔符：** 用特殊字符（如 \r\n）划界；正文若含该字符必须转义（HTTP 头部即按 CRLF 分行）。
- **长度前缀（最常用）：** 帧头写明 body 长度，按长度精确读满一条，兼顾效率与灵活。
- **对比 UDP：** UDP 是数据报、天然保留消息边界，无粘包问题。

## 具体示例

自定义长连接协议普遍用"魔术 + 版本 + 类型 + 长度 + body"的帧头：先读满固定长度的 header、取出 length，再按 length 读满 body 才算一条完整消息——这就是长度前缀法，从根上解决粘包 / 拆包。

## 何时用与何时不用

- **用：** 基于 TCP 的私有 / 长连接协议、RPC 帧、聊天消息流等任何"多消息连续收发"场景。
- **不用：** 请求-响应式短连接（如普通单请求 HTTP）边界天然清晰；用 HTTP / WebSocket 时框架已处理分帧，无需自造。

## 优劣与代价

✅ 长度前缀 / 定长实现简单、解析高效，是绝大多数私有协议的默认做法。
⚠️ 分隔符法遇正文含分隔符需转义、易错；协议缺版本 / 长度字段会让后续演进困难。

## 与相关概念的区别

vs [[用户数据报协议]]：UDP 面向数据报、有消息边界，本文问题只出现在 TCP 字节流上；vs [[WebSocket]]：WebSocket 在 TCP 之上补了帧边界与消息语义，正是为免应用层自造分帧而生。

## 常见误区

- TCP 每次 send 对应接收端一次 recv、消息边界自动保留。
- 粘包是 TCP 的 bug、升级内核就能解决。
- 只有 TCP 有粘包问题，UDP 也一样的说法不成立（UDP 有边界）。

## 面试速答

> 🎯 粘包 / 拆包根源是 TCP 面向字节流、无消息边界：接收端把多次 send 看成连续字节流。分帧靠定长、分隔符（需转义）、长度前缀（最常用：读满 header 再按 length 读 body）；UDP 有边界不受此扰，WebSocket 在 TCP 上补了帧语义。
