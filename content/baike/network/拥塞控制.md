# 拥塞控制


> 📌 **导航**：本文是 **拥塞控制** 词条，属于 network 术语集。相关枢纽：[[DNS深入解析]]、[[TCP深入]]、[[网络基础]]。

## 定义

**一句话定义：** 拥塞控制（Congestion Control）是网络（尤其 TCP）为防止过多数据注入导致路由器过载、丢包甚至"拥塞崩溃"，而动态调节发送速率的一套机制，目标是在避免雪崩的同时最大化吞吐。

**通俗类比：** 像高速公路的车流调控——车太多会堵死，于是用匝道信号灯（限速）控制上路车辆；一旦某路段拥堵（丢包）就减少放行，疏通后再逐步增加，避免整条路瘫痪。

> 多义说明：拥塞控制（全局，防网络过载）≠ 流量控制（点对点，防接收方缓冲溢出、靠滑动窗口）；二者常配合使用。本文讲拥塞控制。

## 为什么需要它

网络中间的路由器与链路缓冲是有限的。若所有发送方都尽力灌数据，会同时把网络塞满 → 丢包 → 重传 → 更塞，最终"拥塞崩溃"、吞吐趋零。拥塞控制让每个 TCP 主动试探、退避、收敛，共享带宽而不冲垮网络。

## 核心机制

- **拥塞信号：** 传统上以丢包（和 / 或 RTT 时延上升）作为网络拥塞的信号。
- **拥塞窗口 cwnd：** 由发送方维护，与接收窗口 rwnd 取较小值决定实际可发送量。
- **Reno 经典四阶段：** 慢启动（cwnd 从 1 MSS 起指数翻倍，直到阈值 ssthresh）→ 拥塞避免（每 RTT 线性加 1、谨慎逼近容量）→ 收到 3 个重复 ACK 触发快重传 + 快恢复（窗口减半后继续，不回到慢启动）→ 超时丢包则 ssthresh 减半、重回慢启动。
- **现代算法：** CUBIC（Linux 默认，窗口按三次函数随时间增长）、BBR（Google，基于带宽与时延建模、而非仅看丢包）。

## 具体示例

Reno：cwnd 在慢启动阶段指数增到 ssthresh 后转拥塞避免线性增；此时连续收到 3 个重复 ACK，判定丢 1 包 → 快重传、把 cwnd 与 ssthresh 约减半后继续线性恢复，而不像超时那样退回慢启动——这正是快恢复"温和退避"的价值。

## 何时用与何时不用

- **用：** TCP 数据传输、文件下载与流媒体、跨广域网传输、数据中心网络（DCTCP）、结合 UDP 的实时算法（GCC、QUIC 的拥塞控制）。
- **不用（选型反面）：** 强实时 / 低延迟场景不宜用激进的增窗算法（波动大）；BBR 在以丢包为常态的无线 / 高带宽时延链路上优于 Reno/CUBIC，反之优质内网 BBR 可能过于保守。

## 优劣与代价

✅ 防止拥塞崩溃、公平共享带宽、提升整体吞吐与稳定性。
⚠️ 基于丢包的算法在高带宽高时延链路上效率低；有缓冲膨胀（bufferbloat）问题；多流公平性与算法调优复杂。

## 与相关概念的区别

vs 流量控制：流量控制用 rwnd（接收窗口）防接收方缓冲溢出，拥塞控制用 cwnd 防网络过载，发送窗口 = min(rwnd, cwnd)；vs [[滑动窗口]]：滑动窗口是可靠传输 / 流量控制的机制骨架，拥塞控制是在其上给 cwnd 套的"动态调速器"。

## 常见误区

- 拥塞控制和流量控制是一回事。
- 只要丢包就一定是网络拥塞。
- 慢启动阶段拥塞窗口是线性增长的。

## 面试速答

> 🎯 TCP 拥塞控制 = 用 cwnd 动态调发送速率防拥塞崩溃：慢启动（指数）→ 拥塞避免（线性，ssthresh 分界）→ 快重传/快恢复（3 重复 ACK 温和减半）→ 超时回慢启动；现代有 CUBIC、BBR（带宽+时延建模），与滑动窗口里的 rwnd 是两回事。
