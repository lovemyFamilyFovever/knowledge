# 缓存策略


> 📌 **导航**：本文是 **缓存策略** 词条，属于 web-backend 术语集。相关枢纽：[[Web框架对比]]、[[缓存策略]]、[[认证与安全实践]]。

## 定义

**一句话定义：** 缓存是把常用数据存在快速访问位置，避免重复计算或查询的技术。

**通俗类比：** 缓存就像把常用的书放在书桌上——不用每次都去书架（数据库）找，直接从桌面（缓存）拿。

## 为什么需要它

数据获取存在成本阶梯：内存纳秒、本地磁盘毫秒、跨网络与聚合计算十毫秒级，而多数读请求命中的是同一小撮热数据。缓存就是把重复的昂贵读换成便宜读。代价是从此同一份数据有两个副本，一致性问题被正式引入系统。

## 核心机制

- **层级**：浏览器缓存 → CDN → 应用缓存（Redis/Memcached）→ 数据库。越靠前越快、越难精确控制失效。
- **HTTP 缓存**：强缓存 `Cache-Control: max-age=3600`（旧写法 `Expires`）在有效期内根本不发请求；协商缓存带 `If-None-Match: <Etag>` 或 `If-Modified-Since` 问一句，未变则回 `304` 只发头。
- **读写姿势**：Cache Aside 最通用——读时先查缓存，未命中回源并回填；写时先更新 DB、再删缓存。Read/Write Through 让缓存层代理 DB 写，一致性要求高时用；Write Behind 异步批量落库，写多读少且可容忍丢数据时用。
- **失效与淘汰**：TTL 到期 + LRU/LFU 容量淘汰；命中率与新鲜度互相拉扯。
- **三类事故**：穿透（查不存在的 key，每次都回源）→ 缓存空值配短 TTL，或布隆过滤器先拦非法 ID；击穿（热点 key 过期瞬间被打穿）→ 互斥锁/singleflight 只放一个请求回源，或逻辑过期 + 后台刷新；雪崩（大批 key 同时过期或缓存实例宕）→ TTL 加随机抖动、多级缓存、高可用与熔断限流（见 [[限流]]）。

## 具体示例

用户资料接口：`get_user` 先 `redis.get("user:<id>")`，命中直接返回；未命中查 DB 后 `setex("user:<id>", 3600, ...)` 回填。写操作只更新 DB 并 `delete` 该 key，而不是"更新缓存"——避免并发写下旧值覆盖新值。若出现扫描式的 `user:<不存在 id>` 请求，就给不存在的 ID 也写一个 60 秒空值，再叠一层布隆过滤器。

## 何时用与何时不用

- **用**：读多写少、能容忍短暂陈旧、计算昂贵（聚合/渲染）、静态资源与可缓存响应。
- **不用**：强一致场景（余额扣减、库存扣到最后一步）、写多读少、数据本就在内存里、用缓存掩盖真实瓶颈——该加索引时加缓存只是延后爆炸（见 [[Web框架对比]]）。

## 优劣与代价

✅ 延迟与 DB 负载同时下降，是水平扩容的第一选择，投入产出比通常最高。
⚠️ 引入第二真相：一致性窗口、双写失败、失效风暴都成了新问题。
⚠️ 运维成本：容量规划、热 key 与大 key、缓存实例宕机后的雪崩放大。

## 与相关概念的区别

- **缓存 vs 索引**：索引加速同一份数据的查询路径、不复制数据，因此不必谈失效；缓存复制数据到更快介质，必须设计失效。
- **缓存 vs 消息队列**：队列传递"将要发生的事"，缓存存放"已经算出的结果"（见 [[消息队列（Message Queue）]]）。
- **本地缓存 vs 分布式缓存**：本地进程内最快但各副本不一致、随进程消失；集中式可共享与统一失效，但多一跳网络（见 [[Redis深入]]、[[分布式缓存]]）。

## 常见误区

- 更新数据时应先删缓存再写数据库，这样绝不会读到脏数据。
- 缓存穿透、击穿、雪崩是同一个问题的三种叫法。
- 命中率越高越好，把 TTL 设得尽量长就是优化。
