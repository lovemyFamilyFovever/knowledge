# 移动开发概览


> 📌 **导航**：本文是 **移动开发概览** 词条，属于 mobile 术语集。相关枢纽：[[移动开发概览]]。

## 定义

**一句话定义：** 移动开发是为手机和平板（iOS、Android）构建应用程序的技术领域，核心命题是怎么在两套平台约束下用合理成本交付可用的原生体验。

**通俗类比：** 像给两个装修规范不同的楼盘做同一套餐厅——可以各请一支施工队（原生）、可以让一家家具厂出两套适配（跨平台）、也可以把餐厅搬进公共大厅（H5/小程序），每种省法各有各的付法。

## 为什么需要它

双平台并存让"谁来写、复用多少"变成组织结构问题：两套原生团队成本翻倍，纯 Web 体验受限，跨平台框架正是这条成本曲线的中间解。移动端还叠了硬件差异与 OS 沙箱限制（后台、权限、耗电、商店审核），所以选型本质是在体验、成本、迭代速度三角里取一个点。

## 核心机制

| 方式 | 技术 | 优点 | 缺点 |
|---|---|---|---|
| 原生 iOS | Swift/ObjC | 性能与体验最佳 | 只覆盖 iOS |
| 原生 Android | Kotlin/Java | 性能最好 | 只覆盖 Android |
| 跨平台 | Flutter/RN | 一套代码两端用 | 性能与包体略逊 |
| H5 混合 | Vue/React + WebView | 开发快、可热更新 | 交互体验差 |
| 小程序 | 微信/支付宝 DSL | 无需安装、有流量入口 | 能力受平台限制 |

- **Flutter**：Dart 语言 + 自绘引擎（Skia/Impeller），不依赖原生控件，两端像素一致；热重载提效。
- **React Native**：JS 编写、渲染到真实原生控件；旧架构靠 Bridge 异步序列化通信，新架构用 JSI/TurboModules 直连原生。
- **移动端六座山**：适配（尺寸/像素密度/安全区）、性能（列表虚拟化、图片复用）、网络（弱网重试、离线缓存）、电量（后台受系统节制）、存储（配额与清理）、权限（最小化 + 动态申请）。
- **工程共性**：签名与出包、CI/CD 与多渠道、灰度发布与崩溃监控（Crash/ANR）、性能预算；Android 还要额外消化碎片化（厂商 ROM 与系统版本分布）。

## 具体示例

电商 App 常见切法：营销与内容页频繁改版，走 H5 或小程序以躲开审核；下单、支付、相册与生物识别走原生或 Flutter；两侧用统一路由与账号体系衔接。发版路径也是成本的一部分：iOS 需 $99/年开发者账号、Xcode Archive → App Store Connect → 人工审核（数天量级）；Android 为一次性 $25、签名 AAB → Play Console，通常数小时（均为政策项，以官方为准）。

## 何时用与何时不用

- **用原生**：硬件密集（相机/蓝牙/传感器）、重度动画与图形、对首帧与卡顿敏感。
- **用跨平台**：团队小、两端功能高度重合、UI 以列表表单为主、要快速验证。
- **不用**：单端诉求硬上跨平台（调试成本反升）；把复杂手势或视频编辑塞进 WebView；用热更新绕过审核做功能剧变——会被下架。

## 优劣与代价

✅ 跨平台一份代码两端跑，功能一致性与人力成本最优；H5/小程序迭代最快。
⚠️ 抽象层要交税：包体内置引擎、桥接时延、新 OS API 常得等框架适配。
⚠️ 二进制不可热更换，任何"快"都要预留审核缓冲；灰度与回滚必须自己设计。

## 与相关概念的区别

- **vs 前端 Web**：Web 是同一个运行时、缓存策略可控；移动端面对两套 OS 沙箱、审核流程与硬件权限（见 [[Web性能优化]]）。
- **vs H5**：H5 跑在 WebView，可即时更新但受渲染与手势限制；原生装在设备上由商店分发。
- **vs 小程序**：小程序不是网页，而是平台自有 DSL 运行时 + 受限原生能力集，"无需安装"来自宿主 App 的分发。

## 常见误区

- 跨平台框架就是套一层 WebView，性能必然和 H5 一个水平。
- 移动适配主要是把屏幕尺寸做成响应式，剩下的交给系统。
- 热更新和 Web 发版一样自由，改功能不必等商店审核。

## 面试速答

> 🎯 选型即原生/跨平台/H5/小程序四选一，落地要过适配、弱网、电量、权限与商店审核五关。
> 🔍 追问：Flutter 自绘与 RN 用原生控件，性能代价分别在哪？
