# HMAC 与校验和


> 📌 **导航**：本文是 **HMAC 与校验和** 词条，属于 security 术语集。归口枢纽：[[哈希算法篇]]；底层摘要族见 [[密码学哈希函数（MD5 · SHA-1 · SHA-256 · SHA-512）]]。

## 定义

**一句话定义：** HMAC 是"带密钥的哈希"(基于哈希的消息认证码)，只有持钥者算得出，因此同时证明消息未被篡改与发送方身份；校验和(CRC、因特网和数)是不设防的错误检测码，只回答"传输有没有出噪声"——两者都是"证明消息没变"，安全强度差着量级，本条合并管理这条光谱。

**通俗类比：** 普通哈希像公开模具铸的封条，谁都能铸一条一模一样贴上去；HMAC 像只有你和银行各有半套纹章的钢印火漆，伪造者没有印模；校验和则像快递面单上的重量核对——防的是搬运丢包，不防专业调包。

## 为什么需要它

裸哈希只保证完整性：攻击者改了报文，可以顺手重算摘要替换分发渠道里的旧值，接收方照样"校验通过"。要回答"这条消息确实来自持钥的对端"，就得把密钥混进计算——这是 HMAC 的位置。而 TCP/IP 首部、磁盘块、zip 里的 CRC 面对的是随机比特翻转而非对手，用得起一行的校验和，没必要上密码学哈希。分不清这两层，就会出现"用 MD5 验签名"或"给首部校验和提安全要求"两类事故。

## 核心机制

一条光谱三档，先对号再选型：

| 机制 | 带密钥 | 防谁 | 典型场景 |
|------|--------|------|----------|
| 普通哈希 | 否 | 只防无意损坏 | 发布镜像旁挂 sha256 值 |
| HMAC | 是(共享密钥) | 防无钥者伪造 | API 签名、JWT HS256、Webhook |
| 校验和(CRC/和数) | 否 | 防噪声不误防对手 | 网卡/首部校验、压缩包 CRC |

- **HMAC 不是 hash(key||msg)**：标准构造对密钥做 ipad/opad 两次填充、嵌套两层压缩函数哈希，正是这个嵌套挡住了 [[密码学哈希函数（MD5 · SHA-1 · SHA-256 · SHA-512）]] 一节所述的长度扩展攻击；底层摘要可换(SHA-1 已弃用，实践用 SHA-256，即 HMAC-SHA256)。
- **验证必须常量时间比较**：比签名值不能用短路相等判断，否则逐字节时序差能远程猜签名；签发/验签共用一个强随机密钥，密钥泄露即全员可伪造——这是它与 [[数字签名]](私钥签、公钥验)最大的运维差异。
- **校验和的"sum"常混用成泛称**：`sha256sum`/`md5sum` 命令名里的 "sum" 是密码学摘要，而网卡的 one's complement 和数与 CRC-32 是检错码：后者线性可解，随手即可造出同校验值的碰撞，绝不能拿来当防篡改依据。

## 具体示例

开放 API 常见约定：请求方把 method、路径、时间戳、随机串与请求体按规范拼接，用共享密钥跑 HMAC-SHA256，hex 结果放签名头；服务方重算并做常量时间比对，同时用时间戳窗口+nonce 集合挡重放。JWT 的 HS256 签名段即对 header.payload 两段做 HMAC-SHA256(见 [[OAuth 与 JWT]])；下载页标 sha256 让用户防镜像站调包，而 TCP 首部 16 位和数只负责链路噪声，二者同屏出现时别混为一谈。

## 何时用与何时不用

- **用 HMAC**：信道不可信但双方可共享密钥——内部服务互调、第三方回调验签、会话令牌签名。
- **改用 [[数字签名]]**：需要"只有我方能签、人人可验"的不可否认性，或非对称体系([[公钥基础设施]])。
- **别用**：别用裸哈希替代 HMAC 做认证；别把 CRC/和数当完整性防线；别把 HMAC 当加密——它不隐藏内容，保密要靠 [[对称加密与非对称加密]]。

## 优劣与代价

✅ HMAC 极便宜：一次底层哈希约两遍压缩即可，适合高频请求签名与嵌入式端。
✅ 与哈希算法解耦，摘要换代(SHA-1 到 SHA-256)不动协议骨架。
⚠️ 共享密钥双向可见：任何一端泄露即可伪造全部消息，无法做公开验证与不可否认，规模化分发是痛点。
⚠️ 校验和零安全属性，把"校验通过"播报成"防篡改"是经典事故源。

## 与相关概念的区别

- **vs [[密码学哈希函数（MD5 · SHA-1 · SHA-256 · SHA-512）]]**：那族是无密钥的摘要原料，HMAC 是给它配密钥的使用法。
- **vs [[数字签名]]**：签名用非对称密钥对，可公开验证、具不可否认性；HMAC 对称、便宜、双方同权。
- **vs CRC/和数类检错码**：检错码防噪声、线性可伪造；HMAC 防对手、依赖密钥保密。
- **vs [[加盐哈希与口令存储]]**：那是对"低熵输入(口令)"的慢哈希防护，HMAC 处理的是"消息+共享密钥"，问题不同。

## 常见误区

- 给文件附上哈希值就能防篡改，因为攻击者算不出同样的摘要。
- HMAC 是一种加密算法，消息签了名内容也就保密了。
- 报文通过了 CRC/首部校验和，说明它没有被恶意修改过。

## 面试速答

> 🎯 HMAC=带密钥的哈希，嵌套 ipad/opad 两层压缩函数、挡住长度扩展，同时证完整性与持钥者身份，用于 API 签名与 JWT HS256；校验和(CRC/和数)只防噪声不防对手；要公开验证与不可否认则升格为非对称的数字签名。
