# 认证与授权篇


> 📌 **导航**：本文是 **认证与授权篇** 词条，属于 security 术语集。相关枢纽：[[公钥基础设施]]、[[密码学基础篇]]、[[零信任安全架构]]。

认证（Authentication）回答"你是谁"，授权（Authorization）回答"你能做什么"。本篇将带你理解 OAuth 2.0、JWT、Session、SSO 等核心概念，以及如何构建安全的身份验证系统。

---

## OAuth 2.0

**一句话定义（大白话）**
OAuth 2.0 是一种授权框架，允许第三方应用在用户授权下访问其资源，而无需暴露密码。

**通俗类比（生活场景）**
像酒店房卡：你给朋友一张临时房卡，他只能进你的房间（授权范围），不能进酒店其他地方，而且房卡可以随时注销。

**具体示例（代码、命令或操作场景）**
```
OAuth 2.0 授权码流程（最安全）：

1. 用户访问第三方应用 → 重定向到授权服务器
   GET /authorize?response_type=code&client_id=APP_ID&redirect_uri=CALLBACK

2. 用户登录并授权
   用户确认"允许访问你的相册"

3. 授权服务器返回授权码
   GET /callback?code=AUTH_CODE

4. 第三方应用用授权码换取访问令牌
   POST /token
   grant_type=authorization_code&code=AUTH_CODE&client_secret=SECRET

5. 第三方应用携带访问令牌访问资源
   GET /api/photos
   Authorization: Bearer ACCESS_TOKEN
```

**为什么需要它（解决什么问题）**
第三方登录（微信登录、Google 登录）、API 访问授权、开放平台。避免用户把密码分享给第三方。

**与相关术语的对比和区分**
- OAuth 2.0 是授权协议，不是认证协议
- OpenID Connect 在 OAuth 2.0 上增加了身份认证层
- JWT 是 OAuth 2.0 中常用的令牌格式

## JWT（JSON Web Token）

**一句话定义（大白话）**
JWT 是一种自包含的令牌格式，包含头部、载荷和签名三部分，可以在各方之间安全地传递声明。

**通俗类比（生活场景）**
像一张防伪身份证：上面有你的信息（载荷），有签发机关盖章（签名），任何人拿到都能验证真伪，但不能篡改。

**具体示例（代码、命令或操作场景）**
```python
import jwt
from datetime import datetime, timedelta

# JWT 结构：Header.Payload.Signature

# 生成 JWT
payload = {
    "user_id": 12345,
    "username": "zhangsan",
    "role": "admin",
    "exp": datetime.utcnow() + timedelta(hours=1)  # 1小时过期
}
secret_key = "your-secret-key"
token = jwt.encode(payload, secret_key, algorithm="HS256")
print(token)  # 类似: eyJhbGciOiJIUzI1NiIs...

# 验证 JWT
try:
    decoded = jwt.decode(token, secret_key, algorithms=["HS256"])
    print(f"用户: {decoded['username']}")
except jwt.ExpiredSignatureError:
    print("令牌已过期")
except jwt.InvalidTokenError:
    print("无效令牌")

# JWT 三部分（Base64 编码）：
# Header: {"alg": "HS256", "typ": "JWT"}
# Payload: {"user_id": 12345, "username": "zhangsan", ...}
# Signature: HMAC-SHA256(base64(header) + "." + base64(payload), secret)
```

**为什么需要它（解决什么问题）**
无状态认证、微服务间通信、API 认证。服务器无需存储 Session，令牌自包含所有信息。

**与相关术语的对比和区分**
- JWT vs Session：JWT 无状态，Session 有状态
- JWT vs 不透明令牌：JWT 可解析，不透明令牌不可解析
- JWT 过期后需要刷新机制（Refresh Token）

## Session

**一句话定义（大白话）**
Session 是服务器端存储的用户会话状态，通过 Session ID（通常存在 Cookie 中）来识别用户。

**通俗类比（生活场景）**
像餐厅的叫号器：你取号（Session ID），服务员根据号码找到你的点餐单（Session 数据）。

**具体示例（代码、命令或操作场景）**
```python
# Flask Session 示例
from flask import Flask, session

app = Flask(__name__)
app.secret_key = 'super-secret-key'

@app.route('/login', methods=['POST'])
def login():
    username = request.form['username']
    session['username'] = username  # 存入 Session
    session['role'] = 'admin'
    return '登录成功'

@app.route('/profile')
def profile():
    if 'username' in session:
        return f'欢迎回来，{session["username"]}'
    return '请先登录'

@app.route('/logout')
def logout():
    session.clear()  # 清除 Session
    return '已退出'
```

**为什么需要它（解决什么问题）**
保持用户登录状态、购物车、个性化设置。HTTP 是无协议的，Session 让服务器"记住"用户。

**与相关术语的对比和区分**
- Session vs Cookie：Session 存服务器，Cookie 存客户端
- Session vs JWT：Session 有状态需服务端存储，JWT 无状态
- Session 需要处理并发和分布式场景下的共享问题

## Cookie

**一句话定义（大白话）**
Cookie 是存储在浏览器中的小型文本数据，每次请求时自动发送到服务器。

**通俗类比（生活场景）**
像超市的会员卡：你每次去超市都带着（自动发送），收银员读取卡号（数据）就知道你是谁。

**具体示例（代码、命令或操作场景）**
```python
# 设置 Cookie
response = set_cookie('user_id', '12345', max_age=3600)
response.set_cookie('session_token', 'abc123', httponly=True, secure=True)

# 读取 Cookie
user_id = request.cookies.get('user_id')

# JavaScript 读取（非 HttpOnly）
document.cookie  # "user_id=12345; session_token=abc123"

# Cookie 属性
# HttpOnly: 防止 JavaScript 读取（防 XSS）
# Secure: 仅通过 HTTPS 发送
# SameSite: 防止 CSRF（Strict/Lax/None）
```

**为什么需要它（解决什么问题）**
保持登录状态、记住用户偏好、跟踪用户行为。是 Web 应用状态管理的基础。

**与相关术语的对比和区分**
- Cookie vs localStorage：Cookie 随请求发送，localStorage 不会
- Cookie vs Session：Cookie 是客户端存储机制，Session 是服务端
- Cookie 大小限制 4KB，不能存储敏感信息

## SSO 单点登录（Single Sign-On）

**一句话定义（大白话）**
SSO 让用户只需登录一次，就能访问多个相互信任的应用系统。

**通俗类比（生活场景）**
像校园一卡通：用一张卡就能进宿舍、图书馆、食堂，无需每处都刷不同的卡。

**具体示例（代码、命令或操作场景）**
```
SSO 工作流程（基于 CAS）：

1. 用户访问应用 A → 重定向到 SSO 登录中心
   GET https://sso.example.com/login?service=https://app-a.com/callback

2. 用户在 SSO 中心登录
   输入用户名密码 → 验证通过

3. SSO 中心返回票据（Ticket）
   GET https://app-a.com/callback?ticket=ST-12345

4. 应用 A 验证票据
   GET https://sso.example.com/validate?ticket=ST-12345&service=https://app-a.com/callback

5. 用户访问应用 B → 重定向到 SSO 中心
   SSO 中心发现已登录 → 直接返回票据，无需再次登录
```

**为什么需要它（解决什么问题）**
企业内部多系统统一登录、减少密码疲劳、提升用户体验和安全性。

**与相关术语的对比和区分**
- SSO vs OAuth：SSO 关注统一登录，OAuth 关注授权
- SSO vs OpenID Connect：OIDC 是 SSO 的一种实现标准
- SSO 需要所有系统信任同一身份提供商（IdP）

## RBAC（Role-Based Access Control）

**一句话定义（大白话）**
RBAC 是基于角色的访问控制，用户被分配角色，角色拥有权限，用户通过角色获得权限。

**通俗类比（生活场景）**
像公司职位体系：员工（用户）被任命为经理（角色），经理拥有审批权限（权限）。离职或调岗时只需调整角色。

**具体示例（代码、命令或操作场景）**
```python
# RBAC 模型示例
class RBAC:
    def __init__(self):
        self.roles = {
            "admin": ["create", "read", "update", "delete"],
            "editor": ["create", "read", "update"],
            "viewer": ["read"]
        }
        self.user_roles = {}  # user_id -> role

    def assign_role(self, user_id, role):
        self.user_roles[user_id] = role

    def check_permission(self, user_id, action):
        role = self.user_roles.get(user_id)
        if role and action in self.roles.get(role, []):
            return True
        return False

# 使用
rbac = RBAC()
rbac.assign_role("user_001", "editor")
print(rbac.check_permission("user_001", "create"))  # True
print(rbac.check_permission("user_001", "delete"))  # False
```

**为什么需要它（解决什么问题）**
权限管理、最小权限原则、职责分离。简化权限管理，避免直接给用户分配权限。

**与相关术语的对比和区分**
- RBAC vs ABAC：RBAC 基于角色，ABAC 基于属性
- RBAC vs ACL：RBAC 间接授权，ACL 直接授权
- RBAC 适合组织结构清晰的系统

---

## ABAC（Attribute-Based Access Control）

**一句话定义（大白话）**
ABAC 是基于属性的访问控制，根据用户属性、资源属性、环境属性等组合条件来决定是否授权。

**通俗类比（生活场景）**
像机场安检：检查你的身份（用户属性）、目的地（资源属性）、时间（环境属性）等多个因素决定是否放行。

**具体示例（代码、命令或操作场景）**
```python
# ABAC 策略示例
class ABACPolicy:
    def evaluate(self, user, resource, environment):
        # 用户属性：角色、部门、安全级别
        # 资源属性：所有者、敏感度、类型
        # 环境属性：时间、IP、设备

        # 策略：只有文档所有者且在工作时间内才能编辑
        if (resource['owner'] == user['id'] and
            environment['hour'] >= 9 and
            environment['hour'] <= 18):
            return True
        return False

# 使用
policy = ABACPolicy()
user = {"id": "user_001", "role": "developer", "department": "engineering"}
resource = {"owner": "user_001", "sensitivity": "high", "type": "document"}
environment = {"hour": 14, "ip": "192.168.1.1", "device": "laptop"}

print(policy.evaluate(user, resource, environment))  # True
```

**为什么需要它（解决什么问题）**
细粒度权限控制、动态授权、复杂业务场景。RBAC 无法处理的场景可用 ABAC。

**与相关术语的对比和区分**
- ABAC vs RBAC：ABAC 更灵活但更复杂
- ABAC 适合云原生、零信任架构
- ABAC 策略通常用 XACML 或 Cedar 语言编写

## API Key

**一句话定义（大白话）**
API Key 是一个唯一的字符串标识符，用于识别和验证 API 调用者的身份。

**通俗类比（生活场景）**
像图书馆的借书证号码：图书馆通过这个号码知道是谁在借书，可以记录和限制。

**具体示例（代码、命令或操作场景）**
```python
# 生成 API Key
import secrets
api_key = secrets.token_urlsafe(32)
print(api_key)  # 类似: dGhpcyBpcyBhIHNlY3JldCBrZXk

# 使用 API Key（放在 Header 或 Query 中）
import requests

# 方式1：Header
headers = {"X-API-Key": "my-api-key-123"}
response = requests.get("https://api.example.com/data", headers=headers)

# 方式2：Query Parameter
response = requests.get("https://api.example.com/data?api_key=my-api-key-123")

# FastAPI 验证 API Key
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()

@app.get("/data")
async def get_data(x_api_key: str = Header(...)):
    if x_api_key != "valid-api-key":
        raise HTTPException(status_code=403, detail="Invalid API Key")
    return {"data": "sensitive information"}
```

**为什么需要它（解决什么问题）**
API 访问控制、调用频率限制、使用统计、身份识别。

**与相关术语的对比和区分**
- API Key vs JWT：API Key 是静态标识，JWT 是动态令牌
- API Key vs OAuth：API Key 简单，OAuth 功能更丰富
- API Key 适合服务端调用，不适合浏览器端

## Basic Auth（Basic Authentication）

**一句话定义（大白话）**
Basic Auth 是最简单的 HTTP 认证方式，将用户名:密码进行 Base64 编码后放在 Authorization 头中。

**通俗类比（生活场景）**
像用明信片寄密码：虽然编码了（Base64），但任何人都能解码，必须配合 HTTPS 使用。

**具体示例（代码、命令或操作场景）**
```bash
# curl 使用 Basic Auth
curl -u username:password https://api.example.com/data
# 等价于
curl -H "Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=" https://api.example.com/data

# Base64 解码
echo "dXNlcm5hbWU6cGFzc3dvcmQ=" | base64 -d
# 输出: username:password
```

```python
# Python requests
from requests.auth import HTTPBasicAuth
response = requests.get("https://api.example.com/data", auth=HTTPBasicAuth("user", "pass"))
```

**为什么需要它（解决什么问题）**
简单 API 认证、内部系统。优点是实现简单，缺点是安全性低。

**与相关术语的对比和区分**
- Basic Auth vs Bearer Token：Basic Auth 传密码，Bearer 传令牌
- Basic Auth 必须配合 HTTPS，否则密码裸奔
- 不推荐用于生产环境，优先选择 OAuth 或 JWT

## Bearer Token

**一句话定义（大白话）**
Bearer Token 是一种令牌，持有者（Bearer）就能访问资源，无需额外证明身份。

**通俗类比（生活场景）**
像现金：谁拿到现金就能花，不需要证明身份。所以必须安全保管。

**具体示例（代码、命令或操作场景）**
```bash
# 使用 Bearer Token 访问 API
curl -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..." https://api.example.com/data

# Token 通常通过 OAuth 2.0 或登录接口获取
curl -X POST https://auth.example.com/token \
  -d "grant_type=client_credentials" \
  -d "client_id=app_id" \
  -d "client_secret=app_secret"
# 响应: {"access_token": "eyJhbGci...", "token_type": "Bearer", "expires_in": 3600}
```

```python
# Python 使用 Bearer Token
headers = {"Authorization": "Bearer " + access_token}
response = requests.get("https://api.example.com/data", headers=headers)
```

**为什么需要它（解决什么问题）**
API 认证、微服务间通信、OAuth 2.0 的标准令牌类型。

**与相关术语的对比和区分**
- Bearer Token vs Basic Auth：Bearer 更安全（令牌可撤销、有过期时间）
- Bearer Token vs API Key：Bearer 通常通过 OAuth 流程获取
- Bearer Token 必须通过 HTTPS 传输

## OpenID Connect（OIDC）

**一句话定义（大白话）**
OIDC 是基于 OAuth 2.0 的身份认证层，让用户证明"我是谁"，而不仅仅是"我有什么权限"。

**通俗类比（生活场景）**
像身份证 + 驾照：OAuth 2.0 只告诉你有驾照（授权），OIDC 还告诉你身份证号和姓名（身份）。

**具体示例（代码、命令或操作场景）**
```
OIDC 流程（简化）：

1. 客户端重定向到 OIDC Provider
   GET /authorize?response_type=code&scope=openid profile email&client_id=APP_ID

2. 用户登录授权

3. 返回授权码

4. 用授权码换取 Token（包含 ID Token）
   POST /token
   响应: {
     "access_token": "...",
     "id_token": "eyJhbGciOiJSUzI1NiIs...",  // JWT 格式
     "token_type": "Bearer"
   }

5. ID Token 包含用户身份信息
   {
     "sub": "user_12345",
     "name": "张三",
     "email": "zhangsan@example.com",
     "email_verified": true
   }
```

**为什么需要它（解决什么问题）**
标准化身份认证、社交登录（Google、Microsoft）、企业单点登录。

**与相关术语的对比和区分**
- OIDC vs OAuth 2.0：OIDC 增加了身份认证层
- OIDC vs SAML：OIDC 更现代、轻量，适合移动端
- OIDC 的 ID Token 是 JWT 格式

## MFA 多因素认证（Multi-Factor Authentication）

**一句话定义（大白话）**
MFA 要求用户使用两种或以上不同类型的凭证来验证身份，通常是"你知道的"+"你拥有的"。

**通俗类比（生活场景）**
像银行取款：需要银行卡（你拥有的）+ 密码（你知道的），两者缺一不可。

**具体示例（代码、命令或操作场景）**
```
MFA 因素类型：
1. 知识因素（Something You Know）：密码、PIN、安全问题
2. 持有因素（Something You Have）：手机、硬件令牌、智能卡
3. 生物因素（Something You Are）：指纹、面部、虹膜

TOTP（基于时间的一次性密码）流程：
1. 用户注册时扫描二维码，获取种子密钥
2. 客户端和服务器都用种子密钥 + 当前时间生成6位数验证码
3. 每30秒刷新一次
4. 用户输入验证码完成验证
```

```python
# 生成 TOTP
import pyotp

# 生成密钥
secret = pyotp.random_base32()
print(f"密钥: {secret}")

# 创建 TOTP 对象
totp = pyotp.TOTP(secret)

# 生成当前验证码
current_otp = totp.now()
print(f"当前验证码: {current_otp}")

# 验证用户输入的验证码
is_valid = totp.verify(user_input)
print(f"验证结果: {is_valid}")
```

**为什么需要它（解决什么问题）**
防止密码泄露导致的账户被盗，大幅提升安全性。银行、邮箱、重要系统都应启用。

**与相关术语的对比和区分**
- MFA vs 2FA：2FA 是 MFA 的子集，严格要求两种因素
- MFA vs 密码管理：MFA 是额外安全层，不替代密码管理
- TOTP vs SMS 验证码：TOTP 离线可用，更安全
