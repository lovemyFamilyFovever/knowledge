# 供应链安全


> 📌 **导航**：本文是 **供应链安全** 词条，属于 security 术语集。相关枢纽：[[公钥基础设施]]、[[密码学基础篇]]、[[零信任安全架构]]。

## 定义

**一句话定义：** 供应链安全(Software Supply Chain Security)保护的是软件从源代码到部署的整条链路——源代码、第三方依赖、构建系统、制品仓库、分发与更新通道;任一环节被污染,攻击就会随正品抵达全部下游。

**通俗类比：** 像食品安全——不必逐家攻破餐厅(目标系统),只要污染上游的一批食用油(依赖包)或一辆送货车(构建机),几千家餐厅就会把问题菜端给所有食客。

## 为什么需要它

现代应用里自己写的代码只占一小部分,大部分是引入的依赖,攻击面因此从"你的代码"转移到"你信任的所有上游"。投毒一次即命中海量下游,投入产出比远高于逐个攻破目标——这是它成为主流攻击路径的原因,也决定了防守必须覆盖构建与分发环节,而不只是扫一遍自家源码。

## 核心机制

- **源代码:** 恶意提交、伪造贡献者身份 → 分支保护与代码评审、提交签名(如 `git commit -S`)、最小权限 CI Token。
- **依赖包:** 仿冒包(typosquatting)、维护者账号被劫持后发布恶意版本、深层传递依赖 → 锁定版本与哈希(lockfile)、私有镜像源、`pip audit` / `npm audit` / Snyk 扫已知漏洞、新版本延迟升级。
- **构建:** 构建机与 runner 被污染 → 构建隔离(不给不可信 runner 发密钥)、可复现构建。
- **制品:** 镜像或包被替换 → 制品签名与校验(Cosign / Notary)、私有仓库准入控制。
- **分发与更新:** 自动更新通道本身就是攻击通道 → 更新包强制签名,并用 SBOM 备出事时定位影响面。

SBOM(软件物料清单)列出软件中所有组件与依赖,主流格式有 SPDX 与 CycloneDX;它的价值集中在事后——漏洞爆出时能立刻回答"谁用到了它"。

## 具体示例

传递依赖决定杀伤半径:漏洞不在你的代码里,而在你依赖的库所依赖的库里(Log4Shell 一类事件就让全行业被迫重扫),而 SBOM 正是把这种重扫从"翻仓库猜"变成"查表"。投毒侧最常见的路径是抢注同名包,或接管久未维护的包后发一个版本号略高的恶意版本,等下游自动升级上门。

## 何时用与何时不用

- **该做:** 任何对外交付的软件、带自动更新通道的客户端、由 CI/CD 掌握发布权的项目——锁依赖、扫漏洞、签制品是底线三件事。
- **别指望:** 只跑一次漏洞扫描(它只覆盖已知 CVE,拦不住仿冒包与被劫持的维护者);只扫自家源码;把 CI Token 配成管理员权限。

## 优劣与代价

✅ 杠杆极高:一处签名、一处版本锁定,保护的是全部下游。
✅ SBOM 让事故响应从猜测变成查表,显著缩短影响面判定时间。
⚠️ 全链路改造成本高:可复现构建、私有镜像、构建隔离都要真金白银的工程投入。
⚠️ 工具链变多会拖慢开发节奏;签名密钥本身升级为新的高价值目标,需 KMS/HSM 托管。

## 与相关概念的区别

- **vs 传统应用安全:** 应用安全看"你写的代码",供应链安全看"你引入的一切",包括谁签的字、哪台机器构建的。
- **vs [[中间人攻击]]:** MITM 在传输通道上劫持;供应链投毒在上游就把脏东西塞进正品,连传输过程都是真货。
- **vs [[零信任安全架构]]:** 零信任是"不默认信任任何一方"的原则,供应链安全是它在构建与分发这条链路上的具体落地。

## 常见误区

- 依赖漏洞扫描通过了,供应链就是安全的。
- 只要自己不写有漏洞的代码,第三方包出事与我无关。
- SBOM 只是合规文档,对防攻击没有实际作用。
