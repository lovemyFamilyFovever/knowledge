# 密码学实用指南


> 📌 **导航**：本文是 **密码学实用指南** 词条，属于 security 术语集。相关枢纽：[[公钥基础设施]]、[[密码学基础篇]]、[[零信任安全架构]]。

## 定义

**一句话定义：** 密码学实用指南是把"该用哪个算法、怎么组合才对"落成一套选型规则:对称加密管批量数据、非对称管密钥交换与签名、哈希管摘要与口令,再由 TLS 与 PKI 把它们串成可部署的体系。

**通俗类比：** 像装修水电手册:电(AES)负责干活,变压器(非对称)负责把高压安全降成能用的电压,水表(哈希)只走数不还原;手册的价值不在讲电磁原理,而在告诉你"哪个位置用哪个件、千万别装反"。

## 为什么需要它

密码学事故几乎从来不是"算法被攻破",而是"用错了地方或参数":拿 ECB 模式加密结构化数据、同一把密钥又加密又签名、把哈希当成可逆加密、自己实现随机数发生器。工程上需要一份按场景直接给答案的清单,让不熟悉数学的人也能组装出正确方案——这一层手册存在的意义就在这里。

## 做法

先按职责挑算法,再按合规与性能微调:

| 算法 | 类型 | 密钥长度 | 用途与特点 |
|------|------|----------|-----------|
| AES-128/256 | 对称 | 128/256 bit | 最常用,批量数据加密 |
| ChaCha20 | 对称(流密码) | 256 bit | 移动端友好,TLS 常用 |
| RSA | 非对称 | 长 | 加密与签名,经典 |
| ECC | 非对称 | 短 | 加密与签名,同强度密钥更短、性能更好 |
| Ed25519 | 非对称 | 短 | 签名,速度快 |
| SM2 | 非对称(国密) | 短 | 签名 / 加密 |
| SM3 | 哈希(国密) | — | 摘要 |
| SM4 | 对称(国密) | — | 批量加密 |

最后一步是把它们拼起来。TLS 握手就是混合加密的标准落地,左到右为消息方向:

```
Client -> ClientHello(支持的加密套件) -> Server
Client <- ServerHello(选定的套件) + 证书 <- Server
Client -> 验证证书 -> 生成预主密钥 -> 用服务端公钥加密 -> Server
双方用预主密钥生成会话密钥 -> 对称加密通信
```

非对称只出现在"安全地协商出那把对称密钥"这一步,之后全部走对称加密——两体制配合的样板。

## 具体示例

给一个跨境 SaaS 排一遍:数据库里的手机号用 AES-256-GCM 加密,密钥进 KMS 而非写死在代码里;登录与所有对外接口走 TLS,证书由 [[公钥基础设施]] 体系签发并严格校验链与域名;服务间 API 令牌用 Ed25519 或 ECDSA 签名;用户口令绝不加密存储,改用专门的慢散列加盐;若面向国内合规场景,整条链路按 SM4 换对称、SM2 换签名、SM3 换摘要,并同步换支持的证书链与硬件。

## 何时用与何时不用

- **该做:** 任何涉及静态数据加密、传输加密、签名验签、口令存储的系统,都先按职责对表选型,再用成熟协议栈(TLS)而不是自拼流程。
- **不该做:** 不要自研算法或自己实现底层原语;不要用加密来存口令(该用散列);不要复用同一把密钥承担两种职责;不要停留在已被淘汰的选项(SHA-1、短密钥 RSA、无认证的 CBC 老用法)。

## 优劣与代价

✅ 按清单选型成本低、见效快,能挡掉绝大多数"用错算法"类事故。
✅ 混合加密(非对称协商 + 对称传输)兼得安全与性能,是被 TLS 长期验证的组合。
⚠️ 清单会过期:算法强度随算力与攻击进展变化,旧条目必须定期淘汰,否则指南本身变成风险源。
⚠️ 合规取向会牵出整套体系:国密改造不是换个算法名,证书链、库与硬件都要配套。

## 与相关概念的区别

- **vs [[对称加密与非对称加密]]:** 那篇讲两类体制的原理与差异,本篇讲"在具体场景里挑哪个、怎么配"。
- **vs [[密码学基础篇]]:** 基础篇是概念地图,本篇是操作手册。
- **vs 加密与散列:** 加密要求可逆且密钥可控,散列要求不可逆;口令属于后者,不能用 AES 代替。

## 常见误区

- 用 AES 把用户口令加密存起来,口令就不会泄露。
- 只要选了 AES-256,用哪种分组模式都一样。
- 哈希和加密是一回事,都能还原出原文。
