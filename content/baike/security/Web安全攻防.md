# Web安全攻防


> 📌 **导航**：本文是 **Web安全攻防** 词条，属于 security 术语集。相关枢纽：[[公钥基础设施]]、[[密码学基础篇]]、[[零信任安全架构]]。

## 定义

**一句话定义：** Web 安全攻防是围绕浏览器与服务端之间那条 HTTP 通道展开的持续对抗:攻击者寻找"输入未分离、信任未收敛、状态未校验"之处下手,防守者用输入处理、认证授权与纵深防御把同类漏洞一次性堵掉。

**通俗类比：** 像一家临街商铺的安保——后门没锁(未鉴权的接口)、收银台只认纸条不认人(Cookie 自动携带)、告示牌谁都能贴(输出未转义)。贼不需要"破解"什么,只要走那扇没锁的门。

## 为什么需要它

Web 应用把大量内部能力(数据库、内网服务、文件读写)包在一个对外暴露的 HTTP 接口之后,任何一处"输入即执行"或"请求即信任"都会把外部暴露面直接接到内部资产上。好在漏洞类型高度收敛——少数几类反复出现,所以攻防可以清单化、可以做成框架默认能力,这是它能被系统性治理的前提。

## 核心机制

按"哪一层信任被骗过"分,四类最常见:

| 攻击 | 欺骗的信任 | 落点 | 根治手段 |
|------|-----------|------|----------|
| SQL 注入 | 数据库把输入当 SQL | 后端数据 | 参数化查询 |
| XSS | 浏览器把响应当可信脚本 | 其他用户浏览器 | 输出编码 + CSP |
| CSRF | 站点把"自动带 Cookie 的请求"当本人 | 用户的账户操作 | CSRF Token + SameSite |
| SSRF | 服务端把自己发出的请求当可信来源 | 内网 / 云元数据 | URL 白名单 + 禁内网 IP |

- **SQL 注入:** 拼接进 SQL 的输入改变语义,详见 [[SQL注入与XSS]]。
- **XSS:** 分存储型(脚本入库,他人访问时触发)、反射型(脚本在 URL 参数中被即时反射)、DOM 型(前端 JS 操作 DOM 不当);防护为输出转义、CSP 头、HttpOnly Cookie。
- **CSRF:** 用户先登录 bank.com 拿到 Cookie,再访问 evil.com,后者自动向 bank.com 发出携带该 Cookie 的请求;防护为 CSRF Token、SameSite Cookie、校验 Referer。
- **SSRF:** 攻击者借服务端去访问它才够得着的地址;防护为白名单 URL、禁用内网 IP、限制协议。

## 具体示例

一个"填网址自动抓封面图"的功能:攻击者输入 `http://169.254.169.254/latest/meta-data/`,服务端替他访问了云厂商元数据端点并把内容回填出来,临时凭据就此外泄——SSRF 的成因正是"自己发出的请求被认为可信"。同一段代码若把用户参数拼进 SQL 语句,它同时还是一处 SQL 注入点。

## 何时用与何时不用

- **该做:** 所有外部输入按上下文处理(参数化 / 编码);所有改状态请求要 CSRF 防护并做服务端二次鉴权;出站请求一律走白名单;Cookie 加 HttpOnly + Secure + SameSite;上线前对照 OWASP Top 10 自查一遍。
- **不够用:** 只靠 WAF(它挡已知模式,不改代码等于留着原漏洞)、只做前端校验、把 HTTPS 当成防注入手段(它只保护传输,不校验内容语义)。

## 优劣与代价

✅ 通用防护一旦做成框架默认(自动转义、CSRF 中间件、连接池参数化),能批量消灭一类漏洞。
✅ 纵深防御让"单点遗漏"降级成"未遂":参数化 + CSP + WAF + 最小权限互为兜底。
⚠️ 必须全链路一致:一处 raw SQL、一处 innerHTML 就前功尽弃,遗留代码改造成本高。
⚠️ CSP 与出网白名单收得太紧会打断业务,需要报告模式与灰度推进。

## 与相关概念的区别

- **vs 网络层安全:** 本词条聚焦 L7 语义,防火墙与 IDS 看的是包和端口,看不出"这条 SQL 想干什么"。
- **vs 渗透测试:** 攻防是持续的能力建设,渗透测试只是某个时点的检查手段。
- **vs 认证与授权:** 认证解决"你是谁",而这里多数漏洞发生在身份已确认之后仍过度信任输入。

## 常见误区

- 装了 WAF,就不必在代码里修注入漏洞了。
- 网站上了 HTTPS,就能防住 SQL 注入和 XSS。
- 前端做过校验,后端可以省掉这一步。
