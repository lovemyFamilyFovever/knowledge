# 银行家算法


> 📌 **导航**：本文是 **银行家算法** 词条，属于 os 术语集。相关枢纽：[[Shell 脚本详解]]、[[操作系统基础术语]]、[[操作系统核心]]、[[进程管理详解]]。

## 定义

**一句话定义：** 银行家算法(Banker's Algorithm)是 Dijkstra 提出的一种死锁避免算法:系统在每次分配资源前,先假设满足该请求并检查系统是否仍处于"安全状态"(存在一个安全序列让所有进程都能完成),只有在安全时才分配,否则让进程等待,从而避免进入死锁。

**通俗类比：** 像银行家放贷——手里现金有限,每当有客户要贷款,先盘算"如果借出去,是否还能找到一种顺序让所有客户最终都能还清并完成"(安全序列);只有仍有回旋余地时才借,否则宁可让客户等,绝不把自己逼进"谁也还不上"的死局。

> 多义说明:银行家算法属死锁的**避免**策略(区别于预防、检测+恢复);它要求预先知道每个进程的最大资源需求。本文讨论该算法。

## 原理与机制

- **数据结构:** Available(可用资源)、Max(每进程最大需求)、Allocation(已分配)、Need = Max − Allocation。
- **安全状态:** 存在一个安全序列 ⟨P₁,…,Pₙ⟩,使每个进程都能用"当前可用 + 它已持有"的资源完成其最大需求。
- **请求处理:** 收到请求 → 若 Request ≤ Need 且 ≤ Available,先试探性分配 → 运行安全性算法检查是否仍安全 → 安全则正式分配,否则回滚并让进程等待。
- **安全性检查:** 反复寻找 Need ≤ Work 的进程,假设其完成并回收资源(Work += Allocation),看能否让所有进程都完成。

## 关键组成

| 组成 | 说明 |
|------|------|
| Available / Max / Allocation / Need | 资源与需求矩阵 |
| 安全状态与安全序列 | 避免死锁的判据 |
| 试探分配 | 先假设满足请求 |
| 安全性算法 | 检查是否仍安全 |
| 回滚 | 不安全时撤销试探分配 |

## 应用场景

- 操作系统资源分配的死锁避免
- 教学与算法演示
- 需要严格避免死锁的资源管理场景

## 优点与局限

- 优点:在满足前提(已知最大需求)下能保证系统永不进入死锁。
- 局限:需预先知道每个进程的最大资源需求(现实常未知);进程/资源数多时开销大;要求需求固定,过于保守;实际操作系统多不采用(信息难获取)。

## 常见误区

- 银行家算法是"避免"(动态判断安全状态),不是"预防"(静态破坏必要条件)。
- 它需要预知 Max 需求,这在现实中往往难以满足。
- 安全状态一定无死锁;但不安全状态不一定已死锁(只是可能走向死锁)。
- 实际系统更常用死锁检测+恢复,或直接忽略(鸵鸟策略)。
