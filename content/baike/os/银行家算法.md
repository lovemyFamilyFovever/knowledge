# 银行家算法


> 📌 **导航**：本文是 **银行家算法** 词条，属于 os 术语集。相关枢纽：[[Shell脚本编程]]、[[操作系统基础术语]]、[[操作系统核心]]、[[进程管理详解]]。

## 定义

**一句话定义：** 银行家算法（Banker's Algorithm）是 Dijkstra 提出的一种死锁避免算法：系统在每次分配资源前，先假设满足该请求并检查是否仍处于"安全状态"（存在一个安全序列让所有进程都能完成），只有安全时才分配、否则让进程等待，从而避免进入死锁。

**通俗类比：** 像银行家放贷——手里现金有限，每当有客户要贷款，先盘算"借出去后是否还能找到一种顺序让所有客户最终都能还清并完成"；仍有回旋余地才借，否则宁可让客户等，绝不把自己逼进"谁也还不上"的死局。

> 多义说明：银行家算法属死锁的避免策略（区别于预防、检测 + 恢复）；它要求预先知道每个进程的最大资源需求。

## 为什么需要它

死锁一旦发生代价很高。与其破坏必要条件去"预防"（牺牲并发），不如在每次分配时动态判断"这一步会不会把系统推向死锁"——只要始终留在安全状态，就能既允许并发、又保证永不进入死锁。银行家算法就是这种"避免"的代表。

## 核心机制

- **数据结构：** Available（可用资源）、Max（每进程最大需求）、Allocation（已分配）、Need = Max − Allocation。
- **安全状态：** 存在安全序列 ⟨P₁,…,Pₙ⟩，使每个进程都能用"当前可用 + 它已持有"的资源完成其最大需求。
- **请求处理：** 若 Request ≤ Need 且 ≤ Available，先试探性分配 → 运行安全性算法检查是否仍安全 → 安全则正式分配，否则回滚并让进程等待。
- **安全性检查：** 反复寻找 Need ≤ Work 的进程，假设其完成并回收资源（Work += Allocation），看能否让所有进程都完成。

## 具体示例

某进程请求 1 个资源 C：把这次分配假想加进系统后跑安全性检查，若仍存在让全部进程都能完成的安全序列就正式分配；若找不到（进入不安全态），即便此刻并未死锁也拒绝请求、让该进程等待。

## 何时用与何时不用

- **用：** 资源种类 / 数量与各进程最大需求可预知的封闭系统（教学演示、特定专用资源管理）。
- **不用：** 通用操作系统几乎不落地——现实进程最大需求未知、资源与进程多时开销高、且过于保守限制并发；实际多用死锁检测 + 恢复或鸵鸟策略。

## 优劣与代价

✅ 在"已知最大需求"前提下能保证系统永不进入死锁，同时仍允许相当并发。
⚠️ 需预知每进程 Max 需求（现实常未知）；进程 / 资源多时开销大；要求需求固定、过于保守；实际系统少用。

## 与相关概念的区别

vs 死锁预防：预防是静态破坏 Coffman 四条件之一，避免是每次分配时动态判安全状态（见 [[死锁]]）；vs 检测 + 恢复：后者允许死锁发生再周期性查环回滚，银行家则从一开始就拒绝会进入不安全态的分配。

## 常见误区

- 银行家算法属于死锁的"预防"策略。
- 系统进入不安全状态就等于已经死锁。
- 银行家算法在实际操作系统中被广泛采用。

## 面试速答

> 🎯 银行家算法 = Dijkstra 的死锁"避免"法：维护 Available/Max/Allocation/Need，每次分配前试探 + 安全性检查，只有留在安全状态（存在安全序列让所有进程都能完成）才分配；需预知最大需求、开销大，实际 OS 少用。
