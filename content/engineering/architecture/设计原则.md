# 设计原则

## 1. SOLID五大原则

### 1.1 单一职责原则（SRP）

**一句话定义：** 一个类只负责一项职责，只因一个原因而变化。

**通俗类比：** 像一个员工只负责一件事，既当会计又当保安容易出错。

**代码示例：**
```java
// 违反SRP
class User {
    void saveToDatabase() { ... }
    void sendEmail() { ... }
    void generateReport() { ... }
}

// 符合SRP
class UserRepository { void save(User user) { ... } }
class EmailService { void send(User user) { ... } }
class ReportGenerator { void generate(User user) { ... } }
```

### 1.2 开闭原则（OCP）

**一句话定义：** 对扩展开放，对修改关闭，新增功能不修改已有代码。

**通俗类比：** 像插座插件，新电器插上就能用，不用改造插座本身。

**代码示例：**
```java
// 违反OCP - 新增支付方式要改switch
void pay(String type) {
    if (type.equals("alipay")) { ... }
    else if (type.equals("wechat")) { ... }
}

// 符合OCP - 新增支付方式只需新增实现
interface Payment { void pay(); }
class Alipay implements Payment { ... }
class WechatPay implements Payment { ... }
```

### 1.3 里氏替换原则（LSP）

**一句话定义：** 子类必须能够替换父类，且不改变程序正确性。

**通俗类比：** 像家具配件，新生产的螺丝必须能完美替换旧螺丝。

**代码示例：**
```java
// 违反LSP - 正方形不是长方形的正确子类
class Rectangle { void setWidth(int w); void setHeight(int h); }
class Square extends Rectangle {
    void setWidth(int w) { this.width = w; this.height = w; }
    void setHeight(int h) { this.width = h; this.height = h; }
}
```

### 1.4 接口隔离原则（ISP）

**一句话定义：** 客户端不应该被迫依赖它不需要的接口。

**通俗类比：** 像遥控器，电视遥控器不应该有打印机按钮。

**代码示例：**
```java
// 违反ISP - 强制实现不需要的方法
interface Worker {
    void work();
    void eat();
    void sleep();
}

// 符合ISP - 细化接口
interface Workable { void work(); }
interface Eatable { void eat(); }
interface Sleepable { void sleep(); }
```

### 1.5 依赖倒置原则（DIP）

**一句话定义：** 高层模块不应该依赖低层模块，两者都应该依赖抽象。

**通俗类比：** 像插座标准，电器和插座都依赖统一标准，而不是彼此直接依赖。

**代码示例：**
```java
// 违反DIP - 高层直接依赖低层
class OrderService {
    private MySQLDatabase db = new MySQLDatabase();
}

// 符合DIP - 依赖抽象
class OrderService {
    private Database db;  // 依赖接口
    OrderService(Database db) { this.db = db; }
}
```

## 2. DRY（不要重复自己）

**一句话定义：** 每一段知识在系统中应该只有一个明确的表示。

**通俗类比：** 像简历模板，做一份模板反复使用，而不是每次重新写。

**代码示例：**
```java
// 违反DRY
if (user.getAge() >= 18 && user.getIdCard() != null) { ... }
// 另一处又写
if (user.getAge() >= 18 && user.getIdCard() != null) { ... }

// 符合DRY
boolean isAdult = user.isAdult();
if (isAdult) { ... }
```

**为什么需要它：** 减少代码重复，修改一处自动生效，降低维护成本。

## 3. KISS（保持简单）

**一句话定义：** 尽量保持代码简单直观，避免不必要的复杂设计。

**通俗类比：** 像说明书，越简单越容易理解，没人喜欢看长篇大论。

**代码示例：**
```java
// 过度设计
public interface DataProcessor<T> {
    <R> R process(Function<T, R> transform);
}
// 对于简单场景
public List<User> filterActiveUsers(List<User> users) {
    return users.stream().filter(User::isActive).collect(Collectors.toList());
}
```

**为什么需要它：** 简单的代码更容易理解、测试和维护。

## 4. YAGNI（你不会需要它）

**一句话定义：** 不要添加当前不需要的功能，等真正需要时再实现。

**通俗类比：** 像装修房子，你不会因为将来可能养狗就现在建狗窝。

**代码示例：**
```java
// 过早优化
class UserValidator {
    // 实现了10种验证规则，但当前只需要验证邮箱
    boolean validateEmail(User user) { ... }
    boolean validatePhone(User user) { ... }     // 暂时用不到
    boolean validateAddress(User user) { ... }   // 暂时用不到
    // ...
}

// YAGNI - 只做需要的
class UserValidator {
    boolean validateEmail(User user) { ... }  // 当前需要
}
```

**为什么需要它：** 减少不必要的代码量，避免过度设计浪费时间。

## 5. 高内聚低耦合

**一句话定义：** 模块内部功能紧密相关，模块之间依赖尽量减少。

**通俗类比：** 像公司部门，市场部专注市场工作，与技术部职责分明但协作顺畅。

**代码示例：**
```java
// 高耦合
class OrderService {
    private UserService userService;
    private PaymentService paymentService;
    private InventoryService inventoryService;
    private NotificationService notificationService;
    // 所有逻辑混在一起
}

// 高内聚低耦合
class OrderService {
    private OrderValidator validator;
    private OrderRepository repository;
    // 只负责订单核心逻辑，其他委托给专门服务
}
```

**为什么需要它：** 降低修改一个模块对其他模块的影响，提高可维护性。

---

## 6. 迪米特法则（最少知识原则）

**一句话定义：** 一个对象应该对其他对象有最少的了解，只与直接朋友通信。

**通俗类比：** 像社交关系，你只需要认识你直接认识的人，不需要认识朋友的朋友。

**代码示例：**
```java
// 违反迪米特法则
String name = order.getCustomer().getAddress().getCity().getName();

// 符合迪米特法则
String name = order.getCustomerCityName();  // 由order提供方法
```

**为什么需要它：** 减少类之间的耦合，修改一个类不会影响太多其他类。

---

## 7. 组合优于继承

**一句话定义：** 优先使用对象组合而非类继承来实现代码复用。

**通俗类比：** 像乐高积木，通过组合不同积木创造新物体，而不是继承一个现成物体。

**代码示例：**
```java
// 继承方式 - 不灵活
class Admin extends User {
    void adminMethod() { ... }
}
// 无法同时是Admin和VIP

// 组合方式 - 灵活
class User {
    private Role role;        // 组合角色
    private List<Tag> tags;   // 组合标签
}
// 可以同时是Admin和VIP
```

**为什么需要它：** 继承是静态的编译时绑定，组合是动态的运行时绑定，更灵活。

---

## 8. 面向接口编程

**一句话定义：** 依赖于抽象而非具体实现，通过接口定义行为契约。

**通俗类比：** 像USB接口，电脑和U盘都遵循USB标准，可以自由搭配。

**代码示例：**
```java
// 面向实现编程
class OrderService {
    private MySQLOrderDao dao = new MySQLOrderDao();  // 绑定具体实现
}

// 面向接口编程
class OrderService {
    private OrderDao dao;  // 依赖接口
    OrderService(OrderDao dao) { this.dao = dao; }
}
```

**为什么需要它：** 便于替换实现、便于测试（mock）、便于扩展。

---

## 9. 控制反转（IoC）

**一句话定义：** 将对象创建和依赖管理的控制权从程序代码转移到外部容器。

**通俗类比：** 像餐厅点餐，你不需要自己做饭（控制权在厨房），你只需要下单。

**代码示例：**
```java
// 传统方式 - 程序自己控制依赖
class OrderService {
    private UserService userService = new UserService();  // 自己创建
}

// IoC - 容器控制
@Service
class OrderService {
    @Autowired
    private UserService userService;  // 容器注入
}
```

**为什么需要它：** 解耦对象的创建和使用，便于管理和替换依赖。

---

## 10. 依赖注入（DI）

**一句话定义：** 对象不自己创建依赖，而是通过外部注入获得依赖对象。

**通俗类比：** 像外卖送餐，你不用自己做饭，有人送到你手上。

**代码示例：**
```java
// 构造器注入（推荐）
class OrderService {
    private final UserService userService;
    OrderService(UserService userService) {
        this.userService = userService;
    }
}

// Setter注入
class OrderService {
    private UserService userService;
    void setUserService(UserService userService) {
        this.userService = userService;
    }
}
```

**为什么需要它：** 是IoC的具体实现方式，便于测试（可注入mock对象）和解耦。

**IoC vs DI：** IoC是设计原则（控制权转移），DI是实现手段（注入依赖），IoC通过DI实现。
