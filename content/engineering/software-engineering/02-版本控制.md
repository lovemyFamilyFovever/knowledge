# 02-版本控制

本章介绍版本控制的核心概念和Git的使用，帮助你理解如何管理代码变更和协作开发。

## Git工作区/暂存区/仓库

**一句话定义**：Git有三个主要区域：工作区（Working Directory）、暂存区（Staging Area）和仓库（Repository），分别用于编辑、暂存和保存变更。

**通俗类比**：就像厨房做饭：工作区是切菜板（编辑文件），暂存区是备菜盘（准备提交），仓库是冰箱（永久保存）。

**具体示例**：修改文件在工作区，`git add`将文件添加到暂存区，`git commit`将暂存区的变更保存到仓库。

**为什么需要它**：这三个区域提供了灵活的变更管理，允许你精细控制哪些修改要提交，哪些要保留。

**与相关术语的对比和区分**：与SVN等集中式版本控制不同，Git是分布式的，每个开发者都有完整的仓库副本。

## git add/commit/push/pull/fetch

**一句话定义**：这些是Git的核心命令，用于管理变更：`add`添加到暂存区，`commit`保存到本地仓库，`push`推送到远程，`pull`拉取并合并，`fetch`只拉取不合并。

**通俗类比**：就像寄信：`add`是把信放进信封，`commit`是盖邮戳，`push`是投递，`pull`是收信并拆开，`fetch`只是收信但不拆开。

**具体示例**：
```bash
git add .
git commit -m "修复登录bug"
git push origin main
git pull origin main
git fetch origin
```

**为什么需要它**：这些命令提供了完整的代码变更管理流程，确保团队协作的同步和版本历史的可追溯。

**与相关术语的对比和区分**：`push`和`pull`是远程操作，而`commit`是本地操作；`fetch`比`pull`更安全，因为不会自动合并。

## 分支（branch）

**一句话定义**：分支是独立的代码开发线，允许你在不影响主线的情况下进行开发。

**通俗类比**：就像游戏存档，你可以创建一个新存档尝试不同策略，而不影响主存档。

**具体示例**：创建新分支开发新功能：
```bash
git branch feature-login
git checkout feature-login
# 或者
git checkout -b feature-login
```

**为什么需要它**：分支支持并行开发、实验性修改和bug修复，是团队协作的基础。

**与相关术语的对比和区分**：与SVN的轻量级分支不同，Git的分支是廉价的，创建和切换速度快。

## 合并（merge）

**一句话定义**：合并是将一个分支的变更整合到另一个分支的操作。

**通俗类比**：就像将两条河流汇合成一条，保留两条河的水流。

**具体示例**：将功能分支合并到主分支：
```bash
git checkout main
git merge feature-login
```

**为什么需要它**：合并是集成不同开发线变更的主要方式，确保所有工作最终整合到主线。

**与相关术语的对比和区分**：与变基（rebase）相比，合并保留完整的分支历史，但可能产生合并提交。

## 变基（rebase）

**一句话定义**：变基是将一个分支的提交重新应用到另一个分支顶部，创造线性历史。

**通俗类比**：就像搬家后重新布置家具，让房间看起来像一直这样整洁。

**具体示例**：将功能分支变基到最新主分支：
```bash
git checkout feature-login
git rebase main
```

**为什么需要它**：变基创造了干净的线性历史，便于理解和管理，但改变了提交历史。

**与相关术语的对比和区分**：与合并相比，变基重写了历史，不适合已推送到公共仓库的提交。

## 冲突解决

**一句话定义**：冲突解决是当两个分支修改同一文件的同一部分时，手动选择保留哪个变更的过程。

**通俗类比**：就像两个人同时修改同一份文档，需要协商决定最终版本。

**具体示例**：合并时遇到冲突，Git会标记冲突文件，你需要编辑解决后：
```bash
git add <resolved-file>
git commit
```

**为什么需要它**：冲突解决确保代码的一致性，防止意外覆盖，是团队协作的必要环节。

**与相关术语的对比和区分**：与自动合并不同，冲突解决需要人工干预，通常发生在竞争性修改时。

## Pull Request/Merge Request

**一句话定义**：Pull Request（GitHub）或Merge Request（GitLab）是请求将分支变更合并到主分支的机制，通常包含代码审查。

**通俗类比**：就像向出版社投稿，编辑审查后决定是否出版。

**具体示例**：在GitHub上创建PR，请求将`feature-login`分支合并到`main`分支，团队成员进行代码审查。

**为什么需要它**：PR/MR提供了代码审查、讨论和质量控制的平台，是团队协作的关键流程。

**与相关术语的对比和区分**：与直接合并相比，PR/MR增加了审查环节，提高了代码质量。

## Code Review流程

**一句话定义**：代码审查是团队成员在代码合并前检查代码质量、设计和安全性的过程。

**通俗类比**：就像老师批改作业，提供反馈和建议。

**具体示例**：在PR中，审查者检查代码风格、逻辑错误、安全问题，并提供反馈。

**为什么需要它**：代码审查提高了代码质量，分享了知识，减少了bug，是团队质量保证的重要手段。

**与相关术语的对比和区分**：与测试相比，代码审查更关注设计、可读性和最佳实践。

## Git Hooks

**一句话定义**：Git Hooks是在Git操作前后自动执行的脚本，用于自动化代码检查和工作流。

**通俗类比**：就像门铃，有人来时自动响铃。

**具体示例**：pre-commit hook在提交前运行代码检查：
```bash
#!/bin/sh
npm run lint
```

**为什么需要它**：Git Hooks自动化了重复性任务，确保代码质量标准，减少了人为错误。

**与相关术语的对比和区分**：与CI/CD相比，Git Hooks在本地执行，更轻量级。

## Git Flow

**一句话定义**：Git Flow是一种分支管理模型，定义了main、develop、feature、release和hotfix分支的用途和流程。

**通俗类比**：就像交通规则，规定了不同道路的用途和行驶方向。

**具体示例**：使用Git Flow管理发布：从develop分支创建release分支，测试通过后合并到main并打标签。

**为什么需要它**：Git Flow提供了清晰的发布流程，适合有定期发布计划的项目。

**与相关术语的对比和区分**：与Trunk Based Development相比，Git Flow更复杂，但适合大型项目。

## Trunk Based Development

**一句话定义**：Trunk Based Development是一种开发实践，团队在主干（trunk）上频繁集成代码，使用短生命周期的分支。

**通俗类比**：就像多人同时在一块白板上绘画，频繁同步。

**具体示例**：开发者每天将小改动直接提交到主干分支，使用特性开关控制未完成功能的可见性。

**为什么需要它**：TBD促进了持续集成，减少了合并冲突，加快了交付速度。

**与相关术语的对比和区分**：与Git Flow相比，TBD更简单，但需要强大的自动化和特性开关支持。

## Cherry-pick

**一句话定义**：Cherry-pick是将特定提交从一个分支应用到另一个分支的操作。

**通俗类比**：就像从杂志上剪下喜欢的文章，贴到自己的剪贴本上。

**具体示例**：将hotfix提交应用到release分支：
```bash
git cherry-pick <commit-hash>
```

**为什么需要它**：Cherry-pick允许选择性合并，适用于修复特定版本的bug。

**与相关术语的对比和区分**：与合并相比，cherry-pick只复制特定提交，而不是整个分支。

## Stash

**一句话定义**：Stash是临时保存工作区变更的操作，允许你切换分支而不提交未完成的工作。

**通俗类比**：就像把做到一半的工作暂时收起来，先处理其他事情。

**具体示例**：保存当前工作：
```bash
git stash
git checkout other-branch
# 恢复工作
git stash pop
```

**为什么需要它**：Stash提供了灵活性，允许在不同任务间快速切换，保持工作区整洁。

**与相关术语的对比和区分**：与提交相比，stash是临时的，不创建提交历史。

## .gitignore

**一句话定义**：.gitignore是一个文件，指定Git应该忽略的文件和目录，如编译产物、日志和本地配置。

**通俗类比**：就像购物清单上划掉不需要的物品。

**具体示例**：.gitignore文件内容：
```
node_modules/
*.log
.env
```

**为什么需要它**：.gitignore防止无关文件被提交到仓库，保持仓库整洁，避免敏感信息泄露。

**与相关术语的对比和区分**：与`.git/info/exclude`相比，`.gitignore`可以提交到仓库，共享给团队。

---

本章介绍了Git版本控制的核心概念和命令。掌握这些术语和操作，能帮助你高效地管理代码变更，支持团队协作，并保持代码库的整洁和可追溯性。在实际工作中，建议结合具体项目需求选择合适的分支策略和工作流。
