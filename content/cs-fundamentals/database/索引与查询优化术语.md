# 索引与查询优化术语

---

## 聚簇索引（Clustered Index）

**一句话定义（大白话）：** 索引的叶子节点直接存储数据行本身，索引和数据"住在一起"。

**通俗类比（生活场景）：** 电话簿按姓名排序，翻到"张三"那页就能直接看到他的电话号码。索引和数据是同一套排序，不用再跳转。

**具体示例：**

```sql
-- InnoDB 中，主键自动成为聚簇索引
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,  -- 这个 id 就是聚簇索引
    username VARCHAR(50),
    email VARCHAR(100)
);

-- 聚簇索引的叶子节点直接存整行数据
-- 所以通过主键查询最快：SELECT * FROM users WHERE id = 1;

-- 一张表只能有一个聚簇索引
-- 如果没有主键，InnoDB 会选择一个非空唯一索引
-- 如果都没有，会创建一个隐藏的 row_id 作为聚簇索引
```

**为什么需要它：** 数据按照索引顺序物理存储，范围查询和排序查询效率极高，避免了额外的"回表"操作。

**与相关术语的对比和区分：** 聚簇索引存数据本身，非聚簇索引存指向数据的指针。聚簇索引是一棵"数据树"，非聚簇索引是一棵"目录树"。

---

## 非聚簇索引（Non-Clustered Index）

**一句话定义（大白话）：** 索引的叶子节点存储的是指向数据行的指针（主键值），需要"回表"才能拿到完整数据。

**通俗类比（生活场景）：** 书后面的索引目录——查到"聚簇索引"在第 50 页，你得翻到第 50 页才能看到具体内容。索引和内容是分开的。

**具体示例：**

```sql
-- 创建非聚簇索引
CREATE INDEX idx_email ON users(email);

-- 查询过程：
-- 1. 在 idx_email 索引树上查到 email='test@example.com' 对应的 id=5
-- 2. 拿着 id=5 回到聚簇索引找完整行数据（回表）
SELECT * FROM users WHERE email = 'test@example.com';

-- 覆盖索引可以避免回表（见"覆盖索引"条目）
SELECT id, email FROM users WHERE email = 'test@example.com';
-- 只查索引列，不用回表
```

**为什么需要它：** 不能所有查询都走主键，非聚簇索引让你能按其他字段快速定位数据。

**与相关术语的对比和区分：** 非聚簇索引每次查询可能需要回表（两次 B+ 树查找），聚簇索引一次查找就能拿到数据。非聚簇索引存的是主键值，不是物理地址。

---

## B+ 树索引（B+ Tree Index）

**一句话定义（大白话）：** 一种树形数据结构，所有数据都存在叶子节点，叶子节点之间用链表连接，支持范围查询。

**通俗类比（生活场景）：** 图书馆的分类检索系统——顶层是大分类（工科、文科），中间是子分类（计算机、数学），最底层是具体书目。叶子节点之间有链条，方便连续翻阅。

**具体示例：**

```
B+ 树结构示意（假设主键是 id）：

            [10 | 20 | 30]           ← 根节点（导航用）
           /    |     |    \
    [1-9]  [11-19] [21-29] [31-40]  ← 内部节点（导航用）
      ↓       ↓       ↓       ↓
   叶子节点（存数据，用链表相连）
```

```sql
-- B+ 树索引支持的操作：
SELECT * FROM users WHERE id = 15;        -- 等值查询（O(log n)）
SELECT * FROM users WHERE id BETWEEN 10 AND 20;  -- 范围查询（高效）
SELECT * FROM users ORDER BY id;          -- 排序（天然有序）
SELECT * FROM users LIMIT 10;             -- 分页（快速定位）

-- B+ 树不支持的操作：
SELECT * FROM users WHERE id * 2 = 20;    -- 索引列参与运算 → 失效
SELECT * FROM users WHERE LEFT(username, 3) = '张三';  -- 函数 → 失效
```

**为什么需要它：** 相比二叉树，B+ 树的每个节点可以有几百个子节点，树的高度很低（通常 3-4 层），磁盘 IO 次数少。叶子节点链表让范围查询非常高效。

**与相关术语的对比和区分：** B+ 树是索引的**实现方式**，聚簇/非聚簇是索引的**组织方式**。InnoDB 默认用 B+ 树实现聚簇索引和二级索引。

## 哈希索引（Hash Index）

**一句话定义（大白话）：** 用哈希函数把索引值映射到固定位置，等值查询极快（O(1)），但不支持范围查询。

**通俗类比（生活场景）：** 快递柜——每个包裹有个取件码（哈希值），直接输入取件码就能拿到包裹，不用挨个翻找。但你没法说"给我所有 100 号柜子里的包裹"。

**具体示例：**

```sql
-- Memory 存储引擎支持哈希索引
CREATE TABLE cache_data (
    key_name VARCHAR(100),
    value TEXT
) ENGINE=MEMORY;

-- InnoDB 自适应哈希索引（自动生成，不可手动创建）
-- 当某些索引值被频繁等值查询时，InnoDB 会自动在内存中建立哈希索引

-- 哈希索引适用场景：
SELECT * FROM cache_data WHERE key_name = 'session_abc';  -- 等值查询，极快

-- 哈希索引不适用：
SELECT * FROM cache_data WHERE key_name > 'a';  -- 范围查询，无法使用哈希
SELECT * FROM cache_data WHERE key_name LIKE 'session%';  -- 模糊查询，无法使用
```

**为什么需要它：** 等值查询场景下，哈希索引比 B+ 树更快。MySQL 的 InnoDB 引擎会自动为频繁查询的索引值建立自适应哈希索引。

**与相关术语的对比和区分：** 哈希索引适合等值查询（O(1)），B+ 树适合范围查询和排序。哈希索引不支持部分列匹配和范围查询，B+ 树都支持。

---

## 全文索引（Full-Text Index）

**一句话定义（大白话）：** 专门用于文本搜索的索引，能快速找到包含某个关键词的行，比 LIKE '%keyword%' 快得多。

**通俗类比（生活场景）：** 搜索引擎——输入"数据库优化"，瞬间找到所有包含这几个词的网页，而不是逐页扫描。

**具体示例：**

```sql
-- 创建全文索引
CREATE TABLE articles (
    id INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200),
    content TEXT,
    FULLTEXT INDEX ft_content (content)  -- 对 content 列建全文索引
) ENGINE=InnoDB;

-- 或者后加
ALTER TABLE articles ADD FULLTEXT INDEX ft_title_content (title, content);

-- 使用全文索引搜索
SELECT * FROM articles
WHERE MATCH(content) AGAINST('数据库 优化' IN BOOLEAN MODE);

-- 自然语言模式（默认）
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('MySQL performance');

-- 布尔模式：支持更复杂的查询
-- +必须包含  -排除  *通配符  ""精确短语
SELECT * FROM articles
WHERE MATCH(content) AGAINST('+MySQL +优化 -Redis' IN BOOLEAN MODE);

-- 比 LIKE 快得多：
-- SELECT * FROM articles WHERE content LIKE '%MySQL%';  -- 全表扫描，慢
-- SELECT * FROM articles WHERE MATCH(content) AGAINST('MySQL');  -- 走索引，快
```

**为什么需要它：** LIKE '%keyword%' 无法使用索引，会全表扫描。全文索引通过倒排索引实现，搜索效率高几个数量级。

**与相关术语的对比和区分：** 全文索引用于文本搜索，B+ 树索引用于精确匹配和范围查询。对于中文全文搜索，需要配合分词器使用。

## 联合索引（Composite Index）

**一句话定义（大白话）：** 对多个列建立的组合索引，比如 (a, b, c) 三个字段联合建索引。

**通俗类比（生活场景）：** 通讯录先按姓排序，姓相同再按名排序。联合索引就是"多级排序"，先按第一个字段排，第一个相同再按第二个排。

**具体示例：**

```sql
-- 创建联合索引
CREATE INDEX idx_name_age ON users (username, age);

-- 联合索引 (username, age) 可以支持：
SELECT * FROM users WHERE username = '张三';              -- 用到索引
SELECT * FROM users WHERE username = '张三' AND age = 25; -- 用到索引
SELECT * FROM users WHERE username = '张三' AND age > 20; -- 用到索引

-- 无法使用该索引：
SELECT * FROM users WHERE age = 25;  -- 跳过了 username，违反最左前缀
SELECT * FROM users WHERE age > 20;  -- 同上

-- 联合索引的列顺序很重要：
-- (username, age) 和 (age, username) 是两个不同的索引
```

**为什么需要它：** 一个联合索引可以替代多个单列索引，减少索引数量，同时提高查询效率（一次索引查找覆盖多个条件）。

**与相关术语的对比和区分：** 联合索引是多个字段的组合索引，遵循最左前缀原则。单列索引只对一个字段有效，联合索引可以同时满足多个字段的查询需求。

---

## 覆盖索引（Covering Index）

**一句话定义（大白话）：** 查询需要的所有列都在索引里，不用回表取数据。

**通俗类比（生活场景）：** 你去超市买三样东西，刚好这三样都在入口处的促销架上，一趟就搞定，不用跑到超市里面去找。

**具体示例：**

```sql
-- 假设有联合索引 idx_name_age (username, age)

-- 需要回表（查询了索引外的列）
SELECT * FROM users WHERE username = '张三';
-- 走 idx_name_age 索引找到 id，再回表取 email 等其他列

-- 覆盖索引（查询的列都在索引中）
SELECT username, age FROM users WHERE username = '张三';
-- 只查 username 和 age，都在索引里，不用回表

-- EXPLAIN 中看到 "Using index" 就是覆盖索引
EXPLAIN SELECT username, age FROM users WHERE username = '张三';
-- Extra: Using index

-- 优化技巧：尽量让查询列被索引覆盖
CREATE INDEX idx_cover ON users (username, age, email);
SELECT username, age, email FROM users WHERE username = '张三';  -- 覆盖索引
```

**为什么需要它：** 回表需要额外的磁盘 IO，覆盖索引能显著减少 IO 次数，提升查询性能。

**与相关术语的对比和区分：** 覆盖索引是查询优化的结果，不是一种独立的索引类型。当索引列恰好覆盖了查询列时，就形成了覆盖索引。

---

## 最左前缀原则（Leftmost Prefix Principle）

**一句话定义（大白话）：** 联合索引 (a, b, c) 只有在查询条件从最左边的列开始连续使用时才能生效。

**通俗类比（生活场景）：** 电话簿先按姓排序，姓相同再按名排序。你可以只按姓查（找所有"张"姓），也可以按姓+名查（找"张三"），但不能跳过姓直接按名查（找所有名字叫"三"的人）。

**具体示例：**

```sql
-- 联合索引 idx_a_b_c (a, b, c)

-- ✅ 能用到索引：
WHERE a = 1                          -- 用到 a
WHERE a = 1 AND b = 2               -- 用到 a, b
WHERE a = 1 AND b = 2 AND c = 3    -- 用到 a, b, c
WHERE a = 1 AND c = 3               -- 只用到 a（MySQL 8.0 索引跳跃扫描可能优化）

-- ❌ 不能用到索引：
WHERE b = 2                          -- 跳过了 a
WHERE b = 2 AND c = 3               -- 跳过了 a
WHERE c = 3                          -- 跳过了 a, b

-- ⚠️ 范围查询后的列无法使用索引：
WHERE a = 1 AND b > 10 AND c = 3    -- a 和 b 用到索引，c 用不到

-- 实际应用：根据查询频率调整索引列顺序
-- 如果经常查 WHERE username = ? AND age > 20
-- 建索引 (username, age) 效果最好
```

**为什么需要它：** 这是 B+ 树联合索引的物理结构决定的。理解这个原则能帮你设计出更合理的索引，避免建了索引却用不上。

**与相关术语的对比和区分：** 最左前缀是联合索引的使用规则，覆盖索引是查询结果的优化状态。满足最左前缀是使用索引的前提，覆盖索引是进一步的优化。

## 索引下推（Index Condition Pushdown，ICP）

**一句话定义（大白话）：** 把原本在 server 层做的 WHERE 过滤"下推"到存储引擎层的索引扫描阶段执行，减少回表次数。

**通俗类比（生活场景）：** 原来的流程：你去仓库（索引）取 100 个包裹（回表），回家拆开发现只有 20 个是你想要的。现在的流程：仓库管理员直接帮你过滤好，只给你 20 个，少跑 80 趟。

**具体示例：**

```sql
-- 假设有联合索引 idx_name_age (username, age)
-- 查询：WHERE username LIKE '张%' AND age = 25

-- 没有 ICP 的流程（MySQL 5.6 之前）：
-- 1. 在索引中找到 username LIKE '张%' 的所有记录（比如 100 条）
-- 2. 回表 100 次，拿到完整行
-- 3. 在 server 层过滤 age = 25（最终可能只有 5 条）

-- 有 ICP 的流程（MySQL 5.6+）：
-- 1. 在索引中找到 username LIKE '张%' 的记录
-- 2. 在索引层直接过滤 age = 25（索引里有 age）
-- 3. 只对满足条件的 5 条记录回表

-- EXPLAIN 中看到 "Using index condition" 就是 ICP
EXPLAIN SELECT * FROM users
WHERE username LIKE '张%' AND age = 25;
-- Extra: Using index condition
```

**为什么需要它：** ICP 减少了存储引擎到 server 层的数据传输量，也减少了回表次数。当索引列可以过滤部分条件时，ICP 能显著提升性能。

**与相关术语的对比和区分：** ICP 是 MySQL 5.6 引入的优化，它利用索引中已有的数据提前过滤，减少回表。覆盖索引是完全不回表，ICP 是减少回表。

## EXPLAIN 执行计划

**一句话定义（大白话）：** 用 EXPLAIN 关键字查看 MySQL 如何执行你的 SQL 语句，是查询优化的核心工具。

**通俗类比（生活场景）：** GPS 导航——输入目的地后，它告诉你走哪条路、经过几个路口、预估多长时间。EXPLAIN 就是 SQL 的"导航预览"。

**具体示例：**

```sql
-- 基本用法
EXPLAIN SELECT * FROM users WHERE username = '张三';

-- 输出解读：
-- +----+-------------+-------+------+---------------+------+---------+------+------+----------+-------+
-- | id | select_type | table | type | possible_keys | key  | key_len | ref  | rows | filtered | Extra |
-- +----+-------------+-------+------+---------------+------+---------+------+------+----------+-------+
-- |  1 | SIMPLE      | users | ref  | idx_name      |idx_name| 153   | const|    1 |   100.00 | NULL  |
-- +----+-------------+-------+------+---------------+------+---------+------+------+----------+-------+

-- 关键字段说明：
-- type: 访问类型（system > const > eq_ref > ref > range > index > ALL）
-- key: 实际使用的索引
-- rows: 预估扫描行数
-- Extra: 额外信息（Using index、Using filesort、Using temporary 等）

-- 常见的危险信号：
-- type: ALL          → 全表扫描，需要优化
-- Extra: Using filesort  → 额外排序，需要优化
-- Extra: Using temporary → 使用临时表，需要优化
-- rows: 很大         → 扫描行数太多

-- EXPLAIN ANALYZE（MySQL 8.0+）：显示实际执行时间
EXPLAIN ANALYZE SELECT * FROM users WHERE username = '张三';
```

**为什么需要它：** 写完 SQL 不知道性能如何，EXPLAIN 让你看到 MySQL 的执行策略，发现全表扫描、索引失效等问题。

**与相关术语的对比和区分：** EXPLAIN 是诊断工具，慢查询日志是发现问题的工具。EXPLAIN 看单条 SQL 的执行计划，慢查询日志找出执行时间长的 SQL。

## 慢查询优化

**一句话定义（大白话）：** 找出执行时间超过阈值的 SQL 语句，分析原因并优化的过程。

**通俗类比（生活场景）：** 体检——先通过体检报告（慢查询日志）找出异常指标，再针对性治疗（优化 SQL/索引）。

**具体示例：**

```sql
-- 1. 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过 1 秒记录
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 2. 分析慢查询日志
-- 使用 mysqldumpslow 工具
-- mysqldumpslow -s t -t 10 /var/log/mysql/slow.log  -- 按时间排序取前 10

-- 3. 优化步骤：
-- a) 用 EXPLAIN 查看执行计划
EXPLAIN SELECT * FROM orders
WHERE user_id = 123 AND status = 'paid' AND created_at > '2025-01-01';

-- b) 添加合适的索引
CREATE INDEX idx_user_status_time ON orders (user_id, status, created_at);

-- c) 避免 SELECT *
SELECT id, user_id, amount, status FROM orders
WHERE user_id = 123 AND status = 'paid' AND created_at > '2025-01-01';

-- d) 避免在索引列上做运算
-- ❌ WHERE YEAR(created_at) = 2025
-- ✅ WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'

-- e) 分页优化
-- ❌ SELECT * FROM orders LIMIT 1000000, 10  (要扫描前 100 万行)
-- ✅ SELECT * FROM orders WHERE id > 1000000 LIMIT 10  (走索引)
```

**为什么需要它：** 慢查询是数据库性能的最大杀手。系统变慢时，慢查询日志是最直接的排查入口。

**与相关术语的对比和区分：** 慢查询优化是整体流程，EXPLAIN 是具体手段。慢查询日志发现"哪些 SQL 慢"，EXPLAIN 分析"为什么慢"，索引优化是"怎么改"。

## 索引失效场景

**一句话定义（大白话）：** 明明建了索引，但查询时 MySQL 没有使用，退化成全表扫描。

**通俗类比（生活场景）：** 你给柜子装了锁和钥匙（索引），但钥匙插反了、断了、或者锁孔被堵了（索引失效），最后只能暴力撬锁（全表扫描）。

**具体示例：**

```sql
-- 常见索引失效场景：

-- 1. 对索引列使用函数
-- ❌ WHERE YEAR(created_at) = 2025
-- ✅ WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'

-- 2. 对索引列做运算
-- ❌ WHERE id + 1 = 10
-- ✅ WHERE id = 9

-- 3. 隐式类型转换
-- ❌ WHERE phone = 13800138000  (phone 是 VARCHAR，传了 INT)
-- ✅ WHERE phone = '13800138000'

-- 4. LIKE 以通配符开头
-- ❌ WHERE username LIKE '%三'   (无法使用索引)
-- ✅ WHERE username LIKE '张%'   (可以使用索引)

-- 5. OR 条件中有非索引列
-- ❌ WHERE username = '张三' OR age = 25  (假设 age 没索引)
-- ✅ 改用 UNION：
-- SELECT * FROM users WHERE username = '张三'
-- UNION
-- SELECT * FROM users WHERE age = 25;

-- 6. NOT IN / NOT EXISTS / !=
-- ❌ WHERE status != 'deleted'
-- ⚠️ 这些不一定失效，取决于数据分布，需要 EXPLAIN 验证

-- 7. IS NULL / IS NOT NULL
-- ⚠️ 取决于数据分布和 NULL 值比例

-- 8. 数据量小时优化器选择全表扫描
-- 表只有几百行时，全表扫描可能比走索引更快
```

**为什么需要它：** 索引建了但失效，等于白建。了解失效场景才能写出真正高效的 SQL，避免"我觉得走了索引其实没走"的坑。

**与相关术语的对比和区分：** 索引失效是索引没被使用的结果，最左前缀原则是联合索引失效的一种特定情况。索引失效的范围更广，包括函数、类型转换、数据分布等多种原因。
