# 微服务治理术语百科

> 本文档涵盖微服务架构中的核心治理概念，包括负载均衡、熔断限流、链路追踪和服务网格等。

---

## 1. 服务注册与发现模式

### 一句话定义
服务注册与发现是微服务间动态感知彼此存在的机制，实现服务的自动注册、健康检查和地址查询。

### 通俗类比
就像外卖平台：商家入驻（注册），平台实时监控商家是否在线（健康检查），用户搜索时展示附近可用商家（发现）。

### 具体示例
```java
// 服务注册
@SpringBootApplication
@EnableDiscoveryClient
public class OrderServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }
}

// 服务发现
@FeignClient(name = "inventory-service")
public interface InventoryClient {
    @PostMapping("/api/inventory/deduct")
    Result deduct(@RequestBody DeductDTO dto);
}
```

### 为什么需要它
微服务实例动态扩缩容，手动维护服务地址不现实，需要自动化的发现机制。

### 三种注册模式对比
| 模式 | 代表 | 特点 |
|------|------|------|
| 客户端发现 | Eureka + Ribbon | 客户端负载均衡 |
| 服务端发现 | Nginx + Consul | 中心化负载均衡 |
| DNS发现 | CoreDNS + K8s | 基于DNS解析 |

## 2. 负载均衡（客户端/服务端/代理）

### 一句话定义
负载均衡是将请求均匀分发到多个服务实例的策略，提升系统吞吐和可用性。

### 通俗类比
就像超市收银台：顾客（请求）被引导到不同收银台（服务实例），避免某个收银台排长队。

### 具体示例
```java
// 客户端负载均衡（Ribbon）
@LoadBalanced
@Bean
public RestTemplate restTemplate() {
    return new RestTemplate();
}

// 轮询策略
ribbon:
  listOfServers: localhost:8080,localhost:8081
  NFLoadBalancerRuleClassName: com.netflix.loadbalancer.RoundRobinRule

// 服务端负载均衡（Nginx）
upstream order-service {
    server 192.168.1.101:8080;
    server 192.168.1.102:8080;
    server 192.168.1.103:8080;
}
```

### 为什么需要它
单实例无法承受高并发，负载均衡将流量分散到多实例，提升整体处理能力。

### 负载均衡策略对比
| 策略 | 算法 | 适用场景 |
|------|------|----------|
| 轮询 | 依次分发 | 实例性能一致 |
| 加权轮询 | 按权重分发 | 实例性能不同 |
| 随机 | 随机选择 | 无状态服务 |
| 最少连接 | 选择连接最少的 | 长连接场景 |
| IP哈希 | 同IP固定实例 | 会话保持 |

## 3. 熔断器模式（Hystrix/Resilience4j/Sentinel）

### 一句话定义
熔断器模式通过快速失败防止故障级联，保护系统整体稳定性。

### 通俗类比
就像家庭电路的保险丝：电流过大时自动断电（熔断），避免烧毁整个电路。等故障排除后，再手动合闸恢复。

### 具体示例
```java
// Resilience4j熔断器配置
@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallback")
public Result deductInventory(DeductDTO dto) {
    return inventoryClient.deduct(dto);
}

// 降级方法
public Result fallback(DeductDTO dto, Throwable t) {
    return Result.fail("库存服务暂时不可用，请稍后重试");
}

// 熔断器配置
resilience4j.circuitbreaker:
  instances:
    inventoryService:
      slidingWindowSize: 100
      failureRateThreshold: 50
      waitDurationInOpenState: 10s
```

### 为什么需要它
一个服务故障可能导致整个调用链阻塞，熔断器快速失败，避免雪崩效应。

### 三大熔断器对比
| 特性 | Hystrix | Resilience4j | Sentinel |
|------|---------|--------------|----------|
| 维护状态 | 停止维护 | 活跃 | 活跃 |
| 信号量 | 不支持 | 支持 | 支持 |
| 限流 | 不支持 | 不支持 | 内置 |
| Dashboard | 有 | 无 | 有 |

## 4. 限流（令牌桶/漏桶/滑动窗口/RateLimiter）

### 一句话定义
限流是控制请求速率，防止系统被突发流量压垮的保护机制。

### 通俗类比
就像高速公路入口：无论路上有多少车，每次只放行固定数量（令牌桶），确保车流平稳进入。

### 具体示例
```java
// 令牌桶算法（Guava RateLimiter）
RateLimiter rateLimiter = RateLimiter.create(100); // 每秒100个请求

if (rateLimiter.tryAcquire()) {
    // 获取令牌成功，处理请求
    processRequest(request);
} else {
    // 令牌不足，拒绝请求
    throw new RateLimitException("请求过于频繁");
}

// Sentinel限流配置
@SentinelResource(
    value = "orderCreate",
    blockHandler = "blockHandler"
)
public Result createOrder(OrderDTO dto) {
    return orderService.create(dto);
}
```

### 为什么需要它
突发流量可能导致系统资源耗尽，限流保护系统在可承受范围内运行。

### 限流算法对比
| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 令牌桶 | 按速率生成令牌 | 允许突发 | 实现复杂 |
| 漏桶 | 固定速率流出 | 流量平滑 | 不允许突发 |
| 滑动窗口 | 统计时间窗口请求数 | 精确 | 内存消耗大 |
| 固定窗口 | 统计固定时间窗口 | 简单 | 有临界问题 |

## 5. 降级策略（自动降级/手动降级/读降级/写降级）

### 一句话定义
降级策略是在系统压力过大时，主动关闭非核心功能，保障核心业务可用。

### 通俗类比
就像商场打折促销：人太多时，先关闭美食区（非核心），只保留购物区（核心），加快疏散速度。

### 具体示例
```java
// 自动降级：根据系统指标触发
@Component
public class DegradeStrategy {
    @EventListener
    public void onHighLoad(SystemLoadEvent event) {
        if (event.getCpuUsage() > 80) {
            // 自动关闭推荐功能
            featureToggle.disable("recommendation");
            // 自动降级到缓存
            enableCacheOnlyMode();
        }
    }
}

// 手动降级：控制台一键降级
@PostMapping("/admin/degrade")
public Result manualDegrade(@RequestParam String service) {
    degradeService.activate(service);
    return Result.ok("已降级");
}
```

### 为什么需要它
系统压力过大时，与其全部崩溃，不如牺牲非核心功能保证核心业务。

### 降级策略对比
| 策略 | 触发方式 | 适用场景 |
|------|----------|----------|
| 自动降级 | 系统指标 | 可预测的故障 |
| 手动降级 | 人工操作 | 不可预测的故障 |
| 读降级 | 读操作时 | 数据读取压力大 |
| 写降级 | 写操作时 | 数据写入压力大 |

## 6. 链路追踪（Jaeger/Zipkin/SkyWalking/OpenTelemetry）

### 一句话定义
链路追踪是监控分布式系统中请求完整调用链路的工具，帮助定位性能瓶颈和故障点。

### 通俗类比
就像快递物流追踪：从下单开始，每个环节（发货、中转、派送）都有记录，你能看到包裹当前在哪一步。

### 具体示例
```java
// SkyWalking链路追踪
@Trace
@Tag("order.create")
public Order createOrder(OrderDTO dto) {
    // 自动记录调用链路
    Order order = orderService.create(dto);
    inventoryClient.deduct(dto.getItems()); // 自动追踪
    paymentClient.charge(dto.getPayment()); // 自动追踪
    return order;
}

// OpenTelemetry
Tracer tracer = GlobalOpenTelemetry.getTracer("order-service");
Span span = tracer.spanBuilder("createOrder").startSpan();
try (Scope scope = span.makeCurrent()) {
    // 业务逻辑
} finally {
    span.end();
}
```

### 为什么需要它
微服务调用链复杂，链路追踪帮助快速定位是哪个环节出了问题。

### 四大追踪工具对比
| 特性 | Jaeger | Zipkin | SkyWalking | OpenTelemetry |
|------|--------|--------|------------|---------------|
| 协议 | OpenTracing | Zipkin | 私有 | OpenTelemetry |
| 语言支持 | 多语言 | 多语言 | Java优先 | 多语言 |
| UI | 完善 | 完善 | 完善 | 无（需配合） |
| 采样 | 支持 | 支持 | 支持 | 支持 |

## 7. 配置中心（动态配置/配置版本/灰度发布）

### 一句话定义
配置中心集中管理微服务配置，支持动态更新、版本管理和灰度发布。

### 通俗类比
就像酒店中央空调系统：前台可以统一调整所有房间温度（动态配置），修改前可以查看历史设置（版本管理），可以先调整部分楼层试试（灰度发布）。

### 具体示例
```yaml
# Nacos灰度发布配置
spring:
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        namespace: prod
        group: DEFAULT_GROUP
        data-id: order-service.yml

# 动态配置监听
@RefreshScope
@RestController
public class ConfigController {
    @Value("${order.timeout:30}")
    private int orderTimeout;
    
    // 配置变更时自动更新
}
```

### 为什么需要它
配置散落在各服务中，修改需要重启，无法快速响应运营需求。

### 配置中心能力对比
| 能力 | Apollo | Nacos | Spring Cloud Config |
|------|--------|-------|---------------------|
| 动态更新 | 支持 | 支持 | 需Refresh |
| 版本管理 | 支持 | 支持 | Git管理 |
| 灰度发布 | 支持 | 支持 | 不支持 |
| 配置回滚 | 支持 | 支持 | 不支持 |

## 8. API网关（路由/认证/限流/日志/转换）

### 一句话定义
API网关是微服务架构的统一入口，负责路由转发、安全认证、流量控制和协议转换。

### 通俗类比
就像机场安检：所有乘客（请求）都要经过安检口（网关），检查身份证（认证）、控制人流（限流）、安排登机口（路由）。

### 具体示例
```yaml
# Spring Cloud Gateway配置
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200

# 认证过滤器
@Component
public class AuthFilter implements GlobalFilter {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (!validate(token)) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
        return chain.filter(exchange);
    }
}
```

### 为什么需要它
微服务对外暴露众多接口，需要统一入口进行安全管控和流量治理。

### API网关对比
| 特性 | Spring Cloud Gateway | Kong | Zuul |
|------|---------------------|------|------|
| 性能 | 高 | 高 | 中 |
| 扩展性 | 插件化 | 插件化 | 过滤器 |
| 语言 | Java | Lua | Java |
| 社区 | 活跃 | 活跃 | 维护模式 |

## 9. 服务网格（Service Mesh/Istio/Envoy）

### 一句话定义
服务网格是处理服务间通信的基础设施层，将网络功能从业务代码中抽离到Sidecar代理。

### 通俗类比
就像每个房间都配了专属管家（Sidecar）：客人（服务）不需要自己处理安保、清洁、快递（网络功能），都由管家代劳。

### 具体示例
```yaml
# Istio服务网格配置
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: order-service
spec:
  hosts:
    - order-service
  http:
    - route:
        - destination:
            host: order-service
            subset: v1
          weight: 90
        - destination:
            host: order-service
            subset: v2
          weight: 10
```

### 为什么需要它
微服务间通信逻辑分散在各服务中，难以统一管理和治理，服务网格将网络功能下沉到基础设施层。

### 服务网格组件对比
| 组件 | Istio | Consul Connect | Linkerd |
|------|-------|----------------|---------|
| 数据面 | Envoy | Envoy | Linkerd2-proxy |
| 控制面 | istiod | Consul | linkerd |
| 功能 | 丰富 | 基础 | 精简 |
| 复杂度 | 高 | 低 | 中 |

## 10. 灰度发布（金丝雀/蓝绿/A-B测试）

### 一句话定义
灰度发布是将新版本逐步推送给部分用户，验证无问题后再全量发布的部署策略。

### 通俗类比
就像餐厅试菜：新菜先给VIP顾客试吃（金丝雀），没问题再上菜单；或者同时准备两个厨房，一个做新菜一个做旧菜（蓝绿）。

### 具体示例
```yaml
# 金丝雀发布配置（Nginx）
upstream order-service {
    server 192.168.1.101:8080 weight=90; # 旧版本
    server 192.168.1.102:8080 weight=10; # 新版本
}

# K8s蓝绿部署
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service-v2
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-service
      version: v2
```

### 为什么需要它
一次性全量发布风险高，灰度发布可控制影响范围，快速回滚。

### 灰度发布策略对比
| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 金丝雀 | 小比例流量验证 | 风险低 | 验证周期长 |
| 蓝绿 | 两套环境切换 | 回滚快 | 资源消耗大 |
| A-B测试 | 按用户特征分流 | 精准 | 实现复杂 |
| 滚动更新 | 逐步替换实例 | 平滑 | 回滚慢 |
