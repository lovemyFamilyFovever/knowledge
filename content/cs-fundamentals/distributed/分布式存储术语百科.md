# 分布式存储术语百科

> 本文档涵盖分布式存储领域的核心概念，包括数据分片、副本机制、共识算法和一致性模型。

---

## 1. 数据分片（Hash分片/范围分片/一致性哈希）

### 一句话定义
数据分片是将大规模数据按规则拆分到多个存储节点上的技术，是水平扩展的基础。

### 通俗类比
就像图书馆把书籍按拼音首字母分到不同楼层：A-F在一楼，G-M在二楼...查找时直接去对应楼层，不用翻遍整个图书馆。

### 具体示例
```java
// Hash分片示例
int shardIndex = hash(userId) % shardCount;
// userId=1001, hash后=5768, shardCount=16
// 分片索引 = 5768 % 16 = 8，路由到第8个节点

// 一致性哈希：节点增减只影响相邻节点的数据
ConsistentHash ring = new ConsistentHash();
ring.addNode("node1");
ring.addNode("node2");
// 新增node3时，只迁移部分数据而非全部
```

### 为什么需要它
单机存储容量和性能有上限，分片后数据分散到多节点，大幅提升存储容量和读写吞吐。

### 分片策略对比
| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| Hash分片 | 取模哈希 | 数据均匀 | 扩容迁移复杂 |
| 范围分片 | 按区间划分 | 范围查询快 | 容易热点 |
| 一致性哈希 | 哈希环 | 扩容平滑 | 实现复杂 |

## 2. 数据副本（主从复制/多主复制/无主复制）

### 一句话定义
数据副本是将同一份数据复制到多个节点，以提高可靠性和读性能的技术。

### 通俗类比
就像重要文件复印多份存放在不同地方——即使一处着火，其他地方还有备份。

### 具体示例
```sql
-- MySQL主从复制配置
-- Master配置
CHANGE MASTER TO
  MASTER_HOST='192.168.1.100',
  MASTER_USER='repl',
  MASTER_AUTO_POSITION=1;

-- 从库读取，主库写入
-- 应用层路由
if (isWriteOperation) {
    routeToMaster();
} else {
    routeToSlave(); // 读写分离
}
```

### 为什么需要它
单点故障会导致服务不可用，副本机制提供数据冗余，主从分离还能提升读性能。

### 副本策略对比
| 类型 | 原理 | 一致性 | 可用性 | 适用场景 |
|------|------|--------|--------|----------|
| 主从复制 | 一主多从 | 强 | 中 | 读多写少 |
| 多主复制 | 多个主节点可写 | 弱 | 高 | 多机房 |
| 无主复制 | 任意节点可写 | 可调 | 最高 | 高可用要求 |

## 3. Raft共识算法（Leader选举/日志复制/安全性）

### 一句话定义
Raft是一种易于理解的分布式共识算法，通过Leader选举确保集群对数据变更达成一致。

### 通俗类比
就像班级选班长：先投票选出班长（Leader选举），班长记录班级决议并通知每个同学（日志复制），确保大家记录一致。

### 具体示例
```
// Raft三种角色
Follower  →  Candidate  →  Leader
  ↑              ↑           |
  └──────────────┴───────────┘

// 状态转换示例
Node A: Follower (term=1)
Node A: 超时未收到心跳 → Candidate (term=2)
Node A: 获得多数投票 → Leader (term=2)
Node A: 广播心跳，其他节点确认 → Follower
```

### 为什么需要它
分布式系统中节点可能宕机，Raft通过多数派投票机制保证集群在部分节点故障时仍能正常工作。

### Raft关键机制
| 机制 | 说明 | 目的 |
|------|------|------|
| Leader选举 | 超时触发投票 | 选出唯一Leader |
| 日志复制 | Leader同步Follower | 保证数据一致 |
| 安全性 | 新Leader包含所有已提交日志 | 数据不丢失 |

## 4. Paxos算法（Basic Paxos/Multi-Paxos）

### 一句话定义
Paxos是解决分布式共识问题的经典算法，通过两阶段提案实现多数派一致。

### 通俗类比
就像大家商量聚餐地点：先收集提议（Prepare阶段），再投票确认（Accept阶段），最终所有人去同一家餐厅。

### 具体示例
```
// Basic Paxos两阶段
Phase 1 (Prepare):
  Proposer: "我要提议值X，请大家承诺不接受更早的提案"
  Acceptor: "好的，我承诺只接受编号>=N的提案"

Phase 2 (Accept):
  Proposer: "请接受提案(N, X)"
  Acceptor: "我接受，值为X"

// Multi-Paxos优化：选一个稳定的Leader，减少Prepare阶段
```

### 为什么需要它
分布式系统需要对某个值达成共识，Paxos提供了理论上的最优解。

### Basic vs Multi-Paxos
| 特性 | Basic Paxos | Multi-Paxos |
|------|-------------|-------------|
| 决策次数 | 单值 | 多值 |
| 性能 | 低 | 高 |
| Leader | 无 | 有稳定Leader |
| 复杂度 | 中 | 高 |

## 5. ZAB协议（ZooKeeper Atomic Broadcast）

### 一句话定义
ZAB是ZooKeeper使用的原子广播协议，基于主从架构实现数据一致性和崩溃恢复。

### 通俗类比
就像广播电台：主持人（Leader）播报新闻，所有频道（Follower）同步转播。如果主持人掉线，自动选举新的主持人继续广播。

### 具体示例
```
// ZAB工作流程
1. Leader选举 → 选出ZXID最大的节点
2. 数据同步 → 新Leader同步历史数据给Follower
3. 原子广播 → 写操作通过2PC提交
4. 崩溃恢复 → Leader挂掉，重新选举

// ZXID = 事务ID，保证全局顺序
ZXID = 64位
  高32位：epoch（纪元）
  低32位：counter（计数器）
```

### 为什么需要它
ZooKeeper需要保证分布式环境下数据的顺序一致性和持久性，ZAB是其实现基础。

### ZAB vs Raft
| 特性 | ZAB | Raft |
|------|-----|------|
| Leader选举 | ZXID最大者 | 随机超时投票 |
| 数据同步 | 2PC | Leader推送 |
| 应用 | ZooKeeper | etcd, Consul |
| 理解难度 | 较高 | 较低 |

## 6. Gossip协议（最终一致性/反熵/谣言传播）

### 一句话定义
Gossip协议是节点间通过随机交换信息，最终达到数据一致的去中心化通信协议。

### 通俗类比
就像谣言传播：你告诉3个朋友，他们每人再告诉3个朋友，很快整个村子都知道了——虽然不是立刻知道，但最终所有人都会知道。

### 具体示例
```java
// Gossip协议工作流程
// 节点A随机选择3个节点发送自己的状态
Node A -> [Node B, Node F, Node H] = {A: state_v1}
Node B -> [Node C, Node D, Node A] = {A: state_v1, B: state_v2}
// 经过多轮传播，所有节点最终状态一致

// Cassandra中的Gossip
// 每1秒随机选1个节点交换信息
// 每次交换携带最新心跳信息
```

### 为什么需要它
中心化架构存在单点瓶颈，Gossip去中心化设计使其适用于大规模、动态变化的集群。

### Gossip三种变体
| 变体 | 机制 | 用途 |
|------|------|------|
| 反熵 | 定期全量同步 | 数据修复 |
| 谣言传播 | 事件驱动传播 | 状态通知 |
| 推拉结合 | 双向交换 | 高效同步 |

## 7. 最终一致性 vs 强一致性

### 一句话定义
- **强一致性**：数据更新后，所有读操作都能立即看到最新值
- **最终一致性**：数据更新后，经过一段时间延迟，最终所有节点都能读到最新值

### 通俗类比
- **强一致性**：银行转账后，余额立刻更新（实时同步）
- **最终一致性**：社交平台点赞数可能延迟几秒才更新（允许短暂不一致）

### 具体示例
```java
// 强一致性：ZooKeeper写后读
zk.create("/config", "v1", ...);
String data = zk.getData("/config", false, null); // 立即读到v1

// 最终一致性：DNS解析
// 修改DNS记录后，全球可能需要几分钟才能全部生效
```

### 为什么需要它
不同业务对一致性要求不同，理解两者区别有助于选择合适的架构方案。

### 对比
| 特性 | 强一致性 | 最终一致性 |
|------|----------|------------|
| 读延迟 | 高 | 低 |
| 写延迟 | 高 | 低 |
| 可用性 | 低 | 高 |
| 适用场景 | 金融交易 | 社交动态 |

---

## 8. 线性一致性 vs 顺序一致性

### 一句话定义
- **线性一致性**：所有操作表现得像在单机上按真实时间顺序执行
- **顺序一致性**：所有操作按某个全局顺序执行，但不要求与真实时间一致

### 通俗类比
- **线性一致性**：全班同学必须按老师点名顺序回答问题
- **顺序一致性**：大家按自己报名顺序回答，只要最终顺序合理即可

### 具体示例
```
// 线性一致性示例
时间线：
  T1: ClientA 写 x=1
  T2: ClientB 读 x → 必须返回1

// 顺序一致性示例
ClientA: 写x=1, 写y=2
ClientB: 读x, 读y
// 可以返回 (1,2) 或 (1,1)，只要保证ClientB看到的顺序与ClientA写入顺序一致
```

### 为什么需要它
不同一致性级别对性能影响不同，选择合适级别可平衡一致性和性能。

### 对比
| 特性 | 线性一致性 | 顺序一致性 |
|------|------------|------------|
| 时间约束 | 真实时间 | 逻辑顺序 |
| 性能 | 较低 | 较高 |
| 实现复杂度 | 高 | 中 |
| 适用场景 | 分布式锁 | 日志系统 |

## 9. 读写一致性（Read-Your-Writes）

### 一句话定义
Read-Your-Writes保证用户读操作总能看到自己最新写入的数据。

### 通俗类比
你在论坛发了帖子，刷新页面一定能立即看到自己发的帖子——这就是读写一致性。

### 具体示例
```java
// 读写一致性实现
// 策略1：读自己写过的主节点
public Data readData(String userId) {
    String masterNode = getMasterNode(userId);
    return readFromNode(masterNode); // 总是从写入的节点读
}

// 策略2：读写分离时，写后强制读主
if (recentlyWritten) {
    return readFromMaster();
} else {
    return readFromSlave(); // 可以负载均衡
}
```

### 为什么需要它
用户体验要求自己操作的结果能立即可见，否则会造成困惑。

### 与其他一致性对比
| 一致性 | 保证范围 | 实现复杂度 |
|--------|----------|------------|
| Read-Your-Writes | 自己的写入 | 低 |
| Monotonic Read | 读单调递增 | 中 |
| Consistent Prefix | 前缀一致 | 中 |

## 10. 会话一致性

### 一句话定义
会话一致性保证在同一会话（或连接）内，读操作能看到该会话内之前写入的数据。

### 通俗类比
就像你和客服的聊天记录：在同一个对话窗口内，你发的消息客服一定能立即看到。

### 具体示例
```java
// 会话一致性实现
public class SessionConsistencyCache {
    private Map<String, String> sessionCache = new ConcurrentHashMap<>();
    
    // 写入时同时更新会话缓存
    public void write(String key, String value) {
        db.write(key, value);
        sessionCache.put(key, value); // 会话内立即可见
    }
    
    // 读取时优先从会话缓存读
    public String read(String key) {
        if (sessionCache.containsKey(key)) {
            return sessionCache.get(key); // 会话内一致
        }
        return db.read(key);
    }
}
```

### 为什么需要它
多实例环境下，用户的读写可能落到不同节点，会话一致性保证体验连贯。

### 与其他一致性对比
| 一致性 | 保证范围 | 跨会话 |
|--------|----------|--------|
| Read-Your-Writes | 自己的写入 | 否 |
| 会话一致性 | 当前会话 | 否 |
| 因果一致性 | 因果关系 | 是 |

## 11. Quorum机制（NRW策略）

### 一句话定义
Quorum机制通过NRW策略（N总副本数、R读副本数、W写副本数）控制数据一致性和可用性。

### 通俗类比
就像班级投票：30个同学（N），15票通过（R），15票以上才算有效（W）——确保多数人意见被采纳。

### 具体示例
```java
// Quorum机制配置
int N = 3; // 3个副本
int W = 2; // 写入2个节点才算成功
int R = 2; // 读取2个节点取最新

// 一致性公式：W + R > N
// 2 + 2 > 3 → 保证读到最新数据

// 如果 W + R <= N，则可能读到旧数据
// 但可用性更高（允许部分节点故障）
```

### 为什么需要它
通过调整NRW参数，可以在一致性和可用性之间灵活权衡。

### NRW策略对比
| 策略 | N | W | R | 一致性 | 可用性 |
|------|---|---|---|--------|--------|
| 强一致 | 3 | 3 | 1 | 强 | 低 |
| 高可用 | 3 | 1 | 1 | 弱 | 高 |
| 平衡 | 3 | 2 | 2 | 强 | 中 |

## 12. 数据一致性模型对比

### 一句话定义
数据一致性模型定义了分布式系统中数据可见性和更新顺序的保证级别。

### 通俗类比
就像不同社交平台的评论刷新机制：有的立即显示（强一致），有的需要刷新（最终一致），有的按时间线显示（顺序一致）。

### 具体示例
```
// 不同一致性模型的应用场景
强一致性: 银行转账、库存扣减
顺序一致性: 日志系统、消息队列
因果一致性: 社交平台评论
最终一致性: DNS、CDN缓存

// 一致性级别选择原则
if (数据敏感度 == "高") {
    选择强一致性;
} else if (可用性要求 == "高") {
    选择最终一致性;
} else {
    选择因果一致性;
}
```

### 为什么需要它
不同业务场景对一致性要求不同，理解各模型有助于做出正确的架构选择。

### 一致性模型对比表
| 模型 | 保证 | 性能 | 适用场景 |
|------|------|------|----------|
| 线性一致性 | 读写全局顺序 | 低 | 金融交易 |
| 顺序一致性 | 进程内顺序 | 中 | 日志系统 |
| 因果一致性 | 因果关系 | 中 | 社交平台 |
| 最终一致性 | 最终相同 | 高 | DNS/CDN |
| Read-Your-Writes | 自己可见 | 高 | 用户操作 |

---

> 📌 **学习建议**：建议先理解CAP定理作为理论基础，再逐一掌握各一致性模型。Raft算法是面试高频考点，建议重点理解Leader选举和日志复制机制。实践中优先掌握Quorum机制和最终一致性，这些在实际项目中最常用。
