# 操作系统基础术语

## 进程（Process）

**一句话定义：** 程序被加载到内存中运行起来后，就变成了一个进程，它是操作系统分配资源的基本单位。

**通俗类比：** 就像你在厨房里炒菜——菜谱是程序，你真正开始炒菜的动作就是一个"进程"。每道菜占用灶台、锅、铲子，这些就是系统资源。

**具体示例：**
```bash
# 查看当前所有进程
ps aux
# 启动一个进程
python3 app.py
# 查看进程树
pstree
```

**为什么需要它：** 操作系统需要区分"哪个程序正在运行"，才能合理分配 CPU 时间、内存等资源。没有进程概念，多个程序就会互相踩踏内存、互相干扰。

---

## 线程（Thread）

**一句话定义：** 线程是进程内部的一个执行单元，同一进程内的多个线程共享内存空间和资源。

**通俗类比：** 进程是餐厅，线程就是餐厅里的服务员。多个服务员（线程）共享同一间餐厅的厨房、桌椅（内存），各自接待不同的客人。

**具体示例：**
```python
import threading

def worker():
    print("线程正在执行任务")

# 创建并启动线程
t = threading.Thread(target=worker)
t.start()
```

**为什么需要它：** 单线程程序一次只能做一件事。多线程可以让程序同时处理多个任务（如 Web 服务器同时响应多个用户请求），大幅提升效率。

---

## 协程（Coroutine）

**一句话定义：** 协程是比线程更轻量的用户态执行体，可以在执行过程中主动挂起、恢复，实现协作式调度。

**通俗类比：** 线程像多个厨师同时炒菜（抢占式），协程像一个厨师同时炒三道菜——炒一会儿 A 菜，主动停下来去翻 B 菜，再回来继续炒 A。切换完全由自己控制。

**具体示例：**
```python
import asyncio

async def fetch_data():
    await asyncio.sleep(1)  # 主动让出控制权
    return "数据已获取"

asyncio.run(fetch_data())
```

**为什么需要它：** 线程切换开销大（内核态切换）。协程在用户态切换，创建和切换成本极低，一个进程可以轻松创建数万个协程，特别适合高并发 I/O 场景。

---

## 进程与线程的区别

| 对比维度 | 进程 | 线程 |
|---------|------|------|
| 内存空间 | 独立地址空间 | 共享所属进程的内存 |
| 创建开销 | 大（需分配独立内存） | 小（共享内存） |
| 切换开销 | 大（涉及内核态） | 小（用户态即可） |
| 通信方式 | IPC（管道/消息队列/共享内存） | 直接读写共享变量 |
| 崩溃影响 | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能导致整个进程崩溃 |
| 资源分配 | 操作系统分配资源的基本单位 | CPU 调度的基本单位 |

**图示关系：**
```
进程A
├── 线程1（独立栈、共享堆）
├── 线程2
└── 线程3

进程B
├── 线程1
└── 线程2
```

## 上下文切换（Context Switch）

**一句话定义：** CPU 从一个进程/线程切换到另一个时，需要保存当前状态、恢复下一个任务状态的过程。

**通俗类比：** 就像你在做两件事——写报告和回邮件。切换时，你得先记住"写到第几行了"，然后去回邮件，回完再回忆"刚才写到哪里了"继续写。

**具体示例：**
```bash
# 查看上下文切换次数
vmstat 1
# 或
cat /proc/stat
```

**为什么需要它：** CPU 是分时复用的，通过快速切换让多个任务"看起来"同时运行。切换越频繁，系统吞吐量可能下降，因为每次切换都有成本。

---

## 中断（Interrupt）

**一句话定义：** 硬件或软件向 CPU 发出的信号，迫使 CPU 暂停当前工作，转去处理紧急事件。

**通俗类比：** 你正在看书，门铃响了（硬件中断），你得放下书去开门；或者你发现闹钟响了（软件中断），放下手头工作先处理提醒。

**具体示例：**
```bash
# 查看中断统计
cat /proc/interrupts
# 查看软中断
cat /proc/softirqs
```

**为什么需要它：** 没有中断，CPU 就必须不断轮询设备状态，效率极低。中断让 CPU 只在需要时才响应，大幅提高效率。

---

## 系统调用（System Call）

**一句话定义：** 用户程序请求操作系统内核提供服务的接口，是用户态进入内核态的唯一合法入口。

**通俗类比：** 你去政府办事，不能直接闯进办公室，必须通过窗口提交申请（系统调用），由工作人员（内核）代为处理。

**具体示例：**
```c
// C语言中的系统调用示例
#include <unistd.h>
write(1, "Hello\n", 6);  // write 是系统调用
```

```bash
# 用 strace 跟踪程序的系统调用
strace ls
```

**为什么需要它：** 操作系统需要隔离用户程序和内核，防止程序直接操作硬件或破坏内核数据。系统调用提供了一道受控的"门"。

---

## 用户态与内核态

**一句话定义：** CPU 运行的两种特权级别——用户态只能执行普通指令，内核态可以执行所有特权指令。

**通俗类比：** 用户态像普通员工只能使用办公电脑；内核态像系统管理员，可以修改系统配置、格式化硬盘等高权限操作。

**具体示例：**
```bash
# 查看进程的特权级别
ps -eo pid,ni,comm
# nice值为-20的进程具有更高优先级（需要权限调整）
```

**为什么需要它：** 如果所有程序都能随意操作硬件，一个程序的 bug 可能导致整个系统崩溃。特权级别划分保护了系统的稳定性和安全性。

---

## 虚拟内存（Virtual Memory）

**一句话定义：** 每个进程看到的"假"内存地址空间，由操作系统和硬件映射到实际物理内存或磁盘。

**通俗类比：** 你有一张银行卡（虚拟地址），背后对应银行金库的实际钞票（物理内存）。你不需要知道钞票具体放在哪个保险箱，银行帮你转接。

**具体示例：**
```bash
# 查看进程的虚拟内存使用
pmap <pid>
# 查看系统虚拟内存统计
vmstat
```

**为什么需要它：** 物理内存有限，多个进程不能同时全部装入内存。虚拟内存让每个进程都以为自己独占一大块内存，实际按需加载，超出部分暂存磁盘（swap）。

---

## 页表（Page Table）

**一句话定义：** 记录虚拟地址到物理地址映射关系的数据结构，由操作系统维护，硬件（MMU）使用。

**通俗类比：** 页表就像一本"翻译词典"，把虚拟地址（英文）翻译成物理地址（中文），CPU 每次访问内存都要查这本词典。

**具体示例：**
```bash
# 查看进程的页表信息（需要 root）
cat /proc/<pid>/maps
# 查看页表统计
grep -i pagetables /proc/meminfo
```

**为什么需要它：** 进程使用虚拟地址，但 CPU 最终要访问物理内存。页表是实现虚拟地址到物理地址翻译的关键数据结构。

---

## 页面置换算法（LRU/LFU/FIFO）

**一句话定义：** 当物理内存不够时，决定淘汰哪个页面（内存页）以腾出空间给新页面的策略。

| 算法 | 策略 | 类比 |
|------|------|------|
| **LRU**（最近最少使用） | 淘汰最久没被访问的页面 | 图书馆清理最久没人借的书 |
| **LFU**（最不经常使用） | 淘汰访问次数最少的页面 | 清理借阅量最低的书 |
| **FIFO**（先进先出） | 淘汰最早进入内存的页面 | 食堂排队，最先排队的最先走 |

**为什么需要它：** 内存有限，必须有策略决定淘汰谁。算法好坏直接影响系统性能——好的算法能最大化命中率，减少磁盘 I/O。

---

## 内存分页与分段

**分页：** 把内存切成固定大小的块（如 4KB），方便管理和分配。
**分段：** 按程序逻辑划分内存区域（代码段、数据段、栈段）。

**通俗类比：** 分页像把一整块蛋糕切成等大的小块方便分发；分段像按口味（巧克力/奶油/水果）来分区摆放。

**为什么需要它：** 分页解决了外部碎片问题，分段更符合程序的逻辑结构。现代系统通常采用"段页式"结合两者优点。

---

## 内存映射（mmap）

**一句话定义：** 将文件或设备映射到进程的虚拟地址空间，对内存的读写等同于对文件的读写。

**通俗类比：** 你有一个大文件，mmap 就像把文件内容"投射"到你面前的白板上，直接在白板上读写，内容自动同步回文件。

**具体示例：**
```c
#include <sys/mman.h>
void *addr = mmap(NULL, length, PROT_READ | PROT_WRITE,
                   MAP_SHARED, fd, 0);
```

**为什么需要它：** 传统 read/write 需要数据在内核缓冲区和用户缓冲区之间拷贝两次。mmap 避免了这次拷贝，大幅提高大文件的 I/O 性能。

---

## 死锁（Deadlock）

**一句话定义：** 两个或多个进程互相持有对方需要的资源，又都在等待对方释放，导致所有进程永远无法继续执行。

**通俗类比：** 两人在窄路上相遇，A 说"你先让"，B 说"你先让"，谁都不肯退，结果谁也过不去。

**死锁的四个必要条件：**
1. **互斥**：资源不能同时被多个进程使用
2. **占有并等待**：持有资源的进程还在等待其他资源
3. **不可剥夺**：已获得的资源不能被强制收回
4. **循环等待**：进程之间形成等待环

**预防/检测/恢复：**
- **预防**：破坏四个条件之一（如按固定顺序获取资源）
- **检测**：用资源分配图检测是否存在环
- **恢复**：终止进程或剥夺资源

---

## 信号量（Semaphore）

**一句话定义：** 一个整型变量，通过 P（wait）和 V（signal）操作来控制多个进程对共享资源的访问。

**通俗类比：** 停车场入口有计数器——有车进来减1，有车出去加1。计数为0时，新来的车必须等待。

**具体示例：**
```python
import threading

sem = threading.Semaphore(3)  # 最多允许3个线程同时访问

def access_resource():
    with sem:
        print("正在使用资源")
```

**为什么需要它：** 简单的互斥锁只能控制"一个或零个"，信号量可以控制"多个"同时访问的上限，更灵活。

---

## 互斥锁（Mutex）

**一句话定义：** 保证同一时刻只有一个线程能访问共享资源的同步机制。

**通俗类比：** 卫生间的门锁——一个人进去后锁上门，其他人只能在外面等，里面的人出来后锁解开，下一个人才能进去。

**具体示例：**
```python
lock = threading.Lock()

lock.acquire()    # 加锁
try:
    # 临界区代码
    counter += 1
finally:
    lock.release()  # 解锁
```

**为什么需要它：** 多线程并发修改共享变量会导致数据竞争（race condition），互斥锁保证了操作的原子性。

---

## 条件变量（Condition Variable）

**一句话定义：** 用于线程之间通信的机制，允许一个线程等待某个条件成立，由另一个线程通知它。

**通俗类比：** 你在餐厅等位（wait），服务员说"有桌了叫你"（signal）。你不用一直盯着，叫到你再去。

**具体示例：**
```python
import threading

cond = threading.Condition()
ready = False

def waiter():
    with cond:
        while not ready:
            cond.wait()  # 等待条件满足
        print("条件已满足，继续执行")

def notifier():
    global ready
    with cond:
        ready = True
        cond.notify()  # 通知等待的线程
```

**为什么需要它：** 互斥锁只能"锁住"或"放开"，不能表达"等待某个条件成立"的语义。条件变量弥补了这个不足。

---

## 自旋锁（Spinlock）

**一句话定义：** 线程在获取锁失败时不挂起，而是不断循环重试（"自旋"），直到获取到锁。

**通俗类比：** 你在门口等厕所，不坐下休息，而是站在门口每隔几秒推一下门看看有没有空。

**与互斥锁的区别：**
| 对比维度 | 自旋锁 | 互斥锁 |
|---------|--------|--------|
| 等待方式 | 忙等（CPU 空转） | 挂起（让出 CPU） |
| 适用场景 | 锁持有时间极短 | 锁持有时间较长 |
| 开销 | 线程切换开销小 | 线程切换开销大 |
| 风险 | 长时间自旋浪费 CPU | 频繁切换也浪费资源 |

**为什么需要它：** 在多处理器系统中，如果锁持有时间很短（纳秒级），线程切换的开销可能比自旋等待更大。自旋锁在这种场景下更高效。
