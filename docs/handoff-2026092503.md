## ⑤ 踩过的坑（绝对不要再踩）

1. **无头浏览器里 `.focus()` 不一定送 focus 事件**。这台机器上 `document.hasFocus()` 是 `false`，`inp.focus()` 只把 `activeElement` 挪过去，`addEventListener('focus')` 收不到 —— 而标签补全是**懒绑定**（首次 focus 才 `TagSuggest.bind`）。表现就是"浮层永远弹不出来"，看着像产品 bug，其实是测试环境。判据：给 `TagSuggest.bind` 打桩数调用次数（`focus()` 后 0 次、补一次 `dispatchEvent(new FocusEvent('focus'))` 后 1 次）。**真人用鼠标点进去一定会发 focus**，所以这是补环境的缺口，不是绕过缺陷。
2. **`evalcdp.mjs` 的视口只有 ~764px 宽**，右栏在那一档没有布局：元素 rect 全是 0、`focus()` 无效。凡是依赖侧栏/浮层定位的行为断言，都用 `scripts/agent/geom.mjs <url> 1600 @expr` 钉一个桌面宽度跑（geom 已支持 `awaitPromise`，能跑 async 表达式）。
3. **要断"中间态"的探针必须分两趟跑，中间由 Python 查磁盘**。收件箱 purge 的"确认词写错 → 不该删"合成在一趟里时，第二次（正确词）尝试紧接着把文件删了，Python 检查永远看到最终态 → 那条断言恒假（第一版就这么假红过）。
4. **破坏性探针一律排最后**。第一版把删除排在看板抽屉之前，等抽屉去 `/tags` 时承载「渲染」标签的两篇文档已经进 `_trash/`，标签云里没那个胶囊 → 6 条集体假红。
5. **Python 字符串里写 JS/CSS 常量必须 raw**。`\n` 会被 Python 先吃掉，落到页面就是未闭合字符串 —— 这就是 §6 第 32 行那个"从来没生效过"的成因，而且它能潜伏多年全靠"没人点过那个图"。
6. **对照组不能省**：注入类逻辑要同时断"该注入的注入了"和"不该注入的没注入"，否则"无条件注入"也算绿（`has_mm = True` 变异就是专门用来验这条的）。
7. **别用 `grep` 读中文测试输出**：控制台是 GBK，中文断言名会花屏，`grep "状态栏"` 找不到 ≠ 没失败。落文件后用 `io.open(..., encoding='gbk', errors='replace')` 读，或只看退出码。
8. **一次只跑一个浏览器套**：P5 / js_props / ui_behavior 都要起 headless Chrome + 临时实例，并发会互相顶红（本轮又踩到一次输出交错）。
9. `content/小说/` 不读、不写脚本、不再提议（用户定的边界，AGENTS 禁区）。本套所有语料都是 `tempfile` 现造的合成样本。

收件箱探针加第三段（勾两篇 → `.sel`/计数/按钮三态 → 批量归档填目标目录 → **两篇真的落盘** →

- `store.add_inbox_ignore` 要求"rel 本身就是目录"（注释原话），前端也照这个发；
- 路由却在中间又 `rsplit` 取了一层父目录 —— 同一个动作算了两遍，于是"忽略 `_inbox/开发产物`"

1. 每个作业前清 origin 存储 + cookies —— 原来"每趟新 profile"白来的干净态现在要显式给；

**两条新坑（台账 §6 第 44/45 行）**：
1. **写在 Node 接管 stdin 之前的作业会被静默丢掉** —— 表现为"套件卡在第一个探针"（不是红，是挂）。

   比事后到处 print 快得多 —— 这次两轮就定位了。

## 再补 · 轮次 34：门禁提速第二档 —— 把「睡够」换成「等到」（P5 197.6s → 73.3s，第 13 套 → 156s）

**改法**：新增 `scripts/agent/quiesce.mjs`（shot 与 geom **共用一份**），把「睡 N 毫秒」换成「测到静默为止」：

   有常驻 canvas 动画的页面不能照搬（那会 DOM 静默而像素一直变）。
2. 计数器必须拼在调用方 `init` **之后**（document-start 脚本按注册顺序执行）：
   反了的话探针自己的 fetch 桩被短路时计数永不归还 → 每次都打满上限 = 改了等于没改。

## 再补 · 轮次 35：`evalcdp` 也换成「等到」（js_props 40.1s → 31.5s）—— 附一条"改快了但读错时刻"的教训

**量**：`test_js_props.py` 的 40.1s 里 39.0s 是 4 次 `evalcdp.mjs` 调用，而 evalcdp 是无条件
`await sleep(WAIT)`（js_props 传 6000ms × 4 = 24s 纯睡眠），根本没有"加载完了"的信号。

**第一版直接失败**：只把睡眠换成 `readyState complete` + DOM/字体静默 → **js_props 红 22 条**
（`got {}`、最后 `KeyError: 'roundtrip'`）。原因：`evalcdp` 用 `/json/new?<url>` 开标签页，
导航已经在飞，此时 `document.readyState` **一上来就是 `complete`**（拿到的是导航前的空文档），
于是求值跑在 `app.js` 之前。

> 教训一句话：**静默判定必须建立在一个真正的加载信号之上**；否则"等得更早"读的是更错的时刻。
> 这也是为什么第二版没有沿用 readyState，而是改用 `Page.loadEventFired`。

**第二版（可用）**：先开 `about:blank` → `Page.enable`/`Runtime.enable` → **先挂 `Page.loadEventFired` 监听**
→ 再 `Page.navigate`；`load` 事件为主，`WAIT` 降级成上限（`Promise.race`，事件不来就退回旧等法，不会更差）；
之后才走 `quiesce.mjs` 的静默判定。
一条限制如实写进源码注释：这里**挂不上在途 fetch 计数器**（标签页一开就开始加载，document-start 来不及），
`quiesceJs` 对缺席计数器按 0 处理，所以判定只剩「字体 + DOM」—— 对静态阅读器页面够用。

**验证**：47/47 绿，连跑三次 32.3 / 31.2 / 31.6s；另外把第 13 套的一次一档回退
（`KB_BEHAVIOR_SESSION=0`）重跑一遍 11/11 绿，确认轮次 34 给 geom 一次一档加的静默判定没把回退路走坏。

**门禁链现状（本机串行实测）**：ui_behavior 156s、P5 70.5s、properties 39.3s、js_props 31.5s、其余约 30s
→ 合计约 **325s**（轮次 32 结束时约 700s）。

**下一档别再打「砍判据」的主意**：cProfile 定位 `properties` 的 39.3s 主要是 722 个临时目录的 rmtree
（`nt.unlink` 3377 次 ≈ 12s，Windows 删除延迟）+ 每条性质 240 个随机样本的真算力。
能做的是「把互相独立的几套并行跑」或「把 js_props 的 4 次调用并进会话档」，
**减样本数 = 减覆盖**，不算优化。


## 再补 · 轮次 36：门禁并行化（非 UI 提交 110s → 83.8s），并行只给「不需要浏览器」的那一组

**为什么还慢**：前几档把等待压掉之后，链上是 9 条纯 Python 套件在串行排队（约 67s），

**为什么不一起并行**：三个吃浏览器的套件（js_props / P5 / 第 13 套）判的是**像素与

**实现要点**（`.githooks/pre-commit`，POSIX sh）：
- 统一入口 `step <名字> <命令…>`；`KB_GATE_PARALLEL` 默认 4，**=1 就是老行为**（逐条串行、日志直出）。

- **按空位放行，不是攒批等最慢的**。第一版攒批被实测打脸：reader 真实 10.7s，报表写 41s，
  因为它和 40s 的 properties 同批被等；改成分配额 + `reap`（谁的 rc 出现就收谁）后报表才是真耗时。

**验证**：`sh -n` 过；**故意注入一条必失败的 step** → exit=1、点名 `gate_fail_probe`、回放日志尾部、
并提示「怀疑并发就用串行档重跑」，确认失败路径可用后才撤掉探针；干净运行 all green。
实测：非 UI 提交 **1m23.8s**（Python 组 67s → 41s，卡在 properties 的真算力上）；

**没有一起动的**：`ci.yml` 仍是串行清单（GitHub runner 核数少且不可控，并行省不了多少还要冒假红的风险）；
