## 0. 全局偏离

### 0.1 阶段顺序改为「先三期、后二期」
- **任务原序**：§1 二期拆分 99 篇 → §2 三期速答压缩 108 篇。
- **实际执行**：先三期速答压缩，再按队列顺序做二期拆分。
- **理由**：二期每篇需从零撰写 3–12 篇全新词条，99 篇合计约 600+ 新文件，在本次会话可获得的工时内**不可能保质完成**；若照原序执行，会在二期前几篇耗尽预算，三期 108 篇一篇都动不了。三期是**有界、可机器验证、单行改动、零风险**的确定性收益。先做完三期，等于把一块可以 100% 收口的资产先收口，再把剩余工时投给二期。
- **代价**：二期完成度不保证全清，未完成篇数会在 final-report 里如实列出，不虚报。

### 0.2 `source_path` 取不到「taxonomy display path」（v1.2 §3 有缺陷）
- **任务与 v1.2 §3 要求**：新建子词条的 `source_path` 取该子域在 `content/_meta/taxonomy.json` 中的 display path。
- **实测**：taxonomy 的 `domains` 只存短标签（`software-engineering: "软件工程"`），**没有** `开发术语 / ` 这一级前缀，无法直接当 display path 用；且同一子域内存量稿分裂成两种写法（software-engineering 11 篇 = 5 篇「开发术语 / 软件工程与测试」+ 6 篇「开发术语 / 软件工程」，恰好与导入批次 09-05 / 09-12 完全重合）。"镜像同子域兄弟条目"因此不是良定义。
- **自决**：**一律继承父文档的 `source_path`**，与 §3 已定的「`collected` 继承父文档」同源同策，保证拆分产物与父文档同批次一致。已用该口径落盘 testing 2 篇、software-engineering 3 篇。
- **待人工**：v1.2 §3 的这条应改写为「继承父文档」，或补一层「短标签 → display path」映射表。

### 0.3 grandfather 判据用的是「末次提交早于 e611848」，存在自失效风险
- **风险**：任一已豁免的存量稿若因**别的原因**被改动一次，其末次提交即跳到门之后，⑨ 会从 WARNING 静默变回硬 FAIL，而改动内容与速答无关。
- **本次自决**：按任务指定口径实现，未擅自改成稳定判据（`git show e611848:<path>` 的快照字数）。三期压缩正好会把这一批文件全部改写一次——**压缩完成后这些文件的 🎯 已 ≤150，即使失去 grandfather 也应继续 PASS**，风险因此被三期工作本身消化掉。
- **待人工**：若后续仍有文件因无关改动而 ⑨ 转红，改用快照判据。
