## 1. 折叠式枢纽信号②b 收紧（修订 v1.1 §2）

v1.1 的 ②b 只验结构：核心机制节内 ≥3 个粗体领起列表项、各带 ≥70 字叙述，配上信号①即拿 3400 豁免。实测出洞——`baike/testing/Playwright 与 Cypress.md`（叶子工具词条）在 2775 字时以"②b 粗体项 6"PASS，它根本不是枢纽。**任何词条只要把「核心能力/做法」写成 ≥3 条粗体 bullet 再配一张 ≥4 行的表，就能把 2200 偷成 3400。**

**定案**：②b 的每一项须同时满足三条才计入豁免信号：

1. 由 `- **<子概念名>**：`、`- **<子概念名>：**` 或 `N. **<子概念名>**：` 领起；
2. 该项自身叙述 ≥70 字（`check_rewrite.BOLD_ITEM_MIN`，不含表格行与代码围栏，口径同 v1.1）；
3. **该项叙述内含 ≥1 个 `[[双链]]`**。

理由：枢纽的**定义性特征是索引子词条**。叶子词条的粗体列表是在罗列自身能力，不会也不该指向别人；真枢纽必然把每个子概念链出去。故双链是把②b 从"结构测试"升级为"语义测试"的最小充分条件。

**影响面（2026-09-19 全库 432 篇实测）**：现行获 3400 豁免的 36 篇，收紧后 **36 篇全部保留、0 篇跌回 2200 而新增 FAIL**。即这是一道**零回归的护栏**——只挡住未来新写的套用者，不追溯既有稿。

> 附带事实修正：v1.1 §2 称"取 70 让 ESB 这类（3 项达标）过"。实测 `middleware/ESB 与服务网格（Service Mesh）.md` 的核心机制粗体项**不含双链**，且全文无 mermaid、最大表 <4 数据行，因此它在 v1.1 下也从未真正拿到 3400（正文 2198 是压着 2200 写的）。该 motivating case 的名额由 `Agent 架构模式详解`（①mermaid ②a=3）与 `软件测试完全指南`（①表8行 ②a=4）这类 **②a 达标**的枢纽承担。**②a 与②b 的关系不变，但 §2 的举例作废，以本条为准。**

## 2. 判据第 4 档：父汇编未收敛时的先行立条（补充 v1.1 §1）

v1.1 §1 的三档隐含前提是"子概念的归口要么已存在可双链，要么不存在"。二期首篇遇到第四种：**归口存在于一个本身仍在 `split-candidates.md` 队列里、尚未收敛的父汇编中**。

实例：拆 `软件测试完全指南` 时需立 `E2E 测试` 与 `Playwright 与 Cypress`，但 `testing/01 - 测试基础.md` 已有 `## 端到端测试（E2E）` 节、`testing/02 - 测试工具.md` 已有 `## Cypress`／`## Playwright`／`## Selenium WebDriver` 三节——而这两篇都是 `split` 状态。按原三档判据，"已有专条"该走双链不新建，但那两处是**未收敛的汇编章节、不是词条**，双链过去等于把枢纽指向一堆待拆的原料。

**定案（第四档）**：

| 情形 | 处理 |
|---|---|
| 子概念归口存在于**仍在拆分队列中的父汇编**里 | **允许先行立条**：现在就新建独立词条，不等父汇编收敛 |

**登记纪律**：立新条时必须在 `docs/refactor/split-candidates.md` 的**重叠去重队列**追加一对（冲突 + 预案），预案动词写"父汇编拆分时删除该节、改双链指向新词条"；并在**新立词条所在** status 行的备注登记：

```
pending-merge: <父汇编路径>
```

登记在新词条行而非父汇编行，是因为一个父汇编可能牵出多条先行立条，挂在父行会互相覆盖；挂在新词条行则一条一行、天然可反查。

**收尾复检**：轮到拆某个父汇编时，`grep -rn "pending-merge: .*<该汇编文件名>" docs/refactor/status/` 找出全部指向它的先行立条，逐条确认该汇编里对应章节已删除并改双链，然后清掉 `pending-merge:`。仍有未清的 `pending-merge:` 指向自己时，该汇编**不得判 done**。

### 2.1 配套操作纪律（2026-09-19 实测补入）

合并类预案（如去重队列第 5 对）会**删除或改名文件**，而 `[[双链]]` 是按文件名解析的，删一个被指向的页面会当场造出悬空链。两条纪律必须与删除动作同批执行：

**纪律一：删除 / 改名前必须先扫并重指向入站双链。**

```sh
# 1. 先扫（必须在动手之前跑，不能事后补）
grep -rl "\[\[<原文件名（不含 .md）>\]\]" content/
# 2. 把命中的每个文件里的 [[原文件名]] 重指向新目标或父枢纽页
# 3. 确认无残留后，才执行 git mv / 改名
```

不做的后果：`content/_trash/` 被 `.gitignore` 排除、不进索引树，所以软删除一个被 19 篇引用的页面 = 立刻造出 22 条悬空链，且 `check_rewrite.py` 的 ⑧ 是朴素正则、还会把它和围栏内 bash 混在一起，只能靠 `index.db` 的 `links.resolved` 兜底——等于把可预防的事故留给收尾去查。**删除/改名后的收尾复检必须重建索引并查一次 `resolved=0`，预期为 0。**

**纪律二：`git mv` 到 gitignore 目录后，立刻把该文件从索引撤出。**

```sh
git mv "content/baike/<子域>/<文件>.md" "content/_trash/<文件>.md"
git rm --cached "content/_trash/<文件>.md"      # 只动索引，磁盘副本原样保留
```

`git mv` 会绕过 `.gitignore` 把目标以 `A` 状态塞进暂存区（`.gitignore` 只对未跟踪文件生效）。不撤就会把语料衍生物提交进库，违反 AGENTS.md 不变量 3/禁区；撤了之后 `.gitignore` 恢复生效，git 历史里的删除记录仍是第二重保险，符合不变量 4。

**机器门**：`check_rewrite.py` **不设重复检测**，故先行立条不会报任何"重复"警告（v1.0/v1.1/v1.2 一致）——去重完全靠本节的重叠队列登记与收尾人工核对，不靠工具。

## 3. 拆分新产物的 frontmatter 模板（新增条款）

**定案：一律继承父文档的身世字段，不引入新口径、也不试图"查子域标准值"。** 由二期拆分/新建的词条，frontmatter 按下列模板生成：

| 字段 | 取值 | 理由 |
|---|---|---|
| `title` | 新词条名（= 文件名去 `.md`） | — |
| `source` | `"baike"` | 身世不变，它仍是百科术语；`knowledge`（知识库自产）留给用户自写的长文，不用于拆分产物 |
| `source_path` | **继承父文档的 `source_path`** | 2026-09-19 裁决：原口径"取 taxonomy display path"不可执行——`taxonomy.json` 只存子域短标签（`software-engineering: "软件工程"`），没有 `开发术语 / ` 这一级；且同一子域存量稿已分裂成两种 source_path（software-engineering 11 篇 = 5 篇「开发术语 / 软件工程与测试」+ 6 篇「开发术语 / 软件工程」，与导入批次完全同分布），"镜像兄弟条目"不是良定义。继承父文档与 `collected` 同源同策，保证拆分产物与父文档同批次一致 |
| `collected` | **继承父文档的 `collected`**（不填拆分日） | 保持语料历史一致性；拆分日是工程动作，不是知识获取时间 |
| `status` | `"imported"` | 与批量重写稿一致，后续统一治理时同批处理 |
| `tags` | `[]` | 留空，避免从父文档继承造成标签污染；标签治理另走 `scripts/govern_tags.py` 的 dry-run 流程 |

**禁止**：为拆分产物发明新 `source` 值；把 `collected` 填成拆分日；从父文档复制 `tags`；**按子域名去 taxonomy 反查 source_path**（已证实查不到可用值）。

**实例**：`algorithms/时间复杂度.md` 等 10 篇按此落盘。**2 篇已回改**：`testing/E2E 测试.md`、`testing/Playwright 与 Cypress.md` 初版误按"镜像同子域兄弟"取了 `开发术语 / 测试与质量`，2026-09-19 裁决后改回继承父文档的 `技术文章 / 编程语言`（父文档 `programming-languages/软件测试完全指南.md` 即此值）。

> **为什么不冲突**：`source_path` 在代码里只作展示用的"原始位置"（`app/app.py`），分类树的权威仍是文件路径 + `content/_meta/taxonomy.json`（AGENTS.md 不变量 5）。所以继承父文档不会把文件放错架子，只是忠实记录身世；本条不新增也不改动任何子域。

## 4. 面试速答长度：≤150 字 + 机器门⑨（修订 v1.0 §2）

v1.0 §2 定 🎯 一句话速答为 30–60 字。实盘全库 331 篇 PASS 稿中，**221 篇 ≤150 字、110 篇 >150 字**，而 30–60 字几乎无稿达到——30–60 字装不下"定义 + 取舍 + 关键词"三件事，规范与实盘长期背离且无门约束。

**定案**：

- 上限改为 **≤150 字**（`> 🎯` 首行去掉全部空白后的字符数）。
- **加入机器门 ⑨**：`check_rewrite.py` 提取正文所有 `> 🎯` 首行，任一超 150 字即 FAIL。
- **无 `> 🎯` 行的不报 ⑨**——该情形由 ③（缺必备 H2「面试速答」）或人工抽查覆盖，⑨ 只管长度，不兼职查存在性。

**存量冲击（必须知情）**：⑨ 生效后全库由 **331 PASS → 223 PASS**，**108 篇原已判 done 的稿子仅因 ⑨ 一项转 FAIL**（分布集中在 `ai-and-llm/` 42、`machine-learning/` 25、`algorithms/` 21、`data-science/` 11、`middleware/` 8、`cs-basics/` 1；最长 296 字：`machine-learning/《AI时代生存指南》第二章.md`）。②b 收紧贡献 0 篇新 FAIL。

**处置定案：⑨ 带 grandfather（2026-09-19 实施）**。默认模式下，同时满足两条的存量稿超标只报 **WARNING**、不 FAIL：

1. 在 `docs/refactor/status/sN.md` 中状态列**恰为 `done`**（`done-hub` / `split` / `exempt-reference` 不豁免——它们是 v1.2 之后的产物）；
2. 该文件的**末次提交严格早于 `e611848`**（⑨ 门落盘的 commit）。

即：**v1.2 之前的存量享受追溯豁免，v1.2 之后新写的稿子一律硬 FAIL**——包括二期拆分新建的子词条、被改写的枢纽页、以及任何未在台账登记 `done` 的路径。这样既不必为补一道门而回修 108 篇，又保证"从现在起写的每一篇"都达标。

**三期清账**：`--strict` 关闭 grandfather、恢复全量硬 FAIL。上述 108 篇就是三期的工作清单，修法是**只压缩 🎯 那一行**（保留定义 + 关键取舍 + 双链，通常能砍掉一半），严禁借机重写全篇、严禁改 frontmatter；每修一篇，其 status 行备注追加 `v1.2-⑨: <原字数>→<新字数>`。

## 8. 信息不重复承载 + 双链核对（修订 v1.0 §4 篇幅预算）

二期拆枢纽页时反复出现同一现象：**正文「核心机制」逐条讲了子概念，紧接着索引表又把同样几条列一遍**，于是表格与散文互为复述，篇幅成倍膨胀——实测 `OpenAPI 规范` 首版 2400/2200、`架构模式` 类汇编改写时同样容易顶到上限。规范原本只给字数上限、不给"怎么不超"的方法，执行者只能靠事后逐句砍，既低效又容易砍掉真信息。

### 8.1 信息不重复承载

**同一子概念的实质内容，只能由表格或散文其中一处承载**，另一处降级：

| 情形 | 处理 |
|---|---|
| 核心机制节已用**对比表 / 子词条索引表**呈现若干子概念 | 正文**不再逐条复述**这些子概念的定义与要点，只保留表格覆盖不到的东西：判据、因果、为什么、易错点 |
| 正文已对某子概念展开详述 | 表格中该行**只作速查摘要**（一短语 + 双链指针），不重复承载其内容 |

推论两条：**散文里出现"第一…第二…第三…"的平行枚举，且每项都会成为表格一行时，应删散文保表格**（表格更省字且可扫）；反之，需要解释"为什么"的内容不该塞进表格单元格，那会让表格既长又难读。枢纽页的正确形态是**表格负责"有什么"，散文负责"为什么这样选"**。

**验收口径**：枢纽页 ≤3400、普通词条 ≤2200 是结果而非手段。若超限，先查是否有表格与散文重复承载同一信息，删重复优先于压句。

### 8.2 新建双链前必须做**概念级**查重

拆分时大量引用别的子域，两类错误都会出问题：

1. **链到不存在的名字**（把 `HTTP协议` 写成 `HTTP 协议详解`）——靠 `ls` 能防：
   ```sh
   ls "content/baike/<子域>/<目标名>.md"
   ```
2. **概念已有专条但名字不同**——`ls` **防不住**。实测教训：按 `CDN` 查 stems 未命中便新写一篇，而 `network/内容分发网络.md` 早就是 done 专条，等于凭空造出重复词条。**建链/新建前必须先做概念级查重**：
   ```sh
   # 用同义词、中英文名、缩写逐个扫，命中即改链、不新建
   grep -rlI --include=*.md -e "CDN" -e "内容分发" content/baike/
   ```
   判据：**"有没有人在讲这件事"优先于"有没有文件叫这个名字"**。名字不同而概念相同 → 改链到已有专条；确属新概念 → 才新建。

**第三条硬性规则：双链目标名禁止包含 `/`。** 概念名自带斜杠时（`CI/CD`、`TCP/IP`、`OAuth 2.0/1.0`），**统一改用 `-`（`CI-CD`）后再命名文件与建链**。原因：文件名含斜杠无法落盘，而不含斜杠的文件名配上带斜杠的链名就会静默悬空——实测 `构建流水线与 CI/CD 工具` 这条链就是这么断的（文件只能叫 `... CI-CD 工具.md`）。`check_rewrite.py` 的 **⑧ 已就此升级为硬 FAIL**（2026-09-19 实测全库 0 处存量，零回归）。

`check_rewrite.py` 的 **⑩（warning 级）** 已把这条做成机器辅助：悬空双链若能按"括号别名 > 词条名 > 定义段 > 正文提及"四档在库内对上（同级按该词首次出现位置排序，专条会开篇定义它），会提示"疑似已有专条 <路径>"。**它是提示不是判决**：命中后要人工确认改链还是确属新词。

收尾复检仍按 §6 走 `index.db` 的 `links.resolved`，预期 0 悬空。

## 9. 报告纪律：commit hash 必须机器生成

收尾报告（`docs/refactor/final-report.md`）每节末尾的 commit hash **一律由 `git log` 自动追加，禁止手写或凭记忆填写**。

```sh
# 本节提交了 N 个 commit，就把最近 N 个自动写进报告
git log --oneline -n <N> --pretty=format:"- %h %s" >> docs/refactor/final-report.md
```

若本节没有提交，显式写一行 `- 本节无提交`，不留空。

**为什么单独立这条**：二期已连续两次凭记忆填错 hash（把 `a0fbd36` 写成 `2f0c0ad`、把 `103d619` 写成 `1ab84b0`），都是在 commit 输出被截断、只看到 `create mode` 行时凭印象补的。报告里一个错 hash 会让人对着不存在的提交复盘，比不写更坏——**而这类错误没有任何机器门会报**。

**配套纪律**：需要 hash 时先跑 `git log --oneline -1` 拿准，再动笔；报告类文本优先用 `git log >> 文件` 追加，而不是手敲。

### 9.1 提交前必须断言台账已暂存

本轮实测出的新流程缺陷：拆分提交 `32bd92c` 时，台账脚本因括号笔误抛异常、没改到 `s4.md`，而 `git add && git commit` 照常执行，产生了一次"正文已提交、账没跟上"的中间态——v1.1 §8 的"一个文件只准一行、不许漏"出现了空窗。该缺陷不被任何机器门捕获（check_rewrite 只看语料，不看账）。

```bash
git diff --cached --name-only | grep -q "docs/refactor/status/s" || { echo "ERROR: status ledger not staged"; exit 1; }
```

凡本批次改动过 `content/baike/` 下任何词条，提交前必须让这条断言通过：即对应的 `docs/refactor/status/sN.md`（涉及拆分时还有 `split-candidates.md`）**已在暂存区**，否则禁止提交。它防的不是写错，而是"写对了但忘了记账"这种只在收尾才暴露的缺口。
