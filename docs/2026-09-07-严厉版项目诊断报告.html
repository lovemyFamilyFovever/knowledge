总评

这个项目的架构判断是对的，工程纪律在快速退化。「Markdown 唯一事实源 + 派生索引可删可重建」是整 个系统最有价值的一条决策，它让一切 bug 都有退路；软删除 + git 双保险、测试文化、BACKLOG 约束都高于个人项目的平均水准。但 748 行的 app.py 正在变成新的「docs.db」——你逃离了一个数据库单点，却在重建一个代码单点。标签、来源、状态全部硬编码在源码里，等于把「知识分类学」焊死在 Python 字典上；每次调整 taxonomy 都要改代码发版，这违背你自己定下的「语料与代码分离」原则。按当前惯性再迭代三个月，改造成本会翻倍。

01做对了什么 —— 先给信用，批评才有分量

  • 事实源决策正确且被坚持：编辑/收藏/备注全部写回文件系统（frontmatter / sidecar），索引可随时重建。这是正确的第一性设计，多数个人知识库项目死在「数据库和文件两套真相」上，你没有。
  • 派生物哲学一致：indexes/、_inbox/、_trash/ 全部不入库，缓存层清晰。
  • 有测试且有真实断言：38 条 reader smoke + 今日新增 3 条 RAG 断言，行为级而非摆设。
  • 产品克制：图谱视图上线当天因「装 B 无实用」被你砍掉（可恢复），BACKLOG 有「不中途插队」纪律——知道自己不要什么，比知道要什么更稀缺。
  • 性能预算合理：客户端路由切文档 ~20ms、语义查询 ~60ms，对单机工具绰绰有余。

02问题清单 —— 按严重度排序

P1 · 架构债：正在形成单点

严重度问题证据与后果处置建议
P1 app.py 单文件神模块 现约 880 行：工厂 + 15 组路由 + FTS 索引 + 双链解析 + frontmatter 读写 + 回收站全在一个文件。每加一个功能都在同一个命名空间里叠状态，回归面越来越大（今日 0a7dffd 的 500 就是耦合的实证）。 拆为 store.py（语料扫描/frontmatter）、fts.py、views.py（Blueprint）三层，接口不动，一次 2 小时的重构。
P1 分类学硬编码在源码 DOMAIN_LABELS / SUB_LABELS / SOURCE_LABELS / GRAPH_HUES 四张字典写死在 Python 里（app.py 头部约 60 行）。加一个子域 = 改代码；taxonomy Plan A 那次全量 remap 的痛苦会重复。 迁到 content/_meta/taxonomy.json，代码只读不存。分类学是内容，不是程序。
P1 双索引双 watcher，同步机制重复且分叉 FTS（index.db）与向量（rag.db）各有一套「30 秒 mtime 轮询 + 增量同步」，失效判据不同（built_at vs mtime+code_version）。两套索引对「删除」的反应时窗不一致，双链/搜索/语义可能在数分钟内给出互相矛盾的结果。 合并为单一 watcher，一次遍历同时喂 FTS 与 RAG 同步；失效判据统一成 tree-sig。
P1 缺 AGENTS.md：AI 协作无契约 你明确要让 AI 长期参与维护，但仓库没有任何给 AI 的约束文件——不变量（md 唯一事实源、_inbox 流程、索引可删）、测试命令、禁区全靠口头。今天任何一次 AI 会话都可能破坏这些隐含规则。 写一份 AGENTS.md：不变量清单 + 常用命令 + 提交纪律。半小时的事，杠杆极大。

P2 · 健壮性债：低频但真实

严重度问题证据与后果处置建议
P2 依赖未锁定版本 requirements*.txt 全部只用 >=。onnxruntime/numpy 大版本升级历史上多次破坏性变更，重建环境时行为不可复现。 pip freeze 生成 lock 文件；.python 运行时一并锁定。
P2 Markdown 直通 innerHTML，无净化 app.js 用 marked.parse 结果直接注入 DOM。语料是自写的所以风险低，但 _inbox 会收外部来源文档（今天收的履历就是机器写的）——一段恶意 HTML 即可在本地执行。 引入 DOMPurify（可本地化一份 min.js），或 marked 配置白名单。半天工作量。
P2 无 CI / 无提交前自动检查 测试全靠手动跑。reader smoke 曾被 UI 改版打断过（你自己的记忆里写过「UI 改动后需全面测试」的教训），教训没有被制度化。 pre-commit 跑三个测试文件 + python -m json.tool 级别的语法检查；GitHub Actions 一个 20 行的 workflow 即可。
P2 content/ 单盘无异地备份 唯一不可再生资产在 E 盘，git remote 虽有 GitHub 但「写完即 commit」纯靠自觉，push 无节奏。磁盘故障 = 语料清零。 每日定时 git add content/ && git commit && git push（Windows 任务计划 5 行脚本），外加 _assets 云同步。

P3 · 产品与体验

严重度问题说明与建议
P3 语义搜索入口可发现性差 ?前缀 是隐藏知识。建议搜索框旁放「语义/关键词」切换 pill，或在空结果页强引导（已做了一半：结果页有「试试语义模式」，空态有链接——进一步做成默认切换）。
P3 右键菜单方案缺「归档动作」 你的功能清单（移动/复制/粘贴/导出/统计）漏了本项目最常用的动作：复制 [[双链]]、复制 Obsidian URI、新建文档、批量归档 _inbox。已替你补进 BACKLOG，并写死三条设计约束（移动必须级联双链索引、统计走 sidecar、保留软删除）。
P3 「已读/阅读时间」数据模型未定 统计功能动工前必须先定数据归属：建议 sidecar .stats.md 或独立 content/_meta/reading.json，不要写进 frontmatter——那会污染「语料即真相」的 diff 纪律。
P3 career 域的沉淀方式 10 月 1 日离职，27 篇职业文档远不足以承接 10 年经验。建议每周固定 30 分钟「回顾入库」仪式（_inbox → 归档），靠系统而不是靠突击。经验回收的敌人不是工具，是节奏。

03RAG 本次引入的新债 —— 批评不含我自己就是虚假的严厉

  • 自研分词器是长期负债：手写 WordPiece 与 tokenizers 库逐 token 对齐只验证了 today 的三个样本；模型一换（如换 Qwen-Embedding）就全部作废。缓解措施已内置（code_version 机制 + 交叉验证脚本），但正解是等 tokenizers 允许时直接依赖它。
  • rag.db 无 schema 版本表：靠 code_version 间接判断，若未来出现「代码没变、schema 变」的场景会漏判。低成本补一张 schema_version meta。
  • 暴力扫描兜底的复杂度：KNN + IN 过滤回退全量扫描的路径目前测不到（语料小），语料到 10 万块后若触发，查询会从 60ms 跳到秒级。届时应升级 sqlite-vec 的分区或改用分区文件。
  • 今天两次全量重建（~10 分钟）本可避免：tokenizer 语义变更本应在我改 lowercase 的第一次就预见到要失效全量索引——浪费了你的等待时间。

0490 天行动清单

  1. 本周：写 AGENTS.md（P1，半小时）；content/ 每日自动 commit+push（P2，1 小时）；pip freeze 锁版本（P2，10 分钟）。
  2. 两周内：app.py 三层拆分；taxonomy 迁 JSON；合并双 watcher。
  3. 一个月内：DOMPurify 接入；pre-commit + GitHub Actions；右键菜单一期（移动/复制双链/统计入口，按 BACKLOG 约束）。
  4. 三个月内：标签合并/重命名工具（taxonomy 治理闭环）；静态发布再评估（VitePress 导出你已延后，合理，但 90 天后语料翻倍时重议）。

一句话收束：这个项目最危险的不是缺功能，而是「个人项目不需要工程化」的错觉已经在代码里显形。你现在每年在这上面投入的时间越多，上面每一条 P1 的利息就越贵。好消息是：所有 P1 加起来不到两个工作日。
