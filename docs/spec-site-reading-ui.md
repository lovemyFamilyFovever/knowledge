# 评估：把 GitHub Pages 站的界面尽量对齐主仓阅读器（纯读口径）

日期 2026-09-30 · 基准 = 主仓 `workbench.html` 的桌面三栏工作台 · 范围 = 只做读，不做任何写回

## 0. 已锁定的边界

- 发布面仍由 `scripts/publish_site.py` 决定：只发 `.md/.html`，排除 `漫画 / projects / 小说` 与所有 `_` 前缀目录。
- 因此站仓上**不存在**书库（epub/txt/pdf）、收件箱、治理、复习刷题这些对象——它们不是"UI 没对齐"，是根本没有对应内容。
- 静态托管（GitHub Pages）无后端：任何 `/api/*` 驱动的控件一律不做，也不做"看着能点其实没反应"的假入口。
- 不引入本地存储状态（用户已定：纯读）。

## 2. 需要你先定的两个决策

**A. 皮肤基准选哪个。** 主仓默认是「玄青」（普鲁士蓝 `#1f4e8c` × 朱砂 `#b23a2a`），而我这两天搬到站上的「纸墨·夜航」对应的是主仓第 2 套皮肤（朱砂 `#c8331f`）。也就是说现在两边**主色就不是同一个**——"跟主仓一样"到底跟默认玄青，还是保留已经定稿的纸墨？这条不定，后面所有颜色活都白做。

**B. 顶栏缺的那 5 项怎么处理。** 三个选项：① 直接不显示，顶栏只留「阅读 · 术语」+ 搜索 + 主题（我倾向这个）；② 显示但灰掉加注释"仅本地阅读器"；③ 换成读版子集「阅读 · 分类 · 标签 · 搜索」。

**C.（附带提醒）不要照抄文案。** 主仓顶栏/状态栏那些「888 篇已入全文索引」「content/ = 唯一事实源」「request.host」是个人环境信息，公开站上既口径不同（站上 866 篇）也没意义。对齐指版式与控件位置，不是把字搬过去。

## 3. 分档与工作量

| 档 | 内容 | 估工 | 风险 |
|---|---|---|---|
| **1 版面 + 排版对齐** | 三栏骨架与折叠、顶栏读版重排、左树域色点、正文排版逐项 diff、皮肤基准落地 | **2–3 天** | 低。纯 CSS/DOM，Quartz 侧的层叠/特异性坑已蹚平 |
| **2 只读交互补齐** | 右栏目录/标签/双链三页签、搜索浮层改形态 + 域筛选（要动 `publish_site.py` 预生成）、阅读进度条、沉浸模式、只读快捷键 | **3–5 天** | 中。域筛选跨两个仓库；FlexSearch 面板要压过 Quartz 组件 CSS（第 6/21 个 stylesheet 那条老坑） |
| **3 双形态收口 + 回归** | 桌面三栏与现有手机壳在同一插件里按断点分治、补截图回归矩阵（站仓目前没有）、发布管线跑通并线上核验 | **2 天** | 低-中。站仓没有视觉回归基线，第一次建矩阵要人工过一遍 |

合计 **7–10 天**。只做档 1 就能达到"一眼像是同一个产品"，性价比最高；档 2 的域筛选是里面最贵也最容易返工的一块，可以单拎出来再议。

## 4. 明确不做（避免以后又捡起来）

收藏 / 备注 / 编辑器 / 删除 / 移动 / 重命名 / 收件箱 / 标签合并 / 治理 / 复习刷题 / 阅读统计与时长 / 语义检索 / epub·txt·pdf 阅读器 / 任何写回或本地状态。

理由同一句话：**静态托管没有可写的后端，而这几项全部要求写回文件系统**（不变量 1、4）。要它们上线只有一条路——把 Flask 应用本身托管到能跑 Python 且有持久盘的地方，那是另一份方案（Cloudflare Tunnel + Access 最省事）。

## 5. 建议的下一步

先答 §2 的 A、B 两问；我按档 1 出一版**只改站仓插件**的落地（不碰主仓、不碰发布管线），改完照旧推 Pages 让你在手机上和电脑上看实物——评估文档里的判定对不对，看实物比看表准。
